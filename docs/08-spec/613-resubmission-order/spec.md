# Spec 613：再発行のジョブが、失敗し続ける古いイベントの数によらず、新しく失敗したイベントを再発行する

種類：整理　規模：M　ステータス：確定

## 背景と目的

再発行のジョブは、失敗の行を発行の古い順に 500 件まで読んでから絞るため、古い 500 件が失敗し続けると、新しく失敗したイベントは再発行されない。この spec は、再発行するイベントの選び方を、最後の試行の古い順に変える。issue #613。#544（リリースの前の整理）の直下の issue で、#556 の pull request #611 のレビューで見つかった。

再発行のジョブ ※1 は、Spring Modulith 2.1.2 の再発行の操作を呼ぶ。1 回の件数の上限と、再発行中の件数の上限は、どちらも 500 である。ソースで確認した、この操作の振る舞いは次のとおり。

- 読む件数は、1 回の件数の上限と、残りの枠（再発行中の件数の上限から再発行中（RESUBMITTED）の件数を引いた数）の小さい方である（件数を決める処理）。
- 失敗の状態の行を、発行の時刻の古い順に、読む件数まで読む（失敗の行を読む処理の SQL の LIMIT）。
- ジョブの filter（最後の試行から間隔が経過した、処理の回数が上限より少ない）は、読んだ後にメモリで掛かる。読む順と SQL の条件は、外から変えられない。

そのため、新しいイベントより古い失敗の行が 500 件以上あると、それらが毎回（間隔 1 分）読む範囲を占め、新しく失敗したイベントは読まれない。古い行が処理の回数の上限（既定 60、約 1 時間）に達して止めたイベントの表へ移り、500 件を下回るまで、新しいイベントは読まれない。変更前のジョブの再発行のメソッド（`resubmit`）のコメントにある「上限を置いても、古いものだけが読まれ続けることはない」は、この場合に成り立たない。

件数に上限を置く目的は、この spec でも守る。リスナーのキュー（スレッドプール）の上限は 1000 である。キューの上限を超えて渡すと、キューが拒否し、イベントは処理されないまま処理の回数だけが増える。Spring Modulith が、処理の回数を先に増やしてからリスナーを呼ぶためである。

| 含める | 含めない |

| 設計書 `docs/02-設計/backend-architecture.md` の「イベントの再発行」の修正 | 止めたイベントの扱いと、復旧の手順 |
| ジョブのコメントの誤りの修正 | 索引の追加と、DB の構造の変更（マイグレーションなし） |

決定：

- 規模 M とする。振る舞い（再発行の順）を変える不具合の修正で、先にテストを書いてレッドを確認するため。コードは、config のパッケージ（`com.ecsite.config.event`）だけを変える。文書は、設計書も変える。前例は spec 603（整理・M）である。
- 決定 1（選び方）：再発行するイベントは、自前の SQL（jOOQ）で選ぶ。SQL は、イベント記録の読み書きのクラスに置く。
  - 条件：失敗の状態、未完了（完了日時が空）、発行から下限の時間より前、最後の試行から間隔が経過した、処理の回数が上限より少ない。今の filter と同じ条件を SQL に移す。最後の試行は、最後の再発行の時刻とし、なければ発行の時刻とする。
  - 並び：最後の試行の古い順。同じなら ID の順。
  - 件数：500 から再発行中の件数を引いた数。0 以下なら、その回は再発行しない（今と同じ）。再発行中の件数も自前の SQL で数える。
  - Spring Modulith の再発行の操作には、1 回の件数と再発行中の件数を、どちらも上限なしで渡す。filter は、選んだ ID の集合に入っているかだけを見る。
  - 理由：キューに渡す件数と再発行中の件数の上限は今と同じ 500 なので、件数に上限を置く目的（処理の回数だけが増えるのを防ぐ）を守る。最後の試行の古い順なので、新しく失敗したイベントも古いイベントも再発行の対象になる。対象が N 件で増えず、再発行中の件数が 0 のままなら、N/500 を切り上げた回数以内に、全てが 1 回は試行される。再発行中の件数が枠を使う間は、回数が増える。
  - 並行して起きる変化と、重なる実行：
    - 選んでから Spring Modulith が読むまでに、行が変わることがある（新しい失敗、監視が失敗にした行、他の処理での完了）。filter は選んだ ID だけを通すので、ジョブの 1 回で渡す件数は、選んだ件数を超えない。
    - 再発行中への状態の更新が失敗し、その行がその回の再発行から外れるのは、完了した行、既に再発行中の行、止めたイベントの表へ移った行だけである。処理中の行では成功する。
    - ジョブは ShedLock のロックで、通常は 1 台だけが動く。ロックの期限（5 分）の後に前の実行が残っていると、ジョブが重なることがある（設計書の「水平スケール」の注）。重なると、2 つのジョブが別々に枠を数えるので、合わせて 500 件を超えて渡しうる（キューの上限は 1000）。同じ行を重ねて渡すこともある。
    - 重ねて渡したイベントは、リスナーの冪等で吸収する。根拠は、設計書 `backend-architecture.md` の「水平スケール」の表の「イベント」の行（at-least-once を前提に、リスナーを冪等にする）と、「イベントの再発行」の、処理が重なる場合の記述である。
    - ジョブが重なったときに枠を別々に数えることは、変更前も同じである（変更前は、Spring Modulith が、ジョブの実行ごとに再発行中の件数を数えていた）。
  - 退けた案 1：処理の回数の少ない順。新しい失敗の流入が毎回 500 件を超え続けると、回数の多いイベントが再発行されず、上限にも達しないまま残る。
  - 退けた案 2：1 回の件数の上限だけを大きくする。読む件数は残りの枠を超えないので（背景と目的）、再発行中の件数の上限が 500 のままなら 500 を超えない。再発行中の件数の上限も大きくすると、キューの上限（1000）を超えて渡しうる。
  - 退けた案 3：新しい順と古い順を分けて読む。Spring Modulith の並びは固定で、新しい順は自前の SQL でしか読めない。発行の時刻が中間のイベントは、どちらにも入らず、再発行が遅れる。
- 決定 2（Spring Modulith が読む行の量と、止まるまでの時間）：
  - Spring Modulith は、発行から下限の時間より前の失敗の行を、毎回全て読む（変更前は 500 件まで）。イベントの本文を復元するのは、選んだ行だけである。
  - 処理の回数が上限以上の失敗の行は、ジョブの各回の最初に、止めたイベントの表へ移す処理で移る。自前の SQL も、その行を選ばない（決定 1 の条件）。
  - 1 回に再発行するのは全体で 500 件まで、1 件が止まるまでに 59 回の再発行が必要である（上限は既定 60 で、発行のときの 1 回を含む）。失敗し続けるイベントが N 件で増えず、再発行中の件数が 0 のままのとき、次のようになる（計算による。実行して確認していない）。
    - 500 件以下：約 1 時間で止まる。読む行も、おおむね 1 時間あたりに新しく失敗する件数に収まる。
    - 500 件を超える：止まるまでの時間は約 60×N/500 分に延びる（5,000 件で約 10 時間）。止めたイベントのログとメトリクスが出るのも、その分だけ遅れる。
    - 変更前との比較：変更前は、古い 500 件から順に止まった。変更後は全体が均等に進むので、最初に止まる時刻は遅くなり、全体が止まり終わる時刻はおおむね同じである（どちらも、再発行の合計は 59×N 回で、1 分に 500 回まで）。
  - 1 時間に約 508 件（500×60÷59）を超える失敗の流入が続く間は、失敗の行と、毎分読む行が増え続ける。
  - 読む行に上限を置かない。上限を置くと、選んだ行に届かず、この spec が修正する不具合が戻るためである。Spring Modulith に渡せるのは発行の時刻の上限だけで、範囲で絞る方法では部分的にしか減らせない。
- 決定 3（文書）：設計書の「イベントの再発行」に、選ぶ順（最後の試行の古い順）と、自前の SQL で選ぶ理由を書く。理由は、Spring Modulith が発行の古い順に件数まで読んでから filter を掛けるためである。決定 2 の性質（止まるまでの約 1 時間は、失敗し続けるイベントが 500 件以下のときの値であること）と、イベントの型のクラスが読めない行の制限（Non-goals）も書く。依存しているバージョン（Spring Modulith 2.1.2）と、バージョンを上げたときに確認すること（失敗の行の読み方：件数の上限、並び、filter を掛ける時点）は、1 行で書く。

## Non-goals

| 項目 | 理由 |
|------|------|
| Spring Modulith が読む行を 500 件までに戻す（読む行の数の削減） | Spring Modulith の読み方は外から変えられない（背景と目的）。読む行に上限を置くと、選んだ行に届かない（決定 2） |
| 失敗の行の索引 | この spec では DB の構造を変えない（DN-613-3）。今の走査は ※2 |
| Spring Modulith への、読み方の変更の提案と、バージョンの変更 | この spec は、Spring Modulith のバージョンと実装を変えないため |
| 件数の上限・間隔・時間の下限・回数の上限の値、止めたイベントの扱いと復旧の手順の変更 | 不具合の原因は選び方だけで、これらの値と手順は変えなくても直せるため |
| イベントの型のクラスが読めない行が枠を占める問題 ※3 | 枠を空けるには、その行を更新する機能の追加が必要なので、この spec では扱わず、起票の案にする |

※2：Spring Modulith の 2 つの SQL（再発行中の件数を数える、失敗の行を読む）は、状態の索引がないので、完了した行も走査する。変更前も同じである。自前の 2 つの SQL には未完了の条件を付け、完了日時の索引を使える形にしている。

※3：イベントの型のクラスが読めない行は、クラスの名前の変更や削除の後に残った失敗の行である。Spring Modulith はその行を読み飛ばすので、処理の回数も最後の試行も変わらず、止めたイベントの表にも移らない。自前の SQL は、その行を先頭で選び続ける。500 件あると、何も再発行されない。変更前も、発行の古い順の枠を同じ行が占めた。
