# バックエンドのアーキテクチャ

[constitution](../constitution.md) 第 5〜7、9、10 節の細則。コードの書き方は [バックエンドの書き方](coding.md)、モジュールごとの設計は [docs/backend/modules/](modules) にある。

## 1. モジュラーモノリス

Spring Modulith でモジュールに分ける。デプロイ単位は 1 つ。

| モジュール | 責務 | レベル（第 2 節） |
|------------|------|-------------------|
| `tax` | 税区分と、適用期間付きの税率 | A |
| `catalog` | 商品、価格、公開、カテゴリ、商品検索 | A |
| `inventory` | 在庫数、引当と減算 | A |
| `media` | 画像の受け付け、検証、保存、配信 | B |
| `storefront` | C 側 API。複数モジュールの結果を合成する参照専用の層 ※1 | B |
| `cart` | カート | B |
| `member` | 会員（IdP のアカウントと EC の会員 ID の対応） | B |
| `order` | 注文と状態遷移 | A |
| `payment` | 決済（外部の決済サービスの腐敗防止層） | A |
| `shipping` | 出荷と配送状況（外部の物流サービスの腐敗防止層） | B |
| `notification` | 消費者へのメール（出荷通知） | B |
| `reporting` | データ収集と簡易レポート | B |
| `region` | 都道府県・市区町村・郵便番号のマスターデータ | B |

※1：C 側で複数モジュールを組み合わせるときの循環依存を避けるため。B 側は合成モジュールを作らず、管理画面が複数の API を呼んで組み合わせる。

`shipping` を B にする理由：配送状態は 4 つで、遷移の規則は順位の比較だけ。状態の履歴を見せないので、イベントストア（C）にする理由もない（[出荷モジュール](modules/shipping.md)）。

`notification` を B にする理由：規則は「同じ注文に同じ種類のメールは 1 通」だけで、集約に守らせる不変条件がない（[通知モジュール](modules/notification.md)）。

`reporting` を B にする理由：持つのは他のモジュールの写しと受けたイベントの履歴だけで、業務の状態を変える操作がない（[レポートモジュール](modules/reporting.md)）。

`region` を B にする理由：参照だけのマスターデータで、業務の状態を変える操作がない。業務のモジュールに依存せず、別のサービスに切り出せる形にする（[地域モジュール](modules/region.md)）。

モジュールが外に公開するもの：

| 公開 | 使い方 |
|------|--------|
| `api/` | 同期の呼び出し。呼ぶ側が必要とする形で作り、呼ぶ側は腐敗防止層（`XxxDirectory`）で包む |
| `event/` | 非同期の通知。Spring Modulith のイベント永続化（AFTER_COMMIT） |

- モジュール間の依存は `package-info.java` の `allowedDependencies` で宣言し、`ModulithTest` で検証する。
- モジュールの追加・統合・分割は、先に本書と `docs/backend/modules/` を直す。

## 2. モジュール内のアーキテクチャレベル

複雑さに応じて選び、選んだ理由を `docs/backend/modules/<module>.md` に書く。層とパッケージの名前はどのレベルでも同じ（[バックエンドの書き方](coding.md) 第 1 節）。

| レベル | 構成 | 向く場面 |
|--------|------|----------|
| A. フル | DDD + Clean Architecture + CQRS | 不変条件や状態機械が複雑 |
| B. 簡略 | domain は振る舞いの少ない型でよく、Spring などに依存してよい。集約ごとのパッケージと CQRS は要らない | ルールが単純、または参照のみ |
| C. イベントストア | Event Sourcing ※2 | 状態の変化の履歴に価値がある |

※2：採用する前に、plan で保存方式・スナップショット・read model を説明し、本書を直す。

レベル A のルール：

- 依存の向き：presentation → application → domain ← infrastructure（domain は何にも依存しない）。
- ドメインオブジェクトは jMolecules で明示し（`@AggregateRoot`、`@ValueObject`、`@Identity`）、状態の変更は集約のメソッドで行ってドメインイベントを登録する。
- 永続化は `toSnapshot()` で書き出し、Factory で組み立て直す。application が投げる例外は `BusinessException` / `SystemException` だけ。

## 3. モジュール間の連携

- 同期の呼び出しは、参照か、すぐに結果が必要な場面だけ。それ以外はイベント（名前は過去形。例：`OrderShipped`）。
- イベントは集約が記録し（`registerEvent`）、リポジトリが保存の後に送り出す。集約を持たないレベル B のモジュールは、application の service が送り出してよい。理由：保存に失敗したときにイベントだけが出ないようにし、domain を送り出しの仕組みから切り離すため。
- 他のモジュールのテーブルを読み書きせず、外部キーも張らない。
- モジュールをまたぐ整合性は結果整合。強い一貫性が必要な所は spec に書き、plan で方法を決める。

## 4. C 側と B 側

- 同じドメインモジュールを共有し、presentation で分ける（`/api/store/**`、`/api/admin/**`）。Controller と Request / Response は共有しない。
- バックエンドを 2 つに分けるのは、スケール・デプロイの頻度・セキュリティの境界がはっきり異なってから。

## 5. 水平スケール

同じアプリを複数のインスタンスで動かせるように作る。

| 項目 | ルール |
|------|--------|
| 状態 | リクエストをまたぐ状態をメモリに持たない。HTTP セッションとローカルディスクを使わない |
| 排他 | JVM の中のロック（`synchronized` など）を使わず、楽観ロック・条件付き更新・DB のロックで行う |
| ローカルキャッシュ | インスタンス間でずれてよいデータだけ。必ず TTL を付ける |
| 定期ジョブ | 分散ロック（ShedLock、PostgreSQL のテーブル）で、同じジョブを同時に 1 インスタンスだけで動かす。業務の正しさは、分散ロックに頼らず、行ロックと冪等な状態の遷移で保つ ※4 |
| 片付け | 不要になったデータ（期限切れ、処理の済んだもの）は、保存期間を過ぎたら、データを持つモジュールの定期ジョブで消す。他の操作が読み書きする行は、件数の上限ずつ分けて消す ※5 |
| 時刻で切り替わるデータ | 定期ジョブで書き換えず、適用期間を持たせて参照時に判定する（予約公開、税率など） |
| 時刻 | `Clock` を注入して取る。ドメインには `Instant` を引数で渡す |
| イベント | at-least-once を前提に、リスナーを冪等にする ※3 |
| 設定 | 環境変数で上書きできる。秘密情報をリポジトリに置かない |
| 運用 | ログは標準出力に JSON。liveness / readiness、graceful shutdown。コンテナイメージでビルドする |
| マイグレーション | アプリの起動と分け、デプロイごとに 1 回（ローカルは起動時でよい） |

※3：処理に失敗した（未完了の）イベントは、定期ジョブが 1 分ごとに、5 分より前のものを再発行する。起動時の再発行は使わない。注文と在庫の増減はイベントを使わない（[plan 002](../specs/002-cart-and-order/plan.md) 第 2 節）。

- 処理の回数（発行の時の 1 回と再発行の回数）が上限（既定 60、約 1 時間）に達したイベントは、再発行しない。失敗の種類では分けない（繰り返しても結果が変わらない失敗は、リスナーが吸収する）。
- 上限に達して最後の処理に失敗したイベントは、次の回で止めた印（処理の回数を上限より 1 つ多くした値）を付け、種類・イベント ID・リスナー・処理の回数をエラーのログに 1 回だけ出す。イベントの中身は出さない。
- 未完了のイベント（止めたものを含む）と止めたイベントの件数を、再発行のジョブが数え直してメトリクス（`ecsite.events.incomplete`、`ecsite.events.stopped`）に置く。値はジョブを動かしたインスタンスだけが新しいので、インスタンスの最大で見る。
- 止めたイベントは処理を終えていないので、片付けで消えない。扱いはログとメトリクスで気づき、原因を直してから、データベースでイベントの記録の処理の回数を上限より小さく戻す（次の回で再発行される）か、要らなければ記録を消す。上限を上げても再発行される。
- 印はイベントの記録の表（Spring Modulith のもの）に直接書く。Spring Modulith を上げるときは、処理の回数と状態の意味が変わっていないかを確かめる（イベントの記録のマイグレーションの注記）。

※4：ロックの期間が切れた後に前の実行が残っていると、ジョブが重なることがある。ロックは無駄な重複を減らすためのもの。

※5：片付けるデータと保存期間。保存期間とジョブの間隔（既定 1 時間）は設定で変えられる（[環境変数](../dev/environment.md) 第 1 節）。保存期間は、データを使う業務の期限と、個人情報（イベントの記録には購入者のメールアドレスが入る）を長く持たないことから決めた。

| データ | 持つ所 | 保存期間の起点 | 既定の保存期間 |
|--------|--------|----------------|----------------|
| 処理の済んだイベント | `config`（Spring Modulith の記録） | 処理を終えた時刻 | 7 日 |
| 引当 | 在庫 | 期限 | 1 日 |
| 注文手続き | 注文 | 期限（注文になったものも消す） | 1 日 |
| カート | カート | 期限（最後の変更から 30 日） | 0（期限で消す） |

## 6. データとファイル

### 6.1 永続化

| 項目 | ルール |
|------|--------|
| データアクセス | jOOQ。生成コードはコミットしない |
| schema | モジュールごとに分ける。各モジュールは自分の schema の jOOQ の生成クラスだけを使う（ArchUnit で確かめる） |
| 識別子 | UUID |
| 時刻 | UTC の `timestamptz` |
| 同時の更新 | `version` カラムで楽観ロック |
| 金額 | 円単位の整数。値オブジェクト `Money`（`float` / `double` は使わない） |
| 論理名 | テーブルとカラムに、DB のコメントで日本語の論理名を付ける ※4 |
| 列挙 | 列挙の名前を文字で持ち、取りうる値を CHECK 制約で限る。制約と列挙の一致、制約のない列挙の列がないことを統合テスト（`EnumColumnConstraintTest`）で確かめる。列挙の列を足したら、そのテストの対応の表にも足す |

※4：用語集と合わせ、論理名だけを書く（補足はマイグレーションの SQL のコメント）。コメントがないことを統合テストで見つける。

業務番号（品番、注文番号など人が使う番号）と識別子を分ける：

- 業務番号は、主キー・他のデータからの参照・イベント・キャッシュのキー・API の URL に使わない（画面の URL には使ってよい）。一意な属性として持つ。
- 画面・API で変えられない番号でも、DB を直せば付け替えられるようにする。
- 過去の記録には、参照ではなくその時点の値を写して持つ。

### 6.2 Flyway

- スキーマの正本は Flyway のマイグレーション（`backend/ecsite/src/main/resources/db/migration/`）。
- 新しいモジュールの schema は、そのモジュールの最初のマイグレーションで作る。最初の 4 つ（common、tax、catalog、inventory）だけは、1 つのマイグレーション（`common_create_schemas`）で作った。schema の名前はモジュールの名前にする。例外は `order` の schema の `ordering`（`order` が SQL の予約語のため）。
- コミット済みのマイグレーションは変えず、新しいバージョンを足す。バージョンはタイムスタンプ（例：`V202610081400__catalog_create_product.sql`）。
- jOOQ のコード生成と統合テストは、Testcontainers の PostgreSQL に Flyway を流して行う。
- 開発と E2E の seed は `db/seed/` に置き、ローカルと E2E の profile でだけ流す（[使い分け](../../backend/ecsite/src/main/resources/db/seed/local/README.md)）。

### 6.3 ファイル保存

- Amazon S3 互換のオブジェクトストレージ（ローカルと CI は SeaweedFS）に置き、DB にはキーだけを持つ。ストレージは port の後ろに置く。
- アップロードは署名付き URL で、ブラウザからストレージへ直接送る（バックエンドはファイルを中継しない）。

### 6.4 値の置き場所

値は、誰が・いつ変えるかで置き場所を決める（spec 016 の BR-33）。

| 値 | 置き場所 | 例 |
|----|----------|-----|
| デプロイせずに運営者や外部のデータで変わる業務のデータ | データベース（マスターデータなど） | 税率、都道府県、市区町村、郵便番号 |
| 環境ごとに違う、デプロイに関わる値 | 環境変数（設定。[バックエンドの書き方](coding.md) 第 6 節） | 接続先、鍵、mock フラグ、ポート |
| 変えるとコードも変わる業務の規則 | バックエンドの domain の定数 | 分類の深さ、画像の枚数、氏名の文字数 |

- どの値も、正となる所は 1 つにする。画面は値を書かず、API の契約（生成した型と制約）か応答から得る（[フロントの書き方](../frontend/coding.md) 第 2 節）。
- domain の定数を API の契約にも書くとき（入力の長さ、枚数の上限など）は、両者が一致することを契約のテストで確かめる。エラーの文に入れる数は、定数から差し込む（[バックエンドの書き方](coding.md) 第 3.2 節）。

## 7. 認証・認可

### 7.1 認証の方式

| 項目 | ルール |
|------|--------|
| 方式 | IdP（Keycloak）に任せる（登録、ログイン、メールの確認、パスワードの再設定）。画面は OIDC（OAuth 2.0 の認可コードフロー）でログインし、API は OAuth 2.0 の Resource Server として access token（JWT）を検証するだけ |
| アカウント | 消費者と運営者は別の realm。共有しない（運営者が買い物をするときは消費者のアカウントを別に作る） |
| 会員の情報 | 本人の識別（ログイン ID、パスワード）は IdP、購入に使う情報（届け先など）は EC。token の subject で結ぶ |
| IdP の設定 | realm・client・role をファイルに書き出してリポジトリに置く（秘密情報は置かない） |

### 7.2 業務のコードとの境界

- domain と application は Spring Security の型に依存しない。呼び出し元は値（会員 ID、運営者の ID と氏名の写し）で渡す。
- 管理 API の権限は endpoint ごとに `resource:action`（例：`product:write`）で spec に書く。運営者の realm の role として token に載せ、読む処理は 1 か所にまとめる。
- ログインしていればよい操作（自分の権限の一覧）は、権限の代わりに `authenticated` と書く。管理画面はメニューと画面を自分の権限の一覧で出し分け、token を自分で読まない。
- `/api/admin/**` は運営者の realm、`/api/store/**` は消費者の realm の token だけを受け付ける。
- 店舗 API の token の要否も、契約（`store.yaml` の `security`）から起動時に読む。`memberToken` だけの操作は token が要り、空の要件（`{}`）を含む操作と `security` のない操作は token なしで使える。
- 認可は既定で拒む。契約にない店舗 API・管理 API の操作は拒み、それ以外の URL は、通知の口（`/api/webhooks/**`）、mock の口（`/mock-payment/**`、`/mock-carrier/**`）、運用の口（`/actuator/**`）だけを許す。拒むときは 401（認証のある要求は 403）。

### 7.3 公開ネットワークへのデプロイの前提

ローカルと CI の設定のままでは IdP と secret が守られない。デプロイ先を決めるときに、次も決める。

- IdP の本番の構成：管理画面の保護、realm の設定の反映方法、client の戻り先と店舗の URL、メールの送信元
- secret の管理：client の secret、店舗画面の Cookie の鍵（ローカル用の値を使わない）
- HTTPS（店舗画面の Cookie は本番で `Secure`）
- 運用ポート（既定 9080。死活監視とメトリクス）を外に出さない。業務ポート（8080）だけを公開する
- mock フラグ（`ecsite.<モジュール>.mock.enabled`）を立てない。ローカル・E2E・Stripe の sandbox の設定ファイルは本番の jar に入らない（第 8 節）
- 店舗画面を公開する URL（`AUTH_URL`）を渡す。ログインとログアウトの戻り先は、この URL から作る（[店舗画面の構成](../frontend/apps/store.md) 第 9 節）
- 管理画面の本番ビルドに、本番の IdP の値（`VITE_OIDC_AUTHORITY`、`VITE_OIDC_CLIENT_ID`）を渡す
- 注文とカートの URL の総当たりを防ぐ（入口での回数の制限など）。カートと注文の画面は、推測できない ID を知っていることを使える条件にしている
- 決済サービスと物流サービスの通知の受け口（`/api/webhooks/*`）を公開する URL と、受け口の回数の制限を決める。認証はなく、署名で確かめる（第 8 節）
- ログインせずに作るカートの作成の回数を、入口（リバースプロキシなど）で制限する
- 確定していないアップロードを消す期限を、アップロードのバケットのライフサイクル規則で設定する（ローカルは 1 日）
- メトリクスにアラートを置く。少なくとも、止めたイベントの件数（`ecsite.events.stopped`。第 5 節）
- 配布物に、第三者のライセンスの告知のファイルと部品表（SBOM）を付ける

## 8. 外部連携（決済・物流）

- 外部サービスは port の後ろに置き、外部の型やエラーコードを domain / application に漏らさない。
- 無料の sandbox があれば使い、なければ内部の mock にする。同じ port を実装し、mock は外部サービスごとの mock フラグ（`ecsite.<モジュール>.mock.enabled`）を立てたときだけ使う。フラグがなければ本番の実装を使い、その設定が足りなければ起動に失敗する。mock の挙動（成功、失敗、タイムアウト、遅延したコールバック）はテストから操作できるようにする。テストだけで使う操作は本番の mock に置かず、テストで共有するソース（`src/testFixtures`）の、mock を包む実装に置く。
- ローカル・E2E・Stripe の sandbox の設定ファイル（mock フラグとローカル用の秘密情報を持つ）は、本番の jar に入れない。Gradle の `checkBootJar`（`check` から呼ぶ）で確かめる。
- 失敗したときの振る舞い、リトライと冪等性、コールバックの検証方法は spec に書く。
- 外部サービスの失敗は、infrastructure の実装が次の表で分け、外部サービスのエラーは種類が外部サービスのエラーのエラーコードで `SystemException` を投げる（全体の例外の処理が 502 にし、warn のログを出す。[API の規約](../api/conventions.md) 第 4 節）。外部の例外の型は外に出さない。

| 外部サービス | 外部サービスのエラー（502） | 入力の誤り（400） | 予期しないエラー（500） |
|--------------|-----------------------------|-------------------|-------------------------|
| 決済（Stripe） | 接続できない・時間内に応答がない、Stripe の側の故障、回数の制限（`PAYMENT_GATEWAY_UNAVAILABLE`） | — | 認証・権限・要求の誤り（設定かコードの誤り） |
| 画像の変換（imgproxy） | 接続できない・時間内に応答がない、502・503・504（`IMAGE_SERVICE_UNAVAILABLE`） | imgproxy が返した 4xx と 500（ファイルを読めない。`IMAGE_CONVERSION_FAILED`）※6 | URL の署名の失敗 |
| ファイル保存（S3） | 接続できない・時間内に応答がない、5xx（`IMAGE_SERVICE_UNAVAILABLE`） | — | 5xx でない失敗（権限、バケットがないなど） |

※6：imgproxy は壊れたファイルに 500 を返すので、imgproxy が応答したらファイルの問題とする。imgproxy の中の故障も 500 なので、その時は「ファイルを確かめる」のメッセージになるが、受け入れる（応答はログに残す）。

- 外部サービスを呼ぶ client には、待つ時間の上限を置く（利用者の要求の中で呼ぶので、上限がないと要求が長く止まる）。上限を超えたら外部サービスのエラーにする。

| 呼び出し | 上限の既定 | 設定 |
|----------|------------|------|
| Stripe | 接続 5 秒、応答 20 秒（1 回の要求ごと。SDK の自動のやり直し 2 回は別） | `ecsite.payment.stripe.connect-timeout`、`read-timeout` |
| S3 | 1 回の試行 10 秒、やり直しを含めた全体 30 秒 | `ecsite.media.storage.attempt-timeout`、`call-timeout` |
| imgproxy | 接続 5 秒、応答 30 秒 | `ecsite.media.converter.timeout`（応答） |
