# Spec 004：開発の基盤の整理

ステータス：確定

## 1. 背景と目的

spec 001〜003 で MVP のコアフローができた。次に、コードと文書をまとめて整理する（spec 004〜006）。本 spec はその土台として、**整理を安全に進めるための規則・テスト・構成**を整える。

- 作業の習慣（エラーの変換の仕方、コメントの書き方など）が、コードの中や会話にしかなく、文書で引けない。見直しで何を確かめるかも決まっていない。
- リファクタリングの安全網が場所によって薄い。店舗画面のサーバーの処理（カート、注文手続き、ログイン）は E2E でしか確かめておらず、管理画面のカテゴリの画面には結合テストがない。カバレッジを測る仕組みもない。
- リポジトリの直下に、Docker の設定が散らばっている。E2E が画面のプロジェクトと同じ場所にあり、バックエンドだけフロントと並びが違う。フロントの 3 つのプロジェクトは、依存を別々に入れている。
- E2E がローカルの画面と同じデータベースと IdP を使うので、ローカルの画面にテストのデータが溜まる。
- プロジェクト自身のライセンスがなく、依存のライセンスの方針もない。
- 文書だけを変えた push でも、CI がすべて流れる。

本 spec の利用者は、開発者とエージェント（対象 D）。**消費者と運営者に見える振る舞いは変えない**（DN-1）。

spec 005（バックエンドの整理）と spec 006（フロントの整理と i18n）は、本 spec の完了を前提にする（ファイルの場所が本 spec で変わるため）。005 と 006 は互いに独立している。

本 spec は**整理の spec** で、機能の spec（001〜003）の AC・US・NFR と番号を混ぜない。整理の目的を DS、完了の条件を DC、非機能要件を DN として、1 から振る（[文書の記号と番号](../../process/notation.md)）。spec の番号（004）とタスクの番号（T4…）は、機能の spec と同じ並びで振る。

## 2. 用語

本 spec で新しく使う開発の用語（カバレッジ、引き継ぎの文書、規則の文書）は、plan で用語集に足す。

## 3. スコープ

P1 は本 spec で必須。P2 は余力があれば入れる。

| # | 目的 | 対象 | 優先度 |
|---|------------|------|--------|
| DS-1 | 作業の規則と習慣を文書で引ける | D | P1 |
| DS-2 | CI が、結果に関わる変更のときだけ流れる | D | P1 |
| DS-3 | ライセンスを明らかにし、依存の方針を守る | D | P1 |

## 4. 目的と完了の条件

### DS-1 作業の規則と習慣を文書で引ける（D / P1）

- **DC-1** コードの書き方とプロジェクトの習慣（層とパッケージ、エラーの変換、入力の検証、命名、コメント、テスト、フロント）を、主題ごとの文書で引ける。各規則には、確かめ方（自動の検査か、見直しで読むか）が書いてある。本 spec では、今のコードで守られている習慣を書き出す。spec 005・006 で決める規則は、その spec で足す。
- **DC-2** エージェントが最初に読む文書に、プロジェクトの skill の一覧（名前と、いつ使うか）がある。
- **DC-3** 引き継ぎの文書は、作った日時と名前の付いた置き場所に作る。新しいセッションは、指示がなければ最新のものを読む。古いものを消すのは利用者で、エージェントは消さない。
- **DC-4** 各 spec の見直しの段階では、DC-1 の文書のうち「見直しで読む」規則の一覧を対照にして確かめる。
- **DC-5** spec・plan・tasks・constitution で使う番号と記号（spec の種類、US・AC・DS・DC などの番号、対象、優先度、文書のステータス、タスクの番号と記号、アーキテクチャのレベル、【提案】）の意味を、1 つの文書で引ける。
- **DC-6** constitution に、spec の 2 つの種類（機能と整理）と、それぞれの書き方（整理の spec は DS・DC・DN の番号を使い、機能の spec の番号と混ぜない）がある。

- **DC-63** README は、全体像と文書の地図、進み具合に絞る。起動・テストの手順、アカウントの表、環境変数の表は、開発の手順の文書に移し、README から地図で引ける。

### DS-2 CI が、結果に関わる変更のときだけ流れる（D / P1）

- **DC-7** CI の結果に関わらないファイル（文書、エージェントの設定と skill、ローカル用のスクリプトなど）だけを変えた push では、CI を流さない。それ以外のファイルが 1 つでも含まれていれば、すべて流す。pull request では、変えたファイルによらず、いつも CI を流す（main に入る前に必ず確かめるため）。どのファイルが「関わらない」かは CI の設定に一覧で書き、constitution には原則だけを書く。

### DS-3 ライセンスを明らかにし、依存の方針を守る（D / P1）

- **DC-8** リポジトリの直下に、プロジェクトのライセンス（MIT）がある。各プロジェクトの設定にも、同じライセンスが書いてある。
- **DC-9** 使ってよい依存のライセンスの方針（許可、条件付き、禁止）が文書にある。有料の版がある製品（データベースの接続の部品、マイグレーションの道具、画像の変換、IdP）は、無料の版の範囲で使うことと、その範囲も書いてある。
- **DC-10** 方針に合わないライセンスの依存（実行時、ビルド時、テスト時のいずれも）が入ると、CI が失敗する。ライセンスが分からない依存も失敗にする。

### DS-4 リファクタリングの前に、テストの網を揃える（D / P1）

- **DC-11** テストを流すと、バックエンド（単体と統合を合わせたもの）と、管理画面・店舗画面のカバレッジの報告が作られ、CI の結果から見られる。基準の値による失敗はさせない。
- **DC-12** 機能の spec のすべての AC に、テスト名で対応するテストがある。テスト名に出ない AC があると、CI が失敗する。テストで確かめられない AC は、理由と一緒に除外の一覧に書く。テスト名の AC 番号は 1 つずつ書く（範囲でまとめない）。
- **DC-13** AC-119（会員が店舗から IdP のアカウントの画面に移れる）を確かめるテストがある。
- **DC-14** 店舗画面のサーバーの処理（カートの操作、カートの引き継ぎとその失敗、注文手続き、ログイン・ログアウト、認証の切れたときの扱い）を、ブラウザーを動かさないテストで確かめられる。
- **DC-15** 管理画面のカテゴリの画面の操作（spec 001 の US-2 の AC のうち、画面で行うもの）を、結合テストで確かめられる。
- **DC-16** 画像の変換と保存の失敗（変換に失敗した、保存先につながらない）のときの振る舞いを、テストで確かめられる。
- **DC-17** テストは、決まった時間を待たない（時計を差し替えるか、条件が満たされるのを待つ）。

### DS-5 リポジトリの構成を揃える（D / P1）

- **DC-18** リポジトリの直下は、次の構成になる。

  | 置き場所 | 中身 |
  |----------|------|
  | `api/` | API の契約（今のまま） |
  | `backend/ecsite/` | バックエンド（フロントの `frontend/<画面>/` と並びを揃える） |
  | `frontend/admin/`、`frontend/store/` | 管理画面、店舗画面 |
  | `e2e/` | E2E（画面のプロジェクトではないので、`frontend/` の外に置く） |
  | `docker/` | ローカルと CI で使うサービスの定義と、その設定・初期化のファイル（IdP の realm とテーマを含む） |
  | `docs/`、`scripts/` | 今のまま |

- **DC-19** 移した後も、ローカルのデータ（データベース、画像、IdP）がそのまま使える。起動とテストは、README と skill の手順で動く。
- **DC-20** フロントの 3 つのプロジェクト（管理画面、店舗画面、E2E）は、1 回のインストールで依存が入る。依存の版を固定する情報は 1 つにまとまる。lint と型チェックの共通の設定を共有する。処理の共有（共通の部品・関数）は spec 006 で行う。
- **DC-21** 今のルールを書く文書（constitution、README、AGENTS.md、モジュール設計書、画面の構成、skill）は、新しい置き場所に合わせる。spec・plan・tasks は経緯の記録なので書き換えない。

### DS-6 E2E とローカルの画面のデータを分ける（D / P1）

- **DC-22** E2E は、ローカルの画面と別のデータベースを使う。E2E を流しても、ローカルの画面のデータ（商品、在庫、カート、注文）は変わらない。
- **DC-23** E2E を流しても、ローカルの画面で使う IdP にアカウントが増えない（会員登録のテストで作るアカウントを含む）。
- **DC-24** E2E は、毎回、決まった状態のデータから始まる。前の実行の残りに結果が左右されない。
- **DC-25** E2E に要るデータと、ローカルの画面で見るためのデータを、別々に持つ。

### DS-7 ローカルの画面を、店として自然なデータで見られる（D / P2）

- **DC-26** ローカルの画面の初期データで、次を見られる。すべてのカテゴリに商品があり、すべての商品に画像がある。注文の状態（spec 002）がそれぞれ 1 件以上ある。在庫切れと残りわずかの商品がある。テスト用の名前（実行ごとの印が付いたもの）の商品や注文がない。

## 5. 業務ルール

なし（本 spec は業務の規則を変えない）。

## 6. 非機能要件

- **DN-1** 消費者と運営者に見える振る舞い（画面、API、データ）を変えない。既存のテストはすべて通る。テストを変えるのは、置き場所の移動と、テスト名の AC 番号の書き方（DC-12）に限る。
- **DN-2** ファイルの移動は、内容の変更と別の commit にする（履歴でファイルを追えるようにするため）。
- **DN-3** カバレッジの計測とライセンスの検査を足しても、CI の所要時間の増加は 1 割以内にする（基準は plan で今の所要時間を測って決める）。

## 7. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| バックエンドのパッケージ・層の名前・共通の値オブジェクト・エラーとメッセージの整理、入力の検証の一元化、API の契約の数値の範囲の補い、コード生成の流れの見直し | spec 005 |
| フロントの共通の部品・関数の共有、画面の処理の整理、i18n | spec 006 |
| 複雑な処理の前のコメントの補い | spec 005・006 の最後（ファイルの移動と削除が終わってから） |
| カバレッジの基準の値 | 将来（MVP では報告だけ） |
| 依存の更新の提案の自動化、既知の脆弱性の検査 | MVP の後に検討 |
| 第三者のライセンスの告知のファイル、部品表（SBOM） | 配布物を作るとき（constitution 16 のデプロイ先と同時） |
| 日本語の文書への中国語の混入の検査 | リポジトリでは行わない（エージェントのローカルの仕組みで、commit の前に行う）。既存の文書の言い回しは、本 spec の見直しで読む |
