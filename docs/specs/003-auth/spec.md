# Spec 003：認証

ステータス：確定

## 1. 背景と目的

**消費者が会員としてログインして自分の注文を照会でき、購入を会員だけにする**（constitution 1）。あわせて、**管理画面と管理 API を、権限を持つ運営者だけが使える**ようにし、公開ネットワークにデプロイできる状態にする（constitution 10）。

- 今は、注文の URL を知っている人なら誰でもその注文を見られ、会員が自分の注文を一覧することもできない。カートもブラウザーごとで、別の端末では続きができない。
- 管理 API に認証がなく、公開ネットワークに出せない。

会員登録、ログイン、メールアドレスの確認、パスワードの再設定は IdP の機能を使い、EC では作らない（constitution 10.1）。本 spec の AC のうち、これらに関するものは IdP の設定で満たす。

AC・US・BR・NFR の番号は、spec 002 から続けて振る。

## 4. User stories と受け入れ条件

### US-22 会員登録する（C / P1）

- **AC-108** 店舗から会員登録の画面に遷移し、メールアドレス、パスワード、氏名で登録できる。会員登録とログインの画面は IdP が表示する。
- **AC-109** 登録済みのメールアドレスでは登録できない。
- **AC-110** パスワードの条件（長さなど）を満たさない登録は拒否される。条件は plan で決める。
- **AC-111** 登録すると確認メールが届く。メールのリンクでメールアドレスを確認するまでは、ログインできない。
- **AC-112** メールアドレスの確認が済むと、ログインした状態で店舗（会員登録を始めた画面）に戻る。会員登録を始めたブラウザーとは別のブラウザーで確認メールのリンクを開いたときは、IdP の画面から店舗に戻り、ログインする。

### US-23 ログイン・ログアウトする（C / P1）

- **AC-113** 店舗からログインの画面に遷移し、メールアドレスとパスワードでログインできる。ログインすると、ログインの前に見ていた画面に戻る。
- **AC-114** ログインしている間、店舗の画面に会員の氏名とログアウトの操作を表示する。
- **AC-115** ログアウトすると、店舗でも IdP でもログインしていない状態になる。同じブラウザーで、パスワードを入れずに再ログインすることはできない。
- **AC-116** パスワードを続けて間違えると、そのアカウントは一定時間ログインできなくなる。回数と時間は plan で決める。
- **AC-117** ログインの状態は、最後に操作してから一定時間（plan で決める）続く。過ぎたら、再ログインする必要がある。

### US-24 パスワードを再設定・変更する（C / P1）

- **AC-118** ログインの画面からメールアドレスを入力して、パスワードの再設定を申し込める。届いたメールのリンクから、新しいパスワードを設定できる。登録されていないメールアドレスでも同じ表示にし、会員かどうかを推測させない。
- **AC-119** ログインしている会員は、店舗から IdP のアカウントの画面に遷移し、パスワードと氏名を変更できる。

### US-25 ログインしてカートを引き継ぐ（C / P1）

- **AC-120** ログインしていなくても、これまでどおりカートを使える（US-14、15）。
- **AC-121** ログインしている間は、会員のカートを使う。会員のカートは会員ごとに 1 つで、どの端末やブラウザーからログインしても同じカートになる（ログインしていないときは AC-73 のとおり）。
- **AC-122** ログインしたとき、そのブラウザーのカート（ログインせずに使っていたもの）に品目があれば、会員のカートに移す。同じバリアントは数量を合算する。移した後、ブラウザーのカートは空になる。
- **AC-123** 移した結果が上限（AC-75）を超える場合は、数量を 10 に切り詰め、30 品目を超える分は移さない。切り詰めたことと移せなかった品目を表示する。販売可能数（AC-76）は移す時点では確認せず、カートの表示（AC-80）に反映する。
- **AC-124** ログアウトすると、そのブラウザーのカートは空に見える。会員のカートは残り、次にログインしたときに使える。

### US-26 会員として注文する（C / P1）

- **AC-125** 注文手続きに進むには、ログインが必要。ログインしていなければログインの画面に遷移し、ログインした後は（AC-122 でカートを移して）カートの画面に戻る。
- **AC-126** 注文手続きは、それを始めた会員だけが操作・参照できる。ほかの会員やログインしていない人には「見つからない」と示し、存在を推測させない。
- **AC-127** 注文の連絡先のメールアドレスには、会員のメールアドレス（確認済み）を使い、注文手続きでは入力しない。注文には、注文時点のメールアドレスの写しを残す（AC-85 のメールアドレスの入力を置き換える）。
- **AC-128** 注文は、注文した会員に結び付く。

### US-27 自分の注文を一覧・確認する（C / P1）

- **AC-129** ログインしている会員は、自分の注文を注文日時の新しい順に一覧できる。注文番号、注文日時、総額、状態を表示する。ページ単位で取得できる。
- **AC-130** 一覧から注文の詳細（AC-93 と同じ内容）に遷移し、キャンセルを申請できる（AC-95、96）。
- **AC-131** 注文の詳細の参照とキャンセルの申請は、注文した会員だけができる。注文の URL を知っていても、ほかの会員やログインしていない人には「見つからない」と示す（AC-94、95 の「URL を知っていれば」を置き換える）。

### US-28 運営者としてログインする（B / P1）

- **AC-132** 管理画面は、ログインしなければ何も表示しない。ログインしていなければ、ログインの画面に遷移する。
- **AC-133** 運営者のアカウントは、会員のアカウントとは別にある（constitution 10.1）。管理画面には会員のアカウントでログインできず、店舗には運営者のアカウントでログインできない。
- **AC-134** 運営者は自分で登録できない。運営者のアカウントは、IdP の管理の画面で作る。
- **AC-135** 管理画面に運営者の氏名とログアウトの操作を表示する。ログアウトと、パスワードを続けて間違えたときの扱いは、会員と同じ（AC-115、116）。

### US-29 権限に応じて操作を制限する（B / P1）

- **AC-136** 管理 API の各操作は、運営者がその操作の権限（spec 001、002 の各 US に記したもの）を持つときだけ受け付ける。
- **AC-137** 認証のない要求（なし、無効、期限切れ）は、管理 API と、店舗 API の会員向けの操作で拒否され、「ログインが必要」と区別できるエラーになる。権限が足りない要求は「権限がない」と区別できるエラーになる。
- **AC-138** 会員のアカウントで得た認証では、管理 API を使えない。運営者のアカウントで得た認証では、店舗 API の会員向けの操作を使えない。どちらも「ログインが必要」と同じ扱いにする。
- **AC-139** 運営者の権限は、IdP で職務（BR-12）を割り当てて与える。
- **AC-140** 職務の付け外しと、アカウントの無効化は、一定時間（plan で決める）のうちに管理 API に反映される。
- **AC-141** 管理画面で権限のない操作をすると、「権限がない」と表示する。

### US-30 操作した運営者を記録する（B / P2）

- **AC-142** 在庫の調整（AC-45 の履歴）、注文のキャンセルの申請の承認・却下、運営者の判断によるキャンセルに、操作した運営者の氏名の写しを残し、在庫の調整履歴と注文の詳細に表示する。

## 5. 業務ルール

spec 002 の BR-6〜11 に加える。

- **BR-12 職務**：運営者に割り当てる、権限の組。MVP の職務は次の 2 つ。職務を追加するのは IdP の設定だけで行え、EC は変えない。

  | 職務 | 権限 |
  |------|------|
  | 管理者 | 全て |
  | 閲覧者 | 参照の権限（`:read`）全て |

- **BR-13 会員の識別**：会員は IdP のアカウントで識別する。メールアドレスは変わりうるので、識別には使わない（constitution 7.1 の業務番号と識別子の区別と同じ考え方）。

## 6. 非機能要件

- **NFR-3** 管理 API は、権限を記していない操作も含めて、既定で拒否する。検査の書き漏れで操作が公開されないようにする。
- **NFR-4** EC はパスワードを受け取らず、保存しない（constitution 10.1）。

## 7. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| ゲストの購入 | MVP の後に検討（constitution 1） |
| ログインせずに作った既存の注文の、会員への移行 | 行わない（本番のデータがないため。開発用のデータは削除する） |
| 注文番号とメールアドレスによる注文の照会（spec 002 の Non-goals） | 行わない（会員は注文の一覧で照会する） |
| 退会（会員の削除）、メールアドレスの変更 | 将来の spec |
| 2 段階認証（会員・運営者とも。ワンタイムパスワード、パスキー） | 将来の spec（IdP の設定で足せ、EC は変わらない） |
| 外部のアカウント（Google など）でのログイン | 将来の spec |
| 会員登録を始めたブラウザーとは別のブラウザーで確認メールのリンクを開いたときに、そのままログインした状態にする | 行わない（リンクを持つ人がログインできてしまうため。IdP の画面から店舗に戻ってログインする。AC-112） |
| ログインの画面の見た目を店舗と揃える | 将来の spec（MVP は IdP の画面にロゴと色を合わせるだけ） |
| 運営者のアカウントと職務を管理する、EC の画面 | 行わない（IdP の管理の画面を使う） |
| 運営者と会員のアカウントの結び付け | 必要になったら IdP の設定で行う（constitution 10.1） |
| 権限のない操作を、管理画面で隠す・押せなくする | 将来の spec |
| 会員の情報（お届け先の保存など）。MVP の注文手続きでは、お届け先を毎回入力する | 将来の spec |
| 管理画面での会員の一覧・参照 | 将来の spec |
| EC からのメールの送信（注文の確認など） | 将来の spec（本 spec のメールは IdP が送る） |
