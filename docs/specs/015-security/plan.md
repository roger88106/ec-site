## 1. 外部サービスの mock フラグ（US-48）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| フラグ | 決済は `ecsite.payment.mock.enabled`、物流は `ecsite.shipping.mock.enabled`。真のときだけ mock を使う ※1 | 統合テスト |
| 決済の選び方 | フラグが真なら mock、それ以外（未設定を含む）なら Stripe。Stripe の設定（鍵）は今の必須の検証のまま | 統合テスト |
| 物流の選び方 | フラグが真なら mock。それ以外なら、物流の設定の検証で起動に失敗させ、フラグの名前を示す ※2 | 統合テスト |
| 今の選択の設定 | 決済の `ecsite.payment.gateway` と物流の `ecsite.shipping.carrier`、その列挙をなくす（AC-230）。mock か Stripe かの条件は、全てフラグで書く | 統合テスト、レビューで読む |
| 設定ファイル | `local` はフラグを 2 つとも立てる。`stripe` は決済のフラグを下ろす。`e2e` は `local` に重ねるので書かない（AC-231） | 単体テスト（設定ファイルを読む） |
| テストの設定 | 統合テストの設定はフラグを 2 つとも立てる。Stripe の実装のテストは、今どおり Spring を使わない | 統合テストが通る |

```yaml
# application-local.yml（抜粋）
ecsite:
  payment:
    mock:
      enabled: true
      base-url: http://localhost:8080
  shipping:
    mock:
      enabled: true
```

※1：決済の mock の設定（`ecsite.payment.mock.base-url`）がすでに `mock` の下にあるので、フラグも `mock` の下に置く。物流も同じ形にそろえる。

※2：物流の本番の実装がないので、フラグがないときに使う実装を作らず、設定の検証で起動を失敗させる。Bean が足りないことで失敗させると、エラーメッセージがフラグの名前を示さないため（NFR-19）。本番の実装を作るときに、この検証を本番の実装の設定の検証に替える。

## 2. 認可（US-49、AC-235、BR-32）

### 2.1 店舗 API

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 正本 | 起動のときに `store.yaml` を読み、操作（メソッドとパス）ごとに token が必要かを決める。管理 API が `admin.yaml` の権限を読むのと同じ形 | 統合テスト |
| token の要否 | `security` が `memberToken` だけの操作は token が必要だ。`security` がない、または空の要件（`{}`）を含む操作は、token なしで使える | 統合テスト |
| 契約にない操作 | 拒む（token がなければ 401、あれば 403）。管理 API と同じ | 統合テスト |
| 契約の読み込み | `admin.yaml` を読む処理から、操作の一覧（`servers.url` を含むパス、具体的なパスを先に照合する並び）を読む部分を共通にし、管理 API と店舗 API で使う ※3 | 単体テスト |
| 手動で並べたパス | 店舗 API の filter chain の、会員の操作のパスの一覧をなくす | レビューで読む |

※3：今の `AdminOperationPermissions` が持つ契約の読み方（`servers.url` の連結方法、パスの並べ方）を、店舗 API で書き換えないため。共通にした型は `config/security` に置く。

### 2.2 その他の URL（業務ポート）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 許すエンドポイント | 決済と物流の通知（`/api/webhooks/**`）、mock のエンドポイント（`/mock-payment/**`、`/mock-carrier/**`）、運用のエンドポイント（`/actuator/**`）、エラーの画面への転送 ※4 | 統合テスト |
| それ以外 | 拒む。ステータスコードは 401（Problem Details の `UNAUTHENTICATED`）。店舗 API・管理 API の拒否と同じ形にする | 統合テスト |
| mock のエンドポイント | パスは常に許し、Controller はフラグが立ったときだけ作る。フラグがなければ 404（AC-229） | 統合テスト |
| テストだけの Controller | 統合テストの設定に、`/api/test-*/**`（エラーの応答の形などを確認する Controller）を許す filter chain を追加する。「存在しないパスは 404」のテストは、そのパスの下で確認する ※4a | 統合テストが通る |

※4：運用のエンドポイントは、業務ポートでは Controller がないので 404 になる（第 3 節）。運用ポートにも同じ filter chain が適用されるので、許すエンドポイントに入れる。エラーの画面への転送を許さないと、許したエンドポイントの 404 が 401 に変わる。

※4a：段階 2 の実装で分かった（plan を書いたときに見落とした）。既存の統合テストのうち、テストだけの Controller を使う 15 件が 401 で失敗した。そのテストの期待値は変えない（NFR-18）。`/api/does-not-exist` の 404 は AC-235 で 401 に変わる振る舞いなので、パスだけを変え、404 の形を確認することは残す。

## 3. 運用ポート（AC-236、237）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 分け方 | 死活監視とメトリクスを、Spring Boot の運用ポート（`management.server.port`）で公開する。業務ポートでは公開しない | 統合テスト（実際のポートで起動） |
| 既定 | `application.yml` に 9080。環境変数 `MANAGEMENT_SERVER_PORT` で変える。E2E は 9090 ※5 | 単体テスト（設定ファイルを読む） |
| 統合テスト | MockMvc のテストは、運用のエンドポイントを業務ポートと同じに置く（運用ポートを業務ポートの番号にする）。運用ポートを分けるテストを 1 つ追加し、実際のポートで確認する ※6 | 統合テストが通る |
| 起動を待つ箇所 | E2E の起動待ち、ローカルの起動待ち（skill `local-dev`、`reset.sh`）、文書の URL を、運用ポートに替える | E2E が通る |
| Windows のポートの予約 | 9080、9090 を `exclude-ports.ps1` に追加する | レビューで読む |

※5：業務ポート（8080、E2E は 8090）と compose のポート（8081、8180 など）と競合しない番号。待ち受けのポートは接続先ではないので、既定値を持たせる（バックエンドの書き方 第 6.1 節）。

※6：既存の運用のエンドポイントのテストを、期待値を変えずに通すため（NFR-18）。

## 4. 画面の設定（US-51）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 管理画面のビルド | `vite.config.ts` で、本番モードのビルドのときに `VITE_OIDC_AUTHORITY` と `VITE_OIDC_CLIENT_ID` を確認し、足りなければ名前を列挙して失敗させる。確認する関数は `src/` の外の TS に置き、Vitest で試す ※7 | 単体テスト |
| 管理画面の既定値 | 開発モードとテストは、今どおりローカルの IdP の値（`oidc.ts`）。本番モードでは既定値に落ちない | 単体テスト |
| ビルドする箇所 | CI の管理画面のビルドと E2E に、ローカル・E2E の IdP の値を渡す | CI、E2E が通る |
| 店舗画面の公開する URL | `AUTH_URL`（Auth.js が読む名前）。本番モードで必須の環境変数に追加する ※8 | 単体テスト |
| ホストの信頼 | Auth.js の `trustHost: true` をやめる。Auth.js は `AUTH_URL` があれば戻り先をそこから作る | 結合テスト ※9 |
| ログアウトの戻り先 | 公開する URL から作り、リクエストヘッダー（`host`、`x-forwarded-proto`）を読まない | 単体テスト |
| 任意の設定 | API の応答を再取得する間隔（`STORE_API_REVALIDATE_SECONDS`）を、設定の 1 か所（`config.ts`）で読む | 単体テスト |
| E2E | 店舗画面に `AUTH_URL`（E2E の店舗の URL）を渡す | E2E が通る |

※7：管理画面の `vite.config.ts` は Node の型の制約で `src/` の TS を読めないため（spec 014 の作業で判明した）。

※8：開発モードとテストでは、今の必須の値と同じく、ローカルの値（`http://localhost:3000`）を既定にする。

※9：Auth.js のリクエストの処理に、別のホストのヘッダーでリクエストを渡し、IdP への移動の戻り先が公開する URL になることを確認する。結合テストで作れなければ、E2E で確認し、tasks を修正する前に報告する。

## 5. ローカル環境と jar（US-52）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| compose のポート | 全ての `ports` を `"${LOCAL_BIND_ADDRESS:-127.0.0.1}:<ホスト>:<コンテナ>"` にする ※10 | CI の検査の script のテスト |
| 他のマシンからつなぐ | `LOCAL_BIND_ADDRESS=0.0.0.0` を環境変数か `docker/.env`（Git に入れない）に書く（AC-247）。手順を開発環境の起動に書く | レビューで読む |
| jar の中身 | `bootJar` で `application-local.yml`、`application-e2e.yml`、`application-stripe.yml` を除外する。`bootRun` とテストは、今どおりリソースから読む | Gradle の検査 ※11 |
| ローカルの profile での本番の起動 | 本番の jar を `local` で起動すると、フラグがないので物流の検証で起動に失敗する（AC-245）。第 1 節と jar の中身の決定から、この振る舞いになる | jar を起動して手動で確認し、レビューの段階で記録する |

※10：compose の `${VAR:-既定}` を使う。名前を `COMPOSE_` で始めないのは、compose 自身の設定の名前と分けるため。

※11：`check` から呼ぶ Gradle の検査で、`bootJar` の中に除いたファイルがないことを確認する。テスト名を持たないので、`ac-exclusions.json` に AC-244 と確認する所を書く。AC-245 も同じく除外に書く。

## 6. mock のテスト用の操作（US-53、P2）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 移す先 | mock の決済の、テストだけで使う操作（次の確定・返金・取消を失敗させる、与信を切れたことにする、確定の途中に処理を挟む、確定・返金・取消の記録、開いた画面の数、状態を削除する）を、テストで共有するソース（Gradle の testFixtures。`src/testFixtures`）の、mock を包む決済サービスの実装に移す。単体テストと統合テストの両方から読む ※12 | 統合テストが通る |
| 本番の mock | 支払画面と、画面の操作に必要なものだけを持つ | 単体テスト（mock の型が、port と画面の操作のほかに公開の操作を持たない） |
| 物流の mock | 状態を削除する操作も同じく移す | 統合テストが通る |

※12：段階 6 の実装で判明した（plan を書いたときに見落とした）。mock の決済の port の振る舞いの単体テストが、与信を切れたことにする操作を使うので、単体テストと統合テストの両方から使える箇所に置く。統合テストのソースから単体テストのソースの全体を読むと、単体テストの Spring の設定クラスまで統合テストの起動で読み込まれるので、共有するものだけを testFixtures に置く。記録の操作も、本番の mock に残すと、公開の操作を持たないこと（AC-246）を満たさないので移す。
