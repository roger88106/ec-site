# 起票と記録の操作

issue と記録を扱う操作の規則。起票するとき、spec を書く・閉じるとき、試作のときに読む。

## 起票

- Dependabot の pull request を除き、全ての変更は issue から始める。
- 後回しにする作業と未決事項は、issue に起票する。対応時期が決まっているものにだけ milestone `1→10` を付ける。spec の Non-goals に「1→10」と書く項目も起票する。完了したら issue を閉じる。
- 起票の時点は次のとおり。

| 時点 | 起票の方法 |
|------|------------|
| spec の途中 | spec（Non-goals、レビューの結果、plan）に記録する |
| spec の最後 | まとめ方の案を pull request に付ける。利用者が承認したら、issue 担当のセッションが、重複を避けて起票する |
| 急ぐ作業（不具合、マージの失敗など） | すぐに起票する |

- issue の本文とコメントは、校閲役に読ませる。対象と時点は、[docs-review.md](../../.claude/skills/review/docs-review.md)の手順 3。新しい用語に名前を付けるときは、[文書の書き方](writing.md)の「用語の選び方」にある造語の手順に従う。

- issue は `.github/ISSUE_TEMPLATE/` のテンプレート（機能・整理・不具合）で作る。コマンドで起票するときも、テンプレートの項目と同じ節を本文に使う。

- spec ごとに追跡の issue を 1 つ作り、その番号を spec の番号とする（[文書の記号と番号](notation.md)）。spec が扱う全ての issue は、`gh api graphql` の `addSubIssue` で追跡の issue の sub-issue に結ぶ。
- issue と spec の対応は、次のとおりにする。

| 対応 | 追跡の issue | 結び方 |
|------|--------------|--------|
| 1 つの issue を 1 つの spec で扱う | その issue を追跡の issue にする | なし |
| 複数の issue を 1 つの spec で扱う | 新しく作る | 扱う issue を、追跡の issue の sub-issue にする |
| 1 つの issue を複数の spec に分ける | spec ごとに新しく作る。元の issue は追跡の issue にしない | 追跡の issue を、元の issue の sub-issue にする |

- GitHub の sub-issue は、親を 1 つしか持てない。親が 2 つ必要になるときは、片方を本文の「関連」に `#番号` で書く。
- 不具合の issue を起票するとき、原因の変更がレビューを通ったか、エージェントがマージしたものなら、label「見逃し」を付ける。「関連」に書く内容は[エージェントの作業フロー](subagents.md)の「モデルや設定を替えるとき」。

## AC 一覧の操作

- spec で AC を追加したら、同じ commit で `node scripts/ci/ac-check.mjs --write` を実行して [AC 一覧](../03-機能仕様/acceptance-criteria.md)に転記し、列「モジュール」に ③ のモジュールの名前か `common` を書く。
- 転記した今の内容は、spec の中だけで通じる参照（※1、事実 2、US の番号など）を書き換える。
- 進行中の spec の AC の文を転記の後に修正したときは、同じ commit で AC 一覧の今の内容も手動で修正する。理由：検査は違いを見つけないため。
- 前の spec の AC を変えた・廃止したときは、AC 一覧のその行の状態、変えた spec、今の内容を手動で修正する。変更の AC の今の内容には、根拠を、文書の名前のリンクの直後に「の「<見出し>」」を続ける形で添える。
- ③ の「今有効な AC」の表は、`--write` で AC 一覧から作る（生成のマーカーがある ③ だけ）。AC 一覧のモジュールや今の内容を書いた・修正した後は、`--write` を再度実行する。
- spec で BR を定義したら、アーカイブに移す前に、③ の業務規則の文に BR の番号を付けて書く（書き方は[文書の記号と番号](notation.md)の「業務規則の番号（BR）」）。
- AC とテストの対応は、`node scripts/ci/ac-check.mjs --tests` で表示する。

## アーカイブの操作

- 完了した 1→10 の spec は、MVP と同じくまとまりごとにアーカイブし、`docs/08-spec/archive/1to10/` に置く（M の spec も同じ）。同じ pull request に含める。理由：後に移すと pull request が増えるため。
- tasks を作るとき、アーカイブに移すタスクを最後にし、spec の最後のレビューと pull request の前のレビューをその前のタスクにする。アーカイブの commit で、そのタスクを含む全てのチェックボックスを `[x]` にする。
- pull request の作成はタスクにせず、spec の最後のレビューの後に draft で作り、URL を追跡の issue に記録する。pull request の前のレビューは draft で行い、指摘に対応して draft を外す。理由：レビュー中に止まっても、作業とレビューの記録が pull request に残るため。
- アーカイブの後、マージの前にタスクを追加するときは、アーカイブのタスクの後に、そのタスクを済ませる commit で `[x]` の行として書く。対象は、[マージと後片付け](merging.md)の「pull request のレビューの対応」の修正や、CI の失敗の修正などである。`develop` を取り込むだけの commit はタスクにしない。理由：進捗の検査が、アーカイブした spec の全タスクの完了を求めるため。

## 構成が決まっていないときの試作

構成が決まっておらず、spec の AC・DC を推測でしか書けないときは、spec を書く前に一時ブランチで試作する。構成とは、節の構成、置き場所、雛形の項目などである。利用者は試作を見て、構成を決める。理由：構成が変わるたびに spec を書き換えることになるため。

| 条件 | 内容 |
|------|------|
| 利用者の同意 | 試作に入る前に、利用者の同意を得る。理由：[AGENTS.md](../../AGENTS.md)の「作業の進め方」にある「tasks にない作業は始めず」の例外のため |
| 起票 | 試作も issue から始める。試作の issue と、構成が決まった後に spec を追跡する issue は分ける |
| ブランチ | `agent/<issue の番号>-trial` の一時ブランチと作業ツリーで試作する |
| push | GitHub の表示を確認するときだけ行う。commit のメッセージに `[skip ci]` を入れる ※ |
| pull request | 作らない。`develop` にマージしない |
| 決まった後 | 構成と決めた理由を、試作の issue のコメントに書く。試作の commit を patch にして `/.local/` に置き、一時ブランチと作業ツリーを削除する |
| 取り込み | 試作の commit は、そのまま取り込まない。spec の tasks で、検査と校閲を通して再度取り込む。理由：試作では、検査と校閲を最小限にするため |

※：一時ブランチでも、push のたびに文書のワークフローが実行されるため。
