# Spec 155：バックエンドのモジュールの構成と依存の向きを整える

ステータス：草案

## 1. 背景と目的

MVP 019 の全体のレビューで、バックエンドの構成（パッケージの大きさ、置き場所、層の間の依存の向き）の指摘が残った。後のバックエンドの spec（テストの補強、決済と設定、使われていないコード）は、本 spec が移すパッケージと衝突する。そのため、本 spec を先に行う。

追跡の issue は [#155](https://github.com/roger88106/ec-site/issues/155) で、扱う issue は #76、#78、#81、#84 である。作業ブランチは `155-backend-structure` である。規模は L で、利用者が 2026-10-23 に承認した。

#84 の「ほか 36 件」は、MVP 019 のレビューの結果のファイルが残っていない。そこで 2026-10-23 に、同じ観点で、今の `develop` のバックエンドを再レビューした。観点は、構成と置き場所、境界と依存である。範囲を 3 つに分け、汎用のモデルで 2 回ずつ実行して和集合を取り、spec 担当のセッションがコードで事実を確認した。

- #76、#78、#81 の項目と、#84 で名前を挙げた 5 件は、今のコードに全て残っていた。
- 再レビューで見つかった新しい指摘は 28 件で、本 spec に含める（第 3 節の DS-155-2〜DS-155-8）。
- 次の 2 件は、規則に合うので除いた。
  - 税の公開の API が、税の計算（domain）を直接呼ぶ。理由：層の依存の表は、公開の API から domain への依存を許すため。
  - 決済の mock の、支払いを済んだことにする操作。理由：決済のモジュールの設計書が、本番に置く mock の操作として定めているため。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。

## 2. 用語

| 用語 | 意味 |
|------|------|
| 層の依存の表 | [バックエンドの書き方](../../rules/backend-coding.md) 第 1.1 節の、層ごとに依存してよい先の表 |
| 腐敗防止層 | 他のモジュールの公開の API を包む port とその実装（バックエンドの書き方 第 1.3 節） |
| テスト専用の操作 | 本番のコードにあり、テストか mock の画面だけが使うメソッドと問い合わせ。テストのために広げた可視性も含む |
| 構成の検査 | ArchUnit と Spring Modulith による、パッケージと依存の自動の検査（`src/test/java/com/ecsite/architecture/`） |

用語集に追加する語は、plan で決める。

## 4. 目的と完了条件

### DS-155-1 共通コード（D / P1）

- **DC-155-1** 設定（`config`）の直下と、その下の各パッケージの `.java` が、パッケージの大きさの目安（10）以下である。目安を超えて分けないパッケージは、バックエンドの書き方 第 1.4 節の表に理由がある。#76 の項目である。
- **DC-155-2** イベントの再発行と片付けのクラスは、設定の下の 1 つのパッケージにある。#76 の項目である。
- **DC-155-3** 共通コードの各クラスは、2 つ以上のモジュールが使う。
- **DC-155-4** 表示順の再採番と、LIKE の検索の文字の扱いは、商品カタログのモジュールにある。理由：使うのが商品カタログだけのため。#76 と再レビューの項目である。
- **DC-155-5** ログインした人の情報を返す操作のクラスは、規則が定める API の入口の置き場所にあるか、規則にその例外と理由がある。
- **DC-155-6** 共通コードと設定がモジュールに依存しないことを、構成の検査が確認する。
- **DC-155-7** モジュールが設定に依存しないことを、構成の検査が確認する。

### DS-155-2 層の依存の向き（D / P1）

- **DC-155-8** application は、同じモジュールの公開の API の型を使わない。対象は注文の見積もり、カート、画像、商品カタログである。#78、#84 と再レビューの項目である。
- **DC-155-9** DC-155-8 の参照の service は application の view を返し、公開の API が view を公開の型に変換する。
- **DC-155-10** 注文のレポート用の公開の API は、集約でなく application の view を受け取って変換する。#78 の項目である。
- **DC-155-11** presentation と application の view は、application の port（参照の Repository と腐敗防止層）の型を使わない。対象は注文と店舗である。
- **DC-155-12** レポートのモジュールで、注文のキャンセルの種類、性別、状態の履歴の状態を、application・port・腐敗防止層・domain の間で列挙として受け渡す。
- **DC-155-13** 公開の API の作り方の規則（バックエンドの書き方 第 1.1 節「公開の API」）が、今の実装と一致する。今の実装では、公開の API は interface を持たないクラスである。
- **DC-155-14** 対象が 0 件で常に通る構成の検査がない。
- **DC-155-15** application が公開の API に依存しないことを、構成の検査が確認する。
- **DC-155-16** presentation と view が application の port に依存しないことを、構成の検査が確認する。

### DS-155-3 モジュールの間の呼び出し（D / P1）

- **DC-155-17** 他のモジュールの公開の API を呼ぶのは腐敗防止層の実装だけであることを、構成の検査が確認する。#84 の項目である。
- **DC-155-18** DC-155-17 の例外は、規則と、検査の許可の一覧の両方にある。例外の例は、要求した会員の ID を得る操作を presentation が使うことである。
- **DC-155-19** 腐敗防止層の実装は全て package-private であり、構成の検査がそれを確認する。#84 の項目である。
- **DC-155-20** 出荷の mock の画面は、通知のモジュールの文言のキーを使わない。

### DS-155-4 設定の値の型と設定のクラス（D / P1）

- **DC-155-21** 出荷、通知、店舗の設定の値の型は、それを使う層のパッケージにある。出荷と通知では infrastructure である。#81 と再レビューの項目である。
- **DC-155-22** 設定の値の型を有効にする設定のクラスは、全てのモジュールで同じ層にあり、その層は規則に書いてある。
- **DC-155-23** presentation は、設定の値の型を直接受け取らない。対象は店舗とレポートである。
- **DC-155-24** 画像の変換の処理は、ファイル保存の設定の値の型に依存しない。理由：外部のサービスの知識を 1 か所に限るため。

### DS-155-5 テスト専用の操作（D / P1）

- **DC-155-25** 配送業者の mock に、テスト専用の記録と、それを返す操作がない。#81 の項目である。
- **DC-155-26** 出荷の統合テストは、testFixtures の包む実装で、配送業者の mock の呼び出しを確認する。#81 の項目である。
- **DC-155-27** 次のテスト専用の操作が、本番のコードにない。
  - 税率のキャッシュを破棄する操作と、そのための public
  - ファイル保存の設定の値の型を複製する操作
  - ファイル保存のクライアントを作る static の操作
  - mock の画面だけが使う、最近の出荷の一覧の問い合わせ
- **DC-155-28** テストのために可視性を広げた本番のクラスがない。例は、決済の期限切れのジョブの public である。

### DS-155-6 複製（D / P1）

- **DC-155-29** 期限切れの片付けのジョブのループ（一定の件数ずつ削除し、上限まで繰り返す）は 1 か所にあり、カート、在庫、注文が使う。#84 の項目である。
- **DC-155-30** イベントの記録の表を読み書きする処理は、1 つのクラスにある。片付けのジョブも、そのクラスを使う。
- **DC-155-31** 認証の情報から token を取り出し、なければ未認証のエラーにする処理は、1 か所にある。
- **DC-155-32** レベル A のモジュールの一覧は、構成の検査の中で 1 か所にある。

### DS-155-7 レベル A の構成（D / P1）

- **DC-155-33** 商品カタログの application の直下が目安（10）以下であるか、バックエンドの書き方 第 1.4 節の表に理由がある。#84 の項目である。
- **DC-155-34** 在庫のモジュールで、設計書の集約とコードが一致する。集約のクラスを作るか、設計書とレベルを今のコードに合わせるかは、plan で決める。
- **DC-155-35** 在庫のモジュールで、販売可能数の参照は参照の service にある。
- **DC-155-36** 商品の画像の追加で、外部の呼び出しの前の読み取り（画像を加えられるかの確認）は、参照の service の 1 か所にある。
- **DC-155-37** 在庫のモジュールの、商品カタログのイベントのリスナーは、他のモジュールのリスナーと同じく application の service に委ね、Repository を直接使わない。
- **DC-155-38** エラーの定義の置き場所は、規則の標準の構成の記述と一致し、全てのモジュールで同じである。
- **DC-155-39** エラーの定義の置き場所のために、集約のパッケージと値のパッケージが循環しない。
- **DC-155-40** 一覧の税込価格の絞り込みと並べ替えのための SQL の計算は、バックエンドの書き方 第 1.5 節に例外として書いてある。例外には、理由と、税の計算と一致することを確認するテストを書く。
- **DC-155-41** レポートの domain がパッケージの大きさの目安を超える理由が、コードと一致する。クラスのまとまり（注文の写しと履歴、集計と期間）で分けられるなら分ける。
- **DC-155-42** 他のモジュールの結果を組み合わせる店舗の service のトランザクションは、バックエンドの書き方 第 5.2 節 ※2 に従う。従わないときは、規則に例外と理由を書く。

### DS-155-8 規則と設計書（D / P1）

- **DC-155-43** 共通コードの設計書（[共通コード・ログ・可観測性](../../design/common.md)）の一覧と本文が、DS-155-1 の後のコードと一致する。
- **DC-155-44** 各モジュールの設計書の「構成」の節が、本 spec の後のコードと一致する。
- **DC-155-45** 今コードと一致しない「構成」の記述が修正されている。対象は、片付けのジョブ、設定の型と設定のクラス、決済の view のパッケージ、カートと税の公開の API の利用者である。
- **DC-155-46** バックエンドの書き方 第 1 節（標準の構成、パッケージの大きさの表）と第 6 節（設定の値の型）が、本 spec の決定と一致する。

### DS-155-9 注文の AC のテスト（D / P1）

- **DC-155-47** AC-84 のテストは、カートの変更の API を呼び、カートの変更のイベントの処理が終わるのを待ってから、引当が解除されたことを確認する。引当を解除する操作を直接呼ばない。#78 の項目である。
- **DC-155-48** AC-128 のテストは、注文に記録した会員の ID が、注文した会員の ID と等しいことを確認する。#78 の項目である。

## 5. 移す範囲

後のバックエンドの spec が衝突を避けられるように、移動・分割するもの（パッケージ、クラス）を挙げる。正確な移動先は plan で決め、本表を更新する。

| 対象 | 今の置き場所 | 移動先（案） | DC |
|------|--------------|--------------|----|
| イベントの再発行と片付けの 6 クラス | `config/` | `config/event/` | DC-155-1、DC-155-2 |
| 認証と認可のクラス（11） | `config/security/` | 分けるか、表に理由を書く（plan） | DC-155-1 |
| `MeController` | `config/security/` | presentation の置き場所か、規則の例外（plan） | DC-155-5 |
| `DisplayOrders`、`LikePatterns` | `common/model/value/`、`common/persistence/` | `module/catalog/` の中 | DC-155-4 |
| `CartQuote` への変換、レポート用の view | `order/application/` | `order/application/model/` に view を置き、`order/api/` が変換 | DC-155-8〜DC-155-10 |
| `CartService`・`MediaService`・catalog の参照の service が返す型 | 各モジュールの `api/` の型 | 各モジュールの `application/model/` の view | DC-155-8、DC-155-9 |
| 注文と店舗の view | `order/application/port/`、`storefront/application/port/`、`storefront/application/` | 各モジュールの `application/model/` | DC-155-11 |
| `ShippingProperties`、`NotificationProperties`、`ShopProperties`、`StorefrontConfig` | 各モジュールの `application/` | 使う層（infrastructure など） | DC-155-21、DC-155-22 |
| `MockCarrierTracking` の確認用の記録 | `shipping/infrastructure/` | `src/testFixtures/` | DC-155-25、DC-155-26 |
| 片付けのジョブのループ | cart、inventory、order の `application/` | 1 か所（plan） | DC-155-29 |
| エラーの定義（`*ErrorCode`） | レベル A は集約のパッケージ、他は `domain/` | 規則に合わせてそろえる（plan） | DC-155-38、DC-155-39 |
| 商品カタログの application の直下、レポートの domain | `catalog/application/`、`reporting/domain/` | 分けるか、表に理由を書く（plan） | DC-155-33、DC-155-41 |

変える設計書は次のとおり。

- 共通コードの設計書（並行の #156 も変えうる）
- 各モジュールの設計書の「構成」の節
- [バックエンドの書き方](../../rules/backend-coding.md)
- [バックエンドのアーキテクチャ](../../design/backend-architecture.md)（mock とテスト専用の操作の記述を変えるとき）

## 6. 非機能要件

- **DN-155-1** 消費者・運営者に見える振る舞いを変えない。API の応答、画面、メールの文面、ログの形は変わらない。
- **DN-155-2** API の契約とデータベースの構造を変えない。
- **DN-155-3** AC を追加・変更しない。DS-155-9 で変えるのは、テストの確認の方法だけである。
- **DN-155-4** 構成の検査に規則を追加するときは、違反を修正した後に有効にする。有効にした後、一時的に違反を入れて、検査が失敗することを確認する。
- **DN-155-5** `./gradlew check` が通る。

## 9. Open questions

1. 再レビューの新しい指摘 28 件を、全て本 spec に含めてよいか。案は、含める。理由：どれもパッケージか層の置き場所に関わり、後の spec と衝突するため。分けるなら、DC-155-20、DC-155-24、DC-155-30〜DC-155-32 を別の issue にできる。
2. ログインした人の情報を返す操作（DC-155-5）を、presentation の置き場所に移すか、設定の下に置く例外を規則に書くか。案は、例外を書く。理由：認可の設定と同じ権限の変換を使い、どのモジュールにも属さないため。
3. 一覧の税込価格の SQL の計算（DC-155-40）を、規則の例外にするか、税の計算を呼ぶ実装に変えるか。案は、例外にする。理由：絞り込みと並べ替えを DB で行うために必要で、一致を確認するテストが既にあるため。
4. 店舗の service のトランザクション（DC-155-42）を、規則に従って読み取り専用にするか、例外にするか。案は、読み取り専用にする。理由：同じく他のモジュールの結果を組み合わせる注文の見積もりの service が、読み取り専用にしているため。
