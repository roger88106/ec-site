# バックエンドのテストの書き方

バックエンドのテストを書く・レビューするときの規則。共通の規則（テストの種類と基準、テスト名、待ち方）は [テストの書き方](test-writing.md)。

## 統合テストの土台

- 統合テストは `@IntegrationTest` を付ける。Spring と、Testcontainers の PostgreSQL・SeaweedFS・imgproxy が起動する ※1。例外は、本番の jar を別のプロセスで起動するテスト（`ProductionJarStartupTest`）で、Spring の外で動くので、必要な PostgreSQL を自分で起動する。
- `@IntegrationTest` は、MockMvc と、テストから時刻を決められる時計（`TestClockConfig`）を含む。API のテストは、注入した MockMvc で呼ぶ。
- コンテキストは 1 つで、DB とイベントの記録は全てのテストで共有する。
- 共有する状態（時計、支払の mock、税率のキャッシュ）は、JUnit の拡張が毎回のテストの前に最初の状態へ戻す。時計を使うテストは、`@BeforeEach` で時刻を決める。
- イベントの再発行は、`AsyncEvents.resubmit` に条件を渡して、自分のイベントだけを再発行する。理由：全件を再発行すると、他のテストが残した失敗も処理されるため。
- `@RecordApplicationEvents` は、別のスレッドで発行されたイベントを記録しない。
- データを残さないテストは `@Transactional` で巻き戻す。
- 巻き戻せないテスト（非同期のリスナー、並行、別のトランザクションで確定させるもの）は、テストごとに作る値（UUID や実行ごとの識別子）でデータを分ける。確認するのは、自分のデータだけである。表の全体の数や一覧の全体は確認しない（テストごとに `reset` する mock の記録は、そのテストのものとみなしてよい）。後処理（`@AfterEach` で削除する）は不要で、今あるものは残してよい。理由：DB はテストの実行ごとに作り、削除には漏れと順序（外部キー）の手間があるため。
- ログを確認するテストは、そのテストの中で出た出力だけを確認する。ログは `LogCapture` で取り込み、確認する処理の前に `LogCapture.clear` で、それまでに取り込んだログを捨てる。理由：準備や前のテストの処理（非同期を含む）が出したログが件数に数えられ、件数を誤っていても通るため（`LogCapture` の Javadoc）。
- 巻き戻せないテストで、他のテストのデータも処理の対象になるときは、処理の前に対象の行を数え、ログの件数がその数と等しいことを確認する（「1 件以上」だけにしない）。

※1：IdP は起動せず、`TestSecurityConfig` が署名の鍵を `TestTokens` の鍵に差し替える。Keycloak は、それを確認するテストだけが自分で起動する。

理由：テストごとにコンテナを再起動せず、データが他のテストに漏れないようにするため。

確認方法：レビュー

## テストデータは補助のクラスで作る

複数のテストで使うデータは、統合テストの補助（次の表）で作る。テストのクラスで同じ手順を再定義しない。補助の置き場所は次のとおり。`com.ecsite` の直下には、テストだけを置く。

- 複数のモジュールのテストで使う補助：`src/integrationTest` の `com.ecsite.support` の下の、用途のパッケージ（`data`：テストデータ、`config`：コンテキストの設定、`security`：token と署名の鍵、`async`：非同期と並行の待ち、`http`：応答の確認と JSON、Mailpit）。ただし、`async` の `Concurrently` は、単体テストからも使うので、`src/test` の同じパッケージに置く
- 1 つのモジュールの複数のパッケージのテストで使う補助：そのモジュールの `support`（例：`module.reporting.support`）
- 1 つのパッケージのテストだけが使う補助：そのパッケージ

| 補助 | 作るもの |
|------|----------|
| `CatalogTestData` | 税区分、カテゴリ、商品（バリアント・画像・公開・販売の終了・公開期間） |
| `InventoryTestData` | 在庫と、入荷の調整 |
| `OrderTestData` | カート、注文手続き、注文、支払画面 |
| `ShippingTestData` | 出荷の登録と売上確定の失敗、配送状態の通知、送り状番号 |
| `ShipmentTestData`（`module.shipping.support`） | 注文を通さない出荷（出荷の API で作る） |
| `ReservationTestData`（`module.inventory.support`） | 在庫の引当 |
| `PaymentTestData` | 支払の作成、与信、売上確定、状態とバージョンの取得 |
| `TestJson` | 応答の本文から読む ID（作成の応答の ID など） |

token は `TestTokens`、画像は `TestImages`、ログの確認は `LogCapture` を使う。

補助以外のテストは、補助が持つ手順（上の表）を直接書かない（その操作そのものを確認するテストを除く）。

補助の使い方は次のとおり。

- `SystemException` は、`assertSystemError` でエラーコードまで確認する（`ErrorCode` 全体の比較は残してよい）。
- 作成の応答の ID（UUID）は、`TestJson.createdId` で読む。
- `CatalogTestData` を入れる変数の名前は `catalog` にする。
- 結果の一覧を作る繰り返しは `IntStream…toList()`、副作用の繰り返しは for 文で書く。
- 全てのスレッドを同時に始めるテストは `Concurrently` を使って書く。行ロックでスレッドを待たせて処理の順を決めるテストは、Executor を直接使い、結果を `AsyncEvents.TIMEOUT` で待つ。タイムアウトの規則は[テストの書き方](test-writing.md)の「待ち方」。

次の 3 つは手順に含めず、テストが直接書いてよい。

- Repository のテストが集約を直接作る処理（支払の Repository のテストなど）
- 作った後に変更する呼び出し（店舗の鮮度のテストで税率を変えるなど）
- 一覧の応答から複数の ID を読む処理（画像の並び、税率の一覧など）

イベントの発行の記録（`EventPublicationRegistry`、`EventPublicationRepository`、`CompletedEventPublications`、`EventPublicationRecords`）を読む操作（名前が `find` か `count` で始まる操作）は、非同期のイベントの補助（`AsyncEvents`、`EventPublications`）の中だけに置く。補助を作るために記録を注入して渡すだけなら、補助の外でもよい。

理由：テストの本文に、確認する項目だけを残すため。

package-private の本番クラス（ジョブ、スケジュールのキャッシュなど）を別のパッケージの統合テストから使うときは、同じパッケージの `src/integrationTest` に public final の補助クラスを置く。補助クラスは、Spring のコンテキストから Bean を取り出して呼ぶ。テストのために可視性を広げない。

確認方法：レビュー（記録を読む操作は自動。`EventPublicationReadTest`。在庫と支払の作成を補助の外で呼ばないことも自動。`TestDataCreationTest`）

## テストの本文の書き方

Java のテストのクラスは、`// ============================== 名前 ==============================` の区切りで分ける。区切りの名前は「定数」「テスト」「確認の補助」「準備の補助」に揃え、「テストのデータ」「操作の補助」のような別の名前を作らない。

- テストの本文は、準備・操作・確認の段落を空行で分け、段落の先頭に `// 準備：`・`// 操作：`・`// 確認：` を付けて、続けて意図だけを書く。1 つの確認の段落では 1 つの観点を確認する。
- 前提の確認は `// 確認（前提）：`、後片付けは `// 後片付け：` と書く。`// Given：`・`// When：`・`// Then：` は書かない。
- 確認する項目が多いときは、private の確認のメソッドにし、その Javadoc に確認する内容を箇条書きで書く。
- 準備のデータと期待値は、同じ定数から作る。準備したものから期待値を取り出さない。実行ごとに変わる ID は引数で渡し、そのことを Javadoc に書く。
- entity と集約を等価（`isEqualTo`、`containsExactly` など）で比べない。値を確認するときは、項目ごとか `usingRecursiveComparison` で比べる。

理由：テストの本文を、何を準備し、何をして、何を確認するかの順で読めるようにするため。entity と集約の `equals` は識別子だけで比べるので、等価で比べると、識別子以外の項目の違いを見落とすため。

確認方法：

- entity と集約を等価で比べない：自動（Error Prone の `EntityEqualityAssertion`。jMolecules の注釈の付いたクラスと基底クラスの継承先が対象で、テストのソースセットのコンパイルでエラーにする）
- それ以外：レビュー

## テストの置き場所

main と同じパッケージに置く。Spring を起動しないものは `src/test`、起動するものは `src/integrationTest`。

理由：同じパッケージに置くと本番のクラスの可視性を広げずに済み、ソースセットを分けると Docker のない環境でも単体テストを実行できるため。

確認方法：自動（ソースセット）

## 単体テストの補助

単体テストの補助は、`src/test` の `com.ecsite.support` に置く（`com.ecsite` の直下には、テストだけを置く）。ただし `Contracts` は、単体テストと統合テストが共有するので `src/testFixtures` の `contract/` に置く。

| 補助 | 使う場面 | 使い方 |
|------|----------|--------|
| `ProductionClasses` | 構成の検査（`architecture/`、`modulith/`）と契約のテスト（`common/message/`、`contract/`） | 本番のクラスとモジュールの一覧を、この補助から読む。テストのクラスごとに `ClassFileImporter` や `ApplicationModules.of` で読み込まない |
| `RestoreFailures` | Repository が DB の値を戻すときの失敗のテスト | 表ごとの行を返す jOOQ の mock を `with` と `dsl` で作り、`assertValueIsHidden` で例外の出力に値がないことを確認する |
| `TestSettings` | 設定のテスト | `load(profile…)` と `bind(接頭辞, 設定の型, 値)` で読む。設定ファイルの読み込みと `Binder` の組み立てを、テストのクラスに書かない |
| `Contracts`（`src/testFixtures` の `contract/`） | 契約のテストと構成の検査、店舗 API の token と Keycloak の統合テスト | OpenAPI の契約と realm の設定と設計書の置き場所は、この補助の関数（`openApi`・`realm`・`path`）で読む。単体テストのクラスに `System.getProperty` や既定の相対パスを書かない ※2 |

※2：統合テストの `RegionApiTest` と `ProductionJarStartupTest` は、Gradle が渡す別の property を読むので対象にしない。

理由：クラスの複製で heap を使わず（`ProductionClasses`）、全ての設定のテストが同じ重ね方で値を読み（`TestSettings`）、Gradle の設定の誤りに気づく（`Contracts`）ため。

確認方法：`ProductionClasses` を使うことは自動（`ProductionClassesTest`。探す呼び出しの一覧はそのテストにある）、`TestSettings` と `Contracts` を使うことはレビュー

## テストのコードの重複

PMD の CPD（Gradle のプラグイン `de.aaschmid.cpd`）が、`./gradlew check` で重複を検出し、見つかると失敗にする（タスクは `cpdCheck`。報告の置き場所は[テストの実行方法](../06-手順書/running-tests.md)の「バックエンド」）。

| 項目 | 内容 |
|------|------|
| 対象 | `src/test`、`src/integrationTest`、`src/testFixtures` の Java のファイル。`src/main` は、生成したコードを含むので見ない |
| 基準 | 100 トークン以上の同じ並び（CPD の既定。変数名と値の違いは同じとみなさない）。基準を上げるときは、値と理由をこの節に書く |
| 修正方法 | 補助に移す。同じ種類のテストデータの作り方は、補助のクラス（「テストデータは補助のクラスで作る」）か、テストのパッケージの補助に置く |
| 修正しない重複 | 重複の場所を `// CPD-OFF 理由` と `// CPD-ON` で囲む。理由は `CPD-OFF` の行に書く。理由：除外と理由を一緒に読めるため |

囲むのは、補助に移すとテストが何を確認するかが読めなくなるとき、または補助にするほどの共通の意味がないときだけ（例：各 API のテストの登録の応答の確認の並び、テストデータの並び）。「修正が面倒」は理由にならない。

理由：同じコードを複数のテストに複製すると、仕様の変更で修正漏れが出て、テストごとに確認の内容がずれるため。

確認方法：自動（`./gradlew check` の `cpdCheck`。PMD の CPD）

## 境界の値のテスト

上限・下限のテストは、次のとおり書く。境界の観点は、[テストの書き方](test-writing.md)の「テストの観点」に書いてある。

- 上限と下限は、別の `@Test` にする。1 つのテストに 2 つの端を入れない。理由：どちらの端が失敗したかを、テストの名前で判断できるため。
- 各端で、「ちょうど」（通る）と「1 つ外」（上限＋1、下限－1）の両方を確認する。
- 境界の値は、本番の定数から作る（例：`NAME_MAX_LENGTH + 1`）。直書きの数（`"あ".repeat(51)` など）は使わない。理由：直書きの数は、本番の定数を変えても追従しないため。
- 本番の定数が見えないとき（非公開の定数、テストの見本の型）は、テストの中に定数を置き、その理由を 1 行のコメントで書く。
- テスト名は、どちらの端かが分かる名前にする。拒否の名前は「400」にそろえ、ページの件数の呼び名は「1 ページの件数」にそろえる。

| 場合 | テスト名の例 |
|------|--------------|
| 上限ちょうど | 上限ちょうどの名前は受け付ける |
| 上限の 1 つ外 | 上限を 1 つ超えると 400 で拒否される |
| 下限ちょうど | 下限ちょうどの数量は受け付ける |
| 下限の 1 つ外 | 下限を 1 つ下回ると 400 で拒否される |
| 1 ページの件数 | 1 ページの件数の上限ちょうどは受け付ける |

- 境界の値を 1 つずらすと、そのテストが失敗することを確認する（break-check）。テストを書いた後に行う。
- この節は、単体テストと統合テストの両方に当てはまる。統合テストで件数の上限を直接ずらすと時間がかかるため、件数の上限は単体テストで確認し、統合テストは API の応答（400 など）の確認に限る。
- 統合テストの範囲は[テストの書き方](test-writing.md)の「テストの種類と基準」に従う。

理由：境界の書き方を 1 つにそろえ、テストごとのずれを防ぐため。

確認方法：レビュー（break-check は、テストを書いた後に手動で確認する）
