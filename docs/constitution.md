# EC Site Constitution

プロジェクト全体の長期ルール。spec、plan、tasks、コードはすべてこれに従う。
ルールを変えるときは、先に本書を更新してから他を変更する。

【提案】が付いた項目は暫定で、実際に使ってみて確定させる。それ以外は確定したルール。

## 1. プロジェクトの位置づけ

- 自社 B2C の EC サイト（多店舗プラットフォームではない）。個人のポートフォリオとして、本番相当のやり方を模擬する。
- コアフローは省略しない：閲覧 → カート → 注文 → 決済 → 出荷 → 配送状況。
  - C 側（消費者）：商品閲覧、カート、チェックアウト、決済、注文・配送状況の照会
  - B 側（運営者）：商品登録、価格変更、在庫、注文管理、出荷通知、データ収集と簡易レポート
- MVP は「コアフロー全体が通る最小版」とする。
- クラウドネイティブで、水平スケールできる構成にする（第 5 節）。
- 対象市場は日本、通貨は日本円のみ。

## 4. バックエンドのアーキテクチャ

### 4.1 モジュラーモノリス

- Spring Modulith でモジュールに分割する。デプロイ単位は 1 つ。
- モジュール間の依存は `package-info.java` の `@ApplicationModule(allowedDependencies = ...)` で宣言し、`ModulithTest` で検証する。
- モジュールが外に公開するのは次の 2 つだけ。
  - `api/`（`@NamedInterface("api")`）：同期呼び出し。呼ぶ側が必要とする形で作る。呼ぶ側は腐敗防止層（`XxxDirectory`）で包み、相手の型を自分の内部に持ち込まない。
  - `event/`（`@NamedInterface("event")`）：非同期通知。Spring Modulith のイベント永続化（AFTER_COMMIT）を使う。
- モジュールの追加・統合・分割は、先に本節と `docs/modules/` を更新する。

| モジュール | 責務 | レベル（4.2） |
|------------|------|---------------|
| `tax` | 税区分と、適用期間付きの税率 | A |
| `catalog` | 商品、価格、公開、カテゴリ、商品検索 | A |
| `inventory` | 在庫数、引当と減算 | A |
| `storefront` | C 側 API。複数モジュールの結果を合成する参照専用の層 | B |
| `cart` | カート | B【提案】 |
| `order` | 注文と状態遷移 | A【提案】 |
| `payment` | 決済（外部決済サービスの腐敗防止層） | A【提案】 |
| `shipping` | 出荷と配送状況（外部物流サービスの腐敗防止層） | C【提案】 |
| `reporting` | データ収集と簡易レポート | B【提案】 |

`storefront` は、C 側で複数モジュールの情報を組み合わせるときに、モジュール同士の循環依存を避けるために置く。B 側は合成モジュールを作らず、管理画面が複数の API を呼んで組み合わせてよい。

### 4.2 モジュール内のアーキテクチャレベル

モジュールごとに、複雑さに応じてレベルを選ぶ。選んだレベルと理由は `docs/modules/<module>.md` に書く。

| レベル | 構成 | 適する場面 |
|--------|------|------------|
| A. フル | DDD + Clean Architecture + CQRS（domain / application / infrastructure / presentation） | 不変条件や状態機械が複雑 |
| B. 簡略 | 3 層（controller / service / repository） | ルールが単純、または参照のみ |
| C. イベントストア | Event Sourcing | 状態の変化の履歴自体に価値がある。採用前に plan で保存方式・スナップショット・read model を説明し、本書を更新する |

レベル A のルール：

- domain は何にも依存しない。application は domain に、infrastructure は domain の port を実装し、presentation は application を呼ぶ。
- ドメインオブジェクトは jMolecules で明示する（`@AggregateRoot`、`@ValueObject`、`@Identity`）。
- 集約の形はドメインで決める。永続化は `toSnapshot()` → Factory で再構築する。
- 状態変更は集約のメソッドで行い、その中でドメインイベントを登録する。
- application 層が投げる例外は `BusinessException` / `SystemException` に限る。

### 4.3 C 側と B 側

- C 側と B 側は同じドメインモジュールを共有し、presentation 層で分ける。
  - C 側 API：`/api/store/**`、B 側 API：`/api/admin/**`
  - Controller、Request / Response は共有しない。
- バックエンドを 2 つに分けるのは、両側でスケール、デプロイ頻度、セキュリティ境界が明確に異なってから。

### 4.4 商品検索

- キーワード検索と、通常の商品照会（カテゴリ・価格帯・並び替えなど）は、別の実装にする。1 つのクエリに混ぜない。
- キーワード検索は `catalog` の検索用 port の背後に置く。
- MVP は PostgreSQL による簡易実装とし、精度は求めない（チューニングや形態素解析はしない）。
- 検索エンジンに置き換えるときは、商品イベントでインデックスを同期し、C 側 API は変えない。

## 5. クラウドネイティブ・水平スケール

同じアプリを複数インスタンス並べて動かせるように作る。

1. **ステートレス**：リクエストをまたぐ状態をメモリに持たない。HTTP セッションを使わない。ローカルディスクにファイルを置かない。
2. **排他は DB で**：`synchronized` など JVM 内のロックで業務上の排他をしない。楽観ロック、条件付き更新、DB のロックを使う。
3. **ローカルキャッシュ**：インスタンス間でずれても許容できるデータに限り、必ず TTL を付ける。
4. **定期ジョブ**：分散ロックで重複実行を防ぐ。
5. **時刻で切り替わるデータ**（予約公開、期間付きの税率など）は、定期ジョブで書き換えず、適用期間を持たせて参照時に判定する。
6. **時刻**：`Clock` を注入して現在時刻を得る。ドメインには `Instant` を引数で渡す。
7. **イベント**：at-least-once 配信を前提に、リスナーは冪等に作る。未完了イベントの再発行が複数インスタンスで重複しないようにする。
8. **設定**：環境変数で上書きできるようにする。秘密情報をリポジトリに置かない。
9. **運用**：ログは標準出力に JSON で出す。liveness / readiness と graceful shutdown を有効にする。コンテナイメージとしてビルドする。
10. **DB マイグレーション**：アプリの起動とは分け、デプロイごとに 1 回だけ実行する。ローカルでは起動時の実行を許可する。

## 6. モジュール間連携

- 同期呼び出しは、参照か、即時に結果が必要な場面だけ。それ以外はイベントにする。
- イベントは過去形で命名する（例：`OrderPlaced`）。
- 他モジュールのテーブルを直接読み書きしない。モジュールをまたぐ外部キーも張らない。
- モジュールをまたぐ整合性は結果整合が基本。強い一貫性が必要な箇所は spec に明記し、plan で方法を説明する。

## 7. 永続化

### 7.1 基本

- jOOQ を使う。生成コードはコミットしない。
- PostgreSQL の schema をモジュールごとに分ける。
- 同時に更新されうる集約は `version` カラムで楽観ロックする。
- 時刻は UTC の `timestamptz` で保存する。
- 識別子は UUID。
- **業務番号と識別子を分ける。**
  - 品番、注文番号など人が使う番号は、主キー、他データからの参照、イベント、キャッシュのキー、URL に使わない。
  - 業務番号は一意な属性として持つ。画面・API から変更できない番号でも、DB を直接更新して付け替えられるようにしておく。
  - 過去の記録に業務番号を残すときは、参照ではなくその時点の値の写しを持つ。

### 7.2 Flyway

- スキーマの正本は Flyway のマイグレーション（`backend/src/main/resources/db/migration/`）。
- コミット済みのマイグレーションは変更しない。変更は新しいバージョンで行う。
- バージョンはタイムスタンプ形式にする（例：`V202610081400__catalog_create_product.sql`）。
- jOOQ のコード生成と統合テストは、Testcontainers の PostgreSQL に Flyway を適用して行う。
- ローカル用の seed は別の場所に置き、ローカル用 profile でだけ適用する。

### 7.3 金額

- 円単位の整数で扱い、値オブジェクト `Money` で表す。`float` / `double` は使わない。

## 8. ファイル保存

- S3 互換のオブジェクトストレージに保存する。DB にはオブジェクトのキーだけを持つ。
- アップロードは署名付き URL で、ブラウザからストレージへ直接送る。バックエンドはファイル本体を中継しない。
- ストレージは port の背後に置く。

## 9. API 規約

- RESTful JSON。
- **契約先行**：OpenAPI を plan の一部として書く。正本は `api/openapi/`（`store.yaml`、`admin.yaml`）。
  - バックエンド：OpenAPI Generator の `spring` ジェネレーター（`interfaceOnly`、`useSpringBoot4`、`useJackson3`）が生成するインターフェースを実装する。
  - フロント：`openapi-typescript` で型を生成する。生成物はコミットしない。
- 作成は `201` + `Location` で、本文に作成した ID を返す。単独の URL を持たないもの（集約の一部、履歴の 1 件など）は `Location` を返さず、本文で結果を返す。戻り値のない更新は `204`。
- 入力検証は presentation 層（Bean Validation）、ドメインルールは domain で行う。
- 例外：`ErrorCode`（`ErrorType`、i18n メッセージ、公開レベル）と `BusinessException` / `SystemException`。ドメインごとに `XxxErrorCode` enum を持ち、`GlobalExceptionHandler` で変換する。
- **エラーレスポンス**：RFC 9457（Problem Details）に次を加える。
  - `errorCode`：フロントが分岐に使うコード
  - `message`：画面にそのまま出せる日本語
  - `traceId`：すべてのエラーで返す
  - `errors`：入力検証エラーのときだけ（`[{ "field", "message" }]`）
  - ステータス：入力・業務ルール 400、見つからない 404、競合 409、システム 500
  - DB の制約違反（一意性、外部キーなど）は、リポジトリで業務のエラーに変換する。500 にしない。
- **ページング**：
  - リクエスト：`page`（1 始まり）、`size`（既定 20、最大 100）、`sort`（endpoint ごとに決めた値。例：`newest`。DB の列名は出さない）
  - レスポンス：`{ "items", "page", "size", "totalItems", "totalPages" }`
  - MVP はオフセット方式。並びの基準が同じ値になる場合は、最後に ID で順序を確定させ、ページをまたいで重複・欠落が出ないようにする。これは MVP の暫定のやり方で、検索エンジンの導入時に見直す（第 16 節）。
- **更新の競合**：同時に編集されうるリソースの更新リクエストには `version` を含め、一致しなければ 409（`CONCURRENT_MODIFICATION`）を返す。
  - 例外：状態の切り替え操作（公開・非公開、販売停止・解除など）は冪等とし、`version` を送らない。すでにその状態なら何もせず成功を返す。
- **日時**：ISO 8601 のオフセット付き文字列。

## 10. 認証・認可

MVP では実装しない。将来 MyIAM（EC は Resource Server として JWT を受ける）と連携するときに、書き換えずに追加できるようにしておく。

1. domain と application は Spring Security の型に依存しない。操作者が必要な場合は `actorId` などの引数で渡す。
2. `/api/admin/**` の endpoint ごとに、必要な権限を `resource:action` の形（例：`product:write`）で spec に書く。これは必要な操作の記録であり、権限の粒度や受け渡し方（token に載せるか、サーバー側で解決するか）は連携時に見直す。
3. C 側と B 側のパスプレフィックスを、認可の境界にする。

**MVP 版を公開ネットワークにデプロイしてはならない**（`/api/admin/**` が無防備なため）。

## 11. 外部連携（決済・物流）

- 外部サービスは port の背後に置き、外部の型やエラーコードを domain / application に漏らさない。
- 無料で実際の挙動を模擬できる外部 API（sandbox）があれば使い、なければ内部 mock にする。両者は同じ port を実装し、設定で切り替える。mock の挙動（成功、失敗、タイムアウト、遅延コールバック）はテストから制御できるようにする。
- spec に、失敗時の振る舞い、リトライと冪等性、コールバックの検証方法を書く。

## 12. テスト

### 12.1 構成

- `src/test`：単体テスト。Spring を起動しない。
- `src/integrationTest`：`@SpringBootTest` + Testcontainers。
- テストは `main` と同じパッケージに置く。
- 必須の統合テスト：Modulith の境界、Repository（永続化・再構築・差分更新・イベント発行）、並行性（並行の不変条件を持つモジュール）、外部連携の port（mock と実装の挙動の一致）。
- すべての AC に、少なくとも 1 つのテストを対応させる。テスト名（`@DisplayName`）に AC 番号を入れる。
- E2E は MVP では手動。フロントは Vitest で、表示部品とロジックを単体テストする。

### 12.2 テスト先行【提案】

| 対象 | 進め方 |
|------|--------|
| domain | 厳密な TDD |
| AC 単位の振る舞い | 実装前に受け入れテストを書き、レッドから始める |
| infrastructure、Controller の配線 | 実装後に書いてよい |
| フロントの UI | 求めない |

tasks では、テストのタスクを実装タスクより前に置く。

## 13. CI

- push と pull request で、バックエンド（ビルド、単体・統合テスト）とフロント（lint、型チェック、テスト、ビルド）を実行する。
- CI が失敗している状態で、次の spec の実装に進まない。

## 14. 言語

- Git に入るものはすべて日本語で書く：ドキュメント、コメント、Javadoc、テスト名、テストデータ、seed、コミットメッセージ、エラーメッセージ。
- 識別子（クラス名、変数名、API のパス、テーブル名・カラム名）は英語。
- **論理名と物理名を分ける。**
  - spec・plan・モジュール設計書の本文は、業務の用語（論理名）で書く。
  - 識別子（物理名）を書くのは、[用語集](glossary.md)、表の識別子の列、コードブロックだけにする。
  - 新しい用語や識別子を作ったら、用語集に追加する。
  - 実装の細部（SQL の句、アノテーション名など）は本文に書かず、意図だけを書く。

## 15. SDD ワークフロー

1. **Spec**（`spec.md`）：何を、なぜ、と受け入れ条件。実装（クラス名、カラム、フレームワーク）は書かない。
2. **Plan**（`plan.md`）：今回の変更について、モジュールをまたぐ決定、API と AC の対応、テストの割り当て、実装の順序。
3. **Tasks**（`tasks/`）：plan を検証可能な小さなタスクに分け、対応する AC を記す。段階ごとに 1 ファイル。
4. **実装**。

文書の置き場所：

| 内容 | 置き場所 |
|------|----------|
| 今回の変更で何をどう作るか | `plan.md` |
| モジュールの現在の設計（集約、不変条件の置き場所、公開する api / event、コードから読み取りにくい設計の理由） | `docs/modules/<module>.md`。plan で決めたら、ここを更新する |
| API の項目 | OpenAPI（`api/openapi/`） |
| テーブル定義 | Flyway のマイグレーション。できるまでは `docs/modules/` に草案を置き、できたらリンクに置き換える |

ルール：

- spec がコードに先行する。spec の誤りに気づいたら、spec を直してからコードを直す。
- 1 つの spec は、単独で検証できる機能の縦切り 1 つ。
- spec には、背景と目的、User stories、受け入れ条件、Non-goals、Open questions を書く。Open questions が空になるまで plan に進まない。
- AC は「できた / できていない」が判断できるように書く。AC 番号は一度振ったら変えず、追加は末尾の番号を使う。
- 決定の経緯は文書に残さず、コミットメッセージに書く。文書には現在のルールだけを書く。
