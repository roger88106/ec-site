# 段階 3：商品・バリアント・公開（US-3〜5）

- 前提：段階 1、2
- 完了条件：US-3〜5 の AC と AC-71、AC-12（商品が所属しているカテゴリ）のテストが通る。C 側での見え方（AC-29、30、32 の表示）は段階 6 で確認する。
- 参照：spec US-3〜5、[catalog.md](../../../modules/catalog.md)、`admin.yaml`（tag: product）

## タスク

- [ ] **T301** マイグレーション：商品、バリアント軸、所属カテゴリ、バリアント、軸の値のテーブル。
- [ ] **T302** [テスト] 値オブジェクトの単体テスト：商品品番・バリアント品番の形式（AC-15、21。英小文字、先頭・末尾・連続のハイフンを拒否）、税抜価格は 1 円以上（AC-25）。
- [ ] **T303** 品番などの値オブジェクトを実装する。T302 を通す。
- [ ] **T304** [テスト] 商品（集約）の単体テスト。
  - 登録直後は非公開（AC-17）。軸は 0〜3（AC-13）
  - バリアントは全軸の値を持つ（AC-22）。軸の値の組み合わせの重複を拒否（AC-23）。軸がなければバリアントは 1 つ（AC-24）
  - バリアントのない商品は公開できない（AC-31）
  - 状態の遷移。販売終了から公開・非公開に戻せない（AC-32）。同じ状態への切り替えは何もしない（冪等）
  - 初回表示日時は最初の公開で記録され、過去になった後は再公開しても変わらない（AC-54 の基準）
  - C 側に一度も表示されていなければ（初回表示日時が空か未来）商品・バリアントを削除できる。表示されたことがあれば削除できない（AC-33、71）
  - 税抜価格の変更（AC-18、25）
  - バリアントの並び順の変更（AC-27）
  - 各操作でイベントが登録される
- [ ] **T305** 商品（集約）、ファクトリ、エラーコードを実装する。T304 を通す。
- [ ] **T306** 税の腐敗防止層を作り、「現時点で有効な税率を持つ税区分か」を確認できるようにする（AC-6）。
- [ ] **T307** [テスト] リポジトリの統合テスト：バリアントを含む保存・再構築・差分更新、バージョン不一致、イベントの発行。
- [ ] **T308** リポジトリを jOOQ で実装する。T307 を通す。
- [ ] **T309** [テスト] 受け入れテスト（MockMvc）。
  - 商品の登録（AC-13〜17、25）。商品品番の重複で 409（AC-14）。同時に同じ品番で登録しても、片方が 409（500 にならない）。有効な税率のない税区分で 400（AC-6）
  - 商品の編集（AC-18、26）。税区分を変えると、詳細の税込価格が変わる（AC-19）
  - バリアントの登録・削除・並び順（AC-20〜24、27、71）。バリアント品番の重複で 409（AC-21）
  - 公開・非公開・販売終了（AC-29〜33）。同じ状態への切り替えは 204。販売終了からの切り替えは 400。商品の削除（AC-33）
  - 状態の切り替え以外の各更新で、バージョン不一致なら 409
- [ ] **T310** アプリケーション層と Controller を実装する。T309 を通す。
- [ ] **T311** [テスト] 商品が所属しているカテゴリの削除の拒否（AC-12）。カテゴリの削除と商品への割り当てが同時に起きて外部キーの違反になっても 400 になる（500 にならない）。通るよう実装する。
- [ ] **T312** seed：サンプルの商品（軸なし・軸 1 つ・軸 2 つ、標準と軽減の税区分を含む）。
- [ ] **T313** [catalog.md](../../../modules/catalog.md) の商品のテーブルを、マイグレーションへのリンクに置き換える。
