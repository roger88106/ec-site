# Spec 330：書き方の規則の 4 つの文書を、規則だけに絞り、設計と手順を分ける

種類：整理　規模：L　ステータス：草案

危険度：高

## 背景と目的

整理の段階の第 2 フェーズの spec 6 である。追跡の issue は #330 で、種類は整理である。規模 L は利用者が決めた（2026-11-03）。2 つに分けないのは、4 つの文書の「規則の一覧」の形を一緒に決めるためである。消費者・運営者に見える振る舞いと、本番のコードは変えない。

4 つの文書は、[バックエンドの書き方](../../05-開発規則/backend-coding.md)、[テストの書き方](../../05-開発規則/test-writing.md)、[フロントの書き方](../../05-開発規則/frontend-coding.md)、[コメントの書き方](../../05-開発規則/comments.md)である。規則のほかに、設計・手順・経緯・ツールの標準の動作の説明と、script・テスト・設定が正本の内容の写しが入っている。この spec で、規則だけを残し、残りを置くべき文書に移すか削除する。

全体の字数の圧縮は、文書の段階の最後の spec 8 で行う（利用者の決定、2026-11-03）。この spec は、区分の分離（規則・設計・手順）と重複の削除までとする。

作業ブランチは `330-coding-rules` で、`develop` の c70c0bc0（#329 のマージ）から作った。アーカイブ先は `docs/08-spec/archive/1to10/330-coding-rules/` である。

危険度は高とする。`docs/05-開発規則/`、`.claude/`（skill review の `checklist.cjs`）、`scripts/ci/`（`test-helpers.mjs`。確認 2 の決定による）を変え、`scripts/ci/risk.json` の「エージェントの規則と設定」の経路に当たるためである。バックエンドのテスト（`ModuleStructureTest`）も変える。マージは利用者が許可する。

CI の検査の script（`test-helpers.mjs`）を変えるので、pull request の前に `reviewer` を 1 回加える。`reviewer` は文脈を持たない高性能のレビュー役である（[エージェントの作業フロー](../../05-開発規則/subagents.md)の「レビューの時点と profile」）。認証・支払・権限の経路は変えないので、セキュリティのレビューは行わない。レビューの profile は「厚め」で、issue 担当のセッションが決めた。

spec 7（#331。skill の整理）と並行で進める（利用者の決定、2026-11-03）。重なりうるファイルと順序は、[plan](plan.md) の「参照と検査」の「並行」に書く。

## 目的と完了条件

DS ごとに DC を書く。1 つの DC に条件を 1 つ書く。確認方法は [plan](plan.md) で決める。

### DS-330-1 4 つの文書を、規則とその理由、確認方法だけにする（D / P1）

- **DC-330-1** 4 つの文書の各節に、規則、理由、確認方法だけがあり、設計・手順・経緯・ツールの標準の動作の説明がない（対象は plan の「移す内容の一覧」）。
- **DC-330-2** 移した内容が移した先の文書にあり、規則が移した先を必要とするときは、元の文書から移した先を指している。
- **DC-330-3** 移す前の 4 つの文書の規則が、欠けずに 4 つの文書にある。移した先に規則を置いていない。
- **DC-330-4** 移した先で、同じ事実を 2 か所に書いていない（バックエンドのアーキテクチャのレベルの表など）。

### DS-330-2 写しを削り、正本を指す（D / P1）

- **DC-330-5** 4 つの文書に、plan の「写しの一覧」の写しがなく、正本を指している（正本の種類は plan の「写しの一覧」）。
- **DC-330-6** テストデータの補助の手順の表が、確認 2 の決定の場所にある。`test-helpers.mjs` の検査が、変更前と同じ違反を見つける（テストがある）。
- **DC-330-7** パッケージの大きさの表が、確認 3 の決定の形になっている。`ModuleStructureTest` を含む `./gradlew check` が通る。

### DS-330-3 「規則の一覧」の形を決め、同じ規則を 2 か所に書かない（D / P1）

- **DC-330-8** 4 つの文書が、確認 1 の決定の形で書かれている。`review.md` の「規則の書き方」がその形を定めている。
- **DC-330-9** レビューのチェックリスト（`checklist.cjs`）が、決定の形から、確認方法が「レビュー」を含む規則を全て出力する（テストがある）。
- **DC-330-10** 1 つの文書の中で、同じ規則を 2 か所に書いていない。

### DS-330-4 食い違いと、先送りした issue を片づける（D / P1）

### DS-330-5 参照と検査（D / P1）

## 非機能要件

- **DN-330-1** 消費者・運営者に見える振る舞いを変えない。本番のコードを変えない。例外は、本番のコードのコメントのうち、移した・見出しを変えた節を指す参照の修正だけである（spec 5 の DN-326-1 と同じ）。
- **DN-330-2** アーカイブした spec を変えない。
- **DN-330-3** 規則の意味を変えない。移すときに、規則と今のコードの食い違いを見つけたら、その場で修正せず起票する（[開発の進め方](../../05-開発規則/workflow.md)の「コードと文書の食い違い」）。例外は、この spec で修正すると決めた `fireEvent` の例だけである。
- **DN-330-4** 検査（`checklist.cjs`、`test-helpers.mjs`、`ModuleStructureTest`）は、形を変えた後も、変える前と同じ対象を見つける。
- **DN-330-5** 文書の検査（`doc-refs`、`note-numbers`、`ja-text`）、`scripts/ci/check-all.sh`、`./gradlew check`、CI が通る。
