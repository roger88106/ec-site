# コメントの書き方

バックエンド、フロント、script に共通するコメントの書き方。

## 何を書くか

- 今のコードが何をし、なぜそうするか（業務の規則そのもの）を書く。決定の経緯（前の実装との違い、採らなかった案）はコミットメッセージに書く。
- spec・plan・tasks の番号は、コード（テスト、E2E、設定、script を含む）のコメントに書かない。本番のコードでは、コメントの外（文字列など）にも書かない。検査の対象のファイルは `scripts/ci/spec/spec-numbers.mjs` の先頭のコメントに書いてある。規則は言葉で書く（`（AC-68）` ではなく「配信する画像は、全て WebP にする」）。番号は次の形である。
  - `AC`・`DC`・`BR`・`NFR`・`US`・`DS`・`DN` の後の数字（`-` で区切ってもよい）
  - `MVP` の後の数字（`-` か空白で区切ってもよい）
  - `spec`・`plan` の後の数字（空白で区切ってもよい）。`spec 3.1` のようなバージョンの番号は除く
  - タスクの番号：`T` に 3〜4 桁の数字が続く形と、`T<番号>-<2 桁>-<2 桁>` の形
- spec との対応は、テストの名前（`@DisplayName`、フロントのテストと E2E の `test`・`it` の名前）に AC の番号で書く（[テストの書き方](test-writing.md)の「AC 番号を入れる」）。
- 根拠の文書の名前や見出しを指す括弧（`（店舗画面の構成の「エラー」）` など）を書かず、規則そのものを短く書く。コードが正本なので、文書の説明を写して厚くしない。型の使い方の規則も同じで、文書を指さずに規則を直接書く。
- 型（クラス・関数）が自分で保証することだけを書く。呼ぶ側への期待や、誰が使うかは書かない。呼び出しの前提は、API の振る舞いとして書く。処理の中のコメントに移した文も、呼ぶ側の名前を書かない。
- イベントで結んだモジュール内の呼び出しだけは、直接呼ばない理由を、見出しのコメントの `※` の後に書く（呼ぶ側を書かない規則より優先する）。
- クラスの説明に、今のメソッドの構成やメソッドの設計を書かない。
- 定数の値や、定数を使う判断の数値を書かず、定数の名前で書く（Java は「Java（Javadoc）」の `{@value}`）。定数の理由と、外部の仕様の説明は書いてよい。
- 分岐の理由は、関数の説明（Javadoc、TSDoc）でなく、分岐の前の 1 行のコメントに書く。
- 呼ぶ側を書かない規則、定数の値を書かない規則、分岐の理由の規則は、フロントと E2E のコメントにも当てる。
- 1 つの段落は 1 つの話題にし（「JavaScript（script）」の規則を、Java と TypeScript にも当てる）、メソッドの説明に移せる詳細をクラスの説明に書かない。話題が混ざった段落は、読む人が要点を探すことになるため。
- 例外：適用済みのマイグレーションはコメントも変えない（Flyway の checksum が変わるため）。新しいマイグレーションには番号を書かない。

理由：コメントを常に今のコードの説明として正しく保つため。spec の番号は仕様の管理の仕方で変わり、テストの名前と違って照合されないので、気づかれないまま古くなる。呼ぶ側、メソッドの構成、定数の値も、コードの構成が変わると古くなる。

確認方法：番号は CI の `spec-numbers.mjs`。適用済みのマイグレーションを変えていないことは CI の `migrations.mjs`。他はレビュー

## Java（Javadoc）

- クラスと全てのメンバー（private を含む）に書く。`@DisplayName` を付けたテストのクラスとメソッドは任意で、複雑なときだけ書く（書くなら、この節の規則に従う）。
- テストの項目に付けるのは、定数とテストデータの補助（時計の値など）だけ。`@Autowired`・`@MockitoBean` の項目には付けない。
- private のメンバーは、何をするかの 1 文でよい。`@param`・`@return` は書けるなら書く（検査は Javadoc があるかだけを見る）。
- 段落は `<p>` で分け、`<br />` は使わない。1 行目の後の補足は、空行の後の `<p>` に書く。項目の Javadoc も同じ。
- クラスの 1 行目は、概念の名前だけ（句点なし）にし、説明は次の `<p>` に書く。
- メソッドの 1 行目は、何をするかの 1 文だけにし、条件や補足は空行の後の `<p>` に書く。
- 決まった形のクラスは、次のとおり書く（1 行目／次の `<p>`）。
  - Controller：「〜のコントローラー」／「C 側の API のうち、store.yaml のタグ xxx の操作を受ける。」
  - `api/package-info`：「<モジュール>モジュールの公開の API」／「他のモジュールが同期で呼び出す。」
  - `event/package-info`：「<モジュール>モジュールの公開のイベント」／「他のモジュールが非同期で受け取る。」
- メソッドの Javadoc は、何をするかと `@param`・`@return`・`@throws` だけにし、record は項目を `@param` で書く。
- `@param` と項目の Javadoc は、識別子を論理名で言い換えるだけの文（`@param orderId 注文 ID`）になっても省かない。
- `@throws` は業務のエラーだけを書く。想定外の `SystemException` と、`IllegalArgumentException`・`IllegalStateException`・`NullPointerException` は書かない。エラーコードのある外部サービスの失敗は書く。
  - 説明に「業務のエラー」とは書かない。
  - 型は import して単純名で書き、`{@link}` は付けない。
  - 条件ごとに `@throws` を分け、続きの行で条件を並べない。
  - 同じエラーコードで条件だけが違うときは、「、または」で 1 行にまとめてよい（強制しない）。
- 定数の値を Javadoc に書かない。エラーコードの Javadoc は `{max}` のように名前で書き、定数はコンパイル時定数なら `{@value #NAME}`、そうでなければ `{@link #NAME}` で書く。
- `@param` などのまとまりの間の空行は任意。
- 中身のない区切りのコメントは削除する。
- 補足のない `@Override` にも `{@inheritDoc}` を書く。
- テストの補助の定数（時刻など）は、1 行目に名前（「テストの現在時刻」など）、次の `<p>` に値の説明を書く。
- インスタンスを作らない補助の private のコンストラクターは、「インスタンスを作らない。」だけ書く。

```java
/**
 * カートの service
 *
 * <p>店舗画面のカートの操作を受け、カートの集約を読み書きする。
 */
@Service
class CartService {

    /**
     * カートの品目の数量を変える。
     *
     * <p>数量が上限を超えるときは、上限に切り詰める。
     *
     * @param cartId カートの ID
     * @param itemId 品目の ID
     * @param quantity 新しい数量
     * @return 変えた後のカート
     * @throws BusinessException カートがない、カートの持ち主でない、またはカートにない品目を指定した（{@code NOT_FOUND}）
     * @throws BusinessException 数量が 1 未満（{@code INVALID_REQUEST}）
     */
    @Transactional
    public CartView changeQuantity(UUID cartId, UUID itemId, int quantity) {
        // …
    }
}
```

理由：使う側が実装を読まずに意味を把握できるようにするため。論理名で言い換えるだけの文も、識別子を業務の用語で読めるようにするので書く。

確認方法：本番のコードの Javadoc の有無は Checkstyle（`./gradlew check`）。内容はレビュー

## TypeScript（TSDoc）

- モジュールの最上位の関数・コンポーネント・型・定数に `/** */` を書く（詳しくは「型の項目」）。shadcn/ui の生成物には書かない。
- 1 行目の書き方は、定数、型の項目、テストの補助、内側の関数を含む全ての TSDoc に当てる。
- 1 行目が名前だけのとき（コンポーネント、型、定数）は句点を付けず、文のとき（関数）は句点を付ける（Java と同じ）。関数は何をするかの 1 文だけにする。
- 段落は、`<br />` でなく空行で分ける（E2E も同じ）。1 行目の後の補足は、空行の後の段落に書く。
- コード片は `{@code …}` でなくバッククォートで書く（`{@link}` は TSDoc の記法なので使う）。
- コンポーネントの props の説明は、props の型の項目の `/** */` に書く（`@param` は使わない。名前で分かる項目には書かない）。
- 関数の `@param`・`@returns`：1 行で言い切れるものは 1 行だけにする。複数行にするときは、全ての `@param` と（戻り値があれば）`@returns` を書き、`@param` の説明の位置を揃える。
- ファイルの中の区切りのコメント（`// ===== プライベート =====` など）を置かない。

```ts
/**
 * カートを移した結果の知らせ
 *
 * カートの画面で一度だけ示す。
 */
export type CartMergeNotice = {
  /** 数量を上限に切り詰めた品目（切り詰めた後の数量） */
  truncated: NoticeItems
}

/** 品目の小計を求める。 */
export function lineSubtotal(line: CartLine): number
```

理由：Java と同じ。

確認方法：レビュー

## JavaScript（script）

`scripts/` の `.mjs`・`.cjs`（検査、hook、開発の補助）のコメント。

- ファイルの先頭のコメントは、1 文目に、その script が守るもの、またはすることを書く。
- 先頭のコメントの細部は、次の段落に書く。段落は 1 つの話題にし、段落の間は空の `//` の行で分ける。
- 関数の JSDoc は、1 文目、空行、補足の順に書く。補足が複数の段落になるときも、段落の間は空行で分ける。
- 数十行のコメントにしない。先頭のコメントは少し長くてよいが、関数の JSDoc はできるだけ短くする。
- 構成で変わる数（「3 つのモジュール」「下の 5 条」）、呼び出し元、定数の値を書かない。定数は名前で書く。
- コードを言い換えたコメントを書かない。
- 分岐の理由と処理のまとまりの見出しは、他の言語と同じ規則に従う（「処理の中のコメント」、「何を書くか」）。
- 区切りのコメントは置かない。

```js
// E2E のロック。
//
// E2E は共有のデータベースとポートを使うので、同時に 1 つだけ実行する。
// ロックの中身は所有者（作業ツリーのパス、PID、開始の時刻）。所有者の PID のプロセスがなければ古いロックとして再取得する。

/**
 * プロセスが実行中か。
 *
 * 権限がなくて信号を送れない（EPERM）プロセスも実行中とみなす。
 *
 * @param {number} pid プロセスの ID
 * @returns {boolean} 実行中なら true
 */
```

理由：Java・TypeScript と同じ。script も、コメントを今のコードの説明として正しく保つため。

確認方法：番号は CI の `spec-numbers.mjs`。他はレビュー

## 処理の中のコメント

- 読んだだけでは理由が分からない処理（例外の扱い、順番に意味があるもの、外部のライブラリやサービスに固有の挙動）の前に、1 行で理由を書く。読めば分かる処理には書かない。分岐の理由は、関数の説明でなく、分岐の前のこの 1 行に書く。
- service の処理のまとまりの前に、1 行の見出しのコメントを書く。形は `// 見出し ※理由` で、理由が要らないときは `※` 以降を省く（例：`// 税区分登録 ※名称の重複は DB の一意制約で検出する`）。

```ts
// redirect は例外で移動を知らせるので、try の外で呼ぶ
redirect(`/checkout/${checkoutId}`)
```

理由：書き換えるときに、意味のある順番や例外の扱いを変えてしまわないため。見出しは、処理を 1 行ずつ読まなくても流れが分かるようにするため。

確認方法：レビュー

## 複雑な処理のコメント

次のどれかに当たる処理の直前に、何の結果を得るか（必要なら理由も）を 1 行で書く。意味が分からない所は推測で書かず、利用者に確認する。

| 当たるもの | 例 |
|------------|----|
| stream の 2 段以上の変換 ※1 | `map` の後に `filter` |
| 集計 | `groupingBy`・`flatMap`・`reduce` |
| 入れ子の繰り返し | — |
| 3 つ以上をつないだ条件 | `a && b && c` |
| 3 つ以上の分岐 | `if`・`else if` の連なり、`switch` |

※1：`toList()` などの終わりの操作は数えない。

```java
// 税率ごとに、税込みの金額を合計する（税は税率ごとに 1 回だけ端数を切り捨てるため）
Map<BigDecimal, Money> totalByRate = lines.stream()
        .collect(groupingBy(Line::taxRate, reducing(Money.ZERO, Line::amount, Money::add)));
```

理由：処理を 1 段ずつ読まなくても何を作っているかが分かり、書き換えるときに結果の意味を変えないようにするため。

確認方法：レビュー

## フロントの文言・型・処理のコメント

### 文言をキーにした所

何が表示されるかを短く書く。文言の全文は転記しない。

| 場所 | 書き方 |
|------|--------|
| JSX の子 | 式の中に `{t('title') /* 税区分 */}` ※2 |
| 属性 | 値の後に `/* 税区分 */` |
| JSX の外の式 | 行の後に `// 税区分` |

※2：要素の後ろに `{/* */}` を置くと、要素の間に空白ができるので使わない。

```tsx
<PageHeader title={t('tax.list.title') /* 税区分 */} />
<Button>{t('common.save') /* 保存 */}</Button>
```

理由：キーだけでは画面に何が表示されるかが分からず、全文を転記すると文言ファイルと食い違っていくため。

確認方法：画面の本番のソース（`.ts` と `.tsx`、共有パッケージを含む）と、店舗画面・管理画面のテストの補助と生成物の `.tsx` で、キーを文字で書いた呼び出し（`t('…')`、`translate('…')`）は CI の `message-comments.mjs`。他はレビュー

### 型の項目

名前と型で分からない項目に、1 文目に論理名、続けて特別な値の意味・単位・範囲・その値を持つ理由を書く。`id`、`name` など分かるものには書かない。

```ts
type CartLine = {
  /** 数量。1〜10（カートの上限） */
  quantity: number
  /** 税込の単価（円）。表示されない商品なら null */
  unitPrice: number | null
}
```

理由：API の契約や業務の規則を開かずに、値の意味が分かるようにするため。

確認方法：レビュー

### 一目で意図が分からない処理

イベントの処理、コンポーネントの差し替え（`render`・`nativeButton` など）、フレームワークの決まりによる書き方（`unstable_rethrow` など）の前に、何のためかを 1 行で書く。

理由：フレームワークの決まりを知らない人が、意味のある書き方を不要と思って削除しないようにするため。

確認方法：レビュー
