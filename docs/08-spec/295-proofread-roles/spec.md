# Spec 295：校閲役を、見つける役と確認する役に分け、評価の一覧で測る

ステータス：草案

危険度：高

## 1. 背景と目的

milestone「整理の段階」の spec である。追跡の issue は [#295](https://github.com/roger88106/ec-site/issues/295) で、作業ブランチは `295-proofread-roles` である。規模は M で、2026-10-31 に利用者が承認した。整理の spec なので、AC、API、データベースは変えない（[文書の記号と番号](../../05-開発規則/notation.md)）。変えるファイルが `.claude/` と `scripts/ci/` の下にあるので、経路の判定（`scripts/ci/risk.mjs`）で危険度は高になる。マージには利用者の許可が必要である。

校閲役（`ja-proofreader`）を通った日本語や、校閲役を通す前に利用者の確認に出した日本語に、後から通じにくい語が見つかる。例は、spec 276 の草案の `判定器`・`護り`・`境界` と、spec 283 で置き換えた `無記憶`・`弾` などである。書く側の漏れ（書く手順に規則がない、など）は spec 283 で修正した。本 spec は、校閲の側の漏れを扱う。

今の校閲役は、1 つのサブエージェントが候補を見つけ、挙げるかどうかも決める。何を見逃したか、何を誤って挙げたかを集める場所がないので、指示やモデルを替えたときに良くなったかを測れない。見逃しと誤検出は、#294（校閲の見逃しの一覧）に集め始めた。

参考は、Anthropic の記事「Solving code review at Anthropic」（<https://claude.dev/blog/solving-code-review-at-anthropic/>、2026-10-31 に読んだ）である。記事のコードレビューは、次の構成である。

| 項目 | 記事の構成 |
|------|------------|
| 役の分け方 | 見つける役が候補を挙げ、別の確認する役が候補ごとに本物かを判定する。判定を通った候補だけを示す |
| 評価の材料 | 過去の不具合を、評価の例として集め続ける。誤検出は、評価の例とは別に、問題のない変更に当てて数える |
| 変更の採用 | 指示・ツール・モデルの変更ごとに全ての例で採点し、点が上がった変更だけを残す |

### 1.1 本 spec の用語

| 用語 | 意味 |
|------|------|
| 校閲 | 中国語で指示する環境で、変えた日本語を読み、通じにくい語と不自然な言い回しを挙げる作業（skill `review` の手順 9） |
| 校閲役 | 校閲を行うサブエージェント。本 spec の実装の後は、見つける役と確認する役の 2 つを指す |
| 見つける役 | 校閲の候補を多めに挙げる役 |
| 確認する役 | 見つける役の候補を 1 件ずつ読み、挙げるか（誤りか、読む人が引っかかるか）を判定する役 |
| 評価の一覧 | 校閲役を採点するための例の一覧（`.claude/skills/review/evals/ja-proofread.md`） |
| 見逃しの例 | 評価の一覧の例のうち、校閲役が挙げるべき語句を含む文 |
| 誤検出の例 | 評価の一覧の例のうち、挙げてはいけない文（正しい日本語） |
| 指摘の表 | 校閲役が返す表（ファイル・行・今の書き方・修正案・理由） |

## 6. 決めたこと

利用者の確認で変えてよい。

### 決めたこと 1：定義の名前

見つける役は今の `ja-proofreader` の定義を書き換えて使い、確認する役は `ja-proof-verifier` として新しく作る。

- 理由：`ja-proofreader` を指す箇所（skill `review` の 2 つのファイル、`zh-mixing.test.cjs`）をそのまま使え、アーカイブした spec の記録の名前とも合うため。
- 別の案：2 つとも新しい名前（`ja-proof-finder`・`ja-proof-verifier`）にし、`ja-proofreader` を削除する。役の名前と定義の名前が一致するが、参照の修正が増える。

### 決めたこと 2：2 つの役のモデル

見つける役は汎用、確認する役は高性能とする。

- 書くセッションとの組み合わせ：書くセッションは、spec 担当が高性能、issue 担当が汎用である。この組み合わせなら、どちらが書いても、2 つの役の一方は書いたセッションと違うモデルになる。
- 候補の扱い：候補を汎用で集め、採否を高性能で決める形は、[エージェントの作業フロー](../../05-開発規則/subagents.md)の「運用の規則」の、文脈で判断する候補の扱いと同じである。
- 費用の見込み：確認する役が読むのは候補と前後の行だけなので、高性能でも費用は小さい見込みである（未確認。採点で token を記録する）。
- 定義に `model` を書くか、呼び出しのときに区分を指定するかは、spec 284 の「決めること 5」に合わせる（「順序と重なり」）。

### 決めたこと 3：記録の置き場所

結果は、[調べた仕組みと実績](../../07-記録/subagents-results.md)に新しい節「校閲の評価の結果」を加えて書く。

- 理由：レビューの実績と見逃しの一覧の種類が同じ文書にあり、新しい文書を加えると constitution の文書の地図も変わるため。
- 結果の行が増えて文書が長くなったら、別の文書に分ける。

### 決めたこと 4：評価の一覧を検査から除く方法

`ja-text.mjs` の `EXCLUDED`（文書）と `zh-mixing.cjs` の `TRACKED_EXCLUDED` に、`.claude/skills/review/evals/` を加える。

- 理由：例文には、使わない語と中国語の混入を書く。許容用語の一覧（`allow`）で 1 語ずつ除くと、例を加えるたびに、許容用語の一覧も変える必要があるため。
- 別の案：例文をインラインコードに入れる。今の `ja-text` はインラインコードを調べない。ただし #291 が、インラインコードにある error の語も見つけるように変えるので、この案は使えなくなる。
