# フロントの書き方

管理画面と店舗画面に共通する書き方。アプリごとの構成は [管理画面の構成](../02-設計/apps/admin.md) と [店舗画面の構成](../02-設計/apps/store.md)。確認方法が「レビュー」のものは、各 spec のレビューで、[書き方の規則とレビュー](review.md)に従って読む。

## 1. 置き場所

### 1.1 画面に依存しない処理は `lib/` の関数

判定、変換、表示の整形、列挙の表示名は `lib/` の関数（React に依存しない）にし、横に単体テストを置く。コンポーネントはその関数を呼ぶだけにする。

- API の列挙の表示名と見た目（Badge の種類など）は、1 つの機能だけで使うなら `features/<機能>/labels.ts`、2 つ以上の機能で使うなら `lib/labels.ts` に置く。
- 2 つの画面で同じ整形と列挙の表示名は、共有パッケージ（「共有パッケージ」）に置く。

理由：規則を描画なしの速いテストで確認し、画面を再作成しても規則が残るようにするため。

確認方法：レビュー

### 1.2 機能ごとに `features/<機能>/`

画面とその画面だけで使うコンポーネント・処理は `features/<機能>/`、複数の機能で使うコンポーネントは `components/`、shadcn/ui の生成物は `components/ui/`（手動で修正せず、Biome の対象外）に置く。

- 機能は、他の機能を import しない。
- 複数の機能で使うファイルの置き場所（`lib/`、`api/`、店舗画面の `actions/`）は、`features/` を import しない。使う処理が `features/` にあれば、`lib/` に移す。

理由：機能の追加・削除で触るファイルを 1 か所にまとめ、機能を削除しても共通の置き場所が壊れないようにするため。

確認方法：機能の間と、共通の置き場所から機能への import は自動（`scripts/ci/frontend-rules.mjs`）、置き場所はレビュー

## 2. API

### 2.1 生成した型で呼ぶ

API は `openapi-fetch`（管理画面は `openapi-react-query` の `$api`）で、生成した型を使って呼ぶ。パスや応答の型を手動で書かない。

理由：契約が変わったときに、型チェックで食い違いが分かるようにするため。

確認方法：自動（型チェック）

### 2.2 エラーの文は API の `message` を表示する

業務と入力のエラーは、API の `message`（項目ごとは `errors`）をそのまま表示する。画面で文を作るのは、通信の失敗など応答がないときだけ。エラーのコードで処理を分ける所（更新の競合など）は、契約の全体の列挙（`ErrorCode`）から生成した型の値で比べる（[API の規約](api-conventions.md)の「エラーの本文」）。

理由：メッセージの正本をバックエンドの 1 か所にするため。

確認方法：文はレビュー、コードは自動（型チェック）

### 2.3 入力の制約は契約から書き出した定数

入力欄の `maxLength`・`minLength`・`max`・`min` は、`generate:api` が OpenAPI から作る `src/api/generated/constraints.ts` の定数で書き、数字を直接書かない。

理由：契約の制約を変えたら、画面の制約も一緒に変わるようにするため。

確認方法：自動（`input-constraints.mjs`）

### 2.4 API の列挙の値ごとの表示は、全ての値を書く

列挙の値ごとに文言や見た目を選ぶときは、`Record<列挙, …>`（または `satisfies Record<列挙, …>`）に全ての値を書き、三項演算子で「それ以外」にまとめない。1 つの値だけを特別に扱う判定（理由が「その他」ならメモを必須にする など）は、比較でよい。

理由：契約に値を追加したときに、表示を決めていない所を型チェックで見つけるため。

確認方法：レビュー（書けば、型チェックが値の漏れを見つける）

## 3. 店舗画面のサーバーアクション

### 3.1 サーバーアクションは `withActionResult` で包む

サーバーアクション（`src/actions/`）では `catch` を書かず、例外は `withActionResult` で結果にする。`redirect` は包みの外で呼ぶ。

理由：Next.js の `redirect`・`notFound` は例外で画面を遷移させるので、捕捉すると遷移が通信の失敗として扱われるため（`withActionResult` は `unstable_rethrow` で通す）。

確認方法：自動（Biome の plugin `no-catch-in-actions`）

### 3.2 結果は `ActionResult` で返す

サーバーアクションは失敗を例外にせず、`ActionResult`（`lib/actionResult.ts`）で返す。401 だけはログイン画面へ遷移させる。

理由：操作した場所の近くに結果を表示し、入力した内容を残すため。

確認方法：レビュー

## 4. 整形と lint

Biome の設定（`frontend/biome.base.jsonc` と各画面の `biome.jsonc`）に従う。

理由：書き方の不統一をツールで防ぎ、レビューで扱わないため。

確認方法：自動（`pnpm lint`）

### 4.1 使われていないものを残さない

使われていないファイル、export、依存を残さない。定義したファイルの中だけで使うものは export しない。報告を外すのは生成物の export と型だけ（`knip.ts`）で、テストだけが import している export は使われているとみなす。失敗したときの修正は[テストの実行方法](../06-手順書/running-tests.md)の「knip が失敗したとき」。

理由：使われていないものがあると、読む人が使われているかを確認する手間が増えるため。

確認方法：自動（knip）

## 5. 共有パッケージ（`frontend/shared/`）

### 5.1 入れるもの・入れないもの

| 入れる | 入れない |
|--------|----------|
| 2 つの画面で使い、画面のフレームワーク（Vite・Next.js）と API の接続に依存しないもの | API の接続、認証、画面の機能、サーバーアクション、片方の画面だけで使うもの |

- 入れるもの：カテゴリの木、ログインの戻り先、整形、列挙の表示名。表示のコンポーネントとテーマ、共通の文言、API の生成の script（`scripts/`）も入れる。
- 共有のものは、各画面の機能を import しない。
- 各画面は、共有のパッケージが公開するものと同じ名前の関数・定数・クラスを定義しない。中身が画面ごとに違うもの（`translate`）は、`frontend-rules-exclusions.json` に理由を書く。
- テーマの CSS は shadcn/ui の生成のまま 1 つにし、片方の画面だけで使う値も含める。分けると、再生成のたびに 2 つのファイルを更新するため。
- shadcn/ui のコンポーネントは各画面の `components/ui/` に追加し、2 つの画面で同じ内容になったら `frontend/shared/src/ui/` に移す。`src/ui/` は `"use client"` の有無も生成物のまま置く。生成物でない共有コンポーネントは `frontend/shared/src/components/` に置く。
- `cn` はパッケージ `cn` から直接 import し（shadcn/ui の CLI が追加するコンポーネントと同じ形）、再 export するファイル（`lib/utils.ts` など）を作らない。`components.json` の別名 `utils` は CLI が求めるので残す。
- `src/components/` の共有コンポーネントは、hook かブラウザーの API を使うものだけに `"use client"` を付ける。
- 共有コンポーネントのクラス名は、各画面の CSS の `@source` で Tailwind に読ませる（`node_modules` の先は自動で読まないため）。

理由：同じ処理とコンポーネントを 1 か所で修正し、片方の画面の都合をもう片方に持ち込まないため。

確認方法：admin と store の同じファイルと、共有のパッケージと同じ名前の定義は自動（`scripts/ci/frontend-rules.mjs`）、共有パッケージに片方だけで使うものがないかはレビュー

## 6. 画面の URL

| 画面 | 作り方 |
|------|--------|
| 管理画面 | `src/app/paths.ts` の `paths` の関数で作る。URL の文字列を直接書かない |
| 店舗画面 | Next.js の `typedRoutes` で、画面の置き場所と照合する。クエリ付きの URL は機能の `*Query.ts` の関数（戻り値は `Route`）で作る |

- クエリは `URLSearchParams` で組み立てる（文字列で `?`・`&` を付けない）。
- 店舗画面の外の URL（IdP など）だけ `as Route` にし、理由をコメントに書く。

理由：間違った URL を型チェックで見つけるため。

確認方法：

- 型の付く URL：自動（型チェック）
- クエリ付きの URL の文字列の組み立て：自動（`scripts/ci/frontend-rules.mjs`）
- 型の付かない他の URL：レビュー（管理画面は `git grep` でパスの直書きを、店舗画面は `as Route`、`revalidatePath()`、`<form action>` を見る）

## 7. 表示の文言とロケール

### 7.1 表示の文言は文言ファイルに置く

- 見出し、ボタン、ラベル、知らせ、確認の文、エラーの既定の文、ページの題名、店の名前は、各画面の `messages/ja.json` に置き、コードではキーで引く。
- 共有の文言（`frontend/shared/src/messages/ja.json` の `common.*`）に置くのは、2 つの画面で同じ役割の文言だけ。たまたま同じ文の別の役割の文言（「状態」など）と、片方の画面だけで使う文言は、それぞれの画面に置く。
- 引き方：コンポーネントの中は `useTranslations`（店舗画面の async のサーバーコンポーネントとサーバーアクションは `getTranslations`）、コンポーネントの外の関数は各画面の `src/i18n/translate.ts` の `translate`。共有パッケージの関数とコンポーネントは、共有の文言（各画面の文言ではない）を共有の `translate`（`frontend/shared/src/lib/translate.ts`）で引く。文言を引くのに hook は使わない（店舗画面のサーバーコンポーネントからも使うため）。
- 文言はモジュールの読み込み時に定数にせず、関数かコンポーネントの中で引く（言語を切り替えたときに古い文が残るため）。
- 数は整形してから渡し（`{amount}` は数を整形しない）、値は名前で差し込む（`{code}を上へ`）。コードで組み立てる表示名（`画像 ${n}` など）も文言にする。
- 例外：テストの中の文字、開発者だけが見るログ、アイコンの代わりの記号、API の応答の文 ※1。入力例（`+10 / -3`、電話番号など）も直接書いてよい。地域で形の変わるものは、地域を追加するときに文言に移す。

※1：API に送る値など文言でないものは、理由と一緒に `scripts/ci/hardcoded-text-exclusions.json` に書く。

理由：文言を 1 か所で管理し、2 つ目の言語を追加できるようにするため。

確認方法：自動（`hardcoded-text.mjs`、型チェック）、共有の文言に置く基準と読み込み時に引かないことはレビュー

### 7.2 文言キーの形

`<機能>.<画面かコンポーネント>.<項目>`（例：`tax.list.title`）、共通は `common.<項目>`。英小文字で始める `camelCase` を `.` でつなぐ。API の列挙の値やエラーコードの表示名は、最後をその値のまま書く（`labels.publicationStatus.PUBLISHED`）。

理由：キーから表示する所を引けるようにするため。

確認方法：レビュー

### 7.3 ロケールは 1 か所

既定のロケール（`ja-JP`）とタイムゾーンは `frontend/shared/src/lib/locale.ts` だけに書き、整形とページの言語（`lang`）はそこから取る。`Intl.*` にロケールを直接書かない。

理由：言語を追加するときに、変える所を 1 か所にするため。

確認方法：自動（`scripts/ci/frontend-rules.mjs`）

## 8. 店舗画面のサーバーの設定とログ

### 8.1 環境変数は起動時に確認する

設定は `src/auth/config.ts` の `readServerConfig()` で読み、各所で `process.env` を読まない（`NODE_ENV` など、Next.js が決める実行のモードは除く）。本番で必須の設定がなければ、起動で失敗させる（必須の設定は[店舗画面の構成](../02-設計/apps/store.md)の「サーバーの設定とログ」）。

理由：設定を忘れたまま、公開されている既定値のまま起動しないようにするため。

確認方法：自動（単体テスト）

### 8.2 サーバーログは 1 行 1 件の JSON

店舗画面のサーバーログは `src/lib/server/log.ts` で書き、`console.*` を直接呼ばない。形とレベルの使い分けは[店舗画面の構成](../02-設計/apps/store.md)の「サーバーの設定とログ」。

理由：バックエンドのログと同じトレース ID で、1 つのリクエストをたどれるようにするため。

確認方法：自動（単体テスト）、`console.*` の直書きは自動（Biome の `noConsole`）

## 9. 依存

### 9.1 依存を追加したら再インストールして確認する

- 依存を追加・更新したら、ルートで `pnpm install --frozen-lockfile` を再実行する。
- インストール時のスクリプトを持つライブラリ（間接の依存も含む）は、`pnpm-workspace.yaml` の `allowBuilds` に、実行するか（`true`・`false`）と理由を書く。
- ライセンスも確認する（`node scripts/ci/licenses/check-frontend.mjs`）。両方は `scripts/dev/check-frontend.sh` でも実行できる。

理由：`allowBuilds` にないライブラリがあると pnpm はインストールを失敗にするが、手元は依存が入った後なので気づかず、CI で初めて失敗するため。

確認方法：自動（CI のインストールとライセンス検査）

## 10. 表示の要素

### 10.1 取り消し線は `<s>` で示す

取り消し線（購入できない品目の小計など）は HTML の要素 `<s>` で示し、CSS のクラス（`line-through`）で書かない。

理由：見た目だけの線は支援技術に伝わらず、テストもクラスでしか確認できなくなるため（[フロントのテストの書き方](test-writing-frontend.md)の「画面に見えるもので探す」）。

確認方法：`line-through` の直書きは自動（`scripts/ci/frontend-rules.mjs`）、他の書き方はレビュー

### 10.2 店舗画面の読み上げの領域は status の役割で作る

店舗画面で、内容の変化を支援技術に読み上げさせる領域は、status の役割（`role="status"`）で作り、`aria-live` を直接書かない。読み上げない領域（`RemainingTime.tsx`）だけは `aria-live="off"` と書いてよい。ページを開いたときに描く知らせ（共有の `Alert`）は対象外である。

理由：`aria-live` を直接書くと、領域ごとに値と `aria-atomic` の有無がばらつくため。

確認方法：`aria-live` の直書きは自動（Biome の plugin `no-aria-live`）、status 以外の役割で作っていないかはレビュー
