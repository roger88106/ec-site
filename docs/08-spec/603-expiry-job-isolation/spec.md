# Spec 603：支払の期限切れのジョブで、1 件の支払の行を復元できなくても、他の支払と他の処理を止めない

種類：整理　規模：M　ステータス：草案

## 背景と目的

支払の期限切れのジョブは、1 件の支払の行を復元できないと、その実行の全体が失敗する。#549 の pull request #602 の、pull request の前のレビュー（文脈を持たないレビュー役）で見つけた不具合で、コードを読んでの判断であり、実行は未確認である。#544（リリースの前の整理）の段階 3 の線 A（支払と注文）として、追跡の issue #603 で修正する。

ジョブは、次の 4 つの処理をこの順に行う。

1. 期限切れの支払の処理（支払画面を閉じて支払なしにする）
2. 与信の反映を待つ支払の与信の取得
3. 売上確定の結果が分からない支払の照合（#423 で加えた）
4. 与信の反映を長く待つ支払の件数の警告

期限切れの支払の検索と、与信の反映を待つ支払の検索は、取得した全ての行を支払（集約）に復元する。DB の値の破損で、状態と与信の参照が整合しないなどの行が 1 件でもあると、検索そのものが例外になる。この検索は 1 件ずつの例外の捕捉の外にあるので、例外がジョブの 1 回の実行の全体を失敗させる。

この spec は、検索が支払を復元しない形にし、各処理の検索の失敗を処理ごとに切り分ける。

期待する振る舞いは、既にある AC-310（決済の機能仕様：1 件の支払で例外が起きても、その支払 ID をログに出力して、残りの支払を処理する）と、決済の設計の「支払の期限切れ」の表の「1 件の失敗」の行である。今のコードはこれを満たしていない。消費者・運営者に見える振る舞いは、不具合の場合を除いて変えない。

## スコープ

| 含める | 含めない |
|--------|----------|
| 期限切れの支払の検索と、与信の反映を待つ支払の検索を、ジョブが使う列だけを読む形にすること | 照合の検索の形 |
| ジョブの 4 つの処理の検索（件数の集計）の失敗を、処理ごとに切り分けること | 1 回の件数の上限、実行間隔、打ち切りの回数 |
| 決済の設計の文書の修正 | 復元できない行を自動で修正する・除く処理（人が修正する） |
| | AC・機能仕様の変更（AC-310 は今のまま） |

決定：

- 規模は M にする。API の契約も DB の構造も変えず、決済のモジュールの中だけを変える。AC は変えないが、振る舞いを変える不具合の修正で、先にテストを書いてレッドを確認するため、tasks を持つ M にする（S にしない）。前例は spec 549（同じジョブの不具合の修正を整理・M で扱った）。
- 決定 1（検索は集約を復元しない）：期限切れの支払の検索と与信の反映を待つ支払の検索は、ジョブが使う列（支払 ID、支払画面の ID と URL）だけを読み、支払（集約）を復元しない。2 つの検索は、支払のリポジトリ（集約を扱う）から参照のリポジトリ（読み取りのモデルを返す）に移し、支払のリポジトリの 2 つの検索は削除する ※1。
  - 集約の復元は、1 件ずつ行ロックを取って支払を変える処理（今のまま）が行う。そこでの復元の失敗は、ジョブの 1 件ずつの例外の捕捉に入り、warn のログに支払 ID が出力される（今のジョブの 1 件の失敗の扱い）。
  - 検索の条件と並び順（期限・支払 ID の順、待ち始めた時刻・支払 ID の順）と、使う部分索引（spec 549 で加えたもの）は変えない。今の実行計画のテストと並び順のテストは、移した検索で確認する形に変える。
  - コードを読むと（実行は未確認）、復元できない行が支払画面を持つ場合、その行は毎回、支払画面を閉じる呼び出しの後に、行ロックの処理で失敗する。人が修正するまで繰り返すが、他の支払は処理される。
  - 理由：検索で失敗しなくなり、復元できない行の支払 ID がログに出力されるため（issue の案のとおり）。
- 決定 2（処理ごとの切り分け）：ジョブの 4 つの処理（期限切れ、与信の取得、照合、長く待つ支払の警告）は、それぞれの検索（警告は件数の集計）の失敗（例外の種類を問わない）を捕捉し、warn のログに、どの処理の検索が失敗したかを出力し、次の処理へ進む。その処理は次の実行で再試行する。
  - 理由：決定 1 の後も、DB の接続の失敗など、検索そのものが失敗することはある。照合の検索は行の復元の失敗も起こしうる（#603 のコメント）。1 つの処理の失敗で、後続の処理を止めないため。
- 決定 3（文書）：決済の設計の「支払の期限切れ」の表に、検索の失敗の扱い（決定 2）の行を加える。検索が支払を復元しないこと（決定 1）と、その理由（復元できない行を 1 件の失敗として扱うため）も、その表の行と注に書く。決済の機能仕様は変えない（AC-310 の文は今のままで合う）。

※1：決定に出るコードの名前は次のとおり。

| 決定 | 識別子 | 指すもの |
|------|--------|----------|
| 1 | `PaymentRepository`、`JooqPaymentRepository`（`findUnpaidPastDeadline`、`findUnpaidAwaitingAuthorization`） | 支払のリポジトリの 2 つの検索（削除する） |
| 1 | `PaymentQueryRepository`、`JooqPaymentQueryRepository` | 参照のリポジトリ（2 つの検索を移す先） |
| 1 | `PaymentQueryService`（`findPastDeadline`、`findAwaitingAuthorization`） | ジョブが呼ぶ参照のサービスの 2 つの検索 |
| 1 | `PastDeadlinePaymentView`、`AwaitingAuthorizationPaymentView` | 2 つの検索が返す読み取りのモデル（項目は変えない） |
| 2 | `PaymentExpiryJob` | 期限切れのジョブ |

## 目的と完了条件

### DS-603-1 1 件の支払の行を復元できなくても、他の支払を処理する（D / P1）

- **DC-603-1** 期限切れの支払の検索の対象に、復元できない行があっても、他の期限切れの支払が支払なしになり、復元できない行の支払 ID が warn のログに出力されることを、テストで確認している。
- **DC-603-2** 与信の反映を待つ支払の検索の対象に、復元できない行があっても、他の支払の与信を取得して与信済みにし、復元できない行の支払 ID が warn のログに出力されることを、テストで確認している。
- **DC-603-3** 移した 2 つの検索が、今と同じ条件・並び順・部分索引で読み取りのモデルを返すことを、テスト（並び順と実行計画）で確認している。

### DS-603-2 1 つの処理の検索が失敗しても、後続の処理を行う（D / P1）

- **DC-603-4** 期限切れ、与信の取得、照合の各処理の検索が例外を投げても、後続の処理が行われ、失敗した処理が warn のログに出力されることを、テストで確認している。
- **DC-603-5** 警告の件数の集計が例外を投げても、ジョブは例外を投げず、失敗が warn のログに出力されることを、テストで確認している。
- **DC-603-6** 決済の設計の「支払の期限切れ」の表と注に、検索が支払を復元しないことと、検索の失敗の扱いが書かれている。

### DS-603-3 検査が通る（D / P1）

- **DC-603-7** `./gradlew check` が通る。

## 非機能要件

- **DN-603-1** 消費者・運営者に見える振る舞いを変えない。変える振る舞いは、次の表の 2 件である ※2。理由：レビューで見つけた不具合の修正のため（開発の進め方の「コードと文書の食い違い」）。前例は spec 549 の DN-549-1。
- **DN-603-2** 変える振る舞いの 2 件は、テストを先に書いて失敗（レッド）を確認してから修正する。
- **DN-603-3** API の契約（OpenAPI）、AC、イベントの項目、DB の構造（表、列、索引、制約）を変えない。
- **DN-603-4** アーカイブした spec と、適用済みのマイグレーションを変えない。

※2：変える振る舞いの 2 件は次のとおり。

| 修正 | 今 | 修正した後 |
|------|-----|------------|
| 期限切れの支払の検索、または与信の反映を待つ支払の検索の対象に、復元できない行がある | コードを読むと（実行は未確認）、ジョブの実行の全体が例外で失敗し、他の支払の処理も後続の処理も行われない。ログに支払 ID が出力されない | その支払だけが失敗し、warn のログに支払 ID が出力される。他の支払と後続の処理は行われる |
| 1 つの処理の検索（件数の集計）が例外を投げる | 後続の処理が行われない | warn のログに出力して、後続の処理を行う |

## Non-goals

| 項目 | 理由 |
|------|------|
| 復元できない行を検索で除く、または自動で修正する | 復元できない行は DB の値の破損で、正しい値を決められないため |
| 照合の検索を、与信の参照が null の行でも失敗しない形にする | #423 で、この形の行を CHECK 制約で防いでいるため。残る検索の失敗は、決定 2 で後続の処理から切り分ける |
| 復元できない行が 1 回の件数を占め続けることへの対処 | 支払画面を閉じられない支払などと同じく、今の 1 回の件数の扱い（決済の設計の注 ※7）の範囲で、件数の上限以上の復元できない行は想定しないため |
