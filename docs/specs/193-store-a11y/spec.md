# Spec 193：店舗画面のエラーメッセージの読み上げと、失敗のログの識別子

ステータス：確定

## 1. 背景と目的

店舗画面の操作の失敗のメッセージが、支援技術（スクリーンリーダーなど）の利用者に伝わらない場合がある。注文のフォームの欄の誤りも、入力欄と結び付いていない。また、サーバーアクションの失敗のログに、カートの ID が残る経路がある。

追跡の issue は [#193](https://github.com/roger88106/ec-site/issues/193)、扱う issue は [#152](https://github.com/roger88106/ec-site/issues/152)（読み上げと欄の誤りの結び付け）と [#153](https://github.com/roger88106/ec-site/issues/153)（サーバーアクションの失敗のログの識別子）である。作業ブランチは `193-store-a11y`。

起源は、[Spec 135](../archive/1to10/135-store-cleanup/spec.md) 第 8 節の起票の案で、利用者が 2026-10-23 に起票を承認した。#152 のコメントには、spec 184 から申し送った次の 2 点がある（spec 184 第 7 節 ※1）。

## 3. User stories と受け入れ条件

### US-193-1 操作の失敗のメッセージを聞ける（C / P1）

消費者として、スクリーンリーダーで操作するときも、操作の失敗のメッセージを読み上げで知りたい。理由：失敗に気づかずに次の操作へ進まないため。

- **AC-193-1** 事実 2 の 6 つの操作の失敗のエラーメッセージは、フォームを送る前から画面にある読み上げの領域の中に出る。
- **AC-193-2** 読み上げの領域は、状態の知らせ（status の役割）として支援技術に伝わる。「カートに入れる」のフォームの、成功の知らせも表示する領域も同じにする。※1
- **AC-193-3** 失敗の後に成功したとき、前のエラーメッセージの文は消え、読み上げの領域は残る。入力を修正して再送したときも同じにする。※2

※1：役割の選び方は第 6.3 節。

※2：今の振る舞いの確認であり、テストで固定する。

### US-193-2 注文のフォームの欄の誤りを、欄で聞ける（C / P1）

消費者として、注文のフォームの誤りを、入力欄に移ったときに聞きたい。理由：欄の下の文を探さずに、どの欄をどう修正するかが分かるため。

- **AC-193-4** 注文のフォームで欄に誤りがあるとき、その欄の誤りの文が、入力欄の説明として支援技術に伝わる。
- **AC-193-5** 誤りのある欄は、誤りのある状態として支援技術に伝わる。誤りのない欄は、その状態を伝えない。
- **AC-193-6** 欄の補足の文（郵便番号・住所・電話番号の入力の例）も、入力欄の説明として伝わる。誤りがあるときは、補足の文と誤りの文の両方が伝わる。

## 4. 非機能要件

- **NFR-193-1** 店舗画面のサーバーアクションが例外で失敗したときの error のログに、カートの ID などの識別子を出さない。例外のメッセージにカートの ID が入っていても、ログに出力されない。テストで確認する。※4
- **NFR-193-2** 本 spec の AC に関わらない既存のテスト（店舗画面、E2E）は、期待値を変えずに通る。
- **NFR-193-3** 見た目（文の位置、色、レイアウト）を変えない。ただし、誤りの状態を付けた欄は、共有の UI のコンポーネントが持つ誤りの見た目（赤い枠）になる。理由：視覚で操作する利用者にも誤りの欄が分かり、実装の段階で利用者が承認した（2026-10-26）ため。
- **NFR-193-4** 新しく書くコメントに、spec の番号を書かない（[コメントの書き方](../../rules/comments.md) 第 1 節）。

※4：MVP 017 の AC-307 を変える。AC 一覧の行を「変更」にする（[開発の進め方](../../rules/workflow.md) 第 1.5 節）。ログに出力する項目は第 6.2 節。

## 5. Non-goals

| 項目 | 理由 |
|------|------|
| 失敗のときに、最初の誤りの欄へフォーカスを移す | 今のフォームの振る舞い（入力を残し、欄の下に表示する）を変える判断が必要になる。必要なら後の spec で扱い、起票のまとめ方の案（T193-03-02）に入れる |

| ログの全体のレビュー（warn の 5xx のログなど） | 5xx のログは既に API の定義のパスだけを出力する（店舗画面の構成 第 4.2 節）。#153 の範囲はサーバーアクションの失敗のログ |
| E2E の追加 | 読み上げの属性は画面のテストで確認できる |

## 6. 決めたこと

spec の確認で、利用者が第 6.1〜6.4 節を全て案 A に決めた（2026-10-26）。規模 M も同じ時に承認した。

### 6.1 種類と規模

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 機能の spec、規模 M |
| 案 B | 整理の spec、規模 M。読み上げを「見える振る舞い」に入れない解釈 |
| 案 C | #153 を分けて規模 S にする |

- 案 A の理由：#152 は支援技術の利用者に聞こえる振る舞いを変える。整理の spec は、消費者に見える振る舞いを変えない（[開発の進め方](../../rules/workflow.md) 第 1.2 節）。#153 は完了した spec の AC-307 を変え、これは新しい機能の spec で行う（[開発の進め方](../../rules/workflow.md) 第 1.5 節）。AC を追加する・変えるので M 以上で、店舗画面だけで API・データベース・モジュールをまたがないので L ではない（[開発の進め方](../../rules/workflow.md) 第 4.2 節）。
- 案 B を推奨しない理由：AC-307 の変更が、整理の spec の規則に合わないため。
- 案 C を推奨しない理由：#153 だけでも AC-307 を変えるので、規模の基準の「AC を追加する・変える」に当たり、M 以上になるため。

### 6.2 ログに出力する項目（NFR-193-1）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 例外の名前と、原因の例外（cause）の名前とコード（`ECONNREFUSED` など）だけを出力し、メッセージは出力しない |
| 案 B | 例外の名前だけを出力する |
| 案 C | メッセージを出力し、UUID の形の文字列を伏せる |

- 案 A の理由：識別子が入らない値だけにするため。接続の失敗の種類は cause のコードで分かる。追跡 ID は今もログにある（[フロントの書き方](../../rules/frontend-coding.md) 第 8.2 節）。
- 案 B：最も単純だが、接続の失敗の種類が分からない。
- 案 C：伏せる形の一覧を保つ必要があり、UUID でない識別子を見逃しうる。

### 6.3 読み上げの領域の役割（AC-193-2）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 全ての領域を status の役割にする（共通のコンポーネントの領域と、「カートに入れる」のフォームの領域） |
| 案 B | エラーは alert の役割（すぐに割り込んで読む）にする |

- 案 A の理由：status の役割は、既定で丁寧な読み上げ（`aria-live` が `polite`）と、領域の全体の読み上げ（`aria-atomic` が `true`）を持ち、今の丁寧な読み上げと同じ強さになるため。第 1 節の申し送り 2 とも合い、テストで役割で探せる。
- 案 B：今の丁寧な読み上げより強い。フォームの送信の結果としては強すぎる。

### 6.4 欄の補足の文を説明に含めるか（AC-193-6）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 含める（P1） |
| 案 B | 含めない。#152 の範囲（誤りの文）だけにし、AC-193-6 を削る |

- 案 A の理由：誤りの文と同じ方法で結び付けられ、補足の文（入力の例）も伝わるため。

### 6.5 並行の可否の決め方

spec 192（使われていないコード）と spec 195（TypeScript 7）は、店舗画面のファイルを変えうる。規模 M には plan がないので、並行の可否は、実装を始める前の照合（[開発の進め方](../../rules/workflow.md) 第 5.6 節）で互いの変えるファイルを照合して決め、追跡の issue のコメントに書く。衝突が見つかったときだけ、利用者に確認する。
