# Spec 477：認証と認可の設定で、設定の誤りへの備えとテストを補う

種類：整理　規模：M　ステータス：確定

危険度：高

## 背景と目的

認証と認可の設定は、既定で拒む、契約にない操作を拒む、realm ごとに issuer と audience と鍵を確認する、という基本を満たしている。しかし、設定を誤ったときに、認証なしで公開されたり、起動が止まらなかったりする箇所が次の 5 つある。

1. 運用のパス（死活監視とメトリクス）を、業務のパスと同じ規則の中で無条件に許している。運用ポートを業務ポートと同じにすると、死活監視とメトリクスが業務ポートで認証なしで公開され、起動にも失敗しない。統合テストの設定は、`MockMvc` で確認するため、同じポートにしている。
2. mock の画面（決済と物流）のパスは、mock のフラグだけで守っている。フラグがなければ画面の Controller がなく 404 になる。本番でフラグを立てても、起動は止まらず、警告もない。
3. 運営者と消費者の realm に同じ issuer と audience を設定しても起動する。その場合、会員の token で、管理 API の「ログインしていればよい操作」を実行できる。
4. 通知のパスを、通知のパスの下の全てで許している。この下に Controller を加えて署名の確認を忘れると、そのリクエストを認証なしで受け付ける。
5. （未確認）IdP に届かないとき、token を検証する decoder の初期化の失敗が 500（Problem Details でない応答）になると、コードから読み取れる。また、リクエストのたびに IdP から設定と鍵を取得すると読み取れる。

テストにも不足が 4 つある。店舗 API の token の検証（audience の違い・期限切れ・署名の誤り）、解釈が分かれうるパス、認可のクラスの単体テスト、token が不要な店舗の操作に無効な token を付けたときである。コードからはどれも拒むと読み取れるが、Spring のバージョンを上げたときの回帰を検出できない。

目的は、設定を誤っても安全側に倒れる（起動で止まる、または拒む）ようにし、回帰をテストで検出できるようにすること。正しい設定のときの、消費者・運営者に見える振る舞いは変えない。例外は 3 つある（DN-477-1）。

追跡の issue は #477。#458 の config のレビューで見つかった。全体の issue #544 では、段階 3 の線 C の 5 番目にあたる。関わる文書は、[バックエンドのアーキテクチャ](../../02-設計/backend-architecture.md)の「認証・認可」と「公開ネットワークへのデプロイの前提」、[API の規約](../../05-開発規則/api-conventions.md)。業務ルール BR-32（既定で拒み、決めた URL だけを許す）と AC-235〜237 に関わる。

2. 運用のパスの扱いは案 A にする。比べた案は次の表。

   | 案 | 内容 | 採る理由・採らない理由 |
   |----|------|------------------------|

   | B | 運用のパスを、運用ポートに届いたリクエストだけに許す | 同じポートにしても公開されないが、死活監視も 401 になり、誤りに気づくのが遅れる |

3. mock の画面のパスは、案 A と B の両方にする。比べた案は次の表。

   | A | mock のフラグを立てて起動したとき、警告のログを出力する | 本番で立てたことに気づける。パスは今のまま |
   | B | フラグを立てたモジュールの mock の画面のパスだけを許す。立てていなければ 401 | フラグと許すパスの対応がずれても、安全側に倒れる |
   | A と B（採る） | 両方 | 本番で立てたことにも気づけ、フラグがなければ拒む |

   - 起動は失敗にしない。理由：本番を見分ける設定がまだないため（デプロイ先は未定。constitution の「CI/CD」）。
   - フラグを立てていないとき、mock の画面のパスは 404 でなく 401 を返す（DN-477-1 の例外 1）。
4. 運営者と消費者の realm の issuer が同じ設定では、起動に失敗する。
   - audience は確認しない。理由：issuer が違えば、署名の鍵の取得先も違い、一方の token は他方の検証を通らないため。
5. 本番で IdP の issuer に https を求めるかは、案 A にする。比べた案は次の表。

   | 案 | 内容 | 採る理由・採らない理由 |
   |----|------|------------------------|
   | A（採る） | コードでは確認しない。「公開ネットワークへのデプロイの前提」の HTTPS の行に、IdP の issuer も https にすることを加える | デプロイ先が未定で、ローカルと CI は http を使う。本番を見分ける設定もまだない |

6. 通知のパスは案 A にする。比べた案は次の表。

   | 案 | 内容 | 採る理由・採らない理由 |
   |----|------|------------------------|
   | A（採る） | 認証なしで許すパスを、決済の通知と物流の通知の 2 つに限る。それ以外の通知のパスの下は 401 | 新しい通知のエンドポイントは、許すパスに加えるまで拒まれ、安全側に倒れる |
   | B | アーキテクチャのテストで、通知のパスの Controller に署名の確認を求める | 署名の確認の有無を、コードの形から推定して判定することになり、漏れが出る可能性がある |

7. IdP に届かないときの応答は、次の順で進める。
   - 先に、統合テストで今の動作を確認し、結果を tasks に記録する（decoder の初期化の失敗と、鍵の取得の失敗の 2 つ）。背景の 5 の想定のとおりでなければ、実装を始めず、issue 担当のセッションに報告する。
   - 想定のとおり 500 なら、503 の Problem Details にする。エラーコードは common に新しく加える（`AUTHENTICATION_UNAVAILABLE`。再試行できる）。メッセージは、今の 503 のメッセージの書き方にそろえて「ログインの状態を確認できませんでした。しばらくしてから、もう一度お試しください。」にする。利用者は、メッセージの確認は不要とした。今の 503 のエラーコード（ロックを待てない）は意味が違うので使わない。
   - リクエストのたびに IdP から設定と鍵を取得することは変えない。理由：IdP が回復したら、すぐに検証できるようにするため。
   - 応答が 500 から 503 に変わる（DN-477-1 の例外 2）。API の契約（OpenAPI）は、共通のエラーコードの列挙（管理 API と店舗 API の 2 つ）にこのコードを加える。共通のエラーコードは契約の列挙に載せる仕組みで、前例は spec 556 の `RESOURCE_BUSY`。操作ごとの応答には書かない。契約への追加は spec の確定の後に見つけた。issue 担当のセッションが、利用者が承認した新しいエラーコードの範囲内として承認した（2026-11-20）。エラーコードの一覧の文書とメッセージも加える。

## 目的と完了条件

### DS-477-1 設定を誤っても、認証なしで公開されない（D / P1）

- **DC-477-1** 運用ポートが業務ポートと同じ設定では、起動に失敗する。統合テストの設定で明示したときを除く。
- **DC-477-2** 運営者と消費者の realm の issuer が同じ設定では、起動に失敗する。
- **DC-477-3** mock のフラグを立てていないモジュールでは、mock の画面のパスを 401 で拒む。
- **DC-477-4** mock のフラグを立てて起動すると、フラグを立てたモジュールごとに警告のログを出力する。
- **DC-477-5** 認証なしで許す通知のパスは、決済の通知と物流の通知の 2 つだけで、それ以外の通知のパスの下は 401 で拒む。

### DS-477-2 認証と認可の回帰をテストで検出できる（D / P1）

- **DC-477-6** 店舗 API が、audience の違う token、期限切れの token、署名の誤った token を 401 で拒むことを、テストで確認している。
- **DC-477-7** 解釈が分かれうる次のリクエストを拒むことを、テストで確認している。

  | 形 | 例 |
  |----|----|
  | 末尾のスラッシュ | 契約の操作のパスの末尾に `/` を付ける |
  | 符号化した文字・区切り | `%2e`・`%2F`・`;` を含むパス |
  | 契約にないメソッド | HEAD・OPTIONS |
  | 大文字 | 契約のパスを大文字にする |
  | 管理 API の接頭辞そのもの | `/api/admin` |
  | エラーのパス | `/error` への直接のリクエスト |

- **DC-477-8** 管理 API の認可のクラス、店舗 API の認可のクラス、パスを取り出すクラス（コンテキストパスがある場合を含む）に、単体テストがある。
- **DC-477-9** token が不要な店舗の操作に無効な token を付けると 401 になることを、テストで確認している。
