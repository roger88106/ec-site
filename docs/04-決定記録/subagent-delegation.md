# サブエージェントへの任せ方で取り入れたもの

## 背景

サブエージェントの使い方を、cc-sdd・superpowers・Spec Kit・OpenSpec で調べた。取り入れるものと取り入れないものを決めた。調べた内容は、[調べた仕組みと実績](../07-記録/subagents-results.md)の「調べた仕組み」。

## 決定

| 項目 | 判断 |
|------|------|
| フレームワーク（Spec Kit、OpenSpec、cc-sdd）を導入する | 取り入れない。必要な仕組みだけを取り入れる |
| 文書（spec・plan・tasks、設計の文書、手順の文書）の本文を、日本語の要点から日本語だけの文脈のサブエージェントに書かせる | 取り入れる。内容は spec 担当のセッションが要点と照合する。数行の修正も同じセッションが行い、言い換えの一覧の検査で確認する |
| 既存の文書の言い回しのレビューに、目指す書き方の見本と、書き方の規則（[文書の書き方](../05-開発規則/writing.md)）を渡す | 取り入れる。和語の言い換えと、論理・比喩などの 2 つの観点を両方見るように指示する |
| 文書の検査に textlint を使う | 取り入れない |
| レビューを、実装の過程を見ていないサブエージェントに任せる | 取り入れる。skill `review` で行う。時点は[エージェントの作業フロー](../05-開発規則/subagents.md)の「役割と作業の流れ」 |
| 1 タスクごとにレビュー役を立てる | 取り入れない。`[リスク]` のタスクの後と、段階の最後、spec の最後などの決まった時点にレビューする（[エージェントの作業フロー](../05-開発規則/subagents.md)の「役割と作業の流れ」） |
| 1 タスクごとに新しい実装役を立てる | 取り入れる。コードは実装役だけが書く。`[テスト]` と実装は同じ実装役が行う。設計の判断の進め方は ※1（[開発の進め方](../05-開発規則/workflow.md)の「中断して質問する条件」） |
| 実装役に渡すもの | 取り入れる。渡すのは、タスクの全文と、関係する plan の節と、決まったインターフェース。曖昧な点の決定と報告の書き先も渡す。会話の履歴と計画の全体は渡さない |
| 気づきを後のタスクに渡す | 取り入れる。tasks のタスクの下に書く |
| 結果の受け取り方 | 取り入れる。詳しい報告はファイル（`/.local/` の下）に書かせ、返すのは状態・commit・テストの要約・懸念だけにする |
| 書き手を並行して動かさない | 取り入れる。同じ作業ツリーで、ファイルを書くサブエージェントを同時に動かさない。並行して動かすのは読むだけの作業か、別の作業ツリー |
| 2 回修正して通らなければ、原因の調査を分ける | 取り入れる。調査は調査役（高性能）が行う |
| モデルを常に明示する | 取り入れる |

※1：設計の判断が必要なときは、実装役が止まって報告し、spec 担当のセッションが plan から判断する。文書にない設計の判断は、利用者に質問する。

## 理由

- フレームワークを導入しない：どれも段階ごとの tasks とテストのレッドを持たず、導入しても自前で作るため。AC とテスト名の検査も、フレームワークにはない。根拠は[調べた仕組みと実績](../07-記録/subagents-results.md)の「調べた仕組み」の ※2。
- 文書の本文を、日本語の要点から、日本語だけのサブエージェントに書かせる：
  - spec 担当の文脈は利用者との会話の言語を含み、そのまま書くと日本語でない語が混ざるため。
  - 内容の質は要点の質で決まるので、spec 担当のセッションが内容を要点と照合する。
  - 試した 4 回とも言い回しの修正が必要なかったため。
- 言い回しのレビューに見本と規則を渡す：
  - 見本がないと、プロジェクトの用語を一般の語に替える案が混ざるため。
  - 規則がないと、擬人化や話し言葉を見落とすため。
  - 観点を 1 つしか書かないと、もう一方を見落とすため。
- 文書の検査に textlint を使わない：技術文書のプリセットが和語の言い換えを見つけられず、用語の辞書が言い換えの一覧の検査と重なるため。
- レビューを実装の過程を見ていないサブエージェントに任せる：作業したエージェント自身のレビューは、同じ見落としを繰り返すため。
- 1 タスクごとにレビュー役を立てない：
  - タスクが細かく数が多いので、1 タスクごとに 2〜3 のサブエージェントを立てると token が数倍になるため。
  - `[テスト]` のタスクでレッドを確認しているので、`[リスク]` のタスク以外は段階ごとで足りる。
- 1 タスクごとに新しい実装役を立てる：文脈が長くなるほど 1 回の呼び出しの費用が増えるため。
- 実装役に渡すものを絞る：渡るのは指示の文字列だけ（Claude Code の公式の文書）で、余分な文脈は token と誤りを増やすため。
- 気づきを後のタスクに渡す：新しい仕組みは不要である。今の書き方（tasks のタスクの下に書く）で足りるため。段階ごとの確認とテストを先に行うことは、開発の進め方と tasks の形に入っている。
- 結果の受け取り方：spec 担当のセッションの文脈を小さく保つため。
- 書き手を並行して動かさない：変更が衝突するため。
- 2 回修正して通らなければ原因の調査を分ける：同じ方法を繰り返さないため。
- モデルを常に明示する：省くと、親のセッションの高性能なモデルを引き継ぐため。
