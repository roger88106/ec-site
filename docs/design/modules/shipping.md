# 出荷モジュール

注文の出荷と、配送状態の管理をする。物流サービス（配送業者）の腐敗防止層。

| 項目 | 内容 |
|------|------|
| レベル | B（不変条件は配送状態の順位だけで、状態の履歴に業務の価値がない。理由は後述） |
| 依存 | なし（注文が出荷の API を呼ぶ。出荷は注文に依存しない ※1） |
| 関連 spec | [009](../../specs/archive/mvp/009-shipping)、[010](../../specs/archive/mvp/010-sales-report)、[015](../../specs/archive/mvp/015-security)、[017](../../specs/archive/mvp/017-stability)、[018](../../specs/archive/mvp/018-docs-and-tools)、[155](../../specs/archive/1to10/155-backend-structure)、[192](../../specs/192-unused-code) |

※1：出荷が注文のイベントを受けると、モジュールが循環する。配送状態の変化を注文に知らせる必要もない（注文は読むだけ）。出荷が公開するイベント「配送状態の変化」を受けるのはレポートだけで、レポートには注文も出荷も依存しないので、循環しない。

## レベルを B とした理由

- 状態は 4 つで、遷移の規則は「今より高い順位にだけ進める」の 1 つだけ。レベル A（フル）の構成（集約ごとのパッケージ、CQRS）を置く複雑さがない。
- 配送状態の履歴は見せないので、イベントストア（レベル C）にして read model を追加する理由がない。
- 外部の物流サービスとの境界（通知のエンドポイント、状態の名前の対応、署名）は `infrastructure` に閉じ、`application` の port で隔てる。

## 出荷（集約）

- 出荷は、注文 ID、配送業者、送り状番号、配送状態、出荷日時、最後に通知を反映した日時を持つ。
- 1 つの注文に出荷は 1 つ（DB の一意制約でも守る）。注文の全ての明細を 1 回で出荷する。
- 出荷を作ると、配送状態は「出荷済み」。最後に通知を反映した日時は空。
- 出荷を編集する操作はない。配送状態は物流サービスの通知だけで進む。

### 配送業者

ヤマト運輸（`YAMATO`）、佐川急便（`SAGAWA`）、日本郵便（`JAPAN_POST`）。決まった一覧から選ぶ。

### 送り状番号

| 規則 | 内容 |
|------|------|
| 文字 | 半角の数字とハイフンだけ。数字が 1 つ以上必要 |
| 長さ | 前後の空白を除いて 30 文字まで（ハイフンを含む） |
| 保存 | ハイフンを除いて保存する。通知の送り状番号も同じ形にしてから検索する |

### 配送状態と順位

| 配送状態 | 順位 | 進める先 |
|----------|------|----------|
| 出荷済み（`SHIPPED`） | 0 | 配送中、配達完了、返送 |
| 配送中（`IN_TRANSIT`） | 1 | 配達完了、返送 |
| 配達完了（`DELIVERED`） | 2 | なし |
| 返送（`RETURNED`） | 2 | なし |

- 今より高い順位にだけ進める。低い順位の通知は無視するので、通知の順序が入れ替わっても状態は戻らない。
- 途中の状態を省略してよい（出荷済みから配達完了へ）。通知が欠けても、後の通知で正しい状態になる。
- 同じ順位の「配達完了」と「返送」は、入れ替わらない。
- 同じ状態の通知が重複して届いても、反映は 1 回だけ（2 回目は順位が上がらないので何もしない）。反映したときだけ、最後に通知を反映した日時を更新する。
- 配送状態が変わるたびに（出荷を作ったときの「出荷済み」を含む）、イベント「配送状態の変化」を登録する。載せるのは、注文 ID、前と後の配送状態（作成では前はない）、発生日時。反映しなかった通知（重複して届いた、戻る）では登録しない。

## 物流サービス

| 項目 | 内容 |
|------|------|
| port | 「追跡を始める」の 1 つ。出荷を作った後、コミットの後に呼ぶ ※2。物流サービスの型とエラーを `infrastructure` の外に出さない |
| 実装 | mock だけ。mock フラグ（`ecsite.shipping.mock.enabled`）を有効にしたときに使う。本番の実装はまだないので、フラグが有効でなければ起動に失敗する |
| 通知 | 物流サービスが、荷物の状態が変わるたびにエンドポイントへ送る |

※2：実在の物流サービスでは、送り状番号の通知を受け取る登録に当たる。コミットの後に非同期で呼び、失敗したら例外で終わって、未完了のイベントの再発行で再試行する（決済の与信の取消と同じ形）。リスナーは DB を使わないので、トランザクションを持たない（物流サービスを待つ間に DB の接続を持たない）。mock は何もしない。

### 通知のエンドポイント

| 項目 | 内容 |
|------|------|
| パス | `POST /api/webhooks/carrier`（EC の API ではないので OpenAPI に書かない） |
| 認証 | 付けない。署名で確認する |
| 署名 | ヘッダー `X-Carrier-Signature` に `sha256=` と、本文（受け取ったままのバイト列）の HMAC-SHA256（16 進、小文字）。鍵は環境変数 `CARRIER_WEBHOOK_SECRET`（設定 `ecsite.shipping.webhook-secret`） |
| 本文 | JSON。配送業者、送り状番号、物流サービスの状態の名前、発生日時 |

本文の項目：

| 項目 | 内容 |
|------|------|
| `carrier` | 配送業者（`YAMATO` など） |
| `trackingNumber` | 送り状番号 |
| `status` | 物流サービスの状態の名前（ヤマト運輸なら「配達中」など） |
| `occurredAt` | 状態が変わった日時（ISO 8601） |

応答：

| 場合 | 応答 | 理由 |
|------|------|------|
| 署名がない・合わない | 401 | 処理しない |
| 署名が合うが、本文が読めない | 400 | 再送しても成功しないが、送信元に知らせる |
| 登録済みのどの出荷とも合わない（配送業者と送り状番号） | 200。記録して何も変えない | 再送させても合うようにならない |
| 状態の名前が対応の表にない | 200。記録して何も変えない | 同上。表に追加すれば、次の通知から反映される |
| 反映した、または順位が上がらず何もしなかった | 200 | 重複して届いても同じ結果 |
| 処理に失敗した（DB の障害など） | 5xx | 物流サービスの再送で再処理する |

- 署名の時刻は確認しない。重複して届いても反映は 1 回だけなので、盗まれた通知の再送で状態が戻ることも、先へ進むこともない。

### 状態の名前の対応

物流サービスの状態の名前から配送状態への対応は、配送業者ごとの表を `infrastructure` に置く。表にない名前は、上の応答の通り何もしない。配送業者ごとの表示と配送状態の対応は[用語集](../glossary.md)にある。

現在の表があるのは、ヤマト運輸だけ（mock が使う名前）。

| 状態の名前 | 配送状態 |
|------------|----------|
| 荷物受付、発送、作業店通過、配達中、持戻、保管中 | 配送中 |
| 配達完了 | 配達完了 |
| 返品 | 返送 |

### mock

- 物流の mock フラグ（`ecsite.shipping.mock.enabled`）を有効にしたときだけ動作する。物流サービスの本番の実装はまだないので、フラグが有効でなければ起動に失敗し、フラグの名前を示す。
- バックエンドが `/mock-carrier` に簡易な HTML を返す。出荷の一覧と、出荷ごとに「配送中」「配達完了」「返送」のボタンを持つ。
- ボタンを押すと、mock が署名付きの通知を作り、HTTP で自分のエンドポイントに送る。本物の物流サービスと同じ経路（署名の検証を含む）を通すため。ボタンは、ヤマト運輸の表示の名前（配送中は「配達中」、配達完了は「配達完了」、返送は「返品」）で送る。
- 送り先は、画面を返したサーバーのエンドポイント（要求と同じ接続先）。設定で URL を持たない。
- 状態の名前の表があるのはヤマト運輸だけなので、ほかの配送業者の出荷にはボタンを表示しない。
- テストのコードから、通知の重複・順序の入れ替わり・途中の欠け・署名の誤り・合わない送り状番号を送れる。mock は、正しい署名の通知を作る操作と、HTTP でエンドポイントに送る操作を公開する。重複は同じ通知を重ねて送り、順序の入れ替わりと欠けは送る内容と順序で作り、合わない送り状番号は別の番号で作る。署名の誤りは、テストだけで使う作り方（`TestCarrierNotifications`。テストで共有するソース `src/testFixtures` に置き、本番の jar に入らない）で、正しい通知の署名を別の鍵で再生成する。決済の mock と同じく、本番の mock にテストだけで使う操作を置かないため。
- 追跡を始めても、mock は何も送信しない。テストが、追跡を始めた送り状番号を確認するときは、テスト共通のソース（`src/testFixtures`）の、mock を包む実装（`TestCarrierTracking`）が記録する。本番の mock にテストだけで使う記録を置かないため。
- 画面の一覧に出す「最近の出荷」は、mock の側の問い合わせ（`MockShipmentQuery`）が読む。出荷日時の新しい順に、件数の上限まで返す。本番の処理は使わないので、出荷のリポジトリの port に置かず、mock のクラスと同じ条件（物流の mock フラグ）のときだけ動かす。
- 自動では進めない。

## 構成

```
shipping/
├── api/                    # 出荷を作る、読む、返送の注文 ID
├── event/                  # 配送状態の変化
├── application/            # 出荷の作成と参照、通知の反映、追跡を始める依頼のリスナー
│   └── port/               # リポジトリ、追跡を始める、通知の受信
├── domain/                 # 出荷、配送業者、配送状態、送り状番号、エラーの定義
└── infrastructure/
    ├── ShippingConfig      # 設定のクラス。設定の値の型 ShippingProperties を有効にする。使う層が infrastructure なので、同じ層に置く
    ├── persistence/        # リポジトリの実装
    ├── carrier/            # 通知のエンドポイント、署名の検証、状態の名前の対応の表
    └── mock/               # mock の物流サービス、mock の画面、最近の出荷の問い合わせ
```

## 他のモジュールへの公開

| 種類 | 内容 | 利用者 |
|------|------|--------|
| API | 出荷を作る（同じ注文で 2 回作らない。作った出荷を返す）、注文 ID でまとめて出荷を読む、配送状態が「返送」の注文 ID の一覧 | 注文 |
| イベント | 配送状態の変化 | レポート |

- 出荷を作る API は、呼び出し元（注文）のトランザクションに参加する。注文を「出荷済み」にすることと、出荷を作ることが、同時に成立する。
- 同じ注文で出荷を重複して作ると、業務のエラー（409）にする。
