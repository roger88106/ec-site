# セッションの運用

issue 担当のセッションと spec 担当のセッションの運用。役割の表は [エージェントの作業フロー](../../../docs/rules/subagents.md) 第 4 節、作業の形・profile・閾値・使用量を読む頻度は [作業の形と使用量](../../../docs/rules/resources.md)。ツールの名前は末尾の「ツールの注」にだけ書く。

## issue 担当のセッション

- 役割：起票と、spec 担当のセッションの起動。資源の配分。低の変更のマージ。`develop` の CI の見届け。弾の終わりの集計と振り返り。
- 起動：利用者が開く。1 つだけにする。
- 待機：待機中は、通知を受けたときに処理を再開する。定期的な問い合わせはしない。

### 待機と監視の token を抑える

1. CI を待つときは、バックグラウンドの実行（ツールの注の名前）でまとめて待ち、短い間隔で読み直さない。
2. spec 担当のセッションへの返事は短くし、判断に必要な事実だけを書く。
3. 弾の区切りで文脈を圧縮するか、新しいセッションにする（利用者が行う）。
4. 汎用の区分で動かす（[エージェントの作業フロー](../../../docs/rules/subagents.md) 第 3 節）。
5. spec 担当のセッションの終わりを待つときは、ターンを使わない待ち方（終わったら知らせる指定）を使い、問い合わせを繰り返さない。

## 資源の配分

- 作業の形、profile、並行の数は、issue 担当のセッションが [作業の形と使用量](../../../docs/rules/resources.md) 第 1 節の表で決める。並行の数の上限は、マシンの環境の文書（`/.local/agent/environment.md`）の値。
- 利用者が特例の配分を指定したときは、[作業の形と使用量](../../../docs/rules/resources.md) 第 1 節に従う。
- 閾値で止めた spec 担当のセッションの再開は、issue 担当のセッションが、使用量が戻った後（戻る時刻の後に使用量を読んで）決め、メッセージで知らせる。単線の兼務のときは、兼ねるセッションが戻る時刻の後に自分で判断する。

## spec 担当のセッションの起動と実装の開始

起動のメッセージに、開始の条件を書く。形：

> 利用者が確認対象を承認し、5 時間の使用量が x% 未満、週が y% 未満なら、問い合わせずに始め、開始を知らせる。

- x と y は、issue 担当のセッションが資源の配分から決める。
- 条件を満たさないとき、または渡されていないときは、spec 担当のセッションは issue 担当のセッションに問い合わせてターンを終える。待つ間は token を使わない。
- 返事がないときは、次に利用者か issue 担当のセッションから指示が来るまで始めない。
- 利用者が確認対象を承認したこと（通常の承認）は、開始の条件の材料である。条件を決めるのは issue 担当のセッション、条件を満たすかを判定して始めるのは spec 担当のセッション。
- 利用者が「今すぐ始めて」などと特例を明示したときは、開始の条件を飛ばし、配分は [作業の形と使用量](../../../docs/rules/resources.md) 第 1 節に従う。
- spec 担当のセッションが直接その特例を受けたときは、issue 担当のセッションに知らせ、返事を待たずに始める。
- 始めたら、[開発の進め方](../../../docs/rules/workflow.md) 第 5.6 節の実装を始める前の照合に進む。
- spec の最後のレビューの後は、pull request を draft で先に作ってから組み込みのコードレビューを行う。順と理由は [開発の進め方](../../../docs/rules/workflow.md) 第 4.2 節。

## セッションの間のメッセージ

名前でなく、セッションの識別子で送る。名前は重なったり変わったりして、別のセッションに届くことがある。

## 遠隔操作

利用者が外にいてセッションを操作できないときに、遠隔操作を有効にする。待機中のセッションには、有効にする前に短いメッセージ（「何もせず、待機中と返して終わる」）を送り、次のターンを開始する状態にしてから有効にする。待機中のままでは有効にできない。

## 単線のときの兼務

単線のときは、1 つのセッションが issue 担当と spec 担当を兼ねる。理由：資源の調整がほぼ要らず、2 つのセッションが固定で持つ文脈と通知の token を省けるため。区分は spec 担当の区分（高性能）にする。兼ねるときも、起票と spec の作業の規則は変えない。

兼務のときは問い合わせる先がない。利用者が確認対象を承認したら、自分で使用量を読んで開始の条件を判定し、開始を追跡の issue に書く。

## マージの後

- `develop` の push の CI を、issue 担当のセッションがバックグラウンドの実行（ツールの注の名前）で見届ける。失敗したら、他の pull request のマージを止めてすぐに起票し（[開発の進め方](../../../docs/rules/workflow.md) 第 4.1 節の急ぐ作業）、直るまで次のマージをしない。
- `.claude/`（skill、サブエージェントの定義、設定）を変えた pull request をマージしたら、issue 担当のセッションが、主のチェックアウトの `develop` を最新にする。理由：skill と定義は主のチェックアウトから読まれ、作業ツリーのバージョンは使われないため。
- 後片付けで自分をアーカイブできないときは、許可した利用者の言葉を添えて、issue 担当のセッションに頼む（[開発の進め方](../../../docs/rules/workflow.md) 第 5.7 節）。

## Dependabot の pull request のマージ

判定が低の pull request を、issue 担当のセッションがまとめてマージするときに使う。判定の読み方は [エージェントの作業フロー](../../../docs/rules/subagents.md) 第 4 節。

```bash
bash scripts/dev/merge-deps.sh 101 102   # 番号の pull request を順に処理する
```

- script は、最新でなければ更新し、CI が終わるのを待って、マージできる pull request ごとに `gh pr merge <番号> --merge --match-head-commit <SHA>` の 1 行を出力する。衝突、失敗、CI が終わらないときは、理由を出して終了コード 1 で止まる。
- 出力されたコマンドを、エージェントが 1 つずつ実行する。理由：hook は Bash のコマンドの文字列だけを読むので、script の中の `gh pr merge` は判定できないため。
- 1 つ目をマージした後に、2 つ目以降のコマンドが失敗したら（`develop` が進んで最新でなくなるため）、残りの番号で script をやり直す。

## 弾の終わり

詳細は [弾と段の終わり](rounds.md)。

1. 集計：`node .claude/skills/review/stats.cjs --round <弾> --profile <profile> <spec の番号...>`。profile ごとに、その profile で動いた spec だけを渡して実行する。1 つの弾に複数の profile があれば、実行を分ける（profile は spec の起動ごとに決まる。[作業の形と使用量](../../../docs/rules/resources.md)）。profile の再検討を利用者に提案する。
2. 効果の測定：整理の第 2 段の最初の弾だけ（第 1 段の測定は issue #265 で済んだ）。閾値・並行の上限・spec の最後のレビューの量を、整理の前の基準と同じ script と方法に、`stats.cjs` の集計を加えて測り直す。測る作業は、起票の案で作った issue で行う（[rounds.md](rounds.md)）。
3. 見逃しの台帳を読む：label「見逃し」の issue のうち、本文の「関連」にエージェントがマージしたと書いたものが 1 件でもあれば、高の経路の一覧と、低のマージの条件の再検討を利用者に提案する（台帳の書き方は [エージェントの作業フロー](../../../docs/rules/subagents.md) 第 5 節）。
4. 振り返り：skill `agent-retro` で行い、集計して整理の issue の案を利用者に示す。
5. 低の変更の推奨と起票の案：この弾で issue 担当のセッションがマージした低の変更の pull request から、本文の「推奨の指摘の扱い」と起票の案を集めて利用者に示す。利用者が承認したものだけを起票する。理由：低の変更は利用者が pull request を確認しないため（2026-10-28 利用者の決定）。

## 段の終わり

振り返りと、定期の全体のレビュー（提案だけ。材料と手順は [弾と段の終わり](rounds.md)）。

## ツールの注

使うサービスに固有の名前と手順。今のサービスは Claude Code のデスクトップアプリ。サービスを替えるときは、この節だけを修正する。

- セッションへのメッセージ：`mcp__ccd_session_mgmt__send_message`（引数に識別子を渡す。一覧は `list_sessions`）。子のセッションへは `SendMessage` も使える。
- 遠隔操作：`mcp__ccd_session_mgmt__set_remote_control`。待機中のセッションで有効にすると「Remote Control requires an active session」で失敗する。先に短いメッセージを送ってから有効にする（6 つのセッションで成功を確認した、2026-10-27）。
- 親子のセッション：子のセッション（起動された側）のターンが終わると、親のセッション（起動した側）に通知が届く。
- 終わったら知らせる指定：バックグラウンドの実行（`run_in_background`）か、起動したセッションの終了の通知。通知でターンが再開する。
- 台帳と CI：`gh issue list --label 見逃し`、`gh run list -b develop -L 1`。
- 使用量：`mcp__ccd_session_mgmt__get_usage`（5 時間と週の使用率、戻る時刻）。
