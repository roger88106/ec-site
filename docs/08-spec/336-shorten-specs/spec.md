# Spec 336：機能仕様・設計・OpenAPI の字数を減らし、設計と実装の内容を機能仕様から除く

種類：整理　規模：M　ステータス：確定

## 背景と目的

整理の段階の第 2 フェーズの最後の作業を、3 つの spec（#334・#335・#336）に分けた。この spec（#336）は、spec を書くときや実装のときに読む ①〜④ の文書（概要・設計・機能仕様・決定記録）と、OpenAPI を扱う。#334 は毎回読む文書と進め方の規則（マージ済み。文書の長さの基準と雛形を、[文書の構成](../../05-開発規則/doc-structure.md)の「文書の長さの基準」「文書の種類ごとの雛形」に決めた）、#335 は書き方の規則・手順書・skill を扱う。

文書はエージェントが読むので、字数がそのまま token の費用になる。減らす量の目標は決めない（利用者の決定、2026-11-03）。

棚卸し（2026-11-03）で、次のことが分かった。大きさは、作業ブランチ `334-shorten-docs` の c02dc7d6 で `wc -c` で測った値である。c02dc7d6 が、この spec の起点である。「見つかったこと」は、棚卸しで文書と script を読んで確認した事実で、「約」の付く量は見込みである。

| 対象 | 大きさ（バイト） | 見つかったこと |
|------|------------------|----------------|

| 設計 `docs/02-設計/` | 187,966 | `backend-architecture.md`（27,753）と `apps/store.md`・`apps/admin.md`（計 51,507）が大きい。モジュールの設計書の「API」の表（計約 10,000）が `role-permissions.md` と OpenAPI に重複する。`common.md` のクラス名の一覧（約 6,000）はコードから読める。雛形の指示の文が、13 の設計書に本文として転記されている（約 3,500） |

AC 一覧の冒頭は「全ての列を手動で書く」としているが、`node scripts/ci/ac-check.mjs --write` が、進行中の spec の AC を AC 一覧に転記する（AC・状態・元の spec・今の内容を書き、モジュールは空のまま）。`ac-check.mjs` の冒頭のコメントも「全て手動で書く」としている。[起票と記録の操作](../../05-開発規則/issues.md)の「AC 一覧の操作」の記述（`--write` で転記し、モジュールを手動で書く）が、コードと合う（コードで確認した）。

消費者・運営者に見える振る舞いも、アプリのコードの動作も変えない。CI の検査の script（`ac-check.mjs`）の動作は、列の形に合わせて変える。追跡の issue は #336。

決定：

- 規模は、issue の提案の L でなく M にする（issue 担当の判断、利用者の委任、2026-11-04）。理由：振る舞いもアプリのコードも変えず、決定が spec の前に決まっていて、plan に書く判断がほとんどないため。

- AC 一覧と ③ の表（含める 1・2）
  - 「今有効な AC」の表は、各モジュールの文書に残す（利用者の決定、2026-11-03）。
  - 列「元の spec」と「変えた spec」は、spec の文書へのリンクから、spec の番号だけ（`001`）にする（利用者の決定、2026-11-04）。今のリンクは、リンクテキストが番号で、リンク先が spec の `spec.md` である。変えた spec が 2 つ以上なら、今と同じく読点で区切る（`003、016`）。理由：番号から spec のディレクトリを 1 つに決められ、`ac-check` が実在を確認するため。
  - `ac-check.mjs` を次のように変える。
    - 元の spec の番号に対応する spec のディレクトリを、共通の `scripts/ci/lib/spec-dirs.mjs` の `listSpecDirs` で探す。探す場所は `docs/08-spec/` の直下と、アーカイブの下のフォルダー（`archive/mvp`、`archive/1to10`）である。ディレクトリの名前の先頭の `<番号>-` が、元の spec の番号と文字列として一致するものを選ぶ。MVP の番号は 3 桁の 0 埋め（`001`）、1→10 は 0 で埋めない番号（`227`）で、そのまま比べる。
    - 番号の形でない、その番号の spec のディレクトリがない、同じ番号のディレクトリが 2 つあるときは失敗にする。
    - 変えた spec も、変更・廃止の AC では同じ検査を各番号に行う（今は形を検査していない）（issue 担当の判断、利用者の委任、2026-11-04）。有効の AC は今と同じく「—」。
    - `--write` が転記する行の元の spec を、番号だけで書く。③ の表の列「元の spec」も番号だけで生成する。
    - 冒頭のコメントの「全て手動で書く」を、`--write` が転記する列と手動で書く列に分けて書き換える。
    - テスト（`scripts/ci/ac-check.test.mjs`）を先に変え、レッドを確認してから実装する。
  - `spec-structure.mjs` は、③ の `##` の節の名前と順だけを読み、列の形を読まないので、変えない（コードで確認した）（issue 担当の判断、利用者の委任、2026-11-04）。issue の「整えるもの」の 1 の補足（`spec-structure.mjs` の変更が必要）は、棚卸しの見込みだった。
  - 進行中の spec をアーカイブに移すときに、AC 一覧の元の spec のリンクを書き換える手順は不要になるので、[起票と記録の操作](../../05-開発規則/issues.md)の「AC 一覧の操作」から削る。[開発の進め方](../../05-開発規則/workflow.md)の「コードと文書の食い違い」にある、アーカイブのときのリンクの書き換えの記述も削る。
  - AC 一覧の冒頭の「全ての列を手動で書く」は、`--write` が転記する列と、手動で書く列（モジュール、変更・廃止のときの状態・変えた spec・今の内容）が分かる文に書き換える。正本は[起票と記録の操作](../../05-開発規則/issues.md)の「AC 一覧の操作」なので、AC 一覧では 1 文にしてそこを指す。
  - AC 一覧の冒頭の、`ac-check` が失敗する条件の箇条（7 つ）は、`ac-check.mjs` の冒頭のコメントと重複するので削り、「検査の内容は `scripts/ci/ac-check.mjs` の冒頭のコメント」と指す（issue 担当の判断、利用者の委任、2026-11-04）。理由：script から読める内容のため（[文書の構成](../../05-開発規則/doc-structure.md)の「文書の長さの基準」）。
  - 13 のモジュールの文書の「今有効な AC」の前置きの文（「選んだ基準は、AC 一覧の列「モジュール」が `<名前>` で、状態が「有効」か「変更」の AC であること。」）は削る。選ぶ基準は、機能仕様の雛形（`docs/03-機能仕様/template.md`）の 1 か所に書く。order.md の前置きにある、どのモジュールの表に入れるかの基準（迷う AC は表示するデータを持つモジュールに入れる、など）は、AC 一覧の列「モジュール」の説明に移す。雛形の「選んだ基準を 1 文で書く」の指示を削る（issue 担当の判断、利用者の委任、2026-11-04）。
  - 表の中の「今の内容」の文と、根拠のリンクは変えない（AC の正本の文のため）。

## 目的と完了条件

### DS-336-1 AC 一覧と ③ の表を短くする（D / P1）
