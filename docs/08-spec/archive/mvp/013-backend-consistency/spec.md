# Spec 013：書き方の統一（バックエンド）

ステータス：確定

## 1. 背景と目的

spec 010 の後の全体のレビューで、バックエンドのコードと書き方の規則（[バックエンドの書き方](../../../../rules/backend-coding.md)）の食い違いと、新旧のモジュールでの書き方の違いが見つかった。

- 生成したモデルを位置で並べるコンストラクターで組み立てる所が、古いモジュール（catalog、inventory、tax、cart）を中心に残っている。cart には応答への変換の mapper がない。同じ型の引数（真偽値 4 つなど）は、取り違えても気づきにくい。
- 注文の一覧の金額が、application の型で整数のまま持たれている。金額の掛け算が `Money` の外にあり、金額の掛け算・割り算と端数の扱いの規則が文書にない。
- 参照と更新の分け方（CQRS）が、catalog と order・payment で違う。order の詳細の参照は集約をそのまま presentation に渡し、payment の更新の service に参照が混在する。storefront は同じデータに近い形の型を 4 段持つ。
- イベントを誰が送り出すか、モジュールの公開の API を誰が実装するかが、モジュールで違い、文書にもない。
- パッケージの構成と名前が規則と合わない所がある（reporting の application の直下の record、order の値の置き場所、order の他のモジュールの port の名前）。
- 設定の値の一部が `@ConfigurationProperties` の外にあり、検証されない。
- 同じ処理の重複（作成の応答の Location、版の比べ方、復元の失敗の扱い、mock の画面の HTML）と、使われないコードがある。
- 一意の制約の違反の扱い、スキーマを作る場所など、コードで守っている慣習が規則に書かれていない。

spec 012 で、書き方の統一で触る所のテストを補った。本 spec は、既存のテストを変えずに通すことを「振る舞いが変わっていない」の証拠にして（[MVP の完成までの一覧](../mvp.md) 第 2 節）、バックエンドを規則にそろえる。規則のほうが今の良い書き方を表していないときは、規則を修正する。

本 spec は**整理の spec**（[文書の記号と番号](../../../../rules/notation.md)）。消費者・運営者に見える振る舞いを変えない。

## 2. 用語

本 spec で新しく使う用語は、plan で用語集に追加する。

## 4. 目的と完了の条件

### DS-35 応答の組み立てが、項目の名前で書かれ、mapper にまとまる（D / P1）

- **DC-118** 生成したモデルを、位置で並べるコンストラクターで組み立てる箇所がない。例外を設けるなら（項目が 1 つのラッパー型など）、バックエンドの書き方 第 2.2 節に書き、他の箇所はそれに従う。
- **DC-119** API の型への変換は、全てのモジュールで mapper にあり、Controller に変換の処理が残らない。cart に mapper がある。

### DS-36 金額を `Money` で扱い、金額の計算の規則が文書にある（D / P1）

- **DC-120** application と domain の型で、金額を整数で持つ所がない。整数で持つのは presentation、infrastructure、設定の値だけで、設定の値の扱いをバックエンドの書き方に書く。
- **DC-121** 金額と数量の掛け算は `Money` の操作で行う。
- **DC-122** 金額の掛け算・割り算は `Money` と税の計算の中だけで行い、端数の扱いを明示する、という規則がバックエンドの書き方にある。

### DS-37 参照と更新の分け方が、レベル A のモジュールでそろう（D / P1）

- **DC-123** order・payment の参照は、参照の service が返す参照用の型（view）を使い、presentation は集約を受け取らない。画面の操作の可否も view に入る。
- **DC-124** 更新の service に参照の処理が混ざらない。参照は参照の service に置く（バックエンドの書き方 第 5.2 節の名前）。注文の手続きの見積もりなど、どちらにも当たらないものの置き方を plan で決め、規則に書く。
- **DC-125** storefront は、catalog の公開の型を写す自分の型（腐敗防止層）を残し、その間の、加工のない写しの型をなくす。並び順など列挙を写すのは 1 か所にする。

### DS-38 イベントの送り出しと公開の API の実装の形が、規則に書かれ、そろう（D / P1）

- **DC-126** イベントは集約が記録し、リポジトリが保存の後に送り出す、という規則がバックエンドのアーキテクチャにある。レベル B のモジュール（集約を持たない）は、application の service が送り出してよい。
- **DC-127** モジュールの中だけのイベントの置き場所と、domain が自分のモジュールの `event/` を参照してよいことが、バックエンドの書き方 第 1.1 節にある。
- **DC-128** レベル A のモジュールのイベントは、全て DC-126 の形で送り出す。
- **DC-129** モジュールの公開の API（`api/`）は、`api/` のクラスが application の service に委ねる形で実装する、という規則がバックエンドの書き方にあり、media もこの形になる。

### DS-39 パッケージの構成と名前が規則に合う（D / P2）

- **DC-130** パッケージの直下のクラスの数が目安（10）を超える所は、分けるか、バックエンドの書き方 第 1.4 節の表に理由がある。reporting の command・query・view は `application/model/` にある。
- **DC-131** レベル A のモジュールの値の型の置き場所がそろう。order の値をどこに置くかは plan で決め、order の設計書に書く。
- **DC-132** 他のモジュールの port の名前が、相手のモジュールの名前になる（order の商品の portを含む）。同じモジュールの中で、同じ単純名の別の型がない。
- **DC-133** モジュールの設計書の「構成」が、今のパッケージと合う（reporting を含む）。
- **DC-134** 参照だけを行う application の処理に、読み取り専用のトランザクションがある。

### DS-40 設定の値を全て検証つきの設定の型で受ける（D / P2）

- **DC-135** 定期の処理の間隔は、設定の型の項目として受け、検証される。設定のキーと既定値は今と同じ。設定のキーを持たない固定の値（定期の処理のロックの上限）は、定数とし、設定にしない理由をコードに書く。
- **DC-136** 設定の型を有効にする宣言は、モジュールの設定のクラスにまとまる。

### DS-41 重複した処理と使われないコードがない（D / P2）

- **DC-137** 作成の応答（Location と作成した ID）、版の比べ方、保存した状態から集約を戻すときの失敗の扱いは、それぞれ 1 か所の共通の処理を使う。
- **DC-138** 支払の期限の判定と、期限切れにする処理は、それぞれ 1 か所にある。
- **DC-139** mock の画面の HTML の組み立ては、モジュールごとに 1 か所にまとまる。配送業者の表示の名前は、メッセージから取る。
- **DC-140** main に、どこからも使われないコードがない。
- **DC-141** main の、テストだけが使うコードは、削除するとテストが変わる（DN-15 を超える）ので残し、テストのためにあることをコードに書く。main でも使える所は main から使う（DC-138 の期限の判定など）。対象：
  - mock の支払の実装の、テストだけが使う操作（次の確定を失敗させる、開いた画面の一覧 など）。mock を本番に出さない仕組みは 015 で作る。
  - catalog の、リスナーのいないイベント（公開、公開の停止、販売の終了、価格の変更）。catalog の設計書に「リスナーはまだない（検索の索引の同期で使う）」と書く。
  - その他、plan の調べで見つけたもの（plan に一覧を書く）。
- **DC-142** コードで守っている慣習が、規則に書かれている：一意の制約の違反の 2 つの扱い方と選び方（バックエンドの書き方 第 3.4 節）、新しいスキーマを作るマイグレーションと、モジュールとスキーマの名前が違う箇所の理由。

## 6. 非機能要件

- **DN-15** 既存のテスト（バックエンド、店舗画面、管理画面、E2E）が通る。テストのコードの変更は、本番のクラスの移動と名前の変更に伴う import、クラスの名前、パッケージだけにし、検査で確認する。それ以外を変えないと通らない所は、振る舞いを変えているので、本 spec で行わず、振る舞いを変える spec に移す。
  - 特例（2026-10-19 利用者）：AC-154 のテスト（支払の期限切れのジョブの間隔）は、`@Scheduled` の間隔の文字列を `${}` だけで解決していた。間隔を設定の型から SpEL で取る（T013-05-05）と解決できないので、Spring の予定の処理と同じく `${}` と `#{}` の両方で解決する形に変える。確認する中身（間隔が 5 分以内）は変えない。差分は名前の対応のファイルに書く。
- **DN-16** API の契約と応答、データベースの構造とデータ、設定のキーと既定値、ログの出力を変えない。
- **DN-17** CI の全体が 10 分以内のまま終わる（spec 011 の DC-85）。
