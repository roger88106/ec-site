# Spec 556：DB のロックの待ちと例外の扱いを整える

種類：整理　規模：M　ステータス：草案

危険度：高

## 背景と目的

#458 のレビューで、DB のロックの待ち、DB の例外、定期ジョブと非同期のリスナーの 3 つの問題（#488）が見つかった。ログに DB のエラーの詳細が残る可能性（#429）もある。この 2 つの issue を 1 つの spec で整える。追跡の issue は #556（組の issue）。sub-issue は #488、#429。#544（リリースの前の整理）の段階 3 の線 C である。

- DB の接続に、ロック待ち・文の実行・トランザクション中のアイドルのタイムアウトがない。行ロックを取る読み込み（注文、決済、出荷、在庫、カテゴリ、注文手続き、カート）の待ちに上限がなく、終わらないトランザクションがあると、待つリクエストがスレッドと接続を使ったまま残る。
- 制約の違反でない DB の例外（デッドロック、ロック取得の失敗、直列化の失敗）は、全てシステムエラー（500）になる。再試行できる競合を 409 で返す処理がない。
- 定期ジョブのスケジューラーのスレッドは既定の 1 本で、6 つの定期ジョブが順に動く。支払の期限切れのジョブ（決済サービスを 1 件ずつ呼ぶ）の間、イベントの再発行と片付けが止まる。ジョブがロックを持つ時間の上限は全て 10 分である。
- 非同期のリスナーは全て既定のスレッドプール（8 スレッド、上限のないキュー）を共有する。外部サービス（SMTP、決済、オブジェクトストレージ、物流）を呼ぶリスナーが遅いと、外部を呼ばないリスナーも待たされる。停止のときに処理中のリスナーを待たない。
- 想定外の DB の例外をログに出力するとき、PostgreSQL のエラーの詳細（キーと値）が含まれ、行の値がログに残る可能性がある（#429。コードからの推定で、実際のログは未確認）。

消費者・運営者に見える振る舞いは、DB の競合の応答と画面のメッセージだけが変わる（DN-556-1）。

危険度を「高」にする理由は、全ての DB の接続、定期ジョブ、非同期のリスナーの実行に関わる設定を変えるため。

※1：デッドロックの 409（共通のエラーの「更新の競合」）は、既に全ての操作が返しうるエラーとして契約にある。Open questions の 2、3 で新しいエラーコードを選んだときだけ、契約に 1 つ加える（DN-556-2）。

決定（issue 担当のセッションが 2026-11-19 に確認した。決定 2 の 3 種のエラーごとの扱いは、Open questions の 1〜3 で確認する）：

- 規模：M とする（特例）。判定の表では L に当たる。2 つ以上のモジュール（「変える範囲」の表）にまたがるため。
  - 理由：どの変更も設定と共通のクラスの変更で、API と AC の対応も、モジュールをまたぐ実装の順序の設計もなく、plan に書く内容がないため。前例は spec 550 である。
- 決定 1（DB のタイムアウト）：全ての DB の接続の初期化で、3 つのタイムアウトを置く。値は設定ファイルに置き、環境変数で上書きできるようにする。推奨の既定値は次のとおり。
  - ロック待ち：5 秒。理由：消費者・運営者のリクエストが行ロックを待つ時間の上限を、画面の操作が待てる長さにするため。
  - 文の実行：30 秒。
  - トランザクション中のアイドル：60 秒。理由：メールの送信はトランザクションの中で SMTP を呼び、タイムアウトが接続・読み取り・書き込みで各 10 秒あるので、それより長くするため（出典：`docs/03-機能仕様/notification.md` 25 行、`application.yml` の `spring.mail.properties`）。
  - マイグレーション（Flyway）の接続では、文の実行のタイムアウトを無効にする。理由：索引の作成など、長いマイグレーションを止めないため。
- 決定 2（DB の競合の扱い）：例外の原因（cause）の連鎖に、PostgreSQL の次の 3 種のエラー（DB の競合）があれば、DB の競合として扱う。デッドロック、ロック取得の失敗（ロック待ちのタイムアウトを含む）、直列化の失敗。
  - エラーの種類ごとの扱い：応答、自動の再試行、画面のメッセージは、3 種を一律にせず、Open questions の 1〜3 の結果で決める。デッドロックの応答は、409（共通のエラーの「更新の競合」）と今の共通のメッセージで確定である。
  - 制約の違反の変換を通る書き込みでも、通らない読み込み（行ロックを取る読み込み）でも同じにする。
  - ログは警告のレベルで出力し、エラーコード・トレース ID・PostgreSQL のエラーの種類（SQLState）を出力する。原因の例外のメッセージ（行の値を含みうる）とスタックトレースは出力しない。
  - 文の実行のタイムアウトで失敗したエラーと、トランザクション中のアイドルのタイムアウトで切断された接続のエラーは、今のとおりシステムエラー（500）にする。理由：再試行しても同じ結果になりうる遅さで、競合ではないため。
  - 定期ジョブと非同期のリスナーでの競合は、今のとおり失敗として扱い、次の回か再発行で再試行する。
- 決定 3（定期ジョブ）：スケジューラーのスレッドの数を、定期ジョブの数（6）にする。理由：ジョブが互いを待たないようにするため。ロックを持つ時間の上限は、ジョブごとに、想定する最大の処理時間より長く決めて、理由をコメントに書く。推奨の値は次のとおり。
  - 支払の期限切れのジョブ：30 分。決済サービスが応答しないときは、1 件で最大約 75 秒かかり、1 回の件数は最大 100 なので、最悪では 1 回が 30 分を超える（出典：支払の期限切れのジョブのコメント）。超えると別のインスタンスで同時に実行されうるが、業務の正しさは行ロックと冪等な状態の遷移で保つ（出典：定期ジョブの設定のコメント）。30 分は、通常の回が収まり、止まったインスタンスのロックが長く残らない値として推奨する。
  - イベントの再発行：5 分。理由：実行の間隔が 1 分のため。
  - そのほかの 4 つ：10 分のまま、明示する。
- 決定 4（非同期のリスナー）：外部サービスを呼ぶリスナー（メールの送信、ファイルの削除、決済の取消、物流の追跡の依頼）のスレッドプールを、外部を呼ばないリスナーのスレッドプールと分ける。両方のスレッドプールで、スレッドの数とキューの上限を設定で明示し、停止のときに処理中のリスナーを待つ。待つ時間の上限は、停止のときに処理中のリクエストを待つ上限（30 秒）に合わせる。
  - 未確認：Spring Modulith のリスナーのアノテーションはスレッドプールを選べないので、スレッドプールを指定するアノテーションを作る必要がある。イベント発行記録が今と同じに働くか（完了の記録、失敗の再発行）、キューが満杯で拒否されたイベントが、未完了のまま残って再発行されるかは、実装の最初のタスクで確認する。
  - 確認できなければ、作業を止めて報告し、スレッドプールを分けない案（1 つのスレッドプールの大きさとキューの上限を明示する）に切り替えるかを確認する。
- 決定 5（ログのエラーの詳細）：制約の違反などを起こし、実際のログに行の値が出るかを確認し、結果を #429 にコメントで書く。値が出るなら、PostgreSQL の JDBC ドライバーの設定（サーバーのエラーの詳細をログに出さない設定）を、全ての環境の共通の設定に置く。
  - 理由：本番の接続先は環境変数で渡すが、設定は共通のファイルにあり、環境で分ける理由がないため。
  - 設定の後も、制約の違反の変換（制約名の取得）が働くことを、テストで確認する。

## Open questions

1. **デッドロック**（SQLState `40P01`）：自動の再試行をするか。
   - 事実：PostgreSQL がデッドロックを検出すると、一方のトランザクションを失敗させる。もう一方は進むので、失敗した側はトランザクションの全体を再実行すれば通ることが多い。
   - 画面のメッセージ：409 と今の共通のメッセージ「他の人が先に更新しました。再読み込みしてください。」で確定（利用者が決めた）。
   - 選択肢 A（推奨）：自動の再試行をしない。理由：再実行は、どの SQL をどの値で発行するかの判断を含めて、トランザクションの全体で行う必要がある（PostgreSQL の文書の「13.5. Serialization Failure Handling」）。そのため、トランザクションの境界の外側に共通の仕組みを加えることになる。デッドロックはまれで、消費者・運営者は画面を再読み込みして操作を再実行できる。
   - 選択肢 B：自動の再試行をする。回数は 1 回（合わせて 2 回の実行）。範囲は消費者・運営者のリクエストの最も外側のトランザクションの全体。定期ジョブと非同期のリスナーは対象外（次の回と再発行で再実行されるため）。費用：共通の仕組みとテストの追加、トランザクションの中で外部サービスを呼ぶ処理がないかの確認。
2. **ロック取得の失敗**（SQLState `55P03`）：自動の再試行と画面のメッセージをどうするか。
   - 事実：
     - このアプリでは、ロック待ちのタイムアウト（決定 1、5 秒）を超えたときに起きる。ロックを待たない指定（NOWAIT）はコードで使っていない。
     - 起きるのは、他のトランザクションが行ロックを 5 秒以上持ち続けたときである。通常の操作がロックを持つ時間は短いので、止まったトランザクションがあるときに起きる。止まったトランザクションは、トランザクション中のアイドルのタイムアウト（60 秒）で切断される。
     - 他の人が更新したとは限らないので、今の共通のメッセージ「他の人が先に更新しました。再読み込みしてください。」は事実と合わないことがある。
   - 自動の再試行の選択肢：
     - A（推奨）：しない。理由：既に 5 秒待った後で、再試行するとさらに最大 5 秒待つ。合わせて約 10 秒は、ロック待ちのタイムアウトを決めた理由（画面の操作が待てる長さ）を超える。ロックを持つトランザクションが止まっているなら、5 秒後も持っている可能性が高い。
     - B：する。回数は 1 回。範囲は 1 のデッドロックの B と同じ。待つ時間は合わせて最大約 10 秒。
   - 画面のメッセージの選択肢：
     - a：今の共通のメッセージを使う（409、更新の競合）。契約は変えない。事実と合わないことがある。
     - b（推奨）：新しい共通のエラーコード（名前の案：`RESOURCE_BUSY`）を加え、新しいメッセージを返す。メッセージの案：「ほかの処理が終わるのを待てませんでした。しばらくしてから、もう一度お試しください。」。HTTP の状態は 503 を推奨する。理由：管理画面は 5xx で「再試行」のボタンを出し、4xx では出さない（#559 の決定）。「しばらくしてから、もう一度」の案内と、再試行のボタンが合う。費用：API の契約（共通のエラーの一覧と列挙）に 1 つ加え、画面の型を再生成する。
     - c：b と同じ新しいエラーコードとメッセージで、HTTP の状態を 409 にする。管理画面に再試行のボタンは出ない。
3. **直列化の失敗**（SQLState `40001`）：扱いを今加えるか。
   - 事実：
     - PostgreSQL では、分離レベルが Repeatable Read か Serializable のトランザクションで起きる（PostgreSQL の文書の「13.5. Serialization Failure Handling」）。
     - このアプリは分離レベルを指定しておらず（コードに指定がない）、PostgreSQL の既定の Read Committed で動くので、今は起きない。
     - PostgreSQL の文書は、`40001` をトランザクションの全体の再実行で解ける失敗とし、アプリに再試行を求めている（同じ節）。spec を確認した利用者は「再実行できない」と考えて、別のメッセージを求めている。
   - 選択肢 A（推奨）：今は扱いを加えず、今のとおりシステムエラー（500）のままにする。理由：今の分離レベルでは起きないため。分離レベルを上げる変更をするときに、その spec で再試行とメッセージを決める。A を選ぶときは、Non-goals の表に行を加える。
   - 選択肢 B：デッドロックと同じ扱い（409、今の共通のメッセージ、自動の再試行は 1 の決定に合わせる）。
   - 選択肢 C：新しい共通のエラーコードと新しいメッセージを加える。メッセージの案：「同時に行われたほかの操作と重なったため、処理できませんでした。もう一度お試しください。」。HTTP の状態は 409。費用は 2 のメッセージの b と同じ。
