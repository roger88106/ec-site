# 文書を書く・修正する

文書の地図は [constitution](../../../docs/constitution.md) 第 3 節。文書は利用者と話して決め、エージェントが書く。

## 1. 置き場所

置き場所は [constitution](../../../docs/constitution.md) 第 3 節の文書の地図。文書を追加したら地図にも記載する。`docs/` の下のフォルダーを追加・変更するときは、`scripts/ci/docs-folders.mjs` の一覧と地図を一緒に修正する。

## 2. 書き方

書き方の規則は [文書の書き方](../../../docs/05-開発規則/writing.md)。書き終えたら、その表を当てはめる。

## 3. 進め方

1. 範囲と形を利用者と決める。大きな整理は、先に計画（置き場所、節の構成、移す先）を示して確認する。
2. 書く。利用者が確認する対象（[開発の進め方](../../../docs/05-開発規則/workflow.md) 第 5.1 節。規模 L は spec、plan と tasks を一緒に、pull request）で止まって見せる。それ以外の文書の修正は、確認を待たずに進める。
   - 新しい文書と、節を追加するような大きな修正：決定・事実・参照を日本語の要点（箇条書きと表）にまとめ、日本語だけの文脈のサブエージェント（汎用）に本文を書かせる。指示も日本語だけで書き、要点・対象の spec・本 skill・正本（[文書の書き方](../../../docs/05-開発規則/writing.md)）・見本の文書だけを読ませる。指示に「理由は、要点にあるもの、または出典（ファイル:行）を示せるものだけを書く。出典のない理由は書かない」を入れる。spec 担当のセッションは本文の内容を要点と照合する（[エージェントの作業フロー](../../../docs/05-開発規則/subagents.md) 第 2 節）。
   - 数行の修正：spec 担当のセッションが修正し、手順 4 の検査で確認する。
   - 既存の文書の言い回しのレビュー：skill `review` の文書のレビューの手順（見本を渡す）で行う。
3. 文書を移した、節の番号や見出しを変えたときは、第 4 節で参照を修正する。
4. 確認する。次が全て通ること：
   - `node scripts/ci/doc-refs.mjs`（Markdown のリンクと、`<文書の名前> 第 N 節` の参照。CI の docs.yml でも実行する）
   - `node scripts/ci/note-numbers.mjs`（注の番号 `※N` が、1 つの文書の中で重複せず、出る順に並ぶ）
   - `node scripts/ci/ja-text.mjs`（日本語の文の検査。error は使わない語で、失敗になるので修正する）
   - `node scripts/ci/ja-text.mjs --warning`（warning の一覧を出力する。終了コードは 0）。文脈で言い換える語と文体の型の文が、ファイルと行とともに示される。型は、連続する「の」・長い文・読点の多い文・否定が続く文・複合動詞の崩れの疑いである。示された文を読み、修正するかを 1 件ずつ決める。自分が書いた・変えた行を優先し、既存の行は、同じ文を変えるときに限って修正する
   - コードのコメントを修正したら、フロントは `pnpm lint`、バックエンドは `./gradlew check`
5. commit を分ける：文書のまとまりごとに 1 つ、参照の修正は最後に 1 つ。全ての変更は issue から始まり、規模 S は issue を spec とする（[開発の進め方](../../../docs/05-開発規則/workflow.md) 第 4 節）。spec の tasks にないタスクの番号は付けない。push と pull request の作成は許可を求めず、マージの許可と担当は、危険度によって異なる（AGENTS.md の Git の表）。

## 4. 参照の修正

| 参照 | 修正方法 |
|------|--------|
| Markdown のリンク | `node .claude/skills/docs/fix-links.cjs 旧パス=新パス ...`（切れたリンクだけを、移した先に修正する） |
| コード・skill・CI・script・文書の本文の中のパス（リンクでないもの） | `node .claude/skills/docs/replace-paths.cjs 旧パス=新パス ...`（適用済みのマイグレーションと seed、テストのデータ、アーカイブを除外する） |
| 節の番号（`<文書の名前> 第 N 節`） | 旧番号から新番号への表を作って置き換え、置き換えた行を再確認する |
| 見出しの名前（`「他のモジュールへの公開」` など） | 見出しを変えたら、`git grep` で引用を探して修正する |

- リンクでないパスの置き換えは、その場で置き換えの script を書かない。置き換えた後に `git grep` で旧パスが残らないことを確認する。
- 節の番号は、2 回付け替わらないよう 1 回で置き換える。`doc-refs.mjs` は、ない節を指す参照だけを見つける。番号が残っていて意味の違う節を指す参照は見つけない。
- 適用済みのマイグレーションと seed の SQL は修正しない（Flyway の checksum が変わり、既存の DB で起動に失敗する）。
- 完了した spec の文書（`docs/08-spec/archive/` の下）は、中のリンクも修正しない。理由：アーカイブは当時の記録で、当時の状態は Git の履歴で読めるため（開発の進め方 第 1.4 節）。
- コードが多く引用している文書の名前（`管理画面の構成` など）は、見出しを変えずに残す。

## 5. 語の一括の置き換え

言い換えの一覧に語を追加し、文書の全体で同じ語を置き換えるときの手順。

1. 活用の対応表を作る：元の語の活用ごとに、新しい語の形を書く（調べる→調査する、調べた→調査した、調べて→調査して、調べ方→調査の方法）。
2. 置き換える。script はスクラッチパッドに書き、第 4 節と同じもの（適用済みのマイグレーションと seed、テストのデータ、アーカイブ）を除外する。
3. 崩れを探す：対応表にない活用は置き換えの後に元の語尾が残り、`確認直す`・`確認きれない`・`確認方は`のような崩れになる。新しい語の語幹の後に続くかなを `node .claude/skills/docs/suffixes.cjs 確認` で数え（少ない順に、続き方、数、最初の場所を表示する）、少ないものを 1 件ずつ読む。git grep の文字の範囲（`[ぁ-ん]`）は、Windows で日本語の 1 文字に当たらないので使わない。
   完了の条件：数の少ない続き方を全て読み、崩れを修正した。
4. `ja-text.json` に新しい語を追加し、元の語が残らないことを確認する（第 3 節の手順 4）。

- 複合動詞（`〜し直す`・`〜し込む` など）の後半だけを置き換えない。理由：`書き直す` の `直す` だけを「修正する」に替えると、前半のかなに漢語が直接続く崩れた語になり、一括の置き換えで実際に起きたため。前半を含む語ごと置き換える（`書き直す` → 「書き換える」「再作成する」）。崩れの語は `ja-text.json` の error にあり、`ja-text.mjs` が失敗にする。
