# フロントの書き方

原則は [constitution](../constitution.md) 第 2・12 節。アプリごとの構成（ディレクトリ、API の呼び出し、表示の決まり、画面の追加手順）は [管理画面の構成](../frontend/admin.md) と [店舗画面の構成](../frontend/store.md) にあり、本書は両方に共通する書き方と、構成の文書から引くべき規則だけを書く。

## 1. 置き場所

### 1.1 画面に依存しない処理は `lib/` の関数にする

- **規則**：判定、変換、表示の整形、列挙の表示名は、`lib/` の関数（React に依存しない）にし、横に単体テストを置く。画面の部品は、その関数を呼ぶだけにする。
- **理由**：規則を描画なしの速いテストで確かめ、画面を作り直しても規則が残るようにするため（constitution 12.2）。
- **確かめ方**：人手（見直し）。

### 1.2 機能ごとに `features/<機能>/`

- **規則**：画面と、その画面だけで使う部品・処理は `features/<機能>/` に置く。複数の機能で使う部品は `components/`、shadcn/ui の生成物は `components/ui/`（手で直さない）。
- **理由**：機能を足す・消すときに触るファイルを 1 か所にまとめるため。
- **確かめ方**：人手（見直し）。shadcn/ui の生成物は Biome の対象から外してある（各プロジェクトの `biome.jsonc`）。

## 2. API

### 2.1 生成した型で呼ぶ

- **規則**：API は `openapi-fetch`（管理画面は `openapi-react-query` の `$api`）で、OpenAPI から生成した型を使って呼ぶ。パスや応答の型を手で書かない。
- **理由**：契約が変わったときに、型チェックで食い違いが分かるようにするため（constitution 9）。
- **確かめ方**：自動（型チェック）。

### 2.2 エラーの文は API の `message` を出す

- **規則**：業務のエラーと入力のエラーは、API のエラーの応答の `message`（項目ごとは `errors`）をそのまま出す。画面で文を作るのは、通信の失敗など API の応答がないときだけ。
- **理由**：メッセージの正本をバックエンドの 1 か所にするため（constitution 9）。
- **確かめ方**：人手（見直し）。

## 3. 店舗画面のサーバーアクション

### 3.1 `catch` では `unstable_rethrow` を先に呼ぶ

- **規則**：サーバーアクションで例外を `catch` するときは、最初に `unstable_rethrow(error)` を呼ぶ。`redirect` は try の外で呼ぶ。
- **理由**：Next.js の `redirect`・`notFound` は例外で移動を知らせるので、`catch` で飲み込むと、ログインの画面への移動などが通信の失敗として扱われてしまうため。
- **確かめ方**：人手（見直し）。サーバーの処理のテストは段階 3 で足す（spec 004 の DC-14）。

### 3.2 結果は `ActionResult` で返す

- **規則**：サーバーアクションは失敗を例外にせず、`ActionResult`（`lib/actionResult.ts`）で返す。ただし 401 はログインの画面へ移す。
- **理由**：操作した部品の近くに結果を出し、入力を消さないため（[店舗画面の構成](../frontend/store.md) 第 4.1・6 節）。
- **確かめ方**：人手（見直し）。

## 4. 整形と lint

- **規則**：Biome の設定（`biome.jsonc`）に従う。インデントは 2 文字、行の長さは 120、文字列は単一引用符、文末のセミコロンは要るところだけ。Tailwind のクラスの並びは Biome が揃える。
- **理由**：書き方の揺れを道具で無くし、見直しで扱わないため。
- **確かめ方**：自動（`pnpm lint`。CI）。

## 5. 共有のパッケージ（`frontend/shared/`）

### 5.1 入れるもの・入れないもの

- **規則**：管理画面と店舗画面の 2 つ以上で使い、画面の枠組み（Vite・Next.js）と API の接続に依存しないものだけを `@ec-site/shared` に入れる（カテゴリの木、ログインの戻り先、クラス名の結合、数・日付・金額の整形、同じ表示の部品とテーマ、共通の文言）。API の接続（接続先と認証が違う）、認証、画面の機能、サーバーアクションは入れない。共有のものは、各画面の機能を import しない。
- **規則**：shadcn/ui の CLI で部品を足すときは、今のとおり各画面の `components/ui/` に足す（`components.json` は変えない）。2 つの画面で同じ内容になったら、`frontend/shared/src/ui/` に移す。共有の部品は、店舗画面のサーバーコンポーネントからも使えるよう、要るものに `"use client"` を付けたままにする（管理画面では意味を持たない）。
- **規則**：共有の部品のクラスは、各画面の CSS の `@source` で Tailwind に読ませる（`node_modules` の先は自動では読まない）。
- **理由**：同じ処理と部品を 1 か所で直せるようにし、片方の画面の都合をもう片方に持ち込まないため。
- **確かめ方**：人手（見直しで、admin と store に同じ内容のファイルがないかを比べる）。共有のものが各画面を import しないことは、型チェック（パッケージの依存にない）。

## 6. 画面の URL

- **規則**：画面の URL は 1 か所で作る（管理画面は `src/app/paths.ts` の `paths` の関数。店舗画面は spec 006 の段階 4 で決めた方法）。`<Link>`・`navigate()`・`redirect()` などに URL の文字列を直接書かない。URL に入る値（ID など）は関数の引数の型で確かめる。
- **理由**：URL を変えるときに直す所を 1 か所にし、間違った URL を型チェックで見つけるため。
- **確かめ方**：人手（見直しで `git grep` で、パスの文字列を直接書いた所を探す）。

## 7. 表示の文言とロケール

### 7.1 表示の文言は文言のファイルに置く

- **規則**：見出し、ボタン、ラベル、知らせ、確認の文、エラーの既定の文、ページの題名は、文言のファイル（`messages/ja.json`）に置き、画面のコードではキーで引く。値は名前で差し込む（`{code}を上へ`）。コードの中で組み立てる表示名（`画像 ${n}` など）も文言にする。
- **例外**：テストの中の文字、開発者だけが見るログ、アイコンの代わりの記号、API の応答の文（バックエンドが文言を持つ。第 2.2 節）。
- **理由**：文言を 1 か所で管理し、2 つ目の言語を足せるようにするため。
- **確かめ方**：自動（日本語の文字を含む JSX の文字と属性を探す検査。`scripts/ci/`。spec 006 の段階 7 で入れる）。存在しないキーは型チェックで失敗する。

### 7.2 文言のキーの形

- **規則**：`<機能>.<画面か部品>.<項目>`（例：`tax.list.title`）。共通のものは `common.<項目>`。英小文字で始める `camelCase` を `.` でつなぐ。
- **理由**：キーから表示する所を引けるようにするため。
- **確かめ方**：人手（見直し）。

### 7.3 ロケールは 1 か所

- **規則**：既定のロケール（`ja-JP`）は `frontend/shared/src/locale.ts` だけに書く。数・日付・金額の整形とページの言語（`lang`）は、そこから取る。`Intl.*` にロケールを直接書かない。
- **理由**：言語を足すときに、変える所を 1 か所にするため。
- **確かめ方**：人手（見直しで `git grep "Intl\."`）。

## 8. 店舗画面のサーバーの設定とログ

### 8.1 環境変数は起動のときに確かめる

- **規則**：本番（`NODE_ENV=production`）で、Cookie の暗号の鍵（`AUTH_SECRET`）、IdP の client の ID と secret、IdP の場所、API の場所がなければ、サーバーの起動（`instrumentation.ts` の `register()`）で、足りない名前を並べて失敗させる。ローカル用の既定の値は、開発のモードとテストでだけ使う。モジュールを読み込むときには確かめない（`next build` も本番のモードで動き、CI のビルドには secret がないため）。
- **理由**：設定を忘れたまま、公開されている既定の値で動き出さないようにするため（バックエンドの設定の値と同じ考え。[バックエンドの書き方](backend.md) 第 6.1 節）。
- **確かめ方**：自動（起動の確かめの単体テスト）。

### 8.2 サーバー側のログは 1 行 1 件の JSON

- **規則**：店舗画面のサーバー側のログは、`src/lib/server/log.ts` で 1 行 1 件の JSON（時刻、レベル、メッセージ、追跡の ID、項目）にする。レベルは、利用者の操作が失敗したが続けられるものを `warn`、予期しない失敗を `error`、調べるための記録を `info` にする。バックエンドへの要求には W3C の `traceparent` を付け、同じ追跡の ID をログに出す。`console.*` を直接呼ばない。
- **理由**：バックエンドのログと同じ追跡の ID で、1 つの要求を辿れるようにするため。
- **確かめ方**：自動（ログの部品の単体テスト）。`console.*` を直接呼ばないことは人手（見直し）。
