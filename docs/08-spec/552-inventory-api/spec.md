# Spec 552：在庫と税のモジュールが公開する API を整える

種類：整理　規模：M　ステータス：確定

## 背景と目的

#458 の main 全体の書き方と構成のレビューで、在庫と税のモジュールが公開する API について次の 2 つが見つかった。

- #485：在庫の引当の API の契約を、呼ぶ側（注文）の使い方に頼って守っている。
  - 「引き当てる」操作は、在庫の行をロックしてから、持ち主の前の引当を削除する。この順は、「減算に置き換える」操作の順とも、在庫の設計の順（持ち主の引当を削除してから在庫をロックする）とも逆である。今は注文が毎回新しい持ち主（注文手続き）で呼ぶので、この順の違いによるデッドロックは起きない。API の説明どおり同じ持ち主の引当の置き換えに使うと、デッドロックになるおそれがある。
  - 不正な数量（0 以下）と、注文に由来する調整の理由と増減量の符号の不一致を、入口で確認していない。
- #478：注文が、他のモジュールの API をループの中で 1 件ずつ呼ぶ箇所が 2 つある。ループの中で SQL を実行しない決まりに合わない。呼ばれる側にまとめて扱う操作がないので、注文の側だけでは直せない。
  - 注文手続きの引当の解除：カートの注文手続きごとに、在庫の API で引当を解く。
  - 見積もり：税区分ごとに、税の API で指定時点の税率を取得する（同じ税区分は 1 回にまとめている）。

#485 の 2 つ目は、#550 の T550-01-08 で済んでいる。数量が 0 以下のときと、理由と符号が合わないときは、在庫と引当を変える前に前提違反の例外にし、テストもある。この spec では変えない。

この spec は、引当のロックの順を設計どおりにそろえる。在庫と税の API にまとめて扱う操作を設け、注文の 2 か所をまとめて呼ぶ形にする。消費者・運営者に見える振る舞いは変えない。API の契約（OpenAPI）、DB の構造、AC も変えない。追跡の issue は #552（組の issue）。sub-issue は #485 と #478。#544（リリースの前の整理）の段階 3 の線 B の 3 番目である。

## スコープ

| 含める | 含めない |
|--------|----------|
| 「引き当てる」操作で、持ち主の引当を削除してから在庫をロックする順にすること | 数量と符号の確認（#550 で済み） |
| 在庫の API に、複数の持ち主の引当をまとめて解く操作を設けること | 送料の税率の取得（ループの中でない） |
| 税の API に、複数の税区分の指定時点の税率をまとめて返す操作を設けること | 注文以外のモジュール（カート、店舗）の税の呼び出し |
| 注文の 2 か所を、まとめて呼ぶ形にすること | レポートの送料の税率の取得 |
| 在庫の機能仕様、在庫と税の設計の文書の修正 | |

決定（issue 担当のセッションが利用者に代わって 2026-11-19 に確認した）：

- 規模：M とする（[開発の進め方](../../05-開発規則/workflow.md)の「規模」の特例）。
  - 判定の表では、3 つのモジュール（在庫、税、注文）にまたがるので L に当たる。
  - M にする理由：API の契約（OpenAPI）と DB の構造は変えず、モジュールをまたぐ決定は在庫と税の公開の操作の形（決定 3、4）だけで、spec の決定に書けるため。plan に書く中身（API と AC の対応、モジュールをまたぐ設計）がほとんどない。
  - 前例は spec 569（複数のモジュールの公開の API を変えた整理、規模 M）。
- 決定 1（引き当てる操作の順）：「引き当てる」操作は、持ち主の前の引当を先に削除してから、在庫の行をバリアント ID の順にロックする。「減算に置き換える」操作と同じ順にする。
  - 同じ持ち主の引当を置き換える、という API の契約は残す。
  - 引当のリポジトリの「置き換える」操作から、削除する処理を除き、「作る（加える）」操作にする。
  - 足りないときは、操作は持ち主の前の引当を削除したままで、足りない品目を返す。「減算に置き換える」操作と同じ扱いである。呼ぶ側（注文）はトランザクションをロールバックするので、前の引当は元に戻る。
  - 注文は毎回新しい持ち主で呼ぶので、消費者に見える振る舞いは変わらない。
  - 退けた案：「引き当てる」操作を新しい持ち主だけの契約にし、削除する処理をなくす案。退けた理由：同じ持ち主で誤って 2 回呼んだとき、在庫の品目が 1 回目と違えば DB の一意の制約でも検出できず、引当が重なって残るため。
- 決定 2（数量と符号）：#485 の 2 つ目は #550 で済んでいるので、この spec ではコードを変えない。
  - #485 の完了の目安は「不正な数量が業務のエラーになるテスト」である。
  - #550 は、呼ぶ側がモジュールの中だけで、呼び出し元の誤りなので、利用者に返す業務のエラーにせず前提違反の例外にすると決めた。この spec はその決定に従う。
- 決定 3（在庫：まとめて解く）：在庫の API の「解く」操作を、複数の持ち主を受け取る形に置き換える。
  - 1 件の持ち主を受け取る操作は残さない。理由：呼ぶ側は注文の 1 か所だけで、1 件は 1 件の集まりとして渡せるため。
  - 渡した持ち主の集まりが空なら、状態を変えずに終える。
  - 引当のない持ち主は、状態を変えずに飛ばす（今と同じ）。
  - 引当は、持ち主の数によらず、1 回の削除の SQL で削除する。
  - 呼んだ側のトランザクションに加わる（今と同じ）。
- 決定 4（税：まとめて返す）：税の API に、複数の税区分と時点を受け取り、税区分ごとの指定時点の税率を返す操作を加える。
  - 税区分がない、またはその時点の税率がない税区分は、結果に含めない。
  - 税区分の読み込みは、税区分の数によらず 1 回の問い合わせにする。
  - 1 件の税区分を受け取る今の操作は残す。理由：見積もりの送料の税率と、レポートの送料の税率が、1 件で使うため。
- 決定 5（注文）：注文の 2 か所を、まとめて呼ぶ形にする。
  - 注文手続きの引当の解除：カートの注文手続きの ID をまとめて、在庫の API を 1 回呼ぶ。
  - 見積もり：バリアントの税区分を重複なく集め、税の API を 1 回呼ぶ。税区分の率がないときの扱い（その品目の単価がない）は今と同じ。
  - 注文の在庫と税の port も、同じ形に変える。
- 決定 6（文書）：
  - 在庫の機能仕様の「操作」の表：「引き当てる」の行に、持ち主の前の引当を先に削除することを書く。「解く」の行を、複数の持ち主の引当を削除する形にする。
  - 在庫の設計の「注文による引当と在庫数の変更」の、順序の箇条と、注文手続きの開始との関係の箇条を、引き当てる操作も持ち主の引当を先に削除する、という形に書き換える。
  - 税の設計の「他のモジュールへの公開」の表の「指定時点の税率」を、複数の税区分をまとめて返せる形にする。
  - AC も業務規則の番号（BR）も追加しない。

## 目的と完了条件

### DS-552-1 在庫の引当のロックの順が、呼ぶ側の使い方によらず設計どおりになる（D / P1）

- **DC-552-1** 「引き当てる」操作が、持ち主の引当を削除してから在庫の行をロックしている。
- **DC-552-2** 引当の既存の統合テスト（同じ持ち主が再度引き当てるときと、1 品目でも足りないときを含む）が通る。
- **DC-552-3** 数量が 0 以下の品目と、理由と増減量の符号の不一致が、在庫と引当を変える前に拒否されることを、テストで確認している（#550 で済み。この spec では有無を確認するだけ）。

### DS-552-2 他のモジュールの API を、ループの中で 1 件ずつ呼ばない（D / P1）

- **DC-552-4** 在庫の API で複数の持ち主の引当をまとめて解けることを、1 件と複数件のテストで確認している。他の持ち主の引当が残ること、持ち主の集まりが空なら状態を変えないことも確認している。
- **DC-552-5** 税の API が、複数の税区分の指定時点の税率をまとめて返せることを、1 件と複数件のテストで確認している。税率のない税区分と存在しない税区分が結果に含まれないことも確認している。
- **DC-552-6** 注文は、引当の解除と見積もりで、他のモジュールの API をループの中で呼んでいない。

### DS-552-3 文書と検査が通る（D / P1）

- **DC-552-7** 在庫の機能仕様と設計、税の設計が、決定 6 の形になっている。
- **DC-552-8** `./gradlew check` が通る。
