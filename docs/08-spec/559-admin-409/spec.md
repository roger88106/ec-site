# Spec 559：管理画面の共有のコンポーネントとフックで、編集中の入力を失わず、409 から抜けられるようにする

種類：機能　規模：M　ステータス：確定

## 背景と目的

管理画面の全ての画面が使う、共有のコンポーネントとフックの 3 つに、次の振る舞いがある。新しい画面も同じ振る舞いになる。追跡の issue は #559（sub-issue：#524、#206）。関わる文書は[管理画面の構成](../../02-設計/apps/admin.md)。

| 対象 | 起きること |
|------|------------|
| 取得の状態の表示 | 再取得が失敗すると、取得済みのデータがあっても画面全体をエラー表示に置き換える。編集中のフォームが画面から消え、入力が失われる ※1 |
| バージョンを持つリソースのフォーム | 編集画面の複数のフォームが、商品のバージョンをそれぞれ保持する。同じ画面の自分の別の操作で、入力中のフォームの保存が 409 になる ※2 |
| 更新の操作の定型 | 更新が 409・404 で失敗しても再取得しない。再読み込みのボタンがない画面もある（バリアントの並び替えなど）。画面が古いデータのままで、同じ操作が失敗し続ける |

※1：TanStack Query の既定（別のタブから戻ったときに再取得する）と重なり、戻った時点で通信が一時的に失敗すると起きる。更新の成功の後の再取得が失敗したときも同じになる。

※2：例：基本情報の名称を変え、保存の前に画像を追加する。409 の後は、入力を捨てるしかない。

画像の登録にも同じ種類の問題がある（#524 のコメント）。複数の画像を登録している間に、同じ画面の他のカード（状態の切り替え、バリアントの販売停止・再開）を操作すると、残りの画像が 409 で登録されない。登録ごとのバージョンを「表示していた商品のバージョン ＋ 何枚目か」で予測して送っていること、状態の切り替えがバージョンを受け取らずにバージョンを上げることが原因である。画面には「他の人が先に更新しました」と表示されるが、原因は自分の操作である。

#524 は、コードを読んでの推定で、画面での再現は未確認である（issue に書いてある）。画像の件は、今の `develop` のコードで確認した（#524 のコメント）。

#206 は、409 の流れのテストで、準備の関数が少しずつ違う形で 4 回書かれている、という issue である。4 回は、商品の編集（基本情報、公開期間、バリアントの追加）と税率のテストにある。409 の流れは、次の順である：入力、他の人の更新、再取得、保存（409）、再読み込み、再保存。着手の条件は、同じ形のテストを加えるとき。この spec で 409 の流れのテストを変えるので、条件が成り立つ。

## スコープ

| 含める | 含めない |
|--------|----------|
| 取得の状態の表示（再取得の失敗の表示） | 店舗画面（#560 が扱う） |
| バージョンを持つリソースのフォームの、基準のバージョンの進め方と再読み込み | データを新しいとみなす時間の既定の変更（決定 2） |
| 画像の登録で送るバージョン | 画像の登録中に、他のカードの操作を押せなくすること |
| 更新が 409・404 で失敗した後の再取得 | API の契約とバックエンド |
| 409 の流れのテストで使う準備の共通化（#206） | |
| 管理画面の構成の更新 | |

決定：

1. 規模は M。理由：振る舞いを変えて AC を加えるが、管理画面だけを変え、API の契約と DB の構造を変えないため。モジュールをまたぐ設計の決定がないので plan を書かない。
2. データを新しいとみなす時間は入れず、TanStack Query の既定（0）のままにする。理由は 2 つ：決定 3 で再取得の失敗が入力を消さなくなる。別のタブから戻ったときの再取得は、他の人の更新を保存の前に表示し、409 を減らす。
3. 取得の状態の表示：取得済みのデータがあれば、再取得が失敗しても画面を残し、画面の上部に取得の失敗の文と「再試行」のボタンを表示する。再取得している間は、ボタンを押せない（権限の一覧の取得の失敗と同じ形）。データがないときだけ、今のまま画面の全体をエラーの表示にする。画面の見た目が変わるので、この形を利用者が確認した。
4. フォームの基準のバージョン：入力の後にリソースのバージョンが変わったら、フォームが扱う項目の値を、基準のリソースと新しいリソースで比べる。同じなら、入力を残して基準のバージョンを新しいものに進める。違えば、今のまま入力を残し、基準を進めない（保存は 409 になる）。理由：更新の API は、フォームが扱う項目だけを更新するため。例：商品の基本情報の更新の本文は、名称・説明・税区分・税抜価格・カテゴリだけである。基準を進めても、他の項目の更新を上書きしない。
   - バリアントの追加のフォームは、値が商品の軸だけで決まるので、他の人が価格などを変えても、再取得した後なら 409 にならない。追加は既存の値を上書きしないので、古い入力で他の人の変更を上書きする懸念（[管理画面の構成](../../02-設計/apps/admin.md)の「バージョンを持つリソースのフォーム」の ※1）に当たらない。今のテスト「バリアントの追加の入力中に他の人が商品を更新した（409）」は、再取得する前に追加して 409 になる流れに書き換える。
5. 再読み込みのボタン：バージョンが変わらなくても、最新の値でフォームを再作成する。理由：決定 7 の再取得で、基準のバージョンが先に進むことがあり、今の実装はバージョンが変わったときだけ再作成するため。
6. 画像の登録：1 枚ごとに、登録の前に商品を再取得し、その時点のバージョンで送る（1 枚目も）。他の人の更新の後でも 409 にしない。理由：画像の登録は末尾に加えるだけで、他の人の変更を上書きしないため。枚数の上限は、サーバーが検証する。
7. 更新が 409 か 404 で失敗したら、成功のときと同じ対象を再取得する。エラーの表示は残す。409 は、バージョンの不一致に限らず、業務の 409（名称の重複など）も含める。理由：再取得しても入力は残り、害がないため。
8. 409 の流れのテストの準備（#206）は、テストの基盤のフォルダーにヘルパーを 1 つ置いてまとめる。
9. 管理画面の構成を、次のように修正する。
   - 「API の呼び出し」：409・404 の後の再取得。
   - 「画像のアップロード」：決定 6。
   - 「バージョンを持つリソースのフォーム」：決定 4・5。
   - 「結果の知らせ方」の取得の失敗の行：決定 3（取得済みのデータがあれば、再取得の失敗で画面を消さない）。

決定に出る識別子：

| 論理名 | 識別子 |
|--------|--------|
| 取得の状態の表示 | `QueryState` |
| バージョンを持つリソースのフォーム | `useVersionedForm` |
| 再読み込み | `reloadAfter` |
| 更新の操作の定型 | `useApiMutation` |
| 画像の登録のカード | `ProductImagesCard` |
| データを新しいとみなす時間 | `staleTime` |

## User stories

| US | 誰が | 何をできる | なぜ |
|----|------|------------|------|
| US-559-1 | 運営者 | 編集中に再取得が失敗しても、入力を失わずに作業を続けられる | 一時的な通信の失敗で入力し直さないため |
| US-559-2 | 運営者 | 同じ画面の自分の操作の後も、入力中のフォームを保存し、画像を登録できる | 自分の操作が原因の 409 で入力を捨てないため |
| US-559-3 | 運営者 | 更新が 409・404 で失敗した後、最新の状態で操作をやり直せる | 同じ操作が失敗し続けないため |

## 受け入れ条件

### US-559-1 再取得の失敗で入力を失わない（B / P1）

- **AC-559-1** 取得済みのデータがある画面で再取得が失敗したとき、画面とフォームの入力を残し、上部に取得の失敗の文と「再試行」のボタンを表示する。
- **AC-559-2** 「再試行」で取得に成功したら、取得の失敗を表示しない。再取得している間は、「再試行」のボタンを押せない。
- **AC-559-3** 取得済みのデータがない画面で取得が失敗したときは、画面の全体を取得の失敗の表示にする（今の振る舞い）。

### US-559-2 自分の操作の後も保存と画像の登録ができる（B / P1）

- **AC-559-4** フォームの入力中にリソースのバージョンが上がっても、フォームが扱う項目のサーバーの値が変わっていなければ、入力を残し、保存は新しいバージョンで送って成功する。例：基本情報の名称を変え、画像を追加してから保存する。
- **AC-559-5** フォームが扱う項目のサーバーの値が変わっていれば、入力を残し、保存は 409 になる（今の振る舞い）。
- **AC-559-6** 409 の後に「再読み込み」を押すと、基準のバージョンが先に進んでいても、フォームを最新の値で再作成し、409 のエラーを表示しない。
- **AC-559-7** 複数の画像を登録している間に、同じ画面の他の操作で商品のバージョンが上がっても、残りの画像を登録する。
- **AC-559-8** 画像の登録は、他の人が商品を更新した後でも 409 にならない。

### US-559-3 409・404 の後に最新の状態でやり直せる（B / P1）

- **AC-559-9** 更新が 409 か 404 で失敗したら、成功のときと同じ対象を再取得し、エラーの表示は残す。例：バリアントの並び替えが 409 になった後、もう一度押すと最新のバージョンで送って成功する。
