校閲役（`ja-proofreader`）を通った日本語や、校閲役を通す前に利用者の確認に出した日本語に、後から通じにくい語が見つかる。例は、spec 276 の草案の `判定器`・`護り`・`境界` と、spec 283 で置き換えた `無記憶`・`弾` である。書く側の漏れは spec 283 で修正した。本 spec は校閲の側の漏れを扱う。

今の校閲役は、1 つのサブエージェントが候補を見つけ、挙げるかも決める。見逃しと誤検出を集める場所がない。そのため、指示やモデルを替えたときに良くなったかを測れない。#294 に集め始めた。

参考にしたのは、Anthropic の記事「Solving code review at Anthropic」（<https://claude.dev/blog/solving-code-review-at-anthropic/>、2026-10-31 に読んだ）である。記事のコードレビューの構成は次のとおりである。

| 項目 | 記事の構成 |
|------|------------|
| 役の分け方 | 見つける役が候補を挙げ、別の確認する役が候補ごとに本物かを判定する。判定を通った候補だけを示す |
| 評価の材料 | 過去の不具合を評価の例として集め続ける。誤検出は、評価の例とは別に、問題のない変更に当てて数える |
| 変更の採用 | 指示・ツール・モデルの変更ごとに全ての例で採点し、点が上がった変更だけを残す |

### 1.1 本 spec の用語

本 spec の中だけで使う語である。後で用語集に加えるのは、校閲役・見つける役・確認する役・評価の一覧の 4 つである（DC-295-39）。

| 用語 | 意味 |
|------|------|
| 校閲 | 利用者が中国語で指示する環境で、変更した日本語を読み、通じにくい語と不自然な言い回しを挙げる作業（skill `review` の手順 9） |
| 校閲役 | 校閲を行うサブエージェント。本 spec の実装の後は、見つける役と確認する役の 2 つを指す |
| 見つける役 | 校閲の候補を多めに挙げる役 |
| 確認する役 | 見つける役の候補を 1 件ずつ読み、挙げるか（誤りか、読む人が引っかかるか）を判定する役 |
| 評価の一覧 | 校閲役を採点するための例の一覧（`.claude/skills/review/evals/ja-proofread.md`） |
| 見逃しの例 | 評価の一覧の例のうち、挙げるべき語句を含む文 |
| 誤検出の例 | 評価の一覧の例のうち、挙げてはいけない文（正しい日本語） |
| 指摘の表 | 校閲役が返す表（ファイル・行・今の書き方・修正案・理由） |

## 6. 決めたこと

利用者の確認で変えてよい。

### 決めたこと 1：定義の名前

見つける役は今の `ja-proofreader` を書き換えて使い、確認する役は `ja-proof-verifier` を新しく作る。

- 理由：`ja-proofreader` を指す箇所（skill `review` の 2 つのファイル、`zh-mixing.test.cjs`）をそのまま使え、アーカイブした spec の記録の名前とも合うため。
- 別の案：2 つとも新しい名前（`ja-proof-finder`・`ja-proof-verifier`）にして `ja-proofreader` を削除する。役の名前と定義の名前が一致するが、参照の修正が増える。

### 決めたこと 2：モデル

見つける役は汎用、確認する役は高性能にする。

- 校閲の対象の文書を書くセッションは、spec 担当が高性能、issue 担当が汎用である。この組み合わせなら、どちらが書いても、一方の役は書いたセッションと違うモデルになる。
- 候補を汎用で集め、採否を高性能で決める形は、[エージェントの作業フロー](../../05-開発規則/subagents.md)の「運用の規則」の、文脈で判断する候補の扱いと同じである。
- 確認する役が読むのは候補と前後の行だけなので、高性能でも費用は小さい見込みである。未確認なので、採点で token を記録する。
- 定義に `model` を書くか、呼び出しで区分を指定するかは、spec 284 の「決めること 5」に合わせる。

### 決めたこと 3：記録の置き場所

`subagents-results.md` に、新しい節「校閲の評価の結果」を置く。
