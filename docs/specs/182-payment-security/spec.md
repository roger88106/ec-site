# Spec 182：決済の設定の検証、セキュリティと設定の指摘、出荷の読み取りを整える

ステータス：草案

## 1. 背景と目的

MVP 019 の全体のレビューと spec 155 の最後のレビューで、決済の設定の検証、セキュリティと設定の推奨の指摘、出荷の登録の読み取りの置き場所が残った。本 spec はこれらを直す。

追跡の issue は [#182](https://github.com/roger88106/ec-site/issues/182) で、扱う issue は #79、#90、#175 である。作業ブランチは `182-payment-security` である。

2026-10-24 に、今の `develop`（spec 155 のマージの後）で、各項目が残っているかをコードで確認した。全て残っていた。

| issue | 項目 | 今のコード |
|-------|------|------------|
| #79 | 支払画面の期限と設定 `ecsite.payment.deadline` を結ぶ検証がない | 支払画面の期限は Stripe の実装の定数（31 分）で、支払の期限の設定（既定 30 分）に上限の検証がない |
| #90 | `security` を書き忘れた店舗の操作が公開になる | 店舗の操作の token の要否は、`store.yaml` の操作に `security` がなければ「不要」とする。今は公開の操作（商品、カテゴリ、カートの作成、店舗の情報、住所の補助）が `security` を書かない |
| #90 | 秘密の値を持つ設定の record の `toString` が値を伏せない | Stripe の設定は伏せる。画像の保存先（S3 の秘密の鍵）と画像の変換（imgproxy の鍵と salt）の設定は伏せない |
| #90 | 復元の失敗で集約の内容を `error` のログに出す | 集約を戻す共通の補助が、保存した状態の全体をデバッグ用のメッセージに入れ、システムのエラーとして `error` のログに出る |
| #90 | `zipkin` の接続先の既定値が共通の設定にある | 共通の設定（`application.yml`）に `http://localhost:9411` があり、local 以外の環境でも送信を試みる |
| #90 | `Location` が `forward-headers-strategy` に依存 | 作成の応答の `Location` は、今のリクエストの URI から絶対 URL を作る。`server.forward-headers-strategy` を設定していないので、プロキシの後ろでは内部のホストを指す |
| #175 | 出荷の登録が、決済を呼ぶ前に集約を Repository から直接読む | 出荷の登録の service が、売上確定の前に注文を Repository から読み、出荷できるかを確認する（バックエンドの書き方 第 1.1 節の「外部の呼び出しの前の読み取り」に反する） |

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。消費者・運営者の画面の振る舞いは変えない。運用（起動の条件、トレースの送信、API の応答の見出し）に見える変化は、第 6 節に挙げる。

## 2. 規模

規模は L を提案する。理由：決済、注文、画像、共通コード、設定（認可）の 5 か所にまたがり、開発の進め方 第 4.2 節の「2 つ以上のモジュールにまたがる」に当たるため。API の契約（`store.yaml` の `security` と `Location` の説明）も変えうる。

## 3. 用語

| 用語 | 意味 |
|------|------|
| 支払画面の期限 | 決済サービス（Stripe Checkout）の支払画面が開ける期限。Stripe は作ってから 30 分以上 24 時間以下を求める |
| 支払の期限 | 注文日時に設定 `ecsite.payment.deadline` を足した時刻。過ぎると期限切れのジョブが支払を「支払なし」にする |
| 公開の操作 | 店舗 API のうち、会員の token なしで使える操作 |
| 秘密の値 | 鍵、パスワード、署名の鍵など、ログに出してはいけない設定の値 |

用語集に追加する語は、plan で決める。

## 5. 目的と完了条件

### DS-182-1 支払の期限と支払画面の期限（#79 / P1）

- **DC-182-1** 支払の期限の設定が、支払画面の期限と食い違う値（支払の期限より前に支払画面が閉じる値）のとき、アプリは起動に失敗するか、支払画面の期限を支払の期限から求める。どちらにするかは Q1。
- **DC-182-2** 決済のモジュールの設計書の設定の表に、支払の期限の制約（上限か、支払画面の期限の求め方）がある。
- **DC-182-3** 制約を、設定の検証か支払画面を作る処理の単体テストで確認する。

### DS-182-2 店舗の操作の公開（#90 / P1）

- **DC-182-4** `store.yaml` の全ての操作が `security` を書く。公開の操作は、空の要件（`{}`）で公開であることを明示する。
- **DC-182-5** `security` を書かない操作が `store.yaml` にあると、検査が失敗する。検査の置き場所（起動か、テストか）は Q2。
- **DC-182-6** DC-182-5 の検査は、一時的に `security` を消した操作で失敗することを確認する。

### DS-182-3 ログに出さない値（#90 / P1）

- **DC-182-7** 秘密の値を持つ設定の record（画像の保存先、画像の変換）の `toString` は、秘密の値を伏せる。単体テストで確認する。
- **DC-182-8** バックエンドの書き方に、秘密の値を持つ設定の record の `toString` を伏せる規則と、その確認方法がある。
- **DC-182-9** 集約を戻すのに失敗したときのメッセージは、集約の名前を含み、保存した状態の内容を含まない。理由：保存した状態は購入者の氏名・住所・メールアドレスなどを含み、`error` のログは長く保存され、広く読まれるため。原因の例外は残す。
- **DC-182-10** DC-182-9 を、共通の補助の単体テストで確認する。

### DS-182-4 環境に依存する値（#90 / P1）

- **DC-182-11** 共通の設定は、トレースの送信先を持たない。local の profile がローカルの Zipkin に送る。local 以外の環境は、環境変数で送信を有効にしたときだけ送る。
- **DC-182-12** 環境変数の一覧（[環境変数](../../guides/environment.md)）が、DC-182-11 の後の既定値と有効にする方法を書く。
- **DC-182-13** 作成の応答の `Location` が、`server.forward-headers-strategy` の設定によらず、クライアントから使える URL を指す。方法は Q3。
- **DC-182-14** DC-182-13 を、作成の応答の補助の単体テストか API のテストで確認する。

### DS-182-5 出荷の登録の読み取り（#175 / P1）

- **DC-182-15** 出荷の登録で、売上確定の前に注文が出荷できるかを確認する読み取りは、注文の参照の service にある。出荷の登録の service は、注文の Repository に依存しない。
- **DC-182-16** 出荷の登録の振る舞い（注文がない、受付でない、与信の期限切れ、決済サービスに接続できない、のエラー）は変わらず、既存の出荷の登録のテストが通る。

## 6. 振る舞いと文書への影響

| 変化 | 誰に見えるか | AC | 変える文書 |
|------|--------------|----|------------|
| 支払の期限の設定が制約を外れると起動に失敗する（Q1 が A のとき）、または支払画面の期限が支払の期限から決まる（Q1 が B のとき） | 運用（設定）。既定値（30 分）では変わらない | 変えない | 決済のモジュールの設計書（設定の表、支払画面の期限） |
| `security` を書かない店舗の操作があると、起動に失敗する（Q2 が A のとき） | 開発者 | 変えない | `store.yaml`（公開の操作に `security` を追加）、認可を書く設計書・規則（plan で特定する） |
| トレースが、local 以外では既定で送られない | 運用 | 変えない | 環境変数の一覧、開発環境の起動 |
| `Location` の形が変わる（Q3 が A のとき、相対の URL になる） | API のクライアント。店舗画面と管理画面は `Location` を使わない（作成した ID を本文から読む） | 変えない | `store.yaml`・`admin.yaml` の `Location` の説明、バックエンドの書き方 第 2.2 節 |

- AC は追加・変更しない。
- データベースの構造は変えない。

## 7. 非機能要件

- **DN-182-1** 消費者・運営者の画面の振る舞い（API の応答の本文、画面、メールの文面）を変えない。
- **DN-182-2** データベースの構造を変えない。API の契約は、第 6 節の変化だけを変える。
- **DN-182-3** AC を追加・変更しない。
- **DN-182-4** 起動の検証と検査は、違反を直した後に有効にし、一時的に違反を入れて失敗することを確認する。
- **DN-182-5** `./gradlew check` と CI が通る。

## 9. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| 管理 API の操作の権限の書き忘れ | 扱わない。管理 API は全ての操作が token を要し、権限の対応にない操作は拒否する |
| 他の外部の呼び出しの前の読み取り（注文の取消など） | 本 spec で見つけたら第 10 節に記録し、起票の案に回す |
| トレースの送信先を Zipkin 以外にする | 起票しない |
| ログの形（ECS の JSON）の変更 | 起票しない |

## 10. Open questions

### Q1 支払の期限と支払画面の期限の結び方（DC-182-1）

| 案 | 内容 | 利点 | 欠点 |
|----|------|------|------|
| A（推奨） | 支払の期限の設定に上限（30 分）の検証を置き、超えると起動に失敗する。支払画面の期限は今の定数のまま | 変えるのが設定の record と設計書だけ。今の運用（30 分）と一致する | 30 分より長い期限にできない |
| B | 支払画面の期限を支払の期限から求める（支払の期限に余裕を足し、30 分以上 24 時間以下に収める）。設定の上限は 24 時間未満 | 期限を長くできる | 支払画面を作る要求に支払の期限を追加するので、port と mock の実装も変わる |

推奨の理由：長い期限を使う予定がなく、B は使わない柔軟さのために変える範囲が広がるため。

### Q2 `security` の書き忘れの検査の置き場所（DC-182-5）

| 案 | 内容 |
|----|------|
| A（推奨） | `store.yaml` を読み込む今の処理で、`security` のない操作があれば起動に失敗する。単体テストで確認する |
| B | 起動では検査せず、`store.yaml` の全ての操作が `security` を書くことを単体テストで確認する |
| C | CI の検査の script（`scripts/ci/`）で `store.yaml` を検査する |

推奨の理由：読み込む処理が既にあり、書き忘れた契約が本番で動くことを確実に防げるため。`store.yaml` はアプリに含めるので、テストが通れば本番の起動で失敗することはない。

### Q3 `Location` の形（DC-182-13）

| 案 | 内容 |
|----|------|
| A（推奨） | `Location` を、ホストを含まない相対の URL（`/api/store/...`）にする。HTTP の仕様は相対の URL を許す |
| B | 共通の設定で `server.forward-headers-strategy: framework` を有効にし、プロキシの見出しから絶対 URL を作る |
| C | コードは変えず、プロキシの後ろに置くときの設定を環境変数の一覧と運用の文書に書く |

推奨の理由：A は配置によらず同じ値になり、プロキシの見出しを信頼する範囲（B は偽の見出しを受け入れうる）を考えなくてよいため。店舗画面と管理画面は `Location` を使わない。
