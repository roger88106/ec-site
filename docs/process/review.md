# 書き方の規則と見直し

書き方の規則（[バックエンド](../backend/coding.md)、[フロント](../frontend/coding.md)、[テスト](../testing/writing.md)、[コメント](comments.md)）の書き方と、spec の見直しでの使い方。

## 1. 規則の書き方

- 各文書の冒頭に「規則の一覧」（節、規則、確かめ方）を置く。
- 確かめ方は、自動（ArchUnit・Modulith のテスト、Biome、テスト、CI の script）か人手（見直しで読む）。自動のものは、使うツールやテストの名前を書く。
- 規則の節は、規則（何をどう書くか）と、1 行の理由（なぜか）を書く。細かな例外は ※ で表の下に書く。
- constitution は原則を、各文書は具体的な書き方を書く。constitution の文を写さない。
- 新しい習慣が決まったら、その spec の plan か tasks で各文書に足す。

## 2. 見直し

各 spec の最後の見直しの段階で、変えたコードを、各文書の一覧の「人手」の規則と照らす。見直しの段階の tasks は、本書を参照に挙げる。

1. 変えたファイルを、spec の最初の commit の 1 つ前（`<base>`）からの差分で探す ※1。
2. 各文書の一覧の「人手」の規則に照らして読み、合わない所を直す。直さないものは、理由を見直しの報告に書く。
3. 一覧にない習慣に気づいたら、規則に足すかを利用者に確かめる。自動で確かめられるようになった規則は、確かめ方を「自動」に直す。
4. 文書・コメント・コミットメッセージが、日本語として自然に書けていることも確かめる。

※1：`git diff -M -l0 --name-status <base> HEAD | grep -v '^R100'`。`-l0` がないと、移動が多いときに追加と削除に見える。`R100`（中身の変わらない移動）は読まなくてよい。
