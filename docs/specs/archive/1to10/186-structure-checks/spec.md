# Spec 186：バックエンドの構成の検査を強める

ステータス：確定

## 1. 背景と目的

spec 155 でバックエンドのパッケージの構成を整えたが、構成の規則のいくつかは機械で確認していない。また、構成の検査（ArchUnit と Spring Modulith のテスト）と契約のテストは、本番のクラスをテストのクラスごとに読み込み、同じ補助の処理を各ファイルに重複して書いている。そのため単体テストの heap を 1GB に上げている。

追跡の issue は [#186](https://github.com/roger88106/ec-site/issues/186) で、扱う issue は #13、#177、#178 である。作業ブランチは `186-structure-checks` である。規模は L で、利用者が 2026-10-24 に承認した（第 1.2 節）。

本 spec は spec 181（[#181](https://github.com/roger88106/ec-site/issues/181)、バックエンドのテスト）から分けた。spec 181 の草案の DS-181-6、7（DC-181-32〜44）を、番号を振り直して移した。利用者が 2026-10-24 に分けることを決めた。spec 181 の確認のための再レビュー（2026-10-24、範囲：モジュールの外のテストと、テストの土台）の指摘のうち、構成の検査とその補助に関するものを、本 spec の項目にした。spec 担当のセッションが、主な指摘を今の `develop` のコードで確認した。

- #13、#177、#178 の項目は、全て今のコードに残っていた。
- 金額の型の検査は、`application.model` の直下にある view（カート、注文、店舗、媒体の view）を検査していない。今は違反がないので通る。
- 構成の検査のうち、本番のクラスの一覧を集めて確認するもの（リポジトリの port の置き場所など）は、対象が 0 件でも通る。
- 店舗向けの並び順の既定値（新着順）は、店舗のモジュールの presentation と、カタログのモジュールの公開の API の 2 か所にある。

本 spec は整理の spec である（[文書の記号と番号](../../../../rules/notation.md)）。

### 1.1 spec 181 との分け方

| spec | 範囲 | 扱う issue |
|------|------|------------|
| spec 181 | テストの確認、AC 番号、データの干渉、書き方の規則、Repository のテスト | #80、#86、#176、#16 のバックエンドの部分 |
| 本 spec（186） | 構成の検査とその補助、テストのコメントの spec の番号 | #13、#177、#178 |

- 分けた理由：1 つの pull request が小さくなり、レビューの負担が減るため。
- 本 spec の実装は、spec 181 のマージの後に始める（利用者の決定、2026-10-24）。理由：重なりうる所（第 7 節）のうち、DC-186-14 のコメントの書き換えは spec 181 が変えるテストに必ず重なり、分けても切り分けられないため。どちらもまだ実装を始めていないので、順に行っても本 spec の完了は大きく遅れない。

### 1.2 規模

L とする（利用者の承認、2026-10-24）。理由：[開発の進め方](../../../../rules/workflow.md) 第 4.2 節の「2 つ以上のモジュールにまたがる」に当たるため（並び順の既定値は店舗とカタログのモジュール、テストのコメントは全てのモジュールのテストを変える）。また、構成の検査の補助の形と、読み込みを 1 か所にする方法（heap を測る手順を含む）を plan で決める必要があるため。

## 2. 用語

| 用語 | 意味 |
|------|------|
| 構成の検査 | 本番のクラスの依存と置き場所を確認する単体テスト。`src/test` の `architecture/` と `modulith/` にある |
| 契約のテスト | OpenAPI の契約と realm の設定を、コードと照合する単体テスト。`src/test` の `contract/` にある |
| 構成の検査の補助 | 構成の検査と契約のテストが共通に使う、本番のクラスの読み込みと、モジュールの一覧を求める処理 |

用語集に追加する語は、plan で決める。

## 4. 目的と完了条件

### DS-186-1 構成の規則の検査（D / P1）

[バックエンドの書き方](../../../../rules/backend-coding.md) の規則の一覧が「自動」とする範囲と、構成の検査が確認する範囲を一致させる。#177 の項目である。

- **DC-186-1** 集約のパッケージと値のパッケージ（`vo/`）の循環を、構成の検査が検出する（バックエンドの書き方 第 1.1 節の domain の直下）。
- **DC-186-2** パッケージの大きさの目安を超えるパッケージが、バックエンドの書き方 第 1.4 節の表と一致することを、構成の検査が確認する。表の外のパッケージが目安を超えたとき、表にあるパッケージが目安以下になったときの両方を検出する。
- **DC-186-3** バックエンドの書き方 第 1.1 節の層の依存の表の全ての組と、共通コードが設定（`config`）に依存しないことを、構成の検査が確認する。
- **DC-186-4** モジュールの公開の API（`api/`）に interface がなく、公開の API の型を公開の API の外が実装しないことを、構成の検査が確認する。spec 155 で削除した常に通る規則の代わりである。

### DS-186-2 対象の漏れと、対象が 0 件で通る検査（D / P1）

- **DC-186-5** 金額を整数で持つ項目の検査は、全てのモジュールの view と command を対象にする（バックエンドの書き方 第 1.5 節）。パッケージの名前でなく、クラスの置き場所と名前で対象を決める。
- **DC-186-6** 本番のクラスの一覧を集めて確認する構成の検査は、対象が 1 件以上あることを確認する。ArchUnit の規則で、空のときに失敗する既定（`failOnEmptyShould`）が効くものは対象外である。
- **DC-186-7** DS-186-1、2 で追加・修正した検査は、違反する例のクラスで違反を検出できることを確認する（今の `NamingTest` などと同じ方式）。

### DS-186-3 読み込みと補助を 1 か所にする（D / P1）

#13 と #178 の項目である。

- **DC-186-8** 構成の検査と契約のテストは、本番のクラスを構成の検査の補助で 1 回だけ読み込み、テストのクラスごとに読み込まない。モジュールの一覧（Spring Modulith の `ApplicationModules`）も 1 回だけ作る。
- **DC-186-9** DC-186-8 の後、単体テストの heap の上限（mutation test の設定を含む）を、測った値に合わせて下げるか、下げない理由を残す。
- **DC-186-10** 層を持つモジュールを求める処理、レベル A のモジュールの一覧、モジュールの名前の取り出し、生成したコードの判定は、構成の検査の補助の 1 か所にある。
- **DC-186-11** 設定ファイルを profile ごとに重ねて読む処理、設定の型への値の当てはめ、契約と realm の置き場所の読み取りは、単体テストの補助（設定の補助と契約の補助）にあり、各テストに重複して書かない。契約と realm の置き場所が渡されないときは、既定の場所を使わずに失敗する。
- **DC-186-12** モジュールの図のテストは、固定した入力で描画を確認し、標準出力に書かない。2 つの Spring Modulith のテストが共に使う定数は、補助にある。

### DS-186-4 テストのコメントの spec の番号（D / P1）

#178 の項目である。

- **DC-186-13** テストのコメント（`src/test`、`src/integrationTest`、`src/testFixtures` の Javadoc と行のコメント）にある spec・plan・タスクの番号を、spec の番号の検査が検出する。テスト名（`@DisplayName`）の AC・BR などの番号は対象外である。
- **DC-186-14** 今のテストのコメントにある番号は、規則を言葉で書く形に書き換える（[コメントの書き方](../../../../rules/comments.md) 第 1 節）。コメントの書き方の対象に、テストのコメントを加える。

### DS-186-5 並び順の既定値（D / P2）

- **DC-186-15** 店舗向けの商品の一覧の並び順の既定値（指定がなければ新着順）は、1 つの層にだけある。消費者に見える並び順は変わらない。#178 の項目である。

## 6. 非機能要件

- **DN-186-1** 消費者・運営者に見える振る舞いを変えない。API の契約とデータベースの構造を変えない。
- **DN-186-2** AC を追加・変更しない。
- **DN-186-3** 追加した構成の検査は、今のコードで違反が 0 件である。違反が見つかったときは、コードを規則に合わせて修正するか、規則の文書の例外の表に理由を書く。どちらにするかが文書で決まらないときは、作業を止めて利用者に確認する。
- **DN-186-4** 検査とテストを弱めない。補助へ移すテストは、確認の内容を変えない（差分で確認する）。
- **DN-186-5** カバレッジと mutation score が基準を下回らず、`./gradlew check` と `scripts/ci/check-all.sh` が通る。
