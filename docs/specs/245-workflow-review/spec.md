# Spec 245：エージェントの作業の流れとレビューの規則を再検討する

ステータス：草案

## 1. 背景と目的

整理の段階（milestone「整理の段階」）の第 1 段の spec である。第 1 段は 6 つの spec（#245〜#250）が並行する。第 6 弾（spec 222〜227）までの作業で、レビューのサブエージェントの費用が大きいこと、マージと並行のセッションの運用に規則がないことが分かった。本 spec は、レビュー、マージ、モデルの選び方、セッションの運用、振り返りの規則を再検討する。目的は、token を減らしつつ品質を上げることである。品質を優先する（利用者、2026-10-27）。

追跡の issue は [#245](https://github.com/roger88106/ec-site/issues/245) で、扱う issue（sub-issue）は #106、#130、#99、#105、#21 である。作業ブランチは `245-workflow-review` である。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。

### 1.2 規模

L とする（利用者が承認、2026-10-28）。理由は次の 2 つである。

- レビュー、マージ、モデル、セッションの運用の 4 つの規則の文書（AGENTS.md、開発の進め方、エージェントの作業フロー、skill `review`・`retro`）と、GitHub の保護の規則・CI の設定にまたがるため。
- 危険度の区分の経路、profile の選び方、振り返りの集め方など、plan で決める設計の判断が多いため。

段階は 3 つの見込みである。段階 1 がレビューとマージ、段階 2 がモデルと作業の形、段階 3 がセッションの運用と振り返りである。段階の分け方は plan で決める。

## 2. 用語

| 用語 | 意味 |
|------|------|
| profile | レビューの量（時点ごとのモデルと回数）の組。今は厚め・標準・節約 |
| 作業の形 | spec を 1 つずつ進める単線と、複数の spec を並行する並行の 2 つ |
| 変更の危険度 | pull request が変えるファイルの経路で決まる区分。マージの承認とレビューの量を決める |
| 既存の指摘 | レビューの指摘のうち、その spec の変更より前からあったコード・文書への指摘 |
| 見逃しの台帳 | レビューの後に見つかった不具合（後のレビュー、CI、利用者が見つけたもの）の一覧 |
| 弾 | 1→10 の改善で、まとめて並行した spec のまとまり（第 4〜6 弾など） |
| 段 | 整理の段階の中の区切り（第 1 段など）。spec の中の区切りは段階という |
| 振り返り | セッションの終わりに、エージェントの環境（規則、skill、ツール）の改善点を挙げること |

用語集に加えるかは plan で決める。

## 4. 目的と完了条件

### DS-245-1 レビューの収束（D / P1）

- **DC-245-1** レビュー役は、各指摘に、その spec の変更が入れたものか、既存の指摘かを付ける。
- **DC-245-2** 既存の指摘について、その spec で修正するものと起票の案にするものの分け方が、規則にある。分け方は plan で決める。
- **DC-245-3** 同じ範囲の 2 回目以降のレビューは、前回のレビューからの差分と、前回の指摘の修正だけを対象にする。
- **DC-245-4** 同じ対象のレビューと修正の繰り返しに、上限がある。上限の値は plan で決める。案は 3 回である。上限に達したら、spec 担当のセッションが修正の前提を 1 文で書いて再検討し、利用者に報告する。
- **DC-245-5** 同じ種類の指摘は、対象の全体で同じ種類を探してからまとめて修正する。
- **DC-245-6** spec の最後のレビューと pull request の前のレビューの観点を、段階のレビューと重ならないように決める。減らす量と根拠は plan で決める。

### DS-245-2 変更の危険度（D / P1）

#106 の項目である。

- **DC-245-7** 変更の危険度の区分が規則にある。区分は、書いたのが人かエージェントかでなく、変えるファイルの経路で決まる区分と、spec で決めた区分のうち、高い方で決まる。
- **DC-245-8** 常に利用者がマージを承認する経路の一覧が、規則にある。CI の workflow、認証、支払、データベースのマイグレーション、リリースの流れを含む。一覧は plan で決める。
- **DC-245-9** spec 担当のセッションは、設計への影響が大きい spec を、spec の段階で危険度の高い変更として提案し、利用者が spec の確認で決める。設計への影響が大きいとは、今の構成に合わない新しい型を加える、モジュールの境界や書き方の規則を変える、などである。利用者は、提案がなくても、spec の確認で危険度の高い変更に指定できる。理由：設計への影響は、ファイルの経路から機械で判断できないため（利用者、2026-10-28）。
- **DC-245-10** plan と実装の途中で、設計への影響が大きいと分かったときは、spec 担当のセッションが危険度を上げて利用者に報告する。途中で危険度を下げない。
- **DC-245-11** マージの承認に数えるものと数えないものが、規則にある。利用者が明示した許可を数え、エージェントの承認は数えない。必要な承認の数を含む。
- **DC-245-12** 危険度が低い変更は、CI が全て通り、レビューの高・必須が 0 なら、issue 担当のセッションがマージすることが、規則にある。危険度の高い変更と機能の spec は、今のとおり利用者が許可する。理由：第 6 弾の特例で問題がなく、利用者の確認を危険度の高い変更に集められるため（利用者が決定、2026-10-28）。
- **DC-245-13** 認証・支払・権限を変える spec は、AI のセキュリティのレビューを行う。時点と使うツールは plan で決め、profile の表に入れる。

### DS-245-3 続けてマージするときの待ち（D / P1）

#130 の項目である。

- **DC-245-14** 続けて複数の pull request をマージするときの待ちを短くする方法を選び、設定と文書に入れる。候補は、保護の規則の「最新の develop を含む」の解除、変えたファイルによる CI の job の省略、Dependabot の更新のまとめ方、merge queue の 4 つである。merge queue は、個人のアカウントで使えるかを確認する。方法は plan で決める。
- **DC-245-15** 選んだ方法でも、`develop` に入った変更の CI が通ることを、マージの後に確認する手順がある。

### DS-245-4 モデル・作業の形・profile の選び方（D / P1）

- **DC-245-16** 作業の種類ごとに、モデルの区分と思考の量（effort）が表にある。作業の種類は、資料を集める、機械的な作業、実装、判断、レビュー、原因の調査、設計の決定である。
- **DC-245-17** 資料を集めて判断しない作業は軽量のモデルに任せることが、規則にある。
- **DC-245-18** 最も高性能な区分のモデルを使う場面と上限が、規則にある。上限は、プランごとの使用の条件に合わせる。2026-10-28 の時点の条件は第 1.1 節の「使用量の上限」の行である。能力・料金・上限は、plan を書くときに公式の文書で確認する。
- **DC-245-19** 軽量のモデルの注の値は、固定の分（system prompt とツールの定義）を含めた値になっている。
- **DC-245-20** セッションの始めに、プランと残りの使用量を読み、作業の形（単線・並行）と profile を選ぶ手順が、規則にある。利用者がマシンごとの環境の文書を手動で修正しなくても選べる。
- **DC-245-21** 残りの使用量が少ないときに、profile を下げる閾値と、作業を止める閾値が、規則にある。
- **DC-245-22** サブエージェントへの指示とその説明は、日本語で書くことが規則にある。

### DS-245-5 固定の文脈（D / P1）

#99 の項目を含む。

- **DC-245-23** spec 担当のセッションと実装役が使わない MCP のツールの定義が、毎ターンの文脈に入らない。方法は、接続を切るか遅延読み込みにするかを plan で決める。
- **DC-245-24** 固定の文脈の token を、変える前と後で同じ方法で測り、spec に記録する。
- **DC-245-25** LSP によるコードの参照を試し、使うか使わないかと理由を記録する。

### DS-245-6 採否と見逃しの記録（D / P1）

- **DC-245-26** レビューごとの token、時間、指摘の数（重要度ごと）、採用した数を、決まった形で 1 か所に記録する。
- **DC-245-27** 記録を集計して profile を再検討する時点が、規則にある。時点は弾ごとなどとし、plan で決める。
- **DC-245-28** 見逃しの台帳が 1 か所にあり、台帳に加える時点が規則にある。
- **DC-245-29** モデル・レビューの指示・profile を替えるときに、見逃しの台帳で採点し直し、対象ごとに再検討する手順がある。対象は、モデルの区分、レビューの観点、profile である。
- **DC-245-30** 見逃しの台帳に、今までの例を少なくとも 1 件入れる。例は、spec 192 の、手元は通り CI だけ失敗した件である。

### DS-245-7 並行のセッションの運用（D / P1）

#105 の項目である。

- **DC-245-31** spec 担当のセッションは、組み込みのコードレビューの結果を出した後もターンを終えず、pull request の作成まで進むことが、規則にある。
- **DC-245-32** セッションの間のメッセージは、名前でなくセッションの ID で送ることが、規則にある。
- **DC-245-33** 待機中のセッションに遠隔操作の接続を入れる手順が、規則にある。先にターンを起こす。置き場所は、共有の文書にするか、マシンごとの環境の文書にするかを plan で決める。
- **DC-245-34** issue 担当の専用のセッションの役割、起動、待機の手順が、文書にある。
- **DC-245-35** issue 担当のセッションの待機と監視の token を抑える方法が、規則にある。方法は plan で決める。
- **DC-245-36** spec 担当のセッションは、利用者が実装の前の確認対象を承認した後、実装を始める前に issue 担当のセッションに開始を問い合わせ、許可を受けてから始める。利用者の承認だけでは始めない。確認対象は、規模 L は plan と tasks、規模 M は spec、規模 S は規模の区分である。理由：開発の資源を issue 担当のセッションが一括で調整するため（利用者、2026-10-28）。資源は、使用量、マシンの資源、並行の数である。issue 担当のセッションがないときの扱いは plan で決める。
- **DC-245-37** 資源の配分は issue 担当のセッションが決める。配分は、実装の開始と待機、並行する spec の中断と再開を含む。利用者が特例を求めたときも、issue 担当のセッションが決めてから進める。

### DS-245-8 振り返り（D / P1）

#21 の項目である。

- **DC-245-38** エージェントが振り返りの skill を呼べる。
- **DC-245-39** spec 担当のセッションは、セッションのアーカイブの前に振り返りを行い、結果を決まった置き場所に 1 件 1 ファイルで残す。
- **DC-245-40** 振り返りは、セッションの記録を読み直さず、spec 担当のセッションの文脈から書く。読む量の上限を含む。
- **DC-245-41** 同じ問題を数え、数が閾値を超えたものを整理の issue の案にする手順と担当がある。閾値は plan で決める。
- **DC-245-42** 定期に全体をレビューして提案だけを出す時点と手順が、規則にある。仕組みは、定期の実行にするか、区切りで手動で行うかを plan で決める。

## 6. 非機能要件

- **DN-245-1** 消費者・運営者に見える振る舞い、本番のコード、API の契約、データベースの構造を変えない。
- **DN-245-2** レビューを減らす変更は、根拠を plan に書く。根拠は、整理の前の基準の測定、採否の記録、見逃しの台帳である。高の指摘が出ている段階のレビューの時点は減らさない。2 回目以降のレビューを差分に絞ること（DC-245-3）は、見る範囲を減らすが、時点は減らさない。理由：品質を token より優先するため（利用者、2026-10-27）。
- **DN-245-3** 規則の本文は、使う AI のサービスに依らない言葉で書く。サービス固有の名前は、AGENTS.md のモデルの区分の表と、ツールの注にだけ書く。サービス固有の名前は、モデル、プラン、ツール、設定の項目である。理由：サービスを替えるときに修正する所を限るため。
- **DN-245-4** 毎回読む文書（AGENTS.md、開発の進め方、エージェントの作業フロー）は、それぞれ第 1.1 節の大きさを超えない。超えるときは、必要なときに読む文書か skill に移す。理由：毎ターンの文脈と実装役の読む量を増やさないため。
- **DN-245-5** GitHub の設定（保護の規則など）を変えるときは、変える内容を示して利用者の許可を得てから行う。
- **DN-245-6** 本 spec で変えた規則は、本 spec のマージの前に、並行する他の spec に適用しない。
- **DN-245-7** 新しい・変えた検査の script と hook は、違反の例で違反を検出することを確認する。

## 9. Open questions

なし。危険度が低い変更のマージは issue 担当のセッションが行い（DC-245-12）、設計への影響が大きい spec は spec の確認で危険度を決める（DC-245-9）。規模は L とする。利用者が 2026-10-28 に決めた。
