# Spec 140：spec 担当のセッションの進め方を補う（実装の前の照合、アーカイブの時点、マージとセッションのアーカイブ）

ステータス：確定

## 1. 背景と目的

spec 7 で決めた進め方を使い始めて、spec 担当のセッションの進め方に 4 つの穴が分かった。

1. 並行を進めるため、文書の段階（spec と plan・tasks の承認まで）を先に進め、実装を後から順に始める spec が出た（spec 17、18、19、134、135）。承認から実装までに `develop` が進む（他の spec のマージ、Java の書式の一括の変更など）ので、plan の前提が成り立たないことがある。
2. マージの後に spec 担当のセッションをアーカイブする（アプリのセッションの一覧から外す）には、利用者が対象のセッションを明示して同意する必要がある。別に質問すると、利用者の確認が 1 回増える（2026-10-22 の利用者の決定）。
3. [開発の進め方](../../rules/workflow.md) 第 4.2 節は、spec を最後のタスクでアーカイブに移すと決めている。一方、進捗の検査（`scripts/ci/progress.mjs`）は、アーカイブした 1→10 の spec の全てのタスクが済んでいることを求める。spec 7 は、pull request の前のレビューと pull request の作成をタスクにしていたので、アーカイブを最後のタスクにできず、順序を入れ替えて避けた（spec 7 の T7-06-03）。spec 131 は pull request の作成をタスクにせず、アーカイブを最後のタスクにして、問題が起きなかった。
4. spec 7 で、`[P]` のタスクの間に書いていない依存があった。spec のディレクトリの読み方を変えるタスクの後に、進捗の検査が失敗した（spec 7 の T7-06-02）。

追跡の issue は [#140](https://github.com/roger88106/ec-site/issues/140)、扱う issue は [#139](https://github.com/roger88106/ec-site/issues/139)（1、2）と [#109](https://github.com/roger88106/ec-site/issues/109)（3、4）、作業ブランチは `140-spec-session-flow` である。本 spec は整理の spec で、規模は M である（API の契約、データベース、AC を変えない。[開発の進め方](../../rules/workflow.md) 第 4.2 節）。規模は spec の確認で合わせて承認を得る。

次に実装を始める spec（134、135、18、19）の開始の指示で、本 spec で決めた手順を使う。

## 3. 目的と完了条件

### DS-140-1 実装を始める前に、plan の前提を最新の `develop` と照合する（D / P1）

- **DC-140-1** [開発の進め方](../../rules/workflow.md) 第 5 節に、実装を始める前の照合の手順がある。spec 担当のセッションは、最初のタスクの前に、作業ブランチに最新の `develop` を取り込み、次を `develop` と照合する：plan（規模 M は spec）の前提、変える範囲（ファイルとモジュール）、依存する spec と部品、承認の後に変わった規則（開発の進め方など）に tasks が合うか。
- **DC-140-2** 差があれば、最初のタスクの前に plan（規模 M は spec）と tasks を直す（文書が先）。設計が変わるときは、plan と tasks の確認（規模 M は spec の確認）で利用者に再度確認する。設計が変わらない直し（パス、済んだ依存、規則に合わせるタスクの順序）は、確認を待たない（開発の進め方 第 5.2 節）。
- **DC-140-3** 照合は、承認の直後に続けて実装を始めるときも行う。`develop` が進んでいなければ「差なし」で終わる。理由：承認から実装までの間が短いかを判断する必要をなくし、判断の誤りを避けるため。
- **DC-140-4** 照合の結果（差の有無と、直したもの）を、追跡の issue の開始のコメントに書く。
- **DC-140-5** [エージェントの作業フロー](../../rules/subagents.md) 第 4 節（セッションの間のやり取り）に、issue 担当のセッションが実装の開始を指示するときに、この照合を求める規則がある。

### DS-140-2 マージの許可と一緒に、セッションのアーカイブの許可を得る（D / P1）

- **DC-140-6** 開発の進め方と [AGENTS.md](../../../AGENTS.md) の Git の表（マージ・tag の行）に、次がある：spec 担当のセッションは、作業ブランチを `develop` にマージする許可を求めるときに、マージと後片付けの後にそのセッションをアーカイブする許可も、同じ質問で求める。理由：セッションのアーカイブは利用者が対象を明示して同意する必要があり、別に質問すると確認が 1 回増えるため。
- **DC-140-7** 後片付けの内容（追跡の issue への完了の記録、扱った issue を閉じる、作業ツリーとスロットの解除など）と、アーカイブを行うセッション（第 6 節の 2 で決める）が文書にある。
- **DC-140-8** 利用者がアーカイブを許可しなかったときは、マージと後片付けだけを行い、セッションを残す。

### DS-140-3 アーカイブを最後のタスクにして、進捗の検査と両立させる（D / P1）

- **DC-140-9** 開発の進め方 第 4.2 節に、次がある：spec をアーカイブに移すタスクは tasks の最後のタスクで、spec の最後のレビューと pull request の前のレビューは、その前のタスクにする。pull request の作成は tasks に入れず、追跡の issue のコメントに記録する。アーカイブの commit で、そのタスク自身を含む全てのチェックボックスを済みにする。
- **DC-140-10** アーカイブの後にタスクを追加するとき（pull request のレビューの対応。開発の進め方 第 5.5 節）は、そのタスクを済ませる commit で、済みの行として追加する。理由：アーカイブした spec に済んでいないタスクがあると、commit の前の検査で止まるため。
- **DC-140-11** 進捗の検査の条件（アーカイブした 1→10 の spec は、全てのタスクが済んでいる）は変えない。失敗の表示に、アーカイブを最後のタスクにする規則（開発の進め方 第 4.2 節）を示す。script のテストで確認する。
- **DC-140-12** AGENTS.md の「完了の基準」と、[CI の検査](../../guides/ci.md) の文書の progress の行が、新しい規則と一致する。
- **DC-140-13** 本 spec を、タスクの順序を入れ替えずにアーカイブに移し、commit の前の検査と CI が通る。

### DS-140-4 tasks の照合で、共有する部品を変えるタスクの書いていない依存を見る（D / P1）

- **DC-140-14** skill `review` の tasks の照合（`.claude/skills/review/SKILL.md` の手順 7 と、`.claude/skills/review/prompts.md` の plan・tasks の照合のひな形）に、次の観点がある：共有する部品（検査の script の共通の関数、生成するファイル、共通の設定、AC 一覧などの共有の文書）を変えるタスクと、それを使う・前提にするタスクの間の、書いていない依存（特に `[P]` のタスクの間）を見る。

## 4. 守る制約

- **DN-140-1** コード（バックエンド、フロント）、API の契約、データベース、AC を変えない。
- **DN-140-2** 進捗の検査の条件を緩めない。
- **DN-140-3** アーカイブした spec を変えない（開発の進め方 第 1.4 節）。

## 5. Non-goals

| 項目 | 理由 |
|------|------|
| 実装の前の照合を script で行う | 前提は文章で書かれ、照合に判断が必要なため |
| spec の最後のレビューと pull request の前のレビューをまとめる | #139、#109 の範囲の外 |
| 承認済みの spec（17、18、19、134、135）の tasks を、本 spec で新しい規則に直す | 各 spec の実装の前の照合（DS-140-1）で直す |

## 6. 決めたこと

spec の確認で、利用者が 2 つとも案 A に決めた（2026-10-22）。規模 M も同じ時に承認した。Open questions はない。

1. **アーカイブの時点と進捗の検査**（#109）：
   - 案 A（推奨。採用）：アーカイブを最後のタスクにし、pull request の作成はタスクにしない。検査の条件は変えない（DC-140-9〜11）。spec 131 で問題が起きなかった形で、検査を緩めない。
   - 案 B：検査を変え、作業ブランチ（pull request）では、アーカイブした spec の済んでいないタスクを許し、`develop` でだけ失敗にする。欠点：pull request で見落としが分からず、マージの後に `develop` の CI が失敗する。
   - 案 C：アーカイブのタスクとその後のタスクだけ、済んでいなくてよいとする（タスクに印を付ける）。欠点：検査が複雑になり、印の付け誤りで別の済んでいないタスクを見逃す。
2. **セッションのアーカイブを行うセッション**（#139）：
   - 案 A（推奨。採用）：spec 担当のセッションが、後片付けの最後に自分をアーカイブする。できないときは、許可した利用者の言葉を添えて issue 担当のセッションに頼む。本 spec で試す。
   - 案 B：spec 担当のセッションは完了の報告に許可を書き、issue 担当のセッションが報告を受けてアーカイブする。欠点：issue 担当のセッションが止まっていると、アーカイブが遅れる。
