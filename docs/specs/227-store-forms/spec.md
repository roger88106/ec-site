# Spec 227：店舗画面のフォームのフォーカスと読み上げ、失敗のログ

ステータス：確定

## 1. 背景と目的

[Spec 193](../archive/1to10/193-store-a11y/spec.md) で、店舗画面のエラーメッセージを読み上げの領域に入れた。注文のフォームの欄の誤りは、入力欄と結び付けた。その spec の起票の案から、次の 3 つが残った。

- 注文のフォームの送信に失敗しても、フォーカスが欄に移らない。どの欄を直すかを、利用者が自分で探す必要がある。
- バリアントの在庫状況の読み上げの領域だけが、ほかの領域と違って役割を持たない。
- サーバーアクションの失敗のログから例外のメッセージを除いた。状態コードをメッセージにだけ入れる経路では、ログに状態コードが出ない。

追跡の issue は [#227](https://github.com/roger88106/ec-site/issues/227)。扱う issue は [#213](https://github.com/roger88106/ec-site/issues/213)（フォーカス）、[#214](https://github.com/roger88106/ec-site/issues/214)（在庫状況の読み上げ）、[#215](https://github.com/roger88106/ec-site/issues/215)（失敗のログの状態コード）である。作業ブランチは `227-store-forms`。

3 つの issue は spec 193 第 9 節の起票の案で、利用者が 2026-10-27 に起票を承認した。

## 3. User stories と受け入れ条件

### US-227-1 送信の失敗の後、直す欄から入力を始められる（C / P1）

消費者として、注文のフォームの送信に失敗したとき、誤りのある欄から入力を直したい。理由：欄を探さずに直せ、スクリーンリーダーの利用者には、フォーカスが移った欄の誤りの文が読み上げられるため。

- **AC-227-1** 注文のフォームの送信が欄の誤りで失敗したとき、フォーカスは、選べる誤りの欄のうち画面の順で最初の欄に移る。選べない欄（事実 5）は飛ばす。※2
- **AC-227-2** 誤りのある欄が全て選べないときは、フォーカスを移さない。
- **AC-227-3** 欄の誤りがない失敗（在庫不足、通信の失敗など、フォームの下に出すもの）では、フォーカスを移さない。※3
- **AC-227-4** フォーカスを移す処理は、送信の結果を受けたときだけ動く。結果を受けた後に欄を入力・選択しても、フォーカスを欄へ移し直さない。
- **AC-227-5** 同じ誤りで再び送信に失敗したときも、AC-227-1 のとおりにフォーカスを移す。

※2：画面の順は事実 1。入力の検証の誤りと、欄に対応するエラーコードの業務のエラー（事実 2）のどちらも対象にする。

※3：第 6.2 節。フォームの下のメッセージは、spec 193 の読み上げの領域が読み上げる。

### US-227-2 在庫状況の変化を、ほかの知らせと同じ役割の領域で聞ける（C / P2）

支援技術の利用者として、バリアントを選んで在庫状況が変わったとき、ほかの知らせと同じ役割の領域で聞きたい。理由：店舗画面の読み上げの領域の役割をそろえるため。

- **AC-227-6** バリアントの在庫状況の領域は、status の役割を持つ。※4

※4：status の役割は、既定で `aria-live="polite"` と `aria-atomic="true"` を持つ（spec 193 第 6.3 節）。領域の中身はバッジか案内の文の 1 つなので、領域の全体を読み上げても、聞こえる文は今と同じである。表示する文と、変わる時（選択を変えたとき）は変えない。

## 4. 非機能要件

- **NFR-227-1** 店舗画面のサーバーアクションが API の失敗の例外で失敗したときの error のログに、その状態コードを出力する。ログは 1 行 1 件の JSON（[フロントの書き方](../../rules/frontend-coding.md) 第 8.2 節）で、状態コードを持たない例外（接続の失敗など）では、状態コードの項目を null にする。テストで確認する。※5
- **NFR-227-2** 店舗画面の本番のソースに `aria-live` を直接書かないことを、機械の検査で確認する。残り時間の表示の `aria-live="off"` は除く。※6
- **NFR-227-3** 本 spec の AC に関わらない既存のテスト（店舗画面、E2E）は、期待値を変えずに通る。
- **NFR-227-4** 見た目（文の位置、色、レイアウト）を変えない。フォーカスが移った欄には、UI のコンポーネントが定めるフォーカスの見た目が付く。
- **NFR-227-5** 新しく書くコメントに、spec の番号を書かない（[コメントの書き方](../../rules/comments.md) 第 1 節）。

※5：第 6.4 節の決定による。null は、原因の例外のコードがないときの今の項目（事実 8）と同じ扱いである。状態コードは注文やカートを指す値ではないので、spec 193 の NFR-193-1（識別子を出さない）に反しない。MVP 017 の AC-307 の今の内容（店舗画面の構成 第 4.2 節）を変えるので、AC 一覧の AC-307 の行も直す。

※6：検査の場所は第 6.5 節。規則の文書にない検査は、先に規則を書いてから加える（spec 183 の確認で利用者が決めた方針）。

## 5. Non-goals

| 項目 | 理由 |
|------|------|
| 注文のフォームの外のフォーム（キャンセルの申請など）のフォーカス | 欄ごとの誤りを表示するのは注文のフォームだけ |
| 失敗のときに、フォームの下のメッセージや注文のボタンへフォーカスを移す | 第 6.2 節 |
| 欄の誤りの数や一覧を、フォームの上にまとめて示す | #213 の範囲は、最初の誤りの欄へ移すこと。誤りの文は、フォーカスが移った欄の説明（spec 193 の AC-193-4）として読み上げられる |
| 4xx の応答を API のクライアントのログに出力する | 第 6.4 節の案 C |
| 管理画面の読み上げとフォーカス | 3 つの issue の範囲は店舗画面だけ |
| 支援技術の実機（NVDA など）での確認 | テストは役割、名前、フォーカスで確認する（spec 193 と同じ） |

## 6. 決めたこと

spec の確認で、利用者が第 6.1〜6.5 節を全て案 A に決めた（2026-10-27）。規模 M も同じ時に承認した。

### 6.1 種類と規模

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 機能の spec、規模 M |
| 案 B | 3 つの issue を分ける。#213 を機能の spec（M）、#214 と #215 を規模 S の issue にする |

- 案 A を機能の spec にする理由：#213 は送信の後の振る舞いを変え、#214 は支援技術の利用者に伝わる役割を変える。#215 は AC-307 の今の内容を変え、これは新しい機能の spec で行う（[開発の進め方](../../rules/workflow.md) 第 1.5 節）。
- 案 A を M にする理由：AC を追加する・変えるので M 以上になる（[開発の進め方](../../rules/workflow.md) 第 4.2 節）。店舗画面だけで、API・データベース・モジュールをまたがないので、L ではない。
- 案 B を推奨しない理由：#214 と #215 も AC を追加する・変えるので、S の基準に合わないため。

### 6.2 欄の誤りがない失敗のときのフォーカス（AC-227-3）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 移さない。欄の誤りがあるときだけ、欄へ移す |
| 案 B | フォームの下のメッセージへ移す |
| 案 C | 注文のボタンへ戻す（送信中に無効になったボタンへ。事実 4） |

- 案 A の理由：フォームの下のメッセージは、spec 193 で status の領域に入れたので、送信の後に読み上げられる。フォーカスを動かさないので、移した先の読み上げとメッセージの読み上げが重ならない。#213 の範囲（最初の誤りの欄へ移す）とも合う。
- 案 B：メッセージの段落をフォーカスできるようにする必要がある。status の領域の読み上げと、フォーカスの移動の読み上げで、同じ文が 2 回読み上げられうる。
- 案 C：キーボードの利用者が、次の操作をボタンの位置から始められる。ただし、在庫不足のときの次の操作（カートを見る）はメッセージに添えたリンクで、ボタンの前にある。#213 の範囲も超える。必要なら後の spec で扱う。

### 6.3 フォーカスの移動の確認方法（AC-227-1〜5）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 画面のテスト（jsdom）で、表示のコンポーネントに送信の結果を props で与え直して確認する。E2E の既存の注文の流れで、郵便番号の誤りを確認する手順に、郵便番号の欄にフォーカスがあることの確認を 1 つ加える |
| 案 B | 画面のテストだけで確認する |

- 案 A の理由：場合分けは画面のテストで確認する。場合は、最初の欄、選べない欄、欄の誤りがない失敗、結果の後の入力、同じ誤りの再びの失敗である。jsdom のフォーカスは実際のブラウザーと違いうるので、実際のブラウザーでは郵便番号の欄の 1 つだけを確認する。既存の E2E の手順に確認を加えるだけで、手順は増やさない。
- 案 B：実行は速いが、実際のブラウザーでフォーカスが移ることを確認しない。

### 6.4 失敗のログの状態コード（NFR-227-1、#215）

#215 は「出すかを決める」issue である。

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 出力する。API の失敗の例外（事実 10 の型）なら、サーバーアクションの失敗のログに状態コードを加える。あわせて、カートを作る API の失敗（事実 9）を、その型の例外にする |
| 案 B | 出力しない。#215 を、理由を追跡の issue に書いて閉じる |
| 案 C | 出力する。ただし、API のクライアントの応答のログ（事実 11）を 4xx にも広げる |

- 案 A の理由：状態コードは識別子でなく、出しても spec 193 の方針に反しない。今の経路は 1 つ（事実 9）だが、後で API の失敗を例外にする経路が増えても、同じ形でログに出る。変えるのは、サーバーアクションの共通の処理とカートを作る処理の 2 つで、今の経路が 1 つでも手間は小さい。
- 案 B：今の経路は 1 つで、カートを作る API は要求の本文を持たないので、入力の誤りの 4xx は起きない。5xx は応答のログに出る（事実 11）。変更は要らないが、ほかの 4xx（認可の誤りなど）が起きたときに、原因をログから調べられない。
- 案 C：入力の誤り（400）や業務のエラー（409）など、画面が想定している 4xx もログに出て、出力が増える。#215 の範囲（サーバーアクションの失敗のログ）を超える。

### 6.5 `aria-live` の検査の場所（NFR-227-2）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 店舗画面の Biome の plugin（GritQL）を 1 つ加える（事実 12 と同じ形）。テストのファイルは対象から外す |
| 案 B | フロントの書き方の規則を確認する既存の検査の script（`scripts/ci/frontend-rules.mjs`）に加える |
| 案 C | 検査を作らず、規則とレビューで守る |

- 案 A の理由：JSX の属性を構文で見つけられ、`aria-live="off"` は条件で除ける。検査の script を変えないので、同じ時期に検査の script を変える spec 225（[#225](https://github.com/roger88106/ec-site/issues/225)）と spec 226（[#226](https://github.com/roger88106/ec-site/issues/226)）を待たずに進められる。GritQL で書けないと分かったときは、利用者に確認して案 B にする。
- 案 B：既存の検査と同じ形（除外は理由付きで書く）になる。ただし、`aria-live="off"` を除く仕組みを加える必要がある。今の除外の一覧のキーは、ファイルのパスか `<画面>:<名前>` の形だからである。spec 225 と 226 も同じ script とテストを変えるので、両方のマージの後に行う。
- 案 C：#214 の本文にある「検査に移す」を満たさない。
