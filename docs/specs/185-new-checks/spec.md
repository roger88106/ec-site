# Spec 185：マイグレーション・文書・テストの書き方の新しい検査を加える

ステータス：確定

## 1. 背景と目的

spec 183 の確認で、CI の検査の script（`scripts/ci/`）の新しい検査を、spec 183 から分けると決めた（[spec 183](../archive/1to10/183-ci-checks/spec.md) 第 6 節の 1）。本 spec は、分けた 3 つの issue と、spec 183 の最後のレビューで本 spec に移した推奨 11 件を扱う。

- #20：マイグレーションの互換性の規則がなく、前のリリースのアプリが動かなくなる変更が入りうる。
- #161：spec 156 で文書を実装に合わせたときに、機械で見つけられる食い違いが残った。
- #169：フロントのテストの書き方の違反を、検査で見つけていない。spec 184 が今の違反を直した（[spec 184](../archive/1to10/184-frontend-tests/spec.md) 第 6 節）。
- spec 183 の推奨 11 件：検査の script の共通の処理の重複と、読み方の漏れ（#185 のコメント。spec 183 第 8 節）。新しい検査の前に行う。

追跡の issue は [#185](https://github.com/roger88106/ec-site/issues/185)、扱う issue は [#20](https://github.com/roger88106/ec-site/issues/20)、[#161](https://github.com/roger88106/ec-site/issues/161)、[#169](https://github.com/roger88106/ec-site/issues/169) である。作業ブランチは `185-new-checks`。本 spec は整理の spec で、規模は M である（第 6 節の 1）。API の契約とデータベースを変えず、AC を変えないため。

前提の spec 183（共通の関数）と spec 184（#169 の違反の修正）は、マージ済みである。

- 1 つの DC に条件を 1 つ書く。出典の列は、spec 183 第 8 節の推奨の番号、spec 158 第 8 節の項目の番号、issue のコメント、spec 184 第 6 節の申し送りの記号である。

## 4. 守る制約

- **DN-185-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。
- **DN-185-2** 検査を弱めない。検査の対象を狭めるのは、誤検出を減らすときだけにし、理由を検査に書く。
- **DN-185-3** 新しく書くコメントと除外の理由に、spec・plan の番号を書かない（[コメントの書き方](../../rules/comments.md) 第 1 節）。
- **DN-185-4** 並行する spec（192 はバックエンドの本番のコード、194 は E2E の script）と重なるファイル（E2E の補助、時間の待ちの検査の対象など）の扱いと、並行の可否は、plan の段階で互いの変えるファイルを照合して決める。規模 M（第 6 節の 1）のときは、[開発の進め方](../../rules/workflow.md) 第 5.6 節の実装の前の照合で決める。
- **DN-185-5** 共有の文書（[CI の検査](../../guides/ci.md)、規則の文書）の衝突は、後でマージする pull request が `develop` を取り込んで解消する。

## 6. 決めたこと

### 6.1 規模

DC は 32 で、spec 183（M、DC-183-1〜30）と同じくらいである。変えるのは検査の script、規則と設計の文書、違反の修正の数行で、API・データベース・モジュールをまたがない。

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 規模 M（1 つのファイルの spec に tasks の節を含める） |
| 案 B | 規模 L（spec、plan、tasks） |

- 案 A の理由：spec 183・158 と同じ種類の作業で、どちらも M で進められた。規模の基準（[開発の進め方](../../rules/workflow.md) 第 4.2 節）では M に当たる。
- 案 B の理由：並行する spec との照合（DN-185-4）を plan で文書に残せる。ただし、規模の基準に合わない。

### 6.2 マイグレーションの互換性の規則（DC-185-12〜14）

spec 183 の確認で利用者が決めた（2026-10-24。[spec 183](../archive/1to10/183-ci-checks/spec.md) 第 6 節の 2〜4 と第 8 節に、本 spec に移したことを記録してある）。

今は、マイグレーションはデプロイごとに 1 回適用し、起動時には適用しない（[環境変数](../../guides/environment.md) 第 1 節）。適用してからアプリを入れ替えるまでの間、前のバージョンのアプリが新しいスキーマで動く。

規則：新しいマイグレーションは、前のリリースのアプリが動き続けられる変更だけにする。表・列の削除と改名、列の型の変更、既存の列を NOT NULL にすること、既定値のない NOT NULL の列の追加は、1 つのリリースでしない。次の 3 段に分ける。

1. 新しい表・列を追加する（前のバージョンのアプリは使わない）。
2. アプリを新しい表・列に切り替えてリリースする。
3. 次のリリースで、使わなくなった表・列を削除する。

- 検査：マイグレーションの検査が、新しいマイグレーションの、上の規則が禁じる SQL 文を失敗にする。手順 3 の削除は、どのリリースで使わなくなったかを理由に書いて、除外の一覧（`{キー: 理由}`）に置く。
- 規則の置き場所は、[バックエンドの書き方](../../rules/backend-coding.md) に節を加える。[CI の検査](../../guides/ci.md) の migrations の行も合わせる。
- 検査を作らずに規則だけを書く案と、前のリリースのアプリの統合テストを新しいスキーマで CI で実行する案は、採らなかった。前者はリリースの前まで違反に気づかず、後者は本番の環境がなく CI の時間が増えるため（第 5 節）。

### 6.4 #169 の検査を加える時点と、今の違反

spec 183 の確認で利用者が決めた（2026-10-24）とおり、#169 の検査は spec 184 のマージの後に加える。spec 184 はマージ済みなので、待つ必要はない。

作業ブランチ（27f901d2）で 2026-10-26 に数え直した違反は、`toBeDefined` が E2E に 2 か所（`e2e/src/auth.ts` の IdP のメール、`e2e/src/shipping.ts` の出荷の通知メール。どちらも `expect.poll(…).toBeDefined()`）である。`toBeTruthy` は 0 件で、フロントの `toBeDefined` も 0 件。他の検査の対象の今の違反は、次のとおりである。
- 並びのインデックス（`getAllBy…`・`findAllBy…` の結果の `[n]`）：数え直しでは 0 件としたが、検査を加えたときに `OrderForm.test.tsx` の 1 か所（変数に入れてから選ぶ形）が見つかり、T185-04-02 で修正した。
- HTML の属性の並びに依存する正規表現・文字の一致：0 件（`toMatch` は `traceparent` の形の 2 件だけで HTML ではない）。
- 識別子だけの `describe` の名前：0 件。

E2E の 2 か所は spec 194 が変えうるファイルなので、DN-185-4 のとおり実装の前に照合する。

店舗画面のテストの共通の設定に、理由のコメント付きの型の変換が 1 か所ある。テストの書き方 第 4.6 節が理由付きの変換を許すので、違反に数えない（DC-185-23 の検査も、理由のコメントのあるものを見つけない）。

## 7. tasks

tasks は第 6 節の決定に基づく。

- `[P]` のタスクはない。同じ段階のタスクは、番号の順に 1 つずつ行う。理由：多くのタスクが共有の文書（[CI の検査](../../guides/ci.md)）と共通の関数を変えるため。
- `[テスト]` のタスクは、テストを書いてレッドを確認し、同じ実装役が続けて実装し、同じ commit に入れる（[開発の進め方](../../rules/workflow.md) 第 2.1 節の例外）。
- 新しい検査と強めた検査で違反が出るときは、検査を変えるタスクで違反も修正する（第 3 節）。修正は振る舞いを変えない（DN-185-1）。
