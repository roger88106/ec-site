全体構成の文書（DC-182・183）の 2 つの図：

- モジュールの依存とイベントの図（Mermaid）。テストが、Spring Modulith のモジュールの検出結果から Mermaid を作り、Git の中のファイルと比較する。違えば失敗し、期待するファイルを修正する手順をメッセージに出力する。イベントは、Spring Modulith の API で取れる範囲で書く。
- 外部システム（IdP、決済、物流、メール、画像の変換と保存）とモジュールの役割の図（手書きの Mermaid）。同じテストが、手書きの図のモジュール名の一覧と、コードのモジュールの一致を確認する。

理由：Spring Modulith の Documenter は PlantUML を出力するが、GitHub で表示できないため、使わない。

ロールと権限の対応表（DC-186）の作り方：

- 入力は、IdP の運営者の realm の設定（ロール → 権限）と、管理 API の契約の各操作の `x-required-permission`。
- 出力は、「ロール × 操作」の表の Markdown。CI の検査が、再生成した結果と Git の中のファイルを比較する。
- 店舗 API は、会員の操作とログイン不要の操作の 2 つに分けて、同じ文書に書く。

新しい文書は全て DN-24 に従い、自動の検査（上の生成と比較）か、レビュー skill のチェックリストの項目と組にする。

- 完了した spec のアーカイブ先は `docs/specs/archive/mvp/` にする。移動は spec 019 の最後に行う。
- 移動の方法は、skill `docs` の移動の手順と、リンクを修正する script（`.claude/skills/docs/fix-links.cjs`）を使う。
- コード、skill、AGENTS.md、CI の workflow のパスも修正する（文書の外に約 300 か所）。`doc-refs.mjs` が通ることで確認する。
- constitution の文書の地図とリポジトリ構成の図を、新しい構成に合わせて書き換える。

※8：constitution は、規範（開発の進め方、言語、テストの原則）と設計の大綱（技術スタック、構成、アーキテクチャの方針）と文書の地図を持つ、プロジェクト全体の入口である。規範の置き場所に入れると、設計の大綱の置き場所が合わなくなり、別の入口の文書も必要になる。AGENTS.md と README が最初に読む文書として指しているので、場所を変えない。

### 7.2 AC 一覧（DC-197、198）

| 項目 | 決定 |
|------|------|
| 置き場所 | `docs/design/` に 1 つの文書 |
| 表の列 | AC、状態（有効・変更・廃止）、元の spec、変えた spec、今の内容の所在（spec の節、または設計の文書）、テスト（テスト名の所在。除外ならその理由） |
| 作り方 | script で spec 001〜017 の AC 312 件を抜き出して、表の雛形を作り、テストの所在を埋める |
| 状態の決め方 | 後の spec の本文にある、前の AC 番号の参照を script で拾って、候補にする。エージェントが読んで決め、利用者が確認する |
| 検査（DC-198） | `ac-check.mjs` が AC 一覧を読む。次の場合に失敗する：有効・変更の AC にテストがなく、除外もない。廃止の AC をテストが参照している。spec にあって AC 一覧にない AC がある |

### 7.3 規則（DC-199）

[開発の進め方](../../rules/workflow.md)に、次の 3 つを追加する。

- コードを唯一の正とする。
- 食い違いは文書を修正する。コードの誤りは、不具合として tasks に追加する。
- spec で AC を追加する・変えるときは、AC 一覧を同じ commit で修正する。

※7：観点は、規則、一貫性、重複、境界、文書とコード、テスト、安定性、不要なもの、後の開発への備え。

サブエージェントとモデルの表（DC-201）：

| 作業 | 使うモデル |
|------|------------|
| 機械的な作業（一覧の作成、照合） | 安価なモデル |
| 判断が必要な作業（規則の当てはめ、一貫性） | 中位のモデル |
| 設計の決定、まとめ、利用者との相談 | メインのセッション |
| リスクの高い作業 | 高性能なモデル |

- 根拠は、spec 010 の後の全体レビューの実績（token、ツールの呼び出し回数、時間）と、そこから得た教訓にする。
- 教訓は 3 つ：範囲を小さく分ける。メインのセッションが規則の要約を渡す。メインのセッションは、全部の結果がそろってからまとめる。

文書の言い回しの安定化（DC-205）：

| 方法 | 内容 |
|------|------|
| A | メインのセッションが書き、日本語だけの文脈のサブエージェントがレビューする |
| B | メインのセッションが日本語の要点（決定の表、事実、参照）を作り、日本語だけの文脈のサブエージェントが本文を書く。メインのセッションは内容だけを確認する |

- 本 plan は方法 B で書いた（試行の 1 回目）。
- あわせて、良い文書の見本を渡す方法と、textlint（技術文書向けの規則のプリセットと、用語の辞書）を評価する。
- 結果から、どの文書にどの方法を使うかを決め、レビュー skill と skill `docs` に書く。

MCP サーバーの評価（DC-206）：

- 候補は 3 つ：IntelliJ の MCP、LSP によるコードの参照（Serena、Claude Code の LSP のプラグイン）、ライブラリの最新の文書（context7）。
- 開発者ごとの環境に依存するもの（有料の機能を含む IDE など）は、導入しても任意（オプション）とし、なくても同じ作業ができるようにする。理由：リポジトリの手順を、特定の有料のツールに依存させないため。
- 同じ作業（ある型の参照元を探す、など）で、使わないときと使うときの token とツールの呼び出し回数を比較する。
- 導入するものは、設定の手順を[開発環境の起動](../../guides/setup.md)に書く。
