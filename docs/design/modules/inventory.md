# 在庫モジュール

バリアントごとの在庫数と調整履歴、注文手続き中の引当を管理する。

| 項目 | 内容 |
|------|------|
| レベル | A（並行して調整されても失われないこと、引当と減算） |
| 依存 | 商品カタログ（イベント） |
| 関連 spec | [001](../../specs/001-catalog-and-inventory)、[002](../../specs/002-cart-and-order)、[017](../../specs/017-stability)、[018](../../specs/018-docs-and-tools)、[019](../../specs/019-mvp-completion) |

## 在庫（集約）と在庫調整

- 在庫は、バリアント、商品、在庫数を持つ。
- 在庫調整は、増減量（0 以外）、調整理由、メモを持つ。理由が「その他」ならメモは必須。
- 運営者の調整は、1 回の増減量が ±1,000,000 以内で、調整後の在庫数が 1,000,000 以下。注文のキャンセルで戻す調整には、在庫数の上限を当てない（引き当てた分を戻すだけで、桁あふれにならないため）。
- 調整履歴は集約に含めず、追記だけの記録として別に保存する（増え続けるため）。

## 在庫の調整は「差分の加算」

在庫を読んで書き戻す方式（楽観ロック）は使わず、「今の在庫数に増減量を加える。ただし結果が負にならず、運営者の調整なら上限を超えないときだけ」という 1 回の更新で行う ※1。

```sql
UPDATE inventory.stock_item
   SET quantity = quantity + :delta
 WHERE variant_id = :variantId AND quantity + :delta >= 0
   AND quantity + :delta <= 1000000  -- 運営者の調整のときだけ
RETURNING quantity;
```

※1：楽観ロックだと、+5 と +3 が同時に来ると片方が失敗して再試行が必要になる。差分の加算なら DB が順に処理するので両方が反映される。

- 更新されなかったら、「負になる」「上限を超える」「在庫がない」のどれか。
  - 増やす調整：運営者の調整なら今の在庫数を読み、増減量を加えると上限を超えるなら 400、それ以外は 404。注文のキャンセルの調整は、在庫の有無を確認せずに 404 ※2。
  - 減らす調整：在庫の有無を確認し、あれば 400、なければ 404。
- 更新後の在庫数を受け取り、同じトランザクションで調整履歴に書く。
- 運営者の調整は、運営者 ID と氏名の写し（token の姓と名）を残し、表示は写しを使う。注文に由来する調整は空。

※2：在庫の有無を確認すると、更新の後に（バリアント登録のイベントで非同期に）作られた在庫が見え、400 と誤ることがあるため。運営者の調整で今の在庫数を読むときは、更新の後に作られた在庫は在庫数 0 で、1 回の増減量は上限以下なので、上限を超えると誤らない。

「在庫数は負にならない」は、ドメインではなく、この更新の条件と DB の CHECK 制約にある。変えるときはここを変える。

### 検証と履歴の並び

| 場面 | 結果 |
|------|------|
| 増減量が 0 か ±1,000,000 超、理由が「その他」でメモが空、メモが 500 文字超 | DB に触れる前にドメインで 400（増減量の範囲は契約でも 400） |
| 調整後に負になる | 400 |
| 運営者の調整で、調整後の在庫数が 1,000,000 を超える | 400 |
| 在庫がまだないバリアント | 404 |

履歴は調整日時の新しい順、同じ日時なら記録した順（連番）の新しい順（ページをまたいでも順序が変わらない）。

## 引当

注文手続きの間、在庫を期限付きで引き当て、他の消費者に売れないようにする。

- 引当は、持ち主（注文手続き）、在庫、数量、期限を持つ。持ち主と在庫の組で 1 つ。
- 販売可能数 ＝ 在庫数 − 有効な引当の合計。期限切れの引当は数えないだけで、すぐには削除しない ※3。
- 期限から保存期間（既定 1 日）を過ぎた引当は、片付けのジョブが削除する（[バックエンドのアーキテクチャ](../backend-architecture.md) 第 5 節）。
- 引当は在庫数を変えない。在庫数を変えるのは、運営者の調整、注文の成立、キャンセルだけ。
- C 側の在庫の有無は、販売可能数が 1 以上か。

※3：期限の判定に解放のジョブも Redis も不要で、引当と注文を同じトランザクションで扱える。

### 操作

いずれも呼び出し元（注文モジュール）のトランザクションに参加する。

| 操作 | 内容 |
|------|------|
| 引き当てる | 対象の在庫をバリアント ID の順に行ロックし、他の持ち主の有効な引当を除いた販売可能数で判定する。全品目が足りれば、この持ち主の引当を置き換える。足りなければ何も書かず、足りない品目を返す |
| 解く | 持ち主の引当を削除する |
| 減算に置き換える | 行ロックのうえ、他の持ち主の引当を除いて足りるかを確認し、在庫数を減らし、持ち主の引当を削除し、理由「注文」と注文番号で調整履歴を書く。1 つでも足りなければ何も変えない |
| 戻す | 在庫数を増やし、理由「注文のキャンセル」と注文番号で調整履歴を書く |

- 運営者の調整は引当を考慮しない（販売可能数より多く減らすと、引当中の注文が成立しないことがある）。
- 理由「注文」「注文のキャンセル」は運営者の調整では選べない（400）。

## 在庫の作成と削除

- バリアントが登録されたら、在庫数 0 の在庫を作る（同じイベントが 2 回届いても 1 つ）。
- バリアント・商品が削除されたら、その在庫と調整履歴を削除する。
- イベントはコミット後に非同期で届くので、登録直後のごく短い間は在庫がない。C 側は「在庫なし」、B 側の調整は「見つからない」になる。

### イベントの処理に失敗したとき

失敗したイベントは、定期ジョブが自動で再発行する（[バックエンドのアーキテクチャ](../backend-architecture.md) 第 5 節）。リスナーは冪等なので、重複して届いてもよい。

| 項目 | 内容 |
|------|------|
| 起きること | 登録のイベントで失敗すると、再発行で処理されるまで在庫が作られず、C 側は「在庫なし」、B 側は「見つからない」。削除のイベントで失敗すると、在庫と履歴が残る（業務上の影響はない） |
| 検知方法 | 未完了のイベントがイベント発行記録に残り、エラーログが出力される。原因が残っていれば、再発行のたびに失敗し、処理の回数が上限に達すると再発行を止める（未完了と止めたイベントの件数はメトリクスに出る） |
| 復旧 | 原因を取り除けば、次の再発行で処理される。止めたイベントは、処理の回数を戻すと再発行される（[バックエンドのアーキテクチャ](../backend-architecture.md) 第 5 節） |
| 順序の逆転 | 削除が登録より先に処理されると、削除済みのバリアントの在庫が残る。参照されないので放置する |

## 構成

```
inventory/
├── api/                    # 販売可能数の照会、在庫の操作（引き当てる、解く、減算に置き換える、戻す）
├── presentation/           # admin.yaml から生成したインターフェースを実装
├── application/            # 在庫の調整と参照、引当、期限切れの引当の片付け、商品カタログのイベントのリスナー
│   ├── model/              # コマンド（command）と表示の型（view）
│   └── port/               # 在庫の参照用リポジトリ
├── domain/
│   └── stock/              # 在庫の調整、行ロックした在庫、引当の判定、エラー。port/ は在庫と引当のリポジトリ
└── infrastructure/
    └── persistence/        # リポジトリと参照用リポジトリの実装、有効な引当の条件
```

## 他のモジュールへの公開

| 種類 | 内容 | 利用者 |
|------|------|--------|
| API | 複数のバリアントの在庫の有無（販売可能数が 1 以上なら「あり」、在庫がなければ「なし」） | 店舗 |
| API | 販売可能数（持ち主を指定すると、その引当を除く） | カート、注文 |
| API | 引き当てる、解く、減算に置き換える、戻す | 注文 |
