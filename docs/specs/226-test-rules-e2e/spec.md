# Spec 226：E2E とフロントのテストの書き方の規則と検査を整える

ステータス：確定

## 1. 背景と目的

テストの書き方の規則のうち、E2E の書き方と、フロントのテストの書き方の一部が、規則の文書にも検査にも足りない。

- spec 185 でフロントのテストの書き方の検査（`scripts/ci/frontend-rules.mjs`）を作った。E2E の書き方の規則（位置（インデックス）で要素を選ばない、`networkidle` で待たない、ボタンを名前（支援技術向けの名前）の完全一致で探す、タイムアウトは定数で書く）は、まだ機械で検査していない（[#218](https://github.com/roger88106/ec-site/issues/218)。出典：spec 185 第 8 節、spec 194 第 9 節の 2）。
- spec 184 の候補のうち、(d)（テストの `const` に、組み込みの名前（`URL`、`screen`、`location`、`name`）を使う）と (e)（`})` の直後に空行なしで `test(`・`describe(` が続く）も、検査にしていない（#218）。本 spec では、(d) を「組み込みの名前のシャドーイング」と呼ぶ。
- spec 194 の最後のレビューで、E2E と手元の script に、未対応の小さな項目が 3 つ見つかった（[#216](https://github.com/roger88106/ec-site/issues/216)。出典：spec 194 第 9 節の 1、3、4）。
- spec 184 でそろえた書き方のうち、jest-dom で状態と属性を確認する、環境変数は `vi.stubEnv` で変える、組み込みの名前をシャドーイングしない、の 3 つが、テストの書き方に書かれていない（[#205](https://github.com/roger88106/ec-site/issues/205)）。`fireEvent` と、要素のプロパティ・属性の `toBe` での比較は、spec 185 の T185-04-01 が [テストの書き方](../../rules/test-writing.md) 第 4.7、4.8 節に書いたので、本 spec では書き直さない。
- 規則の文書にない検査は、先にテストの書き方に規則を書いてから加える（spec 183 の確認で利用者が決めた方針。#218 の本文）。

追跡の issue は [#226](https://github.com/roger88106/ec-site/issues/226)、扱う issue は #218、#216、#205 である。作業ブランチは `226-test-rules-e2e`。本 spec は整理の spec で、規模は M である（第 6 節の 1。追跡の issue の本文に書いた規模は L だった）。

実装は、[#222](https://github.com/roger88106/ec-site/issues/222)（文書の整理。バージョンの意味の一字の語を「バージョン」に言い換える）と、[#225](https://github.com/roger88106/ec-site/issues/225)（CI の検査の script の整理。#219、#221）のマージの後に始める。#225 が整える `frontend-rules` のファイルの種類と振り分けの関数を、本 spec の新しい検査が使うため（第 8 節の 1）。

## 6. 決めたこと

spec の確認で、利用者が第 6 節の 1〜5 を全て案 A に決めた（2026-10-27）。Open questions はない。

### 6.1 規模

- 案 A（推奨。採用）：M。理由：API の契約とデータベースを変えず、モジュールのコードを変えず、AC も変えないため（[開発の進め方](../../rules/workflow.md) 第 4.2 節の判定の基準）。変えるのは検査の script、E2E、手元の script、規則の文書で、似た範囲の spec 185、spec 194 も M だった。
- 案 B：L。3 つの issue をまとめ、並行する spec との順序を plan に書ける。ただし、規模の基準に合わず、順序は第 8 節の 1 に書ける。

### 6.2 テストのコードのコメントの spec の番号（DC-226-16〜18）

今の規則（コメントの書き方 第 1 節）は、本番のコードとバックエンドのテストを対象にし、フロントのテストを対象外にしている。E2E は、対象にも対象外にも書かれていない。

- 案 A（推奨。採用）：対象を全てのテストのコード（フロントのテストと E2E）に広げ、番号の検査の対象に加える。今の違反（18 か所）は、規則を言葉で書く形に修正する。理由：バックエンドのテストと扱いをそろえ、番号が照合されずに古くなる理由（コメントの書き方 第 1 節）は、テストのコードにも当てはまるため。
- 案 B：E2E だけを加える。フロントのテストは対象外のまま。
- 案 C：広げない。E2E を対象外とコメントの書き方に明記する。

### 6.3 組み込みの名前の範囲（DC-226-7、8、10、13）

- 案 A（推奨。採用）：TypeScript の lib（ES と DOM）が宣言するグローバルの名前を、`const`・`let` の宣言でシャドーイングしない。関数の引数は対象外。今の違反は約 21 か所（`status`、`name` など）で、名前を変える。理由：一覧を手動で持たずに済み、宣言を忘れたときに、エラーにならずにグローバルの値が使われることを防ぐため。引数まで含めると違反が倍以上になり、引数の名前は呼び出しの近くで読めるので効果が小さい。
- 案 B：spec 184 で挙げた名前（`URL`、`screen`、`location`、`name`）だけを、検査の一覧に書く。今の違反は E2E の `name` 7 か所。
- 案 C：案 A に関数の引数も含める。

名前の一覧の得方（DC-226-8）は、spec 担当のセッションが次のとおり決めた。CI の検査の script を流す job（`docs.yml`）は依存を入れず、TypeScript の lib を読めないため。

- 名前の一覧は、TypeScript の lib の宣言のファイル（`lib.*.d.ts`）を読んで生成するファイルとして、`scripts/ci/` のサブディレクトリに置き、検査はそのファイルを読む。`scripts/ci/` の直下に置かないのは、`check-all.sh` が直下の script を全て検査として実行するため。生成は `--write` で行う（AC 一覧の `ac-check.mjs --write` と同じ形）。
- 生成したファイルと、今の TypeScript の lib の名前が一致することを、TypeScript を入れる CI の job（管理画面か共有パッケージ）で確認する。どの job のどの手順に置くかは T226-02-02 で決め、結果に書く。

### 6.4 ボタンの名前の完全一致（DC-226-3）

- 案 A（推奨。採用）：`exact: true` の文字列か、先頭（`^`）と末尾（`$`）を固定した正規表現を、完全一致とみなす。理由：注文するボタンのように、名前に金額などの変わる値を含むボタンは、文字列で完全一致させられないため。固定した正規表現は、別のボタンの名前の一部に一致しない。
- 案 B：`exact: true` の文字列だけを認める。注文するボタンは、金額を計算して文字列で探す形に修正する。

### 6.5 E2E の補助の URL の渡し方（DC-226-19、20）

- 案 A（推奨。採用）：URL は最後の引数のオプション（`{ storeUrl }`・`{ adminUrl }` などの項目）で受け取る。他の省略できる引数（遷移先のパス、氏名など）も同じオプションに入れる。理由：引数の位置を覚えずに済み、撮影が空のオプションや既定の値を並べて渡さずに済むため。
- 案 B：URL を各補助の最後の位置引数にそろえる。空のオプションを渡す呼び出しは残る。

## 8. tasks

tasks は第 6 節の決定に基づく。

- `[P]` のタスクはない。同じ段階のタスクは、番号の順に 1 つずつ行う。理由：多くのタスクが、同じ検査の script（`frontend-rules.mjs`）と共有の文書（[テストの書き方](../../rules/test-writing.md)、[CI の検査](../../guides/ci.md)）を変えるため。
- `[テスト]` のタスクは、テストを書いてレッドを確認し、同じ実装役が続けて実装し、同じ commit に入れる（[開発の進め方](../../rules/workflow.md) 第 2.1 節の例外）。
- 検査を加える・広げるタスクは、[CI の検査](../../guides/ci.md) の表の行と、テストの書き方・コメントの書き方の規則の一覧の確認方法を、同じタスクで修正する。
