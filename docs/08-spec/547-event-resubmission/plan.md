共通の決定：

- 危険度は高にしない。
- 1 タスクを 1 commit にする（AGENTS.md の Git の「単位」より厳しい決定）。
- イベントの再発行・止めたイベント・トランザクションを扱うタスクに `[リスク]` を付け、高性能のサブエージェント（実装役）に任せる（[エージェントの作業フロー](../../05-開発規則/subagents.md)の「任せる作業とモデル」）。それ以外の実装は汎用のサブエージェントに任せる。
- レビューの profile は厚めにする（issue 担当の指定）。
- 重い検査（バックエンドの全体のテスト、CI の全検査、E2E）は、並行する全てのセッションを通して同時に 1 つだけ実行する。実行の前に issue 担当に知らせ、合図を待つ。Gradle の daemon を停止する操作は実行しない。途中の確認は、変えたテストのクラスを指定して実行する。
- 並行する spec との重なり：#493 は商品カタログの集約（バリアントの登録のイベントを登録する所）を変えるが、本 spec は商品カタログを変えず、イベントの型も変えないので、ファイルは重ならない。#548 は配送のリスナーを変えうるが、本 spec は確認だけをする。#491 はまだ始まっていない。全体のブランチを取り込むときに、重なりが増えていないかを、実装を始める前の照合で確認する。

次の 3 つは、Spring Modulith 2.1.2 の sources jar を読んで確認したが、実行して確認していない。確認するタスクを添える。

- 条件を渡す再発行の操作（未完了のイベントの再発行）は、完了していない全ての行を読み、条件で絞ってから再発行の印を付ける（T547-01-01 のテストで確認する）。
- 失敗したイベントの再発行の操作は、状態が失敗の行と、状態が空で未完了の行を、発行の古い順に件数の上限まで読む（T547-02-01 で確認する）。状態が空の行は、今のイベントの記録の表の作り方（Spring Modulith 2 の形）では作られないので、実際に読むのは失敗の行だけになる。
- 同期のリスナー（トランザクションの中で受ける）は、Spring Modulith のイベントの記録に行を作らない（T547-01-03 で確認する）。

次の 1 つは、確認しない扱いとして決めた。

- 再発行のときにリスナーが見つからない記録は、エラーのログを出力して失敗の状態に戻される。ローカルの DB に、在庫の非同期リスナーの未完了の記録が残っていたときの扱いである。本番の環境はまだないので、移行の処理は作らない。

## 再発行の対象（DS-547-1：DC-547-1〜3）

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 再発行の条件に「状態が失敗」を加える。発行からの時間、最後の処理からの時間、処理の回数の条件は今のまま | `config/event/EventResubmissionJob` | 統合テスト：発行から下限の時間を過ぎた、発行済み・処理中・再発行済みのイベントを再発行しない（新しく書く。レッドを確認する）。既存の AC-290 のテストが通る |
| 処理の途中でインスタンスが止まったイベントは、Spring Modulith の監視が失敗にした後の実行で再発行する。監視は今の設定で有効なので、設定は変えない ※1 | `application.yml`（変えない）の `spring.modulith.events.staleness` | 統合テスト：監視が失敗にした後に再発行される（既存の AC-291 の「結果の出ないまま 5 分」のテストの形にそろえる） |
| 条件の前のコメントを、今の条件に合わせて書き換える | `EventResubmissionJob` | レビュー |

※1：監視は、処理中・発行済み・再発行済みの時間（どれも 5 分）を設定すると有効になり、定期ジョブの仕組み（`ecsite.scheduling.enabled`、既定で有効）の上で、確認の間隔（5 分）ごとに動く（Spring Modulith 2.1.2 のソースと、今の設定で確認した）。ローカルの起動のログに監視の開始の行が出ることを、T547-02-05 で確認する。

- 理由：処理中のイベントを選ばないので、遅いリスナーに同じイベントを重ねて渡さない。処理の途中で止まったイベントは、監視が失敗にするので取りこぼさない。
- この段階では、今の再発行の操作（条件を渡す方）のまま、条件だけを加える。読み込みの範囲を変えるのは段階 2 である。

## 在庫の作成（DS-547-3：DC-547-9）

| 何を | どこに | 確認方法 |

| バリアントの登録のイベントを、在庫のリスナーが、商品カタログのトランザクションの中で同期で受ける。トランザクションの外で呼ばれたら例外にする ※2 | `inventory/application/handler/CatalogEventHandler` | 統合テスト：バリアントを登録したトランザクションの中で在庫の行が作られている。登録のトランザクションを巻き戻すと在庫の行も残らない（レッドを確認する） |

| 削除が先に処理されても在庫が残らないことは、登録と在庫の作成が同じコミットになることで保つ。削除済みを表す印は残さない | — | 統合テスト：登録の後に削除すると在庫がない（既存の管理 API の流れのテスト） |
| 在庫の作成の重複を無視する今の実装（同じバリアントで 2 回呼んでも 1 つ）は変えない | `StockCommandService`、`JooqStockItemRepository` | 既存のテスト |

※2：同期で受けるには `@EventListener` を使い、呼んだ側のトランザクションに加わることを `@Transactional(propagation = MANDATORY)` で必須にする。

- 理由：削除のイベントは、バリアントの登録がコミットされた後にしか発行されない。在庫の作成が同じコミットに入れば、削除より後に在庫を作ることがない。

- #491 はまだ始まっていない（2026-11-18）。#491 は公開の API にトランザクションの前提の注釈を付ける。このリスナーは公開の API ではないが、呼んだ側のトランザクションに加わる前提のメソッドを必須にする点で、#491 の方針と合う。#491 を始めるときに、このリスナーも対象に含めるかを issue 担当が決める。
- 設計書の更新は、[バックエンドのアーキテクチャ](../../02-設計/backend-architecture.md)の「モジュラーモノリス」（イベントを同期で受ける例外として、在庫の作成を加える）、[在庫モジュール](../../03-機能仕様/inventory.md)の「在庫の作成と削除」の該当の行、[在庫の設計](../../02-設計/inventory.md)の「在庫の作成と削除」の流れである。範囲は段階 1 の tasks の T547-01-06 にある。

## 止めたイベント（DS-547-2：DC-547-4〜8）

段階 2 で行う。

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 止めたイベントの表を common schema に追加する。列と論理名のコメントは ※4 | 新しいマイグレーション（`common_create_event_publication_stopped`） | 統合テスト（論理名のコメントの検査を含む既存の検査） |
| 止める操作：上限以上の失敗した未完了の行を、止めたイベントの表に移し、エラーのログに出力する ※5 | `EventPublicationRecords` | 統合テスト：上限を下げても、上限以上の失敗したイベントが全て移り、ログが 1 回ずつ出る（DC-547-4、5。レッドを確認する） |
| 再発行は、失敗したイベントの再発行の操作に替える。件数の上限は付けない ※6 | `EventResubmissionJob` | 統合テスト：止めたイベントを読まない（DC-547-6）。既存の再発行のテストが通る |
| メトリクス：未完了の件数は、2 つの表の未完了の合計。止めた件数は、止めたイベントの表の件数 | `EventPublicationRecords`、`EventPublicationMetrics` | 統合テスト（DC-547-7） |
| 復旧の手順：止めたイベントの表の行を、イベントの記録の表に戻す。不要なら止めたイベントの表から削除する ※7 | `docs/02-設計/backend-architecture.md` の「イベントの再発行」（SQL をコードブロックで示す） | 統合テスト：設計書の手順で戻した行が、次の実行で再発行される |
| 処理の回数の列のコメント（止めた印の意味）を書き換える | 同じマイグレーション | 統合テスト |
| 片付けのジョブは、止めたイベントの表を消さない（止めたイベントは処理を終えていないため。今と同じ） | `EventCleanupJob`（変えない） | 既存の `EventCleanupJobTest` が通る |

※4：列は、イベントの記録の表のうち復旧に必要なもの（ID、リスナー、種類、中身、発行の時刻、処理の回数、最後の再発行の時刻）と、止めた時刻である。状態と処理を終えた時刻は、止めたイベントでは常に「失敗」と「なし」なので置かない。テーブルと列に論理名のコメントを付ける。理由：Spring Modulith の表と全ての列をそろえると、Spring Modulith を上げて列が増えるたびに、止めたイベントの表も変える必要があるため。復旧の手順（※7）は戻す列を名前で並べるので、列が増えても、増えた列が空を許すかを確認すれば足りる。

※5：移す条件は、処理の回数が上限以上で、状態が失敗で、完了していないこと。1 つの SQL 文で、イベントの記録の表から消して止めたイベントの表に入れる。移した行ごとに、エラーのログを 1 回出力する。

※6：失敗したイベントの再発行の操作は、再発行の選択肢（`ResubmissionOptions`）を受ける。発行からの時間の下限は選択肢の下限の時間（`withMinAge`）で、最後の処理からの時間と処理の回数は選択肢の絞り込みの条件（`withFilter`）で指定する。

※7：戻す行は、状態を失敗、処理の回数を 1 にし、戻したら止めたイベントの表から削除する（1 つのトランザクション）。処理の回数を 1 にするのは、上限に達するまで、もう一度再発行するため。

- 理由（件数の上限を付けない）：上限を付けると、発行の古い失敗したイベントだけが毎回読まれ、新しいイベントの再発行が遅れるため。止めたイベントは移すので、失敗の状態の行は、まだ再発行するものだけになる。
