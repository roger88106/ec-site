# Spec 489：商品の画像の受け付けで、失敗したときに、参照されないファイルが残らず、元のエラーが失われないようにする

種類：整理　規模：L　ステータス：確定

## 背景と目的

#458（main 全体の書き方と構成のレビュー）で、画像の受け付けの失敗の扱いに 3 つの問題が見つかった。追跡の issue は #489 で、#544（リリースの前の整理）の段階 3 の線 B の 3 つ目（#481 の後、#557 の前）である。消費者・運営者に見える振る舞いは変えない（例外は DN-489-1 の表の 1 件）。

1. 画像の用意は、DB に何も残さずに配信のバケット（公開、1 年キャッシュ）へ書く。次のどれでも、参照されない公開のファイルが残り、探す手段がない。
   - 登録か破棄の前にプロセスが落ちる。
   - 破棄が失敗する。
   - 同じ受付 ID で繰り返し用意する。

   今の[メディアモジュール](../../03-機能仕様/media.md)の「アップロードの流れ」も、登録のないファイルの検出と削除は行わないと書いている。
2. 商品カタログの画像の追加は、保存が失敗したときに画像を破棄する。破棄も例外を投げると、破棄の例外が投げられ、元の失敗（バージョンの競合、上限など）が失われる。メディアの破棄が捕捉して例外を投げないのはストレージの削除の失敗（実行時例外）だけで、それ以外（トランザクションの状態の例外など）は投げることがある。
3. 解放は、記録を読んでから削除する 2 回の問い合わせで行う。同じアセットを同時に解放すると、両方がアセット解放のイベントを発行する。ファイルの削除は冪等なので、イベントが重ねて発行されても結果は変わらない。

## スコープ

| 含める | 含めない |
|--------|----------|
| 仮の記録の表（メディアの schema）と、用意・登録・破棄での仮の記録の扱い | アセットの表の変更 |
| 保存期間を過ぎた仮の記録を、配信のファイルと共に削除する片付けのジョブと、その設定 | 仮の記録の導入より前に残った、参照されない公開のファイルの片付け |
| 画像の追加で、破棄の例外を、元の例外に抑制された例外として付けること | アップロードのバケット（非公開）のライフサイクル規則の変更 |
| 解放で、実際に削除した記録の分だけイベントを発行すること | 画像の形式・大きさの規則、API の契約の変更 |
| メディアの機能仕様・設計、環境変数の手順書、用語集、メディアの公開 API のコメントの修正 | |

## 目的と完了条件

### DS-489-1 途中で失敗しても、参照されない公開のファイルが残り続けない（D / P1）

- **DC-489-1** 用意は、配信のバケットに書く前に、仮の記録を残す。
- **DC-489-2** 登録は、呼んだ側のトランザクションの中で仮の記録を削除し、アセットを記録する。呼んだ側の保存が取り消されると、仮の記録は残る。
- **DC-489-3** 破棄は、配信のファイルを削除した後に仮の記録を削除する。ファイルを削除できないときは、仮の記録を残す。
- **DC-489-4** 片付けのジョブは、保存期間を過ぎた仮の記録を削除し、その配信のファイルをコミットの後に削除する。保存期間の中の仮の記録は削除しない。
- **DC-489-5** 用意した画像のうち、仮の記録がないもの（片付けのジョブが削除した後など）は登録できず、呼んだ側の保存も取り消される。

### DS-489-2 破棄が失敗しても、元のエラーが返る（D / P1）

- **DC-489-6** 画像の追加で保存が失敗し、破棄も例外を投げたとき、元の例外が投げられ、破棄の例外は抑制された例外として付いている。

### DS-489-3 解放のイベントが、実際に削除した記録の分だけ発行される（D / P2）

- **DC-489-7** 解放は、記録を実際に削除したアセットの分だけ、アセット解放のイベントを発行する。

### DS-489-4 文書と検査（D / P1）

- **DC-489-8** メディアの機能仕様・設計、環境変数の手順書、用語集が、仮の記録と片付けのジョブを反映している。
- **DC-489-9** `./gradlew check` が通る。

各 DC の確認方法は[plan](plan.md)の各節の表にある。

## 非機能要件

- **DN-489-1** 消費者・運営者に見える振る舞いを変えない。例外は、次の表の 1 件である。理由：レビューで見つけた不具合の修正のため（[開発の進め方](../../05-開発規則/workflow.md)の「コードと文書の食い違い」）。前例は spec 549 の DN-549-1 である。
- **DN-489-2** 例外の 1 件は、テストを先に書いて失敗（レッド）を確認してから修正する。
- **DN-489-3** API の契約（OpenAPI）、AC、アセットの表を変えない。DB は、メディアの schema に仮の記録の表を 1 つ加えるだけにする。
- **DN-489-4** 前のリリースのアプリが、新しいスキーマで動き続けられる（[バックエンドの書き方](../../05-開発規則/backend-coding.md)の「前のリリースのアプリが動き続けられる変更だけにする」）。表を加えるだけで、前のアプリはその表を読み書きしない。用意と登録は、1 つの画像の追加のリクエストの中で、同じインスタンスが続けて行う。そのため、前のアプリが用意して新しいアプリが登録することはない。
- **DN-489-5** アーカイブした spec と、適用済みのマイグレーションを変えない。

DN-489-1 の例外は、次の表のとおり。

| 修正 | 今 | 修正した後 |
|------|-----|------------|
| 画像の追加で保存が失敗し、破棄も例外を投げたとき | 破棄の例外が返り、元の失敗（バージョンの競合など）が失われる | 元の失敗が返る |

## Non-goals

| 項目 | 理由 |
|------|------|
| アセットの表に状態の列を加える形（仮と確定を 1 つの表で持つ） | アセットを読む全ての問い合わせに状態の条件が必要になり、漏れると仮のアセットの URL を返しうるため。別の表なら、今のアセットの操作を変えない |
| 変換した画像を非公開の場所に置き、登録のときに配信の場所へコピーする形（issue の案 1 の後半） | コピーはコミットの後にしかできず（AC-304）、コピーが終わるまで登録した画像の URL で画像を取得できないか、再試行の仕組みが必要になるため ※1 |
| 同じアセットを同時に解放するテスト（2 つのトランザクションを同時に動かすもの） | 削除した行を返す操作をリポジトリのテストで、返した分のイベントの発行をサービスのテストで確認すれば足りるため（前例：spec 549 の Non-goals） |
| 仮の記録の導入より前に残ったファイルの片付け | 本番の環境はまだなく、ローカルは再作成すればよいため |

※1：コピーは外部の呼び出しなので、トランザクションの中ではできない。その間、運営者の画面で画像が表示されない。ストレージの操作にコピーを加える必要もある。
