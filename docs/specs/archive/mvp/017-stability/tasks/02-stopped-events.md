# 段階 2：止めたイベント

- 前提：段階 1（止めたイベントが片付けで消えないことを確認するため）
- 完了条件：US-62 のテストが通る。再発行の回数が上限を超えたイベントは自動で再発行されず、止めたときに 1 回だけエラーのログが出力される。未完了と止めたイベントの件数がメトリクスで公開される。既存のテストが全て通る（`./gradlew check`）。
- 参照：[plan](../plan.md) 第 2 節、spec の US-62、[バックエンドのアーキテクチャ](../../../../../design/backend-architecture.md) 第 5 節

## タスク

- [x] **T017-02-01** [テスト] 再発行の上限の統合テストを書く。レッドを確認する。
  - 失敗し続けるリスナーのイベントは、再発行の回数が上限（テストで小さくする）に達したら、それ以上再発行されない（AC-290）。
  - 上限に達する前に処理できたイベントは、今どおり処理を終える。
  - 再発行の回数の数え方（発行の時点の値、再発行ごとの増え方）を、Spring Modulith の実際の挙動で確認し、テストの名前とコメントに書く。
  - `completion_attempts` は発行の時点で 1、再発行のたびに 1 つ増える。再発行の回数ではなく処理の回数（発行の時の 1 回を含む）なので、上限は「処理の回数」の上限と呼ぶ。既定 60 では、再発行は 59 回（発行の 5 分後から 1 分ごとで、約 1 時間）。
- [x] **T017-02-02** 再発行の設定に上限（`max-attempts`、既定 60）を追加し、再発行のジョブを、上限より少ないものだけを再発行する形に替える。T017-02-01 を通す。
  - plan 第 2 節と変えた：再発行の選択肢（`ResubmissionOptions`）は、状態が `FAILED` のものだけを件数の上限（既定 100）で古い順に読んでから絞り込むので、止めたイベントが 100 件溜まると、新しいイベントが再発行されなくなる。また、処理中のまま止まった（インスタンスが停止した）イベントを対象にしなくなる。今の再発行と同じものを読む、絞り込みの関数を渡す操作（`resubmitIncompletePublications(Predicate)`）で、発行の日時と処理の回数で絞る。
  - 既定値は単体テスト（`EventResubmissionSettingsTest`）で確認した。
