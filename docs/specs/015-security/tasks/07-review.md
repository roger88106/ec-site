## レビューの結果

### 修正したこと

- 外部サービス（決済、物流）の実装を、サービスごとの mock フラグで選ぶ形にした。フラグがなければ本番の実装を使い、物流は本番の実装がないので、フラグの名前を出力して起動に失敗する。決済の実装を選ぶ今までの設定は削除した。
- 店舗 API の token の要否を契約（`store.yaml` の `security`）から読み、契約にないエンドポイントと、どの filter chain にも一致しないエンドポイントを既定で拒む（401）。管理 API と同じ、契約を読む型を共通にした。
- 死活監視とメトリクスを、運用ポート（ローカル 9080、E2E 9090）に移し、業務ポートでは出さない。
- 管理画面の本番ビルドは、IdP の設定がなければ失敗する。店舗画面は公開する URL（`AUTH_URL`）を必須にし、ログイン・ログアウトの戻り先をリクエストヘッダーのホストから作らない。`trustHost` を削除した。
- compose のポートを既定で 127.0.0.1 だけにし、1 つの変数（`LOCAL_BIND_ADDRESS`）で替えられるようにした。本番の jar から、ローカル・E2E・Stripe の設定ファイルを除いた。
- 決済の mock の、テストだけで使う操作を、testFixtures の包む実装（`TestPaymentGateway`）に移した。
- レビューで修正した：本番の jar を物流のフラグなしで起動すると、フラグの名前を出力せずに起動に失敗していた（T015-05-05）。フロントの書き方 第 8.1 節の、`process.env` を読まない規則の除くもの（T015-07-03）。
- 検査を追加した：compose のポートの検査（`compose-ports.mjs`）、本番の jar の中身の検査（Gradle の `checkBootJar`）。ローカルでは、テスト名に出ない AC は警告だけにし、CI では失敗させる（`ac-check`）。

### 修正せずに残したこと

| 項目 | 理由 |
|------|------|
| 業務ポートの既定の filter chain が `/actuator/**` を許す | 運用ポートにも同じ filter chain が掛かるため（plan 第 2 節 ※4）。業務ポートでは Controller がないので 404 になる |
| 物流の mock の、誤った署名や日時を指定した通知を作るエンドポイントは、本番の mock に残る | spec の範囲（AC-246）は決済の mock。物流の mock は、フラグを立てなければ Bean ができない |
| T015-02-01 のレッドはコンパイルの失敗だけ。AC-236 の統合テストと、AC-241 のログインの戻り先のテストは、初めから通った | T015-02-01 は実装を先に書いた。AC-236 はテストが自分でポートを開くので、設定ファイルの値は AC-237 の単体テストで確認した（レッドだった）。AC-241 は、`AUTH_URL` を空にすると失敗することをレッドの代わりにした |
| AC-243、244、245、247 は、テスト名でなく除外の一覧に、確認する所を書いた | compose のファイルの書き方、jar の作り方、jar の起動で決まり、テスト名を持たない（plan 第 5 節） |
