# Spec 245：エージェントの作業の流れとレビューの規則を再検討する

ステータス：草案

## 1. 背景と目的

整理の段階（milestone「整理の段階」）の第 1 段の spec である。第 1 段は 6 つの spec（#245〜#250）が並行する。第 6 弾（spec 222〜227）までの作業で、レビューのサブエージェントの費用が大きいこと、マージと並行のセッションの運用に規則がないことが分かった。本 spec は、レビュー、マージ、モデルの選び方、セッションの運用、振り返りの規則を再検討する。目的は、token を減らしつつ品質を上げることである。品質を優先する（利用者、2026-10-27）。

追跡の issue は [#245](https://github.com/roger88106/ec-site/issues/245) で、扱う issue（sub-issue）は #106、#130、#99、#105、#21 である。作業ブランチは `245-workflow-review` である。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。

### 1.2 規模

L とする（利用者が承認、2026-10-28）。理由は次の 2 つである。

- レビュー、マージ、モデル、セッションの運用の 4 つの規則の文書（AGENTS.md、開発の進め方、エージェントの作業フロー、skill `review`・`retro`）と、GitHub の保護の規則・CI の設定にまたがるため。
- 危険度の区分の経路、profile の選び方、振り返りの集め方など、plan で決める設計の判断が多いため。

段階は 3 つの見込みである。段階 1 がレビューとマージ、段階 2 がモデルと作業の形、段階 3 がセッションの運用と振り返りである。段階の分け方は plan で決める。

## 2. 用語

| 用語 | 意味 |

| profile | レビューの量（時点ごとのモデルと回数）の組。今は厚め・標準・節約 |

## 4. 目的と完了条件

### DS-245-1 レビューの収束（D / P1）

- **DC-245-1** レビュー役は、各指摘に、その spec の変更が入れたものか、既存の指摘かを付ける。
- **DC-245-2** 既存の指摘について、その spec で修正するものと起票の案にするものの分け方が、規則にある。分け方は plan で決める。候補に、既存の指摘を定期の全体のレビューの材料の一覧に集める案を含む。
- **DC-245-3** 同じ範囲の 2 回目以降のレビューは、前回のレビューからの差分と、前回の指摘の修正だけを対象にする。
- **DC-245-4** 同じ対象のレビューと修正の繰り返しに、上限がある。上限の値は plan で決める。案は 3 回である。
- **DC-245-5** 繰り返しが上限に達したら、spec 担当のセッションは、修正の前提を 1 文で書いて再検討し、止まって利用者に報告する。開発の進め方 第 5.3 節の中断の条件に加える。
- **DC-245-6** 同じ種類の指摘は、対象の全体で同じ種類を探してからまとめて修正する。
- **DC-245-7** 同じ種類を全体で探す担当と、探したことを記録する方法は、plan で決める。案は、spec 担当のセッションが実装役に全体の検索を指示する形である。
- **DC-245-8** 採らなかった指摘と起票の案にした指摘の一覧を、後のレビュー役に渡し、同じ指摘を返さないよう指示する。
- **DC-245-9** spec の最後のレビューは、段階をまたぐ影響とファイルをまたぐ影響の観点を必ず残す。
- **DC-245-10** spec の最後のレビューと pull request の前のレビューの観点を、段階のレビューと重ならないように決める。減らす量と根拠は plan で決める。
- **DC-245-11** pull request の前の組み込みのコードレビューの level と件数の上限を、profile ごとに決める。

### DS-245-2 変更の危険度（D / P1）

#106 の項目である。

- **DC-245-12** 変更の危険度の区分が規則にある。区分は、書いたのが人かエージェントかでなく、変えるファイルの経路で決まる区分と、spec で決めた区分のうち、高い方で決まる。
- **DC-245-13** 常に利用者がマージを承認する経路の一覧が、規則にある。一覧は plan で決める。
- **DC-245-14** 常に利用者が承認する経路に、エージェントの規則と設定そのものを含む。対象は、作業の手順、規則の文書、skill、CI の検査の script と workflow、ブランチとリリースの文書などである。理由：規則を弱める変更を、文書だけの低い変更としてエージェントがマージできないようにするため。本 spec 自身も危険度の高い変更になる。
- **DC-245-15** 常に利用者が承認する経路に、CI の workflow、認証、支払、データベースのマイグレーション、リリースの流れを含む。
- **DC-245-16** ファイルの経路による危険度は、script が判定し、pull request に表示する。spec 担当のセッションは自分で判定しない。理由：変更を書いた側の判定は甘くなりうるため。
- **DC-245-17** pull request に表示した危険度と script の判定の食い違いを、CI が検出する。
- **DC-245-18** spec 担当のセッションは、設計への影響が大きい spec を、spec の段階で危険度の高い変更として提案し、利用者が spec の確認で決める。設計への影響が大きいとは、今の構成に合わない新しい型を加える、モジュールの境界や書き方の規則を変える、などである。理由：設計への影響は、ファイルの経路から機械で判断できないため（利用者、2026-10-28）。
- **DC-245-19** 利用者は、提案がなくても、spec の確認で危険度の高い変更に指定できる。
- **DC-245-20** plan と実装の途中で、設計への影響が大きいと分かったときは、spec 担当のセッションが危険度を上げて利用者に報告する。途中で危険度を下げない。
- **DC-245-21** 危険度が高い変更は、profile に依らず、重要な観点のレビューを高性能の区分で行う。
- **DC-245-22** マージの承認に数えるものと数えないものが、規則にある。利用者が明示した許可を数え、エージェントの承認は数えない。
- **DC-245-23** 危険度ごとの利用者の承認の要否が、規則にある。利用者が 1 人であるため、承認の数でなく要否で決める。
- **DC-245-24** 利用者の承認は、承認した時点の commit に対してだけ有効とする。
- **DC-245-25** 承認の後に push があったときに、承認を求め直す条件が、規則にある。条件は plan で決める。
- **DC-245-26** 危険度が低い変更は、CI が全て通り、未解決の高・必須が 0 なら、issue 担当のセッションがマージすることが、規則にある。危険度の高い変更と機能の spec は、今のとおり利用者が許可する。理由：第 6 弾の特例で問題がなく、利用者の確認を危険度の高い変更に集められるため（利用者が決定、2026-10-28）。
- **DC-245-27** issue 担当のセッションが危険度が低い変更をマージするときの、後片付けとセッションのアーカイブの許可の手順が、規則にある。AGENTS.md の Git の表、エージェントの作業フローの役割の表、開発の進め方 第 5.7 節を合わせて変える。
- **DC-245-28** Dependabot の pull request と規模 S の変更の、危険度の決め方とマージの担当が、規則にある。決め方は plan で決める。理由：Actions の更新は CI の workflow の経路なので、決めないと常に利用者の承認になり、続けてマージするときの待ちが減らないため。
- **DC-245-29** 常に利用者が承認する経路のうち、認証・支払・権限の経路を変える変更は、AI のセキュリティのレビューを行う。時点と使うツールは plan で決め、profile の表に入れる。
- **DC-245-30** AI のセキュリティのレビューに未解決の指摘があれば、マージしない。
- **DC-245-31** エージェントがマージした変更が後で不具合を出したら、見逃しの台帳に印を付ける。
- **DC-245-32** 印の件数で、常に利用者が承認する経路の一覧と、エージェントがマージする条件を再検討する手順が、規則にある。

### DS-245-3 続けてマージするときの待ち（D / P1）

#130 の項目である。

- **DC-245-33** 続けて複数の pull request をマージするときの待ちを短くする方法を選び、設定と文書に入れる。候補は、保護の規則の「最新の develop を含む」の解除、変えたファイルによる CI の job の省略、Dependabot の更新のまとめ方、merge queue の 4 つである。merge queue は、個人のアカウントで使えるかを確認する。方法は plan で決める。
- **DC-245-34** 選んだ方法でも、`develop` に入った変更の CI が通ることを、マージの後に確認する手順がある。
- **DC-245-35** 「最新の develop を含む」を外す場合に、`develop` の CI が落ちたときに誰が気づき、他のマージを止めるかが、規則にある。担当は issue 担当のセッションの案である。
- **DC-245-36** 「最新の develop を含む」を外す場合に、開発の進め方 第 5.7 節（マージの前に develop を取り込む）と、ブランチとリリースの文書の Dependabot の手順を、選んだ方法に合わせる。

### DS-245-4 モデル・作業の形・profile の選び方（D / P1）

- **DC-245-37** 作業の種類ごとに、モデルの区分と思考の量（effort）が表にある。作業の種類は、資料を集める、機械的な作業、実装、判断、レビュー、原因の調査、設計の決定と、主のセッション（issue 担当、spec 担当）である。
- **DC-245-38** 表のレビューの行は、モデルを profile の表に任せ、effort だけを決める。
- **DC-245-39** issue 担当のセッションの待機・監視・起票は判断が少ないので、汎用の区分にする案を、plan で検討する。
- **DC-245-40** 資料を集めて判断しない作業は軽量のモデルに任せることが、規則にある。
- **DC-245-41** 軽量のモデルに任せる資料の収集は、固定の分を含めて上限を超えない量に限る。超える量は分けるか、汎用の区分に任せる。
- **DC-245-42** 最も高性能な区分のモデルを使う場面と上限が、規則にある。上限は、プランごとの使用の条件に合わせる。2026-10-28 の時点の条件は第 1.1 節の「使用量の上限」の行である。能力・料金・上限は、plan を書くときに公式の文書で確認する。
- **DC-245-43** 軽量のモデルの注の値は、固定の分（system prompt とツールの定義）を含めた値になっている。
- **DC-245-44** 作業の形（単線・並行）と各 spec の profile は、issue 担当のセッションが、プランと残りの使用量から決めて、spec 担当のセッションに渡す。各 spec 担当のセッションが自分で選ぶのではない。利用者がマシンごとの環境の文書を手動で修正しなくても決まる。
- **DC-245-45** 残りの使用量が少ないときに、profile を下げる閾値と、作業を止める閾値が、規則にある。
- **DC-245-46** 使用量の閾値に達したら、spec 担当のセッションは commit できる区切りで止まり、issue 担当のセッションに報告する。その後の扱いは issue 担当のセッションが決める。
- **DC-245-47** マシンごとの環境の文書にある使用量の閾値（区切りを探して止める値など）を、DC-245-45 と DC-245-46 の規則に移す。
- **DC-245-48** サブエージェントへの指示とその説明は、日本語で書くことが規則にある。方法の候補に、読むだけのレビュー役の定義を含む。

### DS-245-5 固定の文脈（D / P1）

#99 の項目を含む。

- **DC-245-49** spec 担当のセッションと実装役が使わない MCP のツールの定義が、毎ターンの文脈に入らない。方法は、接続を切るか遅延読み込みにするかを plan で決める。
- **DC-245-50** MCP を切るときも、呼び出し元を調べる手段（IDE の MCP か LSP）を、それが必要な作業に残す。開発の進め方 第 1.4 節の、IDE の呼び出しの階層で調べる規則と食い違わないようにする。
- **DC-245-51** 固定の文脈を小さくする方法の候補に、読むだけのレビュー役の定義を含む。定義は、ツールを読むだけに限り、モデルを指定し、プロジェクトの指示の文書などを外す設定である。spec 249 が確認した材料を使う。
- **DC-245-52** 固定の文脈の token を、変える前と後で同じ方法で測り、spec に記録する。
- **DC-245-53** LSP によるコードの参照を試し、使うか使わないかと理由を記録する。
- **DC-245-54** LSP を使うかの判断は、同じ呼び出し元の調査で、今の IDE の MCP と token と正しさを比べて決める。
- **DC-245-55** LSP を試した結果を、MCP を切る決定より先に出す。

### DS-245-6 採否と見逃しの記録（D / P1）

- **DC-245-56** レビューごとの token、時間、指摘の数（重要度ごと）、採用した数を、決まった形で 1 か所に記録する。
- **DC-245-57** レビューの記録に、修正とレビューの繰り返しの回数を加える。
- **DC-245-58** レビューの記録に、指摘が出た時点を加える。時点は、段階、spec の最後、pull request の前である。
- **DC-245-59** 使うツールの使用量の内訳（サブエージェントごとの割合）を、記録と振り返りと定期のレビューの材料にする方法を、plan の候補として検討する。
- **DC-245-60** 記録を集計して profile を再検討する時点が、規則にある。時点は弾ごとなどとし、plan で決める。
- **DC-245-61** 見逃しの台帳が 1 か所にある。
- **DC-245-62** 見逃しの台帳に加える時点が、規則にある。
- **DC-245-63** モデル・レビューの指示・profile を替えるときに、見逃しの台帳で採点し直し、対象ごとに再検討する手順がある。
- **DC-245-64** 再検討の対象は、モデルの区分、レビューの観点、profile と、作業の流れの部品である。部品は、段階ごとのレビュー、引き継ぎの文書、1 タスクごとの実装役、調査役である。
- **DC-245-65** 見逃しの台帳に、今までの例を 5 件以上を目安に入れる。例に、spec 192 の、手元は通り CI だけ失敗した件を含む。
- **DC-245-66** 本 spec のマージの後の最初の弾で、整理の前の基準と同じ方法で、token、レビューの指摘の数、issue 担当の待機の token を測り、基準と比べて記録する。

### DS-245-7 並行のセッションの運用（D / P1）

#105 の項目である。

- **DC-245-67** spec 担当のセッションは、組み込みのコードレビューの結果を出した後もターンを終えず、pull request の作成まで進むことが、規則にある。
- **DC-245-68** 組み込みのコードレビューの後に止まらない方法は、plan で決める。候補に、pull request を先に draft で作り、その後に組み込みのコードレビューを行う順を含む。
- **DC-245-69** セッションの間のメッセージは、名前でなくセッションの ID で送ることが、規則にある。
- **DC-245-70** 待機中のセッションに遠隔操作の接続を入れる手順が、規則にある。先にターンを起こす。置き場所は、共有の文書にするか、マシンごとの環境の文書にするかを plan で決める。
- **DC-245-71** issue 担当の専用のセッションの役割、起動、待機の手順が、文書にある。
- **DC-245-72** issue 担当のセッションの待機と監視の token を抑える方法が、規則にある。方法は plan で決める。
- **DC-245-73** 資源の配分は issue 担当のセッションが決める。配分は、実装の開始と待機、並行する spec の中断と再開を含む。資源は、使用量、マシンの資源、並行の数である。
- **DC-245-74** 資源の配分の規則に、並行の数の上限と、上限を上げ下げする条件がある。
- **DC-245-75** 利用者が特例を求めたときは、利用者の決定が最終である。issue 担当のセッションは、その特例のための配分（他の spec の中断など）を決めて実行し、利用者に報告する。誰も決めない状態を作らない。
- **DC-245-76** issue 担当のセッションは、spec 担当のセッションを起動するときに、実装の開始の条件を渡す。理由：開発の資源を issue 担当のセッションが一括で調整するため（利用者、2026-10-28）。
- **DC-245-77** 利用者が実装の前の確認対象を承認した後、開始の条件を満たすときは、spec 担当のセッションは問い合わせずに始めて、開始を知らせる。確認対象は、規模 L は plan と tasks、規模 M は spec、規模 S は規模の区分である。
- **DC-245-78** 開始の条件を満たさないとき、または条件が渡されていないときは、spec 担当のセッションは issue 担当のセッションに問い合わせて、許可を待つ。理由：問い合わせのたびに issue 担当のセッションの長い文脈を処理し直すため。
- **DC-245-79** 問い合わせに返事がないときの扱いは、plan で決める。
- **DC-245-80** 単線の作業の形で issue 担当のセッションがないときの扱いは、plan で決める。案は、単線でも issue 担当と spec 担当の 2 つのセッションを保つ形と、1 つのセッションが両方を兼ねる形である。単線では資源の調整がほぼ要らない（利用者、2026-10-28）。

### DS-245-8 振り返り（D / P1）

#21 の項目である。

- **DC-245-81** エージェントが振り返りの skill を呼べる。
- **DC-245-82** 振り返りの時点は、アーカイブの許可に結ばず、spec の後片付け（マージの後）で必ず行う。結果を決まった置き場所に 1 件 1 ファイルで残す。
- **DC-245-83** issue 担当のセッションも、区切り（弾や段の終わり）で振り返りを行う。
- **DC-245-84** 外から取り込んだ skill `retro` の原文は変えず、エージェント用の入口を別に書く。入口は、呼び方、出力の形、置き場所、読む量の上限を含む。
- **DC-245-85** エージェント用の入口は、原文の「セッションの記録を読む」手順を使わず、spec 担当のセッションの文脈から書く。
- **DC-245-86** 同じ問題を数え、数が閾値を超えたものを整理の issue の案にする手順と担当がある。閾値は plan で決める。
- **DC-245-87** 定期に全体をレビューして提案だけを出す時点と手順が、規則にある。仕組みは、定期の実行にするか、区切りで手動で行うかを plan で決める。

## 6. 非機能要件

- **DN-245-1** 消費者・運営者に見える振る舞い、本番のコード、API の契約、データベースの構造を変えない。
- **DN-245-2** レビューを減らす変更は、根拠を plan に書く。根拠は、整理の前の基準の測定、採否の記録、見逃しの台帳である。高の指摘が出ている段階のレビューの時点は減らさない。2 回目以降のレビューを差分に絞ること（DC-245-3）は、見る範囲を減らすが、時点は減らさない。段階のレビューを差分に絞ることと、spec の最後のレビューを減らすことを同時に入れるときは、根拠に見逃しの台帳を使う。理由：品質を token より優先するため（利用者、2026-10-27）。
- **DN-245-3** 規則の本文は、使う AI のサービスに依らない言葉で書く。サービス固有の名前は、AGENTS.md のモデルの区分の表と、ツールの注にだけ書く。サービス固有の名前は、モデル、プラン、ツール、設定の項目である。理由：サービスを替えるときに修正する所を限るため。
- **DN-245-4** 毎回読む文書（AGENTS.md、開発の進め方、エージェントの作業フロー）は、それぞれ第 1.1 節の大きさを超えない。skill `review` の SKILL.md と prompts.md も、第 1.1 節の大きさを超えない。超えるときは、必要なときに読む文書か skill に移す。理由：毎ターンの文脈と実装役の読む量を増やさないため。
- **DN-245-5** GitHub の設定と、リポジトリの外の設定を変えるときは、変える範囲を示して利用者の許可を得てから行う。対象は、保護の規則と、利用者の全体の設定などである。
- **DN-245-6** 本 spec で変えた規則は、本 spec のマージの前に、並行する他の spec に適用しない。ただし、資源を issue 担当のセッションが配分する規則（DC-245-73 から DC-245-80）は、利用者が 2026-10-28 に決めた運用として、本 spec のマージの前から第 1 段で既に行っている。
- **DN-245-7** 新しい・変えた検査の script と hook は、違反の例で違反を検出することを確認する。
