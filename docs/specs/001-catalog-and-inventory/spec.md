|------|------|
| ステータス | ドラフト（Open questions 未解決のため plan に進めない） |

## 1. 背景と目的

EC のコアフロー（閲覧 → カート → 注文 → 決済 → 出荷 → 配送状況）の出発点として、**運営者が商品を登録・公開し、消費者がそれを閲覧できる状態**を作る。

本 spec のゴール：

- 運営者が、商品とそのバリアント（色・サイズ違いなど）を、価格・在庫を含めて個別に管理できる。
- 消費税は**税区分と、期間付きの税率**で管理し、税率の改定があってもコード変更なしで対応できる。
- 消費者が、公開中の商品を一覧・検索し、詳細と税込価格、在庫の有無を確認できる。

本 spec の在庫は「運営者が数量を管理し、消費者が在庫の有無を見られる」ところまでとする。注文による引当・減算は、カート・注文の spec で扱う。

## 2. 用語

本 spec 以降、次の用語を統一して使う。

| 用語 | 意味 |
|------|------|
| 商品 | 消費者から見た 1 つの商品ページの単位。例：「オーガニックコットン T シャツ」 |
| 商品品番 | 商品を一意に識別する、運営者が付ける番号 |
| バリアント | 商品の中で、実際に販売・在庫管理する単位。例：「白 / M」。価格と在庫はバリアントごとに持つ |
| バリアント品番 | バリアントを一意に識別する、運営者が付ける番号 |
| バリアント軸 | バリアントを区別する観点。例：「色」「サイズ」 |
| 税区分 | 税率の種類。例：「標準」「軽減」 |
| 税率 | 税区分ごとの率。適用開始日時を持ち、次の税率が始まるまで有効 |
| 税抜価格 | 運営者が登録する価格（Q1 で確定） |
| 税込価格 | 税抜価格に、その時点で有効な税率を適用した価格 |
| 公開 | 消費者に表示されている状態 |
| 在庫数 | バリアントごとの、販売可能な数量 |

## 4. User stories と受け入れ条件

AC の末尾の `[Qn]` は、Open question の回答によって変わりうることを示す。現時点では、各 Q の推奨案を前提に書いている。

### US-1 税区分と税率を管理する（B / P1）

運営者として、税区分と、その税率を適用開始日時付きで登録したい。税率の改定や期間限定の税率変更があっても、システムの改修なしに対応するため。

必要な権限：`tax:read`、`tax:write`

- **AC-1** 税区分を、名称を指定して登録できる。名称が既存の税区分と重複する場合は登録できない。
- **AC-2** 税区分に、税率（%）と適用開始日時を指定して、税率を登録できる。
- **AC-3** 税率は、次の税率の適用開始日時まで有効である。
  - Given：税区分「標準」に、10%（2019-10-01 00:00 開始）が登録されている
  - When：同じ税区分に、8%（2027-04-01 00:00 開始）と 10%（2028-04-01 00:00 開始）を登録する
  - Then：2027-03-31 23:59 時点の税込価格は 10%、2027-04-01 00:00 から 2028-03-31 23:59 までは 8%、2028-04-01 00:00 以降は 10% で計算される
- **AC-4** 同じ税区分に、同じ適用開始日時の税率は登録できない。
- **AC-5** 適用開始日時がすでに過ぎた税率は、変更も削除もできない。まだ始まっていない税率は、変更・削除できる。
- **AC-6** 税率を 1 つも持たない税区分は、商品に割り当てられない。
- **AC-7** 税率は 0% 以上 100% 未満とする。0% の税区分（例：非課税）を作れる。

### US-2 カテゴリを管理する（B / P1）

運営者として、商品を分類するカテゴリを階層構造で管理したい。消費者が目的の商品にたどり着きやすくするため。

必要な権限：`category:read`、`category:write`

- **AC-8** カテゴリを、名称と親カテゴリ（任意）を指定して登録できる。親を指定しない場合は最上位のカテゴリになる。[Q5]
- **AC-9** カテゴリの階層は最大 3 階層とする。4 階層目になる登録は拒否される。[Q5]
- **AC-10** 同じ親カテゴリの下で、名称が重複するカテゴリは登録できない。
- **AC-11** カテゴリの名称と、兄弟カテゴリ間の並び順を変更できる。
- **AC-12** 子カテゴリを持つカテゴリ、または商品が所属しているカテゴリは削除できない。

### US-3 商品を登録・編集する（B / P1）

運営者として、商品の基本情報を登録・編集したい。

必要な権限：`product:read`、`product:write`

- **AC-13** 商品を、商品品番、商品名、説明、税区分、所属カテゴリ（0 個以上）、バリアント軸（0〜3 個）を指定して登録できる。[Q4]
- **AC-14** 商品品番は全商品の中で一意である。既存の商品品番と同じ値では登録できない。
- **AC-15** 商品品番は、半角英数字とハイフンで 1〜32 文字とする。登録後は変更できない。[Q13]
- **AC-16** 税区分は必須である。
- **AC-17** 登録した直後の商品は非公開である。
- **AC-18** 商品名、説明、税区分、所属カテゴリは、登録後に変更できる。
- **AC-19** 税区分を変更すると、その商品の全バリアントの税込価格は、変更後の税区分の税率で計算される。

### US-4 バリアントを登録・編集する（B / P1）

運営者として、1 つの商品の中で、色やサイズの違いをバリアントとして登録し、それぞれ独立した価格と在庫を持たせたい。

必要な権限：`product:read`、`product:write`

- **AC-20** 商品に、バリアント品番、バリアント軸の値（例：色＝白、サイズ＝M）、税抜価格を指定してバリアントを登録できる。[Q1][Q4]
- **AC-21** バリアント品番は全バリアントの中で一意である。半角英数字とハイフンで 1〜32 文字とし、登録後は変更できない。[Q13]
- **AC-22** 商品にバリアント軸が定義されている場合、バリアントはすべての軸の値を持たなければならない。
- **AC-23** 同じ商品の中で、バリアント軸の値の組み合わせが同じバリアントは登録できない。
- **AC-24** バリアント軸を持たない商品は、バリアントを 1 つだけ持てる。
- **AC-25** 税抜価格は 1 円以上の整数である。
- **AC-26** バリアントの価格を変更すると、C 側の表示に反映される（反映までの時間は非機能要件を参照）。
- **AC-27** バリアントの表示順を変更できる。
- **AC-28** バリアントを「販売停止」にできる。販売停止のバリアントは C 側で選択できない。販売停止は解除できる。（P2）

### US-5 商品を公開・非公開にする（B / P1）

運営者として、準備のできた商品だけを消費者に見せたい。

必要な権限：`product:write`

- **AC-29** 非公開の商品を公開にすると、C 側の一覧・検索・詳細に表示される。
- **AC-30** 公開中の商品を非公開にすると、C 側の一覧・検索・詳細に表示されない。
- **AC-31** バリアントを 1 つも持たない商品は公開できない。
- **AC-32** 商品の状態は「非公開」「公開」「販売終了」の 3 つとする。販売終了にした商品は C 側に表示されず、公開に戻すこともできない。[Q12]
- **AC-33** 一度も公開していない商品は削除できる。一度でも公開した商品は削除できず、販売終了にする。[Q12]

### US-6 公開日時を予約する（B / P2）

運営者として、商品の公開開始日時と公開終了日時を指定し、その時刻に自動で公開・非公開を切り替えたい。深夜の発売開始などに対応するため。

必要な権限：`product:write`

- **AC-34** 商品に、公開開始日時と公開終了日時（いずれも任意）を設定できる。[Q6]
- **AC-35** 公開状態の商品は、公開開始日時より前と、公開終了日時以降は C 側に表示されない。運営者の操作なしに、その時刻から表示が切り替わる。
- **AC-36** 公開終了日時は、公開開始日時より後でなければならない。

### US-7 商品画像を登録する（B / P2）

運営者として、商品に画像を登録したい。

必要な権限：`product:write`

- **AC-37** 商品に画像を複数登録でき、並び順を変更できる。先頭の画像が代表画像になる。[Q11]
- **AC-38** バリアントに、画像を 1 枚指定できる（任意）。指定がない場合は商品の代表画像を使う。[Q11]
- **AC-39** 画像は JPEG、PNG、WebP のみとし、1 ファイル 10MB を超えるものは登録できない。[Q11]
- **AC-40** 1 つの商品に登録できる画像は最大 20 枚とする。[Q11]

### US-8 在庫を調整する（B / P1）

運営者として、バリアントごとの在庫数を、入荷や棚卸の結果に合わせて調整したい。

必要な権限：`inventory:read`、`inventory:write`

- **AC-41** 新しく登録したバリアントの在庫数は 0 である。
- **AC-42** 在庫数は、増減量（例：+10、-3）と理由を指定して調整する。在庫数を直接上書きする操作は提供しない。[Q8]
- **AC-43** 調整後の在庫数が負になる調整は拒否される。
- **AC-44** 同じバリアントに対する複数の調整が同時に行われても、すべての調整が反映される。
  - Given：在庫数 10 のバリアント
  - When：+5 と +3 の調整が同時に行われる
  - Then：在庫数は 18 になる
- **AC-45** バリアントごとに、在庫調整の履歴（日時、増減量、理由、調整後の在庫数）を新しい順に参照できる。
- **AC-46** 調整の理由は、「入荷」「棚卸差異」「破損・紛失」「その他」から選ぶ。「その他」の場合はメモが必須。[Q8]

### US-9 運営者として商品を一覧・絞り込みする（B / P1）

運営者として、非公開や販売終了も含めたすべての商品を一覧し、目的の商品を素早く見つけたい。

必要な権限：`product:read`

- **AC-47** 状態（非公開・公開・販売終了）に関係なく、すべての商品を一覧できる。
- **AC-48** 商品品番またはバリアント品番の前方一致、商品名の部分一致、状態、カテゴリで絞り込める。
- **AC-49** 一覧には、商品品番、商品名、状態、バリアント数、在庫数の合計を表示する。
- **AC-50** 一覧はページ単位で取得できる。

### US-10 商品を一覧・絞り込みする（C / P1）

消費者として、カテゴリや価格帯で商品を絞り込み、並べ替えて見たい。

- **AC-51** 一覧には、C 側に表示される条件を満たす商品だけが含まれる（公開状態で、公開期間内）。
- **AC-52** カテゴリで絞り込める。カテゴリを指定すると、その子孫カテゴリに属する商品も含まれる。[Q5]
- **AC-53** 税込価格の範囲で絞り込める。[Q14]
- **AC-54** 新着順（公開した日時の新しい順）、価格の安い順、価格の高い順で並べ替えられる。既定は新着順。[Q14]
- **AC-55** 各商品について、商品名、代表画像、税込価格を表示する。バリアント間で価格が異なる場合は、販売中のバリアントの最安値を「〜」付きで表示する（例：「1,980 円〜」）。
- **AC-56** すべてのバリアントが在庫切れの商品も一覧に表示し、「在庫なし」と表示する。[Q10]
- **AC-57** 一覧はページ単位で取得できる。

### US-11 商品をキーワードで検索する（C / P1）

消費者として、キーワードで商品を探したい。

- **AC-58** キーワードを入力すると、商品名または説明にそのキーワードを含む商品が表示される。
- **AC-59** 検索対象は、US-10 と同じく C 側に表示される条件を満たす商品だけである。
- **AC-60** 検索結果の精度（表記ゆれ、類義語、関連度順）は問わない。（constitution 4.4）
- **AC-61** 検索結果はページ単位で取得できる。

### US-12 商品の詳細を見る（C / P1）

消費者として、商品の詳細を見て、バリアントを選び、価格と在庫の有無を確認したい。

- **AC-62** 商品名、説明、画像、バリアント軸と選択肢を表示する。
- **AC-63** バリアントを選ぶと、そのバリアントの税込価格と在庫状況を表示する。
- **AC-64** 在庫状況は「在庫あり」「在庫なし」の 2 つで表示し、具体的な在庫数は表示しない。[Q9]
- **AC-65** C 側に表示される条件を満たさない商品の詳細を求めた場合は、存在しない商品と同じ結果になる（非公開の商品が存在することを外部から判別できない）。

## 5. 業務ルール

複数の User story にまたがるルール。

- **BR-1 税込価格の計算**：税込価格 ＝ 税抜価格 ×（1 ＋ 表示時点で有効な税率）。1 円未満は切り捨てる。[Q1][Q2]
  - 例：税抜 1,800 円、税率 10% → 税込 1,980 円
  - 例：税抜 1,234 円、税率 8% → 1,332.72 円 → 税込 1,332 円
- **BR-2 C 側に表示される条件**：商品が「公開」状態であり、公開期間内（US-6 を実装する場合）であること。
- **BR-3 日時**：運営者が入力する日時と、画面に表示する日時は日本時間とする。
- **BR-4 価格の表示**：C 側の価格は、すべて税込で表示する。

## 6. 非機能要件

- **NFR-1** 商品、価格、公開状態、在庫の変更は、遅くとも 1 分以内に C 側の表示へ反映される。即時でなくてよい。[Q15]
- **NFR-2** 在庫調整は、同時に実行されても調整が失われない（AC-44）。

## 7. Non-goals

| 項目 | 扱う予定の場所 |

| 注文時の消費税の計算（インボイス制度に沿った端数処理） | 注文の spec |
| 予約価格変更（指定日時から価格を変える） | 将来の spec（Q7） |
| セール価格、クーポン、ポイント | 将来の spec |

| タグ | 将来の spec |
| CSV などによる一括登録 | 将来の spec |
| 複数倉庫の在庫管理 | 将来の spec |

## 8. Open questions

すべて解決するまで plan に進まない。各項目に推奨案を付けている。推奨案でよければ「推奨どおり」で回答してよい。

| # | 質問 | 推奨案 | 理由 |
|---|------|--------|------|
| Q1 | 運営者が登録する価格は、税抜か税込か | **税抜** | 税率が変わったとき、税込価格が自動で正しく変わる。税込で登録すると、税率改定のたびに全商品の価格を手で見直す必要がある |
| Q2 | 税込価格の 1 円未満の端数処理 | **切り捨て**（システム全体で 1 つ） | 消費者に不利にならない。端数処理を税区分ごとに変える必要は当面ない |
| Q3 | 「活動税率」は、AC-3 のような**期間付きの税率**（例：1 年間だけの減税）で表現できるか。それとも、セールなどの販促に紐づく別の仕組みを想定しているか | 期間付きの税率で表現する | 消費税率は法律で決まるもので、販促ごとに変わるものではない。販促による値引きはセール価格（Non-goal）として別に扱うほうが筋がよい |
| Q4 | バリアント軸の持ち方 | 商品ごとに**最大 3 つ**の軸（例：色、サイズ）を定義し、バリアントは軸の値の組み合わせとする | C 側で「色を選んで、次にサイズを選ぶ」という画面が作れる。主要な EC プラットフォームでも同様の作り |
| Q5 | カテゴリは階層か、タグか | **最大 3 階層のツリー**。商品は複数カテゴリに所属できる | タグから後で階層に移行すると、全商品の分類をやり直すことになる。階層の深さを制限すれば、実装の複雑さは抑えられる |
| Q6 | 予約公開（US-6）を MVP に入れるか | **入れる**（P2 のまま、余力があれば） | 公開開始・終了日時を持たせて、表示時に現在時刻と比べるだけで実現でき、定期ジョブが不要。複雑さが小さい |
| Q7 | 予約価格変更を MVP に入れるか | **入れない**（Non-goal） | カートに入れた時点と注文時点で価格が変わる問題など、注文 spec と絡む。注文の spec を作った後に扱うほうが安全 |
| Q8 | 在庫の調整方法 | **増減量 + 理由**で調整し、直接の上書きは提供しない | 後で注文による減算が入ったとき、上書きは注文による減算を打ち消してしまい、在庫が狂う。増減なら並行して処理しても失われない |
| Q9 | C 側の在庫表示 | **「在庫あり」「在庫なし」の 2 つ** | 数量を見せると、競合に販売数を推測される。「残りわずか」は後で追加できる |
| Q10 | 在庫切れ商品・バリアントの C 側の扱い | **表示して「在庫なし」と示す** | 商品が突然消えると、消費者が混乱する。再入荷を待つ動機にもなる |
| Q11 | 画像の単位と制限 | 商品に複数（最大 20 枚）、バリアントに任意で 1 枚。JPEG / PNG / WebP、1 枚 10MB まで | 一般的な EC の水準。数値は後で変えられる |
| Q12 | 商品の削除と状態 | 状態は「非公開・公開・販売終了」。一度も公開していない商品だけ削除できる | 公開済みの商品は、注文履歴などから参照されるため、消すと過去の記録が壊れる |
| Q13 | 品番の形式 | 運営者が入力。半角英数字とハイフン、1〜32 文字、一意、登録後は変更不可 | 品番は外部（倉庫、問い合わせ）でも使われる識別子なので、変わると困る |
| Q14 | C 側一覧の絞り込みと並び順 | 絞り込み：カテゴリ、価格帯。並び順：新着順（既定）、価格の安い順、高い順 | MVP の最小限。人気順は販売データが必要なので、注文の後 |
| Q15 | 変更が C 側に反映されるまでの許容時間 | **1 分以内** | 即時を求めると、複数インスタンスでキャッシュが使いにくくなる（constitution 第 5 節）。1 分なら運用上も問題になりにくい |
