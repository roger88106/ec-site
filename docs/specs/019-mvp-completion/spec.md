# Spec 019：受け入れ確認と MVP の完成

ステータス：確定

## 1. 背景と目的

spec 018 で、文書とツールを整え、レビュー skill を作った。MVP の最後に、**レビュー skill で全体の受け入れ確認を行い、spec をアーカイブし、MVP の完成を main に記録する**。

- これまでのレビューは、spec ごとの差分だけを対象にしてきた。MVP 全体（バックエンド、フロント、E2E、文書、script と CI）を、同じ基準で確認したことがない。
- README と開発環境の文書だけで、新しい環境を起動できるか確認していない。文書を主に読むのはエージェントだが、事前知識のないエージェントが作業できるかも確認していない。
- 機能紹介のページは spec 010 の時点の画面と数値のまま。
- `main` には最初の commit しかなく、MVP の完成がどこにも記録されていない。
- spec 018 の振り返りで、作業のツールと手順の不備が見つかった。文書のパスの置き換えが適用済みのマイグレーションを変えた、commit の前の検査が未 commit のファイルで失敗した、並行したサブエージェントが同じ名前の一時ファイルを上書きした、など。

MVP の完成条件は、本 spec の完了条件とする。機能は spec 010 で揃っているので、機能の一覧では定義しない。

本 spec は**整理の spec**（[文書の記号と番号](../../rules/notation.md)）であり、消費者・運営者に見える振る舞いを変えない（例外は DN-25）。DS・DC・DN の番号は、spec 018 からの連番とする。

## 4. 目的と完了条件

### DS-54 レビュー skill で全体の受け入れ確認を行い、MVP の完成条件を満たす（D / P1）

- **DC-208** レビュー skill で、バックエンド、フロント、E2E、文書、script と CI の全てをレビューする。
- **DC-209** 指摘のうち重要度「高」（セキュリティ、データの破損、金額の誤りなど）は本 spec で修正する。それ以外は TODO 一覧に載せ、本 spec では修正しない（利用者が指定したものを除く）。
- **DC-210** 新しいディレクトリにリポジトリを clone し、README と開発環境の起動の文書だけで、環境を起動し、全てのテストと E2E を実行して成功させられる。
- **DC-211** 事前知識なしのエージェント（安価なモデル）に AGENTS.md だけを渡し、clone、起動、全てのテスト、AC を伴う小さな変更（使い捨ての worktree で行い、マージしない）を、利用者に質問せずに実行させる。止まった箇所、推測した箇所、不要に読んだ文書を記録し、案内の追加・自動の検査・記述の削除のいずれかで対応する。
- **DC-212** 機能紹介のページが、現在の画面と数値（AC、テスト、spec の数）に一致している。
- **DC-213** AC の除外一覧の各項目の理由が、現在も成り立つ。
- **DC-214** spec 011〜019 の tasks が全て完了し、README と MVP の完成までの一覧の状態が「完了」で、CI 全体が通る。

### DS-55 spec をアーカイブし、MVP の完成を main と tag に記録する（D / P1）

- **DC-215** spec 001〜019 を、spec 018 で決めたアーカイブの置き場所に移す。移動後も、文書のリンクと CI の検査が通る。文書の検査（使わない語など）の対象から外すのはアーカイブだけとし、進行中の spec は検査する。
- **DC-216** `develop` を pull request で `main` にマージする。merge commit を使い、commit を書き換えない。理由：tasks・文書・メモに書いた commit ID とタスク番号を追跡できるようにするため。
- **DC-217** `main` の MVP 完成の commit に tag があり、GitHub の Release に短い説明がある。
- **DC-218** 機能紹介のページの公開、CI、AGENTS.md の Git の規則が `main` を基準にする。`develop` という名前を削除し、再利用できるようにし、Git の履歴は失わない。
- **DC-219** `main` にマージした後、tag を付ける前に、CodeQL と Dependabot alerts の初回の結果を確認し、修正するか、理由を付けて閉じる。理由：どちらも既定のブランチ（`main`）だけを見るので、マージの前は結果が出ないため（spec 018 の DC-178、DC-180 から移した）。

### DS-56 spec 018 の振り返りで見つかった、作業のツールと手順の不備を修正する（D / P1）

- **DC-220** 文書の中のリンクでないパスを置き換える script があり、既定で、適用済みのマイグレーション、テストのデータ、アーカイブした spec の本文を置き換えの対象から外す。DC-215 の移動の前に作る。理由：spec 018 で、その場で書いた置き換えの script が、適用済みのマイグレーションとテストのデータを変えたため。
- **DC-221** commit の前の hook が、作業ツリーではなく、ステージした内容だけを検査する。理由：未 commit のファイルによって、検査が誤って失敗する、または誤って通るため。
- **DC-222** 関連する spec の検査が、ステージした差分を次の commit として照合する。理由：今は commit の履歴だけを照合するので、関連する spec の漏れが次の無関係の commit で失敗するため（spec 018 で 2 回起きた）。
- **DC-223** 語ごとの置き換えの手順に、置き換えた語の後に元の活用の語尾が残った崩れ（「確認直す」など）を探す手順がある。
- **DC-224** サブエージェントへの指示のひな形（観点ごとのレビュー、文書のレビュー、文書の本文を書かせる指示）が、理由と根拠に出典（ファイルと行）を求め、出典のない理由を書かせない。理由：spec 018 で、サブエージェントが出典にない理由を文書に書いたため。
- **DC-225** plan の照合の手順を、tasks の完了の条件にも当てる。理由：spec 018 で、tasks の完了の条件が spec の DN より厳しく書かれ、照合で見つからなかったため。
- **DC-226** エージェントの作業フローに、サブエージェントの結果の安定度の実績（spec 018 の段階 5）と、そこから決めた運用の規則（語ごとの規則の全体への適用、文脈の候補の集め方と採否の判断）がある。
- **DC-227** エージェントの作業フローとレビューの指示のひな形に、並行して動かすサブエージェントの一時ファイルには担当の範囲の名前を付ける、と書いてある。理由：spec 018 で、同じ名前の一時ファイルの上書きが 2 回起きたため。

## 6. 非機能要件

- **DN-25** API の応答、画面、データベースの構造とデータを変えない。例外：DC-209 の重要度「高」の修正。修正する場合は、振る舞いのテストを先に書き（TDD）、AC 一覧に反映する。修正が機能の追加に相当する規模なら、本 spec では行わず、TODO 一覧に載せて利用者と扱いを決める。
- **DN-26** CI 全体が 10 分以内に終わる状態を保つ（spec 011 の DC-85）。
