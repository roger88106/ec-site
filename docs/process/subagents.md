# エージェントの作業フロー

エージェント（Claude Code など）がサブエージェントを使うときの規則。[開発の進め方](workflow.md)と [AGENTS.md](../../AGENTS.md) に従い、ここではサブエージェントへの任せ方だけを書く。

## 1. 調べた仕組み（2026-10-20 時点）

| 仕組み | 版 | サブエージェントの使い方 |
|--------|----|--------------------------|
| cc-sdd | v3 | `kiro-impl` が 1 タスクごとに新しい実装役を立て、TDD（レッド → グリーン）で実装させる。実装役にはタスクの要点だけを渡す。別の独立したレビュー役が、差分、TODO の残り、テストの全体、タスクの境界を確認する。実装役が止まったとき、またはレビューで 2 回差し戻されたときは、調査役が原因と直し方を返す（最大 2 回）。タスクをまたぐ気づきは tasks の「Implementation Notes」に書き、後のタスクの実装役に渡す。実装は 1 つずつ順に行い、書き手を並べるときは別の作業ツリーを使う。モデルの選び方の記述はない |
| superpowers（subagent-driven-development の skill） | main（2026-10） | 1 タスクごとに新しい実装役を立てる。実装役に渡すのは、タスクの全文、プロジェクトの 1 行の説明、前のタスクで決まったインターフェース、曖昧な点の決定、報告のファイルのパスだけ。計画の全体や会話の履歴は渡さない。実装役は詳しい報告をファイルに書き、状態・commit・テストの 1 行の要約・懸念だけを返す。1 人のレビュー役が、仕様との一致とコードの品質の 2 つの判定を出す。重大な指摘は直させ、軽い指摘は記録だけにする。直しが 5 回で収まらなければ、制御役（メインのセッション）が裁定する。進み具合は台帳のファイルに書く ※1。実装役を並べて動かさない。モデルは常に明示し、機械的な作業は安価なモデル、複数ファイルの統合は標準、設計と最後のレビューは最も高性能なモデル、レビュー役は中位以上にする |
| Spec Kit | 最新（main） | `/speckit.implement` はサブエージェントを使わない。tasks を段階（Setup、Tests、Core、Integration、Polish）の順に実行し、段階ごとに確認する。`[P]` の付いたタスクは並べて実行できる（同じファイルを触るものは順に）。テストのタスクを実装より先に行う。独立したレビューの段階はない |
| OpenSpec | 最新（main） | `/opsx:apply` が tasks を順に実行し、`/opsx:verify`（任意）が実装と仕様の一致を確認する。サブエージェント、独立したレビュー、モデルの選び方の記述はない |

※1：会話の記憶は、文脈の圧縮で失われるため。

- Claude Code のサブエージェントは新しい文脈で始まり、親から渡るのは指示の文字列だけ（公式の文書）。必要なファイルのパス、決定、差分は、指示に明示して渡す。

## 2. 取り入れるもの・取り入れないもの

| 項目 | 判断 | 理由 |
|------|------|------|
| フレームワーク（Spec Kit、OpenSpec、cc-sdd）を導入する | 取り入れない。必要な形だけを借りる（2026-10-16 決定） | 安定の元がどれにも備わっておらず、作り直しになるため ※1 |
| 文書（spec・plan・tasks、設計の文書、手順の文書）の本文を、日本語の要点から日本語だけの文脈のサブエージェントに書かせる | 取り入れる。数行の修正はメインのセッションが直し、言い換えの一覧の検査で確認する | 試した 4 回とも言い回しの直しが要らなかったため。メインのセッションの文脈は利用者との会話の言語を含むので、そのまま書くと日本語でない語が混ざる。内容の質は要点の質で決まるので、メインのセッションが内容を確認する |
| 既存の文書の言い回しのレビューに、目指す書き方の見本と、言い回しと論理の規則（skill `docs` の参照）を渡す | 取り入れる。和語の言い換えと、論理・比喩などの 2 つの観点を両方見るように指示する | 見本がないと、プロジェクトの用語を一般の語に替える案が混ざるため。規則がないと擬人化や口頭の語を見落とし、観点を 1 つしか書かないと、もう一方を見落とすため |
| 文書の検査に textlint を使う | 取り入れない | 技術文書のプリセットは和語の言い換えを見つけられず、用語の辞書は言い換えの一覧の検査と重なるため |
| レビューを、実装の過程を見ていないサブエージェントに任せる | 取り入れる | 作業したエージェント自身のレビューは、同じ見落としを繰り返すため。レビュー skill（別の作業で作る）で行う |
| 1 タスクごとにレビュー役を立てる | 取り入れない。段階の最後と spec の最後にまとめてレビューする | 1 タスクごとに 2〜3 のサブエージェントを立てると、token が数倍になるため。タスクが細かく、`[テスト]` のタスクでレッドを確かめているので、段階ごとで足りる |
| 1 タスクごとに新しい実装役を立てる | 条件付きで取り入れる。互いに独立し、手順が決まっているタスク（同じ形の修正が多いもの、検査の script の追加など）をまとめて任せる。設計の判断が要るタスクはメインのセッションが行う | 文脈が長くなるほど 1 回の呼び出しが高くなるため。独立した機械的な作業を外に出すと、メインのセッションの文脈が膨らまない |
| 実装役に渡すもの | 取り入れる。渡すのは、タスクの全文、関係する plan の節、決まったインターフェース、曖昧な点の決定、報告の書き先。会話の履歴と計画の全体は渡さない | 公式の文書のとおり、渡るのは指示の文字列だけで、余分な文脈は token と誤りを増やすため |
| 結果の受け取り方 | 取り入れる。詳しい報告はファイル（`/.local/` の下）に書かせ、返すのは状態・commit・テストの要約・懸念だけにする | メインのセッションの文脈を小さく保つため |
| 書き手を並べない | 取り入れる。同じ作業ツリーで、ファイルを書くサブエージェントを同時に動かさない。並べるのは読むだけの作業か、別の worktree | 変更が衝突するため |
| 2 回直して通らなければ、原因の調査を分ける | 取り入れる | 同じ直し方を繰り返さないため（cc-sdd の調査役） |
| 気づきを後のタスクに渡す | 取り入れる。tasks のタスクの下に書く（今の書き方のまま） | 既に tasks の補足に書いているため |
| モデルを常に明示する | 取り入れる | 省くとメインのセッションの高いモデルを引き継ぐため |
| 段階ごとの確認、テストを先に | 既にある | 開発の進め方と tasks の形に入っている |

※1：段階ごとの tasks、前提と完了条件、テストのレッド、文書が先、レビュー、AC とテスト名の検査のどれもが、フレームワークにはない。OpenSpec は要件に英語の SHALL・MUST を求め、日本語の文書と合わない。

## 3. 任せる作業とモデル

| 作業 | 例 | モデル | 条件 |
|------|----|--------|------|
| 機械的な作業 | 一覧の作成、grep の結果の照合、同じ形の置き換え | Haiku | 指示と読む量の合計が 10 万 token を超えない作業に限る ※1 |
| 判断の要る作業 | 規則の当てはめ、一貫性の確認、レビュー、文書の本文（日本語の要点から書く） | Sonnet | 範囲を小さく分ける（1 つのサブエージェントのツールの呼び出しを数十回に収める） |
| リスクの高い作業 | 金額、セキュリティ、データの移行、最後のレビュー | Opus（またはメインのセッションと同じ高性能なモデル） | |
| 設計の決定、まとめ、利用者との相談 | | メインのセッション | サブエージェントに任せない |

※1：Haiku 5.5 は、指示（プロンプト）が 10 万 token を超えると、入力・出力・キャッシュのすべての単価が 5 倍になる（Anthropic の料金の文書、2026-10-20 確認）。品質が落ちるという情報もあるが、確かめられていない。

### 運用の規則

- サブエージェントの文脈は新しい。メインのセッションが規則の要約と対象を指示に書いて渡し、各サブエージェントに原文の全体を読ませない。
- メインのセッションは、サブエージェントの結果を 1 つずつ受けて作業を進めず、全部がそろってからまとめる。理由：結果を受けるたびに、メインのセッションの長い文脈を処理し直すため。

### 実績

| 作業 | 条件 | 結果 |
|------|------|------|
| spec 010 の後の全体レビュー | Sonnet、読むだけ | 6 つのサブエージェントで、合計約 162 万 token、ツールの呼び出し約 390 回。1 つあたり 6〜11 分 |
| plan 018 の本文 | Sonnet、日本語の要点から書く | 約 13.5 万 token、ツール 14 回、約 2 分 |
| tasks 018 の本文 | Sonnet、日本語の要点から書く | 約 12 万 token、ツール 12 回、約 1 分 20 秒 |

- 1 つのサブエージェントで全体を見るより、範囲を分けたほうが安い。理由：文脈が長いほど 1 回の呼び出しが高くなるため。
