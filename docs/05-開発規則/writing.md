# 文書の書き方

文書（docs/・README・AGENTS.md・spec・plan・tasks）を書く・レビューするときの規則。言い回しと論理の規則は、k16shikano 氏の `japanese-tech-writing`（SKILL.md、Unlicense、<https://gist.github.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d>）を出典とする。書籍の原稿向けの規範から、表と短い文が中心のこのリポジトリの文書に当てはまる規則だけを抜き出して書き換えた。

文書の置き場所は、この文書の「文書の置き場所」と、[constitution](../constitution.md)の「文書の地図」。書く手順は skill `docs`、番号と記号は[文書の記号と番号](notation.md)、コードのコメントは[コメントの書き方](comments.md)。

## 1. 言語

- Git に入るものは全て日本語で書く：ドキュメント・コメント・Javadoc・テスト名・テストデータ・seed・コミットメッセージ・エラーメッセージ。
- 識別子（クラス名、変数名、API のパス、テーブル名・カラム名）は英語。
- 例外：外部から取り込んだ skill（`.claude/skills/`）は、原文の言語のまま置いてよい。出典の更新を取り込みやすくし、許諾の条件（原文と出典の表示）を守るため。その代わり、`SKILL.md` の frontmatter の直後に、何をする skill か・いつ使うかの日本語の説明をコメント（`<!-- -->`）で書く。このリポジトリ向けの追記と、自分で作る skill は日本語で書く。

## 2. 文書の置き場所

各フォルダーに置くものは、[constitution](../constitution.md)の「文書の地図」にある。文書を追加したら、地図にも記載する。次の表は、地図にない、文書ごとの書く範囲の規則である。

| 文書 | 書くもの |
|------|----------|
| constitution | 大綱と文書の地図。各節は 1 文、要点（3 つまで）、「細則は〜」の案内だけ |
| README | 概要、起動とテストへの案内、進捗だけ。文書は constitution へ案内する |
| AGENTS.md・skill | エージェントに固有の手順だけ。規則は docs/ を指す |
| `docs/` の直下 | constitution とフォルダーだけを置く |

## 3. 論理名と物理名

- spec・plan・モジュール設計書の本文は、業務の用語（論理名）で書く。
- 識別子（物理名）を書くのは、[用語集](../03-機能仕様/glossary.md)、表の識別子の列、コードブロックだけにする。
- 新しい用語や識別子を作ったら、用語集に追加する。
- 実装の細部（SQL の句、アノテーション名など）は本文に書かず、意図だけを書く。

## 4. 表と注

- **表を先に**：決まり・対応・比べるものは表にする。長い理由と例外は、表の中に `※1`、表の下に `※1：…` と書く。
- **書き方の規則の文書**（`backend-coding.md` など）：冒頭に「規則の一覧」（節、規則、確認方法）、各節は規則と `理由：〜ため。` の 1 行（[書き方の規則とレビュー](review.md) 第 1 節）。
- **今の設計の文書**（`03-機能仕様/<モジュール>.md`・`02-設計/apps/`）：冒頭に概要の表。`<モジュール>.md` はレベル、依存、関連 spec とそのリンク（レベルの行は `| レベル | A（理由） |` の形にする。バックエンドの単体テスト（`ProductionClassesTest`）が、レベル欄の先頭の文字を、レベル A のモジュール一覧と照合する。書式を変えない）、`apps/` は依存、関連 spec とそのリンク（アプリにレベルはない）。本文には spec・plan・tasks の番号（AC-、BR-、plan の節など）を書かず、規則を言葉で書く。

### 4.1 読む人の負担

| 規則 | 避ける書き方 → 修正後の書き方 |
|------|------------------------------|
| 後で使わない固有名（ファイル名、関数名）を出さない。一般的な言い方で済ませる | 「`FooBar.java` のような仕組み」（以後出ない）→ 「同種の仕組み」 |
| 節の問いや結論に関係しない細部（時刻、ステータスコード、率）を入れない。議論に必要な具体は残す | 例に実行時刻と HTTP の全ヘッダーを書く → 結果と原因だけ書く |
| 新しい概念は、先に種類（クラス、手順、制約）を書いてから、性質を書く | 「テストで固定できる `Clock` を注入する」→ 「`Clock` は現在時刻を返すクラス。テストで固定するため、注入する」 |
| 節の中心になる語は、使う前に定義するか、定義の節を指す | 第 1 節で「窓口」を使い、定義が第 4 節 → 初出で定義する |
| 指す内容が文脈で決まらない言い回しは、括弧で特定する | 「この方式」→ 「この方式（ポーリング）」 |
| 新しい例を追加するときは、前の例との違いと、追加する理由を先に書く | 似た例を理由なく列挙する → 「前の例は同期、次は非同期」 |
| 表・コード・図は、それぞれ別の説明を担わせる。1 つで確認した性質を、別の例にそのまま当てはめない | 表に値、コードに手順 |
| 表のセルに、複数の話題を入れない | 理由と例外と手順を詰める → 理由は `※1` に移す |
| 1 文に主張を 1 つにする。短く切る | 「〜であり、〜のため、〜となるが、〜」→ 文を分ける |
| 見出しは、節が答える問いか、扱う対象を指す句にする。手順だけ、または結論を言い切る見出しにしない | 「進め方のまとめ」「重要な点」→ 「サブエージェントへの任せ方」 |

## 5. 用語の選び方

用語は、次の規則を上から順に当てはめて選ぶ。

| 規則 | 避ける書き方 → 修正後の書き方 |
|------|------------------------------|
| 日本語の技術文書の一般の読者に通じる用語を選ぶ。迷ったら、ツールの公式文書（日本語）や一般の技術書で使われる用語にする | `無記憶のレビュー役` → 「文脈を持たないレビュー役」 |
| 造語を作らない。名前が必要なときは、先に専門用語を調べ、あればそれを使う。なければ、用語集に定義を加え、校閲役に読ませてから使う ※1 | `判定器` → 「検査の script」、`口頭の語` → 「話し言葉」、`書面語` → 「書き言葉」 |
| 英語の語を直訳しない。定着した外来語があれば使う | `箱`（box）→ 「ボックス」、`指令`（command）→ 「コマンド」 |
| 話し言葉を書かない | `効く` → 「反映される」「有効になる」、「テストが効く」→ 「テストで回帰を検出できる」、「この設計は筋がいい」→ 「この設計は〜のため有望である」 |
| 少し長くなっても、意味がはっきりする書き言葉を選ぶ | 「何もせず成功を返す」→ 「状態を変えずに成功を返す」、「差分で探す」→ 「差分で特定する」 |
| 和語の言い換えより、技術文書で一般的な用語を使う（下の「技術文書の語」） | `流す` → 「実行する」 |
| 1 つの語で 2 つの意味を表さない。術語を、術語でない場面に流用しない。単独の「高」「低」は、危険度か重要度かを書く | `高の pull request` → 「危険度が高い pull request」、「層」をパッケージとレイヤーの両方に使う → 一方は「パッケージ」 |

※1：造語の手順は、issue を起票する時点にも当てはまる（[開発の進め方](workflow.md)の「起票」）。

- **用語**：複合語とカタカナ語で短く書き、「の」を重ねない（ログイン画面・ライセンス検査・有料版・ツール・ライブラリ）。言い換える語の一覧は `scripts/ci/ja-text.json`（error は CI で失敗、warning は文脈で決める）。「他の」「必要」と漢字で書く。
- **英字**：英字を使うのは、識別子・固有名と、英字のまま定着した外来語だけ。
  - 英字のまま定着した外来語は、このリポジトリで英字のまま使い続けている語（script・hook・pull request・commit・skill など）。それ以外の外来語はカタカナで書く。
  - 英字のまま書く語を新しく使い始めるときは、用語集に載せる。
  - 理由：英語を避けた結果、直訳の造語が生じたため。
- **技術文書の語**：和語より、技術文書で一般的な語を使う。
  - 使う語：確認する・レビュー・実行する・追加する・修正する・削除する・照合する・再作成する・必要・手動で・エンドポイント。
  - `〜し直す` は「再〜」（再試行・再取得・再起動）にする。
  - 業務の用語（用語集の語「写し」「取消」など）は言い換えない。
  - 避ける語の例：`確かめる`・`流す`・`照らす`・`見直し`・`待つ時間の上限`・`〜の口` → 「確認する」「実行する」「照合する」「レビュー」「タイムアウト」「エンドポイント」。
- **漢字とかな**：かなが長く続いて読みにくいときは、漢字の語を使う（全て、再度）。「こと」「とき」「ため」などの形式名詞は、かなで書く。

| 規則 | 避ける書き方 → 修正後の書き方 |
|------|------------------------------|
| 定義した語は、言い換えずに使い続ける。曖昧な語に戻さない | 「注文」「オーダー」「購入」を混ぜる → 用語集の「注文」に統一 |
| 分野で慣用されている語を選ぶ。近い意味の漢語を、一般語の感覚で当てない | プッシュ通知の「配送」→ 「配信」 |
| 指す対象が決まっているときは、広い語でぼかさず、名前を書く | 「ツールで検査する」→ 「`doc-refs.mjs` で検査する」 |
| 抽象的な名詞でなく、具体的な名詞を使う | 「処理を行う」→ 「在庫を引き当てる」 |
## 6. 言い回しと論理

**事実**：設定の値、既定値、必須かどうか、クラスの名前は、コードと照合してから書く。理由が文書にもコミットメッセージにもないときは、推測で書かず利用者に聞く。

### 6.1 論理

| 規則 | 避ける書き方 → 修正後の書き方 |
|------|------------------------------|
| 確認していないことを断定しない。確認してから書くか、未確認と書く | 「この設定が既定値である」（未確認）→ 値を確認して書く。未確認なら「未確認」と書く |
| 「かもしれない」「だろう」を機械的に削除しない。未確認の可能性、ログからの推定、読む人の疑念は残す | 「再試行されているかもしれない」（ログから推定）→ 「再試行されている可能性がある」。推定を「再試行されている」に変えない |
| 「かもしれない」「だろう」を削除してよいのは、根拠なく主張を弱めているときと、文書内の根拠で確定しているときだけ | 「必要だろう」（文書内の根拠で確定）→ 「必要である」 |
| 別のものを「同じ」とまとめない。別々の決定、原因、問題は分けて書く | 相互に依存する 3 つの未決事項を「同じ決定」と書く → 「どれも別の決定で、互いに依存している」 |
| 複数の要因がある事象を、1 つの原因にしない。要因ごとに、どの説明がどれに当たるかを対応づける | 「遅いのは N+1 のため」（インデックスの欠落もある）→ 「N+1 と、インデックスの欠落のため」 |
| 主張は、例が支える範囲に絞る | 「どのモジュールも同じ形」（2 つしか見ていない）→ 「catalog と cart は同じ形」 |
| 因果には、仕組みを 1 文で添える | 「キャッシュを使うと速い」→ 「キャッシュを使うと、同じ問い合わせの DB への往復が減るため速い」 |
| 「必ず」「全て」「常に」は、条件を付けるか、確認してから使う。検出・保証・解決を言い切らない | 「テストで必ず検出できる」→ 「テストが対象の経路を通るときに検出できる」 |
| 「A ではない」と書くときは、否定する内容を正確に書き、根拠を 1 文添える。読み違えそうな解釈を先に退ける | 「全てを任せるわけではない」→ 「設計の決定は任せない。判断の根拠が文書に残らないため」 |
| 「ただし」「とはいえ」を置いたら、その後で論を進める | 例外を書いて終わる → 例外の扱いまで書く |
| 「次節で扱う」「後の spec で行う」と書いた論点は、実際にそこにあることを確認する。ないなら issue に起票する（[開発の進め方](workflow.md) 第 4.1 節） | 回収されない先送り → 行き先を指す |
| 同じ概念の区分と定義は、文書全体で揃える | ある節で「利用者が決める」と分けたものを、別の節で「エージェントが決める」と書く |
| 複数の概念を上位の語でまとめるときは、同じものに帰着する理由を、命名の直前に 1 文書く | 突然「境界」と呼ぶ → 「どれも依存の向きを決めるため、境界と呼ぶ」 |
| 確認していない作業を、済んだように書かない | 「全体を検査した」（一部だけ）→ 「catalog だけ検査した」 |

### 6.2 中身のない言い回し

| 規則 | 避ける書き方 → 修正後の書き方 |
|------|------------------------------|
| 予告と総括を書かない | 「本節では認証を扱う」「ここでは〜を見ていく」「要するに」「〜に他ならない」→ 削って、内容をすぐ書く |
| 「重要なのは〜である」の前置きで主張を予告しない | 「重要なのは、ID を渡すことである」→ 「ID を渡す」 |
| 姿勢だけを宣言する語を使わない | 「正面から扱う」「正面から回収する」→ 「扱う」「ここで回収する」 |
| 中身のない形容と強調を書かない | 「非常に重要な」「不可欠」「核心的」「根本的な」「適切に」→ 何がどうなるかを書く |
| 何をしたかを示さない動詞を書かない | 「掘り下げる」「言語化する」「言及する」「多角的に分析する」→ 実際の作業を書く（「3 つの観点で照合する」） |
| 新しい情報のない接続を書かない | 「〜の観点から」「〜において」、「さらに」「また」「加えて」の連打 → 削る |
| 評価だけの文を書かない | 「これにより、より堅牢になる」→ 防げるものを書く（「二重登録を防ぐ」） |
| 読む人との問答の形にしない。読む人の反応を演じる形も避ける | 「では、どうすればよいか。〜」「〜と感じたかもしれない。そのとおりである」→ 答えだけ書く |
| 「〜という発想である」のような枠取りで、考えを紹介しない | その考えを直接書く |
| 著者の立場の弁明を書かない | 「本書もそれを否定しない」→ 事実だけ書く |
| 飾りの強調（太字、感嘆符）や、危険を煽る列挙を使わない | 「**絶対に**変更しない！」→ 理由を添えて「変更しない（Flyway の checksum が変わるため）」 |

### 6.3 翻訳調の比喩と擬人化

| 規則 | 避ける書き方 → 修正後の書き方 |
|------|------------------------------|
| 英語の比喩を直訳しない（carry、open、expose、live など） | 「ベクトルが選好を運ぶ」「API が内部を晒す」→ 「ベクトルに選好が反映される」「API が内部の型を公開している」 |
| 無生物を主語にして、人の動作をさせない | 「データが語るのは〜」「モデルは文体を知っている」→ 「データから分かるのは〜」「出力には文体の一貫性がある」 |
| 判定：字義どおりの動作を想像できる述語は疑う。主体と対象を具体語で言い換えられるなら、言い換えを書く | 言い換えられない表現は、指す内容が決まっていない。削るか、内容を確定させて書き換える |
| イ形容詞に「です」を付けた文で終えない。文末だけを変えず、前後の流れごと書き換える | 「これは難しいです」→ 「〜のため難しく、〜する」 |

### 6.4 冗長さ

| 規則 | 避ける書き方 → 修正後の書き方 |
|------|------------------------------|
| 同じ主張を言い換えて繰り返さない。加える内容が違う文は、繰り返しではない | 「X は不要。つまり X を置かない」→ 「X は置かない」 |
| 同じ意味を 2 か所に書かない。役割が重なる節は 1 つにまとめる | 重複する節 → 1 か所に書き、他は指す |
| 表を示した直後に、同じ内容を文で要約しない | 表の下に「以上のとおり〜」→ 削る |
| 論理の役割が同じ並列の事実は、1 文にまとめる | 「A は X。B も X。C も X。」→ 「A、B、C はどれも X」 |
| 接続や評価のためだけの文を置かない | 「それでは次に見ていく」「それ自体はよい」→ 削る |
| まだ導入していない概念や文書名を、先回りして示さない | 第 2 節で第 5 節の語を使う → 第 5 節で導入する |
| 本文内の根拠で確定していることは、弱い述語にせず言い切る | 「〜が有効と考えられる」（確認済み）→ 「〜が必要」 |
| 冗長な語尾を短くする | 「〜することができる」「〜を行う」→ 「〜できる」「〜する」 |
| 字数を減らすために、動機・対象・因果・条件を読む人の推論に任せない | 「X のため Y」の「X のため」を削って意味が通らなくなる → 残す |

## 7. 参照

- 参照の形は `<文書の名前>の「<見出し>」`。Markdown では、文書の名前をリンクにする（`[開発の進め方](workflow.md)の「起票」`。この文書からの相対パスにする）。見出しは番号を除いて書く。
- 同じ文書に同じ見出しが 2 つ以上あるときは、親の見出しを前に付ける（`「段階 1」の「タスク」`）。
- 見出しでない所（表の行や列、用語集の語）を指すときは、この形を使わない。「の」と「」の間に、指すものの種類を書く（`用語集の語「写し」`、`AC 一覧の列「テスト」`）。理由：検査が、この形を見出しの参照として読むため。
- constitution の節ではなく、細則の文書を指す。
- 理由：節の番号は、節を加える・移すたびに変わり、参照が意味の違う節を指したまま検査を通る。見出しを変えると、検査（`doc-refs`）が切れた参照を見つける。
- 既存の `第 N 節` の参照は、順に見出しの形へ置き換える。置き換えを終えたら、`第 N 節` の参照を検査で失敗にする。

## 8. spec と plan の書き方

| 対象 | 書き方 |
|------|--------|
| AC・DC | 1 つの AC・DC に条件を 1 つ、1〜2 文で書く。値の一覧と場合分けは、箇条書きか表にする |
| Given / When / Then | 同時の操作など、手順で示さないと分からない条件だけに使う |
| 括弧 | 1 文に 1 つまで。理由は文の後に `理由：〜ため。` で、長い補足は表の下に `※1：` で書く |
| plan の節 | 決定を表（何を、どこに、確認方法）で先に示し、理由を後に書く。1 つの箇条書きに 1 つの決定 |
| 識別子 | ファイル・クラス・関数の名前は、表の列とコードブロックにだけ書き、本文は役割で書く（「論理名と物理名」） |
| 他の文書の内容 | モジュールの設計、API の項目、書き方の規則は転記せず、その文書を指す |

- plan で操作やクラスを移す・削除すると決める前に、テスト（`src/test`・`src/integrationTest`・画面のテスト・E2E）を含む全ての呼び出し元を検索し、plan に挙げる。同じ名前のメソッドが複数あるときは、型で区別できる方法（IDE の呼び出しの階層）で調べる。理由：テストだけが使う呼び出しを見落とすと、実装で決定を変更することになるため。
- 入力の形を判定する script（hook、CI の検査）を作る spec は、判定を許可する形の一覧で書く。理由：禁止する形の一覧に回避の形を 1 つずつ加えても、レビューの指摘が尽きないため。
- その spec は、判定が誤りの防止（誤って書いたものを拒否し、意図して作った回避は対象にしない）か、回避の防止（意図して作った回避も拒否する）かを、DC で先に決める。決めた区分は、レビューで回避の形を高にするかの基準になる（skill `review` の prompts.md）。
- 完了した spec・plan・tasks は当時の記録として、内容と節の番号を変えない。文書を移して切れたリンクも修正しない。理由：アーカイブは当時の記録で、当時の状態は Git の履歴で読めるため。
- 今の設計はモジュールの設計書と `docs/02-設計/` に書くので、古い spec は直さない。

理由：spec と plan は、利用者が承認の前に読み、実装の間にエージェントが何度も読むので、決定と条件を一目で読み取れるようにするため。

## 9. 載せない規則

次の規則は、散文の書籍向けのため、この文書には載せない。

| 種類 | 理由 |
|------|------|
| 段落の構成（1 段落 1 主題、段落の先頭の接続表現、結論を 1 度だけ置く、前方参照の位置） | 表と箇条書きが中心で、長い段落がないため |
| 対比の定義の述部をそろえる、譲歩の書き方、山場の情報を先出ししない | 長い論証の文章の規則で、表では起こらないため |
| 演出の節度（溜め、短い決め台詞の段落、太字の使い方、対句、転回点） | 表と短い文には、演出がもともとないため。飾りの強調だけ 6.2 に載せた |
| 命令調（「〜してはならない」）を避ける | 規則の文書は、規則を命令の形で書くため |
| 例の組み立て（架空の人物を置かない、行為者を主語にする、「あなた」と呼ばない） | 例は、このリポジトリの実際のクラスやコマンドで書くため |
| 人名の原綴り、読者への誠実さ（作為的な例の弁明） | 人名と作為的な例が、このリポジトリの文書にはほとんどないため。確認していないことを書かない規則は 6.1 に載せた |
