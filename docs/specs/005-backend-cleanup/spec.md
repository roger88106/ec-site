# Spec 005：バックエンドの整理

ステータス：確定

## 1. 背景と目的

spec 001〜003 で、バックエンドの 8 つのモジュールができた。作りながら決めたため、モジュールによって構成と書き方が揃っていない。spec 006 以降で機能を追加する前に、読む人が、どのモジュールでも同じ場所に同じものを見つけられるようにする。

- 層とパッケージの名前・置き場所が、モジュールによって違う。腐敗防止層（他のモジュールを呼び出すクラス）が、1 つだけのパッケージとしてモジュールの直下に並んでいる。パッケージの大きさの目安もない。
- 文字列の項目の検証（空白でない、長さの上限）が、モジュールごとに同じ処理として書かれている。長さの上限が API の契約とドメインの両方に手動で書かれ、一致を確認する仕組みがない。API の契約の数値の項目に、範囲の制約の漏れがある。
- 1 つのエラーを 4 か所（エラーの定義、メッセージの定数、メッセージのキー、メッセージのファイル）に書いている。入力の検証のメッセージは、メッセージのファイルで管理していない。
- 現在の会員を取り出す同じ処理が、4 か所にある。商品の集約が大きい。
- 複雑な処理（複数段の変換など）の前に、何をしているかのコメントがない箇所がある。

本 spec は**整理の spec**（[文書の記号と番号](../../rules/notation.md)）。spec 004 の完了を前提にする（ファイルの置き場所、規則の文書、テストの網）。spec 006 とは互いに独立している。

## 2. 用語

本 spec で新しく使う用語（標準の構成、共通の値の型など）は、plan で用語集に追加する。

## 4. 目的と完了の条件

### DS-8 どのモジュールも、同じ構成で読める（D / P1）

- **DC-27** アーキテクチャのレベル（constitution 4.2）ごとに、標準の構成（層とパッケージの名前、何をどこに置くか）が図と一緒に文書にある。全てのモジュールが、自分のレベルの標準の構成に従う。レベル B も、レベル A と同じ層の名前を使う（中身は簡略のまま。constitution 4.2 を修正する）。
- **DC-28** 腐敗防止層（他のモジュールを呼び出すクラス）と、層の外へのインターフェース（port）は、使う側の決まった置き場所にまとめる。クラスが 1 つだけのパッケージを、モジュールの直下に作らない。
- **DC-29** 1 つのパッケージの直下のファイルは、10 を目安、20 を上限にする（パッケージの説明のファイルと、テストは数えない）。上限を超えると、自動の検査で失敗する。目安を超えるパッケージは一覧にして、分けるかを判断した結果を残す。
- **DC-30** モジュールの境界と、DC-27〜29 の構成の規則（層の依存の向き、パッケージの名前と置き場所、ファイルの数）を、コンテナを使わない単体テストで確認する。

### DS-9 値と入力の検証の規則を、1 か所で持つ（D / P1）

- **DC-31** 文字列の項目の検証（空白でない、長さの上限を文字の数で数える）は共通のクラスで行い、モジュールごとに同じ処理を書かない。
- **DC-32** 同じ項目について、API の契約の制約（長さ、範囲）、ドメインの上限、データベースの列の長さが食い違うと、テストが失敗する。
- **DC-33** API の契約のリクエストで、数値の項目（版、件数、増減、金額、大きさ）には全て範囲の制約があり、文字列の項目には全て長さか形式の制約がある。漏れがあると、検査で失敗する。
- **DC-34** 金額は、モジュールの内部で金額の型を使う。モジュールの間の公開の型でも金額の型を使う。整数で持つのは、API の契約とデータベースの境界だけにする。
- **DC-35** モジュールに共通の型（集約の土台、値の型など）は、種類ごとに分けて置く。どの値を共通の型にするかの基準が、規則の文書にある。

### DS-10 エラーとメッセージを、1 か所で定義する（D / P1）

- **DC-36** 1 つのエラーは 1 か所で定義する。メッセージのキーは、エラーの定義から規則で決まる。エラーの定義とメッセージのファイルが食い違うと（片方にしかないと）、テストが失敗する。
- **DC-37** 入力の検証のエラーのメッセージ（フレームワークの既定のものを含む）も、業務のエラーと同じメッセージのファイルで、同じキーの規則で管理する。
- **DC-38** メッセージに値（上限の数、件数など）を差し込める。業務の規則の値（上限など）を文に書いているメッセージは、その値をドメインの定数から差し込み、規則の値が変わると文も変わる。差し込みにしても、今の文は変わらない。
- **DC-64** 画像の変換の結果が WebP でなければ、変換の失敗のエラーにし、アセットを記録しない（AC-68 を守る。spec 004 で見つけた検査の漏れ）。DN-4 の例外：振る舞いを修正するが、通常の応答は変わらない。

### DS-11 大きいクラスと重複を減らす（D / P1）

- **DC-39** 現在の会員（必須、または任意）を取り出す処理を 1 か所にし、API の入口ごとに同じ処理を書かない。
- **DC-40** 商品の集約にある、ほかの集約と共通の処理（文字の検証、並び順の再採番）を、共通のクラスに移す。商品の更新の処理は、用途（商品、バリアント、公開、画像）ごとに分ける。集約の分け方（取引の境界）は変えない。
- **DC-41** バックエンドの全体を、規則の文書（spec 004 と本 spec）に照合して調べ、重複、使われていないコード、規則に合わない所を一覧にする。一覧の各項目に、修正したか、修正しない理由を残す。

### DS-12 設定とビルドを整える（D / P2）

- **DC-42** 設定の値の定義は、置き場所、名前の接頭辞、必須と既定値の扱いが規則どおりになる。必須の値がなければ、起動に失敗する。
- **DC-43** データベースのアクセスのコード生成は、マイグレーションと生成の設定が変わらなければ省かれる（今はビルドのたびにコンテナを起動して再生成し、約 6 秒かかる）。

### DS-13 複雑な処理を、コメントで読めるようにする（D / P1）

- **DC-44** 規則の文書が「複雑な処理」とするもの（複数段の変換、集計、入れ子の繰り返し、3 つ以上の条件の組み合わせ、3 つ以上の分岐）の直前に、何の結果を得るか・なぜそうするかのコメントがある。分からない箇所は推測で書かず、一覧にして利用者に確認する。
- **DC-65** 本番のコード（`src/main`）とビルドの設定（`build.gradle.kts`）のコメントに、spec・plan・tasks の番号（AC・BR・US・NFR、spec・plan の節、タスク番号）がない。番号で示していた規則は、言葉で書かれている。spec との対応はテストの名前にある。

## 5. 業務ルール

なし（本 spec は業務の規則を変えない）。

## 6. 非機能要件

- **DN-4** API の応答の形と、データベースのデータを変えない。既存のテストは全て通る（テストを変えるのは、置き場所の移動と、DC-37 によるメッセージの文の変更に限る）。例外：入力の検証のエラーの文は、DC-37 で変わってよい（管理画面にそのまま表示される）。変わる文は plan で一覧にする。
- **DN-5** コメントだけの変更（DC-44）は、コードの変更と別の commit にする。パッケージの移動は、内容の変更と別の commit にする。
- **DN-6** データベースの構造を変えない（DC-32 で食い違いが見つかった場合を除く。その場合は、修正する前に利用者に確認する）。

## 7. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| 型の変換の部品を、生成の道具に替える | 行わない（手動で書いた変換のほうが型の対応が明確で、生成の手順を増やさない） |
| 商品の集約を分ける | 行わない（取引の境界が変わり、リスクがメリットを上回る） |
| 入力の検証の独自の注釈 | 規則が正規表現で書けず、複数の所で使うものが出てきたとき |
| 2 つ目の言語のメッセージ | 将来の spec |
| フロントの整理 | spec 006 |
