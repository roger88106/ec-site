# Spec 224：統合テストの頑丈さと、集約の復元の失敗のログを整える

ステータス：確定

## 1. 背景と目的

spec 181 で統合テストの間の干渉をなくしたが、spec 181・182・186 のレビューで、今は通るが、他のテストの追加や時刻の変更で壊れうる箇所が残った（#201）。また、集約の復元に失敗したときの error のログに、原因の例外のメッセージがそのまま出ており、メッセージに値が入りうる（#204）。どちらも、バックエンドのテストと共通の部品だけを変え、モジュールをまたぐ決定がない整理なので、1 つの spec で扱う。

追跡の issue は [#224](https://github.com/roger88106/ec-site/issues/224)、扱う issue は [#201](https://github.com/roger88106/ec-site/issues/201)、[#204](https://github.com/roger88106/ec-site/issues/204) である。作業ブランチは `224-backend-tests-log`。本 spec は整理の spec で、規模は M である（第 6 節の 1）。

### 3.1 spec 223 の検査が前提にする今の状態

spec 223（#202）は、補助以外のテストが、在庫の作成、税区分の登録の要求、応答の JSON から ID を取り出す処理を直接書かないことを確認する検査を加える（DC-223-7〜9）。本 spec の後の状態は次の表のとおりで、spec 223 は「検査の対象外」の 2 列を検査の除外にできる（DC-224-8）。カテゴリの登録と支払の作成は、spec 223 の検査の対象ではないが、本 spec で同じく補助に替える。

|------|----------------------|--------------------------------------------------|----------------------|
| 在庫の作成 | `InventoryTestData` | `JooqStockItemRepositoryTest` | なし |
| 税区分の登録の要求 | `CatalogTestData` | `TaxCategoryApiTest`、`AuthorizationTest`、`KeycloakIntegrationTest` | `ProductApiTest` |
| 作成の応答から ID を取り出す処理 | `TestJson`、`CatalogTestData` | `TaxCategoryApiTest`、`CategoryApiTest`、`ProductApiTest`（確認する API の作成の応答） | `ProductApiTest`（税区分とカテゴリの作成） |
| カテゴリの登録の要求 | `CatalogTestData` | `CategoryApiTest` | `ProductApiTest` |

- 表の手順に、次のものは含めない。
  - Repository のテストが、集約を直接作る処理（支払の Repository のテストなど）
  - 作った後の変更の要求（店舗の鮮度のテストの税率の変更など）

- 統合テストに、イベントの記録（`EventPublicationRegistry`）で処理の完了を待つ箇所はない。イベントの片付けと再送のテストは、イベントの補助（`EventPublications`）を作るために注入するだけである。
- 表の「検査の対象外」の 2 列は、実装を始める前の照合で `git grep` で探し直し、確定する。
- 表は、T224-01-03 で [テストの書き方](../../rules/test-writing.md) 第 3.2 節に写す（DC-224-22）。

## 5. 守る制約

- **DN-224-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。ログの内容の変化（DS-224-6）は、運用と開発にだけ見える。
- **DN-224-2** テストを弱めない。補助に移すとき、確認の方法を変えるときは、確認する内容を減らさない。直した確認は、一時的にコードか期待値を変えて、失敗しうることを確認する（[開発の進め方](../../rules/workflow.md) 第 2.1 節）。
- **DN-224-3** AC を追加も変更もしない。AC-173 のテストを分けたら、[AC 一覧](../../design/acceptance-criteria.md) のテストの列が今のテストと合うことを確認する。
- **DN-224-4** 新しく書くコメントに、spec・plan・タスクの番号を書かない（[コメントの書き方](../../rules/comments.md) 第 1 節）。
- **DN-224-5** 統合テストの全体の時間を大きく延ばさない。理由：CI とローカルの確認で毎回実行するため。
- **DN-224-6** 実装は、spec 222（文書の整理）のマージの後に始める。理由：spec 222 が、文書とコードのコメントの語を広く置き換えるため。
- **DN-224-7** 並行する spec 223（#202、#217）と、変えるファイルが重なりうる。重なりと順序は第 8 節の前書きの表に書き、実装を始める前の照合（[開発の進め方](../../rules/workflow.md) 第 5.6 節）で、spec 223 の tasks と照合し直す。
- **DN-224-8** 共有の文書（[テストの書き方](../../rules/test-writing.md)、[AC 一覧](../../design/acceptance-criteria.md)）は、spec 226 などの並行する spec も変える。衝突は、後でマージする pull request が `develop` を取り込んで解消する。

## 6. 決めたこと

spec の確認で、利用者が第 6 節の 2〜5 を全て案 A に決めた（2026-10-27）。規模 M も同じ時に承認した。第 6 節の 5 の方針（値を除く向き）は、それより前に #204 の起票で決めていた。

### 6.1 規模

規模は M である。API の契約とデータベースを変えず、AC を追加も変更もしないため。本番のコードは共通の部品（集約を復元する補助）だけを変え、他は各モジュールのテストを独立に直すので、モジュールをまたぐ決定がない。

### 6.2 管理の注文の一覧のテストの絞り方（DC-224-1、2）

管理の注文の一覧の API は、注文番号の前方一致、状態、注文日の範囲で絞り、ページで返す。注文番号は「注文日-乱数 6 桁」なので、テストの注文だけに共通する前方一致はない。

- 案 A（採用）：注文日の取り決めをなくし、応答の中の自分の注文を ID で識別して確認する。
  - 並び順は、自分の注文の間の順序で確認する。
  - 絞り込みは、自分の注文が入る・入らないことと、返った全ての行が条件に合うことで確認する。
  - ページは、同じ条件の全件を取得して比べ、2 ページ目の行と総数が、全件の該当する部分と合うことを確認する。
  - 理由：[テストの書き方](../../rules/test-writing.md) 第 3.1 節の「自分のデータだけを確認する。一覧の全体を確認しない」に合い、取り決めを守る検査が不要なため。
- 案 B：取り決めを残し、取り決めた日付を補助の定数の一覧にまとめる。他のテストがその日付を使わないことは、ソースの文字列を探す検査でしか確認できず、時刻を計算で作るテストを検出できない。

### 6.3 行ロックのテスト（DC-224-10、20）

- 案 A（採用）：支払の行ロックにも、注文と同じく、別のトランザクションがロックを取れないことを確認するテストを加える。注文と支払のテストの名前は、次の 2 つの形にそろえる。理由：名前に書いた振る舞い（ロック）を確認するため（テストの書き方 第 2.2 節）。
  - 「行ロックして取得すると〜を返す」
  - 「行ロックして取得している間は、別のトランザクションが〜できない」
- 案 B：確認を加えず、支払のテストの名前から行ロックを外す（「取得できる」）。名前と内容は合うが、ロックを外す誤りを見つけられない。

### 6.4 置き場所の system property の読み方（DC-224-12、13）

単体テストの契約の補助は、system property がないか空のとき、名前を示して失敗する。統合テストのソースセットは、単体テストのソースセットを使えない。

- 案 A（採用）：契約の補助を、単体テストと統合テストが共有する既存のテストの補助のソースセット（testFixtures）に移す。補助に theme の置き場所を加え、2 つの統合テストが、契約、realm、theme の置き場所をこの補助で読む。理由：読み方が 1 か所になるため。
- 案 B：統合テストのソースセットに、同じ読み方の補助をもう 1 つ作る。spec 223 と変えるファイルが重ならないが、読み方が 2 か所になる。

spec 223 は、単体テストが文書の置き場所を読む処理を、契約の補助と同じ方法にそろえる（DC-223-10）。統合テストが置き場所を読む処理は、本 spec が扱う（spec 223 第 8 節）。2 つの spec が同じ補助を変えるので、順序を第 8 節の前書きの表に書く。

### 6.5 復元の失敗のログから値を除く方法（DC-224-16〜18）

#204 の方針は、#153 と同じ向きで、例外の種類と、集約を特定する情報だけを残す（利用者が #204 の起票で決めた。2026-10-26）。集約を特定する情報は、集約の名前（`category` など）とし、集約の ID は加えない。理由：ゲストのカートの ID のように、ID が利用者を指す値になる集約があり、#153 でも識別子をログから除いたため。要求との対応は、ログのトレース ID で追跡できる。

- 案 A（採用）：集約を復元する共通の補助で、投げる例外に原因の例外をそのまま持たせず、原因の例外の種類とスタックトレースだけを持つ例外に置き換える。理由：ログに出す経路（例外の処理の共通の部品、定期のジョブ、イベントのリスナー）によらず、メッセージが出なくなるため（DC-224-18）。失敗した場所は、スタックトレースで分かる。
- 案 B：例外の処理の共通の部品で、復元の失敗だけ、原因のメッセージを出さずにログに出す。HTTP の要求の外の経路が残るので、DC-224-18 を満たせない。

| 項目 | 理由 |
|------|------|
| 復元の失敗以外の、想定外のエラーのログから例外のメッセージを除く | #204 の範囲は復元の失敗である。他の例外のメッセージに値が入るかは、例外ごとに調べる必要がある（第 9 節） |
| 補助以外のテストの再定義を見つける検査を加える | spec 223（#202）が、本 spec のマージの後に加える。本 spec は、検査の違反を 0 にする（DC-224-8） |
| 一覧にない配送業者に項目の誤りを返す | 契約と合っている（第 3 節の 11）。変えると API の振る舞いが変わる（DN-224-1） |

## 8. tasks

- `[P]` のタスクはない。同じ段階のタスクは、番号の順に 1 つずつ行う。理由：各タスクの確認に統合テストを実行し、作業ツリーを分けて同時に実行すると、スロットと CPU が足りず短くならないため。段階 1 の T224-01-02 と T224-01-03 は、同じテストの書き方も変える。
- `[テスト]` のタスクは、テストを書いてレッドを確認し、同じ実装役が続けて実装する。テストだけを直すタスク（確認の方法を変える）は、直した確認を一時的にコードか期待値を変えて失敗させ、commit の本文に書く（DN-224-2）。
- 各段階の最後に、統合テストの全体（`./gradlew check`）を実行し、かかった時間を段階 1 の前と比べて、段階のレビューのタスクの結果に書く（DN-224-5）。
- 各段階の最後のレビューは、profile「厚め」で行う（[エージェントの作業フロー](../../rules/subagents.md) 第 4 節）。重要な観点に「テストを弱めていないか」（DN-224-2）と「新しいコメントに spec・plan の番号がないか」（DN-224-4）を含める。

並行する spec と変えるファイルの重なりは次のとおり（DN-224-7）。spec 223 の tasks は、本 spec の確定の時点で未作成なので、実装を始める前の照合で照合し直す。

| 本 spec のタスク | 変えるファイル | 重なる spec | 順序 |
|------------------|----------------|-------------|------|
| T224-01-03 | 補助を使うように直す統合テスト、テストの書き方 第 3.2 節の表 | spec 223 の DC-223-7〜9 の検査 | 本 spec のマージの後に、spec 223 が検査を加える |
| T224-02-04 | 契約の補助（testFixtures に移す）、2 つの統合テスト、ビルドの設定 | spec 223 の DC-223-10（単体テストの置き場所の読み方） | 本 spec の後に spec 223 が同じ補助を使う。spec 223 が先なら、本 spec が取り込んで合わせる |
