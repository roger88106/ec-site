# レビューの観点と指示のひな形

[SKILL.md](SKILL.md) の手順 3 から読む。手順 7・8 のひな形は [docs-review.md](docs-review.md)。

## 観点の一覧

レビュー役には、観点ごとに、下の表の列のファイルを渡す。観点の表を渡しても、チェックリストは一緒に渡す（表にない規則を、チェックリストで拾うため）。差分の変更の種類に合わないファイルは外し、列が「変更の種類に合うもの」の観点は、合うファイルを選ぶ。表の見る問いと過去の見落としの例で、観点を具体的にする。観点の表は、級の列で重要と次要に分け、重要の行を表の前に置く。指摘の級の定義と、次要の数の上限は、下のひな形の「結果」。検証役のひな形は、この後にある。

| 観点 | 見ること | 主な根拠 | 渡す perspectives/ のファイル |
|------|----------|----------|------------------------------|
| 規則と一貫性 | 規則に合うか。モジュール・spec で書き方が違わないか。新しい書き方が全体に行き渡っているか（検出の式で全体を照合する） | 書き方の規則の各文書、既存のコード | 変更の種類に合うもの（コメントを変えたら `perspectives/comments.md`） |
| 構造と共通化 | 比べる対象と比べ、同じ処理の重複、層の誤り、共通の部品を使わない古い形がないか。過ぎた抽象、使われないコード・TODO・残った設定 | バックエンドの書き方の「共通の型」、フロントの書き方の「共有パッケージ」 | `perspectives/backend.md`、`perspectives/frontend.md`、`perspectives/scripts-ci.md` |
| 境界と依存 | モジュールの `api`・`event` の外に触れていないか、腐敗防止層、循環、共有の中身 | バックエンドのアーキテクチャ、ArchUnit・Modulith | `perspectives/backend.md` |
| 文書と振る舞いの照合 | 変えた文書の表と条件の各行が、コード・設定・script と一致するか。古い記述とリンク切れ。食い違いは、コードを正として文書の修正を提案する ※1 | 開発の進め方 | `perspectives/docs.md` |
| AC とテストの対応 | AC の文を場合（条件、境界、拒否）に分けたとき、対応するテストのない場合がないか | spec の AC、テストの書き方 | `perspectives/tests.md` |
| テスト | 弱い確認、重複した・壊れやすいテスト、「テストの観点」の一覧にある観点の抜け | テストの書き方、特に「テストの観点」 | `perspectives/tests.md`、フロントは `perspectives/frontend.md` |
| 安定性と運用 | エラーの扱い・ログ・設定・並行・外部サービスの失敗・セキュリティ・性能 | バックエンドのアーキテクチャ、フロントの書き方 | `perspectives/backend.md`、`perspectives/frontend.md` |
| script と CI | 検査の必要性、検出の正しさ（漏れと誤検出）、速さ、閾値の根拠、script のテスト | CI の検査の追加 | `perspectives/scripts-ci.md` |
| 段階をまたぐ影響 | 段階ごとに通ったものが、段階をまたいで合うか（前の段階で作った script や skill の使われ方、順序、重複） | spec・plan の段階の分け、tasks の各段階の結果 | `perspectives/scripts-ci.md`、`perspectives/docs.md` |
| spec との一致 | spec の各 AC・DC・DN と plan の決定が、コードと文書で満たされているか | spec、plan | なし |
| 決定との一致 | 利用者が決めた一覧と、変えた内容が一致するか（決めていないものを足していないか、決めた置き場所と違う所に書いていないか）。spec にない整理の差分で使う | 利用者の決定の一覧 | `perspectives/docs.md` |
| 整理で振る舞いを変えない | 整理の差分が、振る舞い・契約・URL・遷移の先・テストの判定を変えていないか | 開発の進め方の「中断して質問する条件」、整理の spec | `perspectives/tests.md` |
| ファイルをまたぐ影響 | 値や制約を変えたとき、同じ値と制約を持つ箇所が全て変わったか（DB の制約、他の AC のテスト、文言） | spec・plan の変更点、変えた値の全文検索 | `perspectives/docs.md`、`perspectives/tests.md` |
| 削った文の行き先 | 削った文ごとに、行き先（移した先、正本）があるか。規則や条件が変わっていないか ※2 | 差分の削除行、※2 の表 | `perspectives/docs.md` |
| 後の開発への備え | 初めて読む人（エージェント）に分かるか、機能を追加するときの拡張の場所 | なし | `perspectives/frontend.md`、`perspectives/docs.md` |

※1：自動の検査がない次の文書は、関わるコードを変えたら必ず照合する。
- モジュールの設計（`docs/02-設計/<モジュール>.md`）の「パッケージの構成」
- 共通コード・ログ・可観測性（`common/`、`config/`、ログと運用の設定）
- API の規約の URL の規則（契約のパス）

※2：「正本にある」として文を削るときは、削った実装役かセッションが次の表を報告に含める。セッションが削るときは、pull request の本文に含める。

| 削った文（ファイル:行） | 正本（ファイル:行） | 正本の文 |
|-------------------------|---------------------|----------|

## 指示のひな形（観点ごと）

レビュー役は前面で呼び、結果の token と時間を受け取る。背景で動いて値が返らなかったときは、記録の表に「—」と書き、表の下に理由を書く。

日本語だけで書く。次の形にする。

```
あなたは、<リポジトリ> のコードと文書のレビュー担当です。実装の過程は知らされていません。

## 対象
<対象のファイルの一覧のパス、差分のファイルのパス、または範囲>
比べる対象：<compare-targets の出力のパス>
判断に必要なら、呼び出し元と同じパッケージのクラスを読む。
重要の行の問いには、対象のファイルだけでは分からないものがある。対象の外を、次の手順で読んで比べる。比べる相手は自分で探さず、比べる対象の出力を起点にする。観点に関わる項目だけを行い、作業の表は、結果のファイルの指摘の表の後ろに書く。
- 構造と共通化：出力の「同じ種類のファイル」から 2 つ読み、同じ処理を各自で書いていないかを比べる。同じ形が 2 か所以上あれば、共通にする提案を返す。「共有の部品の一覧」に同じ役割の部品があるのに、古い形で書いていないかも見る。
- 層：出力の「参照元」と、対象が呼ぶ側（イベントのハンドラー、ジョブ、入口）を読み、処理が決まった層に置かれているかを確認する。
- 回数：1 つの要求（画面の表示、API の呼び出し、1 件の読み込み）で、DB と外部のサービスを何回呼ぶかを数える。画面は、開いたときに同時に来る要求（先読み、並べた取得）も合わせて数える。
- 文書と振る舞いの照合：変えた文書の表と条件の各行を、実装（コード、設定、script）の file:line と 1 行ずつ突き合わせ、行ごとに「一致・不一致・実装なし」を表にする。不一致と実装なしを指摘にする。
- AC とテストの対応：AC の文を場合（条件、境界、拒否）ごとに分けて表にし、各行に対応するテストの名前を書く。空いた行を指摘にする。

## 観点
<観点の名前と、見ること>

## 根拠
- チェックリスト：<パス>（この観点に関係する部分）
- 観点の表：<perspectives/ のファイルのパス>（表の見る問いで、級が重要の行を全て見てから、次要の行を見る。過去の見落としの例は、同じ形の見落としを探す手がかりで、指摘の根拠にしない。正本が「なし」の行の指摘は、その行（ファイル:行）を根拠にし、重要度は、級が次要なら「推奨」まで、重要なら「必須」まで）
- spec：<パス>、plan：<パス>
- 採らなかった指摘の一覧：<`rejected.md` のパス。なければ省く>
- 例の表：<形から推定して判定する検査・hook の spec なら、plan（規模 M は spec）の例の表の場所。なければ省く>
- <観点の主な根拠の文書のパス>

## 結果
<結果の書き先> に、次の表で書く。
| 重要度（高・必須・推奨） | 由来（今回・既存） | 場所（ファイル:行） | 指摘 | 根拠（文書と節、または DC・AC） | 修正案 | 機械の検査に移せるか |

- 指摘の級は、重要か次要かで決める。重要は、振る舞いが壊れる・データが漏れる・誤った結果を返す、構造の重複や置き場所の誤りを生む、性能が件数に比例して悪くなる、のどれか。それ以外は次要。
- 重要度の定義と、返す重要度は、[書き方の規則とレビュー](../../../docs/05-開発規則/review.md)の「重要度」のとおり。指示に、この時点で返す重要度（「高」「必須」だけか、「推奨」も含めるか）を書く。
- 次要の指摘は、1 回の結果で最大 5 件。同じ種類のものは 1 件にまとめて場所を並べる。重要の検討を終えてから次要を書く。
- CI・lint が検査するものは指摘しない。チェックリストの「確認方法：自動」の規則と、Biome・Checkstyle・ArchUnit・CI の検査の script が見るもの。
- この一覧の指摘は返さない（採らなかった指摘の一覧）。
- 好みの範囲の指摘は挙げない。根拠を示せない指摘は挙げない。
- 誤りの防止（誤って書いたものを拒否する判定）の spec では、意図して作った回避の形を重要度「高」にしない。回避の防止の spec（DC に書いてある）では、回避の形も返す。
- 例の表があれば、判定をその表と照合する。表にない書き方は、表に加える例として、指摘の欄に「例の表に加える」と書いて返す。
- 根拠と理由には出典（ファイル:行）を書く。出典のない理由は書かない。
- 結果の書き先の外には書かない。返すのは重要度ごとの件数（「高」「必須」「推奨」）だけ。
```

## 検証役の指示のひな形

[SKILL.md](SKILL.md) の手順 5 で、レビュー役の指摘をまとめる前に使う。定義は `reviewer`、モデルは高性能。日本語だけで書く。次の形にする。

```
あなたは、<リポジトリ> のレビューの指摘を確認する担当です。指摘を書いた人と実装の過程は知らされていません。

## 入力
- 指摘の表：<パス>（全てのレビュー役の指摘に番号を付けて 1 つにしたもの）
- 対象：<対象のファイルの一覧と差分のファイルのパス>
- 規則の文書：<指摘の根拠にある文書の置き場所>

## 判定
指摘ごとに、場所のコードや文書を読み直して判定する。
- 本当か：指摘の場所を読み、file:line で確認する。指摘が事実と違えば「偽」、読んでも決まらなければ「不明」。
- 級：重要か次要か。定義は、観点ごとのひな形の「結果」。
- 由来：今回の差分で入ったか、既存か。

## 結果
<結果の書き先> に、次の表で書く。
| 番号 | 本当か（真・偽・不明） | 検証した場所（ファイル:行） | 級（重要・次要） | 由来（今回・既存） | 理由（1 文） |

- 指摘の表にない指摘を足さない。
- 結果の書き先の外には書かない。返すのは、真・偽・不明の件数だけ。
```
