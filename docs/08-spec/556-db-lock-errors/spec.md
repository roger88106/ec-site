# Spec 556：DB のロックの待ちと例外の扱いを整える

種類：整理　規模：M　ステータス：草案

危険度：高

## 背景と目的

#458 のレビューで、DB のロックの待ち、DB の例外、定期ジョブと非同期のリスナーの 3 つの問題（#488）が見つかった。ログに DB のエラーの詳細が残る可能性（#429）もある。この 2 つの issue を 1 つの spec で整える。追跡の issue は #556（組の issue）。sub-issue は #488、#429。#544（リリースの前の整理）の段階 3 の線 C である。

- DB の接続に、ロック待ち・文の実行・トランザクション中のアイドルのタイムアウトがない。行ロックを取る読み込み（注文、決済、出荷、在庫、カテゴリ、注文手続き、カート）の待ちに上限がなく、終わらないトランザクションがあると、待つリクエストがスレッドと接続を使ったまま残る。
- 制約の違反でない DB の例外（デッドロック、ロック取得の失敗、直列化の失敗）は、全てシステムエラー（500）になる。再試行できる競合を 409 で返す処理がない。
- 定期ジョブのスケジューラーのスレッドは既定の 1 本で、6 つの定期ジョブが順に動く。支払の期限切れのジョブ（決済サービスを 1 件ずつ呼ぶ）の間、イベントの再発行と片付けが止まる。ジョブがロックを持つ時間の上限は全て 10 分である。
- 非同期のリスナーは全て既定のスレッドプール（8 スレッド、上限のないキュー）を共有する。外部サービス（SMTP、決済、オブジェクトストレージ、物流）を呼ぶリスナーが遅いと、外部を呼ばないリスナーも待たされる。停止のときに処理中のリスナーを待たない。
- 想定外の DB の例外をログに出力するとき、PostgreSQL のエラーの詳細（キーと値）が含まれ、行の値がログに残る可能性がある（#429。コードからの推定で、実際のログは未確認）。

消費者・運営者に見える振る舞いは、DB の競合の応答と画面のメッセージだけが変わる（DN-556-1）。

危険度を「高」にする理由は、全ての DB の接続、定期ジョブ、非同期のリスナーの実行に関わる設定を変えるため。この 2 点（規模と危険度）は確認待ちである（Open questions の 1、2）。

## スコープ

| 含める | 含めない |
|--------|----------|
| DB の接続のタイムアウト（ロック待ち、文の実行、トランザクション中のアイドル） | API の契約の変更 ※1 |
| DB の競合（デッドロック、ロック取得の失敗、直列化の失敗）を、警告のログと 409（共通のエラーの「更新の競合」）にすること | DB の構造の変更 |
| 定期ジョブのスレッドの数と、ジョブごとのロックを持つ時間の上限 | 文の実行のタイムアウトで失敗したときの応答（500 のまま） |
| 非同期のリスナーのスレッドプールの大きさ・キューの上限・停止のときの待ち | 画面の変更 |
| DB のエラーの詳細の値がログに出るかの確認と、出るなら抑止 | |
| 関係する設計と規則の文書の修正 | |

※1：409 の共通のエラーは、既に全ての操作が返しうるエラーとして契約にある。

決定（推奨。issue 担当のセッションの確認待ち。確認の結果で書き換える）：

- 規模：M とする（特例）。判定の表では L に当たる。2 つ以上のモジュール（「変える範囲」の表）にまたがるため。
  - 理由：どの変更も設定と共通のクラスの変更で、API と AC の対応も、モジュールをまたぐ実装の順序の設計もなく、plan に書く内容がないため。前例は spec 550 である。
- 決定 1（DB のタイムアウト）：全ての DB の接続の初期化で、3 つのタイムアウトを置く。値は設定ファイルに置き、環境変数で上書きできるようにする。推奨の既定値は次のとおり。
  - ロック待ち：5 秒。理由：利用者のリクエストが行ロックを待つ時間の上限を、画面の操作が待てる長さにするため。
  - 文の実行：30 秒。
  - トランザクション中のアイドル：60 秒。理由：メールの送信はトランザクションの中で SMTP を呼び、タイムアウトが接続・読み取り・書き込みで各 10 秒あるので、それより長くするため（出典：`docs/03-機能仕様/notification.md` 25 行、`application.yml` の `spring.mail.properties`）。
  - マイグレーション（Flyway）の接続では、文の実行のタイムアウトを無効にする。理由：索引の作成など、長いマイグレーションを止めないため。
- 決定 2（DB の競合を 409 に）：例外の原因（cause）の連鎖に、PostgreSQL の次の 3 種のエラー（DB の競合）があれば、409（共通のエラーの「更新の競合」）を返す。デッドロック、ロック取得の失敗（ロック待ちのタイムアウトを含む）、直列化の失敗。
  - 制約の違反の変換を通る書き込みでも、通らない読み込み（行ロックを取る読み込み）でも同じにする。
  - ログは警告のレベルで出力し、エラーコード・トレース ID・PostgreSQL のエラーの種類（SQLState）を出力する。原因の例外のメッセージ（行の値を含みうる）とスタックトレースは出力しない。
  - 文の実行のタイムアウトで失敗したエラーと、トランザクション中のアイドルのタイムアウトで切断された接続のエラーは、今のとおりシステムエラー（500）にする。理由：再試行しても同じ結果になりうる遅さで、競合ではないため。
  - 定期ジョブと非同期のリスナーでの競合は、今のとおり失敗として扱い、次の回か再発行で再試行する。
- 決定 3（定期ジョブ）：スケジューラーのスレッドの数を、定期ジョブの数（6）にする。理由：ジョブが互いを待たないようにするため。ロックを持つ時間の上限は、ジョブごとに、想定する最大の処理時間より長く決めて、理由をコメントに書く。推奨の値は次のとおり。値は確認待ちである。
  - 支払の期限切れのジョブ：30 分。決済サービスが応答しないときは、1 件で最大約 75 秒かかり、1 回の件数は最大 100 なので、最悪では 1 回が 30 分を超える（出典：支払の期限切れのジョブのコメント）。超えると別のインスタンスで同時に実行されうるが、業務の正しさは行ロックと冪等な状態の遷移で保つ（出典：定期ジョブの設定のコメント）。30 分は、通常の回が収まり、止まったインスタンスのロックが長く残らない値として推奨する。
  - イベントの再発行：5 分。理由：実行の間隔が 1 分のため。
  - そのほかの 4 つ：10 分のまま、明示する。
- 決定 4（非同期のリスナー）：外部サービスを呼ぶリスナー（メールの送信、ファイルの削除、決済の取消、物流の追跡の依頼）のスレッドプールを、外部を呼ばないリスナーのスレッドプールと分ける。両方のスレッドプールで、スレッドの数とキューの上限を設定で明示し、停止のときに処理中のリスナーを待つ。待つ時間の上限は、停止のときに処理中のリクエストを待つ上限（30 秒）に合わせる。
  - 未確認：Spring Modulith のリスナーのアノテーションはスレッドプールを選べないので、スレッドプールを指定するアノテーションを作る必要がある。イベント発行記録が今と同じに働くか（完了の記録、失敗の再発行）、キューが満杯で拒否されたイベントが、未完了のまま残って再発行されるかは、実装の最初のタスクで確認する。
  - 確認できなければ、作業を止めて報告し、スレッドプールを分けない案（1 つのスレッドプールの大きさとキューの上限を明示する）に切り替えるかを確認する。
- 決定 5（ログのエラーの詳細）：制約の違反などを起こし、実際のログに行の値が出るかを確認し、結果を #429 にコメントで書く。値が出るなら、PostgreSQL の JDBC ドライバーの設定（サーバーのエラーの詳細をログに出さない設定）を、全ての環境の共通の設定に置く。
  - 理由：本番の接続先は環境変数で渡すが、設定は共通のファイルにあり、環境で分ける理由がないため。
  - 設定の後も、制約の違反の変換（制約名の取得）が働くことを、テストで確認する。

## 目的と完了条件

### DS-556-1 DB の待ちにタイムアウトがある（D / P1）

- **DC-556-1** 全ての DB の接続に、ロック待ち・文の実行・トランザクション中のアイドルのタイムアウトがあり、値と理由が設定ファイルにある。
- **DC-556-2** マイグレーションの接続は、文の実行のタイムアウトで止まらない。

### DS-556-2 DB の競合が 409 になる（D / P1）

- **DC-556-3** 行ロックの待ちがタイムアウトしたリクエストは、409（更新の競合）になる。テストがある。
- **DC-556-4** デッドロックと直列化の失敗も 409 になる。
- **DC-556-5** 409 にした DB の競合は、警告のログに、エラーの種類とトレース ID を出し、原因の例外のメッセージを出さない。
- **DC-556-6** 文の実行のタイムアウトで失敗したエラーは、500 のままである。

### DS-556-3 定期ジョブと非同期のリスナーが互いに待たない（D / P1）

- **DC-556-7** スケジューラーのスレッドの数と、ジョブごとのロックを持つ時間の上限が、理由とともに設定かコードにある。
- **DC-556-8** 外部を呼ぶリスナーと外部を呼ばないリスナーのスレッドプールが分かれ、どちらもスレッドの数とキューの上限が設定にある。
- **DC-556-9** 停止のときに、処理中のリスナーを上限の時間まで待つ。

### DS-556-4 DB のエラーの詳細の値がログに残らない（D / P1）

- **DC-556-10** 実際のログに行の値が出るかを確認した結果が、#429 にある。
- **DC-556-11** 値が出るなら、設定の後のログに値が出ず、制約の違反の変換が今のとおり働く。

### DS-556-5 文書（D / P1）

- **DC-556-12** 設計と規則の文書（水平スケール、DB の制約の違反の扱い、API の規約の 409、環境変数の一覧）が、変えた設定と扱いを説明している。

## 非機能要件

- **DN-556-1** 消費者・運営者に見える振る舞いは、DB の競合（3 種）の応答だけが変わる。それ以外の振る舞いを変えない。
  - 応答は 500 から 409 になる。
  - 画面に表示されるメッセージは、「予期しないエラーが発生しました。」から、409 の共通のメッセージ「他の人が先に更新しました。再読み込みしてください。」になる。管理画面は 409 で再読み込みのボタンを表示する。
- **DN-556-2** API の契約と DB の構造を変えない。
- **DN-556-3** 既存のテストと検査（`./gradlew check`）が通る。

## Non-goals

| 項目 | 理由 |
|------|------|
| 文の実行のタイムアウトで失敗したときに 503 などを返す | 競合でなく、再試行の扱いを決める材料もないため。必要になったら起票する |
| 定期ジョブと非同期のリスナーでの競合の自動の再試行 | 今の再実行と再発行の仕組みで再試行されるため |
| 409 の画面のメッセージの書き分け（ロックの競合とバージョンの不一致でメッセージを変える） | 画面の文言の変更は利用者の決定が必要になるため。Open questions の 6 で確認する |

## Open questions

1. 規模を M（特例）にしてよいか。
2. 危険度を「高」にしてよいか。
3. 決定 1 の 3 つの既定値（5 秒、30 秒、60 秒）でよいか。
4. 決定 3 のロックを持つ時間の上限の値でよいか。
5. 決定 4 でスレッドプールを分ける案でよいか。分けない案は、1 つのスレッドプールの大きさとキューの上限を明示するだけである。
6. ロックの競合でも、画面に「他の人が先に更新しました。再読み込みしてください。」と表示してよいか（店舗画面の注文の確定などでも表示される）。変えるなら、画面の文言の変更として利用者の確認が必要になる。
