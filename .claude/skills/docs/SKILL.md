# 文書を書く・直す

文書の地図は [constitution](../../../docs/constitution.md) 第 3 節。文書は利用者と話して決め、エージェントが書く。

## 1. 置き場所

| 置き場所 | 書くもの |
|----------|----------|
| `docs/constitution.md` | 大綱と文書の地図。各節は 1 文、要点（3 つまで）、「細則は〜」の案内だけ |
| `docs/process/` | 開発の進め方、記号と番号、コメントの書き方、書き方の規則と見直し |
| `docs/backend/`・`docs/frontend/` | `architecture.md`（構成）、`coding.md`（書き方の規則）、`modules/<モジュール>.md`・`apps/<アプリ>.md`（今の設計） |
| `docs/api/`・`docs/testing/`・`docs/dev/`・`docs/reference/` | API の規約、テストの書き方と流し方、開発環境、用語集とライセンス |
| `docs/specs/` | spec・plan・tasks（当時の記録）。書き方は [開発の進め方](../../../docs/process/workflow.md) 第 1.4 節 |
| `README.md` | 概要、起動とテストへの案内、進捗だけ。文書は constitution へ案内する |
| `AGENTS.md`・skill | エージェントに固有の手順だけ。規則は docs/ を指す |

- `docs/` の直下には constitution と フォルダーだけを置く。文書を足したら constitution の文書の地図にも足す。
- 同じ意味は 1 か所に書き、ほかは指す。

## 2. 書き方

- **表を先に**：決まり・対応・比べるものは表にする。長い理由と例外は、表の中に `※1`、表の下に `※1：…` と書く。
- **書き方の規則の文書**（`coding.md` など）：冒頭に「規則の一覧」（節、規則、確かめ方）、各節は規則と `理由：〜ため。` の 1 行（[書き方の規則と見直し](../../../docs/process/review.md) 第 1 節）。
- **今の設計の文書**（`modules/`・`apps/`）：冒頭に概要の表（レベル、依存、関連 spec とそのリンク）。本文には spec・plan・tasks の番号（AC-、BR-、plan の節など）を書かず、規則を言葉で書く。
- **参照**：文書の名前と節で書く（`店舗画面の構成 第 4.5 節`、`バックエンドのアーキテクチャ 第 6.1 節`）。constitution の節の番号ではなく、細則の文書を指す。Markdown ではリンクにする。
- **用語**：複合語とカタカナ語で短く書き、「の」を重ねない（ログイン画面、ライセンス検査、有料版、ツール、ライブラリ）。言い換える語の一覧は `scripts/ci/doc-terms.json`（ng は CI で失敗、caution は文脈で決める）。「他の」「必要」と漢字で書く。日本語だけで書き、中国語の字や言い回しを混ぜない。
- **事実**：設定の値、既定値、必須かどうか、クラスの名前は、コードと照らしてから書く。理由が文書にもコミットメッセージにもないときは、推測で書かず利用者に聞く。

## 3. 進め方

1. 範囲と形を利用者と決める。大きな整理は、先に計画（置き場所、節の構成、移す先）を示して確かめる。
2. 書く。1 つの文書か、まとまりごとに利用者に見せ、指示があるまで commit しない。
3. 文書を移した、節の番号や見出しを変えたときは、第 4 節で参照を直す。
4. 確かめる。次がすべて通ること：
   - `node .local/agent/check-zh.mjs --all`（マシンに固有の検査。あれば流す）
   - `node scripts/ci/doc-refs.mjs`（Markdown のリンクと、`<文書の名前> 第 N 節` の参照。CI の docs.yml でも流す）
   - `node scripts/ci/doc-terms.mjs` と `--caution`（使わない語と、文脈で言い換える語。caution で出た語は、言い換えたほうが読みやすければ直す）
   - コードのコメントを直したら、フロントは `pnpm lint`、バックエンドは `./gradlew check`
5. commit を分ける：文書のまとまりごとに 1 つ、参照の直しは最後に 1 つ。spec の外の作業はタスク番号を付けない。push は利用者の許可を得てから。

## 4. 参照の直し

| 参照 | 直し方 |
|------|--------|
| Markdown のリンク | `node .claude/skills/docs/fix-links.cjs 旧パス=新パス ...`（切れたリンクだけを、移した先に直す） |
| コード・skill・CI・script の中のパス | `git grep` で旧パスを探して置き換える |
| 節の番号（`<文書の名前> 第 N 節`） | 旧番号から新番号への表を作って置き換え、置き換えた行を読み直す。番号が 2 回付け替わらないよう、1 回で流す。`doc-refs.mjs` は、ない節を指す参照だけを見つける（番号が残っていて意味の違う節を指すものは見つけない） |
| 見出しの名前（`「他のモジュールへの公開」` など） | 見出しを変えたら、`git grep` で引用を探して直す |

- 適用済みのマイグレーションと seed の SQL は直さない（Flyway の checksum が変わり、既存の DB で起動に失敗する）。
- `docs/specs/` の完了した文書は、リンクのパスだけを直す（開発の進め方 第 1.4 節）。
- コードが多く引用している文書の名前（`管理画面の構成` など）は、見出しを変えずに残す。

## 5. 落とし穴

- Bash の heredoc では `\\` が `\` になり、正規表現が壊れる。script は Write で書く。
- Windows では、`node_modules` のある worktree を消すと、パスが長すぎて失敗する。`git -c core.longpaths=true` か、PowerShell の `\\?\` 付きのパスで消す。
