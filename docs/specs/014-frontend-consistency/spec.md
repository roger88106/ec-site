# Spec 014：書き方の統一（フロント）

ステータス：確定

## 1. 背景と目的

spec 010 の後の全体のレビューで、店舗画面・管理画面のコードと書き方の規則（[フロントの書き方](../../rules/frontend-coding.md)、[フロントのアーキテクチャ](../../design/frontend-architecture.md)）の食い違いと、新旧の spec での書き方の違いが見つかった。

- 金額・日時・税額・郵便番号の整形が、2 つの画面にそれぞれあり、共有パッケージにない。日時の整形は、2 つの画面で実装が違う。管理画面は日本時間のオフセットとロケールをハードコードしている。
- 2 つの画面で同じ文言がそれぞれの文言ファイルにあり、共有の文言には管理画面だけで使う文言がある。
- 店舗画面の注文表示のファイルに、整形・列挙の表示名・状態の判定・数量の選択肢が集まり、注文と関係のない機能からも使われている。列挙の表示名の置き場所は、管理画面の中でも 3 通りある。
- URL のページ番号の読み取り、UUID・日付の形の判定、店舗画面のサーバーアクションの 401 の扱い、小さな UI の形が、spec ごとに書き換えられている。
- 共有パッケージの UI のコンポーネントに、片方の画面だけで使うものがある。
- 文言をモジュールの読み込み時に取得して定数にしている箇所、店の名前とページの題名をハードコードしている箇所、文言をキーで参照する箇所のコメントの漏れがある。
- 契約から書き出した定数がある値を、画面で数値をハードコードしている箇所がある。TypeScript の版と型チェックの設定が、パッケージで違う。

spec 012 で、書き方の統一で変更する箇所のテストを追加した。本 spec は、既存のテストを変えずに通すことを「振る舞いが変わっていない」の根拠にして（[MVP の完成までの一覧](../mvp.md) 第 2 節）、フロントを規則にそろえる。今のコードの書き方のほうが規則より良いときは、規則を修正する。

本 spec は**整理の spec**（[文書の記号と番号](../../rules/notation.md)）。消費者・運営者に見える振る舞いを変えない。

## 4. 目的と完了の条件

### DS-42 2 つの画面で同じ整形と文言が、共有パッケージの 1 か所にある（D / P1）

- **DC-143** 金額、価格（税込と税抜）、日時、税額、郵便番号の整形は、共有パッケージにそれぞれ 1 つずつあり、2 つの画面はそれを使う。画面に表示される文字は今と同じ。
- **DC-144** バリアントの軸の値の並べ方は、各画面で 1 か所にある。2 つの画面で同じ形になるなら共有パッケージに置く。区切りの文字が画面で違う箇所は、違いを残す。
- **DC-145** 日時の整形と日付の変換は、ロケールとタイムゾーンを共有のロケールの設定から取得する。日本時間のオフセット（9 時間、`+09:00`）と、他のロケールをハードコードしない。
- **DC-146** 2 つの画面で同じ文言は共有の文言にあり、共有の文言には片方の画面だけで使う文言がない。共有の文言に置く基準を、フロントの書き方 第 7.1 節に書く。

### DS-43 処理とコンポーネントの置き場所が規則に合い、重複がない（D / P1）

- **DC-147** 店舗画面の注文表示のファイルを、役割（整形、列挙の表示名、注文の状態の判定、数量の選択肢）ごとに分け、それぞれ規則（フロントの書き方 第 1 節）に合う場所に置く。価格の整形のファイルは、DC-143 の整形にまとめる。
- **DC-148** 列挙の表示名の置き場所が、各画面で 1 つの決まりに従い、その決まりを各画面の構成の文書に書く。管理画面の、共有パッケージと同じ名前のファイルをなくす。
- **DC-149** URL のページ番号とクエリの値の読み取りは、各画面で 1 か所にある。UUID と日付の形の判定は、共有パッケージの 1 か所にある。
- **DC-150** 店舗画面の会員の操作のサーバーアクションで、401 でログイン画面へリダイレクトする処理と、成功の後の移動が、共通の関数にまとまる。その使い方を店舗画面の構成の文書に書く。
- **DC-151** 複数の箇所で同じ形の小さな UI（ラベル付きのチェックボックス、商品の画像かその代替アイコン、「全て」とカテゴリの字下げの選択肢）は、1 つのコンポーネントにまとまる。
- **DC-152** 出荷の登録のフォームが他のフォームと違う送信方法を使う理由を、コードに書く。Enter で送信しない振る舞いは変えない。
- **DC-153** 共有パッケージの UI のコンポーネントは、2 つの画面で使うものだけ。片方だけで使うものは、その画面の UI のコンポーネントの置き場所に移す（フロントの書き方 第 5.1 節）。テーマの CSS の、片方だけで使う値の扱いは plan で決める。
- **DC-154** 共有パッケージの、契約の制約を書き出す script の置き場所が、フロントの書き方 第 5.1 節と合う（規則に追加するか、移す）。

### DS-44 文言の扱いが規則に合う（D / P2）

- **DC-155** モジュールの読み込み時に文言を取得して定数にする箇所がない。この規則をフロントの書き方 第 7.1 節に書く。
- **DC-156** 店の名前とページの題名（管理画面の HTML の題名を含む）は、文言ファイルにある。
- **DC-157** フロントの書き方 第 7.1 節に、言語に依らない入力例（`+10 / -3` など）はハードコードしてよいと書く。地域で形の変わる入力例（電話番号など）は、今は日本だけを扱うのでハードコードしてよいが、地域を追加するときに文言に移す、と合わせて書く。
- **DC-158** 文言をキーで参照する箇所に、表示する内容のコメントがある（コメントの書き方 第 6.1 節）。漏れを CI の検査で検出する。
- **DC-159** 文言ファイルの、句点の後の余分な空白をなくす。

### DS-45 契約の定数と依存の設定がそろう（D / P2）

- **DC-160** 契約から書き出した定数がある値（カテゴリの深さの上限、一覧の件数の上限）を、画面で数値をハードコードしない。
- **DC-161** TypeScript の版が、店舗画面・管理画面・共有パッケージでそろう。厳密な型チェックの設定を、3 つで明示する。
- **DC-162** 使っていない依存がない。

## 6. 非機能要件

- **DN-18** 既存のテスト（バックエンド、店舗画面、管理画面、E2E）が通る。テストのコードの変更は、次だけにし、検査（テストの実行方法 第 4 節）で確認する。それ以外を変えないと通らない箇所は、振る舞いを変えているので、本 spec で行わず、振る舞いを変える spec に移す。
  - 本番のファイルの移動と名前の変更に伴う import と名前
  - テストを、中身を変えずに別のファイルへ移すこと。本番の関数を共有パッケージへ移す・ファイルを分けるときに、テストも本番のファイルと同じディレクトリへ移すため（2026-10-19 利用者）。検査をこの移動に対応させる
- **DN-19** API の契約、バックエンド、画面の URL、画面に表示される文字と見た目を変えない。DC-159 の空白の修正は除く。
- **DN-20** CI の全体が 10 分以内のまま終わる（spec 011 の DC-85）。

## 7. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| 画面の操作の可否を、画面で業務の規則から推測せず、API の応答のフラグで受け取る（取消の申請が却下されたか、取消の時に在庫を戻すか聞くか など） | 016（API の契約を変え、テストの API の応答の例も変わる） |
| エラーのコードを契約に入れる、都道府県の表、画像の形式・大きさ・枚数の制約を契約に入れる | 016 |
| 注文の手続きの入力のエラーを、画面の文でなく API の文で返す（上限値を文言に書かない） | 016（画面に出る文が変わる） |
| 管理画面の IdP の設定が足りないときにビルドを失敗にする、店舗画面のホストの信頼と追加の設定の置き場所 | 015 |
| 会員のカートの操作の前の、カートの ID を取る呼び出しを減らす | 行わない（効率の問題で、API の変更が必要になる） |
| テストのコードを書き方の規則にそろえる | MVP の後（spec 012 の Non-goals） |
