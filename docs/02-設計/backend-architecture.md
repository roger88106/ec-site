# バックエンドのアーキテクチャ

[constitution](../constitution.md)の「バックエンドのアーキテクチャ」から「データとファイル」まで、「認証・認可」、「外部連携」の細則。コードの書き方は [バックエンドの書き方](../05-開発規則/backend-coding.md)、モジュールごとの設計は `docs/02-設計/<モジュール>.md` にある。

## 1. モジュラーモノリス

Spring Modulith でモジュールに分ける。デプロイ単位は 1 つ。

モジュールと責務の一覧は[用語集](../03-機能仕様/glossary.md)の「モジュール」にある。店舗モジュール（`storefront`）は、C 側 API で複数モジュールの結果を合成する参照専用の層である ※1。

※1：C 側で複数モジュールを組み合わせるときの循環依存を避けるため。B 側は合成モジュールを作らず、管理画面が複数の API を呼んで組み合わせる。

各モジュールのレベル（「モジュール内のアーキテクチャレベル」）と理由は、`docs/02-設計/<モジュール>.md` の冒頭にある。

モジュールが外に公開するもの：

| 公開 | 使い方 |
|------|--------|
| `api/` | 同期の呼び出し。呼ぶ側が必要とする形で作り、呼ぶ側は腐敗防止層（`XxxDirectory`）で包む |
| `event/` | 非同期の通知。Spring Modulith のイベント永続化（AFTER_COMMIT） |

- モジュール間の依存は `package-info.java` の `allowedDependencies` で宣言し、`ModulithTest` で検証する。
- モジュールの追加・統合・分割は、先に本書、`docs/02-設計/` と `docs/03-機能仕様/` を修正する。

## 2. モジュール内のアーキテクチャレベル

複雑さに応じて選び、選んだ理由を `docs/02-設計/<module>.md` に書く。層とパッケージの名前はどのレベルでも同じ（「層とパッケージ」）。

| レベル | 構成 | 向く場面 |
|--------|------|----------|
| A. フル | DDD + Clean Architecture + CQRS | 不変条件や状態機械が複雑 |
| B. 簡略 | DDD を簡略にした構成 | ルールが単純、または参照のみ |
| C. イベントストア | Event Sourcing ※2 | 状態の変化の履歴に価値がある |

※2：採用する前に、plan で保存方式・スナップショット・read model を説明し、本書を修正する。

レベル A の中身：

- 依存の向き：presentation → application → domain ← infrastructure（各層が依存してよい層は「層とパッケージ」の表のとおり）。
- Repository の port は `domain/<集約>/port/` に置く。command と query の service・Repository を分ける（CQRS）。
- ドメインオブジェクトは jMolecules で明示し（`@AggregateRoot`、`@ValueObject`、`@Identity`）、状態は集約のメソッドで変更し、ドメインイベントを登録する。
- 永続化は `toSnapshot()` で書き出し、Factory で再構築する。application が投げる例外は `BusinessException` / `SystemException` だけ。
- 例外：状態を DB の更新の条件で守るモジュールは、集約のクラスを持たなくてよい ※3。今は在庫だけ。

※3：在庫数の並行の更新を、集約を読んで書き戻さずに、DB の差分の加算と条件で守るため（[在庫モジュール](../03-機能仕様/inventory.md)）。このとき、状態を集約のメソッドで変える規則と、集約を jMolecules で明示する規則は当てはまらない。

レベル B の中身：

- domain は振る舞いの少ない型でよく、Spring などに依存してよい。集約ごとのパッケージは作らず、port は全て `application/port/` に置く。
- CQRS は採用しない。`application/model/` は必要なときだけ作る。
- クラスが多いときは、用途で domain を分けてよい（`domain/<用途>/`。reporting の `domain/snapshot/` と `domain/sales/`）。

### 2.1 層とパッケージ

モジュールの構成は次のとおり。

```
module/<モジュール>/
├── api/                公開の同期の API（@NamedInterface("api")）
├── event/              公開のイベント（@NamedInterface("event")）
├── presentation/       API の入口（生成した interface の実装）と、API の型への変換
├── application/        use case（@Transactional はここ）
│   ├── model/          command・query・view
│   └── port/           application が使う port（参照の Repository、他のモジュールの Directory）
├── domain/             業務の型。エラーの定義（<モジュール>ErrorCode。集約ごとに分けてよい）
│   └── <集約>/         集約、vo/（値）、port/（Repository、domain が使う Directory）
└── infrastructure/     port の実装
    ├── <モジュール>Config  設定のクラス（設定の値の型を有効にする、domain の部品を Bean にする。バックエンドの書き方の「設定の値の型」）
    ├── persistence/    jOOQ の Repository と、それが使うクラス
    ├── directory/      他のモジュールの api を呼ぶ Directory の実装（腐敗防止層）
    └── <外部>/          外部の仕組み（storage、converter、cache など）
```

層ごとの、依存してよい先：

| 層 | 依存してよい先 |
|----|----------------|
| api・event | application、domain、common |
| presentation | application（`port/` を除く）、domain（エラーの定義と値の型）、common |
| application | domain、common、event（自分のモジュールのイベントを発行する。他のモジュールのイベントを購読する） |
| domain | common、自分のモジュールの event（レベル A は Spring・jOOQ にも依存しない） |
| infrastructure | application の port と model（port が返す view）、設定の値の型（設定のクラスが有効にしたもの）、domain、common |
| common | モジュールに依存しない |
| config | common。モジュールに依存しない |

## 3. モジュール間の連携

- 同期の呼び出しは、参照か、すぐに結果が必要な場面だけ。それ以外はイベント（名前は過去形。例：`OrderShipped`）。
- イベントは集約が記録し（`registerEvent`）、リポジトリが保存の後に送り出す。集約を持たないレベル B のモジュールは、application の service が送り出してよい。理由：保存に失敗したときにイベントだけが出ないようにし、domain を送り出しの仕組みから切り離すため。
- 他のモジュールのテーブルを読み書きせず、外部キーも張らない。
- モジュールをまたぐ整合性は結果整合。強い一貫性が必要な所は spec に書き、plan で方法を決める。

## 4. C 側と B 側

- 同じドメインモジュールを共有し、presentation で分ける（`/api/store/**`、`/api/admin/**`）。Controller と Request / Response は共有しない。
- バックエンドを 2 つに分けるのは、スケール・デプロイの頻度・セキュリティの境界が明確に異なってから。

## 5. 水平スケール

同じアプリを複数のインスタンスで動かせるように作る。

| 項目 | ルール |
|------|--------|
| 状態 | リクエストをまたぐ状態をメモリに持たない。HTTP セッションとローカルディスクを使わない |
| 排他 | JVM の中のロック（`synchronized` など）を使わず、楽観ロック・条件付き更新・DB のロックで制御する |
| ローカルキャッシュ | インスタンス間で差があってもよいデータだけ。必ず TTL を付ける |
| 定期ジョブ | 分散ロック（ShedLock、PostgreSQL のテーブル）で、同じジョブを同時に 1 インスタンスだけで実行する。業務の正しさは、分散ロックに頼らず、行ロックと冪等な状態の遷移で保つ ※4 |
| 片付け | 不要になったデータ（期限切れ、処理の済んだもの）は、保存期間を過ぎたら、データを持つモジュールの定期ジョブで削除する（BR-38）。対象は下の「片付け」 |
| 時刻で切り替わるデータ | 定期ジョブで書き換えず、適用期間を持たせて参照時に判定する（予約公開、税率など） |
| 時刻 | `Clock` を注入して取る。ドメインには `Instant` を引数で渡す |
| イベント | at-least-once を前提に、リスナーを冪等にする。失敗したイベントは「イベントの再発行」 |
| 設定 | 環境変数で上書きできる。秘密情報をリポジトリに置かない |
| 運用 | ログは標準出力に JSON。liveness / readiness、graceful shutdown。コンテナイメージでビルドする |
| マイグレーション | アプリの起動と分け、デプロイごとに 1 回（ローカルは起動時でよい） |

※4：ロックの期間が切れた後に前の実行が残っていると、ジョブが重なることがある。ロックは無駄な重複を減らすためのもの。

### 5.1 片付け

- 他の操作が読み書きする行は、件数の上限ずつ分けて削除する。
- 保存期間とジョブの間隔は設定で変えられる。間隔の既定は 1 時間（[環境変数](../06-手順書/environment.md)の「バックエンド」）。
- 保存期間は、データを使う業務の期限と、個人情報（イベントの記録には購入者のメールアドレスが入る）を長く持たないことから決めた（BR-38）。

| データ | 持つ所 | 保存期間の起点 | 既定の保存期間 |
|--------|--------|----------------|----------------|
| 処理の済んだイベント | `config`（Spring Modulith の記録） | 処理を終えた時刻 | 7 日 |
| 引当 | 在庫 | 期限 | 1 日 |
| 注文手続き | 注文 | 期限（注文になったものも削除する） | 1 日 |
| カート | カート | 期限（最後の変更から 30 日） | 0（期限で削除する） |

### 5.2 イベントの再発行

- 処理に失敗した（未完了の）イベントは、定期ジョブが 1 分ごとに、5 分より前のものを再発行する。起動時の再発行は使わない。
- 注文と在庫の増減は、同じトランザクションで呼ぶので、イベントを使わない（[注文モジュール](../03-機能仕様/order.md)）。
- 処理の回数（発行の時の 1 回と再発行の回数）が上限（既定 60、約 1 時間）に達したイベントは、再発行しない。失敗の種類では分けない（繰り返しても結果が変わらない失敗は、リスナーが吸収する）。
- 上限に達して最後の処理に失敗したイベントは、次の回で止めた印（処理の回数を上限より 1 つ多くした値）を付け、種類・イベント ID・リスナー・処理の回数をエラーのログに 1 回だけ出力する。イベントの中身は出力しない。
- 未完了のイベント（止めたものを含む）と止めたイベントの件数は、再発行のジョブが再集計してメトリクスで公開する（収集のたびに DB を読まない。名前は[共通コード・ログ・可観測性](common.md)の「メトリクスと死活監視」）。値が更新されるのはジョブを実行したインスタンスだけなので、インスタンス間の最大値で確認する。
- 止めたイベントは処理を終えていないので、片付けで削除されない。ログとメトリクスで検知し、原因を修正してから、データベースでイベントの記録の処理の回数を上限より小さく戻す（次の回で再発行される）か、不要なら記録を削除する。上限を上げても再発行される。
- 印はイベントの記録の表（Spring Modulith のもの）に直接書く。Spring Modulith を上げるときは、処理の回数と状態の意味が変わっていないかを確認する（イベントの記録のマイグレーションの注記）。

## 6. データとファイル

### 6.1 永続化

| 項目 | ルール |
|------|--------|
| データアクセス | jOOQ。生成コードはコミットしない |
| schema | モジュールごとに分ける。各モジュールは自分の schema の jOOQ の生成クラスだけを使う（ArchUnit で確認する） |
| 識別子 | UUID |
| 時刻 | UTC の `timestamptz` |
| 同時の更新 | `version` カラムで楽観ロック |
| 金額 | 円単位の整数。値オブジェクト `Money`（`float` / `double` は使わない） |
| 論理名 | テーブルとカラムに、DB のコメントで日本語の論理名を付ける ※5 |
| 列挙 | 列挙の名前を文字列として保持し、取りうる値を CHECK 制約で限る。制約と列挙の一致、制約のない列挙の列がないことを統合テスト（`EnumColumnConstraintTest`）で確認する。列挙の列を追加したら、そのテストの対応の表にも追加する |

※5：用語集に合わせ、論理名だけを書く（補足はマイグレーションの SQL のコメント）。コメントがないことを統合テストで検出する。

業務番号（品番、注文番号など人が使う番号）と識別子を分ける：

- 業務番号は、主キー・他のデータからの参照・イベント・キャッシュのキー・API の URL に使わない（画面の URL には使ってよい）。一意な属性として持つ。
- 画面・API で変えられない番号でも、DB を修正すれば付け替えられるようにする。
- 過去の記録には、参照ではなくその時点の値を写して持つ。

### 6.2 Flyway

- スキーマの正本は Flyway のマイグレーション（`backend/ecsite/src/main/resources/db/migration/`）。
- 新しいモジュールの schema は、そのモジュールの最初のマイグレーションで作る。最初の 4 つ（common、tax、catalog、inventory）だけは、1 つのマイグレーション（`common_create_schemas`）で作った。schema の名前はモジュールの名前にする。例外は `order` の schema の `ordering`（`order` が SQL の予約語のため）。
- コミット済みのマイグレーションは変えず、新しいバージョンを追加する。バージョンはタイムスタンプ（例：`V202610081400__catalog_create_product.sql`）。
- jOOQ のコード生成と統合テストは、Testcontainers の PostgreSQL に Flyway のマイグレーションを適用して行う。
- 開発と E2E の seed は `db/seed/` に置き、ローカルと E2E の profile でだけ適用する（[使い分け](../../backend/ecsite/src/main/resources/db/seed/local/README.md)）。

### 6.3 ファイル保存

- Amazon S3 互換のオブジェクトストレージ（ローカルと CI は SeaweedFS）に置き、DB にはキーだけを持つ。ストレージは port の後ろに置く。
- アップロードは署名付き URL で、ブラウザーからストレージへ直接送る（バックエンドはファイルを中継しない）。

### 6.4 値の置き場所

値は、誰が・いつ変えるかで置き場所を決める（BR-33）。

| 値 | 置き場所 | 例 |
|----|----------|-----|
| デプロイせずに運営者や外部のデータで変わる業務のデータ | データベース（マスターデータなど） | 税率、都道府県、市区町村、郵便番号 |
| 環境ごとに違う、デプロイに関わる値 | 環境変数（設定。[バックエンドの書き方](../05-開発規則/backend-coding.md)の「設定の値」） | 接続先、鍵、mock フラグ、ポート |
| 変えるとコードも変わる業務の規則 | バックエンドの domain の定数 | 分類の深さ、画像の枚数、氏名の文字数 |

- どの値も、正となる所は 1 つにする。画面は値を書かず、API の契約（生成した型と制約）か応答から得る（[フロントの書き方](../05-開発規則/frontend-coding.md)の「API」）。
- domain の定数を API の契約にも書くとき（入力の長さ、枚数の上限など）は、両者が一致することを契約のテストで確認する。エラーの文に入れる数は、定数から差し込む（[バックエンドの書き方](../05-開発規則/backend-coding.md)の「エラーは `XxxErrorCode` と `BusinessException`」）。

## 7. 認証・認可

### 7.1 認証の方式

| 項目 | ルール |
|------|--------|
| 方式 | IdP（Keycloak）に委譲する（登録、ログイン、メールの確認、パスワードの再設定）。画面は OIDC（OAuth 2.0 の認可コードフロー）でログインし、API は OAuth 2.0 の Resource Server として access token（JWT）を検証するだけ |
| アカウント | 消費者と運営者は別の realm。共有しない（運営者が買い物をするときは消費者のアカウントを別に作る） |
| 会員の情報 | 本人の識別（ログイン ID、パスワード）は IdP、購入に使う情報（届け先など）は EC。token の subject で対応づける |
| IdP の設定 | realm・client・role をファイルに書き出してリポジトリに置く（秘密情報は置かない） |
| CSRF | API はセッションと Cookie を使わず、token を `Authorization` ヘッダーで受け取るので、Spring Security の CSRF の対策を無効にする。ブラウザーが自動で送る資格情報がないため、CSRF は成り立たない。店舗画面の Cookie は、店舗画面のサーバーだけが読む（[フロントのアーキテクチャ](frontend-architecture.md)） |
| 行わないこと | 会員登録を始めたのと別のブラウザーで確認メールのリンクを開いたとき、ログインした状態にしない（リンクを持つ人がログインできてしまうため。IdP の画面から店舗に戻り、ログインする）。運営者のアカウントと職務を管理する EC の画面は作らない（IdP の管理画面を使う） |

### 7.2 業務のコードとの境界

- domain と application は Spring Security の型に依存しない。呼び出し元は値（会員 ID、運営者の ID と氏名の写し）で渡す。
- 管理 API の権限は endpoint ごとに `resource:action`（例：`product:write`）で spec に書く。運営者の realm の role として token に載せ、読む処理は 1 か所にまとめる。
- 職務は、権限をまとめた IdP の role（複合の role）である。職務を追加・変更するときは、IdP の設定（realm の設定のファイル）だけを変え、EC のコードは変えない（BR-12）。
- ログインしていればよい操作（自分の権限の一覧）は、権限の代わりに `authenticated` と書く。管理画面はメニューと画面を自分の権限の一覧で出し分け、token を自分で読まない。
- `/api/admin/**` は運営者の realm、`/api/store/**` は消費者の realm の token だけを受け付ける。
- 店舗 API の token の要否も、契約（`store.yaml` の `security`）から起動時に読む。
  - `memberToken` だけを書いた操作は、token が必要。
  - `memberToken` と `{}` を並べた操作（token は任意）と、`security: []` の操作（公開）は、token なしで使える。公開の操作は `security: []` で明示する。
  - `security` を書かない操作があると、起動に失敗する。失敗のメッセージは、操作のメソッドとパスを含む。理由：書き忘れた操作を、公開の操作として受け付けないため。
- 認可は既定で拒む。契約にない店舗 API・管理 API の操作は拒み、それ以外の URL は、通知（`/api/webhooks/**`）・mock（`/mock-payment/**`、`/mock-carrier/**`）・運用（`/actuator/**`）のエンドポイントだけを許す（BR-32）。拒むときは 401（認証のあるリクエストは 403）。

### 7.3 公開ネットワークへのデプロイの前提

ローカルと CI の設定のままでは IdP と secret が守られない。デプロイ先を決めるときに、次も決める。

- IdP の本番の構成：管理画面の保護、realm の設定の反映方法、client の戻り先と店舗の URL、メールの送信元
- secret の管理：client の secret、店舗画面の Cookie の鍵（ローカル用の値を使わない）
- HTTPS（店舗画面の Cookie は本番で `Secure`）
- 運用ポート（既定 9080。死活監視とメトリクス）を外に出さない。業務ポート（8080）だけを公開する
- mock フラグ（`ecsite.<モジュール>.mock.enabled`）を立てない。ローカル・E2E・Stripe の sandbox の設定ファイルは本番の jar に入らない（「外部連携」）
- 店舗画面を公開する URL（`AUTH_URL`）を渡す。ログインとログアウトの戻り先は、この URL から作る（[店舗画面の構成](apps/store.md)の「ログイン」）
- 管理画面の本番ビルドに、本番の IdP の値（`VITE_OIDC_AUTHORITY`、`VITE_OIDC_CLIENT_ID`）を渡す
- 注文とカートの URL の総当たりを防ぐ（入口でのレート制限など）。カートと注文の画面は、推測できない ID を知っている人だけが使えるようにしている
- 決済サービスと物流サービスの通知のエンドポイント（`/api/webhooks/*`）を公開する URL と、エンドポイントのレート制限を決める。認証はなく、署名で確認する（「外部連携」）
- ログインせずに作るカートの作成の回数を、入口（リバースプロキシなど）で制限する
- 確定していないアップロードを削除する期限を、アップロードのバケットのライフサイクル規則で設定する（ローカルは 1 日）
- メトリクスにアラートを設定する。少なくとも、止めたイベントの件数（`ecsite.events.stopped`。「水平スケール」）
- トレースを送るなら、`MANAGEMENT_TRACING_EXPORT_ZIPKIN_ENABLED` を true にし、送信先（`MANAGEMENT_TRACING_EXPORT_ZIPKIN_ENDPOINT`）を渡す。既定は送らない（[環境変数](../06-手順書/environment.md)）
- 配布物に、第三者のライセンスの告知のファイルと部品表（SBOM）を付ける

## 8. 外部連携（決済・物流）

- 外部サービスは port の後ろに置き、外部の型やエラーコードを domain / application に持ち込まない。
- 外部サービスと接続するモジュールを加えるとき、外部サービスを変えるときは、[全体構成](overview.md)の「モジュールと外部サービス」の図と表も修正する。テストが確認するのは、図のモジュールがコードにあることだけで、描き忘れは見つけられない。
- 無料の sandbox があれば使い、なければ内部の mock にする。同じ port を実装し、mock は外部サービスごとの mock フラグ（`ecsite.<モジュール>.mock.enabled`）を立てたときだけ使う。フラグがなければ本番の実装を使い、その設定が足りなければ起動に失敗する（BR-30）。mock の挙動（成功、失敗、タイムアウト、遅延したコールバック）はテストから操作できるようにする。テストだけで使う操作は本番の mock に置かず、テストで共有するソース（`src/testFixtures`）の、mock を包む実装に置く。
- ローカル・E2E・Stripe の sandbox の設定ファイル（mock フラグとローカル用の秘密情報を持つ）は、本番の jar に入れない。Gradle の `checkBootJar`（`check` から呼ぶ）で確認する。
- ローカルの profile を本番で指定したことを、起動のときに検出して停止する処理は設けない。本番の jar に設定ファイルがないので、指定しても読まれない。
- 失敗したときの振る舞い、リトライと冪等性、コールバックの検証方法は spec に書く。
- 外部サービスの失敗は、infrastructure の実装が次の表で分ける（BR-39）。外部サービスのエラーは、エラーコード（種類は外部サービスのエラー）を指定して `SystemException` を投げる（共通の例外ハンドラー（`GlobalExceptionHandler`）が 502 にし、warn のログを出力する。[API の規約](../05-開発規則/api-conventions.md)の「HTTP ステータス」）。外部の例外の型は外に出さない。

| 外部サービス | 外部サービスのエラー（502） | 入力の誤り（400） | 予期しないエラー（500） |
|--------------|-----------------------------|-------------------|-------------------------|
| 決済（Stripe） | 接続できない・時間内に応答がない、Stripe の側の障害、回数の制限（`PAYMENT_GATEWAY_UNAVAILABLE`） | — | 認証・権限・要求の誤り（設定かコードの誤り） |
| 画像の変換（imgproxy） | 接続できない・タイムアウト、502・503・504（`IMAGE_SERVICE_UNAVAILABLE`） | imgproxy が返した 4xx と 500（ファイルを読めない。`IMAGE_CONVERSION_FAILED`）※6 | URL の署名の失敗 |
| ファイル保存（S3） | 接続できない・時間内に応答がない、5xx（`IMAGE_SERVICE_UNAVAILABLE`） | — | 5xx でない失敗（権限、バケットがないなど） |

※6：imgproxy は壊れたファイルに 500 を返すので、imgproxy が応答したらファイルの問題とする。imgproxy 内部の障害も 500 なので、その場合はファイルが壊れていないかの確認を求めるメッセージになるが、許容する（応答はログに残す）。

- 外部サービスの呼び出しを、自動で再試行しない（決済サービスの SDK が持つものを除く）。サーキットブレーカーも置かない。MVP の規模では、画面からの再試行で足りるため。
- 外部サービスを呼ぶ client には、タイムアウトを設定し、タイムアウトを超えたら外部サービスのエラーにする（BR-40）。理由：利用者のリクエストの中で呼ぶので、タイムアウトがないとリクエストが長く止まるため。
- 上限の設定と既定値は[環境変数](../06-手順書/environment.md)の「バックエンド」（Stripe、ファイル保存、画像の変換）。imgproxy への接続の上限（5 秒）は設定で変えない。
