# plan・tasks の照合と文書のレビュー

skill `review` の手順 7〜10 の詳細とひな形。本書の手順 1〜4 が、skill の手順 7〜10 に当たる。

## 手順

1. plan と tasks を照合する。plan と tasks を、それぞれ書き終えたときに行う。日本語だけのサブエージェント（汎用）に、spec の各 AC・DC と plan の決定（tasks のときは、各段階の完了の条件と各タスク）を 1 件ずつ照合させる。tasks では、次の 4 点も見させる。(1) 完了の条件が spec の AC・DC・DN より厳しい・緩いもの。(2) 前のタスクが後のタスクで作るものを使う順序。(3) 共有する部品（共通の関数、生成するファイル、共通の設定、AC 一覧など）を変えるタスクと、それを使うタスクの間の、書いていない依存。(4) 並行する spec との変えるファイルの重なりと実装の順序が、plan（規模 M は spec の tasks）に書いてあるか。spec の第 1 節の環境の前提（Claude Code や OS の動き）については、文書の記述によるものか、動かして確認したものかを書き分けているかも見させる。結果は表（AC・DC、plan の節またはタスク、合っている・抜けている・食い違う、説明）で受け取る。抜けと食い違いは、確認の前に修正する。
   完了の条件：全ての AC・DC が表にある。
2. 文書をレビューする。日本語だけのサブエージェント（汎用）に、書き方の見本（[エージェントの作業フロー](../../../docs/rules/subagents.md)、[spec 018 の plan](../../../docs/specs/archive/mvp/018-docs-and-tools/plan.md)）と [文書の言い回しと論理の規則](../docs/tech-writing.md) と、`node scripts/ci/ja-text.mjs --warning` で出力した warning の一覧（対象の文書の行だけ）を渡し、不自然な言い回しを候補として挙げさせる。warning の文は機械が示した候補なので、修正が必要かを読んで判断させる。結果は表（ファイル、行、今の書き方、修正案、理由）で受け取り、spec 担当のセッションが採否を判定する。spec・plan・tasks を書き終えたときと、spec の最後に行う。
   完了の条件：全ての候補の採否が決まっている。
3. 中国語で指示する環境では、校閲役 `ja-proofreader`（[定義](../../agents/ja-proofreader.md)）に、変えた日本語を読ませる。環境は、`git config --local --get ecsite.instructionLanguage` の値（なければ、作業ツリーごとの設定にある同じ名前の値。script の `readConfig` と同じ読み方）が `zh` かで決める（グローバルの設定は読まない。[中国語の混入を調べる](../zh-mixing/SKILL.md)）。日本語で指示する環境では行わない。
   - 対象：最後のレビューと pull request の前のレビューの差分にある、文書、コードのコメント、テスト名、コミットメッセージ。
   - 渡すもの：差分（`git diff` の出力、または対象のファイルと行の範囲）と対象のファイル名だけ。会話の要約と中国語の文は渡さない。指示の文は日本語だけで書く。
   - 結果は表（ファイル、行、今の書き方、修正案、理由）で受け取る。扱いは手順 2 と同じで、spec 担当のセッションが指摘を読んで採否を決め、結果を利用者に示す。
   完了の条件：全ての指摘の採否が決まっている。
4. 校閲役や他のレビューが見つけ、利用者が確認した型を、機械の検査に加える。加えるのは、利用者が型として確認したものだけで、指摘の一件ごとではない。
   - 加える先は原因で決める。日本語の書き方の規則に反する型（使わないと決めた語、文体。誰が書いても誤り）は、層 1 の `scripts/ci/ja-text.json`。中国語の混入（中国語の字・語・直訳）は、層 2 の `.claude/skills/zh-mixing/zh-mixing.json`（書き方は [中国語の混入を調べる](../zh-mixing/SKILL.md) の「一覧の直し方」）。同じ字・語を両方に置かない。
   - 複合動詞の崩れは、確定した語を `error` に加え、疑いを示す漢語を `style` の `compound` に加える。
   - 層 1 の項目の形は、`error` と `warning` が `{ "word", "use" }`（`error` は許す語 `allow` も書ける）。部分の一致が誤検出になる語は、`word` の代わりに `pattern`（正規表現の文字列。`u` フラグで使う）で書け、`examples` の `hit`（当たる例）と `miss`（当たらない例）を 1 つ以上ずつ必ず書く（テストが全ての例を確認する）。文体の型は `style` の閾値と、`scripts/ci/ja-text.mjs` の `findStyleWarnings` で扱う。層 2 には warning がなく、見つかれば失敗にする。
   - error と warning の分け方：error にするのは、リポジトリの全体（アーカイブした spec を除く）に当てて誤検出が 0 の型か、全ての誤検出を許す語（層 1 は `allow`、層 2 は `allow` の `{ "word", "file", "reason" }`）で除ける型だけである。
     それ以外は、文脈で正しいかが決まる型なので、層 1 の warning にする。層 2 には warning がないため、それ以外の型は層 2 に加えない。
   - 当てて数える：層 1 は、先に `warning` に加え、`node scripts/ci/ja-text.mjs --warning` で一覧にして誤検出を数える。error にするときは `error` に移し、`node scripts/ci/ja-text.mjs` の失敗が 0 になるまで、見つかった行を修正するか許す語を追加する。層 2 は、加えてから `node .claude/skills/zh-mixing/zh-mixing.cjs --force tracked` で全体に当てる。環境の印がなくても `--force` で調べられる。
   - 加えたら、それぞれの script のテスト（`node --test scripts/ci/ja-text.test.mjs`、`node --test .claude/skills/zh-mixing/zh-mixing.test.cjs`）と `bash scripts/ci/check-all.sh` が通ることを確認する。
   完了の条件：加えた型ごとに、error か warning かの理由と、全体に当てた誤検出の数が説明できる。

## 指示のひな形（plan・tasks の照合）

skill の手順 7（本書の手順 1）で使う。日本語だけで書く。tasks の照合では、＜tasks のとき＞の行を加える。

```
あなたは、spec と plan（＜tasks のとき＞と tasks）を照合する担当です。実装の過程は知らされていません。

## 対象
- spec：<パス>
- plan：<パス>
- ＜tasks のとき＞tasks：<パス>

## 観点
spec の各 AC・DC と、plan の決定を 1 件ずつ照合する。
＜tasks のとき＞spec の各 AC・DC・DN と plan の決定が、どのタスクで行われるかを照合する。各段階の完了の条件と各タスクの条件が、spec より厳しくないか・緩くないかを見る。前のタスクが後のタスクで作るものを使っていないかを見る。共有する部品（検査の script の共通の関数、生成するファイル、共通の設定、AC 一覧などの共有の文書）を変えるタスクと、それを使う・前提にするタスクの間に、依存に書いていない順序の制約がないかを見る（特に `[P]` のタスクの間）。
spec の第 1 節の環境の前提が、文書の記述によるものか、動かして確認したものかを書き分けているかも見る。

## 結果
<結果の書き先> に、次の表で書く。AC・DC を全て載せる。
| AC・DC | plan の節（＜tasks のとき＞タスク） | 判定（合っている・抜けている・食い違う） | 説明 |

- 判定の根拠は、spec と plan の本文に置き、出典（ファイル:行）を書く。出典のない理由は書かない。
- 他のファイルは変更しない。返すのは件数（合っている、抜けている、食い違う）だけ。
```

## 指示のひな形（文書のレビュー）

skill の手順 8（本書の手順 2）で使う。日本語だけで書く。

```
あなたは、日本語の技術文書のレビュー担当です。実装の過程は知らされていません。

## 対象
<新しく書いた、または変えた文書のパス>

## 見本
目指す書き方の見本：<見本のパス>
言い回しと論理の規則：.claude/skills/docs/tech-writing.md（1〜5 の表を当てはめる）
機械が示した warning の文：<対象の文書の行を抜き出した一覧。なければ「なし」>

## 観点
技術文書として不自然な言い回しを、候補として挙げる。見本の書き方に近づける。次の 3 つを見る。
- 和語の言い換え：技術文書で一般的な語に替える（規則の「用語」の表）。
- 論理、読む人の負担、中身のない言い回し、翻訳調の比喩と擬人化、冗長さ（規則のその他の表）。
- 機械が示した warning の文：「の」の連なり、長い文、読点の多い文、否定が続く文、複合動詞の崩れの疑いなど。文脈を読んで、修正すべきものだけを候補にする（「少し修正する」のような正しい日本語は候補にしない）。

## 守ること
- 意味、番号、節の番号、表の構成を変えない。
- 識別子、文書の題名、節の名前を変えない。
- プロジェクトの用語集の語を一般の語に替えない。
- 理由には出典（規則のファイル:行）を書く。出典のない理由は書かない。

## 結果
<結果の書き先> に、次の表で書く。
| ファイル | 行 | 今の書き方 | 修正案 | 理由 |

- 対象のファイルは変更しない。返すのは候補の件数だけ。
```
