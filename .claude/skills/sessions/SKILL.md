# セッションの運用

issue 担当のセッションと spec 担当のセッションの運用。役割の表は [エージェントの作業フロー](../../../docs/05-開発規則/subagents.md)の「役割と作業の流れ」、作業の形・profile・閾値・使用量を読む頻度は [作業の形と使用量](../../../docs/05-開発規則/resources.md)。ツールの名前は末尾の「ツールの補足」にだけ書く。

- 待機している予備のセッションに担当を渡すときは、[予備のセッションに担当を渡すメッセージ](handover.md)のひな形で送る。
- 作業ツリーのセッションが設定・定義・skill を読む場所は、[作業ツリーのセッションが読むもの](session-reads.md)。作業ツリーを作るとき、定義・skill・hook を変える spec を確認するときに読む。

## issue 担当のセッション

- 役割：起票と、spec 担当のセッションの起動。資源の配分。危険度が低い変更のマージ。`develop` の CI の見届け。ステップの終わりの集計と振り返り。
- 起動：利用者が開く。1 つだけにする。
- issue の本文とコメントの書き手は、[文書の書き方](../../../docs/05-開発規則/writing.md)の「本文の書き手」と、skill `docs` の「進め方」のとおり。
- 起票とコメントの投稿の前に、本文を校閲役に読ませる。対象と時点は、[docs-review.md](../review/docs-review.md)の手順 3。
- 待機：待機中は、通知を受けたときに処理を再開する。定期的な問い合わせはしない。
- 進行中の spec に範囲を加えるときは、spec 担当のセッションにメッセージで送り、加えた DC の番号を返事で受け取る。spec に反映されたことは、その DC の番号で確認する。理由：メッセージで送るだけでは、承認した修正が spec に入らないことがあるため。

### 他のセッションの成果物に問題があるとき

1. 原因を結論づける前に、成果物を作ったセッションにメッセージで聞く。聞くことは、使った skill、書かせたサブエージェント、モデル、指示。そのセッションがアーカイブ済みなら、その記録を読む。
2. 聞いた結果で原因を分け、修正する場所を決める。

   | 原因 | 修正する場所 |
   |------|--------------|
   | 手順どおりに作ったのに問題があった | skill の中身か校閲役 |
   | 手順を参照しなかった、または従わなかった | 規則を参照する経路 |
   | 規則がない | 規則を加える |

3. 利用者への報告では、確認した事実と推測を分けて書く。

理由：原因を推測で決めると、修正する場所を誤り、同じ問題が再発するため。

### 待機と監視の token を抑える

1. CI を待つときは、バックグラウンドの実行（「ツールの補足」の名前）でまとめて待ち、短い間隔で読み直さない。
2. spec 担当のセッションへの返事は短くし、判断に必要な事実だけを書く。
3. ステップの区切りで文脈を圧縮するか、新しいセッションにする（利用者が行う）。
4. 汎用の区分で動かす（[エージェントの作業フロー](../../../docs/05-開発規則/subagents.md)の「任せる作業とモデル」）。
5. spec 担当のセッションの終わりを待つときは、ターンを使わない待ち方（終わったら知らせる指定）を使い、問い合わせを繰り返さない。

## 資源の配分

issue 担当のセッションは、作業の形と profile、並行の数、特例の配分を決める。閾値に達して中断した spec 担当の再開も決める。従う規則は [作業の形と使用量](../../../docs/05-開発規則/resources.md)の「作業の形と profile の決め方」と「止める閾値」。

## spec 担当のセッションの起動と実装の開始

起動のメッセージに、開始の条件を書く。形：

> 利用者が確認対象を承認し、5 時間の使用量が x% 未満、週が y% 未満なら、問い合わせずに始め、開始を知らせる。

- x と y は、issue 担当のセッションが資源の配分から決める。
- 起動のメッセージに、文書の本文の書き手の指示（上の「issue 担当のセッション」と同じ）も入れる。
- 条件を満たさないとき、または渡されていないときの問い合わせは [開発の進め方](../../../docs/05-開発規則/workflow.md)の「実装を始める前の照合」。待つ間は token を使わない。返事がないときは、次に利用者か issue 担当のセッションから指示が来るまで始めない。
- 利用者が確認対象を承認したこと（通常の承認）は、開始の条件の材料である。条件を決めるのは issue 担当のセッション、条件を満たすかを判定して始めるのは spec 担当のセッション。
- 利用者が「今すぐ始めて」などと特例を明示したときは、開始の条件を適用せず、セッションの割り当ては資源の配分に従う。spec 担当のセッションが直接その特例を受けたときは、issue 担当のセッションに知らせ、返事を待たずに始める。
- 始めたら、[開発の進め方](../../../docs/05-開発規則/workflow.md)の「実装を始める前の照合」に進む。
- spec の最後のレビューと pull request の順と理由は [起票と記録の操作](../../../docs/05-開発規則/issues.md)の「アーカイブの操作」、push の時点は [開発の進め方](../../../docs/05-開発規則/workflow.md)の「push のタイミング」。

## セッションの間のメッセージ

名前でなく、セッションの識別子で送る。名前は重なったり変わったりして、別のセッションに届くことがある。

## 遠隔操作

利用者が外にいてセッションを操作できないときに、遠隔操作を有効にする。待機中のセッションには、有効にする前に短いメッセージ（「何もせず、待機中と返して終わる」）を送り、次のターンを開始する状態にしてから有効にする。待機中のままでは有効にできない。

## 単線のときの兼務

単線の定義と区分は、[作業の形と使用量](../../../docs/05-開発規則/resources.md)の「作業の形と profile の決め方」。兼ねるときも、起票と spec の作業の規則は変えない。

兼務のときは問い合わせる先がない。利用者が確認対象を承認したら、自分で使用量を読んで開始の条件を判定し、開始を追跡の issue に書く。

## マージの後

- `develop` の push の CI を、issue 担当のセッションがバックグラウンドの実行（「ツールの補足」の名前）で見届ける。失敗したら、他の pull request のマージを止めてすぐに起票し（[起票と記録の操作](../../../docs/05-開発規則/issues.md)の「起票」の急ぐ作業）、直るまで次のマージをしない。
- `.claude/`（skill、サブエージェントの定義、設定）を変えた pull request をマージしたら、issue 担当のセッションが、メインの作業ツリーの `develop` を最新にする。理由：メインの作業ツリーで起動した `claude -p` は、メインの作業ツリーの skill と定義を読み、作業ツリーのものを読まないため。アプリのセッションは、作業ツリーで動くときも、メインの作業ツリーのものを読む（[作業ツリーのセッションが読むもの](session-reads.md)の表）。
- 後片付けで自分をアーカイブできないときは、許可した利用者の言葉を添えて、issue 担当のセッションに頼む（[マージと後片付け](../../../docs/05-開発規則/merging.md)の「マージの許可と後片付け」）。

## Dependabot の pull request のマージ

危険度が低い pull request を、issue 担当のセッションがまとめてマージするときに使う。判定の読み方は [マージと後片付け](../../../docs/05-開発規則/merging.md)の「マージの許可と後片付け」。

```bash
bash scripts/dev/merge-deps.sh 101 102   # 番号の pull request を順に処理する
```

- 使い方と振る舞い（出力するコマンド、止まる条件、script がマージしない理由）は [merge-deps.sh](../../../scripts/dev/merge-deps.sh) の冒頭。エージェントは、出力されたコマンドを 1 つずつ実行する。
- 1 つ目をマージした後に、2 つ目以降のコマンドが失敗したら（`develop` が進んで最新でなくなるため）、残りの番号で script をやり直す。

## ツールの補足

使うサービスに固有の名前と手順。今のサービスは Claude Code のデスクトップアプリ。サービスを替えるときは、この節だけを修正する。

- セッションへのメッセージ：`mcp__ccd_session_mgmt__send_message`（引数に識別子を渡す。一覧は `list_sessions`）。子のセッションへは `SendMessage` も使える。
- 遠隔操作：`mcp__ccd_session_mgmt__set_remote_control`。待機中のセッションで有効にすると「Remote Control requires an active session」で失敗する。
- 親子のセッション：子のセッション（起動された側）のターンが終わると、親のセッション（起動した側）に通知が届く。
- 終わったら知らせる指定：バックグラウンドの実行（`run_in_background`）か、起動したセッションの終了の通知。通知でターンが再開する。
- 見逃しの一覧と CI：`gh issue list --label 見逃し`、`gh run list -b develop -L 1`。
- 使用量：`mcp__ccd_session_mgmt__get_usage`（5 時間と週の使用率、戻る時刻）。
- `claude -p` の起動：`claude -p --model <モデル> --permission-mode default --allowedTools "<許すツール>" "<指示>"`。`--permission-mode bypassPermissions` は auto mode の判定が拒否するので使わない。Write のツールは、`claude -p` を起動したディレクトリの `.claude/` の下（`settings.json`、`agents/`、`skills/`）に書けない（`--allowedTools Write` でも拒否される）。動作の確認でファイルを置くときは、許可した Bash から script で置く。
- マージの許可を求める確認の画面：遠隔操作（Remote Control）では、hook（`agent-guard`）の確認の画面とアプリの「次の一歩」の表示欄が見えないことがある。許可を求めるときの伝え方は [マージと後片付け](../../../docs/05-開発規則/merging.md)の「マージの許可と後片付け」。
