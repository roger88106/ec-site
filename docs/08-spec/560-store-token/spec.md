# Spec 560：会員の token の再取得を 1 つの経路にまとめ、IdP の障害の間は待ち続けない

種類：整理　規模：M　ステータス：確定

## 背景と目的

店舗画面は、会員の access token の期限が近いと、refresh token で再取得する（[店舗画面の構成](../../02-設計/apps/store.md)の「token の更新」）。1 つのリクエストの中で再取得の入口が 3 つあり、同じ refresh token の再取得をまとめる仕組みがない。IdP の障害の間は、失敗を記録しないので、入口の数だけ、リクエストごとに IdP を待つ。この spec は、再取得を 1 つの経路にまとめ、失敗の間は IdP を呼ばないようにする。

追跡の issue は #560（組の issue。全体の issue #544 の一部）。sub-issue は次の 2 つ。

| issue | 内容 |

| #525 | 整理：token の更新を 1 つの経路にまとめる |
| #442 | 不具合：IdP の障害の間、リクエストごとに IdP の応答を待つ |

### 確認した範囲と限界

再取得の入口は 3 つあり、どれも再取得の関数を呼ぶ。

| 入口 | 出典 |
|------|------|
| proxy から Auth.js の `jwt` コールバックを通る。期限の 60 秒前から再取得し、Cookie に書く | `frontend/store/src/proxy.ts:28`、`frontend/store/src/auth/index.ts:83` |
| サーバーコンポーネントの `auth()`（ヘッダーの `currentMember()`）も `jwt` コールバックを通る。Cookie には書けない | `frontend/store/src/auth/index.ts:110-111`、`frontend/store/src/components/SiteHeader.tsx:27`、next-auth の `lib/index.js` の `getSession` |
| access token を返す関数は、同じリクエストの画面が古い Cookie を読むので、期限が切れていれば自分でも再取得する。結果は保存しない | `frontend/store/src/auth/index.ts:138-143` |

その他の確認した内容は次のとおり。

| 確認した内容 | 出典 |
|--------------|------|
| proxy の matcher は先読みのリクエストも含む。画面に複数のリンクがあると、先読みが同時に再取得を起こすことがある | `frontend/store/src/proxy.ts:42` |
| IdP に届かない、タイムアウト、`invalid_grant` 以外の失敗では、今の token を返すだけで失敗を記録しない | `frontend/store/src/auth/refresh.ts:54`、`:69-71` |
| 障害の間は、1 回あたり最大 10 秒（`AUTH_KEYCLOAK_TIMEOUT_SECONDS` の既定）IdP を待ち、入口の数だけ待つ | #442 の本文 |
| 再取得が重なってもログアウトしないのは、realm で refresh token のローテーションが無効だから。この前提は設計書にない | #525 の本文 |
| ローテーションを有効にすると、2 回目の再取得が `invalid_grant` で拒否され、会員がログアウトする（Auth.js がセッションの Cookie を削除する） | #525 の本文、`frontend/store/src/auth/refresh.ts:54` |
| 再取得の失敗をログに出さない。運用者は、画面の遅れの原因が IdP だと分からない | #442 のコメント（2026-11-17） |
| 店舗画面の設計は、操作が失敗しても処理を続けられるものを warn とする | [店舗画面の構成](../../02-設計/apps/store.md)の「ログ」 |
| 設計書は、カート ID の Cookie を書くのはサーバーアクションだけと書く | [店舗画面の構成](../../02-設計/apps/store.md)の「カート ID の Cookie」 |
| Auth.js の `signIn` のイベントも、Cookie を書く（カート ID の削除と、カートを移した結果の知らせの Cookie） | `frontend/store/src/auth/index.ts` の `events.signIn`、`api/cart.ts` の `mergeCartAfterLogin`、#252 の指摘、#560 の本文 |

ブラウザーと実際の IdP では、まだ確認していない。tasks の手動の確認（T560-01-07）で確認する。

## スコープ

| 含める | 含めない |
|--------|----------|
| 再取得を、プロセスの中で同じ refresh token ごとに 1 回にまとめる（#525 の 1） | 複数のサーバーで動かすときの方式（サーバー側のセッション）と、認証のライブラリの置き換え（#525 の 4） |
| 再取得の失敗を一定の時間記録し、その間は IdP を呼ばない（#442） | 管理画面の token の更新 |
| 再取得の失敗の warn のログ（#442 のコメント） | |
| 先読みのリクエストの扱い（#525 の 2。決定 7） | |
| 設計書の「token の更新」の前提と規則（#525 の 3）、「カート ID の Cookie」の書く場所の修正 | |

決定：

1. 再取得は全て再取得の関数を通す。同じ refresh token の再取得が実行中なら、その結果を待って共有する。終わった結果は決定 4 の時間だけ保持し、その間は IdP を呼ばずに保持した結果を返す。
2. 保持する場所はプロセスのメモリー。proxy とサーバーコンポーネントは別にバンドルされるので、1 つのモジュールの変数でなく、プロセスで共有する場所に置く。理由：サーバーコンポーネントは Cookie を書けず、Cookie に保持できないため。
3. 保持のキーは、refresh token そのものでなく、そのハッシュにする。理由：メモリーに token を残す箇所を増やさないため。保持の時間を過ぎた結果は削除する。
4. 保持の時間は、再取得できたときと、IdP が拒否したとき（`invalid_grant`）が 10 秒。それ以外の失敗（IdP に届かない、タイムアウト、`invalid_grant` 以外のエラーの応答、本文を解析できない）は 30 秒。理由：成功の結果は、同じリクエストと同時のリクエストで共有できれば足りるため。失敗の 30 秒は #442 のコメントの例で、障害の間の IdP の呼び出しを 30 秒に 1 回に減らす。
5. 失敗の warn は、IdP を呼んで失敗したときに 1 件出力する。保持した失敗を返すときは出力しない。項目は、理由の種類（届かない・タイムアウト、エラーの応答、本文を解析できない）と状態コードだけにする。token、Cookie、応答の本文は出力しない。
6. 設計書の「token の更新」に、次の前提を書く。1 つのプロセスの中で再取得をまとめる。IdP の refresh token のローテーションは無効にする。有効にするなら、サーバー側のセッションに変える。複数のサーバーで動かすときの方式は、デプロイの構成を決めるときに判断する。
7. 先読みのリクエストは、proxy の matcher から除かない。#525 の本文の案（matcher から除く）と違う。理由：決定 1 で、先読みの再取得も IdP へのリクエストを増やさないため。除くと、先読みの描画に、proxy が付ける今の画面のパス（`x-pathname`）と追跡の ID（`traceparent`）が付かず、ログインを求める画面の先読みで `redirectToLogin()` が動くと戻り先が `/` になるため。
8. 失敗は refresh token ごとに保持する（IdP の全体で 1 つにしない）。理由：決定 1 の保持と同じ仕組みで済み、#442 のコメントの案もこの形であるため。

## 目的と完了条件

### DS-560-1 token の再取得を 1 つの経路にまとめる（D / P1）

- **DC-560-1** 同じリクエストの中で、proxy、`auth()`、access token を返す関数が再取得しても、IdP への再取得のリクエストは 1 回である。
- **DC-560-2** 同じ refresh token の同時の複数のリクエストでも、IdP への再取得のリクエストは 1 回である。
- **DC-560-3** 再取得の結果を保持する 10 秒の間、同じ refresh token の再取得は IdP を呼ばない。10 秒を過ぎると、再び呼ぶ。

### DS-560-2 IdP の障害の間、リクエストごとに IdP を待たない（D / P1）

- **DC-560-4** `invalid_grant` 以外の失敗の後 30 秒の間は、同じ refresh token の再取得で IdP を呼ばず、今の token を返す。30 秒を過ぎると、再び呼ぶ。
- **DC-560-5** IdP を呼んで失敗したとき、warn のログが 1 件出る。ログに token、Cookie、応答の本文を含まない。

### DS-560-3 設計書が実装と合う（D / P1）

- **DC-560-6** [店舗画面の構成](../../02-設計/apps/store.md)の「token の更新」に、決定 1〜8 の規則と前提が書いてある。
- **DC-560-7** [店舗画面の構成](../../02-設計/apps/store.md)の「カート ID の Cookie」で、Cookie を書く箇所に Auth.js の `signIn` のイベントが含まれている。

### DS-560-4 検査が通る（D / P1）

- **DC-560-8** 店舗画面の `pnpm lint`、型チェック、テストが通る。

## 非機能要件

- **DN-560-1** 消費者に見える振る舞いを変えない。例外は、レビューで見つけた不具合 #442 の修正（DC-560-4）と、運用者が読む失敗の warn のログ（DC-560-5）である。
- **DN-560-2** API の契約とバックエンドを変えない。
- **DN-560-3** メモリーのキーに、token をそのまま残さない。
