# Spec 415：ログインの直後にカートを移せなかったときに、カートを残して、カートの画面で移行を再試行する

種類：機能　規模：M　ステータス：草案

## 背景と目的

ログインの直後（Auth.js の `signIn` のイベント）に、ログインせずに使っていたカート（Cookie のカート）を会員のカートへ移す。移せなかったときは、警告のログを書くだけで利用者に知らせず、Cookie のカート ID を必ず削除する。ゲストのカートは DB に残るが、利用者は ID を失うので戻せない。移す前のカートの取得が例外になったときも、移さずに ID を削除する。出典は `frontend/store/src/auth/index.ts:60-65`、`frontend/store/src/api/cart.ts:41-56`。

この動きは、[店舗画面の構成](../../02-設計/apps/store.md)の「使うカートの選び方」のとおりである（「移せなくても削除する ※3」）。この spec は、これを設計の欠陥として扱う。※3 の理由は、ログインしている間は使わないので、残すとログアウトの後に古いカートが見えることである。ログアウトで Cookie のカート ID を削除する処理（`frontend/store/src/actions/auth.ts:16`）が入ったので、この理由はログアウトについては当てはまらない。

移す処理は、2 回呼ばれても 2 回目は何も起きない（[カートモジュール](../../03-機能仕様/cart.md)の「カートを移す」）。そのため、タイムアウトで実際には移っていても、もう一度呼んでよい。店舗 API のタイムアウトは 30 秒（`frontend/store/src/auth/config.ts:31`）。移す API（`POST /me/cart/merge`）の応答は 200・400・401・404（`api/openapi/store.yaml`）。

テスト「AC-124 移せなかったときも、Cookie のカート ID を消す」（`frontend/store/src/api/cart.test.ts:61`）は、AC-124（ログアウト）と内容が合わない。

追跡の issue は #415。利用者の決定（issue のコメント、2026-11-06）は、次の 3 つ。

- カートの画面を開いたときに移行を再試行する。
- Cookie のカート ID を残すのは一時的な失敗（5xx、例外）のときだけにし、404 と 400 では削除する。
- 知らせの文言と Cookie の形式は担当のセッションが決める。

### 確認した範囲と限界

| 確認した内容 | 方法と出典 |
|--------------|------------|
| 移す API が 500・503 を返すと、Cookie のカート ID が消え、知らせの Cookie も書かれない | 移す処理を MSW で差し替えた一時的なテスト（実行後に削除。issue #415） |
| 通信がタイムアウトの例外になると、同じ結果になる | 同上 |

ブラウザーでの操作と、実際のバックエンドでは確認していない。

## スコープ

| 含める | 含めない |
|--------|----------|
| ログインの直後に移せなかったときの扱い | ログアウトの処理 |
| カートの画面で移行を再試行する処理と、その結果の知らせ | ログインの後のタイムアウトの長さ |
| テスト | カート以外の画面での再試行 |
| AC 一覧と店舗画面の構成の更新 | E2E のテスト |

含めないものの理由は Non-goals に書く。

決定：

1. 規模は M にする。理由：AC を追加するが、API の契約と DB の構造を変えず、店舗画面だけを変えるため。
2. 移した結果を 4 つに分ける。分ける判定は `lib/` の関数にして単体テストを書く。
   - 移せた（200）：Cookie のカート ID を削除する。
   - 移す元がない（404、400）：Cookie のカート ID を削除する。知らせない。理由：再試行しても結果が変わらず、移す品目もないため。
   - 一時的な失敗（5xx、例外）：Cookie のカート ID を残す。
   - 401：Cookie のカート ID を残す。カートの画面での移行の再試行なら、ログインの画面へ移す（ログインの直後に移行を再試行するため）。ログインの直後の 401 は、得たばかりの token なので起こらないはずだが、同じく残す。
3. 移す前のカートの取得（商品名を知らせに使う）が例外になったときも、一時的な失敗として扱い、ID を残す。
4. カートの画面を開いたとき、ログインしていて Cookie にカート ID があれば、移行を再試行する。ログインしている間に Cookie にカート ID があるのは、移せていないときだけである（移せたら削除するため）。
5. 移行の再試行は、カートの画面のクライアントコンポーネントが、表示の後にサーバーアクションを呼んで行う。再試行している間は、カートを移していることを読み上げの領域で示す。再試行した後は、カートの画面を再表示する。理由：サーバーコンポーネントは Cookie を書けず、描画の中で変更の API を呼ばないため。
6. 再試行した結果の知らせは、サーバーアクションの結果としてそのコンポーネントに返して表示する。知らせの Cookie は使わず、その形式も変えない。理由：知らせの Cookie の表示は最初に受けた値を持ち続けるので、表示の後に書いた Cookie は出ないため（`CartMergeNoticeView.tsx` のコメント）。
   - 移せた：切り詰めた品目と移せなかった品目があれば、ログインの直後と同じ形で知らせる。
   - 一時的な失敗：「ログインする前のカートを、会員のカートに移せませんでした。時間をおいて、カートの画面をもう一度開いてください。」の旨を知らせる。文言は実装のタスクで決める。
   - 移す元がない：知らせない。
7. ログインの直後に移せなかったときは、知らせの Cookie を書かない。理由：知らせを表示するのはカートの画面だけで、カートの画面を開くと移行を再試行するので、その結果を知らせれば足りるため。
8. ログインの直後の処理と、カートの画面の移行の再試行は、移す処理と結果の区分を共有する。API の呼び出しと区分は 1 か所に置く。違いは token の渡し方だけで、ログインの直後はログインで得た token、移行の再試行はセッションの token を渡す。
9. 店舗画面の構成の「使うカートの選び方」の、移す処理の箇条と ※3 を書き換える。追記でなく、節の全体を読んで書き換える。

   | 論理名 | 識別子 |
   |--------|--------|
   | ログインの直後に移す処理 | `mergeCartAfterLogin` |
   | 移す API | `POST /me/cart/merge` |
   | 知らせの Cookie | `cart_merge_notice` |
   | カートの画面 | `app/cart/page.tsx` |

## User stories

| US | 誰が | 何をできる | なぜ |
|----|------|------------|------|
| US-415-1 | 消費者 | ログインの直後にカートを移せなくても、ログインする前に入れた品目を失わずに、後で会員のカートに移せる | 購入のためにログインしたときに、品目を入れ直さずに済むようにするため |

## 受け入れ条件

### US-415-1 移せなかったカートを後で移せる（C / P1）

- **AC-415-1** ログインの直後に、一時的な失敗（5xx、通信の失敗）でカートを移せなかったとき、ログインする前のカートは失われない。
- **AC-415-2** ログインの後にカートの画面を開くと、移せていないカートを会員のカートへ再び移し、移した品目を含む会員のカートを表示する。
- **AC-415-3** 再試行した結果が上限を超えたときは、ログインの直後と同じく、切り詰めた品目と移せなかった品目を表示する（AC-123）。
- **AC-415-4** 移行の再試行も失敗したときは、移せなかったことと、カートの画面をもう一度開くと再び移すことを示す。
- **AC-415-5** 移す元のカートがもうない（期限切れなど）、またはカート ID が不正のときは、再試行せず、何も示さない。
- **AC-415-6** 再試行している間は、カートを移していることを示す。

## 非機能要件

- **NFR-415-1** API の契約とバックエンドを変えない。
- **NFR-415-2** 移せなかったときの警告のログに、カートの ID（Cookie の値）を出力しない。今の規則を移行の再試行でも守る。理由：ゲストのカートは ID を知れば操作できるため。

## Non-goals

| 項目 | 理由 |
|------|------|
| ログアウトで Cookie のカート ID を削除する処理 | 変えると AC-124（ログアウトするとブラウザーのカートは空に見える）が変わるため。移せないままログアウトしたときは、ログインする前のカートは戻らない |
| ログインの直後のタイムアウトの長さ（30 秒） | 店舗 API の全体の設定で、カートの移行だけの問題ではないため |
| カート以外の画面での再試行 | 利用者の決定がカートの画面を開いたときであり、注文手続きはカートの画面から始めるため |
| E2E のテスト | 移す API だけを失敗させる手段が E2E の環境にないため。手動の確認で、バックエンドを止めてログインし、再起動してカートの画面を開く |
