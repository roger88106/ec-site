## 1. 背景と目的

1→10 の改善の第 6 弾として、文書の用語と規則を整える。バージョンの意味の「版」が文書とコードに混在している（#187）、spec を並行してよいかの判断が spec の範囲だけで決まる（#188）、店舗の契約の説明が今の操作と食い違う（#203）の 3 つを扱う。

追跡の issue は [#222](https://github.com/roger88106/ec-site/issues/222) である。扱う issue は次の 3 つである。

- [#187](https://github.com/roger88106/ec-site/issues/187)：バージョンの意味の「版」
- [#188](https://github.com/roger88106/ec-site/issues/188)：並行の判断の前に変えるファイルを照合する
- [#203](https://github.com/roger88106/ec-site/issues/203)：店舗の契約の説明の公開の操作の一覧と security の約束

作業ブランチは `222-docs-terms` である。本 spec は整理の spec で、規模は M である。規模は issue 担当のセッションが提案し、2026-10-27 に利用者が第 6 弾の分け方とともに承認した。AC、API の項目、データベースは変えない。文書、コードのコメント、検査の script の文言、検査の設定を変える。

第 6 弾の 6 つの spec（#222〜#227）は、文書の段階を並行して進める。本 spec はほぼ全ての文書と多くのコードのコメントを変えるので、他の 5 つの spec の実装は本 spec のマージの後に始める（issue 担当のセッションの計画）。

## 3. 目的と完了条件

### DS-222-1 バージョンの意味の「版」をそろえる（D / P1）

- **DC-222-1** アーカイブの外の文書（docs/、AGENTS.md、README、skill、.github/）に、バージョンの意味の「版」がない。本 spec の文書は、洗い出しの結果として「版」を挙げるので、アーカイブに移すまでこの条件の対象に含めない。
- **DC-222-2** コード（バックエンド、フロント、検査の script、Gradle の設定）のコメント、Javadoc、テスト名、テストの理由の文、検査の出力の文に、バージョンの意味の「版」がない。楽観ロックの版と、形式の中の版の項目を含む。
- **DC-222-3** 関数の変種の「版」を、第 6 節の 3 の決定のとおりに扱う。
- **DC-222-4** 版（エディション）の意味の複合語（第 1 節の変えない所）は変えない。
- **DC-222-5** 文書の用語の検査（doc-terms）が、文書のバージョンの意味の「版」を見つけて失敗にし、エディションの意味の複合語は許す（第 6 節の 1）。

※2：doc-terms のテストは、語の一致と許す語の動作を試す。一覧の個々の語は試さない。そのため、「版」のテストは加えない。「Node の版」「版は」が失敗し、複合語が通ることは、T222-01-03 の確認方法で確認する。

### DS-222-2 並行の判断の前に変えるファイルを照合する（D / P1）

- **DC-222-6** エージェントの作業フロー（`docs/rules/subagents.md`）第 4 節の並行の節が、spec を分けるとき・spec を並行してよいと判断するときは、spec の範囲だけで決めず、両方の plan と tasks（規模 M は spec の tasks）の変えるファイルを照合してから決める、と定める。
- **DC-222-7** 同じ節が、spec の段階では並行の可否を決めず、「並行の可否は plan の段階（規模 M は tasks を書くとき）で決める」と spec に書く、と定める。
- **DC-222-8** 同じ節が、照合の結果（重なるファイルと実装の順序）を plan（規模 M は spec の tasks）に書く、と定める。依存は今までどおり追跡の issue に書く。
- **DC-222-9** [開発の進め方](../../rules/workflow.md) 第 5.6 節の実装を始める前の照合が、spec の確定の後に、並行する spec の変えるファイルとの重なりが増えていないかの確認を含む（第 6 節の 4）。

### DS-222-3 店舗の契約の説明（D / P2）

- **DC-222-10** 店舗の契約（`api/openapi/store.yaml`）の説明の認証の一覧が、今の全ての操作を、会員の操作、任意の操作、公開の操作のどれかに区分する。公開の操作に、カートの作成と、地域の操作（都道府県・市区町村・郵便番号）を含む。今の説明は、公開の操作を「商品・カテゴリ・店舗の情報」とし、カートの作成と地域の記載がない。任意の操作を「カート」と書くが、カートの作成は公開である。
- **DC-222-11** 同じ説明が、全ての操作に `security` を書くこと、公開の操作は `security: []`、任意の操作は空の要件と会員の token の 2 つを並べることを書く。書いていない操作は、バックエンドの起動が失敗する（spec 182）。

今の操作と security（2026-10-27）は次のとおりである。

| 区分 | operationId |
|------|-------------|
| 公開（`security: []`） | listProducts、searchProducts、getProduct、listCategories、createCart、getShop、listPrefectures、listMunicipalities、findPostalCodeAddresses |
| 任意（`- {}` と `- memberToken: []`） | getCart、addCartItem、changeCartItemQuantity、removeCartItem |
| 会員（残りの 9 つ） | getMemberCart、mergeCart、startCheckout、getCheckout、placeOrder、listMemberOrders、getOrder、requestOrderCancellation、openOrderPaymentPage |

## 6. 決めたこと

### 1. 文書の用語の検査に加える語（DC-222-5）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 「版」を使わない語にし、エディションの意味の複合語（有料版、無料版、コミュニティ版、OSS 版、オープンソース版、Community 版、最小版）を許す語に書く |
| 案 B | 「の版」だけを使わない語にする（#187 の本文の案） |

- 案 A の理由：「版は」「版を」のように「の」の付かない書き方も見つけられる。「の版」を含まない行が今の文書に 3 行ある（`action.yml` の説明の「版はルートの」、`setup.md` の「版は」、`subagents.md` の表の列の名前）。許す語は、どの文書にも使われなくなると検査が失敗するので、一覧が古くならない。
- 案 A の手間：エディションの複合語を新しく書くと、許す語に加える必要がある。
- 案 B の理由：設定が 1 行で済み、複合語（「有料版」など）は「の版」を含まないので許す語が必要ない。ただし、「の」の付かない書き方を見逃す。

### 2. コードのコメントの「版」を、これからどう見つけるか

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 本 spec ではコードのコメントを全てそろえ、検査は文書だけのままにする。コードのコメントの用語の検査は、第 8 節の起票の案にする |
| 案 B | 文書の用語の検査を、コードのコメントにも広げる |

- 案 A の理由：今の検査は文書だけを見る。範囲が大きくなる理由は第 5 節の 1 行目のとおりである。commit の前の手元の中国語の混入の検査は「の版」を見つけるが、Git に入らない各自の設定で、CI の検査ではない。
- 案 B の理由：CI でコードのコメント全てを検査できる。

### 3. 関数の変種の「版」（DC-222-3）

管理画面のテストの補助の 2 つの関数の説明が、「{@link getRow} の、行が現れるまで待つ版」と書く。バージョンでなく、同じ関数の別の形の意味である。

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 言い換える（例：「行が現れるまで待つ {@link getRow}」） |
| 案 B | 残す |

- 案 A の理由：日本語の「〜版」（非同期版など）の使い方もあるが、利用者の指示（2026-10-24）は「版」を中国語の混入として扱う。コードには CI の検査がないので、残すと、新しく書くコードにも同じ書き方が増える。

### 4. 実装を始める前の照合に、並行する spec との照合を含めるか（DC-222-9、#188）

| 案 | 内容 |
|----|------|
| 案 A（推奨。採用） | 含める。最新の `develop` を取り込むときに、並行する spec の plan と tasks（規模 M は spec の tasks）の変えるファイルと自分の変えるファイルを照合し、spec の確定の後に重なりが増えていないかを確認する。増えていれば、順序を再検討する。設計が変わるなら利用者に確認する |
| 案 B | 含めない。照合は spec を分ける・並行を決める時（plan の段階）の 1 回だけにする |

- 案 A の理由：並行する spec の plan・tasks は、確認の後にも実装の中で変わる（spec 195 の T195-01-06 のように、実装の中で範囲のファイルが増える）。実装を始める前の照合で、最新の `develop` との照合を既に行うので、並行する spec の照合を加える手間は小さい。

### 並行の判断

[エージェントの作業フロー](../../rules/subagents.md) 第 4 節の並行の規則（DC-222-6 で書く）を、本 spec に当てはめる。

- 本 spec の中：`[P]` のタスクはない。同じファイルを変える T222-01-01 と T222-01-03（`subagents.md`）に依存を付け、他のタスクは変えるファイルが重ならないが、各タスクの変更が小さく、作業ツリーを分ける手間のほうが大きいので、順に実装する。
- 文書の用語の検査に「版」を加えるのは、spec をアーカイブに移す T222-02-02 の commit にする。理由：本 spec は洗い出しの結果として「版」を含む語を多く挙げ、アーカイブに移すまでは検査の対象（`docs/specs/`）にあるため。
- 本 spec が変えるファイル：第 1 節の表のファイル、`docs/rules/workflow.md`、`docs/rules/subagents.md`、`AGENTS.md`、`api/openapi/store.yaml`、`scripts/ci/doc-terms.json`。
- 他の spec と重なりうる所：次の一覧は issue 担当のセッションの計画からの推測で、各 spec の tasks は未確定である。重なりうるのは、検査の script（`scripts/ci/`、#225、#226）、バックエンドのテストとコメント（#223、#224）、店舗画面（#227）、規則の文書（`docs/rules/`、#226 のテストの書き方など）である。
- 実装の順序：第 1 節のとおり、他の 5 つの spec の実装は本 spec のマージの後に始める。他の spec は、実装を始める前の照合（[開発の進め方](../../rules/workflow.md) 第 5.6 節）で、本 spec で統一した語を反映する。重なりを解消するために、本 spec の実装を遅らせる必要はない。
