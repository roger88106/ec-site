# 機能仕様の雛形

## この雛形の使い方

モジュールごとに 1 つ、`docs/03-機能仕様/<モジュール>.md` として置く。

| 項目 | 内容 |
|------|------|
| 読者 | 主にエージェント。モジュールの規則の正本として読む |
| 置くもの | 業務規則、状態の遷移、データモデル、今有効な AC |
| 置かないもの（設計） | 依存、公開（API、イベント）、パッケージの構成、処理の流れの図。[モジュールの設計の雛形](../02-設計/template.md)で書く `docs/02-設計/<モジュール>.md` に置く |
| 置かないもの（決定記録） | 決定の理由。`docs/04-決定記録/` に置き、本文は決定記録を指す |
| 置かないもの（OpenAPI） | API の項目とエラーコードの一覧 |

- 節の名前と順は固定で、構造を検査する script が確認する。機能仕様を固定の節に書き換えたら、`scripts/ci/spec-structure.mjs` の一覧に加える。
- 当てはまらない節は消さずに「なし」と書く。
- 1 つの事実の正本は 1 つ。他の文書にある内容は転記せず、その文書を指す。

## 写して使う骨組み

````markdown
# <モジュールの論理名>モジュール

<モジュールが管理するものを 1〜2 文で書く。モジュールの境界、処理の流れ、API の一覧、パッケージの構成は [<モジュール>の設計](../02-設計/<モジュール>.md) を指す。>

| 項目 | 内容 |
|------|------|
| レベル | <A、B または C>（<理由>） |

## 業務規則

<モジュールが守る規則を、小見出し（`###`）ごとに、表と短い箇条で書く。決まりと対応は表にする。長い理由は注にする。決定の理由は決定記録を指す。>

## 状態の遷移

<状態を持つ集約の遷移を、次の形で書く。
- 図と表で書く。表は、操作、すでにその状態のときの扱い、できない状態。
- 状態を持たないときは「なし」と書く。
- 図の矢印のラベルに条件を添えるときは、括弧の前に `<br/>` を入れて改行する。
- 画面に今できる操作のフラグを返すときは、小見出し「状態ごとにできる操作」に、状態を行、画面を列にした表を置く。各欄に「`フラグ`：操作」を 1 行ずつ書く。>

## データモデル

<schema、テーブルの関係（Mermaid の erDiagram）、列の規則を書く。列の正本は Flyway のマイグレーション。>

## 今有効な AC

<選んだ基準を 1 文で書く。表は印の組の中に、AC 一覧から生成する。>

<!-- generated:module-ac -->
なし。
<!-- /generated:module-ac -->
````

- レベルの行は `| レベル | A（理由） |` の形にする。記号は[文書の記号と番号](../05-開発規則/notation.md)の「モジュールの設計書の記号」。
- `## 今有効な AC` の表は、[AC 一覧](acceptance-criteria.md)から生成する。列は AC・今の内容・元の spec の 3 つ。入る AC は、状態が有効か変更で、モジュールがこの文書の名前（ファイル名から `.md` を除いた名前）のもの。0 件なら「なし。」の 1 行にする。
- 表は、印の組（`<!-- generated:module-ac -->` と `<!-- /generated:module-ac -->`）の中に置き、手動で書き換えない。今の内容を変えるときは、AC 一覧を修正してから、リポジトリのルートで `node scripts/ci/ac-check.mjs --write` を実行する。印の組は、`scripts/ci/spec-structure.mjs` の一覧に加えた文書にだけ置く。一覧にない文書に置くと、検査が失敗する。
