# Spec 224：統合テストの頑丈さと、集約の復元の失敗のログを整える

ステータス：草案（利用者の確認を待つ）

## 1. 背景と目的

spec 181 で統合テストの間の干渉をなくしたが、spec 181・182・186 のレビューで、今は通るが、他のテストの追加や時刻の変更で壊れうる箇所が残った（#201）。また、集約の復元に失敗したときの error のログに、原因の例外のメッセージがそのまま出ており、メッセージに値が入りうる（#204）。どちらもバックエンドのテストと共通の部品を変える小さな整理なので、1 つの spec で扱う。

追跡の issue は [#224](https://github.com/roger88106/ec-site/issues/224)、扱う issue は [#201](https://github.com/roger88106/ec-site/issues/201)、[#204](https://github.com/roger88106/ec-site/issues/204) である。作業ブランチは `224-backend-tests-log`。本 spec は整理の spec で、規模は M の見込みである（第 6 節の 1）。

### 3.1 spec 223 の検査が前提にする今の状態

spec 223（#202）は、補助以外の統合テストで、在庫の作成、税区分の登録の要求、応答の ID を読む処理の再定義を見つける検査を加える。本 spec の後の状態は次のとおりで、spec 223 はこの表の「除く」を検査の除外にできる（DC-224-8）。

| 検査の対象 | 補助（除く） | その操作そのものを確認するテスト（除く） | 本 spec で直すテスト |
|------------|--------------|------------------------------------------|----------------------|
| 在庫の作成 | `InventoryTestData` | `JooqStockItemRepositoryTest` | なし |
| 税区分の登録の要求 | `CatalogTestData` | `TaxCategoryApiTest`、`AuthorizationTest`、`KeycloakIntegrationTest` | `ProductApiTest` |
| カテゴリの登録の要求 | `CatalogTestData` | `CategoryApiTest` などカテゴリの API のテスト | `ProductApiTest` |
| 応答の ID を読む処理（`UUID.fromString(JsonPath.read`） | `TestJson` | なし | なし |
| 支払の API の作成の操作 | `PaymentTestData` | `PaymentApiTest` | `PaymentExpiryJobTest` |

- 表の対象は、検査が探す書き方に当たるものである。Repository のテストが集約を直接作る処理（支払の Repository のテストなど）と、作った後の変更の要求（店舗の鮮度のテストの税率の変更など）は、対象に含めない。その操作そのものを確認するテストが、確認する API の作成の応答から ID を読む処理（`JsonPath.read` だけの形）も含めない。
- 統合テストで、イベントの記録（`EventPublicationRegistry`）を完了を待つ処理に直接使う箇所はない。イベントの片付けと再送のテストが、イベントの補助（`EventPublications`）を作るために注入するだけである。
- 「その操作そのものを確認するテスト」の列は、実装を始める前の照合で検索し直して確定する。

## 5. 守る制約

- **DN-224-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。ログの内容の変化（DS-224-6）は、運用と開発にだけ見える。
- **DN-224-2** テストを弱めない。補助に移すとき、確認の方法を変えるときは、確認する内容を減らさない。直した確認は、一時的にコードか期待値を変えて、失敗しうることを確認する（[開発の進め方](../../rules/workflow.md) 第 2.1 節）。
- **DN-224-3** AC を追加も変更もしない。AC-173 のテストを分けたら、[AC 一覧](../../design/acceptance-criteria.md) のテストの列が今のテストと合うことを確認する。
- **DN-224-4** 新しく書くコメントに、spec・plan・タスクの番号を書かない（[コメントの書き方](../../rules/comments.md) 第 1 節）。
- **DN-224-5** 統合テストの全体の時間を大きく延ばさない。理由：CI とローカルの確認で毎回実行するため。
- **DN-224-6** 実装は、spec 222（文書の整理）のマージの後に始める。spec 222 は、文書とコードのコメントの語を広く置き換えるため。
- **DN-224-7** 並行する spec 223（#202、#217）と、変えるファイルが重なりうる。重なりと順序は第 8 節の前書きの表に書き、実装を始める前の照合（[開発の進め方](../../rules/workflow.md) 第 5.6 節）で、spec 223 の tasks と照合し直す。

## 6. 決めたこと

spec の確認で、利用者が案を選ぶ。各節の推奨は案 A である。

### 6.1 規模

規模は M である。API の契約とデータベースを変えず、AC を追加も変更もしないため。本番のコードは共通の部品（集約を復元する補助）だけを変え、他は各モジュールのテストを独立に直すので、モジュールをまたぐ決定がない。

### 6.2 管理の注文の一覧のテストの絞り方（DC-224-1、2）

管理の注文の一覧の API は、注文番号の前方一致、状態、注文日の範囲で絞り、ページで返す。注文番号は「注文日-乱数 6 桁」なので、テストの注文だけに共通する前方一致はない。

- 案 A（推奨）：注文日の取り決めをなくし、応答の中の自分の注文だけを ID で識別して確認する。並び順は自分の注文の間の順序で、絞り込みは自分の注文が入る・入らないことと、返った全ての行が条件に合うことで確認する。ページは、同じ条件の全件の取得と比べ、2 ページ目の行と総数が全件の該当の部分と合うことを確認する。理由：[テストの書き方](../../rules/test-writing.md) 第 3.1 節の「自分のデータだけを確認する。一覧の全体を確認しない」に合い、取り決めを守る検査が不要なため。
- 案 B：取り決めを残し、取り決めた日付を補助の定数の一覧にまとめる。他のテストがその日付を使わないことは、ソースの文字列を探す検査でしか確認できず、時刻を計算で作るテストを検出できない。

### 6.3 行ロックのテスト（DC-224-10）

- 案 A（推奨）：支払の行ロックにも、注文と同じく、別のトランザクションがロックを取れないことを確認するテストを加える。名前は、注文と支払で「行ロックして取得すると〜を返す」「行ロックして取得している間は、別のトランザクションが〜できない」の 2 つの形にそろえる。理由：名前に書いた振る舞い（ロック）を確認するため（テストの書き方 第 2.2 節）。
- 案 B：確認を加えず、支払のテストの名前から行ロックを外す（「取得できる」）。名前と内容は合うが、ロックを外す誤りを見つけられない。

### 6.4 置き場所の system property の読み方（DC-224-12、13）

単体テストの契約の補助は、system property がないか空のとき、名前を示して失敗する。統合テストのソースセットは、単体テストのソースセットを使えない。

- 案 A（推奨）：契約の補助を、単体テストと統合テストが共有する既存のテストの補助のソースセット（testFixtures）に移し、theme の置き場所も加えて、2 つの統合テストもそれを使う。理由：読み方が 1 か所になるため。
- 案 B：統合テストのソースセットに、同じ読み方の補助をもう 1 つ作る。spec 223 と変えるファイルが重ならないが、読み方が 2 か所になる。

spec 223 も、#202 で「文書の置き場所の system property の読み方を、構成の検査と契約の補助でそろえる」を扱う。案 A では同じ補助を 2 つの spec が変えるので、順序を第 8 節の前書きの表に書く。

### 6.5 復元の失敗のログから値を除く方法（DC-224-16〜18）

#204 の方針（#153 と同じ向き。例外の種類と、集約を特定する情報だけを残す）は、利用者が決めた（2026-10-26）。集約を特定する情報は、集約の名前（`category` など）とする。集約の ID は加えない。理由：ゲストのカートの ID のように、ID が利用者を指す値になる集約があり、#153 でも識別子をログから除いたため。要求との対応は、ログのトレース ID で追跡できる。

- 案 A（推奨）：集約を復元する共通の補助で、投げる例外に原因の例外をそのまま持たせず、原因の例外の種類とスタックトレースだけを持つ例外に置き換える。理由：ログに出す経路（例外の処理の共通の部品、定期のジョブ、イベントのリスナー）によらず、メッセージが出なくなるため（DC-224-18）。失敗した場所はスタックトレースで分かる。
- 案 B：例外の処理の共通の部品で、復元の失敗だけ原因のメッセージを出さずにログに出す。HTTP の要求の外の経路が残るので、DC-224-18 を満たせない。

## 8. tasks

- `[P]` のタスクはない。同じ段階のタスクは、番号の順に 1 つずつ行う。理由：段階 1 の 3 つのタスクは別のファイルを変えるが、統合テストの全体を実行する時間がかかるので、並列にしても短くならないため。
- `[テスト]` のタスクは、テストを書いてレッドを確認し、同じ実装役が続けて実装する。テストだけを直すタスク（確認の方法を変える）は、直した確認を一時的にコードか期待値を変えて失敗させ、commit の本文に書く（DN-224-2）。
- 各段階の最後に、統合テストの全体（`./gradlew check`）を実行し、かかった時間を段階 1 の前と比べて、段階のレビューのタスクの結果に書く（DN-224-5）。
- 各段階の最後のレビューは、profile「厚め」で行う（[エージェントの作業フロー](../../rules/subagents.md) 第 4 節）。重要な観点に「テストを弱めていないか」（DN-224-2）と「新しいコメントに spec・plan の番号がないか」（DN-224-4）を含める。

並行する spec と変えるファイルの重なりは次のとおり（DN-224-7）。spec 223 の tasks は、本 spec の確認の時点で未作成なので、実装を始める前の照合で照合し直す。

| 本 spec のタスク | 変えるファイル | 重なる spec | 順序 |
