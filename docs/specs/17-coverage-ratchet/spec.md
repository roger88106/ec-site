# Spec 17：カバレッジの基準と、domain の mutation testing

ステータス：確定

## 1. 背景と目的

テストの量の基準がなく、テストが減っても気づけない（issue #17。出典：外部レビューの意見 2026-10-20、MVP 004 の Non-goals）。今の規則は、CI でカバレッジの報告を作るが、基準の値で CI を失敗させない（[テストの書き方](../../rules/test-writing.md) 第 1 節）。

今の報告は `scripts/ci/report/coverage-summary.mjs` が作る。JaCoCo の XML と Vitest の json-summary を読み、job の summary に、合計と、カバレッジが低い順の 10 件を書く。

| 対象 | 計測の方法 | 除くもの |
|------|------------|----------|
| バックエンド | JaCoCo。単体と統合を合わせた `coverageReport` | 生成したコード |
| 管理画面・店舗画面 | Vitest の v8 | 生成したコード、shadcn/ui、テストの補助 |
| 共有パッケージ（`frontend/shared`） | 取っていない。店舗画面のジョブがテストを実行している | |

バックエンドの今の値は、行 98.1%（5876/5991）、分岐 85.3%（1608/1886）である（spec 131 の記録。ジョブの分割の前後で同じ）。

前提は spec 131（CI の整頓）である。spec 131 は、バックエンドのジョブを 4 つに分けた。ビルドと単体テスト、統合テスト 1/2、統合テスト 2/2、カバレッジの報告を作る「バックエンド」（ruleset の必須の検査の名前）である。`ci.yml` の全体は約 6 分 10〜40 秒で、ビルドと単体テストのジョブは統合テストのジョブ（約 5〜6 分）より早く終わる。spec 131 の DC-131-1 は、全体を 8 分以下にする。本 spec の実装は、spec 131 のマージの後に行う。

カバレッジは、テストが実行したコードの割合で、テストが振る舞いを確認しているかは分からない。domain のクラスは各モジュールの `domain` パッケージ（`com.ecsite.module.<モジュール>.domain`）に約 101 個あり、domain の単体テストは `src/test` に約 30 クラスある。統合テストに domain のテストはない。そこで、domain のテストの強さを mutation testing（コードに小さな変異を入れ、テストが失敗するかを確認する）で測る。ツールは PIT（Java の mutation testing）、`gradle-pitest-plugin`、`pitest-junit5-plugin` である。ライセンスは T17-02-01 で確認し、依存とライセンスの文書に書く（constitution 第 15 節）。

追跡の issue は [#17](https://github.com/roger88106/ec-site/issues/17)、作業ブランチは `17-coverage-ratchet` である。本 spec は整理の spec で、規模は M である（2026-10-22 に利用者が承認。[開発の進め方](../../rules/workflow.md) 第 4.2 節。API の契約とデータベースを変えず、AC を変えない）。

## 2. スコープ

| # | 目的 | 対象 | 優先度 |
|---|------|------|--------|
| DS-17-1 | テストが減ってカバレッジが下がったら、CI が失敗して気づける（バックエンド、管理画面、店舗画面、共有パッケージ） | D | P1 |
| DS-17-2 | domain のテストの強さ（mutation score）が下がったら、CI が失敗して気づける | D | P1 |

## 3. 目的と完了条件

### DS-17-1 カバレッジが下がったら CI が失敗する（D / P1）

- **DC-17-1** 基準の値を、リポジトリの 1 つのファイル（`scripts/ci/report/quality-baseline.json`）に置く。ファイルは、対象ごとに値と許容の幅を持ち、対象を後から追加できる形にする（DC-17-10 で mutation score を同じファイルに追加する）。カバレッジの対象は、バックエンド、管理画面、店舗画面、共有パッケージで、行のカバレッジと分岐のカバレッジの全体の割合（小数第 2 位）を持つ。初期値は、spec 131 のマージの後の `develop` の最新の CI の値（各ジョブの summary か coverage の artifact）である。共有パッケージは CI でまだ取っていないので、作業ブランチの CI の値にする。
- **DC-17-2** CI で、今回の値が「基準の値から許容の幅を引いた値」より低いと、そのジョブが失敗する。バックエンドはジョブ「バックエンド」、管理画面・店舗画面はそれぞれのジョブである。共有パッケージは、店舗画面のジョブで、管理画面・店舗画面と同じ v8 の設定と除外の形でカバレッジを取り、比べる。ジョブの名前を変えず、ruleset を変えない。
- **DC-17-3** 基準を下回ったとき、summary とログに、対象、基準の値、今回の値、差、修正の方法を表示する。修正の方法は、テストを追加する。正当な理由で基準を下げるときは、`--write` で基準のファイルを更新し、pull request に理由を書く。
- **DC-17-4** 今回の値が基準より高いときは、失敗させず、summary に警告を表示して、基準の更新を促す。`--write` は、報告の値で基準のファイルを書き換える（上げるときも下げるときも同じ）。書き換えたファイルは、同じ pull request に含める。
- **DC-17-5** 許容の幅は、基準のファイルに対象ごとに持ち、初期値は 0 にする。許容の幅は、値のばらつきに対する余裕である。作業ブランチで、同じ commit の CI を 3 回実行して値のばらつきを測り、許容の幅を決める。ばらつきがなければ 0 のままにする。測った値をタスクの結果に書く。
- **DC-17-6** 検査の script に単体テスト（`*.test.mjs`）がある。確認するケースと期待する結果は、次のとおり。
  - 基準を下回る：失敗にする。
  - 基準と同じ：成功にする。
  - 基準を上回る：成功にして、警告を表示する。
  - 報告がない：失敗にする。
  - 基準のファイルの誤り（対象がない、値の形が違う）：失敗にする。
- **DC-17-7** 基準を下回る push（テストを 1 つ削除）で CI が失敗することを確認し、削除を戻す。結果をタスクに書く。
- **DC-17-8** 基準の検査を、手元でも CI と同じ引数で実行できる。手順を[テストの実行方法](../../guides/running-tests.md)に書く。

### DS-17-2 domain のテストの強さが下がったら CI が失敗する（D / P1）

- **DC-17-9** `./gradlew pitest` で、単体テスト（`src/test`）を使い、domain のクラス（`com.ecsite.module.*.domain.*`）の mutation testing を実行する。報告（HTML と XML）は `build/reports/pitest/` に出力する。
- **DC-17-10** mutation score を、DC-17-1 の基準のファイルに置き、下回ると CI が失敗する（DC-17-2〜4 と同じ扱い）。比較は、PIT を実行するジョブの中で行う。PIT のジョブを分けたときは、そのジョブの失敗が `needs` で「バックエンド」を失敗させる。許容の幅も、DC-17-5 と同じ方法で測る。summary に、mutation score と、生き残った変異（テストが検出できなかった変異）が多いクラスの上位 10 件を表示する。報告を artifact に保存する。
- **DC-17-11** PIT を実行するジョブは、実測で決める。ビルドと単体テストのジョブに PIT を加えたとき、そのジョブの終了が統合テストの遅い方のジョブの終了を超えなければ、そのジョブに入れる。超えたら、PIT のジョブを分けて、「バックエンド」の `needs` に加える。PIT のジョブがスキップ・失敗したときは、「バックエンド」が失敗する（DC-131-4 と同じ）。作業ブランチで 3 回測り、`ci.yml` の全体が 8 分以下（DC-131-1）であることをタスクに書く。
- **DC-17-12** PIT のライセンスを確認し、結果を[依存とライセンス](../../design/licenses.md)に書く。ライセンスの検査（`checkLicense`）の対象に入るかを確認し、結果をタスクに書く。
- **DC-17-13** mutation score を下げる push（domain のテストの検証を 1 つ削除）で CI が失敗することを確認し、削除を戻す。結果をタスクに書く。

## 4. 守る制約

- **DN-17-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。
- **DN-17-2** 値を上げるために、カバレッジの対象から外すもの（除外）を増やさない。テストを弱めない。除外を変える必要が出たら、先に利用者に相談する。
- **DN-17-3** `ci.yml` の全体の時間を、DC-131-1 の 8 分以下に保つ。
- **DN-17-4** spec 104 の範囲（`docker/`、`scripts/dev/`、E2E の script、skill `local-dev`）を変えない。spec 18（Error Prone）と spec 19（フォーマッター）も `build.gradle.kts` を変える。後でマージする方が `develop` を取り込んで、衝突を解消する。

## 5. Non-goals

| 項目 | 理由 |
|------|------|
| フロントの mutation testing（Stryker） | フロントに domain の層がない |
| domain 以外の mutation testing | 時間が増える。domain の外は、カバレッジと統合テストで確認する |
| パッケージ・ファイルごとの基準 | 合計だけにする。細かい基準は、正当な移動や削除でも失敗が増える |
| カバレッジの値の目標（例：90% 以上） | 今の値を下げないことだけを守る |
| E2E のカバレッジ | 対象にしない |

## 6. 決めたこと

利用者への質問ではなく、本 spec の決定である。

- **並行の pull request が同時に基準のファイルを変えたとき**：後でマージする方が `develop` を取り込み、`--write` で基準のファイルを書き換える。衝突を手動で選ばない。
- **フロントも、Vitest の `thresholds` ではなく、同じ script で比べる**：理由は 2 つある。基準を 1 つのファイルにまとめるため。Vitest の `thresholds` は、手元で一部のテストだけを実行すると失敗するため。

## 7. spec の確認で決めたこと

spec の確認で、利用者が 7 つとも案 A に決めた（2026-10-22）。規模 M は、それより前に承認した。Open questions はない。

1. **基準の置き場所**：
   - 案 A（推奨。採用）：リポジトリのファイル。差分がレビューで確認でき、下げるときの理由が残る。
   - 案 B：`develop` の最後の CI の artifact と比べる。artifact には保存期限がある。古い `develop` から切ったブランチでは、比べる値が今の `develop` の値と異なり、判定が誤る。
2. **基準の単位**：
   - 案 A（推奨。採用）：対象ごとの合計。
   - 案 B：パッケージ・ファイルごと。理由は、第 5 節の Non-goals のとおり。
3. **共有パッケージ**：
   - 案 A（推奨。採用）：対象にする。管理画面・店舗画面と同じ設定で取れるので作業が小さく、両方の画面が使うコードである。
   - 案 B：対象にせず、Non-goals にする。
4. **基準より高いとき**：
   - 案 A（推奨。採用）：警告して、`--write` での更新を促す。
   - 案 B：一定（例：0.5 ポイント）以上高いと失敗にして、更新を強制する。
5. **PIT のテスト**：
   - 案 A（推奨。採用）：単体テストだけ。domain は Spring を使わず、単体テストで確認する設計である。
   - 案 B：統合テストも含める。時間が大きく増える。
6. **PIT の頻度**：
   - 案 A（推奨。採用）：毎回の CI。置き場所は DC-17-11 の実測で決める。下げた commit がすぐ分かる。PIT は、どちらの置き場所でも、「バックエンド」を通して必須の検査に入る。
   - 案 B：週に一度の定期と手動。下げた commit を特定しにくい。
7. **`./gradlew check` に PIT を含めるか**：
   - 案 A（推奨。採用）：含めず、`./gradlew pitest` を別に実行する。手元の `check` の時間を増やさない。
   - 案 B：含める。
