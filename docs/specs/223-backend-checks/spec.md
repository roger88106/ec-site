# Spec 223：バックエンドの機械の検査と静的解析を補う

ステータス：確定

## 1. 背景と目的

spec 181、182、186、192 の最後のレビューで、記載漏れ・誤記・重複を機械で見つける検査の候補と、静的解析とモジュールの境界の課題が残った。どれも今は、レビューで確認しているか、まだ確認していない。本 spec は、それらを機械の検査にし、検査で見つかった違反を修正する。

追跡の issue は [#223](https://github.com/roger88106/ec-site/issues/223) で、扱う issue は #202 と #217 である。#202 は、本文の項目と、spec 192 のレビューから加えたコメントの項目を扱う。作業ブランチは `223-backend-checks` である。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。

### 1.1 今の状態

spec 担当のセッションが、2026-10-27 の `develop`（d3174a65）のコードを検索して確認した。違反が 0 件の項目も、今後の記載漏れを防ぐために検査を追加する。

| 項目 | 今の違反 | 確認した内容 |
|------|----------|--------------|
| 秘密の値を持つ設定の `toString` | 0 件 | 秘密の値を持つ設定の型 4 つが、全て値を隠す `toString` を持つ |
| `security` のない店舗の操作 | 0 件 | 店舗の契約の 22 の操作が、全て `security` を持つ |
| ワイルドカードの import | 0 件 | main、テスト、tools のソースセットに 0 件 |
| イベントの発行の記録を直接読む待ち | 0 件 | 非同期のイベントの補助の外に、記録を読んで待つ統合テストはない。補助へ渡すために注入するテストは 2 つある |
| 補助を使わない税区分の登録 | 1 件 | 商品の API のテスト。spec 224 が修正する |
| spec の番号の検査の対象の外にある番号 | 6 件 | `build.gradle.kts` のコメントに 3 件、E2E の設定のファイルに 3 件 |
| 文書の置き場所の system property の読み方 | 3 か所 | 値が渡されないとき、メッセージなしで失敗する |
| 通知モジュールが組み立てる出荷モジュールの文言のキー | 1 件 | 出荷の通知のメール |
| `persistence/` の外の jOOQ | 1 件 | mock の出荷の問い合わせ。モジュールの外の共通の設定は除く |
| 管理画面の IdP の環境変数の既定値 | 3 か所 | 管理画面の認証の設定、ローカルの検査の script、CI |
| 地域のマイグレーションの生成の結果 | 1 行 | 先頭のコメントの文書のパスが違う。コミット済みのものは、今はない `docs/backend/` を指す |

- 契約の読み込みは、小文字でない HTTP メソッドと、パスの下の誤記の項目を無視する。無視した操作は契約にない要求として拒まれる（店舗と管理の認可の処理が、操作が見つからないときに拒否することを、コードで確認した）。ただし、起動で契約の誤りを検出できない。

### 1.2 規模

L とする。理由は次の 2 つである。

- [開発の進め方](../../rules/workflow.md) 第 4.2 節の「2 つ以上のモジュールにまたがる」に当たるため。変えるのは、通知と出荷のモジュール、共通コードと設定、管理画面の認証の設定、CI の検査の script である。
- 重複の検出のツールと基準、jOOQ の置き場所の規則の例外を、plan で決める必要があるため。

## 2. 用語

| 用語 | 意味 |
|------|------|
| 構成の検査 | 本番のクラスの依存と置き場所を確認する単体テスト（ArchUnit、Spring Modulith） |
| 契約の読み込み | 起動のときに OpenAPI の契約を読み、操作ごとの認可の条件を作る処理 |
| テストの補助 | 複数の統合テストが使う、データの作成と応答の読み取りの共通のクラス（在庫・カタログのテストデータ、JSON の読み取りなど） |
| spec の番号の検査 | コードとコメントに spec・plan・タスク・AC などの番号が残っていないことを確認する CI の検査の script |

用語集の「テストの補助」は、今はフロントの置き場所だけを書いている。バックエンドの置き場所を加えるかは plan で決める。他の 3 つは、spec の中だけで使う語である。

## 4. 目的と完了条件

### DS-223-1 設定と契約の記載漏れ・誤記（D / P1）

#202 の項目のうち、spec 182 のレビューから出た 3 つである。

- **DC-223-1** 秘密の値を持つ設定の型が、値を隠す `toString` を持つことを、構成の検査が確認する。秘密の値とみなす項目の名前は plan で決める。
- **DC-223-2** 権限の対応表の検査の script は、`security` のない店舗の操作を違反として失敗にする。token 不要を明示した操作は、今と同じく表の「不要」の行にする。
- **DC-223-3** 契約の読み込みは、パスの下に小文字でない HTTP メソッドがあるとき、起動に失敗する。
- **DC-223-4** 契約の読み込みは、パスの下に、HTTP メソッドと OpenAPI が定める項目の外の項目があるとき、起動に失敗する。

### DS-223-2 テストの書き方の取り決め（D / P1）

#202 の項目のうち、spec 181 のレビューから出た 3 つである。

- **DC-223-5** テストのソースセットのコードの重複を、CI の検査が検出する。ツールと、重複とみなす基準は plan で決める。
- **DC-223-6** 統合テストが、イベントの発行の記録を直接読んで待たないことを、検査が確認する。記録を読んで待つのは、非同期のイベントの補助だけである。
- **DC-223-7** テストの補助を除くテストが、在庫を直接作成しないことを、検査が確認する。
- **DC-223-8** テストの補助を除くテストが、税区分の登録の要求を直接送らないことを、検査が確認する。
- **DC-223-9** テストの補助を除くテストが、応答の JSON から ID を取り出す処理を直接書かないことを、検査が確認する。

DC-223-7〜9 は、その操作そのもののテスト（在庫の Repository のテスト、税区分の API のテスト、認可のテスト）を対象にしない。この 3 つの検査は、spec 224 のマージの後に加える（第 7 節）。

### DS-223-3 構成の検査と契約のテストの補助（D / P1）

#202 の項目のうち、spec 186 のレビューから出たもので、spec の番号の検査を除く 3 つである。

- **DC-223-10** 単体テストが文書の置き場所の system property を読む処理は、契約の補助と同じ方法にそろえ、値が渡されないときはメッセージ付きで失敗する。対象は、バックエンドの書き方、全体の設計、モジュールの設計書のディレクトリの 3 つである。
- **DC-223-11** 生成したコードとモジュールのパッケージの接頭辞は、構成の検査の補助の定数にあり、各テストが文字列で重複して持たない。
- **DC-223-12** エラーの種類の列挙を本番のクラスから探す処理は、構成の検査の補助の 1 か所にある。

### DS-223-4 spec の番号の検査の漏れ（D / P1）

#202 の項目のうち、spec 186 のレビューから出た spec の番号の検査の項目と、spec 192 のレビューから加えたコメントの項目である。

- **DC-223-13** spec の番号の検査は、記号と数字の間に区切りのない番号（`AC10` など）を検出する。
- **DC-223-14** spec の番号の検査は、全角の英字・数字・ハイフンで書いた番号を検出する。
- **DC-223-15** spec の番号の検査は、Gradle の設定のファイルのコメントを対象にする。
- **DC-223-16** spec の番号の検査は、リポジトリのルートと各パッケージの直下にある設定のファイルを対象にする。対象とするファイルの一覧は plan で決める。
- **DC-223-17** DC-223-13〜16 で新しく見つかる今の番号は、規則を言葉で書く形に書き換える（[コメントの書き方](../../rules/comments.md) 第 1 節）。

### DS-223-5 import と認証の情報の取り出し（D / P1）

#217 の項目のうち、静的解析の 2 つである。

- **DC-223-18** Checkstyle が、static の import を含む全てのワイルドカードの import を禁じる。
- **DC-223-19** 認証の情報から token を取り出す共通の操作（会員・運営者の取り出しを含む）を presentation 層の外から呼ばないことを、構成の検査が確認する。今の presentation 層の外の呼び出し元を例外として残すか、移すかは plan で決める。

### DS-223-6 モジュールの境界と、設定・生成物の重複（D / P1）

#217 の項目のうち、モジュールの境界と重複の 4 つである。

- **DC-223-20** 通知モジュールは、出荷モジュールの文言のキーを文字列で組み立てない。代わりに使う出荷モジュールの公開 API は plan で決める。
- **DC-223-21** jOOQ を使うのは `persistence/` のクラスだけであることを、構成の検査が確認する。mock の出荷の問い合わせを `persistence/` に移すか、規則の例外にするかは plan で決める。
- **DC-223-22** 管理画面の IdP の環境変数（認可サーバーの URL とクライアント ID）の既定値を 1 か所に置く。CI などで値を重ねて書く必要があるときは、その値が一致することを検査が確認する。
- **DC-223-23** 地域のマイグレーションの生成の処理は、コミット済みのマイグレーションと同じ先頭のコメントを書き、生成の結果がコミット済みのものと一致する。生成の処理の Javadoc に、適用済みのものに合わせる理由と、今の文書の置き場所を書く。理由：適用済みのマイグレーションは、コメントを変えても checksum が変わるので変えられないため（利用者の決定、2026-10-27）。

## 6. 非機能要件

- **DN-223-1** 消費者・運営者に見える振る舞いを変えない。出荷の通知のメールの文面を含む。
- **DN-223-2** API の契約とデータベースの構造を変えない。適用済みのマイグレーションを変えない。
- **DN-223-3** AC を追加・変更しない。
- **DN-223-4** 追加した検査は、本 spec の完了の時点のコードで違反が 0 件である。見つかった違反は、コードを規則に合わせて修正するか、規則の文書の例外の表に理由を書いて解消する。修正と例外のどちらにするかが文書で決まらないときは、作業を止めて利用者に確認する。
- **DN-223-5** 重複の検出の基準を今のコードに合わせて緩めたときは、緩めた値と理由を規則の文書に書く。
- **DN-223-6** 追加・修正した検査は、違反する例で違反を検出できることを確認する（構成の検査は違反の例のクラス、CI の検査の script はテストの違反の例）。
- **DN-223-7** 検査とテストを弱めない。補助へ移すテストは、確認の内容を変えない。
- **DN-223-8** カバレッジと mutation score が基準を下回らず、`./gradlew check` と `scripts/ci/check-all.sh` が通る。

## 7. 依存

| 相手 | 関係 |
|------|------|
| spec 222（#222。文書の整理） | 本 spec の実装は、spec 222 のマージの後に始める ※1 |
| spec 224（#224。統合テストの頑丈さとログ） | DC-223-7〜9 の検査は、spec 224 のマージの後に加える ※2。その他の DC の実装を spec 224 と並行してよいかは plan で決める |
| spec 225（#225。CI の検査の script） | 並行してよいかと順序は plan で決める ※3 |
| spec 226（#226。テストの書き方と E2E） | 並行してよいかと順序は plan で決める ※4 |

※1：spec 222 が、文書とコードのコメントの多くの用語を変えるため。

※2：spec 224 が修正する商品の API のテストの税区分の登録が、今の違反であるため。spec 224 は、統合テストが契約と realm の置き場所を読む処理もそろえるので、DC-223-10 は単体テストの読み取りだけを扱う。

※3：検査の script の共通の関数と、権限の対応表・spec の番号の script が重なりうる。

※4：テストの書き方の文書、E2E の設定のファイル、ローカルの検査の script（`scripts/dev/`）が重なりうる。

| 項目 | 扱う場所 |
