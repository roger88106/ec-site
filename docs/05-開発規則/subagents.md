# エージェントの作業フロー

エージェントがサブエージェントを使うときの規則。[開発の進め方](workflow.md)と [AGENTS.md](../../AGENTS.md) に従い、ここではサブエージェントへの任せ方だけを書く。

## サブエージェントへの任せ方

決定と理由は [サブエージェントへの任せ方で取り入れたもの](../04-決定記録/subagent-delegation.md)。

- フレームワーク（Spec Kit、OpenSpec、cc-sdd）は導入しない。必要な仕組みだけを取り入れる。
- 文書の本文の書き手は、[文書の書き方](writing.md)の「本文の書き手」の規則に従う。
- 既存の文書の言い回しのレビューには、目指す書き方の見本と、書き方の規則（[文書の書き方](writing.md)）を渡す。変えた文書のレビューでは、差分のファイルと spec も渡す。和語の言い換えと、論理・比喩などの 2 つの観点を両方見るように指示する。
- 文書の検査に textlint を使わない。
- レビューは、実装の過程を見ていないサブエージェントに任せる（skill `review`）。時点は「役割と作業の流れ」。1 タスクごとにはレビュー役を立てず、`[リスク]` のタスクの後と、段階の最後、spec の最後などの決まった時点にレビューする。
- 実装は、1 タスクごとに新しい実装役が行う。`[テスト]` と対応する実装は 1 組で、同じ実装役が順に行う。
- 設計の判断が必要なときは、実装役が作業を中断して報告し、spec 担当のセッションが plan から判断する。文書にない設計の判断は、利用者に質問する（[開発の進め方](workflow.md)の「中断して質問する条件」）。
- 実装役に渡すのは、タスクの全文、関係する plan の節、決まったインターフェース、関わる書き方の文書の名前と守る規則の要約。曖昧な点の決定と報告の書き先も渡す。会話の履歴と計画の全体は渡さない。
- サブエージェントは新しい文脈で始まるので、規則は要約と対象を指示に書いて渡し、原文の全体を読ませない。
- 気づきを後のタスクに渡すときは、tasks のタスクの下に書く。
- 詳しい報告はファイル（`/.local/` の下）に書かせ、返すのは状態・commit・テストの要約・懸念だけにする。
- 同じ作業ツリーで、ファイルを書くサブエージェントを同時に動かさない。並行して動かすのは読むだけの作業か、別の作業ツリー。
- 2 回修正しても通らなければ、原因の調査を調査役（高性能）に任せる。
- モデルを常に明示する。

## 任せる作業とモデル

| 作業 | 例 | 区分 | effort | 条件 |
|------|----|------|--------|------|
| 資料の収集（判断しない） | 該当箇所の要約、事実の確認 | 軽量 | 低 | 固定の分を含めて 1 回の要求が 10 万 token 以下の量に限る。超えるときは範囲を分けるか、汎用にする |
| 機械的な作業 | 一覧の作成、grep の照合、同じ形の置き換え | 軽量 | 中 | 同上 |
| 実装 | タスクの実装 | 汎用 | 中 | 範囲を小さく分ける（1 つのサブエージェントのツールの呼び出しを数十回に収める） |
| `[リスク]` の実装 | 金額、セキュリティ、データの移行 | 高性能 | 高 | |
| 判断・文書の本文 | 規則の当てはめ、日本語の要点から書く | 汎用 | 中 | 範囲を小さく分ける |
| レビュー | 「役割と作業の流れ」の時点 | profile の表で決める | 重要な観点（「レビューの時点と profile」の表の行）は effort 高、一般の観点は effort 中 | |
| 原因の調査 | 2 回修正して通らない失敗 | 高性能（調査役） | 高 | 調査役が 2 回で特定できないときは最上位 ※1 |
| spec 担当のセッション | 設計の決定、判定、利用者との相談 | 高性能 | 中 | サブエージェントに任せない |
| issue 担当のセッション | 起票、資源の配分、危険度が低い変更のマージ、監視 | 汎用 | 中 | 危険度の判定に迷うときは利用者に聞く |

※1：最上位は、調査役が 2 回で特定できないときと、利用者が指定したときだけ使う。使えないプランでは使わず、高性能で代える。使えるプランでは、最上位の使用が週の使用量の 50% を超えたら使わない。最上位の使用も 5 時間と週の使用量に数えるので、止める閾値にも従う。

### 運用の規則

- spec 担当のセッションは、サブエージェントの結果を 1 つずつ受けて作業を進めず、全部がそろってからまとめる。理由：結果を受けるたびに、長い文脈を処理し直すため。
- 語ごとの規則（和語の言い換えなど）は、語ごとに 1 回決め、機械（script）か文脈のサブエージェントで全体に適用する。行ごとのレビューで 1 件ずつ判断しない。
- 文脈で判断する候補（言い回し、論理）は、同じ範囲を汎用で 2 回実行して和集合を取り、高性能なモデルが採否を判断する。
- 並行して動かすサブエージェントの一時ファイルには、担当の範囲の名前を付ける。
- 語ごとの規則、和集合、一時ファイルの名前の理由は[エージェントの作業フローの調べた仕組みと実績](../07-記録/subagents-results.md)の「運用の規則と並行の判断の理由」。
- サブエージェントへの指示と呼び出しの説明は、日本語だけで書き、中国語の字を含む語を使わない。

実績は [エージェントの作業フローの調べた仕組みと実績](../07-記録/subagents-results.md)の「実績」。

## 役割と作業の流れ

### 役割

| 役割 | 数 | 担当 |
|------|----|------|
| issue 担当のセッション | 1 つ | 起票、起動と開始の指示、資源の配分、マージ（担当と条件は [マージと後片付け](merging.md)の「マージの許可と後片付け」） |
| spec 担当のセッション | spec ごと | spec・plan・tasks、サブエージェントへの指示、合否の判定、マージと後片付け |
| 実装役・資料収集役・レビュー役・調査役のサブエージェント | 必要なとき | 実装、資料の収集、レビュー、原因の調査を、それぞれ分けて担当する |

サブエージェントの定義のファイルは、実装役が `.claude/agents/implementer.md`、資料収集役が `researcher.md`、レビュー役が `reviewer.md`。調査役は定義を使わない標準のサブエージェントである。

- issue 担当のセッションは、他に、`develop` の CI を確認し、ステップの終わりに集計と振り返りを行う。spec 担当のセッションが自分をアーカイブできないときの代行は skill `sessions`。
- spec 担当のセッションは、コードを書かず、書くのは、書き手を使う条件（[文書の書き方](writing.md)の「本文の書き手」）に当てはまらない文書の修正だけ。実装は実装役が行う（「サブエージェントへの任せ方」）。
- 合格・不合格の判定は、spec 担当のセッションが行う。理由：サブエージェントに渡らなかった情報を持つのは、spec 担当のセッションだけのため。
- 実装役・資料収集役・調査役のモデルは、「任せる作業とモデル」の表で決める。校閲役（検出役、確認役、単独の校閲役）のモデルは、skill `review` の docs-review.md の「手順」の校閲の手順で決める。校閲役の定義は `.claude/agents/ja-proof*.md`。これらの定義にはモデルを書かず、呼び出しのときに指定する。

### セッションの間のやり取り

手順（起動、開始の条件、資源の配分、待機、メッセージ、遠隔操作）は skill `sessions`。

- 2 つのセッションは親子の関係にあり、ターンの終わりに親へ通知される。
- issue 担当のセッションが spec 担当のセッションを起動し、開始の条件を渡す。条件を満たすまで、spec 担当のセッションは始めない。始める前に、[開発の進め方](workflow.md)の「実装を始める前の照合」に従って照合する。
- 記録は、追跡の issue のコメントに残す（開始、pull request、完了）。
- skill `handoff` は、spec 担当のセッションを途中で別のセッションに替えるときだけに使う。
- 単線の定義は[作業の形と使用量](resources.md)の「作業の形と profile の決め方」。

### タスクの実装

- `[P]` のタスクは、作業ツリーを分けた実装役が同時に実装する。`[P]` でないタスクは順に実装する。
- 作業ツリーでバックエンドや画面を動かす実装役は、始めにスロットを割り当て、作業ツリーを削除する前に解除する（手順は[開発環境の起動](../06-手順書/setup.md)の「スロット（作業ツリーごとの環境）」。エージェントの待ち方などは skill `local-dev` の「スロット（作業ツリーごとの環境）」）。

### レビューの時点と profile

レビューの量は、profile（厚め・標準・節約）で決める。profile の決め方は [作業の形と使用量](resources.md)の「作業の形と profile の決め方」。

| 時点 | 厚め | 標準 | 節約 |
|------|------|------|------|
| `[リスク]` のタスクの後 | 高性能 | 汎用 | 行わない |
| 段階の最後：一般の観点 | 汎用を 2 回（和集合） | 汎用を 1 回 | 汎用を 1 回 |
| 段階の最後：重要な観点（金額、セキュリティ、`[リスク]`、ファイルをまたぐ影響） | 高性能と汎用（和集合） | 高性能を 1 回 | 汎用を 1 回 |
| spec の最後 | 3 つの観点（段階をまたぐ影響、ファイルをまたぐ影響、spec との一致）を高性能で 1 回。文を削る差分では、削った文の行き先の観点も加える | 同左 | 同左 |
| pull request の前 | 完了の定義の確認と、使うツールの組み込みのコードレビュー。特定の経路を変える spec は、文脈を持たない高性能のレビュー役を 1 回加える（下の箇条） | 同左 | 同左 |
| セキュリティのレビュー | 認証・支払・権限の経路を変える変更で、pull request の前に行う | 同左 | 同左 |
| リリースの前 | 高性能（マイグレーション、設定、互換性、リリースの説明の案） | 汎用 | 汎用 |

- 組み込みのコードレビューの level は [AGENTS.md](../../AGENTS.md) の「レビューのツール」の表で指定し、件数の上限は既定のままにする。セキュリティのレビューに未解決の指摘があれば、マージしない。ツールの名前も同じ表。
- 危険度が高い変更は、profile によらず、重要な観点のレビューを高性能で行う。
- 危険度は、実装の前に、変える予定のファイルを `scripts/ci/risk.json` の経路と照合し、issue の「危険度：高」の行も見て確認する。`node scripts/ci/risk.mjs` は差分と spec の宣言から判定するので、最初の commit の後にも実行して確認する。規模 S で危険度が高いときは、規模 M と同じく、pull request の前に spec の最後のレビュー（表の「spec の最後」の行）を行う。記録は pull request の本文の「レビューの記録」に書く。理由：pull request を作った後に危険度が高いと分かり、レビューの計画を変えることがあったため。
- 同じ対象の繰り返しの上限と、上限での手順は[書き方の規則とレビュー](review.md)の「レビューの収束」、重要度の定義と、時点ごとに返す重要度は[書き方の規則とレビュー](review.md)の「重要度」。
- skill `review` の手順 1〜6 のレビュー（`[リスク]` のタスクの後、段階の最後、spec の最後、全体のレビュー）は、レビュー役の定義で行う。理由：指示の文書と memory のない第三者に見させるため。手順 7〜10 は別の形で行う。
- hook（`scripts/dev/hooks/`）、CI の検査の script（`scripts/ci/` の、変更や文書を判定して CI を失敗させるもの。例：`risk.mjs`）、認証・支払・権限の経路のコードを変える spec は、profile によらず、pull request の前に、文脈を持たない高性能のレビュー役（`reviewer`）を 1 回加える。観点は、拒否・判定を別の書き方で回避できないか。理由は[エージェントの作業フローの調べた仕組みと実績](../07-記録/subagents-results.md)の「見逃しの一覧の種類」。
- レビューごとに token、時間、指摘の数、採用した数を記録し、profile を再検討する材料にする。

### 並行

- 並行の単位は、spec 1 つに、セッション、作業ツリー、ブランチ、pull request を 1 つずつとする。
- 並行してよい条件は、次の 3 つを全て満たすこと。
  - モジュールが違う。
  - 契約や同じテーブルを同時に変えない。
  - 依存がない。
- 並行する spec の依存は、追跡の issue に書く。
- spec を分けるとき、または並行してよいと判断するときは、spec の範囲だけで決めない。関わる全ての spec の plan と tasks（規模 M は spec の tasks）の、変えるファイルを照合してから決める。理由は[エージェントの作業フローの調べた仕組みと実績](../07-記録/subagents-results.md)の「運用の規則と並行の判断の理由」。
- 照合の前（spec の段階）は、並行の可否を決めない。spec には「並行の可否は plan の段階で決める」と書く。規模 M は、tasks を書くときに決める。
- 照合の結果として、重なるファイルと実装の順序を、plan（規模 M は spec の tasks）に書く。
- 共有の文書（AC 一覧、用語集）の衝突は、後でマージする pull request が `develop` を取り込んで解消する。

作業ツリーの置き場所と、作業ツリーのセッションが読む設定・定義・skill は、skill `sessions` の[作業ツリーのセッションが読むもの](../../.claude/skills/sessions/session-reads.md)にある。

## モデルや設定を替えるとき

モデル、レビューの指示、profile、サービスを替えるときは、見逃しの一覧で新しい設定を試してから決める。

校閲役は、見逃しの一覧（label「見逃し」）でなく、評価の一覧で採点する（[評価の一覧](../../.claude/skills/review/evals/ja-proofread.md)）。

### 見逃しの一覧

- 見逃しの一覧は、GitHub の issue の label「見逃し」とする。label で一覧にできる ※2。
- 理由：Git に置くと並行する spec が同じファイルを変えて衝突し、`/.local/` に置くとクラウドのセッションと他のマシンから読めないため。
- 加える時点は、不具合の issue の起票（[起票と記録の操作](issues.md)の「起票」）。原因の変更がレビューを通ったか、エージェントがマージしたものに限る。
- 本文の「関連」に、見逃した pull request と、エージェントがマージしたかを書く。
- 見逃した時点も「関連」に書く。段階 n、spec の最後、pull request の前、`[リスク]` のタスクの後のどれかで、名前はレビューの記録の表と同じにする。

※2：`gh issue list --label 見逃し`。

### 替える手順

1. 見逃しの一覧の各件について、見逃した pull request の差分（修正の前）を新しい設定のレビューに渡し、見つけた件数を数える。
2. 対象ごと（モデルの区分、レビューの観点、profile、段階ごとのレビュー、引き継ぎの文書、1 タスクごとの実装役、調査役）に、残すか変えるかを判断する。
