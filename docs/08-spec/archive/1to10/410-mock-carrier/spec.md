# Spec 410：公開の環境で物流の mock の画面を表示せず、物流のフラグなしで起動できるようにする

種類：機能　規模：M　ステータス：確定

## 背景と目的

物流の mock の画面は、認証なしで使える（`SecurityConfig.java:124` の許可の一覧。CSRF も無効）。今は物流の mock フラグを立てないとバックエンドの起動に失敗する（`MockCarrierRequiredConfig`、AC-228）。一方で、公開の環境ではフラグを立てない方針である（`docs/02-設計/backend-architecture.md:224`）。この 2 つは両立しない。公開の環境で運用するにはフラグを立てるしかなく、そのとき次の 2 つが起きる。

- 認証なしで、誰でも出荷の配送状態を「返送」にできる。「返送」になると、運営者が注文をキャンセルできる状態になる。キャンセルするのは運営者なので、それだけでは返金されない。
- `Host` ヘッダーを偽装すると、サーバーから指定のホストとポートへ署名付きの通知を送らせられ、応答のステータスと接続の成否が画面に表示される。パスは通知のエンドポイントに固定、方法は POST に固定、応答の本文は返らない。

この spec は、公開の環境で物流の mock の画面を表示せず、物流のフラグなしでバックエンドが起動するようにする。利用者は issue #410 のコメント（2026-11-06）で、次の 3 つを決めた。

- 公開の環境では、物流の mock の画面を表示しない。
- AC-228 を変更し、フラグがなくても起動できるようにする。
- 実際の物流サービスを接続するまでは配送状態が進まないので、出荷後のキャンセルが事実上できない。このこと（出荷後のキャンセルができないこと）を受け入れる。

追跡の issue は #410。関わる文書は、[出荷モジュール](../../../../03-機能仕様/shipping.md)、[出荷の設計](../../../../02-設計/shipping.md)、[バックエンドのアーキテクチャ](../../../../02-設計/backend-architecture.md)。

## スコープ

| 含める | 含めない |
|--------|----------|
| 物流のフラグがないときに使う、接続していない物流サービスの実装を置く（起動の失敗をやめる） | 実際の物流サービスの接続 |
| AC-226、AC-228、AC-245 を変更する。AC-229 は、フラグがない場合のテストを追加する | 物流の mock フラグを立てたときの、mock の画面の認証と宛先の修正 |
| 機能仕様、設計、手順書、用語集の更新 | 公開の環境で誤ってフラグを立てたことの検出 |
| | 認可の許可の一覧の変更 |

含めないものの理由は Non-goals に書く。

決定：

1. 規模は M にする。理由：AC を変えるが、API の契約と DB の構造を変えず、出荷モジュールの中で閉じるため。
2. フラグがないときの物流サービスの実装は、追跡の開始の依頼を受けても何も送らず成功を返す実装にする。置き場所は物流サービスとの接続のパッケージとし、mock のパッケージに置かない。理由：mock の画面と一緒に使うものではなく、公開の環境で動くものであるため。今の起動に失敗させる設定は削除する。

   | 論理名 | 識別子 |
   |--------|--------|
   | 接続していない物流サービス | `UnconnectedCarrierTracking` |
   | 物流サービスとの接続のパッケージ | `infrastructure/carrier` |
   | 起動に失敗させる設定 | `MockCarrierRequiredConfig` |

3. 接続していない物流サービスが有効なとき、起動のときに 1 回、警告のログを出力する。理由：フラグの設定漏れは今まで起動の失敗で検出できたが、この変更で起動に成功するようになるため。
4. 通知のエンドポイントは、フラグによらず今のまま置く。署名の鍵（環境変数 `CARRIER_WEBHOOK_SECRET`）も必須のままにする。公開の環境では、推測できない値を設定し、どこにも渡さない。理由：鍵を知らない送信元の通知は署名の確認で処理されず、物流サービスを接続するときに同じエンドポイントを使うため。
5. 開発の環境で mock を有効にする方法は変えない。ローカルの設定と統合テストの設定は、フラグを立てる。E2E と Stripe の sandbox の設定は、ローカルの設定のフラグを受け継ぐ（AC-231。`ProfileFlagsTest` で確認する）。
6. 認可の許可の一覧（`/mock-carrier/**`）は変えない。理由：フラグがないとき画面がなく、URL は 404 になるため（AC-229）。

## 受け入れ条件

### US-410-1 物流サービスなしでの公開（B / P1）

- **AC-410-1** 物流のフラグを立てないとき、出荷を登録できる。配送状態は「出荷済み」のままで、追跡の開始の依頼は完了する（未完了のイベントが残らない）。
- **AC-410-2** 物流のフラグを立てずに起動すると、物流サービスに接続していないことを警告のログに出力する。

```
物流のフラグを立てなくても、バックエンドは起動する。根拠は[出荷モジュール](shipping.md)の「物流サービス」。
```

AC-226（決済）の新しい内容：

```
決済と物流に、それぞれ mock フラグがある。フラグを立てたサービスだけが mock を使う。立てなければ、決済は本番の実装を使い、物流は接続していない物流サービスを使う。根拠は[出荷モジュール](shipping.md)の「物流サービス」。
```

AC-245（common）の新しい内容：

```
本番の jar を、ローカルの profile を指定して起動しても、mock フラグとローカル用の秘密情報は読まれない。物流のフラグがないので、物流の mock の画面は見つからない（404）。根拠は[バックエンドのアーキテクチャ](../02-設計/backend-architecture.md)の「外部連携（決済・物流）」。
```

AC-229 と AC-230 の内容は変えない。AC-229 の文は今のまま成り立つ。今までは、フラグがないと起動に失敗し、物流の mock の画面の 404 を確認できなかったので、この 404 のテストを追加する。AC-230 は、フラグだけで選ぶことが変わらない。

## 業務ルール

- **BR-410-1** 実際の物流サービスを接続するまで、フラグのない環境の配送状態は「出荷済み」から進まない。出荷後のキャンセルは配送状態が「返送」の注文に限られるので（`Order.java:234-236`）、事実上できない。理由：利用者が受け入れたため（issue #410 のコメント）。
- **BR-410-2** 物流は本番の実装がないので、フラグがなければ接続していない物流サービスを使い、起動に失敗しない。BR-30 の今の規則（[バックエンドのアーキテクチャ](../../../../02-設計/backend-architecture.md)の「外部連携（決済・物流）」）に、この例外を書く。

## 非機能要件

- **NFR-410-1** API の契約と DB の構造を変えない。
- **NFR-410-2** ローカルの開発、E2E、統合テストで、物流の mock の画面と通知を今までどおり使える。

## Non-goals

| 項目 | 理由 |
|------|------|
| 実際の物流サービスの接続 | 接続先が未定で、利用者が今は接続しないと決めたため |
| mock の画面の認証と、通知の宛先を設定から取ること | mock の画面はローカル、E2E、統合テストだけで使うため |
| 公開の環境で誤ってフラグを立てたことの検出 | 環境変数で明示してフラグを立てる誤りは、この spec の対象外とする ※1 |
| 物流の通知のレート制限と公開の URL | 公開の前提の一覧にあり、デプロイ先を決めるときに決める |

※1：フラグを立てないことは公開の前提の一覧に書いてあり、フラグを立てる設定ファイルは本番の jar に入らない（`checkBootJar`）。
