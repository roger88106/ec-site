## 1. 地域モジュール（US-56、NFR-20）

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| モジュール | `region` を新しく作る。レベル B。責務は都道府県・市区町村・郵便番号のマスターデータ ※1 | `ModulithTest` |
| 依存 | `common` だけに依存し、業務のモジュールに依存しない。イベントを出さない | `ModulithTest` |
| 公開 | `api/` に参照の操作だけを置く（都道府県の一覧、都道府県の市区町村の一覧、市区町村をコードで引く、郵便番号で引く） | 統合テスト |
| 使う側 | `order` と `reporting` は、腐敗防止層（`RegionDirectory`）で包んで呼ぶ | 見直しで読む |
| スキーマ | `region` のスキーマに、都道府県・市区町村・郵便番号の 3 つの表を置く。他のモジュールの表から外部キーを張らない | 統合テスト |
| コード | 都道府県は 2 桁、市区町村は 5 桁（地方公共団体コードの検査数字を除いたもの）。文字で持つ | 単体テスト |
| 郵便番号の表 | 郵便番号・市区町村のコード・町域名・並び順。町域名が注記だけの行は、町域名を空にする（AC-283）。どこからも参照しない（BR-37） | 統合テスト |

※1：1 → 10 で別のサービスに切り出せるようにする（利用者の決定）。依存がなく、使う側が腐敗防止層で包むので、切り出すときは腐敗防止層の実装を HTTP の呼び出しに替えるだけで済む。API は EC に固有の判断を持たず、参照だけにする。名前を「住所」にしないのは、お届け先や会員の住所録（1 → 10）を管理するモジュールと紛れないため。

### 1.1 店舗 API（AC-250、253、254、256）

| 操作 | パス | 応答 |
|------|------|------|
| 都道府県の一覧 | `GET /api/store/prefectures` | コードの順の、コードと名前 |
| 都道府県の市区町村の一覧 | `GET /api/store/prefectures/{prefectureCode}/municipalities` | コードの順の、コードと名前。都道府県がなければ 404 |
| 郵便番号で引く | `GET /api/store/postal-codes/{postalCode}` | 住所の一覧（都道府県、市区町村、町域）。ないときは 200 で空の一覧 ※2 |

- 3 つとも token なしで使える（店舗の情報と同じく、契約に `security` を書かない）。タグは `region`。
- 実装は `region` の presentation に置く（`storefront` を通さない）。理由：切り出すときに、店舗 API の中の地域の操作を、そのまま移せるため。
- `/api/store` は C 側の契約（`store.yaml`）の URL の範囲で、`storefront` モジュールではない。契約を店舗 API に置くのは、C 側と B 側を API の範囲で分け、認可を契約から決めるため（[バックエンドのアーキテクチャ](../../backend/architecture.md) 第 4、7.2 節）。切り出した後も、この 3 つの操作の契約を変えなければ、店舗画面は変わらない。
- 応答はマスターデータの更新でしか変わらないので、店舗画面は API の応答を取り直す間隔の設定で取る（[フロントの書き方](../../frontend/coding.md) 第 8.1 節）。

※2：ない郵便番号は、誤りではなく「補えるものがない」なので（AC-256）。

### 1.2 最初のデータ（AC-259、260、NFR-21）

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| 出典 | 日本郵便の「住所の郵便番号（1 レコード 1 行、UTF-8 形式）」の CSV だけを使う ※3 | 見直しで読む |
| 市区町村 | 郵便番号のデータの地方公共団体コード・都道府県名・市区町村名を、重複を除いて全件入れる。都道府県のコードは市区町村のコードの先頭 2 桁 | 統合テスト（件数が 47 と、総務省の一覧の件数に合う） |
| 郵便番号 | seed・テスト・E2E が使う郵便番号と、変換の確かめに使う郵便番号（町域が複数、注記だけ、複数の行に分かれた町域）だけを入れる。一覧は Git に入れる | 統合テスト |
| 変換 | 郵便番号のデータを読み、注記を除き、マスターデータの行にする処理を、`region` の infrastructure に置く ※4 | 単体テスト（注記の種類ごと） |
| 生成 | Gradle のタスクで、ダウンロードした CSV から、最初のデータを入れる Flyway のマイグレーションを作る。CSV は `/.local/` に置き、Git に入れない。作ったマイグレーションは Git に入れる | タスクを流して差分を見る |
| ライセンス | 出典と利用の条件を[依存とライセンス](../../reference/licenses.md)に書く | 見直しで読む |

※3：市区町村の一覧と郵便番号を同じ出典から作るので、郵便番号の市区町村が一覧にない、ということが起きない。郵便番号のデータの地方公共団体コードは総務省のコードと同じなので、1 → 10 で市区町村を国の API から取るようにしても、郵便番号の表とはコードでつながり、名前で照らさずに済む（利用者と確かめた）。

※4：1 → 10 の取り込みの仕組みから、同じ変換を使うため（NFR-21）。生成のタスクの入り口は本番の jar に入れない（別の source set）。

## 2. お届け先のコード（US-54、56、BR-34、35）

### 2.1 注文

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| 持つ値 | お届け先は、都道府県のコードと名前、市区町村のコードと名前、市区町村より下の住所を持つ。名前は注文の時点の写し（BR-35） | 統合テスト |
| 注文の確定 | 都道府県と市区町村のコードを、`region` の API で確かめる。市区町村がない、または都道府県に属さなければ 400（`INVALID_MUNICIPALITY`）。名前は `region` から取り、リクエストで受けない（AC-251） | 統合テスト |
| 都道府県の表 | 注文のお届け先の都道府県の一覧をなくす（AC-263） | 見直しで読む |
| 住所の上限 | 市区町村より下の住所は、今と同じ 200 文字まで | `FieldConstraintContractTest` |
| レポートの写し | レポート用の注文の写しは、都道府県の名前でなくコードを載せる | 統合テスト |

### 2.2 契約

| 対象 | 変更 |
|------|------|
| 店舗 API の注文の確定のリクエスト | お届け先に `prefectureCode`、`municipalityCode` を受け、`prefecture` をなくす。`address` は市区町村より下 |
| 店舗 API・管理 API の注文の応答 | お届け先にコードと名前（`prefectureCode`、`prefectureName`、`municipalityCode`、`municipalityName`）を返す。リクエストと応答の型を分ける |
| 管理 API の都道府県別の売上 | `prefectureName` を足す（AC-262） |

### 2.3 既存の注文の移行（AC-261）

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| 順序 | `region` の表と最初のデータのマイグレーションの後に、注文の移行を置く | 統合テスト（移行の前の形の行を入れてから流す） |
| 都道府県 | 都道府県名からコードを引く | 同上 |
| 市区町村 | 同じ都道府県の市区町村のうち、住所の先頭に一致するいちばん長い名前を市区町村にし、住所からその名前を除く | 同上 |
| 照らせない注文 | 1 件でもあれば、注文の番号を示して移行を失敗させる | 同上 |
| 列 | 都道府県のコード・名前、市区町村のコード・名前を、すべて必須にする | 同上 |

- 移行の SQL は、一度だけ `region` の表を読む。他のモジュールの表を読まない規則（[バックエンドのアーキテクチャ](../../backend/architecture.md) 第 3 節）の例外とし、移行の SQL のコメントに理由を書く ※5。
- seed（ローカル、E2E）は、新しい形で書き直す。

※5：既存の注文をマスターデータと照らすには、両方の表を同じ所で読むしかない。移行の後は、`order` から `region` の表を読まない。MVP はデプロイしないので、本番のデータの移行はない。

| seed | レポートの seed の都道府県の表をなくし、注文の seed のコードを使う | 見直しで読む |

## 3. 店舗画面のお届け先（US-54、55）

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| 欄 | 郵便番号、都道府県（選ぶ）、市区町村（選ぶ）、市区町村より下の住所の順。都道府県の表のファイルをなくす（AC-248、250） | 結合テスト |
| 都道府県の一覧 | 注文手続きのページを作るときに店舗 API から取る | 結合テスト |
| 市区町村の一覧 | 都道府県を選んだときに、サーバーアクションで店舗 API から取る。都道府県を選び直すと、市区町村の選択を外す（AC-249） | 結合テスト |
| 郵便番号で補う | 郵便番号が 7 桁（ハイフンを除いて）になったら、サーバーアクションで引く。結果の都道府県と市区町村を選び、町域が 1 つで住所の欄が空なら、町域を住所の欄に入れる（AC-255） | 結合テスト |
| 複数の結果 | 住所の都道府県と市区町村がすべて同じなら、それを選ぶ。町域は入れない。都道府県か市区町村が違えば、何も補わない ※6 | 結合テスト |
| 補えないとき | 結果がない、または通信に失敗したら、何も補わず、メッセージも出さない（AC-256） | 結合テスト |
| 補った後 | どの欄も変えられる（AC-257） | 結合テスト |
| 注文の詳細 | 店舗画面・管理画面は、都道府県名・市区町村名・住所の順に出す（AC-252） | 結合テスト |

※6：1 つの郵便番号が 2 つの市区町村にまたがることがある。どちらかを選ぶと誤りを補うことになるので、消費者に選ばせる。

## 4. 入力のエラーの文（US-57）

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| 店舗画面 | 注文手続きの欄ごとの文を、API の応答の文のまま出す。画面の欄ごとの文言（`checkout.fieldErrors`）をなくす（AC-264） | 結合テスト |
| 形の検証の文 | 形の検証（契約の `pattern` など）の誤りの文は、項目のパスごとに業務のエラーのコードを対応づけられる。対応があれば、そのコードの文と差し込む値を使い、なければ今の種類ごとの文 ※7 | 統合テスト |
| 対応づける項目 | お届け先の郵便番号と電話番号（AC-265） | 統合テスト |
| 文の数字 | エラーの文の数字（金額の下限、税率の範囲、価格の下限、郵便番号と電話番号の桁数、画像の形式の一覧）を、ドメインの定数からの差し込みにする（AC-266） | 単体テスト（文に数字がない） ※8 |
| 画面の文言の数字 | 管理画面の画像の説明の数字と形式の一覧を、契約の値の差し込みにする。契約の値が要るので段階 7 で行う | 結合テスト |

※7：業務の検証（ドメイン）が同じ誤りに出す文と同じにし、どちらで見つかっても消費者に同じ文を出すため。対応の表は、そのモジュールの presentation に置く。

※8：`messages.properties` の文に数字がないことを、CI の検査（`message-comments` の隣）で確かめる。例外は検査の許可の一覧に書く。

## 5. 操作の可否と理由（US-58）

| 対象 | 契約の変更 | 画面 |
|------|------------|------|
| 店舗の注文のキャンセルの申請（AC-267） | 変えない（キャンセルの申請の結果は、今も応答にある） | 却下は、申請の結果が却下のときだけにする。注文の状態から推し量る判定をなくす |
| 管理の注文のキャンセル（AC-268） | 注文の操作に、キャンセルの時に在庫に戻すかを聞くか（`cancelAsksRestock`）を足す | キャンセルの確認は、この旗で出し分ける |
| 管理の商品の削除（AC-269） | 商品の操作に、削除できない理由（`deleteBlockedReason`。列挙。今は C 側に表示されたこと、の 1 つ）を足す。削除できるときは省く | 削除できない理由は、この値で出す |
| 管理の分類（AC-270） | 分類の木の節に、子の分類を足せるか（`actions.addChild`）を足す | 子の分類を足す操作をこの旗で出し分ける。分類の深さの定数をなくす |

- 画面の判定をなくしたことは、見直しで読み、画面の中の注文・商品の状態の比較を探して確かめる（AC-271）。

## 6. 上限と形式（US-59、AC-276、282）

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| 画像の形式 | 管理 API の画像の受け付けのリクエストの形式に `enum`、大きさに `maximum` を書く。商品の画像の一覧に `maxItems` を書く（AC-272） | `FieldConstraintContractTest` |
| 管理画面の画像 | 形式・大きさ・枚数を、契約から書き出した定数から取る。手で書いた定数をなくす | 結合テスト |
| 分類の深さ | 契約の `maximum`（今は 3）とドメインの定数の一致を確かめる（AC-273） | `FieldConstraintContractTest` |
| 深さの追従 | ドメインの定数の深さまで分類をつなぎ、いちばん深い分類の商品が、いちばん上の分類の絞り込みで出ることを確かめる。定数を変えて DB の制約か絞り込みが追従しなければ、このテストが失敗する（AC-282） ※9 | 統合テスト |
| バリアントの追加 | 応答に `Location`（`/products/{productId}/variants/{variantId}`）を入れる（AC-276） | 統合テスト |

※9：絞り込みの SQL は今の 3 段の展開のまま変えない。値を変えるときにテストが知らせれば足りるため（BR-33）。

## 7. エラーのコードの契約（AC-274、275）

| 決定 | 内容 | 確かめ方 |
|------|------|----------|
| 全体の列挙 | 店舗 API と管理 API に、その API が返しうるエラーのコードの列挙（`ErrorCode`）を置き、エラーの本文の `errorCode` をその型にする | 生成した型 |
| 操作ごとの一覧 | 各操作に、返しうる業務のエラーのコードを拡張の項目（`x-error-codes`）で書く。共通のエラー（認証、権限、入力の検証、見つからない、競合 など）は書かず、すべての操作で許す ※10 | 統合テスト |
| 全体と一覧の一致 | API ごとに、全体の列挙が、操作ごとの一覧と共通のエラーの和と一致する | 単体テスト |
| バックエンドとの一致 | バックエンドのすべての `XxxErrorCode` の定数が、どちらかの API の全体の列挙にあり、列挙のすべての値がバックエンドにある（AC-275） | 単体テスト |
| 応答の確かめ | 統合テストで返したエラーの本文の `errorCode` が、その操作の一覧か共通のエラーにあることを、すべての統合テストで確かめる ※11 | 統合テスト |
| 画面 | エラーのコードで分ける所（注文手続き、管理画面の競合など）は、生成した型の値で比べる | 型の検査 |

※10：openapi-typescript は拡張の項目から型を作らないので、画面の型は全体の列挙から作る。操作ごとの正しさはバックエンドの統合テストで確かめる。

※11：MockMvc の結果を、テストの設定で毎回確かめる。操作の照らし方は、認可で契約を読む処理（`OpenApiOperations`）を使う。

## 8. 列挙・日本時間・税（US-60）

| 制約の一致 | 列と列挙の対応の表を持ち、DB の制約の値と列挙の値が一致することを確かめる。表に足していない列挙の列があれば失敗する | 統合テスト |
| 日本時間 | `common` に業務の時間帯の定数を置き、注文番号の日付、年齢の基準日、注文の一覧の日付の範囲、レポートの日はそこから取る（AC-280）。seed の SQL は除く | 見直しで読む、既存のテスト |
| 時点の税率 | 税区分の照会の今の税率と、税率の予定の判定を、税区分の時点の税率の判定に寄せる（AC-281） | 既存のテスト |
| 税込価格の SQL | 今の一致のテストを残す | 既存のテスト |
| 規則 | 列挙の写し方を[バックエンドの書き方](../../backend/coding.md) 第 1.3 節に足す | 見直しで読む |

※12：`switch` 式は列挙のすべての値を書かないとコンパイルに失敗するので、値を足して写し忘れると気づける（AC-277）。

## 9. 値の置き場所（BR-33）
