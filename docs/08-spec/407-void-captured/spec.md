# Spec 407：売上確定済みの与信の取消を、返金へ進める

種類：機能　規模：M　ステータス：草案

## 背景と目的

決済サービスで売上の確定が済んだのに、その応答がこのシステムに届かないことがある。決済サービスの SDK は同じ冪等キーで 2 回まで再試行する。再試行も全て失敗するか、インスタンスが確定を反映する前に停止すると、支払は与信済みのまま残る。

その後に運営者が出荷をやり直さず注文をキャンセルすると（運営者の判断か、消費者の申請の承認）、返金されない。経過は次のとおり。

- 与信の取消が決済サービスに拒否され続ける。
- 支払は与信の取消待ちのまま残り、イベントは再発行の上限で止まる。
- 消費者は請求されたまま返金されず、注文はキャンセルになる。
- 止めたイベントの復旧の手順（処理の回数を DB で戻す）でも、同じ理由で拒否される。

出荷をやり直せば、確定済みとして復旧する。この spec が修正するのは、やり直さずキャンセルする経路である。目的は、確定済みの支払をキャンセルしたとき、取消でなく返金に進めること。

追跡の issue は #407。関わる文書は、[決済モジュール](../../03-機能仕様/payment.md)と[決済の設計](../../02-設計/payment.md)。

### 確認した範囲と限界

| 確認した内容 | 方法と出典 |
|--------------|------------|
| 決済サービスの SDK が同じ冪等キーで 2 回まで再試行する | `StripeConfig.java:24` |
| 上の経路で、試行回数 4（止めたイベントを示す値）、状態が失敗、支払は与信の取消待ちになり、返金も取消も 0 件になる | 統合テストで再現した（issue #407 の「再現の手順」） |
| 確定済みの与信の取消は、決済サービスでエラーになる | Stripe の文書で確認した（`succeeded` は取消できる状態ではない）※1 |
| 実際の決済サービスの実装が、`succeeded` の取消を失敗にする | 既存の単体テストで確認した |

※1：docs.stripe.com/api/payment_intents/cancel、2026-11-06 確認。

再現では実際の Stripe を呼んでいない。確定済みの状態は、DB の状態が同じになるテスト用の決済サービスで再現した。Stripe が確定済みの与信の取消をエラーにすることは、この時点では実行して確認していない（T407-01-01 で確認する）。

## スコープ

| 含める | 含めない |
|--------|----------|
| 与信の取消で、決済サービスの状態で処理を分ける（取消済み、売上確定済み、それ以外） | 確定の結果が不明な支払に印を付けて照合すること（Non-goals） |
| 売上確定済みと分かった支払を返金に進める | 決済サービスからの確定の通知を受けること（Non-goals） |
| mock の決済サービスとテスト用の決済サービスを同じ振る舞いにする | API の契約と DB の構造の変更（非機能要件） |
| AC-164 の例外の追記と、機能仕様・設計の文書と用語集の更新 | |

決定：

1. 規模は M にする。理由：AC を追加するが、API の契約と DB の構造を変えず、決済モジュールの中で閉じるため（[開発の進め方](../../05-開発規則/workflow.md)の「規模と push」）。
2. 決済サービスの port の与信の取消は、結果を返す形にする。結果は「取り消した（すでに取消済みを含む）」と「売上確定済みで取り消せない」の 2 つ。理由：決済サービスの型を実装の外に出さず、売上確定の結果と同じ形で返すため（同じ port の売上確定は `CaptureResult` を返す）。

   | 論理名 | 識別子 |
   |--------|--------|
   | 与信の取消の結果 | `VoidResult` |
   | 取り消した | `VOIDED` |
   | 売上確定済み | `ALREADY_CAPTURED` |

3. 決済サービスに取消を拒否されたときは、与信の状態を再取得して、次の表で結果を決める。

   | 決済サービスでの状態 | 結果 |
   |----------------------|------|
   | 取消済み（`canceled`） | 取り消した |
   | 売上確定済み（`succeeded`） | 売上確定済み |
   | それ以外 | 失敗にする（今と同じ。例外で終わり、再発行で再試行する） |

4. 売上確定済みの結果を受けたら、既存の「売上確定の反映」を呼ぶ。機能仕様の状態の遷移の図に、与信の取消待ちから返金待ちへの遷移が既にある。返金の依頼も「売上確定の反映」で登録されるので、状態と遷移を増やさない。
5. mock の決済サービスも、売上を確定した与信の取消は、例外でなく「売上確定済み」を返す。理由：本番の実装と mock が同じ振る舞いを守ることを、同じ契約テストで確認するため。
6. テスト用の決済サービスに、「売上は確定するが、応答が届かない」操作を加える。理由：接続の失敗を再現する今の操作では、mock が売上を確定せず、取消の時点で確定済みにならないため。

| US-407-1 | 消費者 | 売上確定の応答が届かなかった後に注文がキャンセルされても、代金の返金を受けられる | 請求されたまま返金されない状態を防ぐため |

## 受け入れ条件

### US-407-1 売上確定の応答が届かなかった支払の返金（C / P1）

- **AC-407-1** 決済サービスで売上を確定した後に応答が届かなかった支払の注文をキャンセルすると、支払は返金済みになり、総額が 1 回だけ返金される。与信の取消は成立しない。
- **AC-407-2** AC-407-1 の支払について、与信の取消の依頼が重複して処理されても、返金は 1 回だけ行う。
- **AC-407-3** 売上確定の最中に注文がキャンセルされ、与信の取消が売上確定の反映より先に処理されても、返金は 1 回だけ行う。
- **AC-407-4** 決済サービスが与信の取消を拒否し、その与信が取消済みでも売上確定済みでもないときは、支払は与信の取消待ちのまま残り、再発行で再試行する。

### 前の spec の AC の変更

AC-164 の内容を次のとおりに変更する。状態は「変更」、変えた spec は `407`。

```
与信の取消に失敗したら、取り消せるまで再試行する。売上確定済みで取り消せない与信は、再試行せず返金に進める。根拠は[決済モジュール](payment.md)の「与信の取消」。
```

## Non-goals

| 項目 | 理由 |
|------|------|
| 確定の結果が不明な支払に印を付けて照合する | DB の列と定期の照合が要り、規模が M を超えるため ※3 |
| 決済サービスからの確定の通知を受ける | 受け付ける通知を増やす変更で、キャンセルの経路の修正に不要なため |
| 止まったイベントの復旧手順の変更 | 手順は今のまま使える。処理の回数を戻すと、修正後のコードで再処理され、返金に進む（コードを読んで判断した。実行していない） |

※3：キャンセルの経路は、この spec の修正だけで返金に進む。キャンセルも出荷のやり直しもしない支払は、DB が与信済み、決済サービスが確定済みのまま残り、この spec では見つけられない。#423 で扱う。
