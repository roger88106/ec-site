# Spec 181：バックエンドのテストを強める

ステータス：確定

## 1. 背景と目的

MVP 019 の全体のレビューと spec 155 の後に、バックエンドのテストと構成の検査の指摘が残っている。spec 155 でパッケージの構成を整えたので、その上でテストを強める。

追跡の issue は [#181](https://github.com/roger88106/ec-site/issues/181) で、扱う issue は #80、#86、#176 と、#16 のうちバックエンドのテストの部分である。作業ブランチは `181-backend-tests` である。規模は L で、利用者が 2026-10-24 に承認した。理由：複数のモジュールのテストにまたがるため。

#86 の「ほか 22 件」は、MVP 019 のレビューの結果のファイルが残っていない。#16 は、どのテストが規則にそろっていないかを書いていない。そこで 2026-10-24 に、今の `develop` のバックエンドのテストを、テストの書き方の規則と照合して再レビューした。観点は、テスト（抜け、弱い確認、AC 番号と内容の一致、データの干渉）と規則（テストの書き方）と重複である。範囲を 3 つ（商品カタログの系統、注文の系統、モジュールの外と構成の検査）に分け、汎用のモデルで 1 回ずつ実行した。spec 担当のセッションが、主な指摘をコードで確認した。

- #80、#86 で名前を挙げた項目は、今のコードに残っていた。例外は AC-199 のテストで、内容と合っていた。
- #13、#176、#177、#178 の項目は、全て今のコードに残っていた。#13、#177、#178 は、第 1.1 節のとおり別の spec で扱う。
- 再レビューの指摘は、既知の項目を含めて 55 件（高 4、必須 16、推奨 35）である。構成の検査とその補助の指摘を除き、全て本 spec に含める。理由：#86 は推奨の指摘を直す issue であり、#16 は書き方の規則にそろえる issue であるため。
- spec 155 と第 1〜3 回の spec で修正済みのもの（AC-84、AC-128 のテストなど）は、指摘に含まれない。

### 1.1 2 つの spec に分けた

草案では、構成の検査とその補助（#13、#177、#178）を DS-181-6、7 として含めていた。利用者が 2026-10-24 に、次のとおり 2 つの spec に分けることを決めた。

| spec | 範囲 | 扱う issue |
|------|------|------------|
| 本 spec（181） | DS-181-1〜5：テストの確認、AC 番号、データの干渉、書き方の規則、Repository のテスト | #80、#86、#176、#16 のバックエンドの部分 |
| spec 186 | 構成の検査とその補助（草案の DS-181-6、7） | #13、#177、#178 |

- 理由：変えるファイルが重ならず、並行して進められるため。1 つの pull request が小さくなり、レビューの負担が減る。
- DS-181-6、7 と DC-181-32〜44 は、欠番として残す。新しい追跡の issue は #186 である。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。

## 2. 用語

| 用語 | 意味 |
|------|------|
| コミットするテスト | 巻き戻さずにデータを確定させる統合テスト（テストの書き方 第 3.1 節の「巻き戻せないテスト」） |
| 一覧の全体を確認するテスト | 表の全体の件数や、一覧の全体の並びを確認するテスト。他のテストが残したデータで結果が変わる |
| テストの補助 | 統合テストのデータを作るクラス（テストの書き方 第 3.2 節） |

用語集に追加する語は、plan で決める。

## 4. 目的と完了条件

### DS-181-1 テストが確認したい条件を確認する（D / P1）

AC のテストのうち、状態コードだけ、空であることだけ、件数が 1 以上であることだけを確認するものを、AC の条件を確認する形にする。

- **DC-181-1** AC-123 のテストは、会員のカートを 30 品目にしてから移し、移せなかった品目のバリアント ID と数量を確認する。#80 の項目である。
- **DC-181-2** AC-85 のテストは、注文手続きの表示で、税率ごとの消費税額を確認する。#86 の項目である。
- **DC-181-3** AC-158 の消費者の側は、支払待ちの注文へのキャンセルの申請が業務のエラーで拒否され、注文の状態が変わらないことを API で確認する。運営者の側は、実際の状態コードを確認する。#86 の項目である。
- **DC-181-4** AC-173 のテストは、拒否される入力ごとにテストを分け、エラーの種類と項目を確認する。#86 の項目である。
- **DC-181-5** AC-70 は、商品の画像の追加の API で、変換できないファイルが拒否され、商品の画像とバージョンが変わらないことを確認する。媒体の API のテストの、常に成り立つ確認は削除する。
- **DC-181-6** AC-77 は、カートの表示で、画像のある品目の画像の URL を確認する。
- **DC-181-7** AC-81 は、最後の変更から 30 日に満たないカートの品目が残ることも確認する。
- **DC-181-8** AC-144 は、注文の確定の後もカートの品目と数量が変わらないことを確認する。
- **DC-181-9** AC-207 の API のテストは、商品を指定した集計を確認する。
- **DC-181-10** AC-208 の API のテストは、生年月日の分からない会員の注文が年齢層「不明」に入ることを確認する。
- **DC-181-11** AC-198 は、粒度ごとの行を確認するテストがあるか、AC の除外の一覧に理由がある。理由：DC-181-17 で番号を修正すると、AC-198 を確認するテストがなくなるため。
- **DC-181-12** AC-91 のテストは、同じ注文手続きの 2 つ目の注文が、一意の制約の違反で拒否されることを確認する。
- **DC-181-13** AC-288 のテストは、ログに出た件数が、削除した件数と一致することを確認する。
- **DC-181-14** NFR-16 の注文のレポート用の API のテストは、入れ子の項目まで個人の情報の項目がないことを確認する。
- **DC-181-15** 管理用のポートと業務のポートを分けるテストは、期待する状態コードそのものを確認する。
- **DC-181-16** アプリケーションの起動のテストは、全てのモジュールの schema が作られることを確認する。

### DS-181-3 他のテストのデータの影響を受けない（D / P1）

- **DC-181-18** 支払の期限切れのジョブのテストは、他のテストが残した支払の数によらず通る。#86 の項目である。
- **DC-181-19** 出荷の新しい順の読み取りのテストは、配送業者の mock のテストが確定させた出荷によらず通る。
- **DC-181-20** 一覧の全体を確認するテスト（店舗の一覧と検索、管理の商品の一覧、カテゴリの木、管理の注文の一覧）は、自分のデータだけで確認する。テストの書き方 第 3.1 節は変えない。理由：規則と一致し、後処理の漏れの影響を受けないため（利用者の決定、2026-10-24）。#176 の項目である。
- **DC-181-21** コミットするテストが後処理をするときは、非同期のリスナー（商品の登録、レポート、支払）の処理が終わるのを待ってから削除する。対象は AC-84 のテストと、注文の並行のテストである。#176 の項目である。
- **DC-181-22** 失敗したイベントを再発行するテストは、自分のデータの記録だけを確認する。
- **DC-181-23** 後処理が残るときは、削除の処理が 1 か所にあり、4 つのテストクラスで同じ削除の手順を繰り返さない。後処理を削除したテストは、この DC を満たす。

### DS-181-4 テストの書き方の規則（D / P1）

- **DC-181-24** 同じイベントを連続して発行するレポートの集計のテストは、前の発行の処理が終わるのを待ってから次を発行する（テストの書き方 第 5 節）。
- **DC-181-25** イベントの処理を待つテストは、統合テストの待ちの補助を使い、イベントの記録を直接読んで待たない。対象は注文のキャンセルの一貫性のテストと、イベントの再発行のテストである（テストの書き方 第 5 節）。
- **DC-181-26** Spring を起動しない、エラーの種類の検査のテストは、単体テストのソースセットにある（テストの書き方 第 3.3 節）。
- **DC-181-27** 次の表のテストデータの作成は、テストの補助にあり、テストのクラスで再定義しない（テストの書き方 第 3.2 節）。

| テストデータ | 今の重複 |
|--------------|----------|
| 在庫を作って入荷として調整する | 統合テストの 27 ファイル |
| 公開した商品（税区分の登録を含む） | 店舗とカタログの 4 クラス（補助と同じ内容の内部クラスを含む） |
| カテゴリ | 4 クラス |
| 画像の受付・アップロード・確定 | 3 クラスと補助 |
| カートに入れて注文手続きを始める | 注文の 5 クラス |
| 出荷の登録、配送状態の通知、送り状番号 | 出荷と注文の 9 クラス |
| 支払の作成、与信、売上確定、状態の取得 | 支払の 6 クラス |
| 作成の応答から ID を取り出す | 2 つの補助と 9 クラス |
| イベントの記録の表の定義と、発行して待つ処理 | イベントの片付けと再発行の 2 クラス |

### DS-181-5 Repository の統合テストとカートの作成（D / P1）

- **DC-181-28** カートの作成の永続化は、挿入できたかを返す。会員のカートの ID を求める操作は、挿入できたときは読み直さずに ID を返す。注文の挿入と書き方をそろえる。#80 の項目である。
- **DC-181-29** 同じ会員の最初のカートの要求を同時に送っても、カートは 1 つで、全ての要求が同じ ID を受け取ることを、統合テストが確認する（AC-121、テストの書き方 第 1.1 節の並行性）。
- **DC-181-30** 注文の Repository の統合テストが、差分更新、バージョンの競合、行の lock、注文番号の存在の確認を確認する（テストの書き方 第 1.1 節）。
- **DC-181-31** カート、注文手続き、支払、会員、送ったメール、レポートの注文の写し、在庫の引当、画像の資産の Repository は、それぞれ永続化と再構築を確認する統合テストがある（テストの書き方 第 1.1 節）。

## 6. 非機能要件

- **DN-181-1** 消費者・運営者に見える振る舞いを変えない。例外：テストを強めて見つかった不具合は、テストから修正する。修正すると AC の意味が変わる不具合は、修正せずに起票し、利用者に報告する。
- **DN-181-2** API の契約とデータベースの構造を変えない。
- **DN-181-3** AC を追加・変更しない。変えるのは、テストの確認の方法、テスト名の番号、AC の除外の一覧だけである。
- **DN-181-4** 強めたテストと、新しく足したテストは、一時的に期待値かコードを変えて、失敗することを確認する。
- **DN-181-5** 欠番。構成の検査は spec 186 に移した。
- **DN-181-6** テストを弱めない。確認を削除するのは、常に成り立つ確認だけで、理由を commit の本文に書く。
- **DN-181-7** カバレッジと mutation score が基準を下回らず、`./gradlew check` が通る。
