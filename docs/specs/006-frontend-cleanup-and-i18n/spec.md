# Spec 006：フロントの整理と i18n

ステータス：確定

## 1. 背景と目的

管理画面と店舗画面は、spec ごとに画面を追加して作ってきた。spec 007 以降で画面を追加する前に、**同じ処理を 1 か所にし、表示の文言を言語ごとのファイルで管理できる**ようにする。

- 店舗画面は、secret などの環境変数を設定し忘れても、公開されている既定の値で起動してしまう（バックエンドは起動に失敗する）。
- 店舗画面のサーバーの処理で、入力の取り出しと例外の扱い（リダイレクトの例外を飲み込まない決まりなど）を、処理ごとに繰り返して書いている。
- 管理画面と店舗画面に、同じ処理と同じ部品が別々にある。
- 管理画面の更新の操作（成功の通知、一覧の再取得、複数の操作の実行中の状態とエラーの集約）が、26 か所で同じ形に書かれている。画面の URL が文字列のまま散らばり、型で確認できない。
- 表示の文言が画面のコードに直接書かれている。数・日付・金額の整形のロケールも、5 か所に直接書かれている。
- 画面の入力の制約（長さ・範囲）を、API の契約とは別に手動で書いていて、一致を確認する仕組みがない。

本 spec は**整理の spec**（[文書の記号と番号](../../process/notation.md)）。spec 004 の完了を前提にする（フロントの workspace、規則の文書、店舗画面のサーバーの処理のテスト）。spec 005 とは互いに独立している。

## 2. 用語

本 spec で新しく使う用語（文言のファイル、文言のキー、ロケールなど）は、plan で用語集に追加する。

## 4. 目的と完了の条件

### DS-14 店舗画面のサーバーの処理を、安全で短くする（D / P1）

- **DC-45** 本番のビルドで、Cookie の暗号鍵、IdP の client secret、IdP の URL が設定されていなければ、店舗画面は起動に失敗する。ローカルの開発、E2E、CI は、値を渡して動く。
- **DC-46** サーバーの処理の入力の取り出し（文字、整数）と、例外の扱い（リダイレクトの例外を通す、接続の失敗を結果として返す）を、共通の関数で行う。処理ごとに同じ形を書かない。
- **DC-62** 店舗画面のサーバー側のログは、規則の文書で決めた形式（構造化、レベル）で出力し、バックエンドとのトレース ID を引き継ぐ。（P2）
- **DC-47** 認証の処理は、設定、token の更新、ログアウトに分かれている。公開インターフェースは変えない。（P2）

### DS-15 2 つの画面の共通の処理と部品を、1 か所で持つ（D / P1）

- **DC-48** 管理画面と店舗画面で同じ処理（カテゴリの木の組み立て、ログインの戻り先、表示コンポーネントのクラス名の結合、数・日付・金額の整形）と、同じ表示コンポーネント・見た目のテーマは、共有のパッケージに 1 つだけある。
- **DC-49** 共有のパッケージに入れる基準（2 つ以上の画面で使う、画面のフレームワークに依存しない、など）と、入れないもの（API の接続、認証、画面の機能）が、規則の文書にある。

### DS-16 管理画面の繰り返しを減らす（D / P1）

- **DC-50** 更新の操作の定型（成功の通知、関係する一覧の再取得、複数の操作の実行中の状態とエラーの集約、前のエラーの消去）を、共通のフックで 1 行ずつ書ける。今の 26 か所をそれに置き換える。
- **DC-51** 画面の URL は 1 か所で作り、URL に入る値（ID など）を型で確認する。画面のコードに URL の文字列をハードコードしない。
- **DC-52** 画面の入力の制約（長さ・範囲）と、API の契約の制約が食い違うと、テストが失敗する。
- **DC-61** 画面は、業務の規則による操作の出し分け（商品を削除できるか、バリアントを追加できるかなど）を、API の応答の「できる操作」のフラグで決める。同じ判定を画面に書かない。ほかの画面の同じ種類のもの（注文のキャンセルなど）も対象にする。
- **DC-53** バリアントの一覧の 1 行（画像の選択、販売の停止・再開、並べ替え、削除）を、一覧から分けたコンポーネントにする。（P2）

### DS-17 表示の文言を、言語ごとのファイルで管理する（D / P1）

- **DC-54** 管理画面と店舗画面の表示の文言（見出し、ボタン、ラベル、通知、確認メッセージ、エラーの既定の文、ページの題名）を、言語ごとのファイルで管理する。今の言語は日本語だけ。画面のコードに表示の文言をハードコードしない（規則の文書に例外を書く）。2 つの画面に共通の文言を共有するかは、plan で道具を選んでから決める。
- **DC-55** 文言のファイルにないキーを画面のコードに書くと、型チェックで失敗する。
- **DC-56** 数・日付・金額の整形と、ページの言語の指定は、現在のロケールから取る。ロケールをハードコードするのは 1 か所だけ。
- **DC-57** 文言をキーに置き換えた所には、何が表示されるかの短いコメントがある（文言の全文は転記しない）。
- **DC-58** 既存のテストは、今の日本語の文字で要素を探したまま通る。

### DS-18 型とコードを、コメントで読めるようにする（D / P1）

- **DC-59** 型の項目のうち、名前と型だけでは分からないもの（特別な値の意味、単位、範囲、そう持つ理由）に、論理名と説明のコメントがある。名前と型で分かる項目には書かなくてよい。
- **DC-60** 一目で意図が分からない処理（イベントの処理、コンポーネントの差し替え、フレームワークの決まりによる書き方）と、規則の文書が「複雑な処理」とするものの直前に、何のためかのコメントがある。分からない所は推測で書かず、一覧にして利用者に確認する。
- **DC-66** 本番のコード（admin・store の `src` のテスト以外）のコメントに、spec・plan・tasks の番号（AC・BR・US・NFR、spec・plan の節、タスク番号）がない。番号で示していた規則は、言葉で書かれている。spec との対応はテストの名前にある。

## 5. 業務ルール

なし（本 spec は業務の規則を変えない）。

## 6. 非機能要件

- **DN-7** 画面の見た目、表示の文言、操作の振る舞いを変えない（API の契約に追加するのは、DC-61 のフラグだけ）。既存のテストは全て通る（テストを変えるのは、置き場所の移動に限る）。
- **DN-8** 文言の置き換え（DS-17）は、まず仕組み、次に共通の部品、次に機能ごとに段階を分け、1 つの commit に全画面を入れない。コメントだけの変更は、コードの変更と別の commit にする。

## 7. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| 2 つ目の言語、言語の切り替えの操作 | 将来の spec（本 spec は言語を追加するための基盤だけを作る） |
| バックエンドのメッセージの言語の切り替え | 将来の spec |
| API の契約から画面の入力の検証を生成する | 入力エラーによる往復が実際に問題になったとき（今は DC-52 で一致だけを確認する） |
| 型付きのルーターへの置き換え | 行わない（DC-51 で足りる） |
| IdP のログインの画面の文言 | IdP の仕組みで管理する（今のまま） |
| バックエンドの整理 | spec 005 |
| ログインの直後のカートの引き継ぎの失敗を、消費者に知らせる | 機能の spec（spec 007 以降。消費者に見える振る舞いが変わるため） |
