# Spec 558：規則の方針を決める（重複した書き方とモジュールの間の型）

種類：整理　規模：M　ステータス：確定

## 背景と目的

規則が求める重複した書き方と、モジュールの間の型の写しを再検討し、規則と設計の文書の方針を決める。この spec は規則と設計の文書だけを変え、コードは変えない。消費者・運営者に見える振る舞いも変えない。決めた結果のコードの変更は、別の issue にする。その issue は、#544（リリースの前の整理）の段階 2 で行う。追跡の issue は #558（組の issue）。sub-issue は #541（規則が求めている重複と冗長な書き方の再検討）と #492（モジュールの間の型の写しと、公開のイベントの中身の方針）。

## スコープ

| 含める | 含めない |
|--------|----------|
| 8 つの決定（利用者が 2026-11-18 に決めた）を、規則と設計の文書に書くこと | コードの変更（Non-goals） |
| コードの変更を、issue の案にして issue 担当のセッションに送ること | 設定の値の型を有効化するだけの設定のクラス（Non-goals） |

決定：

- 決定 1（列挙の 1 対 1 の変換）
  - 今：規則が、値ごとに書く分岐の式を求め、名前での変換を禁じている。値が全て同名の分岐が 51 個ある（2026-11-18 に、#544 の全体のブランチのコードを調べた数）。
  - 決める：定数の名前の集合が同じ列挙の間は、共通の変換のメソッドを使い、名前で変換してよい。変換元と変換先の列挙の組ごとに、全ての値が変換できることを単体テストで確認する。名前が違う、または 1 対 1 でない変換は、今のとおり分岐の式で書く。
- 決定 2（null 不許可の注釈と NullAway）
  - 今：service の公開の引数、Command の項目、`api/` の公開の引数に、Lombok の null 不許可の注釈を付ける規則がある。NullAway もコンパイルで null を検査するので、二重になっている。
  - 決める：この 3 つの入口には付けず、null の検査は NullAway に任せる。domain の Lombok で作るコンストラクターには今のとおり付け、実行時の検査として残す。
- 決定 3（モジュールの一覧）
  - 今：一覧が 5 か所にある。4 か所はテストか script で照合している。Gradle の jOOQ のスキーマの一覧だけ、照合がない。
  - 決める：各所の一覧はそのままにする（持つ情報が違うため）。照合のない 1 か所に、照合の検査を加える（コードの issue）。規則の文書は変えない。
- 決定 4（名前と同じ文の Javadoc）
  - 今：名前を論理名で言い換えるだけの Javadoc が多い。
  - 決める：今のままにする（論理名があると読みやすいため）。この理由を、コメントの書き方の Javadoc の理由に加える。
- 決定 5（転送だけのメソッド）
  - 今：`api/`、腐敗防止層の実装、service に、受け取った引数をそのまま渡すだけのメソッドがある。規則は、`api/` の転送だけのメソッドを「トランザクションの境界か null の入口なら残してよい」としている。
  - 決める：層の規則は変えない。転送だけのメソッドを層の規則の例外にせず、層の規則に従った結果の形として残してよいことを規則に書く。コードは変えない。
- 決定 6（公開の API の形）
  - 今：5 つの公開の API が呼ぶ側の形で作られ、呼ぶ側も腐敗防止層で包む。同じ項目を、view、API の型、呼ぶ側の型へと 2 回変換している。
  - 決める：公開の API は、提供する側の用語で汎用の形に作り、呼ぶ側の腐敗防止層だけで自分の型に変換する。呼ぶ側の形の 5 つの API は修正する（コードの issue）。例外として残すものはない。
- 決定 7（公開の API の名前）
  - 今：名前が 3 通りある（呼ぶ側の名前、機能の名前、`Api` の付かない 1 つ）。
  - 決める：提供する側の機能の名前に `Api` を付ける。呼ぶ側の名前を入れない。`Api` の付かない 1 つは、presentation に会員の ID を渡す例外として今のまま残す（バックエンドの書き方の「標準の構成」の例外の表にある）。
- 決定 8（公開のイベントの中身）
  - 今：出荷のイベントだけがメールアドレスを載せ、イベントの記録に 7 日残る。出荷では、汎用の状態の変化のイベントと、出荷のイベントの 2 つを発行する。通知モジュールは、配送業者の表示名の文言のキーを得るためだけに、配送モジュールの API に依存している。
  - 決める：公開のイベントに個人情報（メールアドレス、氏名、住所、電話番号など）を載せない。受ける側は、必要なら API で読む。ID、状態、個人情報でない事実（注文番号、配送業者、送り状番号など）は載せてよい。
  - 出荷のイベントは残し、メールアドレスだけを外す（コードの issue）。出荷という業務の事実で、汎用の状態の変化とは別のため。
  - 通知モジュールから配送モジュールの API への依存は残す。同期の参照で、規則どおりの使い方のため。
