# レビュー

実装の過程を見ていないサブエージェントにレビューを任せ、メインのセッションが結果をまとめる。規則の置き場所と書き方は [書き方の規則とレビュー](../../../docs/process/review.md)、サブエージェントへの任せ方は [エージェントの作業フロー](../../../docs/process/subagents.md) にある。

観点の一覧と、サブエージェントに渡す指示のひな形は [prompts.md](prompts.md) にある。

## 使う場面

| 場面 | 対象 | 手順 |
|------|------|------|
| 段階・spec の最後のレビュー | 差分（段階または spec の最初の commit の 1 つ前から HEAD まで） | 手順 1〜6 |
| plan の照合 | spec と plan | 手順 7 |
| 文書のレビュー | 新しく書いた、または変えた文書 | 手順 8 |
| 全体のレビュー（受け入れ確認） | リポジトリ全体 | 手順 1〜6。対象を観点ごとに分け、さらに範囲（バックエンドのモジュール、フロントのアプリ、E2E、文書、script と CI）で分ける |

## 手順

1. 対象を決める。差分なら、変えたファイルを [書き方の規則とレビュー](../../../docs/process/review.md) 第 2 節 ※1 のコマンドで一覧にする。結果の置き場所 `/.local/review/<yyyyMMddHHmm>-<名前>/` を作る。
   完了の条件：対象のファイルの一覧が置き場所にある。
2. チェックリストを作る。`node .claude/skills/review/checklist.cjs` の出力を置き場所に保存する。対象に関係しない文書の節（フロントを変えていないならフロントの書き方 など）は除く。
   完了の条件：チェックリストのファイルがある。
3. 観点を選ぶ。観点の一覧は [prompts.md](prompts.md)。差分のレビューでは、対象に関係する観点だけを選ぶ。
   完了の条件：観点ごとに、読むファイルの範囲が決まっている。
4. 観点ごとにサブエージェントを立てる。読むだけなので、並列で実行してよい。モデルは [エージェントの作業フロー](../../../docs/process/subagents.md) 第 3 節の表で選ぶ（判断が必要な観点は Sonnet、金額・セキュリティは Opus）。指示は [prompts.md](prompts.md) のひな形を使い、日本語だけで書く。渡すのは、対象のファイルの一覧、spec と plan のパス、チェックリスト（関係する部分）、観点、結果の書き先だけにする。会話の履歴と実装の経緯は渡さない。サブエージェントは結果をファイルに書き、件数だけを返す。
   完了の条件：すべての観点の結果のファイルがそろった。
5. すべての結果がそろってから、まとめる。重複を除き、指摘を「必須」と「推奨」に分ける。各指摘に、根拠（規則の文書と節、または spec の DC・AC）、場所、修正案、機械の検査に移せるか（移せる検査の名前、または移さない理由）を付ける。メインのセッションは、指摘が事実か（コードがそうなっているか）を確認してから載せる。
   完了の条件：まとめの表があり、すべての指摘に根拠と「機械の検査に移せるか」がある。
6. 結果を利用者に示し、tasks のレビューの段階に書く（修正したもの、残したものと理由、機械の検査に移したもの）。「必須」は修正する。「推奨」は利用者と決める。機械の検査に移せる指摘は、検査を追加するタスクを tasks に提案する。
   完了の条件：すべての指摘の扱いが決まっている。
7. plan を照合する。日本語だけの文脈のサブエージェント（Sonnet）に、spec の各 AC・DC と plan の決定を 1 件ずつ照合させる。結果は表（AC・DC、plan の節、合っている・抜けている・食い違う、説明）で受け取る。抜けと食い違いは、plan を利用者に見せる前に修正する。
   完了の条件：すべての AC・DC が表にある。
8. 文書をレビューする。日本語だけの文脈のサブエージェント（Sonnet）に、目指す書き方の見本（[エージェントの作業フロー](../../../docs/process/subagents.md)、[spec 018 の plan](../../../docs/specs/018-docs-and-tools/plan.md)）と [文書の言い回しと論理の規則](../docs/tech-writing.md) を渡し、技術文書として不自然な言い回しを候補として挙げさせる。結果は表（ファイル、行、今の書き方、修正案、理由）で受け取り、利用者が採否を決める。spec・plan・tasks を書き終えたとき（利用者に見せる前）と、spec の最後のレビューで行う。
   完了の条件：すべての候補の採否が決まっている。
