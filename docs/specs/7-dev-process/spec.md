# Spec 7：1→10 の開発の進め方への切り替え

ステータス：確定

## 1. 背景と目的

MVP（spec 001〜019）が完成し、tag `v0.1.0` を付けた。1→10 の段階では、複数のセッションで並行して開発する。利用者はコードも文書も自分では書かず、エージェントだけで spec から pull request まで進める。この進め方を改善するために、今の進め方を、並行と自動化に合う形へ切り替える。

今の進め方は、1 つのセッションで順に進める前提になっている。並行と自動化の妨げになる点は次のとおり。

- 後回しにする作業を TODO 一覧のファイル（約 130 項目）に書いている。状態、議論、pull request との関連を記録できず、並行するとファイルが衝突する。
- spec の番号と、spec の中の番号（US・AC・BR・NFR・DS・DC・DN）が、spec をまたぐ連番になっている。並行すると番号が衝突する。spec の番号が 999 を超えると、ディレクトリが番号順に並ばなくなる（TODO 一覧で「必ず決める」とした項目）。
- pull request を `main` に直接入れる。本番の前に確認するブランチがない。
- 文書を書くたび、段階ごとに利用者の指示を待つ。利用者が、並行する複数のセッションに対応できない。
- 利用者と対話するセッションが実装もするので、文脈が大きくなる（spec 003 の記録で、1 つの段階の間に約 8.5 万から約 43.6 万 token）。文脈の圧縮で、決定が抜け落ちやすい。
- 小さな修正にも spec・plan・tasks の 3 つの文書を求める。

本 spec の進め方は、2026-10-22 に利用者とエージェントが検討して決めた。決定の記録は本 spec と plan に置く。追跡の issue は [#7](https://github.com/roger88106/ec-site/issues/7)、作業ブランチは `7-dev-process` である。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。番号の形は本 spec から新しくする。spec の番号は追跡の issue の番号（#7）とする。DS・DC・DN は、spec の番号と spec の中の連番を組み合わせた形にする。例：DS-7-1。MVP の DS-1〜56、DC-1〜227、DN-1〜26 の連番の続きにはしない。変えないものと特例は、6 節の DN-7-1〜3 に書く。

## 2. 用語

| 用語 | 意味 |
|------|------|
| 追跡の issue | spec 1 つに 1 つの issue。番号が spec の番号になる |
| issue 担当のセッション | issue を確認して、優先度と並行の可否を決め、spec 担当のセッションを始めるセッション。release の内容もまとめる |
| spec 担当のセッション | spec 1 つを担当するセッション。利用者と文書を作り、実装とレビューをサブエージェントに任せ、判定する。コードを書かない |
| 規模（S・M・L） | 変更の大きさの区分。区分ごとに、書く文書と、利用者が確認する対象が違う |
| 完了の定義 | `develop` に入れる前に満たす条件 |
| レビューの profile | レビューの量の設定。値は厚め・標準・節約。契約のプランの使用量の上限に合わせて選ぶ |

用語集に追加する語と識別子は、plan で決める。

## 4. 目的と完了条件

### DS-7-1 GitHub Issues で起票し、TODO 一覧のファイルをなくす（D / P1）

- **DC-7-1** issue のテンプレートが「機能」「整理」「不具合」の 3 つある。
- **DC-7-2** GitHub の画面では、テンプレートを選ばない issue を作れない。
- **DC-7-3** issue のテンプレートの項目と、エージェントがコマンドで起票するときの本文の節が一致する。
- **DC-7-4** label は、種類、領域、保留、spec、依存の更新の 5 つがある。
- **DC-7-5** GitHub の既定の label はない。
- **DC-7-6** milestone「1→10」がある。
- **DC-7-7** TODO 一覧の全ての項目が、issue になっているか、移さない理由が記録されている。
- **DC-7-8** 同じ性質のものと順序のあるものは、1 つの issue にまとめてよい。
- **DC-7-9** TODO 一覧の項目のまとめ方は、起票の前に利用者が承認する。
- **DC-7-10** TODO 一覧のファイルがない。
- **DC-7-11** 文書の中で TODO 一覧を指す箇所が、issue を指す。
- **DC-7-12** 後回しにする作業の起票の規則が、時点ごとに文書にある。
  - spec の途中：spec（Non-goals、レビューの結果、plan）に記録する。
  - spec の最後：まとめ方の案を pull request に付ける。利用者が承認したら、issue 担当のセッションが、既存の issue と重複しないように起票する。
  - 急ぐ作業（不具合、マージの失敗など）：すぐに起票する。
- **DC-7-13** Dependabot の pull request を除き、全ての変更が issue から始まることが文書にある。

### DS-7-2 spec の番号と規模の区分を、並行に合う形にする（D / P1）

- **DC-7-14** spec の番号は追跡の issue の番号である。
- **DC-7-15** spec のディレクトリ、作業ブランチ、タスクの番号が、spec の番号と同じ番号を使う。
- **DC-7-16** 番号の飛びは許す。理由：pull request と番号を共有するため。
- **DC-7-17** spec の中の番号は、spec の番号を付けた形にする。例：AC-123-1。
- **DC-7-18** MVP の番号は変えない。
- **DC-7-19** 新しい文書で MVP の spec を指すときは、「MVP 012」と書く。
- **DC-7-20** AC とテストの対応の検査が、新しい番号を扱う。
- **DC-7-21** AC とテストの対応の検査が、MVP の番号を扱う。
- **DC-7-22** 規模の区分 S・M・L が文書にある。
- **DC-7-23** 規模ごとの文書が、次の表のとおり文書にある。

  | 規模 | 文書 |
  |---|---|
  | S | issue だけ。issue の本文を spec とする |
  | M | 1 つのファイル。目的、完了の条件か AC、tasks |
  | L | spec・plan・tasks |

- **DC-7-24** 規模の判定の基準が、次の表のとおり文書にある。

  | 条件 | 規模 |
  |---|---|
  | API の契約かデータベースの構造を変える、または 2 つ以上のモジュールにまたがる | L |
  | AC を追加する・変える | M 以上 |
  | 振る舞いを変えず、範囲が小さい | S |

- **DC-7-25** 規模の区分は、エージェントが提案する。
- **DC-7-26** 規模の区分は、利用者が承認する。
- **DC-7-27** spec が扱う全ての issue が、追跡の issue の sub-issue として結び付いている。
- **DC-7-28** README の進捗は、MVP の spec の表を MVP の節にまとめる。
- **DC-7-29** README の進捗の 1→10 の進み具合は、issue と milestone を指す。
- **DC-7-30** 完了した 1→10 の spec の置き場所は、MVP と同じく、まとまりごとのアーカイブである。
- **DC-7-31** spec は最後のタスクでアーカイブに移し、同じ pull request に含める。理由：マージの後に移すと、移すための pull request がもう 1 つ必要になるため。

### DS-7-3 ブランチを `develop` と `main` に分け、release の手順を決める（D / P1）

- **DC-7-32** `develop`（開発）があり、既定のブランチである。
- **DC-7-33** `main`（本番）がある。
- **DC-7-34** 作業ブランチは `develop` から切る。
- **DC-7-35** 作業ブランチは、pull request で `develop` に入れる。
- **DC-7-36** 作業ブランチの名前の形が、次の表のとおり文書にある。

  | 種類 | 名前の形 |
  |---|---|
  | 通常 | `<issue の番号>-<短い名前>` |
  | 緊急の修正 | `hotfix-<issue の番号>-<短い名前>` |

- **DC-7-37** `develop` と `main` に、次の保護がある。
  - pull request を経ずに変えられない。
  - CI が通らないとマージできない。
  - force push と削除ができない。
- **DC-7-38** `develop` へのマージの前に、作業ブランチが最新の `develop` を含む必要がある。
- **DC-7-39** `main` は、`release-` と `hotfix-` で始まるブランチからの pull request だけを受け付ける。理由：release するのは確認した commit で、`develop` の最新とは限らないため（DC-7-46）。
- **DC-7-40** `main` へのマージ元の制限を CI で検査する。
- **DC-7-41** マージは merge commit で実行する。
- **DC-7-42** `develop` から `main` へは squash しない。理由：履歴が分かれ、次の release で衝突するため。
- **DC-7-43** マージした作業ブランチは、自動で削除される。
- **DC-7-44** 完了の定義が文書にある。次の 3 つを満たしたものだけを `develop` に入れる。
  - CI が通る。
  - 作業ブランチで手動の確認を終えた。
  - 文書を更新した。
- **DC-7-45** 公開を遅らせたい機能は、設定のフラグで無効にすることが文書にある。
- **DC-7-46** release の手順が文書にある。
  1. 確認した commit から `release-<版>` のブランチを作成する。確認した commit は `develop` の最新とは限らない。
  2. pull request で `main` にマージする。
  3. tag を付ける。
  4. GitHub の Release を作成する。
- **DC-7-47** 版は SemVer である。
- **DC-7-48** 1→10 の間は、release ごとに minor を上げる。
- **DC-7-49** 緊急の修正は `main` から切ることが文書にある。
- **DC-7-50** 緊急の修正は、`main` に入れた後に `develop` に戻すことが文書にある。
- **DC-7-51** Dependabot が `develop` に対して更新の pull request を作成する。
- **DC-7-52** Dependabot の更新の頻度は、週 1 回である。
- **DC-7-53** Dependabot の更新の対象は、gradle、npm（pnpm）、GitHub Actions、Docker Compose である。
- **DC-7-54** Dependabot は、minor と patch の更新を、ecosystem（gradle、npm など）ごとに 1 つの pull request にまとめる。
- **DC-7-55** Dependabot は、major の更新を 1 つずつ pull request にする。
- **DC-7-56** Dependabot は、新しい版がリリースされてから、次の表の日数を待って更新の pull request を作成する。

  | 更新の種類 | 待つ日数 |
  |---|---|
  | major | 30 日 |
  | minor | 7 日 |
  | patch | 3 日 |

  ※ GitHub Actions と Docker Compose は SemVer の日数に対応しないので、7 日（default-days）とする。

- **DC-7-57** Dependabot は、セキュリティの更新を待たずに作成する。
- **DC-7-58** Dependabot の pull request は、issue を必要としない。プロジェクトの規則の例外とする。
- **DC-7-59** Dependabot の pull request の commit のメッセージは、英語でよい。プロジェクトの規則の例外とする。
- **DC-7-60** CD、staging、preview の環境の方式は、デプロイの spec で決める、と文書にある。
- **DC-7-61** デプロイの spec で決めるまでの手動の確認は、手元の環境で、作業ブランチに対して実行する。
- **DC-7-62** デプロイの spec で決めるまでの release は、`main` へのマージと tag までとし、デプロイしない。

### DS-7-4 エージェントの作業の流れを、並行と自動化に合う形にする（D / P1）

- **DC-7-63** 役割と担当が、次の表のとおり文書にある。

  | 役割 | 数 |
  |---|---|
  | issue 担当のセッション | 1 つ |
  | spec 担当のセッション | spec ごと |
  | 実装役・レビュー役・調査役のサブエージェント | 必要なとき |

- **DC-7-64** spec 担当のセッションは、コードを書かない。
- **DC-7-65** spec 担当のセッションが書いてよいのは、数行の文書の修正だけである。
- **DC-7-66** 合格・不合格の判定は、spec 担当のセッションが実行する。理由：サブエージェントに渡らなかった情報を持つのは、spec 担当のセッションだけのため。
- **DC-7-67** tasks の各タスクに、並行の記号 `[P]` を書く。`[P]` は、同じ段階の他の `[P]` と同時に実装できることを示す。
- **DC-7-68** tasks の各タスクに、依存を書く。
- **DC-7-69** tasks の各タスクに、変える範囲（ファイルかモジュール）を書く。
- **DC-7-70** `[テスト]` と対応する実装は 1 組で、同じ実装役が順に実装する。
- **DC-7-71** `[P]` のタスクは、作業ツリーを分けた実装役が同時に実装する。
- **DC-7-72** タスクに `[リスク]` の記号を付ける基準が、次のとおり文書にある。
  - 金額
  - セキュリティ
  - データの移行
  - トランザクション、並行処理、冪等性
  - 外部サービス（決済、物流）との接続
- **DC-7-73** レビューの時点が、次のとおり文書にある。
  - `[リスク]` のタスクの後
  - 段階の最後
  - spec の最後
  - pull request の前
  - release の前
- **DC-7-74** profile ごとのモデルの組み合わせが文書にある。
- **DC-7-75** profile はマシンと利用者ごとの環境の文書で選ぶ。
- **DC-7-76** profile の文書の既定は「標準」とする。
- **DC-7-77** spec の最後のレビューに、「ファイルをまたぐ影響」（値や制約を変えたとき、同じ値と制約を持つ箇所が全て変わったか）の観点がある。
- **DC-7-78** 規模ごとに利用者が確認する対象が、次の表のとおり文書にある。

  | 規模 | 利用者が確認する対象 |
  |---|---|
  | L | spec、plan と tasks を一緒に、pull request |
  | M | 1 つのファイルの spec、pull request |
  | S | 規模の区分、pull request |

- **DC-7-79** 段階とタスクの間で、利用者の確認を待たない。
- **DC-7-80** 途中で作業を中断して利用者に質問する条件が、次のとおり文書にある。
  - spec・plan の誤り
  - 文書にない設計の判断
  - 重要度「高」の指摘のうち、修正が機能の追加に相当するもの
  - 調査役でも原因を特定できない失敗
- **DC-7-81** 確認事項は、plan と tasks の確認でまとめて質問することが文書にある。
- **DC-7-82** pull request のテンプレートがある。
- **DC-7-83** pull request のテンプレートに、次の節がある。
  - 規模
  - spec
  - 関連の issue
  - 確認したこと
  - AC ごとの受け入れの確認と根拠
  - 文書
  - 推奨の指摘の扱い
  - 起票する issue の案
- **DC-7-84** マージは、利用者の許可を得てエージェントが実行する。
- **DC-7-85** マージの担当が、次の表のとおり文書にある。

  | マージ | 担当 |
  |---|---|
  | 作業ブランチ → `develop` | spec 担当のセッション |
  | `release-` のブランチ → `main` | issue 担当のセッション |
  | `hotfix-` のブランチ → `main`、その後の `main` → `develop` への取り込み | issue 担当のセッション |

- **DC-7-86** 並行の単位は、spec 1 つに、セッション、作業ツリー、ブランチ、pull request を 1 つずつとする。
- **DC-7-87** 並行してよい条件が、次のとおり文書にある。
  - モジュールが違う。
  - 契約や同じテーブルを同時に変えない。
  - 依存がない。
- **DC-7-88** 並行する spec の依存を追跡の issue に書くことが、文書にある。
- **DC-7-89** 共有の文書（AC 一覧、用語集）の衝突は、後でマージする pull request が `develop` を取り込んで解消することが文書にある。
- **DC-7-90** 手元の環境を並行に対応させるまでは、負荷の高い作業（compose、バックエンドの起動、E2E、バックエンドの全テスト）を、同時に 1 つのセッションだけで実行することが文書にある。

### DS-7-5 本 spec を、新しい進め方で最後まで進める（D / P1）

- **DC-7-91** 本 spec の作業ブランチを pull request で `develop` に入れる。
- **DC-7-92** release を、新しい手順（DC-7-46）で実行する。
- **DC-7-93** release で、tag `v0.2.0` を付ける。
- **DC-7-94** 本 spec を進めて分かった、新しい進め方の不備を、本 spec の中で修正するか、issue として起票する。

## 5. 業務ルール

なし（本 spec は業務の規則を変えない）。

## 6. 非機能要件

- **DN-7-1** API の応答、画面、データベースの構造とデータを変えない。
- **DN-7-2** 完了した MVP の spec・plan・tasks の内容を変えない。変えてよいのは、文書を移して切れたリンクのパスだけ。
- **DN-7-3** 本 spec は特例として、旧い進め方の次の手順に従わなくてよい。新しい進め方は、決まった部分から本 spec に当てはめる。
  - 文書ごとに利用者の指示を待つ。
  - TODO 一覧への追加。
  - spec の連番。
- **DN-7-4** CI と commit の前の検査が通る状態を保つ。

## 7. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| 手元の環境の並行化（基盤を共有し、作業ツリーごとにデータベースとポートを分ける） | 後の spec（1→10 の土台） |
| CI のバックエンドのジョブの分割、負荷でタイムアウトするテストの修正 | 後の spec（1→10 の土台） |
| 品質のツール（フォーマッター、静的解析、カバレッジの基準など） | 後の spec（1→10 の土台） |
| spec 019 の全体のレビューで残した指摘 | 後の spec（1→10 の土台） |
| デプロイ、CD、staging と preview の環境、定期的に release するか | デプロイの spec |
| issue 担当の専用のセッション（本 spec の間は、本 spec のセッションが兼ねる） | 進め方が安定した後 |
| 必要な approve の数など、利用者が承認してからマージするレビューの規則 | 必要になったとき |
