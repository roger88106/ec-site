# Spec 616：Stripe の障害で売上確定・返金が失敗した後、再実行で成功できるようにする

種類：機能　規模：M　ステータス：確定

## 背景と目的

売上確定と返金は、Stripe へ送るリクエストの冪等キーが注文ごとに固定である（売上確定は `capture-<注文 ID>`、返金は `refund-<注文 ID>`）。Stripe は、同じ冪等キーで再送されたリクエストに、最初の応答（5xx を含む）を返す。冪等キーを保持する期間は 24 時間である（Stripe の文書）。

売上確定は、Stripe の側の障害を「接続できない」として扱い、与信済みのまま残して再試行できるとしている（[決済モジュール](../../03-機能仕様/payment.md)の「決済サービスとの通信」）。しかし、1 回目の売上確定が Stripe の障害で終わると、24 時間は同じ障害の応答が返る。運営者が出荷の登録を再実行しても、502 になり続ける。返金も同じである。失敗すると、イベントが未完了のまま残り、イベントの再発行で再実行するが、24 時間は同じ障害の応答が返る。

目的は、Stripe が回復した後の再実行（出荷の登録の再実行、返金のイベントの再発行）で、売上確定と返金ができるようにすること。

追跡の issue は #616。#423 の spec の最後のレビューで見つかった、#423 より前からある問題である。関わる文書は、[決済モジュール](../../03-機能仕様/payment.md)、[決済の設計](../../02-設計/payment.md)、[注文の設計](../../02-設計/order.md)。

含めないものの理由は Non-goals に書く。

決定：

1. 規模は M にする（issue 担当のセッションが承認した）。理由：AC を加えるので M 以上で、決済モジュールの Stripe の実装の中で閉じ、API・DB・モジュールをまたぐ変更がないので L にならないため。
2. 冪等キーの作り方は案 B にする（issue 担当のセッションが承認した）。比べた案は次の表。

   | 案 | 内容 | 採る理由・採らない理由 |
   |----|------|------------------------|
   | A | 売上確定の冪等キーに、売上確定を求めた時刻（#423 で加えた列）を含める。返金は別の方法にする ※2 | 振る舞いは案 B と同じ。port の売上確定のリクエストに時刻を加える変更が必要で、作り方が売上確定と返金で分かれる |
   | B（採る） | 売上確定と返金で冪等キーを明示しない。stripe-java が、POST の呼び出しごとに UUID の冪等キーを作る ※3 | 変更が Stripe の実装の中で閉じる。売上確定と返金で同じ扱いになり、支払画面の作成とも揃う |
   | C | 呼び出しごとに UUID を作り、`capture-<注文 ID>-<UUID>` の形で明示する | 振る舞いは案 B と同じ。キーから注文を探せるが、metadata にも注文 ID があり、利点は小さい |

   ※2：売上確定を求めた時刻の列は使える。出荷の登録のたびに、行ロックの後に現在時刻で上書きされる。返金には同じ用途の列がない。

   ※3：stripe-java はリクエストを作るときにヘッダーを 1 回だけ作るので、その呼び出しの自動の再試行には同じキーが付く（stripe-java 34.1.0 のソースで確認した）。通信の失敗で自動で再試行するときに二重に処理しない点は、[決済の設計](../../02-設計/payment.md)の「Stripe」の表の行「タイムアウトと再試行」のとおり。

3. 冪等キーが試行ごとに変わっても、二重には確定・返金しない。理由：Stripe は、処理済みの PaymentIntent への 2 回目のリクエストを、次の表のとおり 400 で拒否する。このシステムは、それを成功として扱う（[決済の設計](../../02-設計/payment.md)の「Stripe」にある表「売上確定と返金の応答」）。売上確定も返金も金額は総額なので、2 回目が別の額で通ることはない。

   | 操作 | Stripe の拒否 | このシステムの扱い |
   |------|---------------|--------------------|
   | 売上確定済みの PaymentIntent の売上確定 | 400 `payment_intent_unexpected_state` | PaymentIntent を再取得し、`succeeded` なら成功とする |
   | 返金済みの PaymentIntent の返金 | 400 `charge_already_refunded` | 成功とする |

4. 決定 3 の前提（冪等キーが違うときの 2 つの 400 の応答）を、実装の前に Stripe の sandbox で確認する。作った PaymentIntent の ID は、tasks の結果に記録する。

## 受け入れ条件

### US-616-1 障害の後の再実行での売上確定と返金（B / P1）

- **AC-616-1** 売上確定が決済サービスの側の障害（5xx）で失敗した後、決済サービスが回復していれば、同じ注文の出荷の登録の再実行で売上を確定できる。
- **AC-616-2** 返金が決済サービスの側の障害（5xx）で失敗した後、決済サービスが回復していれば、返金のイベントの再発行で返金できる。
- **AC-616-3** 1 回目の売上確定を決済サービスが完了していて、応答だけが障害（5xx）だったときも、再実行で二重に確定せず、成功する。
- **AC-616-4** 1 回目の返金を決済サービスが完了していて、応答だけが障害（5xx）だったときも、再実行で二重に返金せず、成功する。
