# Spec 484：過去の注文の送料の消費税を、注文の成立のときに保存する

種類：整理　規模：M　ステータス：確定
危険度：高

## 背景と目的

追跡の issue は #484。今は、レポートに渡す送料の消費税を、読むたびに今の設定の送料の税区分と注文日時の税率から求めているため、設定の税区分を変える、または税率のマスターを修正すると、過去の注文の値が変わる。また、注文日時の税率がマスターにないと、例外が発生し、その注文のレポートへの取り込みが止まる。この spec は、注文の成立時に送料の消費税額を注文に保存し、読むときはその額を返す形にする。レポートは、注文 API が返す送料の消費税をそのまま使うので、レポートのコードは変えない。

## スコープ

| 含める | 含めない |
|--------|----------|
| 見積もりが、送料の消費税を求めて持つこと | 既存の注文の送料の消費税を、マイグレーションで埋めること（決定 2） |
| 注文の成立で、送料の消費税の額を注文に保存すること（列の追加を含む） | 送料の税率を保存すること（決定 1） |
| 読むときに、保存した額を返し、保存していない既存の注文は今の計算にすること | 税率ごとの消費税額の求め方（明細と送料を合算する）を変えること |
| 注文の設計の文書の修正（決定 5） | レポートのコードの変更 |

決定：

- 決定 1、3、4、5 は、issue 担当のセッションが利用者に代わって確認した。決定 2（既存の注文の扱い、DB の構造）は、利用者が 2026-11-21 に選んだ。
- 規模：M とする（[開発の進め方](../../05-開発規則/workflow.md)の「規模」の特例）。
  - 判定の表では、DB の構造を変えるので L に当たる。
  - M にする理由：変えるのは注文のモジュールの中だけで、モジュールをまたぐ設計の決定と、API と AC の対応がなく、plan に書く中身がないため。
- 危険度：高とする。理由：マイグレーションを加え、注文手続きの経路を変えるため。
- 決定 1（保存するもの）：注文の成立のときに、送料の消費税の額を注文に保存する。列は、注文の表の送料の消費税の列（null を許す）である。率でなく額を持つ。
  - 理由：レポートが使うのは額で、読むたびに端数を処理しなくてよいため。
- 決定 2（既存の注文）：列は null を許し、マイグレーションで既存の注文を埋めない。null の注文は、今と同じく、読むときに注文日時の送料の税区分の税率から求める。
  - 理由：マイグレーションで埋めると、注文のスキーマから税のモジュールの表を読む必要がある。モジュールが他のモジュールの表を読まない規則に反するため。
  - 退けた案：マイグレーションで今の税率から埋めて、NOT NULL にする（理由は上と同じ）。
- 決定 3（求め方）：見積もりが、送料の税率と送料から、送料の消費税を求めて持つ。注文の成立で、その額を注文に持たせる。
  - 求め方は、今の読み方と同じにする。送料が 0 なら 0、そうでなければ、送料だけを課税対象として税のモジュールの API で求めた額である。
- 決定 4（読み方）：レポートに渡す送料の消費税を求めるサービスは、注文に送料の消費税があればそれを返し、なければ今の計算をする。
- 決定 5（文書）：[注文の設計](../../02-設計/order.md)の「注文の参照」の箇条を、決定 1、2 の形に書き換える。成立のときに保存した額を返し、保存していない既存の注文は、注文日時の税率から求める。DB の設計の文書に注文の表の列の一覧があれば、列を加える。

決定に出るコードの名前は、次の表のとおり。

| 決定 | 識別子 | 指すもの |
|------|--------|----------|
| 1、2 | `ordering.sales_order.shipping_tax` | 注文の表の、送料の消費税の列（bigint、null を許す） |
| 2 | `OrderProperties.shippingTaxCategoryId` | 今の設定の、送料の税区分 |
| 3 | `Quote`（`module/order/domain/quote/`） | 注文の見積もり |
| 3 | `QuoteQueryService.shipping` | 見積もりで、送料とその税区分の税率を求める処理 |
| 3 | `taxDirectory.consumptionTaxes` | 税率ごとの消費税額を求める、税のモジュールの API |
| 4 | `OrderReportQueryService.shippingTax` | レポートに渡す送料の消費税を求める処理 |
| 4 | `OrderSnapshot.shippingTax` | 注文の API が返す、送料の消費税 |

## 目的と完了条件

### DS-484-1 過去の注文の送料の消費税が、設定や税率のマスターを変更しても変わらない（D / P1）

- **DC-484-1** 注文の成立で、送料の消費税の額が注文に保存されることを、テストで確認している。
- **DC-484-2** 保存した後に、送料の税区分の設定を変えても、その税率を修正しても、レポートに渡す送料の消費税が変わらないことを、テストで確認している。
- **DC-484-3** 送料が 0 の注文では、保存する送料の消費税が 0 である。

### DS-484-2 既存の注文の扱いが、今と同じである（D / P1）

- **DC-484-4** 送料の消費税を保存していない注文（列が null）は、今と同じく注文日時の税率から求めることを、テストで確認している。

### DS-484-3 文書が決定どおりで、検査が成功する（D / P1）

- **DC-484-5** 決定 5 の文書が、決定の形になっている。
- **DC-484-6** `./gradlew check` が通る。

## Non-goals

| 項目 | 理由 |
|------|------|
| 既存の注文の送料の消費税を埋めること | モジュールが他のモジュールの表を読む規則に反するため（決定 2） |
| 送料の税率を保存すること | レポートが使うのは額のため（決定 1） |
| 税率ごとの消費税額の求め方を変えること | 税率ごとの消費税額は、請求する総額と注文の画面の表示に使い、求め方を変えると消費者に見える金額が変わりうるため |
| レポートのコードの変更 | レポートは、注文の API が返す値をそのまま使うため |
