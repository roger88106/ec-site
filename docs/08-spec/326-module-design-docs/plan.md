共通の決定：

- 危険度は高（spec の冒頭）。マージは利用者が許可する。
- 段階の最後の重要な観点のレビューは、危険度が高いので高性能で行う。
- CI の検査の script を変えるので、pull request の前に、文脈を持たない高性能のレビュー役（`reviewer`）を 1 回加える。観点は、検査の判定を別の書き方で回避できないかである。認証・支払・権限の経路を変えないので、セキュリティのレビューは行わない。
- 実装は実装役（汎用）に 1 タスクずつ任せる。文書の本文は、spec 担当が日本語の要点を書き、日本語だけの文脈の実装役（汎用）が書く。spec 担当はコードを書かない。
- 1 タスクを 1 commit にする。例外は、検査の script のテストと実装である（[開発の進め方](../../05-開発規則/workflow.md)の「循環」）。もう 1 つの例外は、T326-01-02 と T326-01-04 を同じ commit に入れることである。理由：AC 一覧の列を変えると、今の `ac-check` が失敗するため。
- push は段階の最後に行う。draft の pull request は、spec の最後のレビューの後に作る（[開発の進め方](../../05-開発規則/workflow.md)の「規模」）。
- 各段階の ③ の書き換えの確認方法は、「③ の書き換えと構造の検査」に書く。
- BR を移すときは、BR ごとに「BR の行き先」の表に書く（段階 2〜5 で埋める）。
- AC のモジュールの割り当ては、段階 1 で全件を決める（迷う AC の扱いは「AC の正本と ac-check」の表）。
- 並行する C3 のセッションとの重なりは、[spec](spec.md)の「依存」に書く。実装を始める前の照合で、`develop` を取り込み、変えるファイルの重なりを再度照合する。

## ③ の書き換えと構造の検査（DS-326-1：DC-326-1〜6）

| 何を | どこに | 確認方法 |

- 書き換えは、モジュールごとに 2 タスクで行う。段階 3〜5 は同じ形のタスクを繰り返す。各モジュールで、先に ② を作り（API の表を OpenAPI と照合）、後に ③ を書き換える（書き換え前と照合し、構造の検査の対象に加える）。理由：③ から外す内容を、先に ② に移すため。
- 構造の検査の対象に加えるのは、書き換えたモジュールからである。まだ書き換えていない ③ は検査しない。
- ③ の書き換えの確認方法：構造の検査が通り、節の名前か順を変えると失敗する。書き換え前（`develop` の 57ef9635）と並べて読み、規則の欠落を表にする（サブエージェント（汎用）が照合する）。
- 消した・名前を変えた見出しを指すコードのコメントを、`doc-refs` で探し、修正する（DN-326-1 の例外）。例：`CartContents.java` と `CartContentsApi.java` が、カートの ③ の「他のモジュールへの公開」を指している（段階 4）。
- ① から ④ の間で、他の層の内容は写さずに指す（DC-326-5）。
- 確認 10 が案 A である理由：節の名前の正本が 1 つになる。12 件の ③ を対象に加える本 spec で、同時に確認できる。
- 確認 10 が案 B のときは、script の定数を残し、雛形と定数を照合するテストを加える。案 C のときは、#325 を含めず、DC-326-3 を外す。

- AC 一覧の列は、AC、モジュール、状態、元の spec、変えた spec、今の内容の順にする。
- 列「モジュール」は、③ の文書のファイル名から `.md` を除いた名前（`order` など）か、`common`（共通）。廃止の AC は空でよい。
- `--write` の転記（T326-01-04 で実装役が決め、spec 担当が承認した）：AC の順の位置に、モジュールを空、状態を有効、変えた spec を「—」、元の spec を進行中の spec へのリンクにして入れる。モジュールが空なので検査が失敗し、割り当ての書き漏れを知らせる。今の内容は定義の文に箇条を「：」と読点でつなぐ。
- spec をアーカイブに移すときは、AC 一覧の元の spec のリンクを、アーカイブのパスに書き換える（リンク先のディレクトリがないと検査が失敗する）。手順は `workflow.md` に書く（T326-01-09）。
- spec の中だけで通じる参照として検査が見つけるのは、`※` と数字、「事実」と数字、US の番号、「spec の「」の 4 つの形。根拠の形は、リンクの直後に「の「…」」が続くかだけを見る。
- 共通は、どのモジュールにも属さない AC（ポートと構成の設定、API の契約の全体、イベントの再発行、運営者のアカウントと権限など）。AC 一覧だけに置き、③ の表には生成しない。今の内容には、根拠に、今の規則がある共通の文書（② の共通の文書、規則の文書、手順書）を、文書の名前のリンクの直後に「の「<見出し>」」を続ける形で添える（spec の確認 12）。
- 列「今の内容」は 1 つのセルに書く。有効の AC は、spec の定義の文を写す。定義の下の箇条は、「：」の後に読点で並べる。
- 列「今の内容」に、spec の中だけで通じる参照（`※1`、「事実 2」、US の番号、spec の節）を残さない。意味を補って書き換えるか、削る。
- 変更の AC の列「今の内容」は、今の規則を短く書き、根拠を、文書の名前のリンクの直後に「の「<見出し>」」を続ける形で添える。注文の ③ の今の表にある AC は、その表の文を使う。ただし、spec の中だけで通じる言い回し（「元の spec のとおり」「今までどおり」など）は書き換える。
- ③ の生成の表の列は、AC、今の内容、元の spec。マーカーは `<!-- generated:module-ac -->` と `<!-- /generated:module-ac -->` で、モジュールは ③ のファイル名で決まる。
- テストとの対応は `node scripts/ci/ac-check.mjs --tests` で表示する。
- `ac-check` が照合・生成するのは、構造の検査の対象の一覧にある ③ だけである。その ③ の「今有効な AC」の節には、生成のマーカーの組（AC 一覧と同じ形の HTML のコメント）が必須で、ないときは検査でも `--write` でも失敗にする。一覧にない ③ にマーカーがあれば失敗にし、`--write` は一覧にない ③ を変えない。
- マーカーの置き方：マーカーの組は、③ を固定の節に書き換えるときに、「今有効な AC」の節に手動で置く。`--write` は、マーカーの範囲の中の表だけを書き換える。③ の雛形の骨組みの「今有効な AC」の節にも、マーカーの組を置く。
- ③ のモジュールの名前は、バックエンドのモジュールのディレクトリ（`backend/ecsite/src/main/java/com/ecsite/module/<名前>/`）があり、かつ `docs/03-機能仕様/<名前>.md` がある名前である。`template`、`acceptance-criteria`、`glossary` は、バックエンドにないので当たらない。
