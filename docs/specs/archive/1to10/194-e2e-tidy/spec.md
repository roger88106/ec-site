# Spec 194：E2E の推奨の指摘と、ローカルの script のプロセスの操作を整える

ステータス：確定

## 1. 背景と目的

MVP 019 の全体のレビューで出た、E2E に関する推奨の指摘 15 件（#89）が残っている。また、spec 104 で E2E の実行の script とスロットの script にプロセスの操作を加えたが、同じ処理が 2 か所にある（#137）。どちらも E2E と、E2E を実行する script を変える。

- #89 は 5 件の細目だけが残り、「ほか 10 件」の細目は記録に残っていない。spec の作成の最初に、同じ観点で E2E を再調査した（第 3 節）。
- #137 のうち、プロセスの生存の確認は、spec 183（DC-183-11）で共有のモジュールに共通化済みである。残るのは、子のプロセスの停止と、Windows で Gradle のデーモンが起動したバックエンドの停止である。

追跡の issue は [#194](https://github.com/roger88106/ec-site/issues/194)、扱う issue は [#89](https://github.com/roger88106/ec-site/issues/89)、[#137](https://github.com/roger88106/ec-site/issues/137) である。作業ブランチは `194-e2e-tidy`。本 spec は整理の spec で、規模は M である（第 6 節の 1）。

## 5. 守る制約

- **DN-194-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。
- **DN-194-2** テストを弱めない。補助に移すときは、確認する内容を減らさない。AC をテスト名から外すのは、第 6 節の 2 のときだけ。
- **DN-194-3** E2E の全体の時間を大きく延ばさない。理由：CI の E2E のジョブとローカルでの確認で毎回実行するため。
- **DN-194-4** 新しく書くコメントに、spec・plan の番号を書かない（コメントの書き方 第 1 節。本番のコードと同じ扱いにする）。
- **DN-194-5** 並行する spec（#195 TypeScript 7 は E2E の型を、#185 は検査の script と除外の一覧を変える）とファイルが重なりうる。並行の可否は、規模 M で plan がないので、実装を始める前の照合（[開発の進め方](../../../../rules/workflow.md) 第 5.6 節）で互いの変えるファイルを照合して決め、追跡の issue に書く。

## 6. 決めたこと

spec の確認で、利用者が全て案 A に決めた（2026-10-26）。規模 M も同じ時に承認した。Open questions はない。

### 6.1 規模

規模は M である。API の契約とデータベースを変えず、AC を追加も変更もしないため。変えるのは E2E、スロットのライブラリ、E2E の実行の script、文書である。

### 6.2 AC の不一致の修正の方法（DC-194-22〜24）

- 案 A（推奨。採用）：テスト名と step の名前を、確認している内容の AC だけに狭める。外すと AC に他のテストがなくなるときだけ、その確認を E2E に加える。理由：AC の多くはバックエンドと画面のテストで確認していて、E2E は画面をまたぐ流れを確認する役目のため。E2E の時間も延びない（DN-194-3）。
- 案 B：名前を変えず、名前に書いた AC の全ての条件の確認を E2E に加える。照合は 1 回で済むが、E2E が長くなり、他のテストと重なる。

### 6.3 全画面の撮影の作業用のファイル（DC-194-31）

メインの作業ツリーに、全画面を撮る作業用のテスト（約 400 行）と設定がある。

- 案 A（推奨。採用）：`/.local/` に移し、Git の除外の 2 行を削除する。理由：AGENTS.md の Git の表で、作業用の script は `/.local/` に置くため。Playwright は設定でテストの場所を選べるので、ツールが置き場所を決める例外に当たらない。
- 案 B：撮影（showcase）と同じく、リポジトリに入れて保守する。補助の共有（DC-194-13）の対象に加わる。
- 案 C：使わないなら削除する。

### 6.4 テストのファイル名（DC-194-29）

- 案 A（推奨。採用）：公開の予約は `publish-schedule.spec.ts`、在庫の確保の同時の操作は `stock-hold-race.spec.ts` に名前を変える。AC 一覧のテストの列も修正する。
- 案 B：名前を変えない（DC-194-29 を除く）。

### 6.5 Windows のバックエンドの停止の方法（DC-194-3、4）

Windows では、子のプロセスのツリーを停止しても、Gradle のデーモンが起動した Spring Boot のプロセスがツリーの外に残り、ポートを使い続けることがある。利用者のローカルの環境で、バックエンドを起動したタスクを停止した後も、バックエンドのポートが使われ続けたことがある（2026-10-15）。どの場合に残るかは、まだ確認していない。

- 案 A（推奨。採用）：最初のタスクで、スロットのバックエンドと E2E のバックエンドで残るかを確認する。残るなら、ツリーを停止した後に、そのスロットのバックエンドのポートで待ち受けるプロセスを停止する。理由：今の手動の手順（skill `local-dev`）と同じ方法で、ポートはスロットで決まっているため。
- 案 B：バックエンドを Gradle のデーモンを使わずに起動し、ツリーの中に収める。起動が遅くなり、デーモンを使わない起動でも別のプロセスが切り離されることがあるので、確認が必要になる。

T194-01-01 で、残るのはスロットの script の node を強制終了したときだけと分かった（Ctrl+C で停止したときと E2E では残らない）。強制終了のときは script の停止の処理が動かないので、利用者が案 A の停止の時点を次のとおりに決めた（2026-10-26）。

- スロットの解除で、スロットのポートで待ち受けるプロセスを停止する（DC-194-32）。ポートの問い合わせが失敗したときと、停止の後もバックエンドが応答するときは、データを削除せずに解除をやめ、停止のコマンドを表示する（DC-194-34）。理由：問い合わせの失敗を「待ち受けなし」とみなすと、動いているバックエンドのデータベースを削除しうるため（段階 1 の `[リスク]` のレビュー）。
- スロットのバックエンドの起動で、ポートが使われているときは、自動で停止せず、そのプロセスの ID と停止のコマンドを表示して終了する（DC-194-33）。理由：利用者が別に起動したバックエンドを、確認なしに停止しないため。

## 7. Non-goals

| 項目 | 理由 |
|------|------|
| 大きいテストを振る舞いごとに分ける（第 3 節の 16） | 分けると、ログインと商品の作成をテストごとに繰り返し、E2E が長くなる（DN-194-3）。AC を狭める（第 6 節の 2）ことで、名前と内容の不一致は解ける |
| E2E のコメントの spec の番号を削除する、番号の検査を E2E に広げる（第 3 節の 17） | コメントの書き方 第 1 節の対象は本番のコードで、E2E は違反ではない。規則を広げるかは別に決める（第 9 節） |
| 時間の待ちの検査の除外を、行か関数の単位にする | #185 のコメントの 10 で、#185 が扱う。本 spec は E2E の実行の script の除外をなくす（DC-194-7） |

## 8. tasks

- `[P]` のタスクはない。同じ段階のタスクは、番号の順に 1 つずつ行う。理由：多くのタスクが同じ補助のファイルを変えるため。
- `[テスト]` のタスクは、テストを書いてレッドを確認し、同じ実装役が続けて実装する（[開発の進め方](../../../../rules/workflow.md) 第 2.1 節の例外のとおり同じ commit に入れる）。
- E2E を変えるタスクは、変えたテストのファイルを実行して通ることを確認する。各段階の最後に E2E の全体を実行し、かかった時間を段階 1 の前と比べて、段階のレビューのタスクの結果に書く（DN-194-3）。理由：E2E の全体は時間がかかるため。
- 各段階の最後のレビューは、profile「厚め」で行う（[エージェントの作業フロー](../../../../rules/subagents.md) 第 4 節）。重要な観点に「テストを弱めていないか」（DN-194-2）と「新しいコメントに spec・plan の番号がないか」（DN-194-4）を含める。
