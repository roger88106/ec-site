# Spec 547：イベントの再発行と順序の扱いを修正する

種類：整理　規模：L　ステータス：草案

## 背景と目的

#458（main 全体の書き方と構成のレビュー）で、イベントの再発行と順序の扱いに 3 つの問題が見つかった。追跡の issue は #547（#544 の一部）で、sub-issue は #486 と #433 である。#433 は #486 の 1 項目めと同じ内容である。消費者・運営者に見える振る舞いは変えない（例外は DN-547-1）。

1. 再発行のジョブは、発行からの時間、最後の処理からの時間、処理の回数だけでイベントを選び、処理の状態は見ない。まだ処理中のイベントにも、同じイベントがもう一度渡される。
2. 止めた印は、処理の回数が上限と等しいイベントにしか付かない。上限の設定を下げると、印もエラーのログもないまま、止めたイベントの件数に入るイベントができる。
3. 在庫のリスナーは、同じイベントの重複は正しく処理できるが、順序の入れ替わりは正しく処理できない。バリアントの登録のイベントの処理が削除のイベントより後になると、バリアントのない在庫の行が残る。

## スコープ

| 含める | 含めない |
|--------|----------|
| 再発行するイベントを、最後の処理に失敗したものに限る | 再発行の既定値（間隔、時間の下限、回数の上限）の変更 |
| 止めた印の付け方を「処理の回数が上限以上で、まだ印がない」に変え、上限を下げても印とエラーのログが漏れないようにする | 止めたイベントの通知の変更 |
| 止めたイベントを、再発行のための読み込みの対象から外す（方法は Open questions の 1） | 在庫以外のリスナーの修正（確認して、問題があれば起票する） |
| 在庫の作成が、バリアントの削除・商品の削除の後に処理されても、在庫の行が残らないようにする（方法は ※1） | |
| 設計書の「イベント」の規則に「届く順序も前提にしない」を加え、全てのイベントのリスナーが、順序の入れ替わりを正しく処理できるか確認する | |
| 止めたイベントの扱い（印、検知、復旧の手順）の設計書の記述を、変えた方式に合わせる | |

※1：在庫の作成（DC-547-9）の方法は、次のとおり決めた（issue 担当のセッションが利用者に代わって承認した。2026-11-18）。

- 在庫の作成を、商品カタログのバリアントの登録と同じトランザクションの中で、イベントを同期で受けて行う。
- 例外を加える節は、[バックエンドのアーキテクチャ](../../02-設計/backend-architecture.md)の「モジュラーモノリス」。
- DB の構造は変えない。

## 目的と完了条件

### DS-547-1 再発行のジョブが、処理中のイベントを重ねてリスナーに渡さない（D / P1）

- **DC-547-1** 再発行のジョブは、最後の処理に失敗した状態のイベントだけを再発行する。まだ結果の出ていないイベント（発行の直後、リスナーの処理中、再発行の処理中）は、発行から下限の時間を過ぎていても再発行しない。
- **DC-547-2** 処理の途中でインスタンスが止まったイベントは、Spring Modulith の監視が失敗の状態にした後の実行で、再発行されるか止められる。
- **DC-547-3** 処理の回数が上限に達する前に成功したイベントは、完了の状態になる。処理に失敗し続けるイベントは、上限に達したら再発行されない（AC-290 の振る舞いを保つ）。

### DS-547-2 止めたイベントが、上限の設定によらず、漏れずに記録される（D / P1）

- **DC-547-4** 処理の回数が上限以上で、最後の処理に失敗し、まだ止めた印のないイベントに、次の実行で印を付け、エラーのログに 1 回だけ出力する。
- **DC-547-5** 上限を今の処理の回数より小さい値に下げても、その時点で上限以上の失敗したイベントは全て、DC-547-4 のとおり印が付き、エラーのログが出力される。
- **DC-547-6** 止めたイベントは、再発行のジョブが再発行のために読み込む対象に入らない。
- **DC-547-7** 未完了のイベントと止めたイベントの件数のメトリクスが、変えた方式でも今と同じ意味の値を示す。
- **DC-547-8** 止めたイベントを復旧する手順（原因を修正した後に再発行させる、または不要なら削除する）が設計書にある。

### DS-547-3 イベントの届く順序が入れ替わっても、在庫の行が残らない（D / P1）

- **DC-547-9** バリアントを登録する処理が、そのバリアントか商品を削除する処理より後になっても、そのバリアントの在庫の行が残らない。
- **DC-547-10** 設計書の「イベント」の規則に、リスナーは同じイベントの重複に加えて、届く順序も前提にしないことが書いてある。
- **DC-547-11** 全てのイベントのリスナーについて、順序の入れ替わりを正しく処理できるかを確認した結果（リスナー、受けるイベント、結果）が pull request に書いてある。
- **DC-547-12** 在庫以外で、順序の入れ替わりを正しく処理できないリスナーが、issue に起票してある。

### DS-547-4 既存のテストと CI の検査が通る（D / P1）

- **DC-547-13** `./gradlew check` が通る。
- **DC-547-14** ローカルの seed で起動し、管理画面で商品とバリアントを登録・削除して、在庫の画面が開ける。

## 非機能要件

- **DN-547-1** 消費者・運営者に見える振る舞いを変えない。例外は、在庫の行が残る不具合の修正（DC-547-9）と、止めたイベントの扱いの修正（DC-547-4〜6）である。どちらも #458 のレビューで見つけた不具合である。
- **DN-547-2** 再発行の設定のキーと既定値を変えない。
- **DN-547-3** 適用済みのマイグレーションを変えない（Flyway の checksum が変わるため）。

## Open questions

1. 止めたイベントを、再発行のための読み込みから外す方法（DC-547-4〜7）。印を、処理の回数と上限の比較とは別の方法で表す必要がある。Spring Modulith の状態は次の 5 つ（発行済み・処理中・完了・失敗・再発行済み）に決まっていて、止めたことを表す値がないため。
   - 案 A（推奨）：止めたイベントを、イベントの記録の表から、止めたイベントの表（新しく作る）に移す。再発行のジョブは、Spring Modulith の「失敗したイベントの再発行」の操作で、失敗の状態のイベントだけを読む。印は移したことで表し、移す条件（上限以上で失敗）は、上限を変えても同じ判定になる。DB の構造を変える（表の追加）ので、利用者の確認が必要。復旧は、行をイベントの記録の表に戻す手順になる。
   - 案 B：表を変えない。印は、処理の回数をどの上限よりも大きい固定の値にして表す。再発行の条件に失敗の状態を加える。読み込みは今と同じく全ての未完了のイベントを読む（DC-547-6 を満たさない。DC-547-6 を spec から外す）。
