## 注文手続きと注文の成立

- [ ] **T2306** マイグレーション：注文手続き、注文、注文明細、注文の税率ごとの消費税額のテーブル（schema `ordering`。論理名を付ける）。
- [ ] **T2307** [テスト] 注文の単体テスト：初期状態は受付、写し（AC-92）、注文番号の形式（BR-10）、お届け先の検証（AC-86。郵便番号・電話番号の正規化、47 都道府県、長さ）。
- [ ] **T2308** 注文の集約、注文番号、お届け先を実装する。T2307 を通す。
- [ ] **T2309** [テスト] Repository の統合テスト：注文の保存と再構築、注文番号の重複で作り直す、注文手続きごとに注文は 1 つ。
- [ ] **T2310** Repository を実装する。T2309 を通す。
- [ ] **T2311** [テスト] 注文手続きの受け入れテスト（MockMvc）。
  - 進むと全品目を 15 分引き当てる。足りなければ 409 で何も引き当てない（AC-82）
  - 空・購入できない品目のカートは 400（AC-88）
  - 進み直すと前の引当を解いて引き当て直す。カートを変えると引当が解かれる（イベント。AC-84）
  - 注文手続きの表示：見積もりと期限、成立済みなら注文 ID
- [ ] **T2312** 注文手続きと、カート変更のイベントのリスナーを実装する。T2311 を通す。
- [ ] **T2313** [テスト] 注文の成立の受け入れテスト（MockMvc）。
  - 成立で在庫が減り、引当が消え、カートが空になり、注文番号が振られる（AC-87、90）。調整履歴に注文の理由（AC-107）
  - 引当の期限切れ：足りれば成立、足りなければ 409 で在庫も注文もカートも変わらない（AC-87）
  - 確認した総額と違えば 409（AC-89）。注文手続きの後にカートが変われば 409
  - 入力の形式の誤りは 400（AC-86）
  - **二重送信**：同じ注文手続きで同時に 2 回送っても注文は 1 つで、2 回目は同じ注文 ID（AC-91）
  - **同時の注文**：引当の期限が切れた 2 人が販売可能数 1 の在庫を同時に注文すると、1 件だけ成立する
  - 成立後に商品の価格・税率を変えても、注文の内容と金額は変わらない（AC-92）
  - 注文の表示（AC-93、94）。存在しない注文は 404
  - 注文成立のイベントが発行される
- [ ] **T2314** 注文の成立と注文の表示を実装する（plan 002 第 2 節の手順）。T2313 を通す。
