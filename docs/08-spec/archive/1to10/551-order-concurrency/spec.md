# Spec 551：注文手続き・与信の成功の反映・会員とカートの作成の並行の扱いを整える

種類：整理　規模：M　ステータス：確定

## 背景と目的

注文手続き、与信の成功の反映、会員とカートの作成で、並行する処理の扱いを整える。追跡の issue は #551（#544 の組の issue）。sub-issue は #482、#483、#462、#592、#593。#544（リリースの前の整理）の段階 3 の線 A の 4 番目に当たる。消費者・運営者に見える振る舞いは、DN-551-1 の 2 点を除いて変えない。API の契約（OpenAPI）、DB の構造、AC も変えない。

- #482：与信の成功を反映する処理は、注文を受付にし、同じトランザクションで注文した品目をカートから除く。カートの保存は楽観ロックなので、会員が同時にカートを変えると同時の変更（409）になり、注文の受付ごと巻き戻る。注文はイベントの再発行（5 分ごと）まで支払待ちで残り、支払済みなのに「支払待ち」と表示され、支払待ちの上限の数にも入る。また、除く先のカートを注文手続きから特定するので、注文手続きが保存期間の後に消されてから与信が届くと、カートから品目が除かれない（今は注文の機能仕様の、与信の成功の注で受け入れている）。
- #483 の 1：注文手続きの開始は会員のロックを取らない。同じカートで同時に開始すると（二重の送信、複数のタブ）、両方が前の引当を解き、それぞれ引き当てる。期限（15 分）まで二重に引き当てたままになり、他の消費者の販売可能数が減る。注文は会員のロックで直列にしている。
- #483 の 2：カート変更のイベントにはカートのバージョンがなく、受けた側は、そのカートの全ての注文手続きの引当を解く。カートの変更の直後に開始した注文手続きの引当も、遅れて届いた・再送された古いイベントで解かれる。
- #483 の 3：カートの追加・増量で確認する販売可能数は、自分の注文手続きの引当も数える。カートの機能仕様の、販売可能数の注に意図として書いてある。
- #462：会員を作る処理は、一意制約で衝突しても失敗しない挿入の後に会員 ID を再取得し、見つからなければ、原因の例外も、会員を特定する値も持たない例外を投げる。挿入と再取得の間にその行が消えたときにだけ起きる。会員の削除はないが、カートは片付け（最後の変更から 30 日）で消えうる。会員のカートを作る処理も同じ形。
- #592：カート変更のイベントの処理が遅れる（失敗して再発行される）と、その後に始めた注文手続きの引当まで解き、解いた引当は戻らない。与信の成功の処理がカートから除くときに発行するカート変更のイベントでも同じことが起きる。#483 の 2 と同じ原因である。
- #593：与信の成功のイベントの処理が遅れると、その間に会員が変えた同じバリアントの行（数量の変更、同じバリアントの追加で数量が加わった行）も、数量によらず除く。発行の順に処理されれば、会員が変えた行は残る。

決定：

- 決定 1〜7 は、issue 担当のセッションが利用者に代わって 2026-11-20 に確認した（全て推奨の案）。決定 8 は、利用者が同じ日に選んだ。
- 規模：M とする（[開発の進め方](../../05-開発規則/workflow.md)の「規模」の特例）。
  - 判定の表では、3 つのモジュール（注文、カート、会員）にまたがるので L に当たる。
  - M にする理由：API の契約と DB の構造を変えず、モジュールをまたぐ決定は決定 1 と決定 4 だけで、この spec の決定に書けるため。前例は [spec 557](../archive/1to10/557-member-id-lookup/spec.md)。
- 決定 1（除く先のカート）：注文の会員の ID から、カートの API で会員のカートを特定する。カートの API に、会員のカートの ID を返す照会（なければ空。作らない）を加える。
  - 理由：注文手続きは会員の自分のカートでしか始められず、カートは会員ごとに 1 つ（一意制約）なので、今と同じカートになるため。注文手続きの保存期間に頼らない。
  - 今と違いが出るのは 2 つ。注文手続きが消えた後に与信が届いても、カートから除く（#482 の目的）。カートが片付けで消えて再作成されていれば、新しいカートから同じバリアントを除く。
  - 退けた案：注文にカート ID の列を加える。理由：DB の構造を変えるため。
  - ゲストの購入を加えるときは、この決定を再検討する（注文がゲストのカートを知る手段が必要になる）。
- 決定 2（反映とカートからの除去を分ける）：与信の成功を反映する処理は、注文を受付にしてコミットするだけにする。注文モジュールの中に、注文の状態の変化（受付への遷移）のイベントを受けるリスナーを置き、別のトランザクションで注文した品目を会員のカートから除く。
  - カートから除く処理に失敗したら（カートの同時の変更など）、未完了のイベントの再発行で再実行する。
  - カートのモジュールが注文のイベントを受ける形は取らない。理由：注文がカートに依存しているので、依存が循環するため。
  - 消費者に見える差：受付の直後に、注文した品目がカートに短時間残りうる。注文の機能仕様の該当の箇所に明記する。
- 決定 3（開始の会員のロック）：注文手続きの開始の最初で、注文と同じ会員のロックを取る。
  - 注文の設計の「同時の注文」の、会員のロックを取るのは注文だけで開始では取らないとする箇条を書き換える。
  - ロックを取れなければ、#556 の決定どおり 503（処理中）になる。処理中のエラーは全ての操作に共通のエラーに含まれるため、API の契約は変わらない。
- 決定 4（カート変更のイベントのバージョン）：カート変更のイベントに、変更の後のカートのバージョンを加える。受けた側は、そのバージョンより古いカートのバージョンで始めた注文手続きの引当だけを解く。この決定で #592 も解消する（与信の成功の処理が発行するカート変更のイベントも同じ扱い）。
  - バージョンを持たないイベント（変更前に発行され、未完了で残ったもの）は、今と同じく、そのカートの全ての注文手続きの引当を解く。
- 決定 5（会員とカートの作成）：会員の作成と会員のカートの作成を、一意制約で衝突したら同じ値で書き換えて ID を返す 1 つの文にする（文の形は次の表の、1 つの文の行）。再取得して見つからない分岐と、その例外をなくす。
  - 既にあるときは、既存の行の値（作成日時、更新日時、バージョンなど）を変えない。テストで確認する。
  - 退けた案：分岐を残し、例外のメッセージに状況を入れる。理由：分岐の原因が残るため。
  - 退けた案：挿入と再取得を同じ文に書く。理由：同じ文の中では、同時に作られた行が見えないため（#462）。
- 決定 6（カートの販売可能数）：カートの追加・増量で確認する販売可能数は、今と同じく自分の注文手続きの引当も数える。今の振る舞いを固定するテストを加える。
  - 理由：カートの機能仕様の、販売可能数の注に意図として書いてあり、変えると消費者に見える振る舞い（数量が在庫を超えるエラーの有無）が変わり、整理の範囲を超えるため。変えるなら別の機能の spec にする。
- 決定 7（文書）：
  - 注文の機能仕様：
    - カート変更のイベントを受けたときの、注文手続きの箇条は、決定 4 の形にする。
    - 「状態の遷移」の節の、受付になるとき同じトランザクションでカートから注文した品目を除くと定める箇条は、決定 2 の形にする。
    - 与信の成功の注は、決定 1、2、8 の形に書き換える。
    - 注文手続きの開始も会員ごとに 1 つずつ処理することを書く。
  - 注文の設計：「同時の注文」の開始の箇条を決定 3 の形にする。「支払と受付」の図を、受付のコミットの後にイベントで別に除く形にする。
  - カートの設計：イベントの表の「カート変更」の項目にバージョンを加える。API に会員のカートの ID の照会を加える。
  - 会員の機能仕様の、会員の作成の注を、決定 5 の形にする。カートの機能仕様の、会員ごとに 1 つの箇条も同じ形か確認し、必要なら修正する。
  - AC も業務規則の番号（BR）も追加・変更しない。
- 決定 8（与信の成功が遅れた間の会員の変更）：与信の成功の後にカートから除くときは、今と同じく、注文した品目（バリアント）の行を数量によらず除く。処理が遅れた間に会員が同じバリアントの行を変えても、その行を除く。
  - この振る舞いを注文の機能仕様の、与信の成功の注に明記し、テストで固定する。AC-147 の文は変えない。
  - 理由：困るのは、受付の前後にカートに戻って同じバリアントを変えた消費者だけで、影響が小さいため。
  - 退けた案：注文した数量だけ減らす。理由：AC-147 の意味が変わり、完了した spec の AC を変える変更は機能の spec で行うため（[開発の進め方](../../05-開発規則/workflow.md)の「コードと文書の食い違い」）。
  - 退けた案：注文の時点のカートのバージョンより後に変わった行を除かない。理由：バージョンはカートに 1 つで行ごとにないため。行ごとに持たせると DB の構造を変える。
- 決定 9（受付の後に入れた行）：カートから除く処理は、受付の時刻より後に入れた行を除かない。同じイベントが 2 回届いても、1 回目の後に会員が入れ直した行が残る（段階のレビューで見つかり、issue 担当のセッションが 2026-11-21 に確認した）。
  - 受付の時刻とカートの行の入れた日時は、どちらもアプリの時計で記録したものを比べる。インスタンスの時計の差の分だけ、境界がずれうる。

## 目的と完了条件

### DS-551-1 与信の成功の反映が、カートの競合と注文手続きの保存期間に左右されない（D / P1）

- **DC-551-1** カートの保存が同時の変更で失敗しても、注文が受付のまま残ることを、テストで確認している。
- **DC-551-2** カートから除く処理が失敗したとき、イベントの再発行で再実行され、品目が除かれることを、テストで確認している。
- **DC-551-3** 注文手続きが消えた後に与信の成功を受けても、注文した品目が会員のカートから除かれることを、テストで確認している。
- **DC-551-4** 与信の成功の処理が遅れ、その間に会員が同じバリアントの行を変えても、その行を除くことを、テストで固定している。
- **DC-551-14** 同じ受付のイベントを 2 回受けても、1 回目の後に入れた行を除かないことを、テストで確認している。

### DS-551-2 注文手続きの開始とカートの変更が並行しても、引当が正しく残る（D / P1）

- **DC-551-5** 同じカートで注文手続きを同時に開始しても、有効な引当が 1 つの注文手続きの分だけであることを、テストで確認している。
- **DC-551-6** カート変更のイベントを受けても、イベントのバージョン以降に始めた注文手続きの引当を解かないことを、テストで確認している。
- **DC-551-7** イベントのバージョンより古いバージョンで始めた注文手続きの引当は解き、バージョンを持たないイベントでは全ての引当を解くことを、テストで確認している。
- **DC-551-8** カートの追加・増量で、自分の注文手続きの引当も数えて販売可能数を判定することを、テストで固定している。

### DS-551-3 会員とカートの作成で、再取得して見つからない分岐がない（D / P1）

- **DC-551-9** 会員の作成と会員のカートの作成が、1 つの文で ID を返し、再取得の分岐と例外がない。
- **DC-551-10** 既にあるときは既存の ID を返し、既存の行の値（作成日時、更新日時、バージョンなど）が変わらないことを、テストで確認している。
- **DC-551-11** 同じ会員の初回リクエストが同時に届く既存の統合テスト（会員の確認のテスト、会員のカートの API のテスト）が通る。

### DS-551-4 文書と検査が通る（D / P1）

- **DC-551-12** 決定 7 の文書が、決定の形になっている。
- **DC-551-13** `./gradlew check` が通る。

## 非機能要件

- **DN-551-1** 消費者・運営者に見える振る舞いを変えない。例外は 2 点で、注文の機能仕様に明記する。受付の直後に、注文した品目がカートに短時間残りうる（決定 2）。注文手続きが消えた後に与信が届いても、カートから除く（決定 1）。
- **DN-551-2** API の契約（OpenAPI）、DB の構造、AC を変えない。
- **DN-551-3** アーカイブした spec を変えない。
- **DN-551-4** 同時の変更（409）と処理中（503）は、#556 の決定どおり自動で再試行しない。
