# 店舗画面（`frontend/store`）の構成

C 側（消費者）の画面。Next.js（App Router）で、店舗 API（`store.yaml`）をサーバーコンポーネントとサーバーアクションから呼ぶ（ブラウザーから API は呼ばない）。管理画面との違いと共通の決まりは [フロントのアーキテクチャ](../frontend-architecture.md)。新しい画面は「画面を追加する手順」で作る。

| 項目 | 内容 |
|------|------|
| 依存 | 店舗 API（`store.yaml`）、消費者の realm（IdP。ログイン）、共有のパッケージ（`frontend/shared`） |
| 関連 spec | [007](../../08-spec/archive/mvp/007-payment)、[009](../../08-spec/archive/mvp/009-shipping)、[012](../../08-spec/archive/mvp/012-test-safety-net)、[014](../../08-spec/archive/mvp/014-frontend-consistency)、[015](../../08-spec/archive/mvp/015-security)、[016](../../08-spec/archive/mvp/016-master-data)、[017](../../08-spec/archive/mvp/017-stability)、[104](../../08-spec/archive/1to10/104-parallel-local-env)、[134](../../08-spec/archive/1to10/134-admin-tidy)、[135](../../08-spec/archive/1to10/135-store-cleanup)、[157](../../08-spec/archive/1to10/157-frontend-tidy)、[184](../../08-spec/archive/1to10/184-frontend-tests)、[193](../../08-spec/archive/1to10/193-store-a11y)、[192](../../08-spec/archive/1to10/192-unused-code) |

## 1. 技術

| 用途 | 採用 | 補足 |
|------|------|------|
| フレームワーク | Next.js（App Router） | 画面はサーバーコンポーネント、操作のある部分だけクライアントコンポーネント |
| API | openapi-fetch | 取得はサーバーコンポーネント、変更はサーバーアクションから呼ぶ |
| キャッシュ | Next.js の fetch のキャッシュ | 最大 60 秒。会員の token を付けて呼ぶ API はキャッシュしない |
| ログイン | Keycloak provider（Auth.js、`next-auth` v5） | セッションは暗号化した Cookie（JWT 方式）。token はサーバーだけで扱う |
| 文言 | next-intl | サーバーの設定は `src/i18n/request.ts` |
| UI・lint | shadcn/ui、Tailwind CSS、lucide-react、Biome | 管理画面と同じ |
| テスト | Vitest | 関数、表示のコンポーネント、サーバーの処理 |

## 2. ディレクトリ

```
frontend/store/
├── messages/ja.json          # 文言
└── src/
    ├── instrumentation.ts    # 起動時に、本番で必須の環境変数を確認する
    ├── proxy.ts              # 要求ごとにセッションを確認し、token を更新して Cookie に書く。今の画面のパスを知らせる
    ├── app/                  # ルート（取得とコンポーネントの組み立てだけ）。ページのテストは `page.test.tsx`（「テスト」）
    │   ├── api/auth/         # Auth.js のエンドポイント（IdP からの戻り先など）
    │   └── login/            # ログイン・会員登録（IdP）へ移る口
    ├── actions/              # サーバーアクション。資源ごとに 1 ファイル（cart、checkout、order、auth、region）と、ラッパー（withActionResult）と会員の操作のヘルパー（memberAction）
    ├── auth/                 # ログイン（設定とセッション、環境変数、Cookie の名前と接頭辞、token の更新、ログアウト）。「ログイン」
    ├── api/
    │   ├── generated/        # store.yaml から生成（型と、入力の制約の定数）
    │   ├── client.ts         # クライアント。公開用と会員用（サーバー専用）
    │   ├── result.ts         # 応答を結果に変える（ApiError、404 の扱い）
    │   ├── cartCookie.ts     # カート ID と、カートを移した知らせの Cookie（サーバー専用）
    │   ├── cart.ts           # 使うカートを選ぶ（サーバー専用）
    │   └── types.ts          # 画面から使う型の別名
    ├── components/           # 機能をまたぐコンポーネント（価格、ページング、ヘッダー、失敗の表示 ActionError など）。ui/ は shadcn/ui
    ├── i18n/                 # next-intl の設定、共有の文言との結合、キーの型、コンポーネントの外で使う translate
    ├── lib/                  # 画面に依存しない関数（単体テストを横に置く）
    │   ├── labels.ts         # 2 つ以上の機能で使う列挙の表示名（1 つの機能だけなら features/<機能>/labels.ts）
    │   ├── searchParams.ts   # URL のクエリの読み取り（配列の最初、ページ番号、型）
    │   ├── format.ts         # 価格をコンポーネントで分けて出す書式（金額・日時などの整形は共有パッケージの lib/format.ts）
    │   ├── actionResult.ts   # サーバーアクションの結果の型と、API のエラーからの変換
    │   ├── cartChoice.ts     # 使うカートの種類（会員か Cookie か）と選び方（「使うカートの選び方」）
    │   ├── cartId.ts         # カート ID の Cookie の属性と、カートが見つからなかったことを示す値
    │   ├── cartMergeNotice.ts # カートを移した知らせの内容（品目の数の上限を持つ）
    │   ├── login.ts          # ログイン後の戻り先を、店舗画面の中のパスに限る（「ログイン」）
    │   ├── postalCode.ts     # 郵便番号の形の判定
    │   ├── quantity.ts       # 数量の選択肢（契約の下限から上限まで）
    │   └── server/           # サーバー専用の関数。formData（フォームの項目の読み取り）、log（JSON のログ）、timeout（待つ時間の上限）、trace（追跡 ID）
    ├── test/                 # テストの土台（Next.js と Auth.js の置き換え、API の応答のデータ、MSW、描画。画面のコードからは import しない）
    └── features/<機能>/      # catalog、cart、checkout、order
        ├── components/       # その機能だけのコンポーネント
        └── *.ts              # その機能だけの関数・型（クエリの組み立て、注文の状態の判定など）
```

- 画面のコンポーネントは `features/` に置き、`page.tsx` は薄く保つ（`app/` の置き場所は Next.js が決めるため）。
- クライアントコンポーネント（`'use client'`）は、操作のあるコンポーネント（バリアントの選択、絞り込み、フォームなど）だけにし、API ではなくサーバーアクションを呼ぶ。
- サーバーアクションは複数の機能から呼ぶので、`features/` ではなく `actions/` に置く。

## 3. 画面の URL

Next.js の `typedRoutes` で、画面の置き場所と照合する。クエリ付きの URL は機能の `*Query.ts` の関数で作る。

| URL | 画面 | ログイン |
|-----|------|----------|
| `/` | トップ（カテゴリの一覧と新着の商品） | — |
| `/products` | 商品一覧（クエリ：`categoryId`、`minPrice`、`maxPrice`、`sort`、`page`） | — |
| `/search` | 検索結果（クエリ：`q`、`page`） | — |
| `/products/[productId]` | 商品の詳細（カートに入れる） | — |
| `/cart` | カート（カート ID は Cookie に保持し、URL に入れない） | — |
| `/checkout/[checkoutId]` | 注文手続き（確認と、お届け先の入力。メールアドレスは会員のものを示すだけ）。成立済みなら注文へ遷移する | 必要 |
| `/orders` | 注文一覧（新しい順、クエリ：`page`） | 必要 |
| `/orders/[orderId]` | 注文（照会、支払、キャンセルの申請）。注文した会員だけ。支払画面から戻る先（クエリ：`payment=returned`） | 必要 |
| `/login` | 画面ではなく、IdP へリダイレクトするエンドポイント（クエリ：`returnTo` 戻る画面、`register` 会員登録） | — |

- URL は商品 ID で作り、品番は使わない。
- 絞り込み・並び順・ページは URL のクエリに保持し、フォームの GET で送る。
- 表示されない・存在しない・ID の形が違う商品、存在しない・他人の注文手続きと注文は、どれも「見つかりません」（404）※1。

※1：Next.js 16 では、要求ごとに描画する画面で 404 にすると、サーバーはステータスコード 404 と枠だけを返し、中身はブラウザーの JavaScript が表示する。

## 4. API の呼び出し

- サーバーコンポーネントで `const api = await getApi()` としてから `api.GET('<パス>', ...)` で呼ぶ。クライアントは `server-only` にし、ブラウザーのバンドルに入れない。
- `getApi` は画面を要求ごとに描画するようにする（ビルド時に API を呼ばない）。
- 接続先は `STORE_API_BASE_URL`（既定 `http://localhost:8080/api/store`。既定は開発モードとテストだけ）。

### 4.1 キャッシュ

| 取得 | キャッシュ |
|------|------------|
| 一覧・検索・カテゴリ | 最大 60 秒（`STORE_API_REVALIDATE_SECONDS` で変えられる。E2E で短くするため） |
| 商品の詳細 | 使わない（`UNCACHED`）※2 |
| カート・注文手続き・注文 | 使わない（操作のたびに変わるため） |
| 会員の token を付ける API | 使わない（`cache: 'no-store'`。会員ごとの結果を共有のキャッシュに載せないため） |

※2：Next.js のキャッシュは、再取得した応答が 404 のとき古い 200 を置き換えず、非公開にした商品が表示され続けるため。

### 4.2 エラー

| 応答 | 扱い |
|------|------|
| 404 | `notFound()`。ただしカートの 404（Cookie のカートがもうない）は空のカートとして表示する |
| 401 | ログイン画面へリダイレクトする（「ログイン」） |
| それ以外 | エラーの画面（`error.tsx`） |

- タイムアウト：店舗 API のクライアント（公開用と会員用）は、要求のミドルウェアでタイムアウトの signal を付ける（`STORE_API_TIMEOUT_SECONDS`、既定 30 秒）。タイムアウトを過ぎた要求は例外で失敗し、サーバーアクションでは接続できないときと同じ結果になる。既定は、バックエンドで最も長く待つ操作（支払画面を開く）より長くする（短いと、バックエンドが成功しても画面は失敗を表示する）。
- 追跡 ID：店舗 API のクライアント（公開用と会員用）は、要求のミドルウェアで、画面の要求の `traceparent` を付ける。バックエンドのログを画面の要求から辿れるようにするため。Next.js はキャッシュの鍵から `traceparent` を除くので、キャッシュする要求に付けてもキャッシュは使われる。
- サーバーアクションの失敗のログ：サーバーアクションが例外で失敗したら、共通の処理（`withActionResult`）が error のログに例外の名前と、原因の例外（`cause`）の名前とコード（`ECONNREFUSED` など）を出力する。API の失敗の例外（`ApiError`）なら、その状態コードを `status` に出力し、状態コードを持たない例外では null にする。例外のメッセージ（原因のものも含む）は出力しない。メッセージにカートの ID などの識別子が入りうるため。
- 5xx のログ：店舗 API が 5xx を返したら、応答のミドルウェアで warn のログにステータスコード、エラーコード、メソッド、API の定義のパス（`/orders/{orderId}` の形）を出力する。token、Cookie、要求の本文、クエリ（メールアドレスなどを含みうる）は出力しない。エラーコードは、呼んだ側が本文を読めるよう、応答を複製して読む。

### 4.3 サーバーアクション

- 変更（カートに入れる、数量の変更・削除、注文手続きに進む、注文、支払う、キャンセルの申請）は、`actions/` のサーバーアクションから呼ぶ。
- 成功したら、再表示する画面を `revalidatePath` で知らせるか、次の画面へ `redirect` する。失敗は例外にせず `ActionResult` で返す（401 はログイン画面へリダイレクトする）。
- 会員の API の 401 と成功の後の移動は、`actions/memberAction.ts` のヘルパーで書く。
  - `redirectIfUnauthenticated(response, returnTo?)`：応答が 401 ならログイン画面へリダイレクトする。戻り先を渡さなければ、いまの画面に戻る。
  - `redirectOnSuccess(work)`：処理を `withActionResult` でラップし、処理が返した移動先へ遷移する。失敗の結果はそのまま返す（`redirect` をラッパーの外で呼ぶ形を 1 か所にする）。
- `withActionResult` が例外を結果にするときは、画面の移動・not found を通した後、「エラー」のサーバーアクションの失敗のログを出力する。
- フォームは `useActionState` で結果を受け、送信中はボタンを押せなくする（二重送信の防止。API も、同じ注文手続きの再送には作成済みの注文を返す）。

### 4.4 カート ID の Cookie

- カート ID は Cookie `cart_id`（`HttpOnly`、`SameSite=Lax`、`Path=/`、本番は `Secure`）。有効期限 30 日で、変更のたびに延ばす。
- 環境変数 `STORE_COOKIE_PREFIX` があれば、Cookie の名前の先頭に付く（`cart_merge_notice` も同じ。既定は空で、名前は変わらない。[環境変数](../../06-手順書/environment.md)）。
- 読み書きは `api/cartCookie.ts` だけ。読むのはサーバーコンポーネントとサーバーアクション、書くのはサーバーアクションだけ（サーバーコンポーネントは Cookie を書けないため）。
- Cookie がない・形が違うなら、カートがないものとする。「カートに入れる」のときにカートを作って Cookie に書く。
- 変更の API が 404（カートがもうない）なら、カートを再作成して 1 回だけ再試行する。

### 4.5 使うカートの選び方

| 状態 | 使うカート |
|------|------------|
| ログインしていない | Cookie のカート ID |
| ログインしている | `GET /me/cart` の ID（Cookie のカート ID は使わない） |

選ぶ処理は `api/cart.ts` だけに置き、判定は `lib/` の関数にして単体テストを書く。

- **ログインの直後にカートを移す**：IdP から戻ったとき（Auth.js の `signIn` のイベント）に、Cookie にカート ID があれば、その内容を取得してから `POST /me/cart/merge` を呼び、Cookie のカート ID を削除する（移せなくても削除する ※3）。
- 切り詰めた品目と移せなかった品目があれば、商品名・バリアント・数量を知らせの Cookie（`cart_merge_notice`）に書く。カートの画面が一度だけ知らせ、表示したら削除する（知らせのコンポーネントから、削除するためのサーバーアクションを呼ぶ）。Cookie の大きさを抑えるため、品目はそれぞれ 10 まで、残りは数だけ。
- ログアウトでは Cookie のカート ID も削除する。

※3：ログインしている間は使わないので、残すとログアウトの後に古いカートが見えてしまうため。

### 4.6 会員の token を付けて呼ぶ

| 呼ぶもの | クライアント |
|----------|----|
| 会員の操作（`/me/**`、会員のカート、注文手続き、注文） | `getMemberApi()`。セッションの access token を `Authorization` に付け、キャッシュしない |
| 公開の情報（商品・カテゴリ・店舗の情報） | `getApi()`。ログインしていても token なしで、キャッシュを使う |
| ログインしていなくても使える操作（Cookie のカート） | `getApi()`。カートの取得は `UNCACHED` |

### 4.7 支払画面への移動と戻り

| 場面 | 動き |
|------|------|
| 注文の成立 | 支払画面の URL を API で取得し、決済サービスの画面（外部の URL）へ `redirect` する。得られなければ注文の画面へ遷移する |
| 注文の画面の「支払う」 | 同じ API で URL を取得し、リダイレクトする。支払えなければ（支払済み、期限の後）メッセージを示す |
| 支払画面から戻る | 戻る先はバックエンドの設定（`ECSITE_PAYMENT_RETURN_URL`）で、注文の画面に `payment=returned` を付ける。まだ支払待ちなら「確認中」と示す ※4 |

※4：与信の結果は、決済サービスからバックエンドへの通知だけで届くので、戻った時点ではまだ届いていないことがある。画面は決済サービスに問い合わせない。

### 4.8 お届け先の都道府県と市区町村

都道府県と市区町村は、地域のマスターデータ（店舗 API の `region` の操作）から選ぶ。画面に都道府県の表を持たない。

| 場面 | 動き |
|------|------|
| 欄の並び | 郵便番号、都道府県（選ぶ）、市区町村（選ぶ）、市区町村より下の住所 |
| 都道府県の一覧 | 注文手続きのページを作るときに `getApi()` で取得する（公開の情報なのでキャッシュを使う） |
| 市区町村の一覧 | 都道府県を選んだときに、サーバーアクション（`actions/region.ts`）で取得する。別の都道府県を選ぶと、市区町村の選択を外す |
| 郵便番号で補う | 郵便番号がハイフンを除いて 7 桁になったら、サーバーアクションで検索する。補い方は下の表 |
| 補った後 | どの欄も変えられる。補った値を消費者が修正しても、再度は補わない（郵便番号を変えたときだけ再度検索する） |

| 郵便番号を検索した結果 | 補うもの |
|----------------------|----------|
| 1 件 | 都道府県と市区町村を選ぶ。住所の欄が空なら、町域を入れる（町域が空なら入れない） |
| 複数で、都道府県と市区町村が全て同じ | 都道府県と市区町村を選ぶ。町域は入れない（どれか分からないため） |
| 複数で、都道府県か市区町村が違う | 何も補わない（1 つの郵便番号が 2 つの市区町村にまたがるとき。誤りを補わないよう、消費者に選ばせる） |
| ない、通信の失敗 | 何も補わず、メッセージも表示しない（消費者は一覧から選べる） |

- 一覧を取得するサーバーアクションは、変更でなく読むだけなので `ActionResult` を返さず、失敗は空（市区町村の一覧は `null`）で返す。
- 補い方は `features/checkout/` の関数にし、単体テストを書く。古い応答（検索している間に都道府県や郵便番号を変えた）は破棄する。

## 5. 表示の決まり

| 対象 | 決まり |
|------|--------|
| 価格 | C 側の商品は必ず税込価格を持つ |
| 在庫 | 「在庫あり」「在庫なし」だけ（数量は表示しない）。一覧では在庫のない商品に「在庫なし」 |
| 画像 | API の URL をそのまま使う（縮小・変換は配信の側）。一覧は代表画像、詳細は大きな画像と小さな画像の並び。バリアントを選ぶとその画像（なければ代表画像）に替える。画像がなければ代替のアイコン |
| 金額の内訳 | 商品の合計、送料、総額、税率ごとの消費税額（「10% 対象 11,000 円（内消費税 1,000 円）」）。カート・注文手続き・注文で同じコンポーネントを使う |
| 購入できない品目 | 「購入できません」と理由（表示されなくなった、販売停止、在庫切れ、在庫が足りない） |
| 注文の状態 | 「支払待ち」「受付」「キャンセル申請中」「キャンセル」。出荷済みの注文は、注文の状態の代わりに配送状態（「出荷済み」「配送中」「配達完了」「返送」）を表示し、注文詳細に配送業者と送り状番号を添える。申請のフォームは `actions.requestCancellation` で表示する |
| 日時 | 「2026/10/10 14:05」 |
| バリアントの選択 | 軸ごとに値を並べ、在庫切れ・販売停止のバリアントにしかならない値はグレーで表示し、選択できないようにする |

## 6. 結果の知らせ方

- 取得の失敗はエラーの画面に表示する。クエリの誤り（形が違うなど）は API の `message` をその画面に表示する。価格帯の下限が上限より大きいときは例外で、API は空の一覧を返す。
- 成功は、次の画面への移動か表示の変化で示す。「カートに入れる」は、ボタンの近くに「カートに入れました」とカートへのリンクを表示する。

| 操作の失敗 | 出し方 |
|------------|--------|
| 入力の誤り（400） | 入力欄に対応するものはその欄の下、それ以外はフォームの下に `message`。入力は削除しない ※5 |
| 業務のエラー（400、409） | フォームの下に `message`。次にすべきことが別の画面にあるもの（在庫不足、カートの変更）はそこへのリンクを添える。総額が変わったら新しい金額で再表示する |
| 通信の失敗 | 「サーバーに接続できませんでした。」 |

エラーメッセージは、共通のコンポーネント `components/ActionError.tsx` で表示する。

- コンポーネントは、メッセージがなくても `status` の役割を持つ読み上げの領域を常に描き、失敗したときに文だけを入れる。理由：後から描かれた領域は読み上げられない支援技術があるため。
- 文のない領域は、画面から隠して（`sr-only`）並びから外す。`space-y-*` の親の最後の子に置くと前の要素に余白が付くので、そのときは親を `flex flex-col gap-*` にする。
- 親が常にある読み上げの領域を持ち、その中で表示するとき（カートに入れる）は `inLiveRegion` を付け、コンポーネントに領域を付けさせない（領域を入れ子にしない）。
- バリアントの在庫状況の領域（`VariantPicker`）も `status` の役割を持つ。選択を変えたときに、領域の中の文（在庫のバッジか案内の文）が変わる。

注文のフォームの欄は、補足の文と誤りの文を、この順で入力欄の説明（`aria-describedby`）として結び付ける。誤りのある欄には `aria-invalid` を付ける。入力欄と選択欄の UI のコンポーネント（shadcn/ui）が持つ誤りの見た目（赤い枠）になる。

注文のフォームの送信が欄の誤りで失敗したときは、無効でない誤りの欄のうち画面の順（氏名、郵便番号、都道府県、市区町村、住所、電話番号）で最初の欄へフォーカスを移す。移った欄の誤りの文は、`aria-describedby` で入力欄に結び付けてあるため、入力欄の説明として読み上げられる。無効の欄（一覧を取得できていない市区町村）は飛ばす。誤りのある欄が全て無効のときと、欄の誤りがない失敗（在庫不足、通信の失敗など）では、フォーカスを移さない。フォーカスを移すのは、送信の結果を受けたときだけである。結果を受けた後の入力では、移し直さない。

※5：欄の下には、API の応答の項目ごとの文（`errors[].message`）をそのまま表示し、画面で文を作らない（`features/checkout/placeOrderErrors.ts`）。契約の形の検証で見つかった誤りも、API が業務の検証エラーと同じ文を返す（[バックエンドの書き方](../../05-開発規則/backend-coding.md)の「入力の検証のメッセージ」）。

キャンセルの申請が却下された注文には、問い合わせ先（`GET /shop` の店舗の情報。値はバックエンドの設定）を示す。

店舗画面の環境変数には、画面の処理の設定（接続先、キャッシュの秒数など）だけを置く。

## 8. 画面を追加する手順

1. 使う API が `store.yaml` にあるかを確認する。なければ、先に plan と `store.yaml` を修正する。
2. `app/` にルートを作り、コンポーネントは `features/<機能>/components/` に置く。操作のある部分だけクライアントコンポーネントにする。
3. データはサーバーコンポーネントで取得する（「API の呼び出し」）。ログインを求める画面は、取得の前にログインを確認する（「ログイン」）。
4. 新しい表示の決まりは `lib/` か `features/` の関数にし、単体テストを書く。
5. lint、型チェック、テスト、ビルドを通し、開発サーバーで表示を確認する。

## 9. ログイン

店舗画面のサーバーが IdP とやり取りし（BFF）、token はサーバーだけで扱う。

| 項目 | 決まり |
|------|--------|
| 設定 | `auth/` に Auth.js の設定を集め、外からは `@/auth` だけを import する（ライブラリを替えるときの範囲を狭くするため）。provider は Keycloak（`ec-store` realm の `ec-store-web`、confidential client）、認可コード + PKCE |
| 環境変数 | `AUTH_KEYCLOAK_ISSUER`（既定 `http://localhost:8180/realms/ec-store`）、`AUTH_KEYCLOAK_ID`（既定 `ec-store-web`）、`AUTH_KEYCLOAK_SECRET`、`AUTH_SECRET`（Cookie の暗号化の鍵）、`AUTH_URL`（店舗画面を公開する URL。既定 `http://localhost:3000`）※7 |
| 戻り先 | ログイン（IdP からの戻り先）とログアウト（IdP のログアウトの後の戻り先）の URL は `AUTH_URL` から作り、リクエストヘッダーのホストとプロトコル（`host`、`x-forwarded-*`）を使わない（ヘッダーは偽装できるため）※8 |
| セッション | 暗号化した HttpOnly の Cookie に、access・refresh・ID token、期限、氏名・メールアドレスを保持する（サーバーに状態を保持しない） |
| 画面から読める情報 | `auth()` の結果（ブラウザーからも読める）には氏名とメールアドレスだけ。token は `getAccessToken()` で Cookie から直接読む（サーバー専用） |
| 氏名 | token の姓（`family_name`）と名（`given_name`）を「姓 名」で並べる |
| ログインの状態 | サーバー側で `currentMember()`（ログインしていれば氏名とメールアドレス、していなければ `null`）。クライアントコンポーネントでは取らず、必要なら props で渡す |
| アカウント | ヘッダーから IdP のアカウント画面（`<issuer>/account`）へ遷移する。変えた氏名は次のログインから反映する |

※7：既定値はローカルと CI だけで使う値（realm の JSON と同じ）で、開発モードとテストでだけ使う。本番モードでは、この 5 つと `STORE_API_BASE_URL` がなければ起動時に失敗する（`src/auth/config.ts`）。E2E は `playwright.config.ts` で渡す。

※8：Auth.js は `AUTH_URL` があれば、リクエストの URL をそれに置き換える。`trustHost` は指定しない。ログインの戻り先のテストは、このファイルだけ実際の Auth.js を使う（`auth/loginRedirect.test.ts`）。

### 9.1 token の更新

access token の有効期限（5 分）の残りが 1 分未満なら、refresh token で再取得する。

- `proxy.ts` が要求ごとにセッションを確認し、再取得した token を Cookie に書く（サーバーコンポーネントは Cookie を書けないため）。
- 同じ要求の中では画面は古い Cookie を読むので、`getAccessToken()` は期限切れなら自分でも再取得して使う（Cookie には次の要求で `proxy.ts` が書く）。
- 再取得できなければ（IdP のログインが切れた）、ログインしていないものとして扱う。
- IdP に到達できない・タイムアウト（`AUTH_KEYCLOAK_TIMEOUT_SECONDS`、既定 10 秒）を過ぎたときは、ログインの状態を残す（期限が切れていれば、API が 401 を返してログイン画面へリダイレクトする）。
- ログインの IdP への呼び出し（discovery、token の交換、userinfo）にも、Auth.js の provider の fetch を差し替える仕組み（`customFetch`）で同じタイムアウトを付ける。

### 9.2 ログイン画面へ移す

- `/login?returnTo=<戻る画面>` から IdP へリダイレクトし、ログイン後は `returnTo` に戻る。`returnTo` は画面の中のパス（`/` で始まり、`//` と `/\` で始まらず、制御文字（U+0000〜U+001F と U+007F）を含まない）だけを受け付け、それ以外は `/`。判定には、管理画面と同じ共有パッケージの関数を使う（管理画面の構成の「API に付ける token」）。
- 会員登録は `/login?register=1&returnTo=...`（OIDC の `prompt=create`）。
- 画面とサーバーアクションは `redirectToLogin()` で今の画面に戻るようにリダイレクトする。今のパスは `proxy.ts` が要求のヘッダー（`x-pathname`）で渡す（サーバーコンポーネントは URL を直接知らないため）。
- ログインを求める画面（注文手続き、注文一覧、注文）は、取得の前に `currentMember()` を確認し、`null` なら `redirectToLogin()`。API が 401 を返したときも同じ。注文手続きに進む操作も、ログインしていなければカートに戻るようにログイン画面へリダイレクトする。

### 9.3 ログアウト

サーバーアクション（`actions/auth.ts`）で、セッションの Cookie と Cookie のカート ID を削除し、IdP のログアウト（RP-Initiated Logout。ID token と店舗のトップを添える）へリダイレクトする。IdP のログインも終わるので、パスワードなしでは再ログインできない。
