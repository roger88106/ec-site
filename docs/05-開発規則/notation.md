# 文書の記号と番号

spec・plan・tasks・モジュールの設計書で使う番号と記号の意味。業務の用語と識別子（クラス名、テーブル名など）は[用語集](../03-機能仕様/glossary.md)で引く。

## spec の種類

| 種類 | 内容 | 例 |
|------|------|----|
| 機能 | 消費者・運営者に見える振る舞いを作る・変える。単独で検証できる機能の縦切り（バーティカルスライス）1 つ | 001、007、010 |
| 整理 | 消費者・運営者に見える振る舞いを変えずに、規則・テスト・構成・コードを整える | 004、008、011 |

## spec の番号

新しい spec の番号は、その spec を追跡する issue の番号である。種類によらず 1 つの並びで、issue と pull request が番号を共有する。tasks のタスク番号と commit のメッセージから、spec の種類によらず、spec を特定できるようにするため。

| 対象 | 書き方 | 例（spec 123） |
|------|--------|----------------|
| spec のディレクトリ | `<番号>-<短い名前>`。0 で埋めない | `123-<短い名前>` |
| 作業ブランチ | spec の番号と同じ番号を使う | 番号は `123` |
| タスク | `T<番号>-<段階>-<連番>` | `T123-01-01` |
| spec の中の番号 | spec の番号を付けた形（「spec の中の番号」の表） | `AC-123-1` |

- 番号の飛びを許す。理由：pull request と番号を共有するため。
- MVP の spec（001〜019）の番号は 3 桁の 0 埋めのまま、変えない。新しい文書で MVP の spec を指すときは「MVP 012」と書く。
- 検査の script は、0 で始まる 3 桁の番号を MVP、0 で始めない番号を 1→10 の spec として区別する。理由：spec 7〜19 が MVP の 007〜019 と同じ数になるため。

## spec の中の番号

番号は一度振ったら変えない。追加は末尾の番号を使う。

MVP の spec（001〜019）は、下の表の `n` だけの形で、spec をまたいで続けて振る。1→10 の spec は、各番号に spec の番号を付け、`<記号>-<spec の番号>-<連番>` の形で、その spec の中で 1 から振る（例：`AC-123-1`、`DC-7-14`）。

| 番号 | 意味 | 使う spec | 振り方 |
|------|------|-----------|--------|
| `US-n` | User story（誰が何をできるか） | 機能 | 機能の spec をまたいで続けて振る |
| `AC-n` | 受け入れ条件。「できた / できていない」が判断できる文。テスト名（`@DisplayName` など）に入れる | 機能 | 同上 |
| `BR-n` | 業務ルール。複数の AC にまたがる規則 | 機能 | 同上 |
| `NFR-n` | 非機能要件 | 機能 | 同上 |
| `DS-n` | 整理の目的（開発者・エージェントが何をできるようになるか） | 整理 | 整理の spec をまたいで続けて振る |
| `DC-n` | 整理の完了の条件。「できた / できていない」が判断できる文。確認方法（CI・テスト・検査の script・レビューで読む）を plan で決める。テスト名には入れなくてよい | 整理 | 同上 |
| `DN-n` | 整理の spec の非機能要件（守る制約） | 整理 | 同上 |

整理の spec の番号に `AC-`・`US-`・`NFR-` の文字列を含めないのは、コードやテストの中の `AC-119` などを検索したときに、整理の spec の番号が混ざらないようにするため。

## spec の中の記号

| 記号 | 意味 |
|------|------|
| 対象 `C` | 消費者（店舗画面・店舗 API） |
| 対象 `B` | 運営者（管理画面・管理 API） |
| 対象 `D` | 開発者とエージェント（整理の spec） |
| 優先度 `P1` | その spec で必須 |
| 優先度 `P2` | 余裕があれば入れる。入れない場合は Non-goals か後の spec に移す |

## 文書のステータス

| 文書 | ステータス | 意味 |
|------|------------|------|
| spec | 草案 | 議論中。Open questions が残っていてよい |
| spec | 確定 | Open questions が空で、利用者が確定した。plan を書き始められる |
| plan | 承認済み（tasks 作成済み） | 利用者が plan と tasks を一緒に承認した（規模 L） |

spec の進み具合（どの段階まで完了したか）は、MVP の spec は README の進捗の表、1→10 の spec は追跡の issue と milestone に書く。

## tasks の番号と記号

| 番号・記号 | 意味 |
|------------|------|
| 段階 | tasks の 1 ファイル（`tasks/NN-<名前>.md`）。冒頭に前提・完了条件・参照を書く |
| `T123-01-01` | タスク（1→10 の spec）。`T` ＋ spec の番号 ＋ `-` ＋ 段階 ＋ `-` ＋ 連番（例：`T7-01-01` は spec 7 の段階 1 の 1 つ目）。spec の番号は 0 で埋めず、spec のディレクトリの番号のまま書く。段階と連番は 2 桁。commit のメッセージの末尾に `（T7-01-01）` の形で書く |
| `T011-01-01` | タスク（MVP の spec）。`T` ＋ spec の番号 ＋ `-` ＋ 段階 ＋ `-` ＋ 連番（例：`T011-01-01` は spec 011 の段階 1 の 1 つ目）。spec の番号は spec のディレクトリの番号のまま書き、桁を固定しない（1000 を超えても `T1000-01-01`）。段階と連番は 2 桁。commit のメッセージの末尾に `（T011-01-01）` の形で書く |
| 途中で追加するタスク | 段階のファイルの末尾に、その段階の続きの番号で追加する。番号を振り直さない |
| 古い形式 | MVP の spec 001〜010 の記録は古い形式のまま残す。spec 001 は `T` ＋ 段階 ＋ 連番（例：`T301`）、spec 002〜010 は `T` ＋ spec の番号の下 1 桁 ＋ 段階 ＋ 連番（例：`T3101` は spec 003 の段階 1 の 1 つ目） |
| `[P]` | 並行。同じ段階の他の `[P]` のタスクと同時に実装できる。`[P]` のタスクは、作業ツリーを分けた実装役が同時に実装する |
| `[リスク]` | 次のどれかを扱うタスクに付ける。金額、セキュリティ、データの移行、トランザクション・並行処理・冪等性、外部サービス（決済、物流）との接続 |
| `[テスト]` | テストを書くタスク。対応する実装のタスクより先に行い、失敗することを確認してから実装に進む。`[テスト]` と対応する実装は 1 組で、同じ実装役が順に実装する |
| `[E2E]` | E2E を書くタスク。画面と API の実装の後に行い、通ることを確認する（失敗の確認は求めない） |
| `- [x]` / `- [ ]` | 完了 / 未完了 |

### tasks のタスクの書き方

各タスクに、並行の記号 `[P]`（同時に実装できるとき）、依存、変える範囲（ファイルかモジュール）を書く。依存と範囲は、タスクの行の下に字下げして書く。例：

```markdown
- [ ] **T7-02-01** [P] [テスト] spec のディレクトリと番号：…を書き、レッドを確認する（DC-7-14〜19）。
  - 依存：なし
  - 範囲：`scripts/ci/lib/spec-dirs.test.mjs`
- [ ] **T7-02-02** T7-02-01 のテストが通る実装を書く。
  - 依存：T7-02-01
  - 範囲：`scripts/ci/lib/spec-dirs.mjs`
```

レビューの段階のタスクの結果は、レビューごとに 1 行の表で書く。列の形は skill `review` の手順 6 にある。

## モジュールの設計書の記号

| 記号 | 意味 |
|------|------|
| アーキテクチャのレベル `A` | フル：domain / application / infrastructure / presentation（[バックエンドのアーキテクチャ](../02-設計/backend-architecture.md) 第 2 節） |
| アーキテクチャのレベル `B` | 簡略：3 層（[バックエンドのアーキテクチャ](../02-設計/backend-architecture.md) 第 2 節） |
| アーキテクチャのレベル `C` | イベントストア（[バックエンドのアーキテクチャ](../02-設計/backend-architecture.md) 第 2 節） |

モジュールごとのレベルと選んだ理由は、`docs/03-機能仕様/<module>.md` の冒頭に書く。
