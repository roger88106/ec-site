# Spec 131：CI を整える（バックエンドのジョブの分割と、負荷に弱いテスト）

ステータス：草案

## 1. 背景と目的

CI（`ci.yml`）の全体の時間は、バックエンドのジョブで決まる。バックエンドのテストを全て流す実行では、バックエンドのジョブが 8 分 29 秒〜9 分 55 秒かかり（2026-10-21〜22 の `develop` の 6 回）、10 分の目安（MVP 011 の DC-85）までの余裕が少ない。他のジョブは、E2E が約 5 分 30 秒、管理画面と店舗画面が約 1 分 30 秒である。

バックエンドのジョブの内訳（2026-10-22 の実行 39752002840。Gradle の出力の時刻から読んだ概算）は次のとおり。統合テストが全体の約 3 分の 2 を占めるので、単体テストと統合テストを別のジョブに分けるだけでは、約 40 秒しか短くならない。統合テストを複数のジョブに分けて同時に流す必要がある。

| 部分 | 時間 |
|------|------|
| 準備（checkout、Java、Gradle） | 約 10 秒 |
| ライセンスの検査、jOOQ のコードの生成、OpenAPI、コンパイル、Checkstyle | 約 2 分 20 秒 |
| 単体テスト | 約 40 秒 |
| 統合テストのコンパイル | 約 30 秒 |
| 統合テスト | 約 6 分 |
| カバレッジの報告 | 約 5 秒 |

- バックエンドのコードが変わらない実行では、Gradle のビルドのキャッシュでテストを飛ばし、バックエンドのジョブは約 35 秒で終わる。本 spec の時間の条件は、テストを全て流す実行で測る。
- 外部サービスの失敗のテスト（画像の変換、オブジェクトストレージ）は、正常の応答を確認するテストでも、待つ時間の上限を 0.3 秒にしている。開発サーバーなどと同時に `./gradlew check` を流すと、正常の応答でも上限を超えて失敗した（MVP 019 の試行）。並行の開発（spec 104）でテストが同時に流れる機会が増えるので、先に直す。
- メディアの内部イベント `AssetReleased` は `domain/` にあるが、メディアはレベル B のモジュールなので、[バックエンドの書き方](../../rules/backend-coding.md) の規則（モジュールの中だけのイベントは、レベル B は application に置く）に反する（MVP 019 の全体のレビュー）。

追跡の issue は [#131](https://github.com/roger88106/ec-site/issues/131)、扱う issue は [#14](https://github.com/roger88106/ec-site/issues/14) と [#75](https://github.com/roger88106/ec-site/issues/75)、作業ブランチは `131-ci-tidy` である。本 spec は整理の spec で、規模は M である（[開発の進め方](../../rules/workflow.md) 第 4.2 節。API の契約とデータベースを変えず、AC を変えない）。

## 2. スコープ

| # | 目的 | 対象 | 優先度 |
|---|------|------|--------|
| DS-131-1 | バックエンドのテストを全て流す実行でも、CI の全体が 10 分の目安を余裕をもって下回る | D | P1 |
| DS-131-2 | 外部サービスの失敗のテストが、負荷のある環境でも正常の応答で失敗しない | D | P1 |
| DS-131-3 | メディアの内部イベントの置き場所が、バックエンドの書き方の規則に合う | D | P1 |

## 3. 目的と完了条件

### DS-131-1 CI の全体を 10 分の目安より短くする（D / P1）

ジョブの構成（決めること 1）：

| ジョブ | 実行するもの |
|--------|--------------|
| バックエンド（ビルドと単体テスト） | 依存のライセンスの検査、ビルド、Checkstyle、OpenAPI の構文の検証、単体テスト。統合テストは流さない |
| バックエンド（統合テスト n/2） | 統合テストを 2 つに分けた片方。2 つのジョブを同時に流す |
| バックエンド | 上の 3 つのジョブの後に、カバレッジの実行データを合わせて報告を作り、summary に書く。上のジョブが 1 つでも成功しなければ失敗する |

- **DC-131-1** バックエンドのテストを全て流す実行で、`ci.yml` の全体の時間（最初のジョブの開始から最後のジョブの終了まで）が 8 分以下である。作業ブランチの 3 回の実行で測り、時間をタスクの結果に書く。
- **DC-131-2** 統合テストの全てのテストクラスが、分けたジョブのどれか 1 つだけで流れる。テストクラスを追加しても、分け方の設定を変えなくてよい。
- **DC-131-3** 統合テストの 2 つのジョブの時間の差が、1 分 30 秒以下である（DC-131-1 と同じ 3 回で測る）。
- **DC-131-4** ジョブ「バックエンド」は、ビルドと単体テストのジョブ、統合テストのジョブのどれかが失敗・中止・スキップしたとき、失敗になる。作業ブランチで、統合テストをわざと失敗させた push で確認し、戻す。理由：ruleset はジョブの名前で必須の検査を決めていて、スキップは成功と同じに扱われるため。
- **DC-131-5** ruleset（`develop` 25616507、`main` 25616508）の必須の検査の名前を変えない。ジョブ「バックエンド」の名前を残すため（決めること 3）。
- **DC-131-6** 合わせたカバレッジの報告が、分割の前と同じ範囲（単体と統合の合計、生成したコードを除く）を数える。合計の行のカバレッジが、分割の前の `develop` の最後の実行と ±1 ポイント以内で、JaCoCo の実行データとクラスの不一致の警告がない。
- **DC-131-7** 失敗したジョブは、テストレポートを artifact に保存する（今と同じ）。
- **DC-131-8** 手元のコマンドは今と同じに使える。`./gradlew checkLicense build` は単体と統合の全てのテストを流し、`./gradlew coverageReport` は合わせた報告を作る。
- **DC-131-9** 統合テストのフォークの数（`maxParallelForks`）は、Gradle のプロパティで変えられ、手元の既定は 1 である。CI で 2 にするかは、作業ブランチで測って、統合テストのジョブが 10% 以上短くなれば 2 にする（決めること 2）。測った値をタスクの結果に書く。
- **DC-131-10** [CI の検査](../../guides/ci.md) のジョブの表と手元での実行、[テストの実行方法](../../guides/running-tests.md)、`ci.yml` のコメントが、新しい構成と一致する。

### DS-131-2 外部サービスの失敗のテストを、負荷に強くする（D / P1）

- **DC-131-11** 画像の変換（`ImgproxyImageConverterFailureTest`）とオブジェクトストレージ（`S3ObjectStorageFailureTest`）の失敗のテストで、正常に応答するサーバーを使うテスト（4xx・5xx・200・404・403、つながらない）は、待つ時間の上限を 5 秒以上にする。
- **DC-131-12** 時間の上限を確認するテスト（応答しないサーバー）は、短い上限のままで、上限を超えたときに外部サービスのエラーになることを確認し続ける（テストを弱めない）。
- **DC-131-13** テストのサーバーの応答をわざと 1 秒遅らせても、DC-131-11 のテストが全て通る。手で遅らせて確認し、戻す。結果をタスクに書く。

### DS-131-3 メディアの内部イベントの置き場所を直す（D / P1）

- **DC-131-14** `AssetReleased` が、メディアの `application` のパッケージにある。振る舞い（コミットの後に配信のファイルを消す）は変えない。
- **DC-131-15** [メディアの設計書](../../design/modules/media.md) の構成の説明（domain と application の行）が、新しい置き場所と一致する。

## 4. 守る制約

- **DN-131-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。
- **DN-131-2** テストの数と、テストが確認する内容を減らさない。
- **DN-131-3** spec 104 の範囲（`docker/`、`scripts/dev/`、E2E の script、skill `local-dev`）のファイルを変えない。変える必要が出たら、先に利用者に相談する。
- **DN-131-4** バックエンドの全てのテストは、CI で確認する。手元で `./gradlew check` などを流すのは、同時に 1 つのセッションだけ（skill `local-dev`）。

## 5. Non-goals

| 項目 | 理由 |
|------|------|
| E2E のジョブを短くする | 約 5 分 30 秒で、10 分の目安まで余裕がある |
| 管理画面・店舗画面のジョブの変更 | 約 1 分 30 秒で、全体の時間を決めない |
| 手元の環境の並行化 | spec 104 で扱う |

## 6. 決めること（Open questions）

spec の確認で利用者が決める。推奨は、各項目の最初の案。

1. **バックエンドのジョブの分け方**：
   - 案 A（推奨）：第 3 節の表のとおり、ビルドと単体テスト、統合テストを 2 つに分けたジョブ、合わせるジョブ「バックエンド」の 4 つにする。見込み：統合テストのジョブが約 3 分＋準備とコンパイル約 3 分で、約 6 分。全体は E2E（約 5 分 30 秒）とほぼ同じになる。
   - 案 B：issue #14 の原案のとおり、ビルドと単体テスト、統合テストの 2 つのジョブにし、統合テストのフォークを 2 にする。見込み：統合テストのジョブが約 8 分（約 13% 短くなる）。10 分は下回るが、余裕が少ない。
2. **統合テストのフォークの数**：
   - 案 A（推奨）：プロパティで変えられるようにし、CI で測って 10% 以上短くなれば 2 にする。手元の既定は 1（並行の開発で、手元のコンテナの数を増やさないため）。
   - 案 B：手元も CI も 2 にする。
3. **ruleset の必須の検査**：
   - 案 A（推奨）：合わせるジョブに「バックエンド」の名前を残し、ruleset を変えない。GitHub の設定を変えずに済む。
   - 案 B：分けた各ジョブを必須の検査に登録し直す（ruleset の変更に利用者の許可が必要になる）。
