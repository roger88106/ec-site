# フロントの観点

画面のコード（店舗画面、管理画面、共有）と E2E のコードを書く・変えたときに、結果を返す前の自己確認とレビューの両方で読む。規則の文は、表の「規則の正本」で読む。

| 観点 | 級 | 見る問い | 過去の見落としの例 | 規則の正本 |
|------|------|------|------|------|
| 共有の部品の既定の振る舞い | 重要 | 共有の部品の既定の振る舞いは、全ての画面で困らないか。 | バックグラウンドの再取得が 1 回失敗すると、入力中のフォームがエラー表示に替わった。version を複数のカードが別々に持ち、保存が 409 になった | なし（レビューの判断） |
| 共有に置くもの | 重要 | 店舗画面と管理画面に、同じ役割の部品・整形・判定を別々に持っていないか（もう一方の画面で同じ役割を探す）。 | 画面の見出しの部品を管理画面だけに持ち、店舗画面にも同じ役割の部品があった | [フロントの書き方](../../../../docs/05-開発規則/frontend-coding.md)の「共有パッケージ（`frontend/shared/`）」の「入れるもの・入れないもの」 |
| 失敗の経路のテストの分担 | 重要 | 送信、サーバーアクション、再描画の失敗の経路を、どの層のテストが確認するか決まっていて、実際にあるか。 | 失敗の経路をどの層も確認しておらず、カートの数量の選択の不具合が漏れた | [テストの書き方](../../../../docs/05-開発規則/test-writing.md)の「テストの種類」、[フロントのテストの書き方](../../../../docs/05-開発規則/test-writing-frontend.md)の「店舗画面のテストは、対象ごとの方法で書く」 |
| フレームワークの推奨との照合 | 重要 | 公式の推奨（エラーからの回復、読み込み中の表示、キャッシュの既定）と合っているか。更新が失敗した後（競合、見つからない）も、古いデータを取り直すか。 | サーバーコンポーネントのエラーからの回復に、推奨と違う関数を使っていた。公開の API の呼び出しが既定でキャッシュし、呼ぶ側が毎回切る必要があった | なし（レビューの判断） |
| 認証と多層防御 | 重要 | 認証の部品を入口ごとに列挙し、流れをたどったか。同じ資格情報を 1 つの要求で 2 回以上使う経路がないか。ヘッダーと CSP が追加の防御か。 | 1 つの要求の中で token を何度も取り直していた。管理画面にセキュリティヘッダーがなかった | [店舗画面の構成](../../../../docs/02-設計/apps/store.md)の「token の更新」「セキュリティヘッダー」（店舗画面だけ。管理画面はなし） |
| 読み込みの大きさ | 重要 | 画面ごとに JS を分けているか。一覧の画像は表示の大きさに合わせているか。 | 管理画面の JS が 1 つのファイルで、報告の画面だけが使うグラフも最初に読んでいた。一覧の縮小の画像に原寸の画像を使っていた | なし（レビューの判断） |
| 拡張の手間 | 重要 | 1 つの追加に変える所の数は少ないか。変え忘れを型の誤りで気づけるか。 | 絞り込みの条件を 1 つ追加するのに多くのファイルを変え、変え忘れても型の誤りにならない所があった | なし（レビューの判断） |
| 画面の型と生成物の保守 | 次要 | 新しい画面の型（skill の例）が今のコードと合っているか。生成したファイルを手で直し、次の生成で戻る形になっていないか。 | skill の画面の型が、整理で消した部品を参照していた。生成した部品の import を手で直していた | なし（レビューの判断） |
| 見出しと読み上げ | 次要 | 各画面に h1 があるか。画像の alt、ボタンの名前、入力のラベルがあるか。 | 店舗画面のトップにだけ h1 がなかった | なし（レビューの判断） |
