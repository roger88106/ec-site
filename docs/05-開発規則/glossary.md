# 開発の用語集

開発の進め方・ツール・テスト・セッションの役割などの用語と、コード・ファイルでの名前の対応表。
業務の用語は[用語集](../03-機能仕様/glossary.md)にある。

| 用語 | 識別子 | 意味 |
|------|--------|------|
| 機能の spec | | 消費者・運営者に見える振る舞いを作る・変える spec（[開発の進め方](workflow.md)の「仕様駆動開発」） |
| 整理の spec | | 消費者・運営者に見える振る舞いを変えずに、規則・テスト・構成・コードを整える spec。利用者は開発者とエージェント（[開発の進め方](workflow.md)の「仕様駆動開発」） |
| MVP の完成までの一覧 | `docs/08-spec/archive/mvp/mvp.md` | MVP を完成させるまでの spec の順と理由 |
| アーカイブ | | 完了した spec を、MVP などのまとまりごとに移す置き場所（`docs/08-spec/archive/<まとまり>/`）。当時の記録として残し、文書の言い回しの検査から外す |
| AC 一覧 | `docs/03-機能仕様/acceptance-criteria.md` | 全ての AC の状態、モジュール、今の内容の正本。`ac-check` が読む |
| 言い換えの一覧 | `scripts/ci/ja-text.json` | 日本語の文の検査の一覧。error と warning に分けて書く |
| 受け入れ確認 | | レビュー skill でリポジトリ全体をレビューし、完成の条件を満たすかを判断すること。対象は、バックエンド・フロント・E2E・文書・script と CI（skill `review` の「使う場面」） |
| 文書レビュー | | 日本語だけの文脈のサブエージェントが、見本の文書と言い回しの規則を基に、技術文書として不自然な言い回しの候補を挙げるレビュー。利用者が採否を決める（skill `review`） |
| 日本語だけの文脈 | | サブエージェントへの指示と読ませる文書を、日本語だけにすること。利用者との会話の言語が文書に混ざらないようにする（[エージェントの作業フロー](subagents.md)） |
| CI の検査の script | `scripts/ci/*.mjs` | `./gradlew check` と画面の検査のほかに CI が実行する、文書とコードの検査の script。一覧は[CI の検査](../06-手順書/ci.md) |
| 書き方の規則 | `docs/05-開発規則/*-coding.md` など | コードの書き方とプロジェクトの習慣を、規則・理由・確認方法の形でまとめた文書（[書き方の規則とレビュー](review.md)） |
| 引き継ぎの文書 | `/.local/handoff/` | 作業を別のセッションに引き継ぐための文書。Git に入れない（[AGENTS.md](../../AGENTS.md)） |
| カバレッジ | | テストで実行されたコードの割合（行・分岐）。基準の値から許容の幅を引いた値を下回ると CI が失敗する（[テストの書き方](test-writing.md)の「カバレッジと mutation score の基準」） |
| mutation score | `backend-domain` | PIT で測る、テストが検出できた変異の割合（検出した変異 ÷ 全変異）。バックエンドの domain が対象（[テストの書き方](test-writing.md)の「カバレッジと mutation score の基準」） |
| カバレッジの基準 | `scripts/ci/report/quality-baseline.json` | カバレッジと mutation score の、対象ごとの値と許容の幅（`tolerance`）。CI が今回の値と比べる（[CI の検査](../06-手順書/ci.md)の「カバレッジと mutation score の基準の検査」） |
| mock フラグ | `ecsite.<モジュール>.mock.enabled` | 外部サービスの代わりに、内部の mock を使う設定。立てたときだけ mock を使う。ローカルと E2E の設定だけで立てる |
| 本番の実装 | | 外部サービスの port の、本物のサービスにつなぐ実装（決済の Stripe）。mock と同じ port を実装する |
| テスト用の決済サービス | `TestPaymentGateway` | テストで、決済の mock をラップし、失敗させる操作と、呼ばれた操作を記録する機能を加えた実装 |
| テスト用の物流サービス | `TestCarrierTracking` | テストで、物流の mock をラップし、追跡を始めた送り状番号を記録する実装 |
| 業務ポート | `server.port` | API と mock の画面を提供するポート。公開するのはこのポートだけ |
| 運用ポート | `management.server.port` | 死活監視とメトリクス（`/actuator/*`）を提供するポート。外部に公開しない |
| 共有の基盤 | | compose で動かすミドルウェア。PostgreSQL のサーバー・Keycloak・SeaweedFS・imgproxy・Mailpit・Zipkin の 6 つで、全ての作業ツリーで 1 つを使う |
| メインの作業ツリー | | 作業ツリーのうち、リポジトリを clone したもの。スロット 0 を使う |
| スロット | `.local/slot`、`scripts/dev/slot.mjs` | 作業ツリーに割り当てる番号。0 はメインの作業ツリー、1〜3 はそれ以外の作業ツリー。番号ごとにデータベース、画像のバケット、ポートが決まる |
| スロットの環境 | | 1 つのスロットのデータベース、画像のバケット、バックエンド、店舗画面、管理画面 |
| Cookie の接頭辞 | `STORE_COOKIE_PREFIX` | 店舗画面の Cookie の名前の先頭に付ける文字列。スロットごとに変え、同じブラウザーで複数のスロットにログインしてもセッションが混ざらないようにする |
| 契約テスト | `*ContractTest` | 外部との契約を確認するテスト。外部連携の port の実装（mock と本物）が同じ振る舞いを守ることを、同じテストで確認するもの（`PaymentGatewayContractTest`）と、IdP の設定ファイルの値を確認するもの（`RealmSettingsContractTest`）がある |
| 非同期の処理の待ち | `AsyncEvents` | 統合テストで、コミットの後に動くイベントのリスナーが終わる（または失敗する）のを、イベントの発行の記録で待つ補助（[テストの書き方](test-writing.md)の「待ち方」） |
| 標準の構成 | | どのモジュールも従う、層とパッケージの名前と置き場所（[バックエンドのアーキテクチャ](../02-設計/backend-architecture.md)の「層とパッケージ」。層の中の役割は[バックエンドの書き方](backend-coding.md)の「標準の構成」） |
| 腐敗防止層 | `XxxDirectory` | 他のモジュールの API を呼び、その情報を自分のモジュールの型に変換するクラス。インターフェースは使う層の `port/`、実装は `infrastructure/directory/` |
| 参照の service | `XxxQueryService` | データを更新しない application の service。読み取り専用のトランザクションで、view（または外部へのリクエストの型）を返し、集約を返さない（[バックエンドの書き方](backend-coding.md)の「標準の構成」） |
| 更新の service | `XxxCommandService` など | データを更新する application の service。参照だけのメソッドを持たない |
| view | `application/model/view/` | 参照の service が返す、表示や使う側に必要な項目だけの型。画面の操作の可否は、view を作る所で集約の判定を呼んで入れる |
| 作成の応答 | `CreatedResponses` | 作成の API の応答（201、作成したものの Location、作成した ID）。共通の補助で作る |
| jest-dom | `@testing-library/jest-dom` | DOM の要素の状態を確認する照合の関数（`toBeDisabled`、`toHaveAttribute`、`toHaveAccessibleName` など）を Vitest に加えるライブラリ |
| テストの差分の検査 | `scripts/ci/review/test-diff.mjs` | 整理の spec で、既存のテストに加えた変更が、本番のクラスの移動と改名に伴うものだけであることを確認する script |
| 共通の値の型 | `common/model/value/` | 2 つ以上のモジュールで使い、規則（範囲、丸め、比べ方）を持つ値の型（金額、文字の長さの上限など） |
| メッセージのキー | `ecsite.<モジュール>.<名前>` | エラーの文を `messages.properties` から取得するためのキー。エラーの定義（enum の定数）の名前から決まる |
| 共有パッケージ | `frontend/shared`（`@ec-site/shared`） | 店舗画面と管理画面の両方で使う、UI のコンポーネント・関数・文言を置くパッケージ（[フロントの書き方](frontend-coding.md)の「入れるもの・入れないもの」） |
| 共有の文言 | `common.*` | 共有パッケージの文言。2 つの画面で同じ役割の文を置き、各画面の文言と、最上位のキーの単位で合わせて使う（[フロントの書き方](frontend-coding.md)の「表示の文言は文言ファイルに置く」） |
| 整形の関数 | `@ec-site/shared/lib/format` | 金額・価格・数・日時・税額・郵便番号・軸の値を、画面に表示する文字列にする関数。2 つの画面で共有する |
| 既定の数の整形 | `formatNumber`（`@ec-site/shared/lib/format`） | 既定のロケールで、3 桁ごとに区切る数の整形。金額の整形の数の部分も同じ |
| 表示名 | `labels.ts` | API の列挙の値を画面に表示する名前と、Badge の見た目。1 つの機能だけで使うなら `features/<機能>/labels.ts`、2 つ以上なら `lib/labels.ts`。ただし、2 つの画面で同じ表示名は、機能の数によらず共有パッケージに置く（[フロントの書き方](frontend-coding.md)の「画面に依存しない処理は `lib/` の関数」） |
| テストの補助 | | 複数のテストで使う、データの作成・API の差し替え・操作・確認の関数（[テストの書き方](test-writing.md)の「複数のテストで使うものは、テストの補助に置く」） |
| 型を回避する変換 | `as never`、`as unknown as` | 値の型を検査させずに、別の型として扱わせる書き方。テストでは使わない（[テストの書き方](test-writing.md)の「型を回避する変換を使わない」） |
| 注文の表示名 | `orderLabels` | 注文の状態・配送状態・配送業者の表示名を返す関数。2 つの画面で同じ文言なので、共有パッケージに置く |
| 金額の内訳 | `AmountsSummary` | 商品の合計・送料・総額・税率ごとの消費税額を並べて表示する、共有のコンポーネント |
| リンクの見た目のボタン | `LinkButton` | Button の見た目で、リンクの要素を描画する共有のコンポーネント |
| 文言のキーのコメントの検査 | `scripts/ci/message-comments.mjs` | 画面のコードで文言を取得する `t('…')` の呼び出しに、出る文を示すコメントがあることを確認する script（[コメントの書き方](comments.md)の「文言をキーにした所」） |
| 追跡の issue | | spec 1 つに 1 つの issue。番号が spec の番号になる |
| issue 担当のセッション | | 起票し、作業の形と profile、並行の可否を決め、spec 担当のセッションを起動するセッション。危険度が低い変更のマージと、リリースの内容のまとめも行う |
| spec 担当のセッション | | spec 1 つを担当するセッション。利用者と文書を作り、実装とレビューをサブエージェントに任せる（[エージェントの作業フロー](subagents.md)の「役割」） |
| 実装役 | | spec 担当のセッションから実装を任される、サブエージェント |
| 資料収集役 | | spec 担当のセッションから、判断を伴わない資料の収集（該当箇所の要約、事実の確認）を任される、サブエージェント（定義は `researcher`） |
| レビュー役 | | レビューを任される、サブエージェント。指示の文書と memory のない、文脈を持たない第三者として読む |
| フェーズ | | 整理の作業の大きな区切り（例：整理の第 2 フェーズ）。フェーズの下の区切りがステップ |
| ステップ | | フェーズの下の区切り（例：整理の第 2 フェーズの最初のステップ） |
| 規模（S・M・L） | | 変更の大きさの区分。区分ごとに、書く文書と、利用者が確認する対象が違う |
| 完了の定義 | | `develop` に入れる前に満たす条件 |
| レビューの profile | | レビューの量の設定。値は厚め・標準・節約。プランと使用量を見て、issue 担当のセッションが決める |
| モデルの区分 | | サブエージェントに使うモデルの区分。最上位・高性能・汎用・軽量。実際のモデルとの対応は [AGENTS.md](../../AGENTS.md) の「モデルの区分」 |
| 変更の危険度 | | pull request の変更の区分。「危険度が高い」「危険度が低い」のどちらか（[マージと後片付け](merging.md)の「マージの許可と後片付け」） |
| 見逃しの一覧 | | レビューを通った後の不具合の、label「見逃し」の issue。モデルや設定の採点に使う。校閲役は除く（[エージェントの作業フロー](subagents.md)の「モデルや設定を替えるとき」） |
| 校閲役 | | 利用者が中国語で指示する環境で、変更した日本語を読み、通じにくい語と不自然な言い回しを挙げる、サブエージェント。検出役と確認役の 2 つを指す |
| 検出役 | `ja-proofreader` | 校閲の候補を、好みの範囲かどうかで絞らず、多めに挙げる役割 |
| 確認役 | `ja-proof-verifier` | 検出役の候補を 1 件ずつ読み、挙げるか（読む人が引っかかる、または意味を取り違えるか）を判定する役割 |
| 評価の一覧 | `.claude/skills/review/evals/ja-proofread.md` | 校閲役を採点するための例の一覧。挙げるべき語句を含む見逃しの例と、挙げてはいけない誤検出の例がある |
| 作業ブランチ | | `develop` から切り、1 つの spec（規模 S は 1 つの issue）の作業をするブランチ。名前は `<issue の番号>-<短い名前>` |
| `develop` | `develop` | 開発のブランチ。既定のブランチ |
| `main` | `main` | 本番のブランチ |
| リリースのブランチ | `release-` | 確認した commit から作るブランチ（`develop` の最新とは限らない）。名前は `release-` で始める |
| 緊急の修正 | `hotfix-` | 緊急の修正のブランチ。名前は `hotfix-` で始める |

文書の番号と記号（AC・DC、`[テスト]` など）は [文書の記号と番号](notation.md) で参照する。
