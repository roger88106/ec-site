# Spec 554：識別子を種類ごとの型にし、識別子と乱数を注入できるようにする

種類：整理　規模：M　ステータス：確定

危険度：高

## 背景と目的

識別子は全て `java.util.UUID` のまま使われ、UUID を 3 つ以上引数に取るメソッドが 36 ある（#542。例：`CartService.addItem(UUID cartId, UUID requester, UUID variantId, int)`）。引数の順を取り違えてもコンパイルでき、テストでしか気づけない。また、識別子は domain・application・リポジトリの中で `UUID.randomUUID()` を直接呼んで作り、注文番号の乱数も `new SecureRandom()` を項目に持つので、テストで値を固定できない（#495）。

この spec は、識別子を種類ごとの型にしてコンパイルで取り違えを検出できるようにし、識別子と乱数を、時刻（`Clock`）と同じく注入できるようにする。API の JSON、DB の列、イベントの記録の JSON は変えず、消費者・運営者に見える振る舞いは変えない。追跡の issue は #554（#542 と #495 をまとめたもの）。#544（リリースの前の整理）の一部である。

## スコープ

| 含める | 含めない |
|--------|----------|
| 集約と entity の識別子と、それを参照する項目・引数・戻り値を、種類ごとの型にすること | API の JSON と DB の列の型（UUID のまま） |
| 種類ごとの型の、DB（jOOQ）・JSON（Jackson）・生成した API の型との変換 | イベント ID（`DomainEvent.eventId`）の型 |
| 識別子を作るクラスと乱数のクラスを注入すること | 業務番号（注文番号、商品コードなど。識別子でない） |
| 注文番号の衝突と打ち切りの単体テスト | テストのデータの作り方の共通化 |
| 識別子と乱数の規則を、書き方の規則と自動の検査に加えること | jMolecules の `Association` |

決定（issue 担当のセッションが利用者に代わって 2026-11-22 に確認した）：

- 規模と種類：整理・規模 M とする。
  - 理由（規模）：全てのモジュールにまたがるので、規模の判定の表では L になる。ただし、同じ機械的な規則を当てるだけで、API と AC の対応も、モジュールごとの設計の決定もない。#542 で、利用者の判断で特例として M にした。#495 は、識別子を作る場所と同じ所を変えるので、まとめる。
  - 理由（整理）：消費者・運営者に見える振る舞いを変えないため。
- 決定 1（型の形）：識別子の型は、UUID を 1 つ持つ record にし（例：`record OrderId(UUID value)`）、共通の interface `EntityId` を実装する。`EntityId` は jMolecules の `Identifier` を継承し、`UUID value()` を持つ。コンストラクターで null を検査する。`toString()` は UUID の文字列を返す（理由：メッセージ、ログ、ファイルのキーなどで文字列に連結したときに、今と同じ文字列にするため）。
  - 理由：jMolecules を既に使っていて（`@Identity` など）、`Identifier` で識別子の型だと分かるため。`Identifier` は、依存に入っている `jmolecules-ddd` にある。共通の interface があると、JSON の変換を 1 か所で書けるため。
- 決定 2（型の置き場所）：
  - 案 A（採用）：2 つ以上のモジュールが使う識別子は `common/model/id/` に置く（会員、商品、バリエーション、カテゴリー、税区分、カート、注文、画像の素材、アップロード、運営者）。1 つのモジュールだけが使う識別子は、そのモジュールの domain に置く（決済、チェックアウト、出荷、在庫、在庫の調整、商品の画像、税率など）。
  - 案 B：識別子を持つモジュールの `api/` に置き、使うモジュールは腐敗防止層で自分の型に変換する（例：バリエーションは catalog）。欠点は、同じ識別子の型が、使うモジュールの数だけできることである（バリエーションは 6 つ）。
  - 理由（案 A）：腐敗防止層の規則（他のモジュールの型を内部で使わない）のままで、モジュールをまたぐ識別子の取り違えもコンパイルで検出できるため。
- 決定 3（UUID を使ってよい場所）：domain・application・`api/`・`event/` の項目・引数・戻り値には、識別子の型を使い、UUID を使わない。UUID を使うのは、presentation（生成した API の型との変換）、infrastructure（jOOQ との変換）、共通のクラス（`AdvisoryLocks`、`CreatedResponses`）、イベント ID だけにする。共通のクラスは UUID のまま使い、呼び出し側が `id.value()` を渡す。自動の検査（ArchUnit）で確認する。
  - 例外：在庫の引当の行 ID と送信したメールの行 ID は、ドメインの型を持たない行の ID なので、infrastructure の中で UUID のまま扱う。
  - 例外：設定の型（`@ConfigurationProperties` を付けた record。例：注文の設定の送料の税区分 ID）は UUID のまま持ち、使う側で識別子の型に変換する。理由：設定の値は環境変数の文字列から作り、presentation と同じく外から入る値の境界であるため。文字列から識別子の型に変換する仕組み（Converter）を加えないのは、使う所が少なく、加える型と設定が増えるため。
- 決定 4（在庫の引当の持ち主）：在庫の引当の持ち主（今の `holderId`。実体はチェックアウトか注文）は、持ち主の型（`ReservationHolderId`）にし、`common/model/id/` に置く。注文のモジュールは、腐敗防止層でチェックアウトや注文の識別子から変換する。
  - 理由：在庫は持ち主の種類を区別せず、注文のモジュールに依存しないため。在庫と注文の 2 つのモジュールが使うので、置き場所は決定 2 に従う。`inventory.api` に置かないのは、層の依存の規則で、同じモジュールの application と domain が `api` に依存できないため。
- 決定 5（変換）：
  - DB：jOOQ が生成するコードは UUID のままにし、リポジトリで変換する（`id.value()`、`new OrderId(uuid)`）。理由：生成したコードがモジュールの型に依存しないようにするため。列ごとの変換の設定（forcedTypes）にしないのは、列名の対応が多いため。
  - JSON：`EntityId` を UUID の文字列として書き、読む Jackson 3（`tools.jackson`）のモジュールを、設定に 1 つ置く。イベントの記録（Spring Modulith の `event_publication`）と、注文の JSON の列は、今と同じ JSON になる。理由：既に記録したイベントと JSON の列を、そのまま読めるようにするため。domain の型に Jackson の注釈を付けないため。
  - API：生成した API の型は UUID のままにし（OpenAPI の生成の設定は変えない）、presentation で変換する。
- 決定 6（識別子を作るクラス）：識別子は、`common` の `IdGenerator`（UUID を返す）を注入して作る。domain は識別子を引数で受け取る（時刻の `Instant` と同じ）。
  - domain のファクトリと生成のメソッド（`ProductFactory`、`CategoryFactory`、`TaxCategoryFactory`、`Product` のバリエーションの追加、`StockAdjustment` の生成）は、識別子を引数で受け取る形にする。呼び出す application が `IdGenerator` で作って渡す。
  - イベント ID は、共通のメソッド（`DomainEvent` に置く静的メソッド）で作り、各イベントの作成のメソッドがそれを呼ぶ。型と注入は替えない（Non-goals）。
  - trace ID（`TraceIdResolver`）、決済の mock の支払画面の ID（`MockPaymentGateway`）、行 ID（在庫の引当、送信したメール、在庫）も `IdGenerator` で作る。
  - `UUID.randomUUID()` を呼ぶのは、`IdGenerator` の実装と、イベント ID を作る共通のメソッドだけにし、自動の検査（ArchUnit）で確認する。
  - 理由：時刻と同じ形にして、テストで識別子を固定できるようにするため。
- 決定 7（乱数）：乱数は、`RandomGenerator` の Bean（`SecureRandom`）を注入して使う。`new SecureRandom()`・`new Random()` を直接書かないことを、自動の検査（ArchUnit）で確認する。注文番号の生成（`OrderPlacementCommandService`）は、注入した乱数を使う。
- 決定 8（進め方）：
  - 段階 1：共通のクラス（決定 1、5 の JSON、6、7）と、注文番号のテストを入れる。
  - 段階 2：モジュールごとに識別子の型に替える。使われる側のモジュールから替え（税、画像の素材、会員、商品、在庫、決済、出荷、カート）、使う側（注文、通知、レポート、店舗の画面）を後にする。まだ替えていないモジュールとの間は、腐敗防止層（`infrastructure/directory/`）で UUID と変換する。そのモジュールを替えるときに、その変換を削除する。各タスクの終わりは、コンパイルとテストが通る状態にする。
  - 理由：新旧の書き方が混ざる場所を腐敗防止層に限り、モジュールごとに commit できるようにするため。
- 決定 9（文書）：
  - バックエンドの書き方の規則：識別子の型（決定 1〜5）と、識別子・乱数の注入（決定 6、7）の節を加える。「共通の型」に、識別子の型を置く例外（決定 2）を書く。
  - バックエンドの構成の設計：永続化の表の「識別子 | UUID」に、コードでは種類ごとの型にすることを書く。

## 目的と完了条件

### DS-554-1 識別子の取り違えをコンパイルで検出できる（D / P1）

- **DC-554-1** domain・application・`api/`・`event/` の項目・引数・戻り値に UUID がない（決定 3 の例外を除く）ことを、自動の検査で確認している。
- **DC-554-2** 識別子の型が、UUID の文字列の JSON として書かれ、その JSON から読めることを、テストで確認している。
- **DC-554-3** イベントの記録の JSON が、識別子の型に替える前と同じ形（識別子は UUID の文字列）であることを、テストで確認している。

### DS-554-2 識別子と乱数をテストで固定できる（D / P1）

- **DC-554-4** `UUID.randomUUID()` を呼ぶのが `IdGenerator` の実装とイベント ID を作るメソッドだけで、`new SecureRandom()`・`new Random()` を直接書いていないことを、自動の検査で確認している。
- **DC-554-5** 注文番号が衝突したときに次の候補を試すことと、決まった回数で打ち切ってエラーにすることを、固定した乱数を使う単体テストで確認している。

### DS-554-3 振る舞いが変わらず、文書が決定の形になる（D / P1）

- **DC-554-6** API の契約（OpenAPI の定義）と DB の構造（マイグレーション）に差分がない。
- **DC-554-7** バックエンドの書き方の規則と、バックエンドの構成の設計が、決定 9 の形になっている。
- **DC-554-8** `./gradlew check` が通る。

## 非機能要件

- **DN-554-1** 消費者・運営者に見える振る舞い（API の応答、画面、メール、レポート）を変えない。
- **DN-554-2** API の契約、DB の構造、イベントの記録の JSON、注文の JSON の列の形を変えない。既に記録したイベントと JSON の列を読める。
- **DN-554-3** 既存のテストの期待を弱めない。テストの変更は、識別子の型に替えるための書き換えに限る。

## Non-goals

| 項目 | 理由 |
|------|------|
| イベント ID の型と注入 | イベント ID は重複を見分けるためだけに使い、他の識別子と並んで引数に渡らないので、取り違えが起きにくい ※1 |
| jOOQ が生成するコードの型（forcedTypes） | 決定 5 の理由 |
| OpenAPI の生成の型の対応（typeMappings） | API の契約の型は UUID のままで、presentation の変換で足りる |
| テストのデータの作り方の共通化 | この spec はコードの型を替えるだけにする。テストの書き換えは `new OrderId(UUID.randomUUID())` の形にする |
| jMolecules の `Association` | 他の集約への参照を表す型。識別子を種類ごとの型にすれば参照の取り違えも防げるので、今は使う利点がない |

※1：注入にすると、21 個のイベントを作るメソッドの引数が増える。テストで値を固定する必要がない。
