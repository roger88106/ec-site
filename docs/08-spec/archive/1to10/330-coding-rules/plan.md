共通の決定：

- 危険度は高（spec の冒頭）。マージは利用者が許可する。
- DN-330-1、DN-330-2：spec の最後のレビューで、`develop` との差分のファイルの一覧で確認する（本番のコードの変更がコメントの参照の修正だけであること、アーカイブの変更がないこと）。
- DN-330-3：移すときに規則と今のコードの食い違いを見つけたら、その場で修正せず、spec の Non-goals に起票の案として記録する。各段階の最後のレビューの確認する項目にも加える。
- 段階の最後のレビューは、一般の観点を汎用で 2 回行い和集合にする。重要な観点（ファイルをまたぐ影響）は、高性能と汎用で行い和集合にする。危険度が高いので、重要な観点は高性能を必ず含む。
- 各段階の最後に、差分の追加行の校閲（検出役 → 確認役）と `ja-text --changed` を行う。
- CI の検査の script（`test-helpers.mjs`）を変えるので、pull request の前に、文脈を持たない高性能のレビュー役（`reviewer`）を 1 回加える。認証・支払・権限の経路を変えないので、セキュリティのレビューは行わない。
- 実装は実装役（汎用）に 1 タスクずつ任せる。文書の本文は、spec 担当が日本語の要点を書き、日本語だけの文脈の実装役が書く。spec 担当はコードを書かない。
- `[テスト]` のタスク（`checklist.cjs`、`test-helpers.mjs`、`ModuleStructureTest`）は、レッドを確認してから実装する。`scripts/ci/` と skill の script のテストは、続く実装のタスクと同じ commit に入れる（[開発の進め方](../../../../05-開発規則/workflow.md)の「循環」）。
- push は段階の最後に行う。段階 1〜4 の最後のレビューで指摘を修正した後に push する（`origin 330-coding-rules`）。段階 2 は `ModuleStructureTest` を変えるので、`./gradlew check` を手元で通す（Docker が必要）。段階 3・4 も、Java のファイル（コメントを含む）を変えたときは通す。
- draft の pull request は、spec の最後のレビューの後に作り、URL を追跡の issue に記録する。
- 移した先の節の見出しには、今の決まりのとおり番号を付ける（#289 は未決）。
- 節を移したら、`doc-refs` で切れた参照を修正する。リンクでないパスは `replace-paths.cjs` で修正する（skill `docs` の「参照の修正」）。
- `running-tests.md`、`ci.md`、skill を書き換えるタスクは、書き換える前に issue 担当のセッションに知らせる（「並行」）。
- 段階 1 の最初のタスクで、書き換える前の 4 つの文書の規則（「規則の一覧」の全ての行。節、規則、確認方法）を `.local/spec330/rules-before.md` に、`checklist.cjs` の出力を `.local/spec330/checklist-before.md` に保存する（Git に入れない手元の記録）。

※1：文書を読む処理は `parseHelperTable` と `TEST_WRITING_DOC` である。文書には、補助以外のテストは決まった手順を書かない規則と、対応の正本が script の表であることだけを書く。表の 1 つ目（補助と作るもの）は文書に残す。

※2：`ModuleStructureTest` は、目安を超えるパッケージの集合と表の行の集合の一致だけを照合する。表は、見出しの番号でなく、見出しの名前（「パッケージの大きさ」）で探す。

確認 2 の理由は、手順の名前と探す関数の対応が script の 1 か所になり、文書の表の書式を守る注意が不要になるためである。確認 2 が案 B のときは、表を文書に残し、本文の注意だけを短くする。

確認 3 の理由は、クラスを 1 つ追加するたびに文書を修正する手間がなくなるためである。上限（20）は別のテスト（ArchUnit）が見るので、数を照合しなくても上限の超過は見つかる。見出しの名前で探せば、節の番号を動かしても（#289 で番号を外しても）テストが壊れない。確認 3 が案 B のときは、列を残し、表の探し方だけを見出しの名前にする。案 C のときは変えない。

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 冒頭の「規則の一覧」の表をやめる。各節の規則と理由の後に、`確認方法：` で始まる行を置く ※3（確認 1 の決定による） | 4 つの文書 | DC-330-10：段階の最後のレビューで読む。同じ規則が表と本文の 2 か所にないこと |

| `checklist.cjs` が、各節の見出しと `確認方法：` の行を読み、確認方法に「レビュー」を含むものを、チェックリストに出力する ※4 | `.claude/skills/review/checklist.cjs`、`checklist.test.cjs` | DC-330-9：テスト（レッドから）。変える前の出力（`checklist-before.md`）と同じ規則が出力されることを、4 つの文書で照合する |

※3：1 つの節に確認方法の違う規則が複数あるときは、`確認方法：` の行の後に、規則ごとの箇条（`- <規則の短い名前>：<確認方法>`）を置く。

※4：確認方法が複数あるときは、規則ごとの箇条を 1 行ずつ出力する。

`checklist.cjs` が読む文書は、`docs/05-開発規則/` の文書のうち、行の始めが `確認方法：` の行を持つものである。`docs/05-開発規則/` の外の文書（spec・tasks など）の `確認方法：` は読まない。理由：tasks の各タスクにも `確認方法：` の行があり、それを規則として読まないため。

確認 1 の理由は、規則の文を 1 か所に書け、確認方法が規則の隣にあるので、規則を変えるときに確認方法も一緒に見直せるためである。規則の全体はチェックリストの script で一覧にできるので、表がなくても読める。確認 1 が案 B のときは、表の「規則」の列を節の見出しへの参照だけにし、本文に確認方法を書かない。この場合、`checklist.cjs` は今の 3 列を読む。案 C のときは、4 つの文書の形を変えない。

この段階は規則の中身を変えない。形を書き換えるだけで、規則の文と確認方法は、書き換え前と同じ内容を保つ。
