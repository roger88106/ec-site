## レビューの結果

### 修正したこと

- 処理の済んだイベント、期限切れの引当・注文手続き・カートを、保存期間を過ぎたら片付ける定期ジョブを、データを持つモジュールに置いた。件数の上限ずつ分けて削除し、分散ロックで同時に 1 つだけが動く。注文になった注文手続きを削除しても、注文は読める。
- 再発行の上限まで処理に失敗したイベントを止め、止めたときだけログを 1 回出力し、未完了と止めたイベントの件数をメトリクスに置いた。止めたイベントは片付けで消えない。
- 外部サービス（決済、画像の変換、ファイルの保存）の失敗を分け、外部サービスのエラーは 502 とエラーコード・メッセージで返す。外部サービスが読めないとエラーを返した画像だけを 400 にする。管理・店舗画面はその文を表示する。
- 外部サービスの client（Stripe、S3、imgproxy）と、店舗画面から店舗 API・IdP への呼び出しに、タイムアウトを設定した。
- 外部サービスをトランザクションの外で呼ぶようにした。商品画像の追加は、確認・用意（外）・保存の 3 つに分け、保存が失敗したら用意したファイルを削除する。返金・与信の取消・配信のファイルの削除・追跡の開始のリスナーは、トランザクションなしにした。出荷のメールは、理由を書いてトランザクションの中に残した。
- 店舗画面は、サーバーアクションの失敗と店舗 API の 5xx を、秘密情報を含めずにログに出力する。
- 支払の期限切れのジョブは、1 件の例外で止まらず、決済サービスで支払済みの支払を「通知を待つ支払」にして次の回から探さない。通知を長く待つ支払の件数を警告のログに出力する。
- 会員の確認は、会員が登録済みのときは読み取り専用のトランザクションだけで済ませる。
- レビューで、商品画像を加える前の確認を参照の service に移し、設計書の関連 spec と環境変数の既定値の書き方を修正した（T017-08-02、04）。

### 修正せずに残したこと

| 項目 | 理由 |
|------|------|
| 出荷のメールの送信は、トランザクションの中で行う | 送信の記録と送信を同じトランザクションにし、送信に失敗したら記録も取り消して再発行で再送するため（外で送ると、記録の失敗で二重に送りうる）。理由は通知モジュールの設計書に書いた（plan 第 5.2 節 ※10） |
| 画像の「用意」を、トランザクションの中で呼んでも失敗させない | テストのトランザクションの中で画像を追加するテストがあるため（段階 4 で利用者と決めた）。トランザクションの外で呼ぶことは、商品画像の統合テストで確認する |
| 履歴の書き換え（段階 4・7 で、push していない commit を fixup で修正した） | 誤りが commit の範囲に入っていたため。push の前なので、履歴の書き換えの規則（AGENTS.md「Git」）に合う |

### 後の spec に回したもの

spec の Non-goals と plan 第 11 節のとおり（止めたイベントを画面で扱う操作、メトリクスによる警報、外部サービスの自動の再試行、通知を待つ支払の与信を決済サービスから取得して補完することは 1 → 10）。レビューで新しく回したものはない。
