# Spec 321：設計書と spec・plan・tasks の雛形を、試作で決めた構成で入れる

種類：整理　規模：L　ステータス：確定

危険度：高

## 背景と目的

整理の段階の第 2 フェーズの spec 4 である。追跡の issue は #321 で、種類は整理、領域は docs である。規模 L は利用者が承認した（2026-10-29）。消費者・運営者に見える振る舞いと、本番のコードは変えない。

構成は #320 の試作で決め、利用者が承認した（2026-11-02）。構成と理由は [#320 のコメント](https://github.com/roger88106/ec-site/issues/320#issuecomment-6569734740)にあり、この spec には写さず指す。

試作の commit は、`/.local/refactor/320-trial/patches/`（Git に入らない）に patch として残した。試作では検査と校閲を最小限にしたので、そのまま取り込まず、tasks で検査と校閲を通して、再度取り込む。

作業ブランチは `321-design-templates` で、`develop` の d0029132 から作った。アーカイブ先は `docs/08-spec/archive/1to10/321-design-templates/` である。

危険度は高とする。`scripts/ci/`、`docs/05-開発規則/`、`docs/constitution.md`、`.github/` を変え、`scripts/ci/risk.json` の「エージェントの規則と設定」「CI とリリース」の経路に当たるためである。マージは利用者が許可する。

CI の検査の script を変えるので、pull request の前に、文脈を持たない高性能のレビュー役を 1 回加える（[エージェントの作業フロー](../../05-開発規則/subagents.md)の「レビューの時点と profile」）。認証・支払・権限の経路は変えないので、セキュリティのレビューは行わない。

この spec は整理の spec で、試作で作った整理の spec の雛形（`spec-refactor.md`）の形で書く。後で入れる構造の検査の対象に、この spec 自身が入るためである。

## 目的と完了条件

DS ごとに DC を書く。DC は 1 つに条件を 1 つ書く。確認方法は [plan](plan.md) で決める。

### DS-321-1 設計書の 4 層に、層ごとの雛形を置く（D / P1）

- **DC-321-1** ① `docs/01-概要/`、② `docs/02-設計/`、③ `docs/03-機能仕様/`、④ `docs/04-決定記録/` に、雛形 `template.md` がある。
- **DC-321-2** 各雛形に、読者、置くもの、置かないもの（置き場所）と、写して使う骨組みがある。内容は、#320 のコメントの「1. 設計書の 4 層」の層ごとの形と食い違わない。
- **DC-321-3** ③ の雛形のレベルの行は、レベル A のモジュールとして数えられない形である（`ProductionClassesTest` が通る）。
- **DC-321-4** constitution の「文書の地図」と各フォルダーの README に、雛形と新しい文書がある。
- **DC-321-5** 書き方の規則（`writing.md` の「表と注」、`notation.md` の「モジュールの設計書の記号」）にある、モジュールの設計書の置き場所と冒頭の表の書き方が、4 層の構成と食い違わない。

### DS-321-2 注文の設計書を、4 層の構成で書く（D / P1）

- **DC-321-6** ① に、システムの全体像（`system.md`）と注文の流れ（`order.md`）がある。
- **DC-321-7** ② に、注文の設計（`order.md`）がある。節は、境界、処理の流れ、API、パッケージの構成である。
- **DC-321-8** ③ の注文モジュール（`order.md`）の `##` の節が、業務規則、状態の遷移、データモデル、今有効な AC の順である。
- **DC-321-9** ④ に、出荷の登録の前に売上を確定する決定記録がある。③ の本文は、理由を書かずに決定記録を指す。
- **DC-321-10** 書き換え前の ③ の注文モジュールの規則が、欠けずに ① から ④ のどこかにある。
- **DC-321-11** ③ の「今有効な AC」の各行が、AC 一覧（`docs/03-機能仕様/acceptance-criteria.md`）の今の内容と食い違わない。
- **DC-321-12** ① から ④ の間で、同じ事実を 2 か所に書いていない。他の層の内容は、写さずに指す。

### DS-321-3 図を作り、Mermaid の図の構文を CI で検査する（D / P1）

- **DC-321-13** ① のシステムの全体図が、draw.io の `.drawio.svg`（図の元データを埋め込んだ SVG）である。
- **DC-321-14** ① にある画面の操作の流れの画像は、手動で撮らず、script（`e2e/docs/order-flow.spec.ts`）で再度撮れる。再度撮る手順が ① に書いてある。
- **DC-321-15** docs の Mermaid の図に描画できないものがあると、CI が失敗する。
- **DC-321-16** Mermaid の検査の script にテストがある。
- **DC-321-17** 試作の自己レビューで見つけた、Mermaid の検査への指摘が、修正されているか、扱わない理由が spec か plan にある。指摘は次の 5 つである。
  - 他のコードブロック内の図の誤検出
  - 閉じていないコードブロックの見逃し
  - info string の大文字と後ろの文字
  - 一時ディレクトリのパスの空白
  - Chrome がないときに作業のディレクトリが残ること

### DS-321-4 spec・plan・tasks の雛形と見本を置き、構造を CI で検査する（D / P1）

- **DC-321-18** `docs/08-spec/templates/` に、雛形（機能の spec、整理の spec、plan、段階の tasks）がある。見本（機能・規模 L、整理・規模 M。番号 900）もある。
- **DC-321-19** 進行中の spec・plan・tasks、見本、雛形の構造が雛形と食い違うと、CI が失敗する。
- **DC-321-20** 同じ spec の中で参照した ID が定義されていないと、CI が失敗する。
- **DC-321-21** 構造の検査の対象にした ③ の文書で、`##` の節の名前か順が固定と違うと、CI が失敗する。
- **DC-321-22** 構造の検査の script にテストがある。
- **DC-321-23** 構造の検査の判定は、誤りの防止（誤って書いたものを拒否し、意図して作った回避は対象にしない）である。
- **DC-321-24** 試作の自己レビューで見つけた、構造の検査への指摘が、修正されているか、扱わない理由が spec か plan にある。指摘は、次の 7 つである。
  - 雛形そのものを検査しないこと
  - spec 自身の番号の打ち間違いの見逃し
  - 太字の ID をどこでも定義とみなすこと、重複した定義
  - 段階のファイル名・見出し・タスク番号の段階の一致
  - 冒頭の種類・規模・ステータスの行の探し方
  - 範囲の展開の上限と列挙の誤読
  - コードブロックの閉じの判定
- **DC-321-25** `workflow.md` の「spec の種類と書くこと」の表の節の名前が、spec の雛形と一致する。
- **DC-321-26** `notation.md` の「文書のステータス」に、承認前の plan のステータスの値がある。

### DS-321-5 設計書を読むバックエンドのテスト 3 つの扱いを決める（D / P1）

## 非機能要件

- **DN-321-1** 消費者・運営者に見える振る舞いを変えない。本番のコードを変えない。例外は、本番のコードのコメントのうち、書き換えた設計書の見出しを指す参照の修正だけである（利用者の決定、2026-11-02）。理由：③ の見出しを変えたので、コメントの参照が無い節を指すため。
- **DN-321-2** アーカイブした spec を変えない。
- **DN-321-3** 注文以外のモジュールの設計書を、4 層の形に書き換えない（spec 5）。
- **DN-321-4** 文書の検査（`doc-refs`、`note-numbers`、`ja-text`）と `scripts/ci/check-all.sh`、CI が通る。
- **DN-321-5** commit 前の hook（`check-all.sh`）の実行時間を、大きく増やさない。理由：commit のたびに実行されるため。
