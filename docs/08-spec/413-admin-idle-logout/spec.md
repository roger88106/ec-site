# Spec 413：管理画面から、操作がないまま 30 分たったらログアウトする

種類：機能　規模：M　ステータス：草案

## 背景と目的

[管理画面の構成](../../02-設計/apps/admin.md)の「ログイン」の表は、token の更新を「再取得できなければ（最後の操作から 30 分、またはログインから 8 時間を過ぎたとき）再ログインする」と書く。実際は、管理画面は操作がなくても access token を自動更新し続ける。Keycloak の文書によれば、refresh token で更新するたびに、IdP（運営者の realm）のセッションのアイドルタイムアウト（30 分）が延びる。

そのため、管理画面を開いたまま席を離れても、タブが開いていて PC が動いている間は、最大 8 時間（IdP のセッションの最大の存続時間）、権限が必要な画面を操作できる。共用の PC で、注文や個人情報を他の人に見られるおそれがある。店舗画面は、リクエストのときだけ token を更新するので、この問題はない。

この spec は、運営者の操作が 30 分ないと管理画面からログアウトし、ログアウトの 2 分前に警告を表示する。

追跡の issue は #413。関わる文書は、[管理画面の構成](../../02-設計/apps/admin.md)の「ログイン」、[AC 一覧](../../03-機能仕様/acceptance-criteria.md)。

### 確認した範囲と限界

| 確認した内容 | 方法と出典 |
|--------------|------------|
| 管理画面は、操作なしでテストの時計を 40 分進めると、4 分ごとに 10 回 token を更新し、ログインから 8 時間を超えると更新が止まる | issue #413 の jsdom の一時的なテスト |
| access token の自動更新が有効になっている | `frontend/admin/src/auth/oidc.ts:18` |
| 運営者の realm のアイドルタイムアウトは 1800 秒、最大の存続時間は 28800 秒、access token の期限は 300 秒 | `docker/keycloak/realms/ec-admin-realm.json` |
| refresh token での更新が、IdP のアイドルタイムアウトを延ばす | Keycloak の文書（Session and token timeouts） |

実際の Keycloak では、更新でアイドルタイムアウトが延びることを確認していない。

## スコープ

| 含める | 含めない |
|--------|----------|
| 操作がないときのログアウトと、その前の警告 | API の契約、バックエンド、IdP の設定 |
| 最後に操作した時刻をタブの間で共有すること | ログインから 8 時間の最大の存続時間の扱い |
| テストの追加 | 401 で IdP へ移るときの入力の消失 |
| AC 一覧と管理画面の構成の更新 | ログイン画面に、ログアウトの理由を示すこと |
| | 店舗画面 |

含めないものの理由は Non-goals に書く。

決定：

1. 規模は M にする。理由：AC を追加するが、API の契約と DB の構造を変えず、管理画面だけを変えるため。
2. 方式：access token の自動更新は残し、運営者の操作が 30 分ないとログアウトする。
   - 採らなかった案：自動更新をやめ、操作のあるときだけ更新する案。理由：長い入力の最中（5 分以上通信がない間）に access token が失効し、保存が 401 になって入力が失われるため（issue #413 の「案と注意点」）。
3. 操作に数えるものは、キーの入力、ポインターの押下（クリック、タップ）、ホイールのスクロール。数えないものは、API の呼び出しとポインターの移動。理由：API の呼び出しを数えると、再取得やバックグラウンドの取得で、ログインの有効な時間が延びるため。ポインターの移動は、マウスに触れただけでも起きるため。
4. 警告：操作がないまま 28 分（ログアウトの 2 分前）たつと、ログアウトする時刻と「操作を続ける」ボタンをダイアログに表示する。ボタンを押すか、他の操作をすると、ダイアログを閉じ、30 分の計測を最初から始める。
5. ログアウトの仕方：今のログアウトと同じく、IdP のログアウト（RP-Initiated Logout）へ移る。戻り先は管理画面のトップで、そこからログイン画面に移る。理由：管理画面の token を捨てるだけでは IdP のセッションが残り、再読み込みでパスワードなしにログインできるため（[管理画面の構成](../../02-設計/apps/admin.md)の「ログイン」の ※5）。
6. 最後に操作した時刻を、ブラウザーのローカルストレージに置き、タブの間で共有する。置くのは時刻だけで、token は置かない。
7. 各タブは、共有した時刻から判定する。どのタブで操作しても、全てのタブで最後の操作として扱う。そのため、全てのタブがほぼ同じ時刻に警告とログアウトをする。
8. スリープの後：現在の時刻と最後に操作した時刻を比べて判定する。PC のスリープなどでタイマーが停止しても、再開したときに最後の操作から 30 分を過ぎていれば、ログアウトする。
9. 30 分の値は、管理画面の定数として定義し、運営者の realm のアイドルタイムアウト（1800 秒）と同じにする。2 つを同じにすることを、管理画面の構成に書く。
10. 管理画面の構成の「ログイン」の表で、「token の更新」の行を書き換え、「操作がないときのログアウト」の行を加える。

論理名と識別子の対応は次のとおり。

| 論理名 | 識別子 |
|--------|--------|
| ログインを求めるコンポーネント | `AuthGate` |
| 自動更新の設定 | `frontend/admin/src/auth/oidc.ts` |
| 無操作の判定を置く場所 | `frontend/admin/src/auth/` |
| ローカルストレージ | `localStorage` |
| 文言のファイル | `frontend/admin/src/i18n/messages.ts` |

## User stories

| US | 誰が | 何をできる | なぜ |
|----|------|------------|------|
| US-413-1 | 運営者 | 管理画面を開いたまま席を離れても、30 分でログアウトされる | 共用の PC で、注文や個人情報を他の人に見られないため |
| US-413-2 | 運営者 | ログアウトの前に知らされ、操作を続けられる | 入力の途中でログアウトされて、入力が消えないようにするため |

## 受け入れ条件

### US-413-1 無操作でのログアウト（B / P1）

- **AC-413-1** 運営者が操作しないまま 30 分たつと、管理画面からログアウトする。
- **AC-413-2** ログアウトの後に管理画面を再び開くと、パスワードを求められる。
- **AC-413-3** キーの入力、ポインターの押下、ホイールのスクロールを、操作として数える。
- **AC-413-4** API の呼び出しとポインターの移動は、操作として数えない。
- **AC-413-5** 同じブラウザーの複数のタブで開いているとき、どのタブの操作も、全てのタブの最後の操作として数える。
- **AC-413-6** PC のスリープなどで画面の処理が停止した後に再開したとき、最後の操作から 30 分を過ぎていれば、ログアウトする。

### US-413-2 ログアウトの前の警告（B / P1）

- **AC-413-7** 操作しないまま 28 分たつと、ログアウトする時刻と「操作を続ける」ボタンをダイアログに表示する。
- **AC-413-8** 警告の間に操作すると、警告を閉じ、30 分の計測を最初から始める。

## 非機能要件

- **NFR-413-1** API の契約、バックエンド、IdP の設定を変えない。
- **NFR-413-2** token はメモリーにだけ置く。タブの間で共有するのは、最後に操作した時刻だけにする。
- **NFR-413-3** 操作が続く間は、今のとおり access token を自動更新し、ログインから 8 時間まで使える。

## Non-goals

| 項目 | 理由 |
|------|------|
| API の契約、バックエンド、IdP の設定 | 操作の有無は管理画面だけで判定でき、IdP のセッションは今のログアウトで終えられるため（NFR-413-1） |
| ログインから 8 時間で更新に失敗した後の扱い（表示が次の 401 まで残る） | アイドルタイムアウトとは別の経路で、issue #413 の期待した振る舞いに含まれないため |
| 401 で IdP へ移るときに、編集中の入力が消えること | 今の振る舞いで、この spec の変更で起きる経路ではないため。無操作のログアウトによる消失は、警告（AC-413-7）で減らす |
| ログイン画面に、ログアウトの理由を示すこと | ログイン画面は IdP の画面で、管理画面の範囲の外であるため |
| 店舗画面 | リクエストのときだけ token を更新するので、同じ問題がないため |
