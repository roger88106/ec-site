# 開発の進め方

[constitution](../constitution.md) 第 4、13 節の細則。仕様駆動開発（SDD）で何を作るかを先に決め、テスト駆動開発（TDD）で作る。
番号と記号の意味は [文書の記号と番号](notation.md)、エージェントの作業の手順は [AGENTS.md](../../AGENTS.md)、サブエージェントへの任せ方は [エージェントの作業フロー](subagents.md) にある。

## 1. 仕様駆動開発（SDD）

### 1.1 流れ

規模 L の流れを示す。規模 S・M の文書は第 4.2 節にある。全ての変更は issue から始まる（第 4.1 節）。

| 段階 | 文書 | 書くこと |
|------|------|----------|
| spec | `spec.md` | 何を、なぜ作るかと、受け入れ条件（整理の spec は完了の条件）。実装（クラス名、カラム、フレームワーク）は書かない |
| plan | `plan.md` | 今回の変更について、モジュールをまたぐ決定、API と AC の対応、テストの割り当て、実装の順序。あわせて OpenAPI を書き、モジュールの設計が変わるなら `docs/design/modules/` を更新する |
| tasks | `tasks/` | plan を検証可能な小さなタスクに分け、対応する AC を記す。段階ごとに 1 ファイル |
| 実装 | コード | tasks に沿って、TDD（第 2 節）で進める |

### 1.2 spec の種類と書くこと

| 種類 | 書くこと | 番号 |
|------|----------|------|
| 機能 | 背景と目的、User stories、受け入れ条件、業務ルール、非機能要件、Non-goals、Open questions | US・AC・BR・NFR |
| 整理 | 背景と目的、目的、完了の条件、非機能要件、Non-goals、Open questions | DS・DC・DN |

- 機能の spec は、単独で検証できる機能の縦切り（バーティカルスライス）1 つ。
- 整理の spec は、消費者・運営者に見える振る舞いを変えない。変える必要が出たら、機能の spec にする。
- Open questions を空にし、利用者が spec を確定してから plan に進む。
- DC の確認方法（CI、テスト、検査の script、レビューで読む）は plan で決める。
- 設計への影響が大きい spec は、ステータスの下に「危険度：高」の行を書く（[エージェントの作業フロー](subagents.md) 第 4 節）。

### 1.3 文書の置き場所

| 内容 | 置き場所 |
|------|----------|
| 今回の変更（何を・どう・手順） | `docs/specs/<番号>-*/` の spec・plan・tasks（1→10 の番号は 0 で埋めない。MVP は archive の下） |
| モジュールの今の設計<br/>（集約、不変条件、公開する api・event、設計の理由） | `docs/design/modules/<module>.md` |
| フロントの各アプリの構成 | `docs/design/apps/`、`docs/design/frontend-architecture.md` |
| API の項目 | `api/openapi/` |
| テーブルの定義 | Flyway のマイグレーション（作成するまでは `docs/design/modules/` に草案を置く） |
| 後回しの作業と未決事項 | issue（milestone `1→10`。第 4.1 節） |
| 規模 M の spec | `docs/specs/<番号>-<名前>/spec.md`（第 4.2 節） |
| ブランチとリリースの手順 | `docs/guides/branches.md` |
| 用語と識別子の対応 | `docs/design/glossary.md` |
| AC の今の状態とテスト | `docs/design/acceptance-criteria.md`（AC 一覧） |
| コードの書き方 | `docs/rules/backend-coding.md`、`docs/rules/frontend-coding.md`、`docs/rules/test-writing.md`、`docs/rules/comments.md` |
| 起動・テストの手順 | `docs/guides/` |
| spec の進み具合 | MVP の spec は README の進捗の表、1→10 の spec は追跡の issue と milestone |
| 決定の経緯 | コミットメッセージ |
| 完了した 1→10 の spec | `docs/specs/archive/1to10/`（第 4.2 節） |

文書には今のルールと設計だけを書く。

### 1.4 spec と plan の書き方

| 対象 | 書き方 |
|------|--------|
| AC・DC | 1 つの AC・DC に条件を 1 つ、1〜2 文で書く。値の一覧と場合分けは、箇条書きか表にする |
| Given / When / Then | 同時の操作など、手順で示さないと分からない条件だけに使う |
| 括弧 | 1 文に 1 つまで。理由は文の後に `理由：〜ため。` で、長い補足は表の下に `※1：` で書く |
| plan の節 | 決定を表（何を、どこに、確認方法）で先に示し、理由を後に書く。1 つの箇条書きに 1 つの決定 |
| 識別子 | ファイル・クラス・関数の名前は、表の列とコードブロックにだけ書き、本文は役割で書く（第 3.2 節） |
| 他の文書の内容 | モジュールの設計、API の項目、書き方の規則は転記せず、その文書を指す |
| 参照 | 文書の名前と節で書く（`店舗画面の構成 第 4.5 節`）。constitution の節の番号は使わない |

- plan で操作やクラスを移す・削除すると決める前に、テスト（`src/test`、`src/integrationTest`、画面のテスト、E2E）を含む全ての呼び出し元を検索し、plan に挙げる。同じ名前のメソッドが複数あるときは、型で区別できる方法（IDE の呼び出しの階層）で調べる。理由：テストだけが使う呼び出しを見落とすと、実装で決定し直すため。
- 完了した spec・plan・tasks は当時の記録として、内容と節の番号を変えない。修正するのは、文書を移して切れたリンクのパスだけ。
- 今の設計はモジュールの設計書と `docs/design/` に書くので、古い spec は直さない。

理由：spec と plan は、利用者が承認の前に読み、実装の間にエージェントが何度も読むので、決定と条件を一目で読み取れるようにするため。

### 1.5 コードと文書の食い違い

- 現在の振る舞いは、コードを唯一の正とする。文書は、その振る舞いと設計の理由を説明する。
- 文書とコードの食い違いに気づいたら、誤っている方で扱いを分ける。コードが正しく文書が古いときは、文書を修正する。コードが spec の意図と異なるとき（不具合）は、その場ではコードも文書も変えない。自分の spec の範囲の不具合は、tasks に追加してテストから修正する。spec の範囲の外の不具合は、issue に起票する（第 4.1 節）。
- 完了した spec の AC を変える振る舞いの変更（上限の値を変える、など）は、新しい機能の spec で行い、AC 一覧の行で示す。整理の spec で行うのは、レビューで見つけた不具合の修正（その spec の非機能要件で例外にしたもの）だけ。
- 値（上限、件数、期限など）を変えるときは、AC の番号によらず、旧い値をテスト（バックエンド、画面、E2E）と文言の全体で検索する。境界の値（上限と上限 ＋ 1）は、別の AC のテストにもある。
- spec で AC を追加する・変えるときは、同じ commit で [AC 一覧](../design/acceptance-criteria.md)を修正する。追加した AC は `node scripts/ci/ac-check.mjs --write` で行が追加される。前の spec の AC を変えた・廃止したときは、その行の状態、変えた spec、今の内容を手動で修正する。

理由：文書を正とすると、コードと異なる文書に従って作業し、誤りが広がるため。

## 2. テスト駆動開発（TDD）

### 2.1 循環

1. **レッド**：失敗するテストを書き、失敗することを確認する。
2. **グリーン**：テストが通る最小の実装を書く。
3. **リファクタリング**：テストが通ったまま、コードの構造を改善する。次の振る舞いのレッドに進む。

振る舞いを変えないリファクタリングの前には、今の振る舞いを固定するテストを追加してよい。このテストは最初から通るので、一時的にコードか期待値を変えて、失敗しうることを確認する。

CI の検査の script（`scripts/ci/`）のテストは、commit の前の hook が実行するので、レッドのままでは commit できない。`[テスト]` のタスクは手元でレッドを確認するところまでとし、続く実装のタスクと同じ commit に入れる（「1 つの commit に 1 つのタスク」の規則の例外）。commit の本文に、レッドを確認したことを書く。

### 2.2 対象ごとの進め方

| 対象 | 進め方 |
|------|--------|
| domain | 厳密な TDD |
| AC 単位の振る舞い | 実装前に受け入れテストを書き、レッドから始める |
| infrastructure、Controller の配線 | 実装後に書いてよい |
| フロントの関数（判定、変換、表示の整形） | 厳密な TDD |
| フロントの主な操作の流れ（保存、エラーの表示、確認など） | 結合テストを書く。実装の前でも後でもよい |
| フロントの見た目 | 求めない（目視で確認する） |
| E2E | 実装の後に書く（`[E2E]` のタスク）。レッドは求めない |

※ E2E は、画面・API・バックエンドがそろってはじめて動き、先に書くと失敗の理由を絞れない。振る舞いのレッドは、単体・結合・統合のテストで確認する。

## 3. 文書の書き方

### 3.1 言語

- Git に入るものは全て日本語で書く：ドキュメント、コメント、Javadoc、テスト名、テストデータ、seed、コミットメッセージ、エラーメッセージ。
- 識別子（クラス名、変数名、API のパス、テーブル名・カラム名）は英語。
- 例外：外部から取り込んだ skill（`.claude/skills/`）は、原文の言語のまま置いてよい。出典の更新を取り込みやすくし、許諾の条件（原文と出典の表示）を守るため。その代わり、`SKILL.md` の frontmatter の直後に、何をする skill か・いつ使うかの日本語の説明をコメント（`<!-- -->`）で書く。このリポジトリ向けの追記と、自分で作る skill は日本語で書く。

### 3.2 論理名と物理名

- spec・plan・モジュール設計書の本文は、業務の用語（論理名）で書く。
- 識別子（物理名）を書くのは、[用語集](../design/glossary.md)、表の識別子の列、コードブロックだけにする。
- 新しい用語や識別子を作ったら、用語集に追加する。
- 実装の細部（SQL の句、アノテーション名など）は本文に書かず、意図だけを書く。

## 4. 起票と規模

### 4.1 起票

- Dependabot の pull request を除き、全ての変更は issue から始める。
- 後回しにする作業と未決事項は、issue に起票する。対応時期が決まっているものにだけ milestone `1→10` を付ける。spec の Non-goals に「1→10」と書く項目も起票する。完了したら issue を閉じる。
- 起票の時点は次のとおり。

| 時点 | 起票の方法 |
|------|------------|
| spec の途中 | spec（Non-goals、レビューの結果、plan）に記録する |
| spec の最後 | まとめ方の案を pull request に付ける。利用者が承認したら、issue 担当のセッションが、重複を避けて起票する |
| 急ぐ作業（不具合、マージの失敗など） | すぐに起票する |

- issue は `.github/ISSUE_TEMPLATE/` のテンプレート（機能・整理・不具合）で作る。コマンドで起票するときも、次の表の項目（\* は必須）と同じ節を本文に使う。

| テンプレート | 項目 |
|--------------|------|
| 機能 | 背景と目的\*、やりたいこと\*、条件付きの条件、出典、関連 |
| 整理 | 背景と目的\*、整えるもの\*、完了の目安、条件付きの条件、出典、関連 |
| 不具合 | 起きたこと\*、再現の手順\*、期待した振る舞い\*、発生した場所、関係する AC、関連 |

- spec ごとに追跡の issue を 1 つ作り、その番号を spec の番号とする（[文書の記号と番号](notation.md)）。spec が扱う全ての issue は、`gh api graphql` の `addSubIssue` で追跡の issue の sub-issue に結ぶ。
- issue と spec の対応は、次のとおりにする。

| 対応 | 追跡の issue | 結び方 |
|------|--------------|--------|
| 1 つの issue を 1 つの spec で扱う | その issue を追跡の issue にする | なし |
| 複数の issue を 1 つの spec で扱う | 新しく作る | 扱う issue を、追跡の issue の sub-issue にする |
| 1 つの issue を複数の spec に分ける | spec ごとに新しく作る。元の issue は追跡の issue にしない | 追跡の issue を、元の issue の sub-issue にする |

- GitHub の sub-issue は、親を 1 つしか持てない。親が 2 つ必要になるときは、片方を本文の「関連」に `#番号` で書く。
- 不具合の issue を起票するとき、原因の変更がレビューを通ったか、エージェントがマージしたものなら、label「見逃し」を付ける。「関連」に書く内容は[エージェントの作業フロー](subagents.md) 第 5 節。

### 4.2 規模

規模（S・M・L）はエージェントが提案し、利用者が承認する。文書は次のとおり。

| 規模 | 文書 |
|------|------|
| S | issue だけ。issue の本文を spec とする |
| M | `spec.md` の 1 つのファイル。目的、完了の条件か AC、tasks の節 |
| L | spec・plan・tasks |

判定の基準は次のとおり。

| 条件 | 規模 |
|------|------|
| API の契約かデータベースの構造を変える、または 2 つ以上のモジュールにまたがる | L |
| AC を追加する・変える | M 以上 |
| 振る舞いを変えず、範囲が小さい | S |

- 規模 M の spec.md は、`docs/specs/<番号>-<名前>/` に置く。理由：検査の script が spec.md を読むため。
- 完了した 1→10 の spec は、MVP と同じくまとまりごとにアーカイブし、`docs/specs/archive/1to10/` に置く（M の spec も同じ）。同じ pull request に含める。理由：後に移すと pull request が増えるため。
- tasks を作るとき、アーカイブに移すタスクを最後にし、spec の最後のレビューと pull request の前のレビューをその前のタスクにする。アーカイブの commit で、そのタスクを含む全てのチェックボックスを `[x]` にする。pull request の作成はタスクにせず、spec の最後のレビューの後に draft で作り、URL を追跡の issue に記録する。pull request の前のレビューは draft で行い、指摘に対応して draft を外す。理由：先に作ると、レビュー中に止まっても、作業とレビューの記録が pull request に残るため。
- マージの前に、アーカイブの後にタスクを追加するとき（第 5.5 節のレビューの対応、CI の失敗の修正など）は、アーカイブのタスクの後に、そのタスクを済ませる commit で `[x]` の行として追加する。`develop` を取り込むだけの commit はタスクにしない。理由：進捗の検査が、アーカイブした spec の全タスクの完了を求めるため。

## 5. 利用者の確認と中断

### 5.1 利用者が確認する対象

| 規模 | 利用者が確認する対象 |
|------|----------------------|
| L | spec、plan と tasks を一緒に、pull request |
| M | 1 つのファイルの spec、pull request |
| S | 規模の区分、pull request |

pull request の確認は、利用者の許可が必要なマージだけ（第 5.7 節）。

### 5.2 待たないこと

段階とタスクの間で、利用者の確認を待たない。

### 5.3 中断して質問する条件

次のときだけ、作業を中断して利用者に質問する。

- spec・plan の誤り
- 実装を始める前の照合（第 5.6 節）で、設計が変わる差
- 文書にない設計の判断
- 重要度「高」（定義は skill `review` の prompts.md の「重要度」）の指摘のうち、修正が機能の追加に相当するもの
- 最上位（使えなければ高性能）でも原因を特定できない失敗
- 同じ対象のレビューと修正の繰り返しが上限に達したとき（skill `review` の convergence.md）

使用量の閾値に達したときは、区切りで止まって報告する（[作業の形と使用量](resources.md) 第 2 節）。

### 5.4 まとめて質問する

確認事項は、plan と tasks の確認でまとめて質問する。

### 5.5 pull request のレビューの対応

利用者が pull request に付けた指摘は、見つけた時点と影響の範囲で扱いを分ける。

| 場合 | 例 | 扱い |
|------|----|------|
| マージの前で、spec の意図の範囲の中 | 言い回し、文書の書き方、小さなコードの修正 | 同じ pull request で直す。文書は追加せず、指摘に直した commit を返信する |
| マージの前で、spec・plan の誤り | 動かして、plan の判定の誤りが分かった | 同じ pull request で、spec・plan を先に直し、tasks に段階を追加して（アーカイブの後は第 4.2 節のとおり）、テストから直す。設計が変わるときは第 5.6 節のとおり |
| マージの後 | `develop` で動かして分かった不具合や変更 | issue に起票し、新しい spec（規模による）で直す。アーカイブした spec は変えない |

- 境目は `develop` へのマージ。マージの前は、アーカイブに移した spec も直してよい。理由：アーカイブはマージで確定するため。

### 5.6 実装を始める前の照合

spec 担当のセッションは、照合の前に、開始の条件（起動のメッセージに書かれる）を確認する。満たさないときは、issue 担当のセッションに問い合わせてターンを終える。兼務のときは skill `sessions` に従う。

満たしたら、最初のタスクの前に、作業ブランチに最新の `develop` を取り込み（merge で行う。理由：push 済みの履歴を守るため）、次を照合する。理由：承認の後に `develop` が進み、plan の前提が成り立たなくなることがあるため。

- plan（規模 M は spec）の前提が、最新の `develop` で成り立つか
- 変える範囲（ファイルとモジュール）が、最新の `develop` と合うか
- 依存する spec と部品の状態
- tasks が、承認の後に変わった規則（本書など）に合うか
- 並行する spec の変えるファイル（plan と tasks。規模 M は spec の tasks）との重なりが、spec の確定の後に増えていないか。増えていれば、実装の順序を再検討する

差があれば、plan（規模 M は spec）と tasks を直す（文書が先）。

- 設計が変わるときは、plan と tasks の確認（規模 M は spec の確認）で利用者に再度確認する。設計が変わらない直し（パスの修正、依存する spec の完了の反映、タスクの順序の変更）は、確認を待たない（第 5.2 節）。
- 承認の直後に実装を始めるときも行う。`develop` が進んでいなければ「差なし」。
- 結果（差の有無と直したもの）は、実装の開始のコメントとして追跡の issue に書く。

### 5.7 マージの許可と後片付け

利用者の許可が必要なマージと操作は、[AGENTS.md](../../AGENTS.md) の Git の表のとおり。それ以外は、CI が全て通り未解決の高・必須が 0 なら、issue 担当のセッションがマージする（[エージェントの作業フロー](subagents.md) 第 4 節）。

spec 担当のセッションは、マージの許可と一緒にアーカイブの許可を求める。低の変更では、pull request の報告と一緒に求める。理由：別に質問すると確認が 1 回増えるため。アーカイブは、使うツールの機能で自分のセッションを一覧から外すこと。

利用者の許可が必要なマージの許可を求めるときは、許可の後に hook の確認の画面が表示されることも伝える。理由：利用者が確認の画面を hook の誤動作と取り違えて拒否することを防ぐため。利用者が遠隔操作のときは、許可の質問と選択肢を返答の文章に書き、確認の画面と「次の一歩」の表示欄だけに頼らない。理由：遠隔操作では、それらが見えないことがあるため。

マージの前に `develop` を取り込むのは、衝突があるときか、`develop` が同じファイルを変えたときだけ。承認の後の取り込みは、衝突がなく CI が通ったときだけ。そのときは、差分を利用者に示し、承認は求め直さず、取り込みの後の head の commit を指定してマージする（[エージェントの作業フロー](subagents.md) 第 4 節）。

作業ブランチ（リモート）は自動で削除される（[ブランチとリリース](../guides/branches.md) 第 3.4 節）ので、削除しない。マージの後（自分でマージしたとき、または issue 担当から知らせを受けたとき）、spec 担当のセッションが次を行う。

- 追跡の issue に完了を記録する。マージで閉じなかった扱った issue があれば閉じる（通常は本文の `Closes` で閉じる）。
- 振り返りを行う（skill `agent-retro`）。アーカイブの許可によらず、作業ツリーの削除の前に行う（tasks を読むため）。
- その spec の記録（メインの作業ツリーの `/.local/review/`、`impl/`、`pr/` の、その spec のもの）を削除する（[開発環境の起動](../guides/setup.md) 第 10 節）。
- スロットを解除してから、作業ツリーとローカルの作業ブランチを削除する（skill `local-dev`。自分が動いている作業ツリーの削除も同じ）。
- アーカイブの許可を得たときは、最後に自分をアーカイブする。許可がなければ、セッションを残す。できないときは skill `sessions` に従う。

## 6. 完了の定義

### 6.1 `develop` に入れる条件

次の 3 つを満たしたものだけを `develop` に入れる。

- CI が通る。
- 作業ブランチで手動の確認を終えた。
- 文書を更新した。

### 6.2 公開を遅らせたい機能

公開を遅らせたい機能は、設定のフラグで無効にする。
