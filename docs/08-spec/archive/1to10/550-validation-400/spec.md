# Spec 550：入力の誤りが 500 や誤った 400 になる漏れを修正する

種類：整理　規模：M　ステータス：確定

## 背景と目的

管理 API と店舗 API の入力の誤りのうち、次のものが 400 にならず 500 になる、または誤った 400 になる。どれも小さな修正なので、1 つの spec で扱う。

- 一覧の要素の null（#480）：契約の一覧の要素に null を拒む制約がなく、Controller の変換で例外になり 500 になる。
- 1 マイクロ秒未満の長さの税率の適用期間（#519）：domain はナノ秒で前後を判定し、DB はマイクロ秒に丸めて保存する。丸めた後に開始と終了が同じになると、DB の CHECK 制約の違反で 500 になる。
- 在庫の調整と引当の 4 つの漏れと、上限を超えた在庫を減らす調整のエラーの種類（#520 の本文とコメント）。

消費者・運営者に見える振る舞いは、不具合の修正の分だけ変わる（DN-550-1）。追跡の issue は #550（組の issue）。sub-issue は #480、#519、#520。#544（リリースの前の整理）の段階 3 の線 C の最初である。

## スコープ

| 含める | 含めない |
|--------|----------|
| 契約の全てのリクエストの一覧（本文とクエリー）の要素の null を 400 にすること | 画面の入力欄の文字数の数え方 |
| API の日時の入力をマイクロ秒に切り捨てること（税率の適用期間と、商品の公開期間） | 契約の上限の値、AC の値の変更 |
| 文字の長さの形の検証を、domain と同じ code point の数え方にすること（契約の全ての文字の項目） | DB の列の型の変更 |
| 在庫の注文に由来する調整の符号、引当の数量、運営者の氏名の長さ、上限を超えた在庫を減らす調整のエラー | |
| 関係する設計・機能仕様・規則の文書の修正 | |

決定（issue 担当のセッションが利用者に代わって 2026-11-19 に確認した）：

- 規模：M とする（特例）。判定の表では、2 つ以上のモジュール（catalog・tax・inventory・order と共通）にまたがり、店舗 API の契約の記述を 1 か所変えるので L に当たる。
  - 理由：どの修正も独立した小さな修正で、モジュールをまたぐ設計の決定は、この spec の決定に書く。plan に書く中身（API と AC の対応、実装の順序の設計）がない。前例は spec 548（M の整理で、決定を spec に書いた）である。
- 決定 1（一覧の要素の null）：生成の設定で、リクエストの一覧の要素に null を拒む制約を付ける。
  - 設定は全ての一覧の要素に付き、契約で要素を nullable にした一覧には付かないことを、試しの生成で確認した。
  - 要素の null は、今の入力の検証のエラー（400）になる。
  - 店舗 API の注文手続きの開始の、確認した注文の ID の一覧は、要素の null を許す今の振る舞いを保つ（AC-406-1：null の要素を含むなら、確認していないものとして扱う）。契約で要素を nullable と書く。今の振る舞いを契約に書くだけで、振る舞いは変えない。
  - 対象は、決定の後の表の 9 つの一覧（8 つの操作）である。店舗の確認した注文の ID の一覧は対象外である。
  - 理由：1 か所の設定で、契約の全ての一覧と、後から加える一覧に反映されるため。Controller ごとの検査では、同じ検査を全ての一覧に書く必要があり、加えた一覧で漏れる。
- 決定 2（日時の精度）：API の日時の入力を、アプリの日時に変える共通の変換で、マイクロ秒に切り捨てる。
  - 税率の適用期間と、商品の公開期間の両方に反映される。どちらも同じ変換を通り、DB に「開始 < 終了」の CHECK 制約がある。#519 は税率だけを挙げているが、商品の公開期間も同じ原因で 500 になる。
  - 切り捨てた後に開始と終了が同じなら、今の domain の検査で、業務のエラー（400）になる。エラーの種類は税率と商品で別である。
  - 隣り合う税率の重複・途切れの判定（AC-3）も、切り捨てた値で行う。マイクロ秒未満だけ重なる・途切れる一覧は、切り捨てた値でつながるので受け付ける（spec の最後のレビューで分かった）。
  - 理由：DB の精度に合わせると、domain が判定する値と保存する値が同じになり、判定と制約が食い違わないため。
  - 採らない案：domain でマイクロ秒未満の日時を拒否する案は、外部から来た日時の精度を利用者に意識させ、入口が増えるたびに同じ検査が必要になるため採らない。
- 決定 3（文字の長さの数え方）：契約の文字の長さの制約（生成した `@Size` の文字の項目。一覧の要素の文字を含む）を、code point で数える。
  - やり方：共通のクラスに、文字列の長さの制約を code point で数える検証の実装を置き、Bean Validation の標準の仕組みで登録する。
  - Hibernate Validator は、文字列の型だけを対象にする実装を、文字の並び全般を対象にする標準の実装より優先して選ぶ。この選び方は最初のテストで確認し、確認できなければ作業を停止して報告する。
  - 理由：書き方の規則（`backend-coding.md` の「形の検証は presentation、業務の規則は domain」）は、契約の制約とドメインの上限を一致させ、長さを code point で数えると決めている。今は、契約の検証が UTF-16 の長さで数えるので、サロゲートペアの文字を含む値が、ドメインの上限以内でも 400 になる。在庫の調整のメモ（#520 の 1）だけでなく、商品名・説明・軸・カテゴリ名・税区分の名前・配送先の氏名と住所・キャンセルの理由も同じである。
  - 採らない案（テンプレート）：生成のテンプレートを置き換える案は採らない。一覧の要素の制約は生成器のコードで作られ、テンプレートでは変えられない。生成器を上げるたびに、テンプレートとの差の確認も必要になる。
  - 採らない案（契約の上限）：契約の上限を UTF-16 の数に書き換える案は採らない。契約の上限が業務の上限と違う値になり、画面が契約の値で上限を表示しているため。
  - DB の列は文字（code point）で数えるので、変えない。
- 決定 4（注文に由来する調整の符号。#520 の 2）：注文に由来する調整を作るとき、理由が「注文」なら増減量が負、「注文のキャンセル」なら正であることを検査し、合わなければ前提違反の例外にする。
  - 理由：呼び出し元は在庫のモジュールのサービスだけで、外部の入力から起きない。理由と符号の組み合わせが合わないのは、呼び出し元の誤りのため。同じメソッドの「理由が注文に由来しない」の検査と同じ扱いである。
- 決定 5（引当の数量。#520 の 3）：モジュールの API の引当・減算・戻しで、数量が 0 以下の品目があれば、前提違反の例外にする。在庫と引当の数は変えない。
  - 今は、引当は DB の CHECK 制約の違反（想定外のエラー）になり、減算と戻しの数量 0 は業務のエラーになる。3 つをそろえる。
  - 理由：数量は注文のモジュールが、検証した後のカートと注文の明細の数量（1 以上）で渡す。0 以下は呼び出し元の誤りで、利用者に返す業務のエラーではないため。
  - モジュールの API の説明（Javadoc）の例外の記述を合わせる。
- 決定 6（運営者の氏名の長さ。#520 の 4）：token から運営者を読むとき、姓と名を連結した氏名を、写しの列の長さ（255 文字、code point）に切り詰める。切り詰める長さは、1 か所の定数にする。
  - 運営者の氏名の写しを持つ列は、在庫の調整の履歴、注文のキャンセルの判断をした運営者、注文のキャンセルをした運営者の 3 つで、どれも 255 文字の列である。注文のキャンセルも 500 になるので、この修正に含める。
  - 理由：氏名は表示のための写しで、255 文字を超える部分を落としても、運営者 ID で本人を特定できるため。
  - 採らない案（列を広げる）：DB の構造の変更（2 つのモジュールのマイグレーション）と利用者の確認が必要になるため採らない。
  - 採らない案（IdP の上限に頼り、切り詰めない）：IdP の上限（Keycloak の既定は、姓と名がそれぞれ 255 文字まで）に頼る案は、連結した氏名が 255 文字を超えうるため採らない。
- 決定 7（上限を超えた在庫を減らす調整。#520 のコメント）：上限の超過のエラーを返す（#520 のコメントの案 2）。減らす調整にも上限を適用する今の更新の条件を保ち、更新されなかった理由を選ぶ処理で、減らす調整でも「今の在庫数 ＋ 増減量」が上限を超えれば、上限の超過のエラー（400）を返す。
  - 理由：AC-42 と機能仕様は「運営者の調整の後の在庫数が 1,000,000 以下」と書いており、その文のとおりなら、上限を超えたままの在庫への減らす調整は拒否し、エラーの種類だけが誤っている。AC の文を変えずに修正できる。
  - 機能仕様の「在庫と在庫調整」の、減らす調整の手順の文（今は「在庫の有無を確認し、あれば 400、なければ 404」）を、上限を超えるときの 400 を含めて書き換える。AC は変えない。
  - 採らない案（在庫を増やす調整にだけ上限を適用する。#520 のコメントの案 1）：AC-42 の文を変えるため、機能の spec で扱う（Non-goals）。
- 決定 8（文書）：次の 4 点を修正する。
  - 書き方の規則（`backend-coding.md` の「形の検証は presentation、業務の規則は domain」）に、次の 2 点を書く。
    - 決定 1：一覧の要素の null は生成の設定で拒否し、null を許す一覧は契約で nullable と書く。
    - 決定 3：契約の長さの検証も code point で数える。
  - 機能仕様（在庫）の減らす調整の手順の文（決定 7）を修正する。
  - 在庫・税・商品の機能仕様と設計の文書に、今回の修正と食い違う記述があれば修正する（実装のときに検索する）。
  - 運営者の氏名の写しの切り詰め（決定 6）を、バックエンドのアーキテクチャの「認証・認可」の、運営者の ID と氏名の写しの箇条に書く。

## 目的と完了条件

### DS-550-1 入力の誤りが 400 になる（D / P1）

- **DC-550-1** 決定 1 の表の管理 API の一覧（8 つの操作の 9 つ）に、要素の null を送ると、400（入力の検証のエラー）になることを、統合テストで確認している。
- **DC-550-2** 店舗 API の注文手続きの開始が、要素の null を含む一覧を今と同じく扱う（AC-406-1 のテストが通る）。
- **DC-550-3** 税率の一覧の置き換えと、商品の公開期間の変更に、開始と終了の差が 1 マイクロ秒未満の期間を送ると、業務のエラー（400）になる。税率と商品が変わらないことも、統合テストで確認している。
- **DC-550-4** 在庫の調整のメモに、code point では上限以内で UTF-16 では上限を超える文字（サロゲートペアを含む）を送ると受け付ける。上限を 1 文字超えると 400 になる。どちらも統合テストで確認している。
- **DC-550-5** 文字の長さの検証の実装が、code point で数えることを、単体テストで確認している。他の文字の項目は同じ実装を通るので、項目ごとのテストは加えない。

### DS-550-2 在庫の前提違反と上限のエラー、運営者の氏名の長さが正しく扱われる（D / P1）

- **DC-550-6** 注文に由来する調整で、理由と増減量の符号が合わないと例外になることを、単体テストで確認している。
- **DC-550-7** 引当・減算・戻しで、数量 0 と負の品目があると例外になり、在庫と引当が変わらないことを、テストで確認している。
- **DC-550-8** 255 文字を超える氏名の運営者が在庫を調整すると成功し、履歴の氏名が 255 文字に切り詰められることを、テストで確認している。
- **DC-550-9** 在庫が上限を超えている状態（上限にし、注文で減らし、運営者が増やし、キャンセルで戻して作る）で、運営者が上限を超えたままになる量を減らすと、上限の超過のエラー（400）になる。上限以下になる量なら成功する。どちらも統合テストで確認している。更新されなかった理由を選ぶ処理の単体テストにも、減らす調整で上限を超える場合を加えている。

### DS-550-3 文書と検査（D / P1）

- **DC-550-10** 書き方の規則・機能仕様・設計の文書が、決定 8 の形になっている。
- **DC-550-11** `./gradlew check` が通る。契約から生成した型が変わるので、フロントの検査も通る。

## 非機能要件

- **DN-550-1** 消費者・運営者に見える振る舞いを変えない。例外は、DN-550-4 の後の表の 7 件である。理由：レビューで見つけた不具合の修正のため（[開発の進め方](../../../05-開発規則/workflow.md)の「コードと文書の食い違い」）。前例は spec 548 の DN-548-1 である。
- **DN-550-2** 例外の修正は、テストを先に書いて失敗（レッド）を確認してから修正する。
- **DN-550-3** API の契約の振る舞い、DB の構造、AC を変えない。契約の記述の変更は、決定 1 の 1 か所だけである。
- **DN-550-4** アーカイブした spec を変えない。

DN-550-1 の例外は、次の表のとおり。

| 修正 | 今 | 修正した後 |
|------|-----|------------|
| リクエストの一覧の要素の null（決定 1 の表の一覧） | 500 | 400 |
| 1 マイクロ秒未満の差の、税率の適用期間と商品の公開期間 | 500（丸めた後に同じになるとき）、成功（丸めた後に異なるとき） | 業務のエラーの 400 |
| 隣り合う税率の終了と開始の、マイクロ秒未満の重複・途切れ | 400（重複・途切れ） | 切り捨てた値でつながるので受け付ける |
| マイクロ秒未満の日時の保存 | 四捨五入 | 切り捨て |
| code point では上限以内で、UTF-16 では上限を超える文字 | 400 | 受け付ける |
| 氏名が 255 文字を超える運営者の、在庫の調整と注文のキャンセル | 500 | 成功し、氏名の写しを切り詰める |
| 上限を超えた在庫を、上限を超えたままの値に減らす運営者の調整 | 400（在庫不足） | 400（上限の超過） |

※ 引当・減算・戻しの数量（決定 5）と注文に由来する調整の符号（決定 4）は、モジュールの中の呼び出しだけで起き、利用者から起こせないので、表に入れない。
