共通の決定：

- 危険度は高（spec の冒頭）。マージは利用者が許可する。
- レビューの profile は「厚め」で、issue 担当のセッションが決めた（週の使用量 5%）。危険度が高いので、段階の最後の重要な観点のレビューは高性能で行う。

- 実装は実装役（汎用）に 1 タスクずつ任せる。文書の本文は、spec 担当が日本語の要点を書き、実装役（汎用、日本語だけの文脈）が書く。spec 担当はコードを書かない。
- 試作の commit はそのまま取り込まない。実装役は、参照用の作業ツリーのファイルを材料にし、本書の決定と、試作の自己レビューの指摘を反映して書く。
- 1 タスクを 1 commit にする。例外は、検査の script のテストと実装である（[開発の進め方](../../05-開発規則/workflow.md)の「循環」）。`[テスト]` はレッドの確認まで行い、実装と同じ commit に入れる。
- push は段階の最後に行う。draft の pull request は、spec の最後のレビューの後に作る（[開発の進め方](../../05-開発規則/workflow.md)の「規模」）。
- 段階は番号の順に進める。段階 3 の構造の検査は、本 spec の spec・plan・tasks 自身も検査する。そのため、段階 1・2 で tasks を追加するときも、雛形の形を守る。
- DN-321-1〜3 は、spec の最後のレビューで、`develop` との差分のファイルの一覧を確認する（本番のコード、アーカイブ、注文以外の ③ がない）。
- 並行する他の spec はない（issue 担当の知らせ）。実装を始める前の照合で、`develop` を取り込み、変えるファイルの重なりを再度照合する。

| 検出する | 整理の spec が AC・US・BR・NFR を定義する。機能の spec が DS・DC・DN を定義する |
| 検出する | ID の連番を 0 で埋める（`DC-321-01`） |
| 検出する | 閉じていないコードブロックがある（後ろの見出しと ID を読めないため） |
| 検出しない | チルダと 4 つ以上のバッククォートのコードブロックの中の見出しと ID |
| 検出しない | 1 行のコード（`` `DC-321-99` ``）の中の ID |
| 検出しない | 表の中の太字の ID、箇条の途中の太字の ID（定義とみなさない。参照として読む） |
| 検出しない | MVP の spec を指す「MVP 012」、MVP と古い形式のタスクの ID（`T011-01-01`、`T301`） |
| 検出しない | 日付、commit の ID、issue の番号、`TDD`、語の途中の `AC-`（`MAC-321-1`） |
| 検出しない | 番号が文字の記号の ID（`DC-n`、`AC-<番号>-1`） |
| 検出しない | 区切りも助詞も続かない列挙の数（`2 段階`、`30 秒`、日付）。範囲の端（`〜` の後ろの数）は、数字・`-`・`.` が続かなければ常に読む |
| 検出しない | `###` の見出し（名前と順を見ない）。3 行目の後ろの `危険度：高` の行 |
| 検出しない | 見本の番号 900 の ID の参照 |

- 次は対象にしない。理由：判定は誤りの防止で、意図して作った回避か、このリポジトリで書いていない形のため。
  - ID の接頭辞の全角・小文字、区切りの全角のハイフン（ID として読まない）
  - 引用（`>`）の中も区別せず、通常の行として読む
  - タスクの依存・範囲の箇条があるか（書き方の規則で、レビューで見る）
- 例はレビュー役（汎用）が挙げた 103 件から、spec 担当が採否を決めた（T321-03-03）。
