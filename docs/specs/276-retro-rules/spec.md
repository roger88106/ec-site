# Spec 276：整理の第 1 段の振り返りの 4 件を skill と規則に入れる

ステータス：確定

## 1. 背景と目的

milestone「整理の段階」の spec である。追跡の issue は [#276](https://github.com/roger88106/ec-site/issues/276) で、sub-issue は次の 5 つである。作業ブランチは `276-retro-rules` である。整理の spec なので、AC、API、データベースは変えない。規模は M で、2026-10-29 に利用者が承認した。変えるファイルが `.claude/` と `docs/rules/` の下にあるので、経路の判定（`scripts/ci/risk.mjs`）で危険度は高になる。マージには利用者の許可が必要である。

| issue | 内容 |
|-------|------|
| [#271](https://github.com/roger88106/ec-site/issues/271) | auto mode の判定・hook・検査に止められる書き方と避け方を skill にまとめる |
| [#272](https://github.com/roger88106/ec-site/issues/272) | 作業ツリーのセッションが設定・定義・skill を読む場所と効く時点を、動かして確認して skill に書く |
| [#273](https://github.com/roger88106/ec-site/issues/273) | 高の pull request のマージの許可を求めるとき、hook の確認の画面と遠隔操作での扱いを書き添える |
| [#274](https://github.com/roger88106/ec-site/issues/274) | 同じ種類の指摘が続く審査で、禁止の一覧から許可の一覧へ前提を変える案を出す規則を加える |
| [#277](https://github.com/roger88106/ec-site/issues/277) | 利用者の確認に出す文書と、issue の本文を、出す前に校閲役に読ませる |

#271〜#274 は、整理の第 1 段の振り返り（spec 245、246、247 と issue 担当のセッション）で、2 つ以上のセッションに出た問題である。どれも振る舞いを変えない skill と規則の修正で、変える文書が重なるので、1 つの spec で扱う。第 2 段の文書の棚卸しの前に終える。#277 は、本 spec の確認で利用者が造語に気づき、加えた（2026-10-29）。

### 本 spec の用語

| 用語 | 意味 |
|------|------|
| auto mode の判定 | Claude Code が、エージェントのコマンドを実行してよいかを自動で決める判定 |
| hook | `settings.json` と `settings.local.json` の hook（agent-guard、backslash-guard） |
| 検査 | git の hook（commit-msg、pre-commit）が実行する、日本語の書き方と中国語の混入の検査 |
| メインの作業ツリー | clone した元のディレクトリ（`git worktree add` で作った作業ツリーでないもの） |
| アプリの作業ツリー | Claude のデスクトップアプリがセッションのために作った作業ツリー |
| 手動の作業ツリー | セッションが `git worktree add` で作り、絶対パスで作業する作業ツリー（セッションはメインの作業ツリーで起動している） |
| 誤りの防止 | 誤って書いたコマンドを拒否する判定。意図して作った回避は、拒否する対象にしない |
| 回避の防止 | 意図して作った回避も拒否する判定 |

### 今の記述と振り返りの事実

#### #272 作業ツリーのセッションが読むもの（今の記述）

| 対象 | 今の記述 | 記述の根拠 |

- 確認していない組がある：アプリの作業ツリーの `settings.json`・`agents/`・`skills/`、手動の作業ツリーの全て、`claude -p` を作業ツリーで起動したとき。
- 起動したディレクトリによって、読む設定・定義・skill が変わる可能性がある。アプリの作業ツリーのセッションと、メインの作業ツリーで起動したセッションは、新しいセッションを起動しないと確認できない。利用者が遠隔操作のときは、新しいセッションを起動できないことがある。

#### #273 マージの許可の箇所（今の記述）

- AGENTS.md の Git の表は、許可が必要なマージで hook が確認の画面を表示することを書いている。許可を求めるときに、それを利用者に伝えることは書いていない。
- [開発の進め方](../../rules/workflow.md) 第 5.7 節は、許可を求める時点（アーカイブの許可と一緒に）だけを書いている。
- 遠隔操作（Remote Control）では、確認の画面とアプリの「次の一歩」の表示欄が見えないことがある。PR #269 のマージで、利用者は確認の画面を hook の誤動作と思って拒否した。

#### #274 収束の規則（今の記述）

- skill `review` の convergence.md は、上限（3 回）と、同じ種類の指摘（まとめて検索して修正する）を書いている。修正の前提を変える案を出す時点は書いていない。
- 判定の script（hook、CI の検査）を作る spec の書き方の規則はない。plan の型のファイルもない。
- PR #268 の審査は 6 回になり、高の数は 4→2→2→1→1→0 だった。禁止する形の一覧に回避の形を 1 つずつ加え、最後に許可する形の一覧に替えて収束した。

#### 「判定器」の語（校閲の結果、2026-10-29）

- PR #275 が「判定器」の語を `develop` に入れた。指す対象は、hook・CI の検査の script・認証・支払・権限の経路のうちの一部である。最初に確認に出した本 spec は、同じ語を「コマンドの実行を拒否するもの」の意味で使った。
- 校閲と利用者の決定で、「判定器」は使わない。日本語の技術文書で通じにくく、意味もそろわないためである。コマンドを拒否するものは、総称を作らず「auto mode の判定・hook・検査」と書く。`scripts/ci/` の、CI を失敗させる script は「CI の検査の script」と書く。
- リポジトリ全体で使う語（「無記憶」「弾」「段」「台帳」「主のチェックアウト」「効く」など）は、本 spec では変えない。issue #267 と第 4 段の日本語の整理で扱う。

#### #277 利用者の確認の前のレビュー（今の記述）

- skill `review` の文書のレビュー（手順 8）は、「spec・plan・tasks を書き終えたときと、spec の最後」に行うと書いている（docs-review.md の手順 2）。使う場面の表には、spec・plan・tasks を書き終えたときの行がない。
- 校閲役（手順 9）が読むのは、最後のレビューと pull request の前のレビューの差分だけである。利用者の確認の前には読まない。
- [開発の進め方](../../rules/workflow.md) 第 5.1 節は、確認の対象だけを書き、出す前に行うことを書いていない。
- issue 担当のセッションが書く issue の本文とコメントは、どのレビューも通らない。規模 S では、issue の本文が spec の役割を持つ。
- 「判定器」は、issue #265 のコメントで使われ始め、spec 265（PR #275）が規則に取り入れた。最初に確認に出した本 spec も、造語（「判定器」と、今の「誤りの防止」「回避の防止」に当たる「護り」「境界」）を含んでいた。

## 3. 目的と完了条件

完了条件は、第 6 節の推奨の案で書いた。

### DS-276-1 auto mode の判定・hook・検査に止められる書き方と避け方を skill に書く（D / P1）

- **DC-276-1** skill `local-dev` の「シェルと Git の落とし穴」に、#271 の表（第 1 節）の全ての書き方がある。各書き方に、止めるもの（auto mode の判定、hook、検査の名前）と避け方を書く。避け方は少なくとも次を含む。
  - Markdown の表（`\|`）を含む追記は、Edit で書く。
  - GitHub の状態を変える `gh` の操作（pull request の編集・ready・マージ、issue の編集）は、1 つのコマンドに 1 つにする。
  - `cd` で作業ディレクトリを移さず、`git -C` と絶対パスを使う。
- **DC-276-2** skill `sessions` のツールの注が、`claude -p` の起動の形（`--permission-mode default` と、`--allowedTools` で許すツール）と、`bypassPermissions` を使わないことを書いている。
- **DC-276-3** skill `zh-mixing` に、次の 2 つがある。skill `local-dev` の DC-276-1 の該当の行から、この箇所を指す。
  - コミットメッセージと spec で検査に見つかりやすい語の一覧（層 1 の `scripts/ci/ja-text.json`）への参照
  - 利用者の中国語の言葉は、日本語に訳して書くこと

### DS-276-2 作業ツリーのセッションが読む場所と効く時点を、動かして確認して表にする（D / P1）

- **DC-276-4** skill `sessions` のツールの注に、次の表がある。
  - 行：起動の形。アプリの作業ツリーのセッション、メインの作業ツリーで起動して手動の作業ツリーで作業するセッション、作業ツリーで起動した `claude -p` の 3 つ。
  - 列：`.claude/settings.json`・`settings.local.json`・`.claude/agents/`・`.claude/skills/` の読む場所と、変更が効く時点。
- **DC-276-5** DC-276-4 の表の各欄は、動かして確認した結果（確認した日と方法）である。確認していない欄は「未確認」と書き、第 7 節の T276-01-09 で、利用者が戻った後に確認する。
- **DC-276-6** DC-276-4 の表の後に、定義・skill・hook を変える spec の確認の手順がある。マージの前に、その作業ツリーで新しいセッションか `claude -p` を起動し、変更が読まれることを確認する。
- **DC-276-7** 次の 4 か所の、作業ツリーのセッションが読むものの記述が、DC-276-4 の表と食い違わない。重なる記述は表を指す形にする。
  - AGENTS.md の環境の節
  - [エージェントの作業フロー](../../rules/subagents.md) 第 4 節
  - skill `sessions` の「マージの後」
  - skill `local-dev` の「手元の hook の設定」
- **DC-276-8** skill `review` の docs-review.md の照合の項目に、次がある。spec の第 1 節の環境の前提が、文書の記述によるか、動かして確認したものかを書き分けているか。

### DS-276-3 危険度が高い pull request のマージで許可を求めるときに、伝えることを決める（D / P2）

- **DC-276-9** [開発の進め方](../../rules/workflow.md) 第 5.7 節が、次を書いている。利用者の許可が必要なマージの許可を求めるときは、許可の後に hook の確認の画面が表示されることも伝える。
- **DC-276-10** 同じ箇所が、次を書いている。利用者が遠隔操作のときは、許可の質問と選択肢を返答の文章に書く。確認の画面と「次の一歩」の表示欄だけに頼らない。
- **DC-276-11** skill `sessions` のツールの注が、確認の画面を表示する hook（agent-guard）と、遠隔操作では確認の画面が見えないことがあることを書いている。

### DS-276-4 同じ種類の指摘が続くときに前提を変える規則と、判定の spec の書き方を加える（D / P2）

- **DC-276-12** skill `review` の convergence.md に、次の行がある。同じ種類の指摘（同じ判定の別の書き方）が 2 回続いたら、修正の前提を変える案を出す。変え方は、禁止の一覧から許可の一覧へ替えるか、対象の外（既知の制限）とするかである。
- **DC-276-13** [開発の進め方](../../rules/workflow.md) 第 1.4 節に、入力の形を判定する script（hook、CI の検査）を作る spec の書き方として、次の 2 つがある。
  - 入力の形の判定は、許可する形の一覧で書く。
  - 判定が誤りの防止か回避の防止かを、DC で先に決める。
- **DC-276-14** skill `review` の prompts.md の指示のひな形に、次がある。誤りの防止の spec では、意図して作った回避の形を高にしない。

### DS-276-5 `develop` の文書の「判定器」の語を書き換える（D / P2）

- **DC-276-15** アーカイブした spec 以外の文書と skill に、「判定器」の語がない。PR #275 で入った箇所（エージェントの作業フロー、調べた仕組みと実績、skill `review` の SKILL.md）は、「CI の検査の script」に書き換えている。

### DS-276-6 利用者の確認に出す文書と issue の本文を、出す前に校閲役に読ませる（#277）（D / P1）

- **DC-276-16** [開発の進め方](../../rules/workflow.md) 第 5.1 節と、skill `review` の使う場面の表が、次を書いている。規模 M の spec と、規模 L の spec・plan・tasks は、文書のレビュー（手順 8）と校閲役（手順 9）を通してから、利用者の確認に出す。
- **DC-276-17** skill `sessions` の issue 担当のセッションの役割が、次を書いている。issue の起票とコメントの投稿の前に、本文を校閲役に読ませる。同時に書いた複数の本文は、1 回にまとめて渡す。
- **DC-276-18** skill `review` の docs-review.md の校閲役の手順が、次を書いている。対象に DC-276-16・17 の文書を含める。リポジトリ全体で使う語を変える指摘は、その文書では修正せず、issue #267 に集める。

## 4. 守る制約

- **DN-276-1** 振る舞い、API、データベース、AC、script を変えない。変えるのは、文書と skill だけである。
- **DN-276-2** 確認のために、メインの作業ツリーの `.claude/`（設定、定義、skill）と `/.local/` を変えない。確認は、本 spec の作業ツリーか、スクラッチパッドに作った確認用の Git のリポジトリで行う。理由：メインの作業ツリーは issue 担当と他のセッションが使うため。
- **DN-276-3** 確認のための一時の設定・定義・skill は、確認の後に削除し、commit しない。
- **DN-276-4** `scripts/ci/check-all.sh` と CI が通る。

## 5. Non-goals

| 項目 | 理由 |
|------|------|
| hook（agent-guard、backslash-guard）と検査（ja-text、zh-mixing）の判定を変える | 本 spec は避け方を書くだけで、振る舞いを変えない（DN-276-1） |
| 既存の判定の script を許可の一覧に書き直す | DC-276-13 は今後の spec の書き方。既存の script を変えるなら別の issue にする |
| Claude Code の文書の記述の誤りを報告する | 本 spec の範囲の外 |
| plan の型のファイルを作る | 型のファイルはなく、規則は開発の進め方 第 1.4 節に置く（決めたこと 3） |
