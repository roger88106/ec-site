# Spec 184：フロントのテストの書き方の残りをそろえる（第 2 回）

ステータス：確定

## 1. 背景と目的

spec 157 で、フロント（管理画面、店舗画面、共有のパッケージ）のテストを[テストの書き方](../../rules/test-writing.md)と[フロントの書き方](../../rules/frontend-coding.md)にそろえた。店舗画面の HTML に描画するテストの書き換えと、フォームのテストの React の差し替えは範囲から外し（spec 157 の Non-goals）、DC に当たらない推奨の指摘（spec 157 の plan 第 7 節）と最後のレビューの指摘を、#171〜#173 に起票した。本 spec はその残りをそろえる。

| 項目 | 値 |
|------|----|
| 追跡の issue | [#184](https://github.com/roger88106/ec-site/issues/184) |
| 作業ブランチ | `184-frontend-tests` |

扱う issue は次のとおり。

| issue | 扱う部分 |
|-------|----------|
| #171 | 全体（店舗画面のテストの確認の書き方、jest-dom、フォームのコンポーネントの分割） |
| #172 | 全体（テストの構成と書き方の残り） |
| #173 | 全体（テストの補助とデータの重複の残り） |

出発点は、spec 157 の Non-goals と plan 第 7 節、spec 157 のテストのレビューの結果（`/.local/review/202610231200-157-frontend-tests/`）、spec 157 の起票の案（PR #170 の本文の案 A〜C）である。spec を書く前に、今の `develop` で該当の箇所を確認した（2026-10-24）。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。

## 2. 用語

| 用語 | 意味 |
|------|------|
| HTML に描画するテスト | 部品を `renderToStaticMarkup`（店舗画面の補助の `renderMarkup`）で HTML の文字にし、文字の一致や正規表現、開始タグの属性（補助の `findTag`）で確認するテスト |
| DOM に読み込む | 描画した結果を jsdom の文書に置き、Testing Library の問い合わせ（役割と名前、見出し）で要素を探せるようにすること |
| jest-dom | DOM の要素の状態を確認する照合の関数（`toBeDisabled`、`toHaveAttribute`、`toHaveAccessibleName` など）を Vitest に加えるライブラリ。管理画面は使っている |
| 結果を props で受けるコンポーネント | サーバーアクションの結果（`useActionState` の状態）を props で受け取り、表示だけを行うコンポーネント。サーバーアクションを呼ぶ側と分ける |

用語集に追加する語は、plan で決める。

## 4. 目的と完了条件

### DS-184-1 DOM に読み込んで探す（D / P1）

- **DC-184-1** 店舗画面と共有のパッケージのテストは、描画した HTML の文字を、文字の一致、正規表現、開始タグの属性で確認しない。描画した結果を DOM に読み込み、役割と名前（ない要素は見える文言、見出し）で探す（[テストの書き方](../../rules/test-writing.md) 第 4.1 節）。対象は、今 `renderMarkup` か `renderToStaticMarkup` を使う 19 ファイル（店舗画面 18、共有のパッケージ 1）である。
- **DC-184-2** サーバーコンポーネントとクライアントコンポーネントの初期表示は、今と同じく効果（`useEffect`）を実行しない描画で確認する。理由：サーバーで描画した最初の HTML を確認する、という今のテストの目的を変えないため。
- **DC-184-3** DC-184-1 で探す名前がない要素には、画面に支援技術向けの名前を追加する。見える文言は変えない。
- **DC-184-4** DC-184-1 の後に使わなくなった HTML の補助（`markup.ts` の `startTags`、`findTag` と、そのテスト）は削除する。
- **DC-184-5** [店舗画面の構成](../../design/apps/store.md) 第 7 節のテストの表と補助の表が、DC-184-1〜4、DC-184-8 の後の書き方と一致する。

### DS-184-2 jest-dom（D / P1）

- **DC-184-6** 店舗画面のテストで jest-dom を使える。設定は全てのテストに共通の setup に置く。
- **DC-184-7** 要素の状態と属性を、プロパティの値や `getAttribute` の比較で確認しない。jest-dom の照合の関数（`toBeDisabled`、`toBeEnabled`、`toHaveAttribute`、`toBeInTheDocument` など）で確認する。今は `ProductShowcase.test.tsx`、`VariantPicker.test.tsx`、`CancellationRequestForm.test.tsx` に 14 か所ある。

### DS-184-3 フォームのコンポーネントの分割（D / P1）

- **DC-184-8** 注文のフォーム（`OrderForm`）とカートに入れるフォーム（`AddToCartForm`）は、サーバーアクションを呼ぶコンポーネントと、結果を props で受けるコンポーネントに分ける。
- **DC-184-9** 2 つのフォームのテストは、React の関数（`useActionState`）を差し替えず、結果を props で受けるコンポーネントに結果を渡して確認する。`vi.mock('react')` がテストに残らない。
- **DC-184-10** 分割で、フォームの見える振る舞い（表示、エラーの出し方、送る内容）を変えない。送る内容は、今と同じくサーバーアクションのテストと E2E で確認する。

### DS-184-4 テストの構成と書き方（D / P2）

- **DC-184-11** 1 つのテストに複数の振る舞い（409 の検出、入力の保持、再読み込み、再保存）を詰めたテストを、振る舞いごとのテストに分ける。対象は、管理画面の商品の編集（3 つ）と税率（1 つ）である。分けた後も、もとのテストが確認していたことを全て確認する。
- **DC-184-12** テストの定数と変数の名前は、組み込みの名前（`URL` など）をシャドーイングしない。今は管理画面の 5 ファイルに `const URL` がある。
- **DC-184-13** テストとテストの間に空行を置く。
- **DC-184-14** hook のテストは、`renderHook` で hook を呼ぶ。今は変更をまとめる hook（`useMutationGroup`）のテストが、hook を直接呼んでいる。
- **DC-184-15** ファイルの選択は `user.upload` で、日時の入力（`datetime-local`）は 1 つのテストの補助で操作する。今は管理画面の商品の編集に `fireEvent` が混ざり、日時の入力の補助は税率のテストだけにある。
- **DC-184-16** 店舗画面のテストは、環境変数を `vi.stubEnv` で差し替える（`process.env` に直接代入しない）。現在の時刻の秒の計算は、テストの補助の 1 か所にする。ログインの状態は `signInAs` で作る。
- **DC-184-17** 偽の時計の後始末（`vi.useRealTimers`）を、各ファイルで繰り返さない。

### DS-184-5 テストの補助とデータ（D / P2）

- **DC-184-18** テストの補助にあるデータを、テストのファイルで再定義しない。今は、管理画面のレポートの条件の商品 ID、店舗画面の地域と注文のフォームの値、管理画面の商品の編集の値が残っている。
- **DC-184-19** 管理画面のログインの戻り先のテストは、共有のパッケージのテストと同じ確認を繰り返さず、管理画面に固有の振る舞いだけを確認する（spec 157 の DC-157-27 の店舗画面と同じ考え方）。
- **DC-184-20** 一覧のセルの補助と、ダウンロードの記録の補助は、想定した使い方（補助の TSDoc に書いたもの）の外で使われたときに、テストを失敗させるか、TSDoc に扱いを書く。対象は、行の見出しのセル、入れ子の表、ダウンロードでないリンクのクリックである。
- **DC-184-21** 支援技術向けの名前を、親と子に同じ値で重ねない。今は、カテゴリの木の項目（li）と行、商品の画像の項目（li）と画像に重なりがある。DN-184-1 のとおり、見える文言は変えない。
- **DC-184-22** 名前が似ていて区別しにくいテストの名前を、確認する振る舞いの違いが分かる名前にする。対象は、購入できない品目の小計のテストと、金額の内訳の 2 つの見た目の種類のテストである。

## 5. 非機能要件

- **DN-184-1** 運営者・消費者に見える振る舞いを変えない。DC-184-3、21 で変える支援技術向けの名前は、見える文言を変えない。DC-184-8 の分割は、コンポーネントの構成だけを変える。
- **DN-184-2** API の契約とデータベースの構造を変えない。
- **DN-184-3** AC を追加・変更しない。テストを書き換え、分け、移したときは、AC 一覧のテストの列を再生成する。
- **DN-184-4** テストを書き換えるときに、確認を弱めない。書き換えたテストは、一時的に実装か期待値を変更して、失敗しうることを確認する（[開発の進め方](../../rules/workflow.md) 第 2.1 節）。
- **DN-184-5** spec 17 のフロントのカバレッジの基準（行と分岐。[テストの書き方](../../rules/test-writing.md) 第 1.2 節）を下げない。下回ったら、残すテストで確認を補う。
- **DN-184-6** CI の検査の script（`scripts/ci/`）は変えない。同時に進む spec 183 が変える。本 spec で直す違反の一覧は第 6 節に書き、spec 183（#169）の検査の対象と合わせる。
- **DN-184-7** shadcn/ui の生成物は修正しない（[管理画面の構成](../../design/apps/admin.md) 第 2 節）。
- **DN-184-8** 並行の spec（181、182、183）と同じファイルを変更する箇所は、plan に挙げ、その spec に知らせる。

## 6. spec 183 の検査の対象と、本 spec で直す違反

spec 183 は、#169（spec 157 の起票の案 D を含む）で、テストの書き方の違反を見つける検査を加える。本 spec は、次の検査の違反を 0 件（例外は理由付きのものだけ）にする。0 件であることは、本 spec の中で `git grep` で確認する。数は 2026-10-24 の `develop` で数えた。

| 検査（#169） | 今の違反 | 本 spec の扱い |
|--------------|----------|----------------|
| 型を回避する変換（`as never`、`as unknown as`）で、理由のコメントがないもの | 違反は 0 件。理由のコメント付きの変換が `store/src/test/setup.ts` に 1 か所ある | 変えない（理由付きの例外として残る） |
| 探した結果を `toBeTruthy`・`toBeDefined` で確認する書き方 | 3 か所（`ActionError.test.tsx` 2、`PageLinks.test.tsx` 1。どれも `findTag` の結果） | DC-184-1、4 で修正する |
| HTML の属性の並びや要素に依存する正規表現・文字の一致 | 7 ファイル 14 か所（`PageLinks`、`CartMergeNoticeView`、`AddToCartForm`、`CategoryList`、`ListFilterForm`、`ProductCard`、`OrderForm` のテスト） | DC-184-1 で修正する |
| `getAllBy…(…)[n]` の並びのインデックス | 0 件 | なし |
| describe の名前が関数名だけ | 0 件 | なし |
| `ac-check` が `each` の表を読めない件 | テストのコードの違反でなく、検査の script の件 | spec 183 が扱う |

- 本 spec で加わる jest-dom の書き方（DC-184-7）と、プロパティや `getAttribute` の比較を見つける検査は、#169 の範囲にない。加えるかは spec 183 に知らせ、spec 183 が決める。

## 8. Open questions

2026-10-24 に、利用者が全て案 A に決めた。Open questions はない。

1. **規模**：店舗画面、管理画面、共有のパッケージにまたがり（2 つ以上のモジュール）、HTML に描画する 19 個のテストのファイル（DC-184-1）とフォームのコンポーネントを書き換える。
   - 案 A（採用）：規模 L（spec、plan、tasks）。[開発の進め方](../../rules/workflow.md) 第 4.2 節の「2 つ以上のモジュールにまたがる」に当たる。前の spec 157 も L だった。
   - 案 B：規模 M（spec に tasks の節を含める）。振る舞いを変えない整理で、項目は多いが、各項目の判断は小さい。
2. **DOM に読み込む方法**（DC-184-1、2）：
   - 案 A（採用）：今の `renderMarkup` で HTML にし、それを jsdom の文書に置いて、Testing Library の問い合わせで探す補助にする。効果を実行しない描画（DC-184-2）を保てる。サーバーコンポーネントのページのテストも同じ補助で書ける。
   - 案 B：Testing Library の `render` で jsdom に描画する（`renderInBrowser` と同じ）。描画の後に効果が実行されるので、初期表示でなく効果の後の表示を確認することになる。
3. **共有のパッケージの金額の内訳のテスト**（DC-184-1）：共有のパッケージで HTML に描画するテストは `AmountsSummary.test.tsx` の 1 ファイルだけで、共有のパッケージには jsdom と Testing Library がない。
   - 案 A（採用）：含める。共有のパッケージに jsdom、Testing Library、jest-dom を開発の依存として加え、店舗画面と同じ書き方にする。テストの書き方が 2 種類残らない。
   - 案 B：含めない。共有のパッケージは HTML の文字の確認のまま残し、見た目に依存する確認がないこと（spec 157 で直した）だけを保つ。
