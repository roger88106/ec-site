# MVP の完成までの一覧

spec 010 で MVP の機能がそろった。MVP を完成させるまでの整理を spec 011〜018 に分け、ここに順序と理由をまとめる。spec ごとの進み具合は [README の進捗](../../README.md#進捗)に書く。

spec の名前は、spec の文書を書くまで仮のもの。spec の文書ができたら、番号をリンクにする。

|------|------|------|--------------|------|

## 2. 並べた原則

1. ツール → テストの安全網 → 書き方の統一 → 振る舞いの変更、の順に行う。
2. 書き方の統一（013、014）は振る舞いを変えない。完了の条件は「既存のテスト（バックエンド、フロント、E2E）を変えずにすべて通る」。テストを変えないと通らない所は、振る舞いを変えているので、振る舞いを変える spec（主に 016）に移す。
3. テストの安全網（012）で足す・直すテストは、今のコードで通る（今の振る舞いを書いている）ことと、コードをわざと壊すと失敗することを確かめる。新しい振る舞いのテストは、その振る舞いを作る spec が TDD で書く。
4. 振る舞いを変える spec（015〜017）は、統一の後に行い、新しいコードを最初から統一した書き方で書く。

## 3. MVP の後に回した決定

| 項目 | 決める時 | 理由 |
|------|----------|------|
| spec の番号が 999 を超えたときの、spec とタスクの番号の付け方 | MVP の後の開発の進め方を決めるとき（**必ず決める**） | タスクの番号は桁を固定しないので 1000 を超えても書けるが、spec のディレクトリの番号は 3 桁で、並び順が崩れる |
| MVP の後の開発の進め方（今の仕様の単位、変更の単位、起票、ブランチの運用） | 1 → 10 の最初の大きな機能 | spec が増え続けると、今の仕様を探しにくい。最初の大きな機能で、別のブランチで試してから決める |
| AC のテストの漏れを、どの CI で失敗にするか | MVP の後の開発の進め方を決めるとき | 今は CI のすべての実行で失敗にする（CI の検査 第 3 節）。MVP の間は `develop` に直接 push し、spec の最後にまとめて push するため。作業ブランチから pull request で入れるようになったら、pull request と `develop`・`main` への push だけで失敗にし、作業ブランチの push では警告にする |
| 都道府県・市区町村のマスターデータの取得と更新（国の API）、郵便番号のマスターデータ（日本郵便） | 1 → 10 | 016 ではマスターデータの構造と最初のデータだけを作る。外部から取り込む仕組みは、デプロイの後に要る |
| デプロイ、依存の自動更新 | 1 → 10 | MVP はローカルと CI で動かすところまで |
| AC にテストがないと分かったもの、不安定なテスト | spec 012 | spec 011 で見つけた。一覧は次の表 |

spec 012 に回すテストの問題：

| 対象 | 問題 | 見つけた時 |
|------|------|------------|
| AC-90（注文番号を振り、カートを空にする） | テストのまとまり（`@Nested` のクラス）の名前にだけ書かれ、メソッドのテスト名にない。`ac-exclusions.json` で除いている。カートを空にする所は spec 007 の AC-147 で変わった | AC とテストの対応の検査を直したとき |
| 管理画面の `ProductCreatePage.test.tsx` の AC-15 | 店舗画面・管理画面のテストを続けて流したとき、Vitest の既定のタイムアウト（5 秒）で 1 回失敗した。単独で流すと通る | E2E のコードの lint を `check-frontend.sh` に足したとき |

どちらも spec 012 で直した（T012-03-01、T012-06-01）。
