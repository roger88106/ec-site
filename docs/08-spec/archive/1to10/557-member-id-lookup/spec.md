# Spec 557：会員 ID の照会と地域の照会を、毎回 DB に問い合わせない形にする

種類：整理　規模：M　ステータス：確定

## 背景と目的

#458 の main 全体の書き方と構成のレビューで挙がった、次の問題を解消する。

- #496 の 1：ログインした店舗の API のリクエストごとに、別の読み取り専用のトランザクションが始まる。IdP のアカウントの ID（token の subject）から会員 ID を求めるためだけである。この対応（アカウントの ID と会員 ID）は作った後に変わらず、会員の表の行を削除する処理はない（会員の削除も、統合テストの片付けもない）。
  - 会員 ID を求めるクラスの、ログインが任意の操作で使うメソッドは、カートの表示などの参照の操作でも会員を作る。名前からは書き込むことが分からない。
- #496 の 2：都道府県と市区町村はマイグレーションでしか変わらないのに、店舗の選択肢、レポートの表示（47 件）、注文の住所の確認のたびに DB に問い合わせる。地域のデータを変える取り込みの仕組みと管理 API はない（[地域モジュール](../../../../03-機能仕様/region.md)の「最初のデータ」）。郵便番号は件数が多いので DB のままにする。
- #539：token の会員の型は、IdP のアカウントの ID に null を許容する。それなのに、会員 ID を求めるクラスは null でないことを改めて確認している。型で前提を示す。

調べた今の振る舞い：店舗 API の token の検証は subject を必須にしていない。subject のない token は検証を通り、会員 ID を求める所の null の確認で NullPointerException になる。この例外は想定外のエラー（500）の応答になる。token の会員を直接読むのは注文の確定だけで、同じ操作で会員 ID も求める。このため、subject のない token は、会員 ID を求める全ての経路で 500 になる。

消費者・運営者に見える振る舞い、API の契約（OpenAPI）、DB の構造、AC は変えない。追跡の issue は #557（組の issue）。sub-issue は #496 と #539。#544（リリースの前の整理）の段階 3 の線 B の 4 番目（最後）である。

決定（issue 担当のセッションが利用者に代わって 2026-11-19 に確認した。全て推奨の案で承認）：

- 規模：M とする（[開発の進め方](../../../../05-開発規則/workflow.md)の「規模」の特例）。
  - 判定の表では、3 つのモジュール（共通、会員、地域）にまたがるので L に当たる。
  - M にする理由：API の契約と DB の構造を変えず、モジュールをまたぐ設計の決定がなく、それぞれのモジュールの中で閉じるため。前例は spec 552（規模 M の整理）。
- 決定 1（キャッシュのライブラリ）：Caffeine を直接使う。Spring のキャッシュの抽象は使わない。
  - Caffeine のバージョンは Spring Boot の BOM が管理し、ライセンスは Apache-2.0（[依存とライセンス](../../../../05-開発規則/licenses.md)の方針に合う）。
  - 退けた案：自前の件数の上限と期限を持つ Map。理由：依存は増えないが、件数の上限と期限の処理を自分で書いてテストする分のコードが増えるため。
- 決定 2（会員 ID のキャッシュ）：IdP のアカウントの ID から会員 ID への対応を、件数の上限と期限を付けてメモリに持つ。
  - キャッシュに入れるのは、会員が見つかったとき、または会員を作ったとき（作るトランザクションが確定した後）だけ。
  - キャッシュにあるときは、トランザクションを始めず、DB に問い合わせない。
  - 件数の上限と期限は設定にする。接頭辞は `ecsite.member.id-cache`、件数の上限の既定は 10,000（1 以上）、期限の既定は 1 時間。
  - 設定の型は、[バックエンドの書き方](../../../../05-開発規則/backend-coding.md)の「設定の値」（設定の record に値の制約を付ける）に合わせる。
  - インスタンスごとにキャッシュの中身が違ってよい。理由：対応は作った後に変わらず、[バックエンドのアーキテクチャ](../../../../02-設計/backend-architecture.md)の「水平スケール」のローカルキャッシュの規則（インスタンス間で差があってもよいデータだけ、必ず TTL を付ける）に合うため。
  - 統合テストはアプリケーションコンテキストを共有し、ロールバックするテストがある。ロールバックで消えた会員の ID が、キャッシュから後のテストに返されないようにする。方法は実装で決め、レビューで確認する。
- 決定 3（地域のキャッシュ）：都道府県と市区町村の全件（市区町村は約 1,900 行）を 1 つの値としてメモリに持つ。
  - 最初に使うときに読み、期限が切れたら再読み込みする。起動のときに読まない。理由：起動を DB に依存させないため。
  - キャッシュにあるときは、トランザクションを始めず、DB に問い合わせない。
  - キャッシュを使う照会は、次の 4 つ。郵便番号で検索する照会は DB のまま。
    - 都道府県の一覧
    - 都道府県をコードで取得する
    - 都道府県の市区町村の一覧
    - 市区町村をコードで取得する
  - 期限は設定にする。接頭辞は `ecsite.region.cache`、期限の既定は 24 時間。設定の型は決定 2 と同じ規則に合わせる。
  - 今の決定との関係：[地域モジュール](../../../../03-機能仕様/region.md)の「参照」に「地域の API の応答のキャッシュを、バックエンドに持たない」とあり、spec 016 の plan の Non-goals にも同じ決定がある。この決定を、バックエンドに期限つきで持つ形に書き換える。
  - 書き換える理由：地域のデータを変えるのはマイグレーションだけで、マイグレーションはデプロイのときに行い、デプロイで再起動したインスタンスは新しいデータを読むため。DB を直接変えたときは、期限が切れるまで古い値を返しうる。
  - [バックエンドのアーキテクチャ](../../../../02-設計/backend-architecture.md)の「値の置き場所」は、都道府県・市区町村を、デプロイせずに変わりうるデータとして DB に置く。期限が切れたら再読み込みするので、この規則と矛盾しない。
  - 店舗画面が地域の API を再取得する間隔（地域モジュールの「参照」）は変えない。
  - 都道府県の市区町村の一覧で、都道府県がないときに 404 を返す振る舞いは変えない。
- 決定 4（メソッドの名前）：会員 ID を求めるクラスの 2 つのメソッドの名前は変えない。ログインが任意の操作で使うメソッドの Javadoc の 1 行目で、初めての会員なら会員を作ることを示す。
  - 理由：カートと店舗の呼び出し元を変えずに済むため。
  - 退けた案：`findOrCreate` などへの改名。理由：カートと店舗の呼び出し元の 4 か所を変えるため。
- 決定 5（IdP のアカウントの ID を、null を許容しない型にする）：token の会員の型で、IdP のアカウントの ID から null を許容する注釈を外す。代わりに、コンストラクターで null を拒む Lombok の注釈を付ける。
  - 根拠：[バックエンドの書き方](../../../../05-開発規則/backend-coding.md)の「null の扱い」は、共通の値のコンストラクターの引数に `lombok.NonNull` を付けると定めている。
  - subject のない token は、token の会員を作る箇所で NullPointerException になり、今と同じく 500 になる。会員 ID を求めるクラスの null の確認を外す。
  - 今の振る舞い（subject のない token は 500）を固定するテストを、型を変える前に加える（[開発の進め方](../../../../05-開発規則/workflow.md)の「循環」）。
  - 退けた案：token の検証で subject を必須にする。理由：subject のない token が 401 に変わり、整理の範囲を超えるため。
- 決定 6（文書）：
  - 地域の機能仕様の「参照」の、バックエンドにキャッシュを持たない箇条を、決定 3 の形に書き換える。
  - 地域の設計に、都道府県と市区町村をメモリに期限つきで持つことを書く。
  - 会員の機能仕様の「会員を求める」で、会員がいるときは読み取り専用のトランザクションだけで済む、という箇条を、キャッシュにあればトランザクションを始めない形に書き換える。
  - 会員の設計の「会員 ID を求める」の図に、キャッシュを加える。
  - 環境変数の一覧の「バックエンド」の表に、2 つのキャッシュの設定の行を加える。
  - 依存とライセンスの文書の「バックエンド」の表に、Caffeine の行を加える。
  - AC も業務規則の番号（BR）も追加しない。
