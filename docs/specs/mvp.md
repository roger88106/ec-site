spec 010 で MVP の機能がそろった。MVP を完成させるまでの整理を spec 011〜019 に分け、ここに順序と理由をまとめる。spec ごとの進み具合は [README の進捗](../../README.md#進捗)に書く。

spec の名前は、spec の文書を書くまで仮のもの。spec の文書ができたら、番号をリンクにする。

## 2. 並べた原則

1. ツール → テストの安全網 → 書き方の統一 → 振る舞いの変更、の順に行う。
2. 書き方の統一（013、014）は振る舞いを変えない。完了の条件は「既存のテスト（バックエンド、フロント、E2E）を変えずに全て通る」。テストを変えないと通らない所は、振る舞いを変えているので、振る舞いを変える spec（主に 016）に移す。
3. テストの安全網（012）で追加する・修正するテストは、今のコードで通る（今の振る舞いを書いている）ことと、コードをわざと壊すと失敗することを確認する。新しい振る舞いのテストは、その振る舞いを作る spec が TDD で書く。
4. 振る舞いを変える spec（015〜017）は、統一の後に行い、新しいコードを最初から統一した書き方で書く。
