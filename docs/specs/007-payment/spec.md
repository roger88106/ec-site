# Spec 007：決済

ステータス：確定

## 1. 背景と目的

コアフローの「注文 → 決済」を作る。**消費者が注文の代金をカードで支払い、支払が済んだ注文だけを運営者が受け付ける状態**にする。

- 今は、注文が成立した時点で「受付」になり、代金を受け取る手段がない。
- spec 002 で、決済を加えるときは「受付」の前に「支払待ち」を追加すると決めた。

支払はカードだけとし、外部の決済サービスのテストモードを使う。カード番号は決済サービスの画面で入力し、EC は受け取らない。決済サービスの画面に表示する支払の方法は、決済サービスの設定でカードだけにする。

与信（オーソリ）は注文のときに取り、売上の確定は出荷のときに行う（出荷の spec）。出荷の前のキャンセルは与信の取消で済み、本 spec では返金を扱わない。

AC・US・BR・NFR の番号は、spec 003 から続けて振る。

## 2. 用語

[用語集](../../reference/glossary.md)の「注文」「注文の状態」を参照。「支払」「与信」「支払の期限」などは plan で追加する。

## 4. User stories と受け入れ条件

### US-31 注文の代金をカードで支払う（C / P1）

- **AC-143** 注文手続きで注文すると、注文は「支払待ち」で作られ、決済サービスの支払画面に移る。
- **AC-144** 「支払待ち」の注文を作ると、全品目の在庫数を減らす。在庫の扱いは spec 002 の AC-87 と同じ。カートはこの時点では変えない。
- **AC-145** カード番号は決済サービスの画面で入力する。EC の画面と API は、カード番号を受け取らない。
- **AC-146** 決済サービスで総額の与信が成功すると、注文は「受付」になる。売上は確定しない。
- **AC-147** 与信が成功すると、注文した品目（バリアント）をカートから除く。注文の後にカートに追加した品目は残る。※1
- **AC-148** カードが拒否されたときは、決済サービスの画面で別のカードを入力して再試行できる。拒否では注文の状態は変わらない。
- **AC-149** 支払を終える・やめると、決済サービスの画面から注文の画面に戻る。
- **AC-150** 戻った時点で与信の結果が EC に届いていなければ、注文の画面に「支払の確認中」と示す。画面を開き直すと、その時点の状態を示す。
- **AC-151** 支払の期限の前なら、「支払待ち」の注文の画面から、支払画面に移り直して支払える。
- **AC-152** 同じ注文で支払画面に何度移っても、与信は 1 回だけ取られる。

※1：支払の期限が切れても、カートから注文し直せるようにするため。「支払待ち」の間もカートは使え、同じカートから別の注文を作れる。それぞれの注文は別に在庫を減らす。

### US-32 支払の期限が切れた注文を取り消す（C / P1）

- **AC-153** 支払の期限（BR-16）までに与信が成功しなかった注文は、キャンセルになり、明細の数量だけ在庫数を戻す。
- **AC-154** 期限切れのキャンセルは、期限から一定時間（plan で決める）のうちに行われる。
- **AC-155** 期限切れのキャンセルの理由は「支払期限切れ」とし、注文の詳細（店舗・管理画面）に示す。
- **AC-156** 期限の直前に与信が成功した注文は、期限切れでキャンセルしない。
- **AC-157** 期限切れでキャンセルした後に与信の成功が届いたら、その与信を取り消す。注文はキャンセルのまま。
- **AC-158** 「支払待ち」の注文は、消費者のキャンセルの申請も、運営者のキャンセルもできない。理由：期限で自動でキャンセルになるため。

### US-33 支払の状態を確認する（C・B / P1）

- **AC-159** 店舗の注文の一覧と詳細に、「支払待ち」の注文の支払の期限を示す。詳細には、支払画面に移る操作を示す。
- **AC-160** 管理画面の注文の一覧と詳細に、支払の状態（BR-15）を示す。
- **AC-161** 管理画面の注文の一覧で、状態「支払待ち」で絞り込める。

### US-34 キャンセルした注文の与信を取り消す（B / P1）

- **AC-162** 与信済みの注文がキャンセルになると、与信を取り消す。キャンセルの理由（消費者の申請の承認、運営者の判断）によらない。
- **AC-163** キャンセルは、与信の取消の結果を待たずに成立する。理由：決済サービスが応えないときも、キャンセルと在庫の戻しを止めないため。
- **AC-164** 与信の取消に失敗したら、取り消せるまで再試行する。再試行の方法は plan で決める。
- **AC-165** 与信の取消が済むまで、管理画面の注文の詳細に「与信の取消待ち」と示す。
- **AC-166** 同じ与信の取消が重ねて行われても、成功し、何も変わらない。

## 5. 業務ルール

spec 002 の BR-6〜11、spec 003 の BR-12、13 に加える。

- **BR-14 注文の状態**：spec 002 の BR-9 に次を加える。
  - 注文は「支払待ち」で作られる。
  - 「支払待ち」→「受付」（与信の成功）
  - 「支払待ち」→「キャンセル」（支払の期限切れ）
  - 「受付」からの遷移は BR-9 のとおり。

- **BR-15 支払の状態**：注文の状態とは別に、注文ごとに持つ。

  | 支払の状態 | 意味 |
  |------------|------|
  | 未払い | 与信がまだ成功していない |
  | 与信済み | 総額の与信が成功し、売上は確定していない |
  | 与信の取消待ち | 注文がキャンセルになり、与信の取消が済んでいない |
  | 与信の取消済み | 与信を取り消した |
  | 支払なし | 与信が成功しないまま、注文がキャンセルになった |

  ※ 売上の確定と、その後の状態は出荷の spec で追加する。

- **BR-16 支払の期限**：注文を作ってから 30 分。決済サービスの支払画面も、同じ時刻に使えなくなる。

- **BR-17 決済サービスからの通知**：支払の結果は、決済サービスからの通知だけで受け取る。
  - 通知は、決済サービスの署名を確認し、確認できないものは処理しない。
  - 同じ通知が重ねて届いても、結果は 1 回だけ反映する。
  - 通知の順序が入れ替わっても、注文と支払の状態は BR-14、15 の遷移を外れない。
  - 処理に失敗した通知は、決済サービスの再送で処理し直す。

## 6. 非機能要件

- **NFR-5** EC は、カード番号、有効期限、セキュリティコードを受け取らず、保存しない。
- **NFR-6** 決済サービスは設定で切り替える。自動テストと CI は、外部の決済サービスに接続せず、内部の mock で、成功・拒否・期限切れ・通知の遅れ・重複を再現する（バックエンドのアーキテクチャ 第 8 節）。
- **NFR-7** 期限切れのキャンセルは、アプリを複数のインスタンスで動かしても、1 つの注文に 1 回だけ行われる（バックエンドのアーキテクチャ 第 5 節）。
- **NFR-8** 決済サービスの秘密の値（API キー、通知の署名の鍵）は、Git に入れず、環境変数で渡す。

## 7. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| 売上の確定、与信の有効期限切れ | 出荷の spec |
| 返金（売上の確定後の取消） | 返品の spec（出荷後はキャンセルできないため、本 spec では起きない） |
| カード以外の支払（コンビニ、銀行振込など） | 将来の spec（与信だけを取れないので、支払の流れを再検討する） |
| カードで払うウォレット（Apple Pay、Google Pay、Link） | MVP の後に再検討する（決済サービスの設定で表示でき、与信だけを取れるので、支払の流れは変わらない） |
| カードの保存、次回の支払での再利用 | 将来の spec |
| 「支払待ち」の注文を、消費者が期限の前に取り消す（支払画面で「やめる」としたときの取消を含む） | 将来の spec（MVP は期限切れを待つ。やめても注文の画面に戻るだけ） |
| 管理画面からの、与信の取消の手動の操作 | 将来の spec（AC-164 で自動で再試行する） |
| 公開ネットワークでの通知のエンドポイント（URL、回数制限など） | 公開ネットワークへのデプロイの前提と同時（constitution 16） |
| 支払の確認のメール、領収書 | 将来の spec |
| 期限切れのカートと引当の削除（spec 002 の Non-goals） | 別の spec（本 spec の plan で定期ジョブの分散ロック方式を決めるので、その後に行える） |
