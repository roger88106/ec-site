# 文書の記号と番号

spec・plan・tasks・constitution・モジュール設計書で使う番号と記号の意味。業務の用語と識別子（クラス名、テーブル名など）は[用語集](../reference/glossary.md)で引く。

## spec の種類

| 種類 | 内容 | 例 |
|------|------|----|
| 機能 | 消費者・運営者に見える振る舞いを作る・変える。単独で検証できる機能の縦切り 1 つ | 001〜003 |
| 整理 | 消費者・運営者に見える振る舞いを変えずに、規則・テスト・構成・コードを整える | 004〜006 |

spec の番号（`NNN`）は、種類によらず 1 つの並びで振る。tasks のタスク番号と commit のメッセージから、どちらの種類の spec かによらず辿れるようにするため。

## spec の中の番号

番号は一度振ったら変えない。追加は末尾の番号を使う。

| 番号 | 意味 | 使う spec | 振り方 |
|------|------|-----------|--------|
| `US-n` | User story（誰が何をできるか） | 機能 | 機能の spec をまたいで続けて振る |
| `AC-n` | 受け入れ条件。「できた / できていない」が判断できる文。テスト名（`@DisplayName` など）に入れる | 機能 | 同上 |
| `BR-n` | 業務ルール。複数の AC にまたがる規則 | 機能 | 同上 |
| `NFR-n` | 非機能要件 | 機能 | 同上 |
| `DS-n` | 整理の目的（開発者・エージェントが何をできるようになるか） | 整理 | 整理の spec をまたいで続けて振る |
| `DC-n` | 整理の完了の条件。「できた / できていない」が判断できる文。確かめ方（CI・テスト・検査の script・見直しで読む）を plan で決める。テスト名には入れなくてよい | 整理 | 同上 |
| `DN-n` | 整理の spec の非機能要件（守る制約） | 整理 | 同上 |

整理の spec の番号に `AC-`・`US-`・`NFR-` の文字列を含めないのは、コードやテストの中の `AC-119` などを検索したときに、整理の spec の番号が混ざらないようにするため。

## spec の中の記号

| 記号 | 意味 |
|------|------|
| 対象 `C` | 消費者（店舗画面・店舗 API） |
| 対象 `B` | 運営者（管理画面・管理 API） |
| 対象 `D` | 開発者とエージェント（整理の spec） |
| 優先度 `P1` | その spec で必須 |
| 優先度 `P2` | 余力があれば入れる。入れない場合は Non-goals か後の spec に移す |

## 文書のステータス

| 文書 | ステータス | 意味 |
|------|------------|------|
| spec | 草案 | 議論中。Open questions が残っていてよい |
| spec | 確定 | Open questions が空。plan に進める |
| plan | 承認済み（tasks 作成済み） | 利用者が承認し、tasks に分けた |

spec の進み具合（どの段階まで完了したか）は、README の spec の表に書く。

## tasks の番号と記号

| 番号・記号 | 意味 |
|------------|------|
| 段階 | tasks の 1 ファイル（`tasks/NN-<名前>.md`）。冒頭に前提・完了条件・参照を書く |
| `Tnnn` | タスク。spec 001 は `T` ＋ 段階 ＋ 連番（例：`T301`、`T1106`）。spec 002 以降は `T` ＋ spec の番号の下 1 桁 ＋ 段階 ＋ 連番（例：`T3101` は spec 003 の段階 1 の 1 つ目）。commit のメッセージの末尾に `（T3101）` の形で書く |
| `[テスト]` | テストを書くタスク。対応する実装のタスクより先に行い、失敗することを確かめてから実装に進む |
| `[E2E]` | E2E を書くタスク。画面と API の実装の後に行い、通ることを確かめる（失敗の確かめは求めない） |
| `- [x]` / `- [ ]` | 完了 / 未完了 |

## constitution の記号

| 記号 | 意味 |
|------|------|
| 【提案】 | 暫定のルール。実際に使ってみて確定させる |
| アーキテクチャのレベル `A` | フル：domain / application / infrastructure / presentation（バックエンドのアーキテクチャ 第 2 節） |
| アーキテクチャのレベル `B` | 簡略：3 層（バックエンドのアーキテクチャ 第 2 節） |
| アーキテクチャのレベル `C` | イベントストア（バックエンドのアーキテクチャ 第 2 節） |

モジュールごとのレベルと選んだ理由は、`docs/backend/modules/<module>.md` の冒頭に書く。
