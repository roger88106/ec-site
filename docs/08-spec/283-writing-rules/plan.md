## 2. 用語を選ぶ規則（DS-283-2：DC-283-7〜10）

「利用者に確認すること」の確認 2 の案 A で書く。正本の「用語の選び方」に、次の順で書く。

| 規則 | DC | 例（避ける → 使う） |
|------|----|---------------------|
| 一般の日本語の技術文書の読者に通じる用語を選ぶ。迷ったら、ツールの公式文書（日本語）や一般の技術書で使われる用語にする | 7 | `無記憶のレビュー役` → 「文脈を持たないレビュー役」 |
| 造語を作らない。名前が必要なときは、先に専門用語を調べ、あればそれを使う。なければ、用語集に定義を加え、校閲役に読ませてから使う | 8 | `判定器` → 「検査の script」、`口頭の語` → 「話し言葉」、`書面語` → 「書き言葉」 |
| 英語を直訳しない。定着した外来語があれば使う | 9 | `箱`（box）→ 「ボックス」、`指令`（command）→ 「コマンド」 |
| 話し言葉を書かない | 10 | `効く` → 「反映される」「有効になる」 |
| 和語の言い換えより、技術文書で一般的な用語を使う（今の規則） | 10 | `流す` → 「実行する」 |
| 1 つの語で 2 つの意味を表さない。単独の「高」「低」は、危険度か重要度かを書く | 10 | `高の pull request` → 「危険度が高い pull request」 |

- 「日本語だけで書く」は、「英字は識別子と固有名だけに使う。外来語は使ってよい」と明確にする。理由：英語を避けた結果、直訳の造語が生じたため（[spec](spec.md)の「今の状態」 ※2）。
- 英字のまま定着した外来語（script、hook、pull request など）は、英字のまま書いてよい（段階 2 のレビューの指摘、2026-10-30）。理由：リポジトリ全体がこれらを英字で書いていて、カタカナに替える利点がないため。
- 造語の手順（DC-283-8）は、起票の時点にも当てはまると書く。issue の本文を校閲役に読ませる今の規則（開発の進め方の「起票」）と合わせる。理由：`判定器` は、issue のコメントで使い始めた用語が規則に入ったため（#277）。

| 決定 | 置き場所 | DC | 確認方法 |

| 参照の形は `<文書の名前>の「<見出し>」`。Markdown では、文書の名前をリンクにする（`[開発の進め方](../../05-開発規則/workflow.md)の「起票」`）。見出しは番号を除いて書く | 正本の「参照」 | 11 | 文書を読む |

| 見出しの参照として見るのは、リンクか文書の名前の直後の `の「…」` だけ。文書の名前は、今と同じく各文書の 1 行目の見出しから作る | 同上 | 12 | テスト。理由：「」は引用にも使うので、文書を指す所だけを見るため |
| 既存の `第 N 節` の参照を、見出しの形に置き換える。`doc-refs` の解決の処理で番号から見出しを求め、script で置き換える。解決できないものは、1 件ずつ修正する | アーカイブの外の全てのファイル | 13 | `git grep "第 [0-9.]* 節"` の残りが、節の参照でないものだけ |
| 置き換えの後、アーカイブの外の `第 N 節` の参照を失敗にする。Markdown ではインラインコードの外が対象、コードのコメントでは文書の名前の直後が対象 | `scripts/ci/doc-refs.mjs` とテスト | 14 | テスト（レッドから） |
| skill `docs` の「参照の修正」を見出しの形に合わせる。見出しを変えたら `doc-refs` が切れた参照を示すので、その一覧で修正する手順にする | `.claude/skills/docs/SKILL.md` | 15 | 文書を読む |

- 見出しの末尾の全角の括弧の補足（`## 5. 文体の検査（DS-283-5：DC-283-21〜25）` の括弧）は、参照で省いてよい。`doc-refs` は、補足を除いた形でも比べる（T283-03-03）。理由：plan と spec の見出しの多くに補足があり、全て書くと参照が長くなるため。見出しでない所（表の行や列、用語集の語）は、`用語集の語「写し」` のように種類を書いて、見出しの参照の形にしない（T283-03-03）。
- 同じ文書の中の節を指す参照は、文書の名前を付けずに `「<見出し>」` と書き、`doc-refs` で確認しない。レビューで確認する（利用者、2026-10-30。段階 3 のレビューの指摘）。理由：同じ文書の中は読む人が照合しやすく、名前のない「」は引用や語の例と見分けられないため。
- `fix-links.cjs` は、リンクのパスだけを修正する script なので変えない。
- constitution の節の番号を使わない今の規則は、見出しの形でも変わらない（細則の文書を指す）。
- 判定は、誤りの防止とする（[文書の書き方](../../05-開発規則/writing.md)の「spec と plan の書き方」）。理由：参照を正しく書く規則で、回避策を作る動機がないため。

### 4.2 置き換えの方法

| 種類 | 用語 | 方法 |
|------|----|------|
| 一括で置き換える | `弾`、`無記憶`、`主の`、`箱`、`指令`、`ツールの注`、`書面語`、`口頭の`、`許す語` | skill `docs` の「語の一括の置き換え」の手順（活用の対応表、スクラッチパッドの script、崩れの確認）。除外は、アーカイブ、適用済みのマイグレーションと seed、テストのデータ |
| 文脈で置き換える | `段`、`台帳`、`効く`、`高`・`低`、`動かして確認する` | `git grep` の一覧を実装役が 1 行ずつ読み、新しい用語を選ぶ（[エージェントの作業フロー](../../05-開発規則/subagents.md)の「運用の規則」にある語ごとの規則）。一覧と選んだ用語を結果に書く |

- 関連 spec の検査（`related-specs`）は、用語集などの設計の文書を変えた commit を見る。参照と用語の置き換えは設計を変えないので、その段階の最初のタスクで、除外の一覧に段階のタスク番号の接頭辞（`T283-03`、`T283-04`）を加える。
- 参照と用語の置き換えは、それぞれを 1 つの段階にまとめる。各段階の最後に `develop` を取り込み、取り込んだ分（Dependabot の変更など）にあれば再度置き換える。

## 5. 文体の検査（DS-283-5：DC-283-21〜25）

利用者の決定（2026-10-30、「利用者に確認すること」の確認 5・6）：失敗にせず、警告だけにする。理由：閾値を超える必要がある例外があるため。

| 決定 | 置き場所 | DC | 確認方法 |
|------|----------|----|----------|
| `ja-text` に、差分の追加行の文体を示すオプション（`--changed`）を加える。差分の追加行の文に、字数か読点の数が閾値以上のものがあれば、警告として示す。終了コードは 0 にする | `scripts/ci/ja-text.mjs`、テスト | 21、23 | テスト（レッドから） |
| CI では、警告を GitHub Actions の注釈（`::warning file=…,line=…::`）で出し、pull request の画面の該当する行に表示する | 同上 | 21 | テスト。pull request の画面で注釈を確認する |
