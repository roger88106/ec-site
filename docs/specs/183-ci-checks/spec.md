# Spec 183：CI の検査の script を整え、文書・マイグレーション・テストの検査を追加する

ステータス：草案

## 1. 背景と目的

spec 156、157、158 の後に、CI の検査の script（`scripts/ci/`）の整理と、新しい検査の追加が残っている。同じ script を変えるので、1 つの追跡の issue にまとめた。

- spec 158 の後回しにした項目（spec 158 第 8 節の 1〜32）は、#161、#165〜#169 に起票した。spec 155・157 の備忘が、#161、#166、#169 のコメントに加わっている。
- #20（マイグレーションの互換性）は、規則がまだない。規則を決めてから検査にする（第 6 節の 2）。
- #169 の検査は、同時に進む spec 184（フロントのテストの第 2 回）が修正する違反と重なる（第 6 節の 4）。

追跡の issue は [#183](https://github.com/roger88106/ec-site/issues/183)、扱う issue は [#20](https://github.com/roger88106/ec-site/issues/20)、[#161](https://github.com/roger88106/ec-site/issues/161)、[#165](https://github.com/roger88106/ec-site/issues/165)、[#166](https://github.com/roger88106/ec-site/issues/166)、[#167](https://github.com/roger88106/ec-site/issues/167)、[#168](https://github.com/roger88106/ec-site/issues/168)、[#169](https://github.com/roger88106/ec-site/issues/169) である。作業ブランチは `183-ci-checks`。本 spec は整理の spec で、規模は M を提案する（第 6 節の 1）。API の契約とデータベースを変えず、AC を変えないため。

範囲が大きいので、2 つの spec に分けることを提案する（第 6 節の 1）。分けるときは、DS-183-1〜4 を本 spec に残し、DS-183-5〜7 を新しい spec に移す。

## 4. 守る制約

- **DN-183-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。
- **DN-183-2** 検査を弱めない。検査の対象を狭めるのは、誤検出を減らすとき（DC-183-15、18 など）だけにし、理由を検査に書く。
- **DN-183-3** `scripts/ci/` は本 spec だけが変える。spec 184 は変えない。
- **DN-183-4** 共有の文書（[CI の検査](../../guides/ci.md)、規則の文書）と、spec 181、182、184 と重なるファイルの衝突は、後でマージする pull request が `develop` を取り込んで解消する。
- **DN-183-5** 新しく書くコメントと除外の理由に、spec・plan の番号を書かない（コメントの書き方 第 1 節。spec 158 の DC-158-44 と同じ）。

## 6. 決めること

利用者に確認する。全て案 A を推奨する。

### 6.1 規模と、2 つの spec への分け方

DC は 49 で、spec 158（M、51）と同じくらいである。変えるのは検査の script、workflow、文書と、違反の修正の数行で、規模の基準（[開発の進め方](../../rules/workflow.md) 第 4.2 節）では M に当たる。分けるかは、次の 2 つで判断した。

- DS-183-1〜4（#165〜#168）は、今の検査を整える作業で、他の spec を待たずに始められる。
- DS-183-5〜7（#20、#161、#169）は新しい検査で、#20 の規則の決定と、spec 184 のマージを待つ。DS-183-1 の共通の関数（テストのファイルの探し方など）を使うので、DS-183-1 の後に作るほうが手戻りがない。

| 案 | 内容 |
|----|------|
| 案 A（推奨） | 2 つの M の spec に分ける。本 spec は DS-183-1〜4（#165〜#168。DC 30）、新しい spec は DS-183-5〜7（#20、#161、#169。DC 19）。新しい spec は本 spec のマージの後に始める |
| 案 B | 1 つの M の spec のまま、段階を DS の順に並べ、DS-183-7 の段階を spec 184 のマージの後にする |
| 案 C | 1 つの L の spec にし、plan を書く |

- 案 A の理由：pull request が小さくなる。spec 184 のマージや #20 の決定を待つ間も、本 spec の作業を進められる。新しい spec は、本 spec の共通の関数がそろった `develop` から始められる。
- 案 A の手間：追跡の issue を 1 つ増やす（issue 担当のセッションが作り、#20、#161、#169 を移す）。spec の最後のレビューが 2 回になる。
- 案 A のとき、本 spec の DS-183-5〜7 の節は、新しい spec に移して番号を振り直し、本 spec から除く。
- 案 B の理由：レビューと pull request が 1 回で済む。ただし、spec 184 のマージが遅れると、本 spec の全体が待つ。
- 案 C は、API・データベース・モジュールをまたがないので、規模の基準に合わない。

### 6.2 マイグレーションの互換性の規則（DC-183-31〜33）

今は、マイグレーションはデプロイごとに 1 回適用し、起動時には適用しない（[環境変数](../../guides/environment.md) 第 1 節）。適用してからアプリを入れ替えるまでの間、前の版のアプリが新しいスキーマで動く。

規則（全ての案で共通）：新しいマイグレーションは、前のリリースのアプリが動き続けられる変更だけにする。表・列の削除と改名、列の型の変更、既存の列を NOT NULL にすること、既定値のない NOT NULL の列の追加は、1 つのリリースでしない。次の順に分ける。

1. 新しい表・列を追加する（前の版のアプリは使わない）。
2. アプリを新しい表・列に切り替えてリリースする。
3. 次のリリースで、使わなくなった表・列を削除する。

| 案 | 検査 |
|----|------|
| 案 A（推奨） | マイグレーションの検査が、新しいマイグレーションの、上の規則が禁じる文を失敗にする。手順 3 の削除は、どのリリースで使わなくなったかを理由に書いて、除外の一覧に置く |
| 案 B | 検査を作らず、規則だけを書く。リリースの前のレビュー（高性能。マイグレーション、互換性の観点）で読む |
| 案 C | 案 A に加え、前のリリースのアプリの統合テストを、新しいスキーマで CI で実行する |

- 案 A の理由：禁じる文は SQL の字面で見つけられ、誤検出は除外の一覧で理由を残して許せる。除外の一覧の形は、spec 158 でそろえた `{キー: 理由}` と同じにできる。
- 案 B は、リリースの前まで違反に気づかず、手順 1〜3 の分け直しが大きくなる。
- 案 C は、本番の環境がなく、CI の時間が増える。本番を作るときに改めて検討する（第 5 節）。
- 規則の置き場所は、[バックエンドの書き方](../../rules/backend-coding.md) に節を加える。[CI の検査](../../guides/ci.md) の migrations の行も合わせる。

### 6.3 規則の文書にない #169 の検査（DC-183-43、45、46、47）

#169 のコメントで加えた 5 つの検査のうち、3 つは [テストの書き方](../../rules/test-writing.md) の本文に規則がない。並びのインデックス（DC-183-44）はテストの書き方 第 4.1 節の「並びの 1 つ目は使わない」に、型の変換（DC-183-42）はテストの書き方 第 4.6 節にある。

| 検査 | 今の規則 |
|------|----------|
| `toBeTruthy`・`toBeDefined` で探した要素を確認する（DC-183-43） | なし。テストの書き方 第 4.1 節は探し方だけを書く |
| HTML の属性の並びに依存する正規表現（DC-183-45） | なし |
| `describe` の名前が識別子だけ（DC-183-46） | テストの書き方 第 2.2 節はテスト名にメソッド名を書かないとするが、`describe` に触れない |

- 案 A（推奨）：spec 158 の第 6 節の 5 と同じく、先に規則を [テストの書き方](../../rules/test-writing.md) に書いてから検査を加える。理由：規則のない検査は、失敗したときに修正の方法を示せないため。
- 案 B：規則のない 3 つの検査は本 spec に入れず、起票に回す。

### 6.4 spec 184 と重なる違反と、検査を加える順序（DC-183-49）

今の `develop`（7b4312c6）の違反は次のとおり。

| 検査 | 件数 | 場所 | 修正するもの |
|------|------|------|----------|
| 型を回避する変換（DC-183-42） | 1 | 店舗画面のテストの共通の設定（`src/test/setup.ts`） | 本 spec（理由のコメントを書くか、型に合う値にする）。spec 184 の範囲にない |
| `toBeDefined`（DC-183-43） | 3 | 店舗画面のコンポーネントのテスト（HTML に描画して探すもの） | spec 184（#171 で、役割と名前で探す形に書き換える） |
| `toBeDefined`（DC-183-43） | 2 | E2E（IdP の画面、出荷） | 本 spec |
| HTML の属性の並びの正規表現（DC-183-45） | 4 か所以上 | 店舗画面のコンポーネントのテスト | spec 184（#171） |
| 並びのインデックス、`describe` の名前 | 0 | — | — |

- 案 A（推奨）：DS-183-7 の検査は、spec 184 のマージの後に `develop` を取り込んでから加える。spec 184 の範囲にない違反（上の表の「本 spec」）は、検査を加えるタスクで修正する。理由：spec 184 が書き換えるファイルを本 spec が先に修正すると、衝突と二重の作業になるため。
- 案 B：検査を先に加え、spec 184 が直す違反を除外の一覧に置き、spec 184 のマージの後に除外を消す。
- 第 6 節の 1 で案 A（分ける）なら、DS-183-7 は新しい spec に移るので、新しい spec の前提が spec 184 のマージになる。案 B（分けない）なら、DS-183-7 を最後の段階にする。spec 184 のマージが他の段階より遅れるときは、利用者に扱いを相談する。

### 6.5 YAML を読む検査の読み方（DC-183-12）

今の検査の script は Node の標準の機能だけを使い、依存を install せずに動く（commit の前の hook でも同じ）。

- 案 A（推奨）：パーサーを使わず、読む節の中で、知っている書き方に当たらない行があれば失敗にする。理由：依存を加えずに、読み飛ばしたまま成功することをなくせ、新しい書き方は失敗で気づいて読み方を足せるため。
- 案 B：YAML のパーサーをルートの開発用の依存に加え、検査がそれで読む。全ての書き方を読めるが、CI の文書の検査のジョブと hook の前に install が必要になる。
