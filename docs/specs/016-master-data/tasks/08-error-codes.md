# 段階 8：エラーのコードの契約

- 前提：段階 1〜7（エラーのコードを足し終えてから）
- 完了条件：店舗 API と管理 API の契約に、エラーのコードの全体の列挙と、操作ごとの一覧がある。バックエンドのエラーのコードと契約が一致し、すべての統合テストのエラーの応答が、その操作の一覧か共通のエラーにある。画面はエラーのコードを生成した型で比べる。AC-274、275 のテストが通る。`./gradlew check`、`check-frontend.sh` が通る。
- 参照：[plan](../plan.md) 第 7 節、spec の US-59、[API の規約](../../../api/conventions.md) 第 4 節、[バックエンドの書き方](../../../backend/coding.md) 第 3.2 節、[フロントの書き方](../../../frontend/coding.md) 第 2 節

## タスク

- [x] **T016-08-01** API の規約 第 4 節に、エラーのコードの全体の列挙、操作ごとの一覧（`x-error-codes`）、共通のエラーを書く。フロントの書き方 第 2 節に、エラーのコードは生成した型で比べることを書く。
- [x] **T016-08-02** [テスト] 契約の単体テストを書く。レッドを確かめる。
  - API ごとに、全体の列挙が、操作ごとの一覧と共通のエラーの和と一致する。
  - バックエンドのすべてのエラーのコードが、どちらかの API の全体の列挙にあり、全体の列挙のすべての値がバックエンドにある（AC-275）。
- [x] **T016-08-03** [テスト] 統合テストの設定に、エラーの応答の確かめを足す：MockMvc の結果のエラーの本文の `errorCode` が、その操作の一覧か共通のエラーにあることを、毎回確かめる。操作の照らし方は、認可で契約を読む処理を使う（plan 第 7 節 ※11）。この確かめ自体のテスト（一覧にないコードを返すと失敗する）を書き、レッドを確かめる（AC-274）。
- [x] **T016-08-04** 店舗 API と管理 API の契約に、全体の列挙と、各操作の一覧を書く。操作ごとの一覧は、その操作の実装が投げうるエラーのコードを読んで決める。T016-08-02 と、すべての統合テストを通す。
  - 決め方：まず、統合テストが実際に返した（操作、コード）を一時的に記録して土台にした（記録の処理は commit していない）。テストが通らないコード（品番・名前・説明の形、メモの長さ、画像の変換の失敗、送り状番号、出荷の重複、売上確定できない支払など）は、コードを投げる所を `git grep` し、その処理を呼ぶ操作に足した。
  - 共通のエラーは `CommonErrorCode` の 9 つ。テストだけの endpoint（`/api/test-errors`）は契約の API の外なので、確かめから外した。
- [x] **T016-08-05** 画面のエラーのコードの比較を、生成した型の値にする（店舗画面の注文手続き、管理画面の競合など）。`check-frontend.sh` が通る。
  - テストのエラーの本文を作る関数（`problem`）の引数も生成した型にした。契約にないコードを使っていたテスト（`UNAUTHORIZED`、`VALIDATION_ERROR`、`TAX_CATEGORY_NOT_FOUND`）が型チェックで見つかったので、バックエンドが返すコード（`UNAUTHENTICATED`、`INVALID_REQUEST`、`NOT_FOUND`）に直した。
- [ ] **T016-08-06** 段階の完了の確認：`./gradlew check`、`check-frontend.sh`、`check-all.sh` が通る。
