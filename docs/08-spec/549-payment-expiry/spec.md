# Spec 549：支払の期限切れのジョブの検索を索引に合わせ、開いた支払画面を閉じずに支払なしにする不具合を直す

種類：整理　規模：M　ステータス：確定

## 背景と目的

期限切れの支払の検索は、未払いの期限の部分索引に含まれない条件（与信の反映を待ち始めた時刻がない）で絞る。そのため、与信の反映を待つ支払の行を毎回読んでから除く。与信の反映を待つ支払の検索と、与信の反映を長く待つ支払の件数の集計には、待ち始めた時刻の索引がない。この 2 つの検索は件数の上限を付けるが、並び順に、同じ値の行の順を決める列（支払 ID）がない。取りこぼしは起きないが、返る行の順が実行ごとに変わりうる。支払が増えると、ジョブの実行のたびに読む行が増える。#497 のマイグレーションと検索の突き合わせで分かった（#499）。

期限切れのジョブは、行ロックを取らずに支払の一覧を読み、各支払に支払画面があるかで、画面を閉じるかを決める。画面がなければ閉じない。その後の支払なしにする処理は、行ロックを取ってから期限を確認するが、支払画面が作られたかは確認し直さない。支払画面を記録するトランザクションがコミットする前に、ジョブが期限を過ぎた支払を読むと、画面が開いたまま支払なしになる。決済サービス（Stripe）の支払画面は作ってから 31 分有効なので、消費者はキャンセル済みの注文の代金を払える。与信の成功の通知が届けば与信の取消待ちになり、届かなければ与信は取り消されない。コードを読んでの判断で、実行は未確認である（#545）。#252 の既存の指摘（#409 の pull request #428 のレビュー）と同じ内容で、2026-11-18 に今のコードでも同じ処理の順であることを、コードを読んで確認した。

この spec は、期限切れのジョブの検索を索引に合わせ、開いた支払画面を閉じずに支払なしにしないようにする。消費者・運営者に見える振る舞いは、#545 の不具合の修正の 1 点だけ変わる（DN-549-1）。DB は索引だけを変える（DN-549-3）。追跡の issue は #549（組の issue）。sub-issue は #499 と #545。#544（リリースの前の整理）の段階 3 の線 A（支払と注文）の最初の spec である。

## スコープ

| 含める | 含めない |
|--------|----------|
| 期限切れの支払の検索と、与信の反映を待つ支払の検索・件数の集計に合わせた部分索引（マイグレーション） | 支払の表の列の変更 |
| 2 つの検索の並び順に支払 ID を加えること | ジョブ 1 回の処理件数の上限と実行間隔の変更 |
| 行ロックの後に支払画面の有無を再確認し、開いた画面を閉じずに支払なしにしないこと | 支払画面の期限切れの通知の扱い（変えない） |
| 決済の機能仕様と設計の文書の修正 | 注文のモジュールのコード |

決定（issue 担当のセッションが利用者に代わって 2026-11-19 に確認した）：

- 規模：M（特例）とする。判定の表では、DB の構造（索引）を変えるので L になる。ただし、モジュールをまたぐ設計の決定がなく、plan に書くことがないため M にする。変えるのは決済のモジュールだけである。前例は spec 501。
- 決定 1（索引）：今の未払いの期限の部分索引を削除し、次の 2 つの部分索引を加える。マイグレーションは 1 つ（決済のモジュール）。索引の名前は、既存の索引と同じく、表の名前、対象の条件、列の名前の順に付ける。
  - 期限切れの支払の検索用：支払の期限と支払 ID。対象は、未払いで、与信の反映を待ち始めた時刻がない行。
  - 与信の反映を待つ支払の検索と件数の集計用：待ち始めた時刻と支払 ID。対象は、未払いで、待ち始めた時刻がある行。
  - 理由（削除する）：今の索引を使う検索は期限切れの支払の検索だけで、新しい索引がその条件を全て含むため。
  - 理由（支払 ID を索引に含める）：並び順のまま索引を読み、件数の上限で止められるため。
  - 索引の削除と追加では、前のリリースのアプリもそのまま動くため、[バックエンドの書き方](../../05-開発規則/backend-coding.md)の「前のリリースのアプリが動き続けられる変更だけにする」の 3 段に分けない。
  - 新しいマイグレーションのコメントに、索引を追加する理由を書く。与信の反映を待ち始めた時刻を追加したマイグレーションには、索引を追加しない理由がコメントにあるため。
- 決定 2（並び順）：期限切れの支払の検索は期限・支払 ID の順、与信の反映を待つ支払の検索は待ち始めた時刻・支払 ID の順にする。
- 決定 3（画面の再確認）：期限切れのジョブが支払なしにするとき、行ロックの後の支払に、ジョブが読んだときになかった支払画面があれば、支払なしにしない。その回は何もせず、info のログに支払 ID を出力する。次の回のジョブが、その画面を読んで閉じてから、今の流れで扱う。閉じる前に支払が済んでいれば与信の反映を待つ支払にし、そうでなければ支払なしにする。
  - 支払画面は 1 つの支払に 1 つだけで、一度記録したら変わらない。期限を過ぎた支払には新しい画面を記録しない。そのため、次の回のジョブは、その画面を読んで閉じられる。
  - 案 A（採用。上の形）：次の回に回す。案 B：同じ回の中で、行ロックの後に見つけた画面を閉じ、もう一度行ロックして支払なしにする。
  - 理由（案 A）：ジョブの今の「失敗したら次の回で再実行する」と同じ形で、処理の経路が増えないため。
  - 影響（案 A）：画面が開いたままになる時間が、ジョブの間隔（既定 1 分）だけ延びる。その間に支払われても、次の回に画面を閉じるときに「支払が済んでいた」と分かり、与信の反映を待つ支払になる。これは、期限を過ぎてからジョブが実行されるまでに支払われた場合の今の扱いと同じである。
- 決定 4（文書）：
  - 決済の設計の「支払の期限切れ」の図と表に、行ロックの後に支払画面を再確認することと、2 つの検索の並び順に支払 ID を加えることを書く。
  - 決済の機能仕様の「支払の期限」に、決定 3 の規則を書く。AC も業務規則の番号（BR）も追加しない。

決定に出るコードの名前は、次の表のとおり。

| 1 | `payment_unpaid_deadline_id_idx`、`payment_unpaid_awaiting_authorization_since_id_idx` | 加える 2 つの部分索引（期限切れの支払の検索用、与信の反映を待つ支払の検索と件数の集計用） |
| 1、2 | `JooqPaymentRepository`（`findUnpaidPastDeadline`、`findUnpaidAwaitingAuthorization`） | 支払のリポジトリの 2 つの検索 |

## 目的と完了条件

### DS-549-1 期限切れのジョブの検索が索引で絞れ、並び順が一意に決まる（D / P1）

- **DC-549-1** 期限切れの支払の検索が、期限切れの支払の検索用の部分索引を範囲の条件で使うことを、実行計画のテストで確認している。
- **DC-549-2** 与信の反映を長く待つ支払の件数の集計が、待ち始めた時刻の部分索引を範囲の条件で使うことを、実行計画のテストで確認している。与信の反映を待つ支払の検索が、同じ索引を使うことも確認している ※1。
- **DC-549-3** 2 つの検索で、同じ期限（同じ待ち始めた時刻）の支払が支払 ID の順に返ることを、テストで確認している。

※1：与信の反映を待つ支払の検索の条件は「待ち始めた時刻がある」だけで、部分索引の対象の条件と同じなので、範囲の条件が付かない。索引を並び順に読めば足りる。

- **DC-549-4** ジョブが読んだ後に支払画面が記録された支払は、その回では未払いのまま残り、次の回で画面を閉じてから支払なしになることを、テストで確認している。
- **DC-549-5** 決済の機能仕様と設計が、決定 3 と 4 の形になっている。
