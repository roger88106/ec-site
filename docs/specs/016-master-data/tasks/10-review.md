## レビューの結果

### 修正したこと

- 地域モジュールを作り、都道府県・市区町村の全件と郵便番号の一部を、日本郵便のデータから作ったマイグレーションで入れた。店舗 API に、都道府県・市区町村の一覧と郵便番号で引く操作を追加した（token なし）。
- 注文のお届け先は、都道府県と市区町村をコードと注文の時点の名前で持つ。注文の確定はコードを地域の API で確認する。既存の注文は移行で照合し、照合できなければ移行を失敗させる。
- 店舗画面の注文手続きは、都道府県と市区町村を一覧から選び、郵便番号から補う。画面の都道府県の表を削除した。レポートは都道府県のコードで集計し、名前を応答で返す。
- エラーの文は、ドメインの定数から数を差し込む（文に数字を書かない。CI の検査 `message-numbers`）。形の検証の誤りのうち、郵便番号と電話番号は業務のエラーの文とコードを返す。
- 操作の可否と理由を API が返す（在庫に戻すかを聞くか、商品を削除できない理由、子の分類を追加できるか）。画面は状態から判定しない。
- 画像の形式・大きさ・枚数と分類の深さの上限を契約に書き、バックエンドの値との一致を契約のテストで確認する。管理画面は契約から得る。バリアントの追加の応答に Location を入れた。
- エラーのコードの全体の列挙と操作ごとの一覧を契約に書き、全ての統合テストで応答のコードを確認する。画面は生成した型で比べる。
- 列挙の写しを `switch` 式にし、列挙の列に CHECK 制約を追加して、統合テストで一致を確認する。業務の時間帯と時点の税率の判定を 1 か所にした。値の置き場所の規則を設計書に書いた。

### 修正せずに残したこと

| 項目 | 理由 |
|------|------|
| 在庫の調整のフォームが、理由が「その他」のときにメモを必須と表示する判定を画面に実装している | 操作の可否でなく入力の規則で、理由の値によって必須になる条件は契約に書けない。バックエンドもドメインで同じ規則を確認するので、前後の両方で確認する今の形でよいと利用者と決めた（T016-10-03） |
| 画像の形式の外・10MB 超の申告は、業務のエラーの文でなく `INVALID_REQUEST` になる | 契約に形式と上限を書いた帰結。管理画面は送る前に同じ契約の値で確認するので、利用者が見る文は変わらない（T016-07-02） |
| レポートの注文の写しのキャンセルの種類と性別は、列挙にせず文字のまま持つ | 注文の記録の名前を写すだけで、レポートの中で比べない。取りうる値は制約で限る（T016-09-05、07） |
| 履歴の書き換え（T016-01-02 の補足が T016-01-03 の commit に入った） | 対話の rebase を使えないため（T016-10-03） |
