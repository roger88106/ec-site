# EC Site Constitution

本書はプロジェクト全体に適用される長期ルールである。すべての spec、plan、tasks、コードはこれに従う。
本書と矛盾する場合は本書を優先する。ルールを変えたいときは、先に本書を（理由を添えて）更新し、その後で他を変更する。

## 0. 本書の読み方

各ルールには状態タグを付ける。

| タグ | 意味 |
|------|------|
| 【確定】 | 作者が明示的に決めたもの。勝手に変更しない |
| 【踏襲】 | 参考プロジェクト MyIAM のやり方を踏襲するもの。理由がない限りそのまま従う |
| 【提案】 | 現時点の暫定案。該当する plan で確認・調整する |
| 【未定】 | まだ決まっていないもの。第 17 節に一覧する |

## 1. プロジェクトの位置づけ

- 自社 B2C の EC サイト。B2B2C ではなく、複数店舗のプラットフォームでもない。【確定】
- 個人のポートフォリオ用プロジェクト。目的は規模ではなく、**本番相当のやり方を模擬すること**。【確定】
- 規模は大きくないが、**コアフローは省略しない**：閲覧 → カート → 注文 → 決済 → 出荷 → 配送状況。【確定】
- **クラウドネイティブで、水平スケール可能な構成**を前提とする（第 5 節）。【確定】
- 2 つの利用者向け面：
  - C 側（消費者）：商品閲覧、カート、チェックアウト、決済、注文・配送状況の照会
  - B 側（運営者）：商品登録、価格変更、在庫、注文管理、出荷通知、データ収集と簡易レポート
- 現在のフェーズ：ゼロからの MVP。MVP の方針は「コアフロー全体が通る最小版」であり、全機能を深く作ることではない。
- 対象市場は日本、通貨は日本円のみ。【確定】

## 3. リポジトリ構成

【確定】単一リポジトリ（モノレポ）。理由：SDD では spec が唯一の事実の源であり、1 つの spec がフロントとバックの両方に及ぶことが多い。リポジトリを分けると、spec と実装が別々の場所に置かれ、バージョンを揃えにくくなる。

ディレクトリ構成【提案】：

```
ec-site/
├── .github/workflows/           # CI
├── api/
│   └── openapi/
│       ├── store.yaml           # C 側 API 契約の正本
│       └── admin.yaml           # B 側 API 契約の正本
├── docs/
│   ├── constitution.md
│   ├── architecture.md          # plan から徐々に蓄積
│   ├── modules/                 # 各モジュールの設計書（採用レベルを含む。4.2 参照）
│   └── specs/
│       └── 001-<feature>/
│           ├── spec.md
│           ├── plan.md
│           └── tasks.md
├── backend/                     # Spring Boot（Gradle）
├── frontend/
│   ├── store/                   # C 側
│   └── admin/                   # B 側
└── compose.yaml                 # ローカル開発用
```

見直しのトリガー：フロントとバックでリリース頻度が明確に分かれた場合、または CI や権限管理を分ける必要が出た場合に、リポジトリ分割を検討する。分割の前に本節を更新すること。

## 4. バックエンドのアーキテクチャ

### 4.1 モジュラーモノリス

- モジュール化は維持する。内部を Spring Modulith で複数モジュールに分割する。【確定】現時点ではデプロイ単位は 1 つ。【踏襲】
- モジュール間の依存は、各モジュールの `package-info.java` に `@ApplicationModule(allowedDependencies = ...)` で宣言する。宣言のない依存は `ModulithTest` で失敗させる。【踏襲】
- モジュールが外に公開するものは次の 2 種類に限る。【踏襲】
  - `api/`（`@NamedInterface("api")`）：同期呼び出し。インターフェースは「呼ぶ側が必要とする形」で作り、呼ぶ側は腐敗防止層（`XxxDirectory` など）で包む。相手の型を自分の内部に持ち込まない。
  - `event/`（`@NamedInterface("event")`）：非同期通知。状態変化は呼び出しの連鎖ではなくイベントで伝える。イベント発行は Spring Modulith のイベント永続化（AFTER_COMMIT）を使う。
- 想定モジュール：【提案】

| モジュール | 責務 |
|------------|------|
| `catalog` | 商品、価格、公開 / 非公開、商品検索 |
| `inventory` | 在庫数、引当と減算 |
| `cart` | カート |
| `order` | 注文とその状態遷移 |
| `payment` | 決済（外部決済サービスの腐敗防止層） |
| `shipping` | 出荷と配送状況（外部物流サービスの腐敗防止層） |
| `reporting` | データ収集と簡易レポート |

モジュールの追加・統合・分割はアーキテクチャ変更であり、先に本節と `docs/modules/` を更新する。

### 4.2 モジュール内のアーキテクチャレベル（モジュールごとに選定）

モジュールごとに複雑さに応じて異なるレベルを採用できる。全モジュール統一にはしない。【確定】各モジュールがどのレベルかは `docs/modules/<module>.md` に理由とともに記す。【提案】

| レベル | 構成 | 適する場面 |
|--------|------|------------|
| A. フル | DDD + Clean Architecture + CQRS（domain / application / infrastructure / presentation。MyIAM と同じ作り） | 複雑な不変条件や状態機械があり、他モジュールとイベントでやり取りする |
| B. 簡略 | 3 層（controller / service / repository）。Command / Query は分けない | データ保守が中心でルールが単純 |
| C. イベントストア | イベント列を状態の源とする（Event Sourcing） | 「状態がどう変化したか」自体に価値がある。例：配送状況の履歴 |

暫定の割り当て（【提案】。最終的には各モジュールの plan で確定する）：

| モジュール | 暫定レベル | 理由 |
|------------|------------|------|
| `catalog` | A | 価格や公開状態にルールがあり、他モジュールの土台になる |
| `inventory` | A | 引当・減算に並行性と不変条件がある |
| `cart` | B | ルールが単純 |
| `order` | A | 状態機械と、モジュールをまたぐイベント |
| `payment` | A | 状態機械であり、外部連携を包む |
| `shipping` | C | 配送状況の履歴がコア |
| `reporting` | B | 参照と集計が中心 |

レベル A のルール（MyIAM を踏襲）：

- domain はフレームワークにも他レイヤーにも依存しない。application は domain に依存する。infrastructure は domain の port を実装する。presentation は application を呼ぶ。
- ドメインオブジェクトは jMolecules のアノテーションで明示する（`@AggregateRoot`、`@ValueObject`、`@Identity`）。
- 集約の形はテーブルではなくドメインで決める。永続化は `toSnapshot()` → Factory で再構築する。
- 集約の状態変更はメソッド経由で行い、メソッド内でドメインイベントを登録する。
- application 層が投げる例外は `BusinessException` / `SystemException` に限る。

レベル C は今のところ「許容される選択肢」にとどまる。実際に採用する前に、そのモジュールの plan で保存方式、スナップショット戦略、プロジェクション（read model）の作り方を説明し、本書を更新すること。

### 4.3 フロント側 / 管理側（C 側 / B 側）の分け方

【提案】

- バックエンドは単一のデプロイ単位とする。C 側と B 側は同じドメインモジュールを共有する（商品・在庫・注文は同じデータであり、バックエンドを 2 つに分けると同期の問題が増えるだけ）。
- 両側は **presentation 層で分離**する：
  - C 側 API：`/api/store/**`
  - B 側 API：`/api/admin/**`
  - Controller、Request / Response は別々に持ち、共有しない。B 側のレスポンスには、C 側に見せてはいけない項目（原価、在庫内訳など）が含まれることが多い。
- バックエンドを 2 つのプロジェクトに分ける条件：両側でスケール、デプロイ頻度、セキュリティ境界が明確に異なる場合。分割の前に本節を更新すること。

### 4.4 商品検索

- 商品の**キーワード検索**と、**通常の商品照会**（カテゴリ、価格帯、並び替えなど構造化された条件での一覧・絞り込み）は、別々の実装として分離する。両者を 1 つのクエリに混ぜない。【確定】
- キーワードを含む検索は、すべて `catalog` の検索用 port の背後に置く。通常の商品照会は、通常の Query 側（SQL）で実装する。【確定】
- MVP の検索実装は PostgreSQL による簡易実装とする。**精度は求めない。機能として動けばよい。**【確定】
  - 1 → 10 の段階で検索エンジンに置き換える前提なので、簡易実装のチューニングや日本語の形態素解析対応などはしない。
- 検索エンジンへの置き換え時は、商品イベントでインデックスを同期する read model とし、C 側 API は変えない。【提案】

## 5. クラウドネイティブ・水平スケール

【確定】アプリケーションは、同じものを複数インスタンス並べて動かせることを前提に設計する。

具体的なルール【提案】：

1. **ステートレス**：インスタンスはリクエストをまたぐ状態をメモリに持たない。HTTP セッションを使わない。ローカルディスクにファイルを保存しない。
2. **整合性は DB で担保する**：`synchronized` など JVM 内のロックで業務上の排他制御をしない。楽観ロック、条件付き更新、DB のロックを使う。
3. **ローカルキャッシュ**（Caffeine など）：インスタンス間で値がずれても許容できるデータに限り、必ず TTL を設定する。インスタンス間で共有する必要が出たら Redis 導入を検討し、本書を更新する。
4. **定期ジョブ**：複数インスタンスで重複実行されないよう、分散ロックで制御する。方式は最初に定期ジョブが必要になった plan で選定する。
5. **イベント**：少なくとも 1 回（at-least-once）配信を前提とし、リスナーは冪等に作る。Spring Modulith の未完了イベント再発行が、複数インスタンスで重複しないよう設定を確認する。
6. **設定**：環境変数で上書きできるようにする（12-factor）。秘密情報をリポジトリに置かない。
7. **ログ**：標準出力に構造化ログ（JSON）で出す（第 13 節）。
8. **ヘルスチェックと停止**：Actuator の liveness / readiness を有効化する。graceful shutdown を有効化する。
9. **DB マイグレーション**：アプリの起動とは分離し、デプロイごとに 1 回だけ実行するジョブとする。ローカル開発ではアプリ起動時の実行を許可する。
10. **コンテナ**：コンテナイメージとしてビルドする。デプロイ先（Kubernetes など）は第 17 節。

## 6. モジュール間連携の原則

- 同期呼び出しは「参照」または「即時に結果が必要」な場面だけに使う。それ以外はイベントにする。
- イベントは「すでに起きた事実」であり、過去形で命名する（例：`OrderPlaced`）。
- モジュール間でテーブルを共有しない。あるモジュールが他モジュールのテーブルを直接読み書きしてはならない。【踏襲】
- モジュールをまたぐ整合性は結果整合が基本。強い一貫性が必要な箇所（例：在庫の引当）は、spec に明記し、plan で方法を説明する。

## 7. 永続化

### 7.1 jOOQ

- 【確定】jOOQ を使う。
  - 理由：(1) MyIAM と一貫する。(2) フルレベルのモジュールでは集約を Factory で再構築するため、JPA の entity マッピングとは相性が悪い。jOOQ なら「ドメインモデル」と「テーブル」を分離したままにできる。(3) 在庫のような並行性の高い場面では SQL（条件付き更新、ロック）を正確に制御する必要があり、jOOQ のほうが素直。
- jOOQ の生成コードはバージョン管理しない。【踏襲】
- スキーマはモジュール単位（モジュールごとに PostgreSQL の schema を 1 つ）。【踏襲】
- 楽観ロック：並行して更新されうる集約には `version` カラムを持たせる。【踏襲】
- 時刻：UTC の `Instant`（`timestamptz`）で保存し、表示時にタイムゾーンを変換する。【踏襲】
- 識別子：UUID。【踏襲】

### 7.2 Flyway

- 【確定】スキーマの正本は Flyway のマイグレーションファイルとする（MyIAM の `docker/postgres/init/*.sql` 方式は採用しない。初回起動時しか実行されず、既存データへのスキーマ変更ができないため）。
- 配置場所は `backend/src/main/resources/db/migration/`。【提案】
- 一度コミットしたマイグレーションファイルは変更しない。変更は必ず新しいバージョンで行う。【提案】
- ファイル名のバージョンはタイムスタンプ形式とし、ブランチ間の番号衝突を避ける（例：`V202610081400__catalog_create_product.sql`）。【提案】
- jOOQ コード生成：Testcontainers で使い捨て PostgreSQL を起動 → Flyway を適用 → 生成。統合テストも Flyway で同じスキーマを作る。【提案】
- ローカル開発用のテストデータ（seed）は、スキーマのマイグレーションとは別の場所に置き、ローカル用 profile でのみ適用する。【提案】

### 7.3 金額

- 通貨は日本円のみ。多通貨対応はスコープ外。【確定】
- 金額は円単位の整数で保存・計算する。`float` / `double` は使用禁止。【提案】
- 値オブジェクト（`Money`）で表現し、プログラム中で生の数値を持ち回らない。【提案】
- 消費者向けの価格表示は税込（総額表示）を前提とする。【提案】
- 税率（標準税率・軽減税率）と端数処理は、価格を扱う spec で決める。【未定】

## 8. ファイル保存

- 商品画像などのファイルは、S3 互換のオブジェクトストレージに保存する。【確定】
- アプリのローカルディスクには保存しない（第 5 節）。DB にはオブジェクトのキーだけを持ち、URL はキーから組み立てる（将来 CDN を前に置けるようにする）。【提案】
- アップロードは署名付き URL（presigned URL）を使い、ブラウザからストレージへ直接送る。バックエンドはファイル本体を中継しない。【提案】
- ストレージは port の背後に置く。ローカル開発用の S3 互換エミュレーターは、最初にファイルを扱う plan で選定する。【提案】

## 9. API 規約

- RESTful JSON。パスのプレフィックスは 4.3 参照。
- **OpenAPI 定義は plan の成果物の一部とする（契約先行）。**【確定】
  - 正本は `api/openapi/` 配下（C 側・B 側で 1 ファイルずつ）。【提案】
  - plan では追加・変更する endpoint を OpenAPI で記述し、tasks の最初で正本に反映する。【提案】
  - バックエンドは OpenAPI から生成したインターフェースを実装し、フロントは生成した型を使う。生成ツールは最初の plan で選定する。【提案】
- リソース作成は `201` + `Location`、戻り値のない更新は `204`。【踏襲】
- 入力検証は presentation 層で Bean Validation、ドメインルールは domain 内で検査する。両方必要で、フロントだけに頼らない。
- エラーは MyIAM の体系を踏襲する：`ErrorCode`（`ErrorType`、i18n メッセージ、公開レベルを含む）、`BusinessException`、`SystemException`。`GlobalExceptionHandler` でレスポンスに変換する。各ドメインは自分の `XxxErrorCode` enum を持つ。【踏襲】
- エラーレスポンスの JSON 形式は最初の plan で決め、以降すべてのモジュールで統一する。【未定】
- ページング、ソートのパラメータ規約は最初の plan で決め、以降すべての一覧 API で統一する。【未定】

## 10. 認証・認可

【確定】MVP 段階では認証・認可を**実装しない**。ただし、**将来 MyIAM と連携する余地は残す**。

将来の連携を「書き換え」ではなく「追加」で済ませるため、今から次を守る：

1. domain と application は Spring Security の型に依存しない。「操作者は誰か」が必要な場合は、引数（例：`actorId`）で渡す。
2. `/api/admin/**` の各 endpoint について、必要な権限を spec に明記する。命名は MyIAM 流の `resource:action`（例：`product:write`、`inventory:write`）。後から認可チェックを機械的に付けられるようにする。
   - ただし、権限の**粒度**と**受け渡し方**（token に載せるか、サーバー側で role から解決するか）はここでは決めない。EC は機能が多く、すべての権限を token に載せると token（HTTP ヘッダー）が肥大化するおそれがあるため、MyIAM 連携時に見直す。spec に書く権限名は「必要な操作の記録」として扱い、最終的な権限モデルではない。【確定：連携時に随時見直す】
3. C 側と B 側のパスプレフィックス（4.3）が、将来の認可ルールの境界線になる。
4. 将来は、EC が Resource Server として MyIAM（JWT）に接続する想定。これは方向性であり、MVP の範囲ではない。

注意：MVP では `/api/admin/**` は無防備である。**MVP 版を公開ネットワークにデプロイしてはならない。**

## 11. 外部連携（決済・物流）

- 外部サービスは必ず port の背後に置き、infrastructure で実装する。外部の型、フィールド、エラーコードを domain / application に漏らさない。【腐敗防止層の考え方を踏襲】
- 選択の優先順位：【確定】
  1. 無料で、実際の挙動を模擬できる外部 API（sandbox / test mode）がある → 外部を使う
  2. ない → 内部 mock
- 内部 mock と外部実装は**同じ port** を実装し、Spring profile や設定で切り替える。mock の挙動（成功、失敗、タイムアウト、遅延コールバック）はテストから制御できること。
- 外部連携ごとに、対応する spec に次を明記する：失敗時の振る舞い、リトライと冪等性の扱い、コールバック（webhook）の検証方法。

## 12. テスト

### 12.1 構成

- MyIAM の 2 層構成を踏襲する：【踏襲】
  - `src/test`：単体テスト。集約と値オブジェクトの振る舞い。JUnit + AssertJ のみで Spring は起動しない。
  - `src/integrationTest`：`@SpringBootTest` + Testcontainers（PostgreSQL）。Docker 必須。
  - テストは `main` と同じパッケージ構成に置く。
- 必須の統合テストの種類：
  - Modulith の境界テスト
  - Repository テスト（永続化、再構築、差分更新、イベント発行）
  - 並行性テスト（在庫の引当・減算で売り越しが起きないこと）。並行性の不変条件を持つモジュールのみ
  - 外部連携の port テスト（mock と実実装で挙動が一致すること）
- E2E は MVP では自動化せず、`.http` ファイルで手動確認する。フロントのテスト方針は第 17 節。【未定】

### 12.2 テスト先行（TDD）

【提案】受け入れ条件（AC）を起点に、テストを先に書く。ただし対象によって厳しさを変える。

| 対象 | 進め方 |
|------|--------|
| domain（集約、値オブジェクト） | 厳密な TDD。レッド → グリーン → リファクタ |
| AC 単位の振る舞い | 実装前に受け入れテスト（統合テストまたは MockMvc）を書き、レッドから始める |
| infrastructure、Controller の配線 | 実装後にテストを書いてよい |
| フロントの UI | TDD を求めない |

- **すべての受け入れ条件に、少なくとも 1 つのテストを対応させる**。テスト名またはコメントに AC 番号を記す。
- `tasks.md` では、テストのタスクを対応する実装タスクより前に置く。

## 16. SDD ワークフロー

1. **Constitution**（本書）：長期ルール。
2. **Spec**（`docs/specs/NNN-<feature>/spec.md`）：「何を、なぜ」と受け入れ条件だけを書く。**実装は書かない**（クラス名、テーブルのカラム、フレームワークを書かない）。
3. **Plan**（`plan.md`）：spec に基づき、アーキテクチャ、データモデル、API 設計（OpenAPI）、モジュールのレベルを決める。本書との対照を項目ごとに行うこと。
4. **Tasks**（`tasks.md`）：plan を小さく検証可能なタスクに分割し、各タスクに対応する AC を記す。テストのタスクを実装より先に置く。
5. **実装**：tasks に沿って進める。

ルール：

- **spec がコードに先行する。** 実装中に spec の誤りが見つかったら、先に spec を直し、次にコードを直す。コードだけを直すことは許されない。
- 1 つの spec は、単独で検証できる機能の縦切り 1 つに対応させる。MVP はまず商品と在庫（spec 001）から始め、残りはコアフローの順に広げる。
- spec には次を含める：背景と目的、User stories、受け入れ条件（AC-1、AC-2…と採番）、Non-goals、Open questions。
- Open questions が空になるまで plan に進まない。
- 受け入れ条件は検証可能であること。「できた」か「できていない」かが判断できるように書く。
- spec と plan の commit は分け、commit メッセージに変更理由を書く。
