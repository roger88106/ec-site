# コメントの書き方

原則（何を書き、何を書かないか、言語）は [constitution](../constitution.md) 第 4.5・14 節。本書は書き方の形を書く。

## 1. 何を書くか

- **規則**：今のコードが何をするか、なぜそうするか（業務の規則、AC・BR の番号、根拠の文書の節）を書く。決定の経緯（前の実装との違い、採らなかった案）は書かず、コミットメッセージに書く。
- **理由**：コメントを、今のコードの説明としていつも正しく保つため（constitution 4.5、15）。
- **確かめ方**：人手（見直し）。

根拠は、文書の名前と節で書く（例：`（店舗画面の構成 第 4.2 節）`、`（constitution 9）`、`（AC-81）`）。

## 2. Java（Javadoc）

- **規則**：クラスと、すべてのメンバー（private を含む）に Javadoc を書く。1 文目に何かを書き、続けて補足が要るときは 1 文目の後に `<br />` を置く。メソッドには `@param`・`@return`（例外を投げる条件があれば `@throws`）を書く。record は、項目を `@param` で書く。
- **理由**：constitution 4.5。
- **確かめ方**：人手（見直し）。

```java
/**
 * 違反した制約の名前を取り出す。<br />
 * jOOQ や Spring の例外に包まれていても、原因をたどって PostgreSQL のエラーを探す。
 *
 * @param ex 例外
 * @return 制約名。制約違反でなければ空
 */
```

## 3. TypeScript（TSDoc）

- **規則**：モジュールの最上位にある関数・部品・型・定数に `/** */` を書く。型の項目にも、意味が名前だけで分からないものは書く。関数には `@param`・`@returns` を書き、`@param` の説明の位置を揃える。1 行で書けるものは 1 行にする。shadcn/ui の生成物には書かない。
- **理由**：Java と同じく、使う側が実装を読まずに意味を引けるようにするため。
- **確かめ方**：人手（見直し）。

```ts
/** カートを移した結果の知らせ（AC-123）。カートの画面で一度だけ示す */
export type CartMergeNotice = {
  /** 数量を 10 に切り詰めた品目（切り詰めた後の数量） */
  truncated: NoticeItems
}
```

## 4. 処理の中のコメント

- **規則**：読んだだけでは理由が分からない処理（例外の扱い、順番に意味があるもの、外部の仕組みの癖）の前に、1 行で理由を書く。何をしているかが読めば分かる処理には書かない。
- **理由**：書き直すときに、意味のある順番や扱いを壊さないため。
- **確かめ方**：人手（見直し）。

```ts
// redirect は例外で移動を知らせるので、try の外で呼ぶ
redirect(`/checkout/${checkoutId}`)
```
