# カートモジュール

消費者のカートと、その品目（バリアントと数量）を管理する。

| 項目 | 内容 |
|------|------|
| レベル | B（品目の上限と合算だけで、状態遷移を持たない） |
| 依存 | 商品カタログ・在庫（API）、会員（API。presentation だけ） |
| 関連 spec | [002](../../specs/archive/mvp/002-cart-and-order)、[003](../../specs/archive/mvp/003-auth)、[007](../../specs/archive/mvp/007-payment)、[017](../../specs/archive/mvp/017-stability)、[019](../../specs/archive/mvp/019-mvp-completion) |

## カート

- カートは、品目の一覧、バージョン、最終更新日時を持つ。品目は、バリアント、数量、入れた日時を持つ。
- 価格は持たない。表示のたびに注文モジュールの見積もりで今の価格を求める。
- カート ID は推測できない UUID。ログインせずに作ったカート（会員なし）は、ID を知っている人だけが使える。
- 変更（追加・数量の変更・削除・空にする・注文した品目を除く）のたびにバージョンを上げる（注文モジュールが、注文手続きの後の変更を見つけるため）。
- 注文の与信が成功したら、注文モジュールが、注文した品目（バリアント）を数量によらず行ごと除かせる。注文の後に追加した品目は残る。支払の期限が切れても、カートから再び注文できるようにするため。

### 品目の追加と変更

| 決まり | 内容 |
|--------|------|
| 合算 | 同じバリアントは数量を合算する。品目は入れた順に並べる |
| 上限 | 数量は 1〜10、品目は 30 まで（合算の結果で判定）。数量の上限は、ドメインの定数、契約の `maximum`、カートの品目と注文の明細の DB の CHECK の 4 か所に同じ値で置く。変えるときは全てを変える（カートの上限の数量で注文できることを、注文の統合テストで確認する） |
| 追加・増量の確認 | 商品カタログで「C 側に表示される商品の、販売停止でないバリアント」か、在庫で販売可能数が数量以上かを確認する ※1 |
| 減量・削除 | 確認しない |

※1：確認するのは追加・変更の時点だけ。その後に買えなくなった品目は、カートの表示と注文で扱う。

### 期限

- 最終更新から 30 日たったカートは、読むときに空として扱い、次に書くときに品目を削除してから書く。
- 期限が切れたカートは、片付けのジョブが品目と共に削除する（既定では期限で削除する。[バックエンドのアーキテクチャ](../backend-architecture.md) 第 5 節）。削除したカートを使う操作は 404 になり、店舗画面は新しいカートを作る。会員のカートは、次に求めたときに再作成する。
- 読み込んだ後に片付けで削除されたカートを保存すると、同時の変更（409）になる。

### 会員のカート

- 会員のカートは会員 ID を持ち、会員ごとに 1 つ。会員が初めて使うとき（`/me/cart`）に作る。ログインせずに作ったカートが、後から会員を持つことはない。
- 持ち主の会員だけが読み書きできる。他の人にはカートがないときと同じく 404（存在を推測させない）。
- 持ち主の確認は、カートと要求した会員 ID（ログインしていなければなし）で行う。会員なしのカートは、だれでも使える。

### カートを移す

ログインせずに使っていたカートの品目を、会員のカートへ移す。店舗画面のサーバーが、ログインの直後に 1 回呼ぶ。

- 移すカートの品目を、元のカートに入れた順に入れる。同じバリアントは合算し、10 を超えたら 10 に切り詰める。品目が 30 に達したら残りは移さない。
- 切り詰めた品目と移せなかった品目（バリアントと数量）を返し、画面が一度だけ知らせる。
- 商品カタログ・在庫は確認しない（買えない品目は、表示と注文で扱う）。
- 移し終えたら移すカートを空にする（2 回呼ばれても 2 回目は何も起きない）。
- 移す元にできるのは会員なしのカートだけ（会員のカートなら 404）。期限切れのカートは空として扱う。
- 会員のカートや移すカートが変わったら、カート変更のイベントを出す（その会員の注文手続きの引当を解くため）。

## 構成

```
cart/
├── api/                    # 店舗・注文に公開する API
├── event/                  # カート変更のイベント
├── presentation/           # store.yaml から生成したインターフェースを実装
├── application/            # カートの操作
│   └── port/               # リポジトリと腐敗防止層の port（選べるバリアントか、販売可能数）
├── domain/                 # カート、品目、エラー
└── infrastructure/
    ├── persistence/        # リポジトリの実装
    └── directory/          # 商品カタログ・在庫の腐敗防止層
```

入れるときの販売可能数は、自分の引当も数える ※2。

※2：カートは注文手続きを知らないため。注文手続きの途中でカートに戻って同じ品目を増やすと、自分の引当の分だけ少なく判定されることがあるが、引当はカートの変更や 15 分の期限で解かれるので受け入れる。

## 他のモジュールへの公開

| 種類 | 内容 | 利用者 |
|------|------|--------|
| API | カートの品目・バージョン・会員 ID（期限切れは品目が空）、注文した品目を除く（注文が受付になるのと同じトランザクション） | 店舗、注文 |
| イベント | カート変更（カート ID） | 注文（引当を解く） |

## データモデル

[V202610111100__cart_create_cart.sql](../../../backend/ecsite/src/main/resources/db/migration/V202610111100__cart_create_cart.sql)、[V202610121100__cart_add_member_id.sql](../../../backend/ecsite/src/main/resources/db/migration/V202610121100__cart_add_member_id.sql)

- バリアントと会員は他のモジュールの ID なので、外部キーは張らない。
- 品目は入れた順の連番を持つ。保存では品目を削除して再挿入するので、連番は再採番される。
- 保存は、保存済みのバージョンが読み込んだときの値と一致するときだけ行う（同時の変更は 409）。
- 会員ごとに 1 つは一意制約で守る（同じ会員の初回の要求が同時に来ても 1 つ）。
