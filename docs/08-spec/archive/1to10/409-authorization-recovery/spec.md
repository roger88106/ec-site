# Spec 409：与信の通知が届かなくても、期限切れのジョブで与信済みにする

種類：機能　規模：M　ステータス：確定

## 背景と目的

与信済みへ進む経路は与信の成功の通知だけで（BR-17）、通知が届かないと注文は支払待ちのまま進まなくなる。期限切れのジョブは、決済サービスで支払済みの支払を「通知を待つ支払」として記録し、次回以降の検索の対象から外す ※1。

支払待ちの注文は、運営者もキャンセルできず（AC-158）、支払画面も開けない。検知は warn のログの件数だけである。進まなくなるのは次のとき（Stripe の文書 docs.stripe.com/webhooks、2026-11-06 確認）。

- 本番で最長 3 日の再送を過ぎて気づかず、手動の再送もしない。
- 再送するときに送信先が無効か削除済みである。
- `checkout.session.completed` を送信先に登録していない。
- sandbox では、再送が数時間で上限に達する。

進まなくなった後は、在庫は減ったまま戻らず、与信期限が近づく。通知を受けた時刻を与信の時刻にしているので、通知が遅れると、与信期限が実際より後に計算される。

目的は、通知が届かなくても、期限切れのジョブが決済サービスから与信を取得して、支払を与信済みにすること。そのために BR-17 を変更する（利用者の決定、issue のコメント、2026-11-06）。決めたこと：

- 期限の処理で、決済サービスで支払済みと確認できたときは、PaymentIntent を取得して与信済みにする。
- 与信の時刻は、PaymentIntent の時刻を使う。
- 既に通知を待っている支払の行も、処理の対象に戻す。

追跡の issue は #409。関わる文書は、[決済モジュール](../../03-機能仕様/payment.md)と[決済の設計](../../02-設計/payment.md)。

※1：期限切れのジョブの記録は `PaymentExpiryJob.java:68-71`、検索の対象から外す条件は `JooqPaymentRepository.java:140`。支払待ちの注文をキャンセルできない判定は `Order.java:376`。

### 確認した範囲と限界

| 確認した内容 | 方法と出典 |
|--------------|------------|
| 完了した Session の中に PaymentIntent の ID があり、PaymentIntent を読める | sandbox の完了済みの Session 3 件を読んだ（2026-11-06） |
| PaymentIntent の作成の時刻は、Session の作成より 33〜1319 秒後で、与信（Charge）の作成より 0〜18 秒前 | 同上 |
| 与信を取り消した PaymentIntent（`canceled`）の Session も `complete` のまま残る | 同上（2 件） |
| sandbox の Charge の `capture_before` は、作成から 30 日後 | 同上。機能仕様の与信期限の既定は 7 日で、この spec では変えない（Non-goals） |

- 読んだのは過去の Session で、PaymentIntent の状態は `succeeded` 1 件、`canceled` 2 件。`requires_capture` の Session は読んでいない。
- 読み方は REST で、API のバージョンは本番の実装と同じとは確認していない。本番の実装で sandbox を読むことを T409-01-04 で確認する。
- 与信の時刻が PaymentIntent の作成の時刻なので、実際の与信より早い時刻になる（読んだ 3 件では 0〜18 秒）。与信期限も、その分だけ早く計算される。

## スコープ

| 含める | 含めない |
|--------|----------|
| 期限切れのジョブで、決済サービスから与信を取得して与信済みにする | 与信の成功の通知の処理の変更（決定 10） |
| 既に待っている支払も、同じ処理の対象にする | 検知の仕組み（メトリクス、アラート）の追加（Non-goals） |
| mock とテスト用の決済サービスに同じ操作を加える | 支払画面から戻ったときに決済サービスに問い合わせること（Non-goals） |
| BR-17、AC-311、AC-312 の変更、機能仕様・設計・用語集の更新 | API の契約と DB の構造の変更（非機能要件） |

決定：

1. 規模は M にする。理由：BR と AC を変えるが、API の契約と DB の構造を変えず、決済モジュールの中で閉じるため（[開発の進め方](../../05-開発規則/workflow.md)の「規模と push」）。
2. 決済サービスの port に操作「与信を取得する」を加える。支払画面 ID を受け取り、与信の参照と与信の時刻を返す。支払画面を閉じる操作の結果は変えない。理由：既に待っている支払は、画面を再び閉じる必要がないため。閉じる結果に与信を持たせると、画面を開く処理の「使わない画面を閉じる」呼び出しでも Stripe の読み取りが増えるため。

   | 論理名 | 識別子 |
   |--------|--------|
   | 与信を取得する | `fetchAuthorization` |
   | 取得した与信 | `PaymentGateway.Authorization` |

3. Stripe の実装は、PaymentIntent を含めて Session を取得する。与信の参照は PaymentIntent の ID、与信の時刻は PaymentIntent の作成時刻にする。Session が `complete` でないか、PaymentIntent がないときは失敗にする（失敗の種類は他の操作に合わせる）。
4. 支払の集約の与信の反映は、与信の時刻を受け取る形にする。通知の処理は今までどおり現在時刻を渡す。遷移は変えない（与信済みにする操作は冪等）。与信の成功のイベントの発生時刻は現在時刻のまま。
5. 用語「通知を待つ支払」を「与信の反映を待つ支払」に変える（機能仕様、設計、用語集、環境変数の説明、AC-311、AC-312、ログの文）。理由：通知だけでなく、ジョブが与信を取得したときにも待ちが解消されるため。識別子（`awaiting_authorization_since`、`awaitAuthorization`）には「通知」が入っていないので変えない。DB の列のコメントはマイグレーションを追加しないと変わらないので変えない。
6. テスト用の決済サービスに、与信の取得を失敗させる操作を加える。mock は「支払を済ませた」時刻を記録し、与信の時刻として返す（mock に時計を渡す）。
7. ジョブの取得で与信済みにしたときは、warn のログに支払 ID を出力する。理由：ジョブが与信済みにすると通知が届かないことが注文に現れなくなるので、ログで気づけるようにするため。
8. 既に待っている支払は、毎回の実行で検索の対象に入れる（下の処理の順 2）。理由：データの移行が要らず、取得に失敗しても次の回で再試行できるため。
9. 与信の取得に失敗した支払は、与信の反映を待つ支払のまま残し、次の回で再試行する。理由：期限切れの検索の対象に残すと、失敗が 100 件を超えたときに新しい期限切れの支払が処理されなくなり、AC-311 に反するため。
10. 通知の処理の与信の時刻は、通知を受けた時刻のままにする。理由：支払の期限を過ぎるとジョブが先に与信済みにするので、ジョブが動いていれば、ずれは支払の期限の長さ（既定も上限も 30 分）以内になるため。通知の処理に Stripe の呼び出しと失敗の経路を増やさない。
11. 通知とジョブの取得は、先に反映した方の与信の時刻と参照を残す。後から届いた通知は状態を変えない（今の冪等な遷移のまま）。
12. 決済サービスで与信が切れていた（PaymentIntent が `canceled`）支払も、他の支払と同じく与信済みにする。与信の時刻が古いので「期限が近い」と表示され、出荷すると売上確定が与信期限切れで失敗し、運営者がキャンセルできる。与信の取消は、取消済みとして成功する。理由：通知が遅れて届いた場合と同じ扱いになり、新しい分岐が増えないため。
13. 片付けのジョブは変えない。注文手続きは期限の 1 日後に削除されるので（[バックエンドのアーキテクチャ](../../02-設計/backend-architecture.md)の表）、その後に与信済みになると、注文した品目がカートから除かれない。この問題が起きるのは、既に待っている古い支払と、取得の失敗が 1 日以上続いた支払だけである。理由：影響はカートに品目が残ることだけで、修正すると注文モジュールも変わり、規模が L になるため。
14. 順 2 で、決済サービスへの接続の失敗（外部サービスのエラー）が 3 件続いたら、その回の順 2 を打ち切り、その旨を warn のログに出力する。他の失敗と成功は、連続した件数を 0 に戻す。理由：次の「失敗の影響」のとおり、ロックの上限を超えないようにするため。接続の失敗だけを数えるのは、取得に失敗し続ける支払が先頭にあっても、後ろの支払を処理するため。

期限切れのジョブの 1 回の実行は、次の順で処理する。

| 順 | 処理 |
|----|------|
| 1 | 今までどおり、期限を過ぎた未払いの支払（与信の反映を待つ支払を除く）の支払画面を閉じる。支払済みなら与信の反映を待つ支払にする。閉じられたら支払なしにする |
| 2 | 与信の反映を待つ支払を、待ち始めた時刻の古い順に上限（100 件）まで検索し、1 件ずつ与信を取得して与信済みにする。トランザクションの外で取得し、行ロックの後に反映する |
| 3 | 今までどおり、長く待つ支払の件数を warn のログに出力する |

- 順 1 で待ち始めた支払は、順 2 の上限に入り、取得に成功すれば、同じ実行で与信済みになる。
- 既に待っている支払は、順 2 の検索に入るので、データの移行は要らない。

### 順 2 の失敗の影響

| 項目 | 内容 | 扱い |
|------|------|------|
| 1 件の時間 | 決済サービスが応答しないと、1 回の取得で最大約 75 秒かかる ※2 | — |
| ロックの上限 | ジョブのロックの上限は 10 分 ※3。100 件が全て応答しないと約 125 分かかり、上限を超える | 決定 14 で、3 件（約 225 秒）の失敗で打ち切る |
| 断続的な失敗 | 接続の失敗の間に成功が入ると、連続した件数が 0 に戻るので打ち切らない。応答のない取得が多いと、ロックの上限を超えうる | 既知の限界とし、今回は修正しない。理由：起きるのは取得の重複と時間の超過だけで、業務の正しさは行ロックと冪等な遷移で保つため |
| 先頭の詰まり | 古い順に 100 件なので、取得に失敗し続ける支払が 100 件以上あると、新しく待ち始めた支払が処理されない | 既知の限界とし、今回は修正しない。理由：件数が少なく、AC-312 の警告で気づけるため |
| 順 1 の時間 | 順 1 も、決済サービスが応答しないとロックの上限を超えうる。今の実装にもある振る舞いである | この spec では変えない。理由：ロックは重複実行を減らすためのもので、業務の正しさは行ロックと冪等な遷移で保つため（`SchedulerLockConfig.java:16`） |

※2：接続 5 秒と応答 20 秒のタイムアウト（[環境変数](../../06-手順書/environment.md)の「バックエンド」）を、最初の 1 回と再試行 2 回の 3 回分足した値（`StripeConfig.java:24`）。再試行の間の待ち時間は含まない。

※3：`SchedulerLockConfig.java:26`。

|----|------|------------|------|
| US-409-1 | 消費者 | 与信の通知が届かなくても、支払った注文を受け付けてもらえる | 支払ったのに注文が進まない状態を防ぐため |
| US-409-2 | 運営者 | 与信の通知が届かなかった注文を、通常の注文と同じに出荷・キャンセルできる | 誰も動かせない注文を残さないため |

## 受け入れ条件

### US-409-1 与信の通知が届かなかった支払の受付（C / P1）

- **AC-409-1** 通知が届いていなくても、期限切れのジョブが決済サービスで支払済みと確認した支払は与信済みになり、注文は受付になる。
- **AC-409-2** AC-409-1 の支払の与信の時刻は、決済サービスの PaymentIntent の作成時刻になり、与信期限はこの時刻から計算する。
- **AC-409-3** AC-409-1 より前から与信の反映を待っていた支払も、次のジョブの実行で与信済みになる。
- **AC-409-4** AC-409-1 の後に与信の成功の通知が届いても、支払の状態と与信の時刻は変わらず、与信の成功のイベントは 1 回だけ発行される。
- **AC-409-5** AC-409-1 の処理の前に通知が届いていれば、与信の時刻は通知を受けた時刻のままで、与信の成功のイベントは 1 回だけ発行される。
- **AC-409-6** 決済サービスから与信を取得できないときは、その支払 ID を warn のログに出力し、支払は与信の反映を待つ支払のまま残す。打ち切る場合（AC-409-10）を除き、残りの支払を処理する。次のジョブの実行で再試行する。
- **AC-409-9** AC-409-1 の処理で与信済みにしたときは、その支払 ID を warn のログに出力する。
- **AC-409-10** 与信の取得で、決済サービスへの接続の失敗が 3 件続いたら、その回の与信の取得を打ち切り、その旨を warn のログに出力する。次のジョブの実行で再試行する。

### US-409-2 与信の通知が届かなかった注文の出荷・キャンセル（B / P1）

- **AC-409-7** AC-409-1 で受付になった注文は、与信の参照で売上を確定できる（出荷の登録）。
- **AC-409-8** 決済サービスで与信が切れていた支払も与信済みになり、注文の出荷の登録は与信期限切れで失敗する。その注文を運営者がキャンセルできる。

### 前の spec の AC の変更

AC-311 と AC-312 の内容を次のとおりに変更する。状態は「変更」、変えた spec は `409`。

```
AC-311：与信の反映を待つ支払が 1 回の処理の件数を超えて滞留しても、それより新しい期限切れの支払を処理する。根拠は[決済モジュール](payment.md)の「支払の期限」。
AC-312：与信の反映を待つ支払が、待ち始めてから決めた時間（設定で変更できる）を過ぎても残っていたら、警告のログに件数を出力する。根拠は[決済モジュール](payment.md)の「支払の期限」。
```

AC-158 は変えない（支払待ちのキャンセルはできないまま）。理由：与信の反映を待つ支払は、ジョブで与信済みになり、受付の注文としてキャンセルできるようになるため。

## 業務ルール

- **BR-409-1** 支払の結果は、決済サービスからの通知で受け取る。例外は期限切れのジョブで、決済サービスで支払済みと確認した支払は、決済サービスから与信を取得して反映する。BR-17 の「通知だけで受け取る」をこの規則に置き換える。署名の確認、重複、順序、再送の BR-17 の規則は変えない。
- **BR-409-2** 支払画面から戻ったときに、決済サービスに問い合わせない（今の規則を維持する）。

## 非機能要件

- **NFR-409-1** API の契約と DB の構造を変えない。
- **NFR-409-2** 画面の表示を変えない。
- **NFR-409-3** 与信の取得は、トランザクションの外で行い、外部の応答を待つ間に行ロックを持たない。

## Non-goals

| 項目 | 理由 |
|------|------|
| メトリクスとアラートの追加 | ジョブの取得に成功すれば、通知を待ったまま進まない支払は残らない。ジョブの取得と取得の失敗は warn のログに出力する |
| 支払の期限の前に決済サービスへ問い合わせる | 期限までは通知を待てる。期限の後のジョブで与信済みにできる |
