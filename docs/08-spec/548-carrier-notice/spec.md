# Spec 548：物流サービスの通知の発生日時を反映し、出荷のロックの順をそろえる

種類：整理　規模：M　ステータス：草案

## 背景と目的

物流サービスの通知のエンドポイントは、通知の本文の発生日時をログに出力するだけで、受け取りの port に渡していない。配送状態の変化のイベントの発生日時と、出荷の「最後に通知を反映した日時」には、処理した時刻（アプリの時計）を使っている。再送や順序の入れ替わりで処理が遅れると、レポートの状態の履歴の時刻が実際とずれる。出荷の照合は（配送業者、送り状番号）だけなので、古い通知の再送や、配送業者が再利用した送り状番号で、後から作った別の出荷が進みうる。#458 のレビューで、2 つのモデルがどちらもこの点を挙げた（#487）。

同じ配送業者と送り状番号の出荷を、行をロックして複数の出荷を取るとき、並び順の指定がない。配送業者と送り状番号の組は一意でないので、同じ番号の通知が同時に 2 つ届くと、2 つのトランザクションが行を違う順でロックし、デッドロックになるおそれがある。他のリポジトリは、ロックを取る順を ID でそろえている（#500。#487 の最後の段落と同じ内容）。

この spec は、通知の発生日時を出荷に反映し、同じ送り状番号の出荷のロックの順をそろえる。消費者・運営者に見える振る舞いは、レビューで見つけた不具合の修正の 2 点だけ変わる（DN-548-1）。API の契約（OpenAPI）、DB の構造、AC、イベントの項目は変えない。追跡の issue は #548（組の issue）。sub-issue は #487 と #500。#544（リリースの前の整理）の段階 3 の線 B の 2 番目である。

## スコープ

| 含める | 含めない |
|--------|----------|
| 通知の発生日時を受け取りの port に渡し、出荷日時より前の通知を反映しないこと | 通知の署名の鍵を配送業者ごとにすること（#477 で扱う） |
| 発生日時が範囲の外（極端に古い、未来）の通知を拒否すること | 送り状番号の再利用を見分ける仕組み（出荷日時より後の再利用の通知） |
| 配送状態の変化のイベントの発生日時に、通知の発生日時を使うこと | 署名に時刻を含めること |
| 同じ送り状番号の出荷のロックの順を ID でそろえること | レポートのモジュールのコードの変更 |
| 出荷の機能仕様と設計の文書、イベントの説明の修正 | |

決定（推奨。issue 担当のセッションに確認を求める）：

- 規模：M とする。判定の表の L の条件（API の契約・DB の構造の変更、2 つ以上のモジュール）に当たらない。変えるコードは出荷のモジュールと、共通のイベントの型の説明（Javadoc）1 か所だけである。
- 決定 1（port）：受け取りの port に、通知の発生日時を渡す引数を加える。
- 決定 2（出荷日時より前の通知）：通知の発生日時が出荷日時より前なら、その出荷には反映しない。
  - 反映しないときは、配送状態も「最後に通知を反映した日時」も変えず、イベントも発行しない。
  - 同じ日時は反映する。
  - 同じ送り状番号の出荷が複数あるときは、出荷ごとに判定する。
  - 応答は今の「順位が上がらない通知」と同じ 200 で、結果は「変えなかった」とする。
  - 判定は出荷（集約）で行う。
  - 理由：出荷日時より前に起きた変化は、この出荷の荷物で起きたものではないため。再送された古い通知か、送り状番号が再利用される前の荷物の通知である。
  - 注意：物流サービスが荷物を受け取った後に運営者が出荷を登録すると、受け取りの通知は反映されない（Non-goals）。
- 決定 3（範囲の外の発生日時）：通知の発生日時が、現在時刻より「古さの上限」以上前か、現在時刻より「未来の許容」を超えて先なら、署名が合っていても処理せず 400 を返す。
  - 判定は、エンドポイントで、本文の読み取りの後、port を呼ぶ前に行う。
  - 古さの上限は 30 日、未来の許容は 5 分を既定にする。
  - どちらも出荷の設定の値にする。設定のキーは実装のタスクで決める。
  - 下限は spec 553 の規則に合わせて 1ms 以上とし、null を許さない。
  - 理由（400）：本文が読めない通知と同じく、再送しても受け付けられないことを、送信元に知らせるため。出荷の設計の「通知のエンドポイント」の既存の理由と同じである。
  - 理由（未来も拒否）：決定 4 で発生日時をレポートの履歴に使うので、未来の日時が入ると履歴が誤るため。#487 の本文は「極端に古い」だけを挙げているが、同じ理由で含める。
  - 理由（5 分）：物流サービスとアプリの時計のずれを許すため。
- 決定 4（イベントの発生日時）：配送状態の変化のイベントの発生日時には、通知の発生日時を使う。
  - 出荷の「最後に通知を反映した日時」は、今のまま処理した時刻（アプリの時計）を使う。
  - 出荷を作ったときのイベントの発生日時は、今のまま出荷日時とする。
  - 理由（イベント）：レポートの状態の履歴は「いつ状態が変わったか」を記録するもので、物流サービスで状態が変わった時刻が正しいため。決定 2 と 3 で、発生日時は出荷日時以後、現在時刻に未来の許容を足した時刻以前に限られる。
  - 理由（最後に通知を反映した日時）：名前のとおり、アプリが反映した時刻の記録のため。
  - 共通のイベントの型の説明は、今「発生時刻はアプリの時計から得た時刻にする」としている。「外部のサービスが通知した日時を使うイベントは、その日時」を加える。
- 決定 5（ロックの順）：同じ配送業者と送り状番号の出荷を、行をロックして取るとき、出荷 ID の順に取る。
- 決定 6（文書）：
  - 出荷の機能仕様の「通知のエンドポイント」と「状態の遷移」に、決定 2〜4 の規則を書く。AC も業務規則の番号（BR）も追加しない。
  - 出荷の設計の「通知のエンドポイント」に、範囲の外の発生日時が 400 であることと理由を書く。「物流サービスの通知の反映」の図の後に、ロックの順を書く。
  - 環境変数で渡す設定にしたときは、加える 2 つの設定を環境変数の一覧に書く。環境変数で渡すかは、実装のタスクで決める。
  - 配送状態の変化のイベントの説明で、発生時刻を「出荷日時、または通知を反映した日時」から「出荷日時、または通知の発生日時」に修正する。
  - 出荷の設計で署名の時刻を確認しない理由の箇条を、範囲の外の発生日時の拒否と、出荷日時による判定を加えて書き換える。

## 目的と完了条件

### DS-548-1 古い通知や範囲の外の通知で、出荷が進まない（D / P1）

- **DC-548-1** 通知の発生日時が出荷日時より前なら、配送状態と最後に通知を反映した日時が変わらず、イベントが発行されないことを、テストで確認している。同じ日時なら反映することも確認している。
- **DC-548-2** 送り状番号が同じ 2 つの出荷のうち、出荷日時が通知の発生日時以前の出荷だけが進むことを、テストで確認している（再利用された送り状番号の場合）。
- **DC-548-3** 発生日時が古さの上限以上前の通知と、未来の許容を超えて先の通知が 400 になり、出荷が進まないことを、テストで確認している。上限と許容の境界のすぐ内側の値が受け付けられることも確認している。
- **DC-548-4** 古さの上限と未来の許容の設定に下限（1ms 以上、null 不可）があり、許す範囲の外の値で起動できないことを、テストで確認している。

### DS-548-2 配送状態の変化の発生日時が、物流サービスの日時になる（D / P1）

- **DC-548-5** 通知で配送状態が進んだときのイベントの発生日時が、通知の発生日時であることを、テストで確認している。
- **DC-548-6** 出荷の最後に通知を反映した日時が、処理した時刻であることを、テストで確認している。
- **DC-548-7** 出荷の機能仕様と設計、イベントの説明、共通のイベントの型の説明が、決定 2〜4 と 6 の形になっている。

### DS-548-3 同じ送り状番号の出荷のロックの順が決まっている（D / P1）

- **DC-548-8** 同じ配送業者と送り状番号の出荷を、行をロックして取るとき、出荷 ID の順に返ることを、テストで確認している。

### DS-548-4 検査が通る（D / P1）

- **DC-548-9** `./gradlew check` が通る。

## 非機能要件

- **DN-548-1** 消費者・運営者に見える振る舞いを変えない。例外は、DN-548-4 の後の表の 2 件である。理由：レビューで見つけた不具合の修正のため（[開発の進め方](../../05-開発規則/workflow.md)の「コードと文書の食い違い」）。前例は spec 134 の DN-134-1 である。
- **DN-548-2** 例外の 2 件は、テストを先に書いて失敗（レッド）を確認してから修正する。
- **DN-548-3** API の契約（OpenAPI）、DB の構造、AC、イベントの項目を変えない。
- **DN-548-4** アーカイブした spec を変えない。

DN-548-1 の例外は、次の表のとおり。

| 修正 | 今 | 修正した後 |
|------|-----|------------|
| レポートの状態の履歴の、配送状態の変化の発生日時 | 通知を処理した時刻 | 物流サービスの通知の発生日時 |
| 出荷日時より前の通知と、発生日時が範囲の外の通知 | 配送状態の順位が上がれば進む | 進まない（範囲の外は 400） |

## Non-goals

| 項目 | 理由 |
|------|------|
| 通知の署名の鍵を配送業者ごとにする | #477 で扱う |
| 出荷日時より後に再利用された送り状番号の見分け | 物流サービスの仕様（再利用の通知の形）が決まっていないため。実際の物流サービスを接続するときに扱う |
| 荷物の受け取りが出荷の登録より前になる場合の許容 | 受け取りの時刻が物流サービスでどう通知されるかが決まっていないため。実際の物流サービスを接続するときに再検討する |
| 署名に時刻を含めること | 古さの上限を超える通知は拒否し、出荷日時より前の通知は反映しないため。範囲の内の再送は、配送状態の順位が上がらなければ反映されない |
