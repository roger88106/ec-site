# フロントの観点

画面のコード（店舗画面、管理画面、共有）と E2E のコードを書く・変えたときに、結果を返す前の自己確認とレビューの両方で読む。規則の文は、表の「規則の正本」で読む。

| 観点 | 見る問い | 過去の見落としの例 | 規則の正本 |
|------|----------|--------------------|------------|
| 共有の部品の既定の振る舞い | 共有の部品の既定の振る舞いは、全ての画面で困らないか。 | 背景の再取得が 1 回失敗すると、入力中のフォームが誤りの表示に替わった。1 つの version を複数のカードが別々に持ち、保存が 409 になった | [管理画面の構成](../../../../docs/02-設計/apps/admin.md)の「フォーム」 |
| 失敗の経路のテストの分担 | 送信、サーバーアクション、再描画の失敗の経路を、どの層のテストが確認するか決まっていて、実際にあるか。 | 失敗の経路をどの層も確認しておらず、カートの数量の選択の不具合が漏れた | [テストの書き方](../../../../docs/05-開発規則/test-writing.md)の「テストの種類」、[フロントのテストの書き方](../../../../docs/05-開発規則/test-writing-frontend.md)の「店舗画面のテストは、対象ごとの方法で書く」 |
| フレームワークの推奨との照合 | 使うバージョンのフレームワークの公式の推奨（誤りからの回復、読み込み中の表示、キャッシュの既定）と合っているか。 | サーバーコンポーネントの誤りからの回復に、推奨と違う関数を使っていた。公開の API の呼び出しが既定でキャッシュし、呼ぶ側が毎回切る必要があった | なし（レビューの判断） |
| 認証と安全の二重の守り | token の更新が 1 つの経路にまとまっているか。セキュリティのヘッダーと CSP が、XSS の第 2 の守りになっているか。 | 1 つの要求の中で token を何度も取り直していた。管理画面にセキュリティのヘッダーがなかった | [店舗画面の構成](../../../../docs/02-設計/apps/store.md)の「token の更新」「セキュリティヘッダー」 |
| 読み込みの大きさ | 画面ごとに JS を分けているか。一覧の画像は表示の大きさに合わせているか。 | 管理画面の JS が 1 つのファイルで、報告の画面だけが使うグラフも最初に読んでいた。一覧の縮小の画像に原寸の画像を使っていた | なし（レビューの判断） |
| 拡張の手間 | 1 つの追加に変える所の数は少ないか。変え忘れを型の誤りで気づけるか。 | 絞り込みの条件を 1 つ追加するのに多くのファイルを変え、変え忘れても型の誤りにならない所があった | なし（レビューの判断） |
| 写し元と生成物の保守 | 新しい画面の型（skill の例）が今のコードと合っているか。生成したファイルを手で直し、次の生成で戻る形になっていないか。 | skill の画面の型が、整理で消した部品を参照していた。生成した部品の import を手で直していた | なし（レビューの判断） |
| 見出しと読み上げ | 各画面に h1 があるか。画像の alt、ボタンの名前、入力のラベルがあるか。 | 店舗画面のトップにだけ h1 がなかった | [フロントの書き方](../../../../docs/05-開発規則/frontend-coding.md)の「表示の要素」 |
