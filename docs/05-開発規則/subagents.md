# エージェントの作業フロー

エージェント（Claude Code など）がサブエージェントを使うときの規則。[開発の進め方](workflow.md)と [AGENTS.md](../../AGENTS.md) に従い、ここではサブエージェントへの任せ方だけを書く。

## 1. 調べた仕組み（2026-10-20 時点）

調べた仕組み（cc-sdd、superpowers、Spec Kit、OpenSpec）の使い方は、[調べた仕組みと実績](../07-記録/subagents-results.md) 第 1 節。

## 2. 取り入れるもの・取り入れないもの

| 項目 | 判断 | 理由 |
|------|------|------|
| フレームワーク（Spec Kit、OpenSpec、cc-sdd）を導入する | 取り入れない。必要な形だけを借りる（2026-10-16 決定） | どれも段階ごとの tasks とテストのレッドを持たず、導入しても自前で作るため（[調べた仕組みと実績](../07-記録/subagents-results.md) 第 1 節 ※2） |
| 文書（spec・plan・tasks、設計の文書、手順の文書）の本文を、日本語の要点から日本語だけの文脈のサブエージェントに書かせる | 取り入れる。内容は spec 担当のセッションが要点と照合する。数行の修正も同じセッションが行い、言い換えの一覧の検査で見る | 試した 4 回とも言い回しの修正が必要なかったため。詳しい理由は[実績](../07-記録/subagents-results.md)第 4 節 |
| 既存の文書の言い回しのレビューに、目指す書き方の見本と、書き方の規則（[文書の書き方](writing.md)）を渡す | 取り入れる。和語の言い換えと、論理・比喩などの 2 つの観点を両方見るように指示する | 見本がないと用語の言い換えが混ざり、規則がないと擬人化などを見落とすため（[実績](../07-記録/subagents-results.md)第 4 節） |
| 文書の検査に textlint を使う | 取り入れない | 理由は[実績](../07-記録/subagents-results.md)第 4 節 |
| レビューを、実装の過程を見ていないサブエージェントに任せる | 取り入れる | 作業したエージェント自身のレビューは、同じ見落としを繰り返すため。skill `review` で行う。時点は第 4 節 |
| 1 タスクごとにレビュー役を立てる | 取り入れない。`[リスク]` のタスクの後と、段階の最後、spec の最後などの決まった時点にレビューする（第 4 節） | 2〜3 のサブエージェントを立てると token が数倍になるため。`[テスト]` のタスクでレッドを確認しているので、`[リスク]` のタスク以外は段階ごとで足りる |
| 1 タスクごとに新しい実装役を立てる | 取り入れる。spec 担当のセッションはコードを書かず、実装は全て実装役が行う。`[テスト]` と対応する実装は 1 組で、同じ実装役が順に行う。設計の判断が必要なときは、実装役が止まって報告し、spec 担当のセッションが plan から判断する。文書にない設計の判断は、利用者に質問する（[開発の進め方](workflow.md) 第 5.3 節） | 文脈が長くなるほど 1 回の呼び出しの費用が増えるため |
| 実装役に渡すもの | 取り入れる。渡すのは、タスクの全文、関係する plan の節、決まったインターフェース、曖昧な点の決定、報告の書き先。会話の履歴と計画の全体は渡さない | 渡るのは指示の文字列だけで、余分な文脈は token と誤りを増やすため |
| 気づきを後のタスクに渡す | 取り入れる。tasks のタスクの下に書く | 理由は[実績](../07-記録/subagents-results.md)第 4 節 |
| 結果の受け取り方 | 取り入れる。詳しい報告はファイル（`/.local/` の下）に書かせ、返すのは状態・commit・テストの要約・懸念だけにする | spec 担当のセッションの文脈を小さく保つため |
| 書き手を並行して動かさない | 取り入れる。同じ作業ツリーで、ファイルを書くサブエージェントを同時に動かさない。並行して動かすのは読むだけの作業か、別の作業ツリー | 変更が衝突するため |
| 2 回修正して通らなければ、原因の調査を分ける | 取り入れる。調査は調査役（高性能）が行う | 同じ修正方法を繰り返さないため |
| モデルを常に明示する | 取り入れる | 省くと、親のセッションの高性能なモデルを引き継ぐため |

## 3. 任せる作業とモデル

| 作業 | 例 | 区分 | effort | 条件 |
|------|----|------|--------|------|
| 資料を集める（判断しない） | 該当箇所の要約、事実の確認 | 軽量 | 低 | 固定の分を含めて 1 回の要求が 10 万 token 以下の量に限る。超えるときは範囲を分けるか、汎用にする |
| 機械的な作業 | 一覧の作成、grep の照合、同じ形の置き換え | 軽量 | 中 | 同上 |
| 実装 | タスクの実装 | 汎用 | 中 | 範囲を小さく分ける（1 つのサブエージェントのツールの呼び出しを数十回に収める） |
| `[リスク]` の実装 | 金額、セキュリティ、データの移行 | 高性能 | 高 | |
| 判断・文書の本文 | 規則の当てはめ、日本語の要点から書く | 汎用 | 中 | 範囲を小さく分ける |
| レビュー | 第 4 節の時点 | profile の表で決める | 重要な観点は高、一般の観点は中 | |
| 原因の調査 | 2 回修正して通らない失敗 | 高性能（調査役） | 高 | 調査役が 2 回で特定できないときは最上位 ※1 |
| spec 担当のセッション | 設計の決定、判定、利用者との相談 | 高性能 | 中 | サブエージェントに任せない |
| issue 担当のセッション | 起票、資源の配分、低の変更のマージ、監視 | 汎用 | 中 | 危険度の判定に迷うときは利用者に聞く |

※1：最上位は、調査役が 2 回で特定できないときと、利用者が指定したときだけ使う。使えないプランでは使わず、高性能で代える。使えるプランでは、最上位の使用が週の使用量の 50% を超えたら使わない。最上位の使用も 5 時間と週の使用量に数えるので、止める閾値にも従う。

### 運用の規則

- サブエージェントの文脈は新しい。spec 担当のセッションが規則の要約と対象を指示に書いて渡し、各サブエージェントに原文の全体を読ませない。
- spec 担当のセッションは、サブエージェントの結果を 1 つずつ受けて作業を進めず、全部がそろってからまとめる。理由：結果を受けるたびに、長い文脈を処理し直すため。
- 語ごとの規則（和語の言い換えなど）は、語ごとに 1 回決め、機械（script）か文脈のサブエージェントで全体に適用する。行ごとのレビューで 1 件ずつ判断しない（理由は[実績](../07-記録/subagents-results.md)第 3 節）。
- 文脈で判断する候補（言い回し、論理）は、同じ範囲を汎用で 2 回実行して和集合を取り、高性能なモデルが採否を判断する（理由は[実績](../07-記録/subagents-results.md)第 3 節）。
- 並行して動かすサブエージェントの一時ファイルには、担当の範囲の名前を付ける（理由は[実績](../07-記録/subagents-results.md)第 3 節）。
- サブエージェントへの指示と呼び出しの説明は、日本語だけで書き、中国語の字を含む語を使わない。

実績は [調べた仕組みと実績](../07-記録/subagents-results.md) 第 2 節。

## 4. 役割と作業の流れ

### 役割

| 役割 | 数 | 担当 |
|------|----|------|
| issue 担当のセッション | 1 つ | 起票、spec 担当のセッションの起動と実装の開始の指示、資源の配分、危険度が低く機能の spec でない変更のマージ、`develop` の CI の見届け、弾の終わりの集計と振り返り、`release-` のブランチと `hotfix-` のブランチから `main` へのマージと、`hotfix-` の後の `main` から `develop` への取り込み（どちらも利用者の許可を得て行う）、spec 担当のセッションが自分をアーカイブできないときの、そのセッションのアーカイブ（許可した利用者の言葉を添えた依頼を受けて行う） |
| spec 担当のセッション | spec ごと | spec・plan・tasks、サブエージェントへの指示、合格・不合格の判定、危険度が高い変更と機能の spec の、作業ブランチから `develop` へのマージ（利用者の許可を得て行う）、後片付けの最後の、自分のセッションのアーカイブ（利用者の許可を得て行う） |
| 実装役・資料を集める役・レビュー役・調査役のサブエージェント | 必要なとき | 実装役：タスクの実装（定義 `.claude/agents/implementer.md`）。資料を集める役：判断しない収集（`researcher.md`、軽量）。レビュー役：レビュー（`reviewer.md`）。調査役：失敗の原因の調査（高性能。定義を使わない標準のサブエージェント） |

- spec 担当のセッションは、コードを書かず、書くのは数行の文書の修正だけ。実装は実装役が行う（第 2 節）。
- 合格・不合格の判定は、spec 担当のセッションが行う。理由：サブエージェントに渡らなかった情報を持つのは、spec 担当のセッションだけのため。
- 実装役・資料を集める役・調査役のモデルは、第 3 節の表で決める。これらの定義にはモデルを書かず、呼び出しのときに指定する。

### セッションの間のやり取り

手順（起動、開始の条件、資源の配分、待機、メッセージ、遠隔操作）は skill `sessions`。

- 2 つのセッションは親子の関係にあり、ターンの終わりに親へ通知される。
- issue 担当のセッションが spec 担当のセッションを起動し、開始の条件を渡す。条件を満たすまで、spec 担当のセッションは始めない。始める前に、[開発の進め方](workflow.md) 第 5.6 節の照合を行う。
- 記録は、追跡の issue のコメントに残す（開始、pull request、完了）。
- skill `handoff` は、spec 担当のセッションを途中で別のセッションに替えるときだけに使う。
- 単線のときは、1 つのセッションが issue 担当と spec 担当を兼ねる（区分は高性能）。

### タスクの実装

- `[P]` のタスクは、作業ツリーを分けた実装役が同時に実装する。`[P]` でないタスクは順に実装する。
- 作業ツリーでバックエンドや画面を動かす実装役は、始めに `node scripts/dev/slot.mjs assign` でスロットを割り当て、作業ツリーを削除する前に `release` する（skill `local-dev`）。
### レビューの時点と profile

レビューの量は、profile（厚め・標準・節約）で決める。profile は、issue 担当のセッションが、プランと使用量で決める（[作業の形と使用量](resources.md)）。

| 時点 | 厚め | 標準 | 節約 |
|------|------|------|------|
| `[リスク]` のタスクの後 | 高性能 | 汎用 | 行わない |
| 段階の最後：一般の観点 | 汎用を 2 回（和集合） | 汎用を 1 回 | 汎用を 1 回 |
| 段階の最後：重要な観点（金額、セキュリティ、`[リスク]`、ファイルをまたぐ影響） | 高性能と汎用（和集合） | 高性能を 1 回 | 汎用を 1 回 |
| spec の最後 | 3 つの観点（段階をまたぐ影響、ファイルをまたぐ影響、spec との一致）を高性能で 1 回 | 同左 | 同左 |
| pull request の前 | 完了の定義の確認と、使うツールの組み込みのコードレビュー。hook・CI の検査の script・認証・支払・権限の経路を変える spec は、無記憶の高性能のレビュー役を 1 回加える（下の箇条） | 同左 | 同左 |
| セキュリティのレビュー | 認証・支払・権限の経路を変える変更で、pull request の前に行う | 同左 | 同左 |
| リリースの前 | 高性能（マイグレーション、設定、互換性、リリースの説明の案） | 汎用 | 汎用 |

- 組み込みのコードレビューの level は毎回明示し、件数の上限は既定のままにする。セキュリティのレビューに未解決の指摘があれば、マージしない。値とツールは [AGENTS.md](../../AGENTS.md) のモデルの区分の表。
- 危険度が高い変更は、profile によらず、重要な観点のレビューを高性能で行う。
- 同じ対象の繰り返しは 3 回まで。上限での手順は skill `review` の convergence.md。
- skill `review` の手順 1〜6 のレビュー（`[リスク]` のタスクの後、段階の最後、spec の最後、全体のレビュー）は、レビュー役の定義で行う。理由：指示の文書と memory のない第三者に見させるため。手順 7〜10 は別の形で行う。
- 重要度（高・必須・推奨）の定義と、時点ごとに返す重要度（推奨は spec の最後だけ。機械の検査に移せるかを付ける）は skill `review` の prompts.md。
- hook（`scripts/dev/hooks/`）、CI の検査の script（`scripts/ci/` の、変更や文書を判定して CI を失敗させるもの。例：`risk.mjs`）、認証・支払・権限の経路のコードを変える spec は、profile によらず、pull request の前に、無記憶の高性能のレビュー役（`reviewer`）を 1 回加える。観点は、拒否・判定を別の書き方で回避できないか。理由：spec 246 の hook で、段階・spec の最後・組み込みのコードレビューを通った後に、pull request の後の無記憶のレビュー役が高を 10 件見つけた（見逃しの台帳 #270）。台帳の各件の種類は[実績](../07-記録/subagents-results.md)第 6 節。
- spec の最後のレビューの量（上の表の「spec の最後」の行）は、[作業の形と使用量](resources.md)の閾値と同じ理由で、整理の第 1 段の測定（issue #265、2026-10-29）では変えない。新しい規則で全ての段階を通った spec が 2 つだけで、判断する数が足りないため。整理の第 2 段の最初の弾でもう一度測る。
- レビューごとに token、時間、指摘の数、採用した数を記録し、profile を再検討する材料にする。

### 変更の危険度

危険度は高と低に分ける。経路の判定（`scripts/ci/risk.mjs`。高の経路の一覧は `scripts/ci/risk.json`）と、spec の「危険度：高」の行の、高い方で決まる。テストだけのファイルも、高の経路の下なら高。

- 「危険度：高」の行は、spec の冒頭のステータスの下に書く。spec 担当のセッションが spec の確認で提案し、利用者が決める。利用者は提案がなくても指定できる。途中で設計への影響が大きいと分かったら、spec 担当のセッションが行を加えて利用者に報告する。行は消さない。
- spec 担当のセッションは、pull request の本文の「危険度」の節に script の出力を貼る。CI が本文と判定を比べ、本文が判定より低いか空なら失敗する。本文が判定より高いときは失敗にしない。
- 承認に数えるのは、利用者が会話か pull request で明示した許可だけ。エージェント（issue 担当を含む）の承認とレビューの合格は数えない。GitHub の approve の数は求めない。
- 利用者の許可が必要なマージは、[AGENTS.md](../../AGENTS.md) の Git の表のとおり（危険度が高い変更と機能の spec など）。危険度が低く機能の spec でない変更は、CI が全て通り、未解決の高・必須が 0 なら、issue 担当のセッションがマージする。spec 担当のセッションは、pull request を作り、条件を満たしたことを issue 担当のセッションに知らせる。推奨の指摘と起票の案も本文に書き、利用者は弾の終わりに確認する（skill `sessions`）。
- 承認は、求めたときの head の commit にだけ有効。マージは head の commit を指定して行い、承認の後に push したら求め直す。例外：承認の後に `develop` を取り込んだだけで衝突がなく CI が通ったときは、取り込みの差分を利用者に示し、求め直さず、取り込みの後の head の commit を指定してマージする。
- issue 担当のセッションが低の変更をマージしたら、spec 担当のセッションに知らせる。後片付け、振り返り、アーカイブの許可は [開発の進め方](workflow.md) 第 5.7 節。
- Dependabot の pull request は、CI の job が判定をジョブの要約に出す（判定の規則は [ブランチとリリース](../06-手順書/branches.md) 第 6 節）。issue 担当のセッションは、マージの前にその判定を読み、高なら利用者に許可を求める。
- 規模 S は経路で判定し、spec の宣言はない。issue 担当のセッションが起票のときに設計への影響が大きいと見れば、issue に「危険度：高」を書き、spec 担当のセッションが pull request の本文で高にする。

### 並行

- 並行の単位は、spec 1 つに、セッション、作業ツリー、ブランチ、pull request を 1 つずつとする。
- 並行してよい条件は、次の 3 つを全て満たすこと。
  - モジュールが違う。
  - 契約や同じテーブルを同時に変えない。
  - 依存がない。
- 並行する spec の依存は、追跡の issue に書く。
- spec を分けるとき、または並行してよいと判断するときは、spec の範囲だけで決めない。関わる全ての spec の plan と tasks（規模 M は spec の tasks）の、変えるファイルを照合してから決める。理由は[実績](../07-記録/subagents-results.md)第 3 節。
- 照合の前（spec の段階）は、並行の可否を決めない。spec には「並行の可否は plan の段階で決める」と書く。規模 M は、tasks を書くときに決める。
- 照合の結果として、重なるファイルと実装の順序を、plan（規模 M は spec の tasks）に書く。
- 共有の文書（AC 一覧、用語集）の衝突は、後でマージする pull request が `develop` を取り込んで解消する。

作業ツリーの置き場所と、作業ツリーのセッションが読む設定：

- 置き場所は `.claude/worktrees/<issue の番号>-<短い名前>`。`.gitignore` で無視され、検索の対象にならない。手動で作るときは、メインの作業ツリーで `git worktree add .claude/worktrees/<issue の番号>-<短い名前> -b <issue の番号>-<短い名前> develop`。Claude のデスクトップアプリが作る作業ツリーも同じ場所に置かれる。IntelliJ の `reformat_file` が使えない注意は [バックエンドの書き方](backend-coding.md)。
- 作業ツリーのセッションが読む設定・定義・skill と、変更が効く時点は、skill `sessions` のツールの注の「作業ツリーのセッションが読むもの」の表。デスクトップアプリの作業ツリーのセッションは、`.claude/settings.local.json` に限らず、設定・定義・skill をメインの作業ツリーから読む（spec 276、2026-10-29）。作業ツリーに `settings.local.json` がなくても、メインの作業ツリーの hook が動く（デスクトップアプリの作業ツリーで動かして確認した、2026-10-29）。`$CLAUDE_PROJECT_DIR` もメインの作業ツリーを指す。
- Claude Code の文書は、作業ツリーのセッションがその作業ツリーの `settings.local.json` を読むと書いており、spec 246 第 1 節の調べもこの記述による。作業ツリーで起動した `claude -p` は文書の記述のとおりだが、デスクトップアプリの作業ツリーのセッションは、メインの作業ツリーの `settings.local.json` を読み、文書の記述とは違う。
- 作業ツリーにない script を hook が呼ぶと失敗するので、`settings.local.json` の hook のコマンドは、script のパスを `git rev-parse --show-toplevel` の作業ツリーから先に探し、なければ `$CLAUDE_PROJECT_DIR` の下を使う形にする。探し方は `settings.json` と同じだが、どちらにも見つからないときは、`settings.json` はコマンドを止め、`settings.local.json` の例は何もせず通す（skill `local-dev` の「手元の hook の設定」）。

## 5. モデルや設定を替えるとき

モデル、レビューの指示、profile、サービスを替えるときは、台帳で新しい設定を試してから決める。

### 見逃しの台帳

- 台帳は、GitHub の issue の label「見逃し」とする。label で一覧にできる ※2。
- 理由：Git に置くと並行する spec が同じファイルを変えて衝突し、`/.local/` に置くとクラウドのセッションと他のマシンから読めないため。
- 加える時点は、不具合の issue の起票（[開発の進め方](workflow.md) 第 4.1 節）。原因の変更がレビューを通ったか、エージェントがマージしたものに限る。
- 本文の「関連」に、見逃した pull request、見逃した時点（段階・spec の最後・pull request の前）、エージェントがマージしたかを書く。

※2：`gh issue list --label 見逃し`。

### 替える手順

1. 台帳の各件について、見逃した pull request の差分（修正の前）を新しい設定のレビューに渡し、見つけた件数を数える。
2. 対象ごと（モデルの区分、レビューの観点、profile、段階ごとのレビュー、引き継ぎの文書、1 タスクごとの実装役、調査役）に、残すか変えるかを判断する。
