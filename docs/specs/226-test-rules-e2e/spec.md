# Spec 226：E2E とフロントのテストの書き方の規則と検査を整える

ステータス：草案

## 1. 背景と目的

テストの書き方の規則のうち、E2E の書き方と、フロントのテストの書き方の一部が、規則の文書にも検査にも足りない。

- spec 185 でフロントのテストの書き方の検査（`scripts/ci/frontend-rules.mjs`）を作った。E2E の書き方の規則（位置で探さない、`networkidle` で待たない、ボタンの名前は完全一致、タイムアウトは定数）は、まだ機械で検査していない（[#218](https://github.com/roger88106/ec-site/issues/218)。出典：spec 185 第 8 節、spec 194 第 9 節の 2）。
- spec 184 の候補のうち、(d)（テストの定数で、組み込みの名前を同じ名前の宣言で隠す。シャドーイング）と (e)（`})` の直後に空行なしで `test(`・`describe(` が続く）も、検査にしていない（#218）。
- spec 194 の最後のレビューで、E2E と手元の script に、未対応の小さな項目が 3 つ見つかった（[#216](https://github.com/roger88106/ec-site/issues/216)。出典：spec 194 第 9 節の 1、3、4）。
- spec 184 でそろえた書き方のうち、jest-dom で状態と属性を確認する、環境変数は `vi.stubEnv` で変える、組み込みの名前を隠さない、の 3 つがテストの書き方に書かれていない（[#205](https://github.com/roger88106/ec-site/issues/205)）。`fireEvent` と、要素のプロパティ・属性の比較は、spec 185 の T185-04-01 が [テストの書き方](../../rules/test-writing.md) 第 4.7、4.8 節に書いたので、本 spec の対象から除く。
- 規則の文書にない検査は、先にテストの書き方に規則を書いてから加える（spec 183 の確認で利用者が決めた方針。#218 の本文）。

追跡の issue は [#226](https://github.com/roger88106/ec-site/issues/226)、扱う issue は #218、#216、#205 である。作業ブランチは `226-test-rules-e2e`。本 spec は整理の spec で、追跡の issue の見込みは規模 L だが、本 spec は規模 M を提案する（第 6 節の 1）。

実装は、[#222](https://github.com/roger88106/ec-site/issues/222)（文書の整理。「版」をバージョンの意味で使わない言い換え）と、[#225](https://github.com/roger88106/ec-site/issues/225)（CI の検査の script の整理。#219、#221）のマージの後に始める。#225 は `scripts/ci/` の共通の関数と `frontend-rules` の正規表現の重複を整えるので、本 spec の検査の追加と、変えるファイルが重なる。重なるファイルと実装の順序は、規模 M なら tasks、L なら plan で、#225 の文書と照合して書く。

## 5. 守る制約

- **DN-226-1** 消費者・運営者に見える振る舞い、API の契約、データベースを変えない。AC を追加・変更しない。
- **DN-226-2** テストを弱めない。名前を変えるだけの修正で、確認する内容を変えない。
- **DN-226-3** E2E の全体の時間を延ばさない。理由：CI の E2E のジョブとローカルの確認で毎回実行するため。
- **DN-226-4** 検査は、今の違反を除外の一覧に入れずに 0 件にする。除外するときは、理由のコメントを書く（spec 185 の `fireEvent` と同じ形）。
- **DN-226-5** 新しく書く文書に、バージョンの意味で「版」を書かない（#222 が言い換える）。
- **DN-226-6** 並行する spec と、変えるファイルが重なる。
  - #225：`scripts/ci/frontend-rules.mjs` の正規表現の重複と対象の選び方、`scripts/ci/lib/` の走査の補助、`frontend/admin/src/test/inputs.ts` のコメント。
  - #222：テストの書き方、コメントの書き方を含む、ほぼ全ての文書。
  - [#223](https://github.com/roger88106/ec-site/issues/223)：バックエンドの検査。`scripts/ci/` を変えうる。
  - 実装は #222 と #225 のマージの後に始め、重なりと順序を、規模 M なら tasks、L なら plan に書く。

## 6. 決めること（Open questions）

spec の確認で利用者が決める。決まったら、決めた案と日付を書き、Open questions を空にする。各項目は、案 A（推奨）を先に書く。

### 6.1 規模

- 案 A（推奨）：M。理由：API の契約とデータベースを変えず、モジュールのコードを変えず、AC も変えないため（[開発の進め方](../../rules/workflow.md) 第 4.2 節の判定の基準）。変えるのは検査の script、E2E、手元の script、規則の文書で、似た範囲の spec 185、spec 194 も M だった。
- 案 B：L（追跡の issue の見込み）。3 つの issue をまとめ、並行する spec との順序を plan で詳しく書ける。

### 6.2 テストのコメントの spec の番号（DC-226-16、17）

今の規則（コメントの書き方 第 1 節）は、本番のコードとバックエンドのテストを対象にし、フロントのテストを対象外にしている。E2E は、対象にも対象外にも書かれていない。

- 案 A（推奨）：対象を全てのテストのコード（フロントのテストと補助、E2E）に広げ、番号の検査の対象に加える。今の違反（E2E 15 か所、フロント 1 か所）は、規則を言葉で書く形に修正する。理由：バックエンドのテストと扱いをそろえ、番号が照合されずに古くなる理由（コメントの書き方 第 1 節）は、テストのコードにも当てはまるため。
- 案 B：E2E だけを加える。フロントのテストは対象外のまま。
- 案 C：広げない。E2E を対象外とコメントの書き方に明記する（DC-226-17 を除く）。

### 6.3 組み込みの名前の範囲（DC-226-7、9、13）

- 案 A（推奨）：TypeScript の lib（ES と DOM）が宣言するグローバルの名前を、`const`・`let` の宣言で隠さない。関数の引数は対象外。今の違反は約 21 か所（`status`、`name` など）で、名前を変える。理由：一覧を手動で持たずに済み、宣言を忘れたときに、エラーにならずにグローバルの値が使われることを防ぐため。引数まで含めると違反が倍になり、引数の名前は呼び出しの近くで読めるので効果が小さい。
- 案 B：spec 184 で挙げた名前（`URL`、`screen`、`location`、`name`）だけを、検査の一覧に書く。今の違反は E2E の `name` 7 か所。
- 案 C：案 A に関数の引数も含める。

### 6.4 ボタンの名前の完全一致（DC-226-3）

- 案 A（推奨）：`exact: true` の文字列か、先頭（`^`）と末尾（`$`）を固定した正規表現を、完全一致とみなす。理由：注文するボタンのように、名前に金額などの変わる値を含むボタンは、文字列で完全一致させられないため。固定した正規表現は、別のボタンの名前の一部に一致しない。
- 案 B：`exact: true` の文字列だけを認める。注文するボタンは、金額を計算して文字列で探す形に修正する。

### 6.5 E2E の補助の URL の渡し方（DC-226-18、19）

- 案 A（推奨）：URL は最後の引数のオプション（`{ storeUrl }`・`{ adminUrl }` などの項目）で受け取る。他の省略できる引数（遷移先のパス、氏名など）も同じオプションに入れる。理由：引数の位置を覚えずに済み、撮影が空のオプションや既定の値を並べて渡さずに済むため。
- 案 B：URL を各補助の最後の位置引数にそろえる。空のオプションを渡す呼び出しは残る。
