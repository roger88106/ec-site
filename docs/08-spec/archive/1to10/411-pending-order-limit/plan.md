# Plan 411：会員ごとの支払待ちの注文に上限を設ける

ステータス：承認済み（tasks 作成済み）　対象：[spec.md](spec.md)

前提：上限の値（3 件）、拒否と案内、複数のアカウントを扱わないことは、利用者が 2026-11-06 に決めた（issue #411）。spec・plan・tasks と「利用者に確認すること」の 3 つは、2026-11-09 に、利用者の委任で issue 担当のセッションが承認した。読む文書は[文書の書き方](../../05-開発規則/writing.md)、[文書の構成](../../05-開発規則/doc-structure.md)、[文書の記号と番号](../../05-開発規則/notation.md)。

共通の決定：

- 危険度は高にしない。判定は spec 406 の会員のロックの中に 1 つ加えるだけで、ロックの順序もテーブルも変えないため。
- レビューの profile は厚め（起動の指示）。区分は[エージェントの作業フロー](../../05-開発規則/subagents.md)の「任せる作業とモデル」に従う。
- #413、#415 と重なりうるのは、AC 一覧、用語集、店舗画面の文書（[店舗画面の構成](../../02-設計/apps/store.md)）である。#415 が変える店舗画面のコード（`api/cart.ts`、`auth/index.ts`）は、この spec が変える `actions/cart.ts` と別のファイルである。実装の順序は決めず、後にマージする側が、先の変更を取り込んで衝突を解消する。
- DB の構造は変えない。判定は既存の注文の列（会員、状態）と索引（会員と注文日時）で行う。理由：会員ごとの支払待ちは上限で数件に限られ、新しい索引の利点が小さいため。

## 上限の判定（US-411-1：AC-411-1〜8）

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 上限の判定を、支払待ちの注文の判定に加える。確認の判定の後に、その時点の支払待ちの件数が上限以上なら拒否する | `PendingOrderGuard` | `CheckoutApiTest`、`PlaceOrderApiTest` |
| 開始の時点は、確認の判定の後、前の注文手続きの引当を解く前に判定する | `CheckoutService` | `CheckoutApiTest` |
| 注文の時点は、会員のロックの後、作成済みの注文の確認（再送）と確認の判定の後に判定する | `OrderPlacementService` | `PlaceOrderApiTest`、`PlaceOrderConcurrencyTest` |

- 注文の時点の判定は、spec 406 の会員のロックの中で行うので、同時の注文でも上限を超えない（[注文の設計](../../02-設計/order.md)の「同時の注文」）。ロックの順序は変えない。
- 確認の判定と上限の判定は、同じ支払待ちの ID の読み取りを使う。読み取りを 2 回にしない。
- 適用の時点で上限以上の支払待ちを持つ会員も、件数で判定されるので、移行の処理は必要ない（AC-411-8）。

## API の形と設定（US-411-1、US-411-2：AC-411-1、3、9、10）

| 何を | どこに | 確認方法 |
|------|--------|----------|
| エラーコード `PENDING_ORDER_LIMIT_EXCEEDED`（409）を、開始と注文の両方の `x-error-codes` と説明、エラーコードの一覧（`ErrorCode`）に加える | `api/openapi/store.yaml`、`OrderErrorCode` | 統合テスト、`ErrorCodeContractTest` |
| 拒否のメッセージを加える。上限の件数は文に入れない | `messages.properties` | エラーコードの単体テスト |
| 上限の件数の設定 `ecsite.order.pending-order-limit`（既定 3、1 以上） | `OrderProperties`、[環境変数](../../06-手順書/environment.md) | `OrderProperties` の単体テスト |

- 409 にする理由：確認を求める応答（`PENDING_ORDER_CONFIRMATION_REQUIRED`）と同じく、会員の注文の状態による拒否で、期限切れなどで件数が減れば成功するため。
- 文に件数を入れない理由：設定を変えたときに、文と画面の文言を修正しなくてよいため。

## 店舗画面（US-411-2：AC-411-9〜11）

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 開始と注文の 409 で `PENDING_ORDER_LIMIT_EXCEEDED` を受けたら、上限を示すクエリパラメーターを付けた確認の画面の URL へ遷移する。注文のときは、入力したお届け先を保存しない | `actions/cart.ts` の `startCheckout`、`actions/checkout.ts` の `placeOrder`、`lib/pendingOrders.ts` | `cart.test.ts`、`checkout.test.ts` |
| 確認の画面は、クエリパラメーターがあれば、上限に達したことと、支払うか期限を待つよう促す文を、見出しの下に表示する。注文の一覧と「支払へ進む」は今と同じ | `app/checkout/pending-orders/page.tsx`、`PendingOrdersConfirmation.tsx`、`messages/ja.json` | 確認の画面のテスト |

- クエリパラメーターは `limit=reached` にする。理由：開始と注文の両方の拒否を、同じ遷移の形で扱えるため。
- 上限による開始の拒否は、確認の画面の「新しく注文する」で起きる。カートからの開始は確認した注文を送らないので、支払待ちがあれば先に確認を求める（AC-411-4）。

既存のテストへの影響：

| 対象 | 影響 | 対応 |
|------|------|------|
| 統合テスト | 同じ会員で支払待ちを 3 件以上残して注文するテストは失敗する | 統合テストを全て実行し、失敗するものを、会員を分けるか、先の注文を支払う形に変更する。テストを弱めない |
| E2E | 共用の会員に支払待ちが残る。E2E の支払の期限は 12 秒なので、12 秒の間に同じ会員で 3 件を注文しなければ上限に達しない | 段階 2 で E2E を全て実行し、失敗すれば同じく修正する |

## 利用者に確認すること

| # | 確認 | 案 | 推奨と理由 |
|---|------|----|------------|
| 1 | 開始の時点でも上限で拒否するか | 案 A：開始と注文の両方で拒否する。案 B：注文の時点だけで拒否する | 案 A（承認で決定）。案 B は、お届け先を入力して「注文する」を押してから拒否されるため。判定の正は注文の時点のままにする（BR-411-2） |
| 2 | E2E を書くか | 案 A：書かず、手動で確認する。案 B：支払の期限を延ばして E2E を書く ※1 | 案 A（承認で決定）。E2E の支払の期限は 12 秒で、3 件を注文する間に先の注文が期限切れになるため ※1 |
| 3 | 確認の画面で、上限のときに「新しく注文する」を隠すか | 案 A：隠さない。押すと拒否され、上限の文を表示する。案 B：一覧 API に上限に達しているかを加え、隠す | 案 A（承認で決定）。案 B は API の形を変え、表示の後に件数が変わる場合の拒否も別に必要になる |

※1：案 A は、統合テストと店舗画面のテストで確認し、画面は手動の確認で見る。案 B で期限を延ばすと、期限切れを待つ既存の E2E が遅くなる。
