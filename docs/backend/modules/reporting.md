# レポートモジュール

注文と出荷のデータを集めて写しを持ち、運営者に売上のレポート（売上の推移、バリエーションの売れ行き、地域・年齢層・性別）を返す。

| 項目 | 内容 |
|------|------|
| レベル | B（集約の不変条件がなく、写しと集計だけ。理由は後述） |
| 依存 | 注文（API、イベント）、出荷（イベント）、商品カタログ（API）。他のモジュールはレポートに依存しない |
| 関連 spec | [010](../../specs/010-sales-report) |

## レベルを B とした理由

- 業務の状態を変える操作がない。持つのは他のモジュールの写しと、受けたイベントの履歴だけ。
- 写しは、イベントを受けるたびに注文の API から読み直して上書きするので、守る不変条件がない。
- 集計は問い合わせのときに SQL で行う。結果を持たないので、CQRS の read model も要らない。

## 集めるデータ

**データは広く集め、どう数えるかはレポートごとに決める**。集めるときには絞らない（支払待ち、支払の期限切れ、キャンセル、返送の注文も集める）。後で別の見方（返送の率、受け取られにくい地域、会員の継続など）をしたくなっても、集め直さずに作れるようにするため。

| データ | 持つもの | 作り方 |
|--------|----------|--------|
| 注文の写し | 注文 ID、注文番号、会員 ID、注文日時、状態、出荷日時、配送状態、キャンセル（日時、種類、在庫に戻したか）、郵便番号、都道府県のコード、注文時の年齢と性別、総額、送料、消費税の合計、送料の消費税 | 下の「写しの作り方」 |
| 明細の写し | 行番号、商品 ID、バリアント ID、商品品番、バリアント品番、商品名、軸の値、数量、税率、税込小計、税抜小計 | 同上 |
| 状態の履歴 | 受けたイベントごとに 1 行：出来事（注文の状態の変化、配送状態の変化）、注文 ID、前と後の状態、発生日時、キャンセルの種類と在庫に戻したか、元のイベント ID | イベントをそのまま足す |

- 今の 3 つのレポートで使わない項目（会員 ID、郵便番号、日時の時刻、税率、状態の履歴）も持つ ※1。
- 氏名、住所、電話番号、メールアドレス、生年月日は持たない。会員 ID と郵便番号は、レポートの API で返さない。

※1：状態の履歴は後から作り直せない（注文は今の状態しか持たない）ので、使う前から集める。

### 写しの作り方

注文のイベント「注文の状態の変化」と、出荷のイベント「配送状態の変化」を、コミットの後に非同期で受ける。どちらを受けても、同じトランザクションで次を行う。

1. 状態の履歴に 1 行足す。元のイベント ID で一意にし、すでにあれば足さない。
2. 注文の API（レポート用の注文の写し）で、注文の今の写しを読み直す。
3. 商品カタログの API で、明細のバリアントの商品 ID を求める ※2。
4. 出荷日時と配送状態は、状態の履歴から求める（下の表）。
5. 注文と明細の写しを上書きする（明細は消して入れ直す）。

| 項目 | 状態の履歴からの求め方 |
|------|------------------------|
| 出荷日時 | 注文の状態が出荷済みになった変化、または配送状態が出荷済みになった変化の、早いほうの発生日時 |
| 配送状態 | 配送状態の変化の後の状態のうち、順位の最も高いもの（[出荷モジュール](shipping.md)「配送状態と順位」） |

- イベントの中身で写しを差分で直さない。読み直して上書きするので、イベントが何度・どの順で届いても、写しは同じになる。
- 処理に失敗したら例外で終わり、未完了のイベントの再発行（[バックエンドのアーキテクチャ](../architecture.md) 第 5 節）でやり直す。業務の処理（注文・出荷）は待たない。写しの遅れは、通常は数秒、上限は再発行の間隔。

※2：注文の明細は商品 ID を持たず、品番は参照に使わない（[商品カタログモジュール](catalog.md)）。注文されたバリアントは削除できない（C 側に表示されたことがあるため）ので、商品 ID は変わらない。読めなかったときは、前の写しの商品 ID を残す。

### 都道府県のコード

写しを作るときに、お届け先の都道府県の名前を、全国地方公共団体コードの上 2 桁（北海道 `01` 〜 沖縄県 `47`）に読み替えて持つ。対応の表はレポートの中に置く。表にない名前は空（不明）にして、警告をログに出す。

- 注文がお届け先をコードで持つようになったら（郵便番号と住所を結び付ける spec）、この表を除く。

## 集計

レポートは、問い合わせのたびに写しを SQL で集計する。集計の結果は持たない ※3。

| 項目 | 規則 |
|------|------|
| 期間 | 始まりと終わりの日（日本時間、両端を含む）。始まりが終わりより後、または 5 年を超えると 400 |
| 数える注文（売上の数え方） | 注文基準：状態が受付・キャンセル申請中・出荷済みの注文を、注文日で数える。出荷基準：状態が出荷済みの注文を、出荷日で数える ※4 |
| 売上額 | 既定は総額（明細の税込小計の合計 ＋ 送料）。消費税を除くときは消費税の合計を、送料を除くときは送料（消費税を除くなら税抜の送料）を引く |
| 商品を選んだとき | その商品の明細の税込小計（消費税を除くなら税抜小計）だけを数え、送料は含めない（応答に「送料を除いた」を載せる）。注文件数は、その商品の明細を含む注文の数 |
| 販売数量 | 数える明細の数量の合計 |

※3：売上の数え方、消費税・送料を除くか、商品の選択の組み合わせごとに集計を持つと数が多くなるため。数万件なら索引で足りる。

※4：出荷の後のキャンセルは返送による返金だけなので、状態が出荷済みのものだけを数えれば、返金待ち・返金済みを除ける。決済のモジュールに依存しなくて済む。

### 売上の推移

| 粒度 | 区切り |
|------|--------|
| 週 | 月曜から日曜 |
| 月 | 暦の月 |
| 四半期 | 会計年度の 3 か月ごと。会計年度の始まりの月は設定 `ecsite.reporting.fiscal-year-start-month`（既定 `4`） |
| 年 | 会計年度。年度は始まりの月の年で呼ぶ（4 月始まりなら、2026 年 4 月〜2027 年 3 月は 2026 年度） |

- 期間のすべての区切りを並べ、売れなかった区切りは 0 にする。
- 期間が区切りの途中で切れたら、その区切りは期間の中の日だけを数える（応答の区切りの始まりと終わりも、期間で切った日にする）。
- 日ごとに SQL で集計し、区切りへのまとめは Java で行う（会計年度の計算を単体テストで確かめるため）。

### バリエーションの売れ行き

- 商品を 1 つ選び、バリアントごとの販売数量と売上額を返す。送料は含めない。
- 商品カタログの API で商品のバリアントの一覧を受け、売れなかったバリアントも 0 として返す。
- 販売数量の多い順。同じなら、商品カタログの並びの順。

### 地域・年齢層・性別

| 分け方 | 並び | 不明 |
|--------|------|------|
| 都道府県 | 全国地方公共団体コードの順。売れた都道府県だけを返す | コードのない注文は「不明」として最後 |
| 年齢層 | 10 代以下、20 代、30 代、40 代、50 代、60 代以上、不明。売れなかった層も 0 として返す | 年齢を記録していない注文 |
| 性別 | 男性、女性、その他、不明。売れなかったものも 0 として返す | 性別を記録していない注文と「回答しない」 |

- 年齢層は、写しの年齢から問い合わせのときに求める（層の切り方を変えても、写しを作り直さずに済むため）。

## 権限

| 権限 | レポート |
|------|----------|
| `report-sales-trend:read` | 売上の推移 |
| `report-variant-sales:read` | バリエーションの売れ行き |
| `report-customer:read` | 地域・年齢層・性別 |

- 権限はレポートごとに分け、レポートの中の選択肢（粒度、商品など）ごとには分けない。
- 役割と権限の対応は IdP（運営者の realm）に置く。管理者と管理職は 3 つとも、営業は売上の推移以外の 2 つを持つ。閲覧者は持たない。

## 他のモジュールへの公開

なし（管理 API だけ）。

## 列指向のデータベースへの移し方の見通し

件数が増えて、索引と日付での分割で足りなくなったら、写しを列指向の分析用のデータベースに移す。写しを持つのはレポートだけなので、`infrastructure` の写しの保存と集計の実装を替えれば済み、他のモジュールは変わらない。導入のときに、依存とライセンスを確かめる。

## 構成

```
reporting/
├── application/            # イベントのリスナー、写しの作り直し、3 つのレポートの集計、区切り、年齢層
│   └── port/               # 写しと履歴の保存、集計の問い合わせ、注文と商品カタログの腐敗防止層
├── domain/                 # 都道府県のコード、区切りと年齢層と性別の値
├── infrastructure/
│   ├── directory/          # 注文と商品カタログの API の呼び出し
│   └── persistence/        # 写しと履歴の保存、集計の SQL
└── presentation/           # 管理 API（3 つのレポート）
```

## データモデル

- schema は `reporting`。注文・バリアント・商品・会員は他のモジュールの ID なので、外部キーは張らない。
- 注文の写しは、注文 ID を主キーにする。注文日と出荷日（日本時間の日付）を列に持ち、索引を付ける（日で集計するため）。
- 明細の写しは、注文 ID と行番号を主キーにする。商品 ID に索引を付ける。
- 状態の履歴は、元のイベント ID を主キーにする。注文 ID に索引を付ける。
