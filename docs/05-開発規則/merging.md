# マージと後片付け

pull request のマージと、その後の作業の規則。pull request を作る・マージする・後片付けをするときと、利用者が pull request に付けた指摘に答えるときに読む。

## 1. マージの許可と後片付け

### マージの許可

- 利用者の許可が必要なのは、次のとき。操作のたびに求める。
  - 危険度が高い変更、機能の spec
  - `release-`・`hotfix-` の pull request
  - `hotfix-` の後の `main` から `develop` への取り込み
  - tag
- 危険度が高い変更と機能の spec は、spec 担当のセッションが、作業ブランチから `develop` へ、利用者の許可を得てマージする。`release-` のブランチと `hotfix-` のブランチから `main` へのマージと、`hotfix-` の後の `main` から `develop` への取り込みは、issue 担当のセッションが、利用者の許可を得て行う。
- それ以外は、CI が全て通り、未解決の重要度「高」「必須」の指摘が 0 なら、issue 担当のセッションがマージする。spec 担当のセッションは、pull request を作り、条件を満たしたことを issue 担当のセッションに報告する。推奨の指摘と起票の案も本文に書き、利用者はステップの終わりに確認する（skill `sessions`）。
- issue 担当のセッションが危険度が低い変更をマージしたら、spec 担当のセッションに知らせる。
- 承認に数えるのは、利用者が会話か pull request で明示した許可だけ。エージェント（issue 担当を含む）の承認とレビューの合格は数えない。GitHub の approve の数は求めない。
- 承認は、求めたときの head の commit にだけ有効。マージは head の commit を指定して行い、承認の後に push したら再度求める。
- 例外：承認の後に `develop` を取り込んだだけで衝突がなく CI が通ったときは、取り込みの差分を利用者に示し、再度求めず、取り込みの後の head の commit を指定してマージする。
- マージの前に `develop` を取り込むのは、衝突があるときか、`develop` が同じファイルを変えたときだけ。
- 利用者の許可が必要なマージの許可を求めるときは、許可の後に hook の確認の画面が表示されることも伝える。理由：利用者が確認の画面を hook の誤動作と取り違えて拒否することを防ぐため。利用者が遠隔操作のときは、許可の質問と選択肢を返答の文章に書き、確認の画面と「次の一歩」の表示欄だけに頼らない。理由：遠隔操作では、それらが見えないことがあるため。
- spec 担当のセッションは、マージの許可と一緒にアーカイブの許可を求める。危険度が低い変更では、pull request の報告と一緒に求める。理由：別に質問すると確認が 1 回増えるため。アーカイブは、使うツールの機能で自分のセッションを一覧から外すこと。

### 変更の危険度

危険度は「高」と「低」の 2 つに分ける。経路の判定（`scripts/ci/risk.mjs`。危険度が高い経路の一覧は `scripts/ci/risk.json`）と、spec の「危険度：高」の行の、高い方で決まる。テストだけのファイルも、危険度が高い経路の下なら危険度が高い。

- 「危険度：高」の行は、spec の冒頭のステータスの下に書く。spec 担当のセッションが spec の確認で提案し、利用者が決める。利用者は提案がなくても指定できる。途中で設計への影響が大きいと分かったら、spec 担当のセッションが行を加えて利用者に報告する。行は削除しない。
- spec 担当のセッションは、pull request の本文の「危険度」の節に script の出力を貼る。CI が本文と判定を比べ、本文が判定より低いか空なら失敗する。本文が判定より高いときは失敗にしない。
- Dependabot の pull request は、CI のジョブが判定をジョブの要約に表示する（判定の規則は [ブランチとリリース](../06-手順書/branches.md)の「Dependabot」）。issue 担当のセッションは、マージの前にその判定を読み、危険度が高ければ利用者に許可を求める。
- 規模 S は経路で判定し、spec の宣言はない。issue 担当のセッションが起票のときに設計への影響が大きいと判断すれば、issue に「危険度：高」を書く。そのときは、spec 担当のセッションが pull request の本文の「危険度」の節を「判定：高」にする。

### 後片付け

作業ブランチ（リモート）は自動で削除される（[ブランチとリリース](../06-手順書/branches.md)の「自動の削除」）ので、削除しない。マージの後（自分でマージしたとき、または issue 担当から知らせを受けたとき）、spec 担当のセッションが次を行う。

- 追跡の issue に完了を記録する。マージで閉じなかった扱った issue があれば閉じる（通常は本文の `Closes` で閉じる）。
- 振り返りを行う（skill `agent-retro`）。アーカイブの許可によらず、作業ツリーの削除の前に行う（tasks を読むため）。
- その spec の記録（メインの作業ツリーの `/.local/review/`、`impl/`、`pr/` の、その spec のもの）を削除する。作業ツリーの `/.local/review/` の記録は、作業ツリーの削除で一緒に消える（[開発環境の起動](../06-手順書/setup.md)の「手元の置き場所」）。
- スロットを解除してから、作業ツリーとローカルの作業ブランチを削除する（skill `local-dev`。自分が動いている作業ツリーの削除も同じ）。
- アーカイブの許可を得たときは、最後に自分をアーカイブする。許可がなければ、セッションを残す。できないときは skill `sessions` に従う。

## 2. pull request のレビューの対応

利用者が pull request に付けた指摘は、見つけた時点と影響の範囲で扱いを分ける。

| 場合 | 例 | 扱い |
|------|----|------|
| マージの前で、spec の意図の範囲の中 | 言い回し、文書の書き方、小さなコードの修正 | 同じ pull request で直す。文書は追加せず、指摘への返信に、直した commit を書く |
| マージの前で、spec・plan の誤り | 実際に実行して、plan の判定の誤りが分かった | 同じ pull request で、spec・plan を先に直し、tasks に段階を追加して、テストから直す ※ |
| マージの後 | `develop` で実際に実行して分かった不具合や変更 | issue に起票し、新しい spec（規模による）で直す。アーカイブした spec は変えない |

※：アーカイブの後は[起票と記録の操作](issues.md)の「アーカイブの操作」のとおりにする。設計が変わるときは[開発の進め方](workflow.md)の「実装を始める前の照合」のとおりにする。

- 境目は `develop` へのマージ。マージの前は、アーカイブに移した spec も直してよい。理由：アーカイブはマージで確定するため。
