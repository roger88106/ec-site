自社ブランドのための EC サイト

商品を並べて、注文を受けて、
在庫と税金まで正しく回す。

お客様が買い物をする「店舗画面」と、お店の人が商品や注文を扱う「管理画面」の二つで動く、日本向けの通販サイトです。見た目だけの試作ではなく、在庫・消費税・ログイン・権限といった、実際にお店を開くときに困るところから作っています。

店舗画面と管理画面お客様向けとお店向けを別々の画面に分け、それぞれに合った操作にしています。
軽減税率に対応10% と 8% の商品を一緒に買っても、税率ごとの内訳を正しく出します。
売り越しを起こさない最後の 1 個に注文が同時に来ても、在庫がマイナスになりません。

お客様ができること

探す、選ぶ、買う、あとで確かめる

会員登録をしたお客様が、商品を探して注文し、注文の状況を自分で確かめられます。

色やサイズを選んで、カートへ

  • キーワード検索とカテゴリ（衣類 → トップス → T シャツ のような階層）で探せます。
  • 商品ページでは、色やサイズを選ぶとその組み合わせの在庫を示します。
  • 写真は 1 商品に 20 枚まで載せられ、色ごとに見せる写真を決められます。
  • ログインせずにカートに入れた商品も、ログインすると引き継がれます。

注文の明細は、税率ごとに分けて示す

  • 食品（8%）と衣類（10%）を一緒に買っても、税率ごとの対象額と消費税を分けて示します。インボイス（適格請求書）と同じ考え方です。
  • 注文の履歴と状態（支払待ち・受付・キャンセル申請中・キャンセル）を、お客様がいつでも見られます。
  • キャンセルは「申請」として受け、お店が確かめてから取り消します。

支払はカードで。番号はサイトに残さない

  • 注文すると決済サービスの支払の画面に移り、カードで支払います。カード番号はその画面で入力するので、サイトには届きません。
  • 支払が済むまで、注文は「支払待ち」です。30 分の期限までに支払がなければ、自動で取り消して在庫を戻します。
  • 支払の画面から途中で戻っても、注文の画面の「支払う」から、期限までならやり直せます。
  • 注文のときはカードの利用枠を確保（与信）するだけで、代金は出荷のときに確定します。

出荷したら、届くまでの状況が見える

  • 出荷すると、配送業者と送り状番号を書いたメールが届きます。
  • 注文の画面と注文の履歴に、「出荷済み」「配送中」「配達完了」と配送の状況が出ます。
  • 配送の状況は、配送業者からの知らせで自動で進みます。

お店の人ができること

商品、在庫、税率、注文、売上を一つの管理画面で

専門の知識がなくても、画面の案内に沿って商品を出し、在庫を直し、注文を扱い、売れ行きを確かめられます。

商品を登録して、公開の日時を予約する

  • 一つの商品に「白の M」「黒の L」のような組み合わせ（バリアント）を持たせ、それぞれに在庫を持てます。
  • 公開の開始と終了の日時を決めておけば、その時間に自動で店に出て、自動で引っ込みます。セールや季節商品に使えます。
  • スマートフォンで撮った写真（HEIC など）もそのまま登録でき、軽い形式に変えて配信します。撮影場所などの情報は自動で消します。
  • 一度店に出した商品は消せず、「販売終了」にします。過去の注文の記録が崩れないためです。

在庫は、増減の理由と操作した人まで残る

  • 入荷・棚卸差異・破損などの理由を付けて在庫を増減します。
  • 注文で減った分も、注文番号付きで履歴に残ります。「なぜ数が合わないのか」を後から追えます。
  • 複数の担当者が同時に在庫を直しても、どちらの操作も失われません。

税率が変わっても、日付を入れておくだけ

  • 「標準 10%」「軽減 8%」のような税区分を商品に割り当てます。
  • 税率には適用の開始と終了の日時を持たせられるので、税制が変わるときや期間限定の減税にも、その日に合わせて自動で切り替わります。

注文を一覧で見て、出荷する

  • 注文の明細を品番・税抜単価・税率・税込単価まで表で確かめられます。
  • 配送業者と送り状番号を入れて出荷を登録すると、その時にカードの代金を確定します。確定できなければ、出荷は登録されません。
  • カードの利用枠の確保には期限があるので、期限が近い注文に印を付け、絞り込めます。
  • お客様のキャンセルの申請を受け、在庫を戻して取り消します。返送された注文は、在庫に戻すかを選んで取り消し、代金を返金します。
  • 担当者ごとに、できる操作を分けられます。

売上の動きを、週・月・四半期・年で見る

  • 期間と区切りを選ぶと、売上額と販売数量の推移をグラフと表で示します。商品を一つ選べば、その商品だけの動きも見られます。
  • 注文した日で数えるか、出荷した日で数えるかを切り替えられます。消費税や送料を除いた額にもできます。
  • 四半期と年は、お店の会計年度の区切りで数えます。
  • 表はそのまま CSV で取り出し、表計算ソフトで開けます。

どの色・サイズが売れているか

  • 商品を選ぶと、色やサイズの組み合わせごとの販売数量と売上額を、売れた順に並べます。
  • まったく売れなかった組み合わせも 0 として示すので、仕入れを見直すきっかけになります。

どこの、どんなお客様が買っているか

  • お届け先の都道府県、注文した時の年齢層、性別ごとに、売上額と注文件数を示します。
  • 年齢と性別は、会員登録のときに任意で入れてもらいます。生年月日や氏名はレポートに出しません。
  • レポートを見られる人は、担当者ごとに分けられます。営業の担当には売上の推移を見せない、といったことができます。

安心して任せられる理由

お店を開いてから困ることを、先につぶしてある

売り越しと二重の注文を防ぐ

人気商品の最後の 1 個に、同時に何人も注文した場面を自動で再現して確かめています。在庫がマイナスになることはありません。

カード番号を預からない

カード番号は、外部の決済サービス（Stripe）の画面で入力します。サイト側はカード番号を受け取らず、保存もしないので、サイトからカード番号が漏れることはありません。

ログインは専用の仕組みに任せる

パスワードの管理を自前で作らず、実績のある認証の仕組みを使っています。お客様と運営者のアカウントも完全に分けています。

直すたびに、全部を自動で確かめる

変更を入れるたびに、1,500 件以上の自動テストが流れます。新しい機能を足して、前の機能が壊れたまま出ることを防ぎます。

作り方

決めてから作る。確かめてから進む。

一人で開発していますが、チームで本番のサービスを作るときと同じ手順を守っています。作るものを文書で決め、決めたとおりに動くことをテストで証明してから、次に進みます。

225文書で決めた「こう動くべき」という条件。すべてにテストを対応させています
1,500 以上自動テストの件数（画面・サーバー・ブラウザでの通し操作）
10仕様書の数。機能を足すたび、また整理するたびに一つ書きます
2画面の数（店舗・管理）。文言は差し替えられるように作り、多言語化に備えています
仕様を書く誰が何をできるか、どうなれば完成かを、条件の一覧として書く。
設計を決める画面とサーバーのやり取りの約束（API）を先に決め、両側がそれに合わせる。
テストを先に書くまだ動かないことをテストで確かめてから、作り始める。
作って、見直すテストが通るように作り、決めた書き方の規則と照らして見直す。
サーバー業務ごとに部品を分け、将来は別々のサービスに切り出せる形にしています。Java 21 / Spring Boot / Spring Modulith / PostgreSQL / jOOQ
店舗画面表示が速く、検索エンジンにも読まれやすい作り。Next.js / TypeScript / Tailwind CSS
管理画面表や入力の多い業務向けの作り。React / TanStack Query / React Hook Form
決済カード番号を扱わない、決済サービスの支払の画面を使う方式。Stripe（テストモード）
ログイン標準の方式（OpenID Connect）に沿った専用の認証サーバー。Keycloak
品質変更のたびに自動でテストし、ブラウザの通し操作まで確かめます。JUnit / Testcontainers / Vitest / Playwright / GitHub Actions
運用アクセスが増えたら、同じサーバーを並べて増やせる作りにしています。Docker / S3 互換ストレージ / Prometheus

ここまで

買い物の流れから、売れ行きを見るところまで

「商品を見る → カート → 注文 → 支払 → 出荷 → 配送状況」の流れを省略せずに通し、集まった注文から、お店の人が売れ行きを確かめられるようになりました。

商品・在庫・税率の管理完成
カートと注文、キャンセル完成
会員登録・ログイン・運営者の権限完成
カード決済完成
出荷と配送状況完成
売上の簡易レポート完成

画面の写真は開発用の環境で撮ったもので、商品・お客様・注文はすべて試験用のデータです。決済は Stripe のテストモードで、実際の支払は発生しません。
