# 書き方の規則とレビュー

書き方の規則（[バックエンド](backend-coding.md)、[フロント](frontend-coding.md)、[テスト](test-writing.md)、[コメント](comments.md)）の書き方と、段階の最後のレビューでの使い方。

## 1. 規則の書き方

- 各文書の冒頭に「規則の一覧」（節、規則、確認方法）を置く。
- 確認方法は、自動（ArchUnit・Modulith のテスト、Biome、テスト、CI の script）かレビュー（段階の最後のレビューで読む）。自動のものは、使うツールやテストの名前を書く。
- 規則の節は、規則（何をどう書くか）と、1 行の理由（なぜか）を書く。細かな例外は ※ で表の下に書く。
- constitution は原則を、各文書は具体的な書き方を書く。constitution の文を転記しない。
- 新しい習慣が決まったら、その spec の plan か tasks で各文書に追加する。

## 2. レビュー

各段階の最後のレビューで、変えたコードを、各文書の一覧の確認方法が「レビュー」の規則と照合する。レビューの段階の tasks は、本書を参照に挙げる。レビューは、実装の過程を見ていないサブエージェントが skill `review` の手順で行う。

1. 変えたファイルを、spec の最初の commit の 1 つ前（`<base>`）からの差分で特定する ※1。
2. 各文書の一覧の確認方法が「レビュー」の規則と照合しながら読み、合わない所を修正する。修正しないものは、理由をレビューの報告に書く。
3. 一覧にない習慣に気づいたら、規則に追加するかを利用者に確認する。自動で確認できるようになった規則は、確認方法を「自動」に修正する。
4. 文書・コメント・コミットメッセージが、日本語として自然に書けていることも確認する。

※1：`git diff -M -l0 --name-status <base> HEAD | grep -v '^R100'`。`-l0` がないと、移動が多いときに移動の検出が打ち切られ、追加と削除として表示される。`R100`（中身の変わらない移動）は読まなくてよい。
