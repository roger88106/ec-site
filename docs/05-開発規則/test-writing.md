# テストの書き方

今のテストで守っている書き方。実行方法は [テストの実行方法](../06-手順書/running-tests.md)、テスト先行の進め方は [開発の進め方](workflow.md)の「テスト駆動開発」。確認方法が「レビュー」のものは、各 spec のレビューで、[書き方の規則とレビュー](review.md)に従って読む。バックエンドのテストは [バックエンドのテストの書き方](test-writing-backend.md)、画面と E2E のテストは [フロントのテストの書き方](test-writing-frontend.md)に分けてある。

## テストの種類と基準

### テストの種類

テストの種類と置き場所は、[テストの実行方法](../06-手順書/running-tests.md)の「テストの種類」。

- 層ごとの確認（バックエンド）：
  - domain は、単体テスト（と PIT）で自分の規則を確認し、後の層のテストに任せない。レベル A の domain は、単体テストだけで C0（命令網羅）・C1（分岐網羅）を満たし、C2（条件網羅）もできるだけ満たす。
  - application、presentation、`api/` は、入口ごとの統合テストで確認する。API のテストは presentation に置き、application も通す。API から届かない分岐だけ、単体テストで確認する。
  - infrastructure は、Repository と port の統合テストで確認する。
  - 画面をつないだ流れは、E2E で確認する。
  - 入口（service・Command・`api/`）以外の `lombok.NonNull` に null を渡すだけのテストは追加しない（[バックエンドの書き方](backend-coding.md)の「null の扱い」）。
- 流れのテスト（入口から複数の層を通す統合テストと E2E）は、正常と、標準の流れの中で起きる例外だけを確認する。標準でない流れでだけ起きる例外は、presentation と domain の、的を絞ったテストで確認する。
- 必須の統合テスト：Modulith の境界、Repository（永続化・再構築・差分更新・イベント発行）、並行性（並行の不変条件を持つモジュール）、外部連携の port（mock と実装の挙動の一致）。
- 店舗画面には結合テストを置かない ※1（対象ごとの方法は [フロントのテストの書き方](test-writing-frontend.md)の「店舗画面のテストは、対象ごとの方法で書く」）。画面をつないだ流れは E2E で確認する。
- 見た目（配置、色、余白）は目視で確認する。
- テストに出ない AC は CI が失敗にする。テストで確認できない AC は、理由と一緒に除外の一覧に書く。
- IdP（Keycloak）の振る舞いだけで決まる AC は、realm の設定ファイルの契約テスト（`RealmSettingsContractTest`）で確認する ※2。

※1：操作がサーバーアクションを通り、ブラウザーの中だけでは再現できないため。サーバーアクションを呼ばない操作はこの理由に当たらないので、例外にする。「送信 → サーバーアクション → 再描画」の失敗の経路（誤りの表示、フォーカスの移動、表示の遷移）は、E2E に任せず jsdom で確認する。同じ要素が残ることなどの表示の遷移は、静的な HTML では確認できない（結果を変えて再描画するため）。そこで、サーバーアクションの処理は差し替え、表示だけを確認する（処理はサーバーアクションのテストと E2E で確認する）。

※2：IdP は自分たちで作っていないので、設定が正しければ IdP が振る舞いを守る、とみなす。IdP を取り替えたときは、会員の登録・ログインの E2E で振る舞いを確認する。対象の AC は、`node scripts/ci/spec/ac-check.mjs --tests` で `RealmSettingsContractTest` が表示される AC である。

理由：テストの種類ごとに確認する対象を決め、どのテストでも確認されない AC や振る舞いを残さないため。

確認方法：

- 層ごとの確認：レビュー
- 流れのテストの範囲：レビュー
- 必須の統合テスト：レビュー
- 店舗画面に結合テストを置かない：レビュー
- テストに出ない AC：自動（`scripts/ci/spec/ac-check.mjs`）
- IdP の振る舞いだけで決まる AC：自動（`RealmSettingsContractTest`）

### カバレッジと mutation score の基準

基準の値、許容の幅、失敗したときと基準を変えるときの手順は、[テストの実行方法](../06-手順書/running-tests.md)の「カバレッジと mutation score の基準の検査」。

### テストの観点

テストを書く前と、レビューのときに、次の観点で抜けを探す。AC に書いてある観点は、AC のテストで確認する。

- 正常、業務の例外（`ErrorCode` ごとに 1 つ）、500 系（想定外の失敗）。
- 境界：上限・下限は、「ちょうど」（通る）と「1 つ外」（上限＋1、下限－1）の両方を確認する。DB を通る時刻の境界の 1 つ外は、1 マイクロ秒にする（DB の時刻の精度）。
- エッジケース：参照する商品の取り下げ・削除、税率の失効。
- domain の上限・下限の値が、DB に保存できること。
- 状態遷移：許す遷移と、許さない遷移。
- 拒否のとき、副作用がないこと：拒否した操作の後で、DB・イベント・外部の呼び出しが変わらない。
- 並行と冪等：同じ操作を同時に、または繰り返して行う。
- 外部の失敗：外部の port の失敗。
- 権限：権限のない操作者、他人のデータ。
- 時刻：期限の前後、日付の境目。
- 金額：端数、税、0 円、上限。
- DB の制約の違反：一意・外部キー・NOT NULL を破る操作の結果。
- 確認の強さ：状態コードだけ、件数だけで判定せず、結果の中身（項目の値、DB の状態）まで確認する。テストの土台の設定で、確認したい処理が実行されない形にしない。

理由：上限の「ちょうど」だけを確認して 1 つ外を確認していないテストや、状態コードと件数だけを確認して結果の中身を確認していないテストがあったため。

確認方法：レビュー

## テスト名

### AC 番号を入れる

AC を確認するテストは、名前（Java は `@DisplayName`、Vitest・Playwright は `test` の第 1 引数）の先頭に AC 番号を入れ、続けて振る舞いを日本語で書く（`AC-43 調整後に負になる調整は拒否される`）。複数の AC は 1 つずつ並べ（`AC-8、9、10`）、範囲（`AC-8〜10`）でまとめず、空白で区切った並び（`AC-1 AC-2`）にもしない。1→10 の AC は、spec の番号を付けて `AC-7-1、AC-7-2` と書く（`AC-7-1、2` は曖昧なので、ac-check が失敗にする）。

- AC と BR・NFR を並べるときは、AC を先にする。
- 複数の AC は番号の昇順にする。
- テストの名前にタスク番号（`T9314` など）を書かず、対応する AC・NFR の番号に替える。
- E2E の `test.step` の名前に AC の番号を書く所は、末尾に `（AC-…）` を付ける（`管理画面：画像を 2 枚選ぶと、ストレージへ送って登録する（AC-37）`）。書いていないステップには追加せず、書いてあるものは消さない。

理由：AC からテストを、テストから AC を引けるようにするため。

確認方法：

- 先頭の AC 番号と並べ方の形：自動（`ac-check.mjs`）
- BR・NFR との順、昇順、タスク番号を書かないこと、`test.step` の名前の形：レビュー

### 名前は振る舞いを書く

「〜すると〜になる」の形で、画面や API に起きることを書く。メソッド名やクラス名をそのまま書かない。フロントの `describe` の名前も同じで、関数名・コンポーネント名だけにせず、日本語で振る舞いを書く（`describe('ページ送り', …)`。`describe('Pagination', …)` は書かない）。

- Java のテストは、全ての `@Test`・`@ParameterizedTest` に `@DisplayName` を付ける。
- 1 つの観点を 1 つのテストにし、AC の番号はテストのメソッドの `@DisplayName` に付ける。
- `@Nested` の名前に AC の番号を書かない。その中のテストの名前にない AC の番号は、テストの名前に移す。
- `@DisplayName` に、場合を列挙しない。
- パラメーター化テストの名前は `@ParameterizedTest(name = "「{0}」")` にする（`{0}` は場合の名前）。
- 名前に書く AC の番号は、spec の AC の文と照合してから書く（`ac-check` は番号があることだけを確認し、中身が合うかは見ない）。

理由：失敗したときに、どの振る舞いが壊れたかが名前だけで分かるようにするため。

確認方法：レビュー（`@DisplayName` があることは自動。`TestNameTest`）。フロントの `describe` の名前が識別子だけでないことは自動（Biome の plugin `no-identifier-describe`）


## 待ち方

時間で待たない（`Thread.sleep`、`waitForTimeout`）。条件で待つ（Playwright の `expect(...).toBeVisible()` などの自動の再試行、状態を直接確認する）。

- 決まった時間だけ見て「起きないこと」を確認しない（Awaitility の `during`）。バックエンドでは、`AsyncEvents` でイベントのリスナーが終わる（または失敗する）のを待ってから、起きた数を確認する。
- E2E で 1 回だけ読む確認（`page.evaluate`、`boundingBox()`、`textContent()`）は、`expect.poll` か web-first の `expect`（`toBeVisible` など）で、条件を満たすまで待ってから確認する。
- E2E は、通信がなくなるまで待つ `networkidle` で待たない。画面の状態（要素が見えるなど）を条件にして待つ。
- タイムアウトは、バックエンドは `AsyncEvents.TIMEOUT`（単体テストの同時実行で使う `Concurrently` は、`AsyncEvents` を参照できないので、同じ値の `Concurrently.TIMEOUT` で待つ）、E2E は `e2e/src/waits.ts` の定数を使う。E2E は、定数を定義する `waits.ts` の外で、`timeout` などのタイムアウトを数字のリテラル（`10_000`、`5 * 1000` など）で書かない。長く待つ必要がある場合は、`waits.ts` に理由を書いた定数を加えて使う。
- E2E で裏の処理の結果を画面を再度開きながら待つときは、`e2e/src/waits.ts` の `reopenUntil` を使う。
- 同じイベントを連続して発行するテストは、前の発行の処理が終わるのを待ってから次を発行する。Spring Modulith は処理中の発行を（イベント、リスナー）の組で持つので、同じイベントの処理が重なると発行の記録が完了にならないことがある。

理由：処理が遅い環境では失敗し、速い環境では待ち時間が無駄になるため。決まった時間だけ見ると、遅い環境では、処理が終わる前に確認が終わり、誤って通るため。

確認方法：

- E2E で 1 回だけ読む確認を待つこと：レビュー
- 時間で待つこと：自動（バックエンドは `TimeWaitTest`、フロントと E2E は Biome の plugin `no-time-wait`）
- `networkidle`：自動（Biome の plugin `no-network-idle`）
- タイムアウトの数字のリテラル（`timeout` を含む項目、`intervals`、`setTimeout`・`setDefaultTimeout` などの引数。`e2e/src/waits.ts` を除く）：自動（Biome の plugin `no-timeout-literal`）
