# 会員モジュール

IdP（Keycloak）のアカウントと、EC の会員 ID の対応を管理する。

- レベル：B（業務の不変条件は「1 つのアカウントに 1 人の会員」だけ。3 層：api / service / infrastructure）
- 依存：なし（カート・注文の presentation 層から api で呼ばれる）
- 関連 spec：003（US-25〜27、BR-13）
- 用語と識別子：[用語集](../glossary.md)

## 会員

- 会員は、EC の会員 ID（UUID）、IdP のアカウントの ID（token の subject）、登録日時を持つ（[plan 003](../specs/003-auth/plan.md) 第 3.4 節）。
- カート・注文手続き・注文が持つのは、IdP のアカウントの ID ではなく会員 ID。IdP を替える・アカウントを移すときは、この対応だけを直す（BR-13）。
- メールアドレスと氏名は持たない。IdP が正本で、必要なときに token から読む（写しを同期しないため）。注文には、注文の時点のメールアドレスを注文の側に写す（AC-127）。
- 届け先などの会員の情報は、将来の spec でここに足す（spec 003 の Non-goals）。

## 会員を求める

- 会員は、会員の token で初めて EC の API を呼んだときに作る。IdP の登録を EC に知らせる仕組みは作らない。
- 「IdP のアカウントの ID から会員 ID を求める（なければ作る）」を、api で公開する。
- 同じアカウントの初回の要求が同時に来ても、会員は 1 人だけ作る。IdP のアカウントの ID の一意制約で守り、作れなければ（ほかの要求が先に作った）読み直す。作る処理は、呼び出し元のトランザクションを壊さない挿入で行う。

## token から会員を取り出す

presentation 層が、token から会員の情報（IdP のアカウントの ID、メールアドレス、確認済みか、姓、名）を取り出す部品は、`common/security` に置く（[plan 003](../specs/003-auth/plan.md) 第 3.2 節）。Spring Security の型を、モジュールに出さないため（constitution 10.2）。

- 店舗 API の「会員」の操作（[plan 003](../specs/003-auth/plan.md) 第 5.1 節）は、token がなければ filter で 401 にする。
- 「任意」の操作（カート）は、token があれば会員として扱い、なければログインしていない人として扱う。

## 構成

```
member/
├── api/             # 会員 ID を求める（カート・注文の presentation 層が使う）
├── service/         # 会員、リポジトリの port
└── infrastructure/  # リポジトリの実装
```

## 他モジュールへの公開

| 種類 | 内容 | 利用者 |
|------|------|--------|
| API | IdP のアカウントの ID から会員 ID を求める（なければ作る） | カート、注文 |

## データモデル

草案（T3303 でマイグレーションに置き換える）。

| 列 | 型 | 説明 |
|----|----|------|
| `id` | uuid | 会員 ID（主キー） |
| `idp_subject` | varchar(255) | IdP のアカウントの ID。一意 |
| `created_at` | timestamptz | 登録日時（会員を作った日時。IdP の登録日時ではない） |
