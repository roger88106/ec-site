# バックエンドのコードの観点

バックエンドのコードを書く・変えたときに、結果を返す前の自己確認とレビューの両方で読む。規則の文は、表の「規則の正本」で読む。

| 観点 | 級 | 見る問い | 過去の見落としの例 | 規則の正本 |
|------|------|------|------|------|
| 型の置き場所 | 重要 | 型が役割で決まった場所にあるか。具象に依存させるために public にしていないか。port の interface の内側に、他の層が使う型を置いていないか。 | `vo/` の型が持つ列挙を集約のパッケージに置き、パッケージが循環した。他の層が使う型を、port の interface の内側に置いていた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「標準の構成」「パッケージの大きさ」 |
| 層の役割と service の分け方 | 重要 | 処理は決まった service にあるか。同じ集約の service が呼ぶ側ごとに分かれていないか。 | ジョブから外部サービスを直接呼んでいた。同じ処理が 2 つの service にあった | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「標準の構成」「名前の形」 |
| トランザクションの付け方 | 重要 | 読むだけ・書くだけの service はクラスに、Command と Query を分けない service はメソッドに `@Transactional` があるか。 | 読むだけの用途の service の多くが、メソッドに付けていた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「トランザクションは application」 |
| SQL の回数 | 重要 | 1 つの要求・1 件の読み込みの SQL の数（子の表ごとの SELECT を含む）が、件数に比例しないか。1 回にできる呼び出しが 2 回以上ないか。 | 複数の行の登録を、ループの中で 1 行ずつ実行していた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「検索と更新と値の取り出し」 |
| 列挙の変換の置き場所 | 重要 | イベントの列挙への変換が、ドメインの列挙のメソッドにあるか。名前で変換する組は、定数の名前の集合が同じか。組ごとに、全ての値を変換できるテストがあるか。 | 同じ変換を、使う側のクラスごとに書いていた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「他のモジュールは腐敗防止層で包む」 |
| entity・集約の同一性 | 重要 | entity・集約の equals の決まりが文書にあり、それに従っているか。テストで entity を `isEqualTo` で比べて、ID だけで通っていないか。 | 集約の equals の決まりがどの文書にもなく、上書きするかが人によって違った | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「entity と集約の同一性」 |
| ロックと検索の順・インデックス | 重要 | 行をロックする検索に順序があるか。ジョブの検索の条件にインデックスがあるか。 | 出荷の行をロックする検索に `ORDER BY` がなかった | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「行をロックする検索」 |
| 上下限の一致（契約・domain・DB） | 重要 | 契約の制約、domain の定数、DB の列が一致するか。数え方（code point と UTF-16、精度）が同じか。 | 備考の上限を domain と契約で別の数え方にし、絵文字で結果が違った。期間の精度が domain と DB で違い、CHECK の違反で 500 になった | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「形の検証は presentation、業務の規則は domain」、[テストの書き方](../../../../docs/05-開発規則/test-writing.md)の「テストの観点」 |
| `lombok.NonNull` の置き場所 | 軽微 | service・Command・`api/` の公開の引数に付けていないか。NullAway が確認する引数に、同じ null の検査がないか。 | 入口に付けたうえに、下の層にも同じ null の検査が残っていた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「null の扱い」 |
| null と Optional の選び方 | 軽微 | `findXxx` は Optional か空の一覧、`getXxx` は NOT_FOUND か。ローカル変数に `@Nullable` を付けていないか。 | IDE の誤検知を消すために、ローカル変数に `@Nullable` を付け、`requireNonNull` で包んでいた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「null の扱い」 |
| 名前の形 | 軽微 | Config・Handler・Job・find と get・catch の変数・区切りの名前が、決めた形か。公開の API が `<機能>Api` で、呼ぶ側の名前を含んでいないか。 | catch の変数名が違った。テスト用のメソッドに区切りがなかった | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「名前の形」「細かいコードの書き方」 |
| 細かい書き方の統一 | 軽微 | 条件が 1 つの検索を Query で包んでいないか。引数をそのまま返していないか。代入だけのコンストラクターを手で書いていないか。 | 代入だけのコンストラクターを手で書き、引数をそのまま返すメソッドが残っていた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「細かいコードの書き方」 |
| jOOQ の値の取り出し | 軽微 | 位置で値を取っていないか。同じ変換を定数にまとめているか。 | 同じ型の列の順を取り違えてもコンパイルできる、位置での取り出しが多くの所にあった | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「検索と更新と値の取り出し」 |
| 外部のクライアントの作り方 | 軽微 | 外部のクライアントを Config の `@Bean` で作って注入し、テストは同じ設定から作っているか。 | 外部のクライアントを、使うクラスのコンストラクターの中で組み立てていた | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「設定の値の型」 |
| 想定外の例外の文と調べる手がかり | 軽微 | 想定外の例外の文に、利用者を指す ID を入れていないか。原因と、調べる手がかり（trace ID、原因の例外）が残るか。 | 再取得で見つからないときの例外に、原因も手がかりもなく調べられなかった | [バックエンドの書き方](../../../../docs/05-開発規則/backend-coding.md)の「想定外の例外のメッセージ」 |

## 重要の行の例

形で示すと分かりやすい行だけ、悪い例と良い例を書く。例の名前は、実際のコードの名前でなく一般的な名前にする。

### SQL の回数

悪い例：
```java
for (var item : items) {
    dsl.insertInto(TABLE).set(toRecord(item)).execute();
}
```
良い例：
```java
var insert = dsl.insertInto(TABLE, COL_A, COL_B);
for (var item : items) {
    insert = insert.values(item.a(), item.b());
}
insert.execute();
```

### 列挙の変換の置き場所

悪い例：使う側のクラスごとに、同じ変換を書く。
```java
var eventKind = switch (status) { case PAID -> EventKind.PAID; case CANCELED -> EventKind.CANCELED; };
```
良い例：ドメインの列挙のメソッドに 1 つだけ置く。
```java
var eventKind = status.toEvent();
```

### ロックと検索の順

悪い例：
```sql
SELECT * FROM shipment WHERE status = 'WAITING' FOR UPDATE
```
良い例：
```sql
SELECT * FROM shipment WHERE status = 'WAITING' ORDER BY id FOR UPDATE
```
