# 段階 9：フロントのテスト

- 前提：段階 7（管理画面）、段階 8（店舗画面）
- 完了条件：管理画面の主な操作の流れに結合テストがあり、コアフローの E2E があり、どちらも CI で通る。段階 7・8 の手動確認のうち、E2E にしたものを手で行わなくてよくなる。
- 参照：constitution 12・13、[管理画面の構成](../../../frontend/admin.md)、[店舗画面の構成](../../../frontend/store.md)
- 目的：段階 7・8 の手動確認で見つかった不具合（入力中に他の人が更新したときのバージョン、商品の詳細のキャッシュ）のような問題を、変更のたびに自動で見つけられるようにする。

## 結合テストの土台

- [x] **T901** 管理画面に React Testing Library、user-event、MSW、jsdom を入れる。テスト用の描画の補助（QueryClient、ルーター、toast を含む）と、API の応答を差し替える補助（admin.yaml の型に合わせた MSW のハンドラー）を作る。管理画面の構成に、結合テストの書き方の節を足す。

## 管理画面の結合テスト

各テストは、画面に見える文字・ラベル・ボタンの名前で操作し、結果を確かめる（constitution 12）。

- [x] **T902** 税率の一覧：行の追加（開始は直前の行の終了から）、保存の成功の toast、サーバーのエラー（期間の途切れ）の表示、入力中に他の人が更新したときの 409 と再読み込み（AC-3、4）。
- [x] **T903** 商品の登録・編集：品番の英小文字が大文字になる、サーバーの入力検証エラーが入力欄の下に出る、基本情報の 409 と再読み込み、販売終了・削除の確認のダイアログ、C 側に表示されたことのある商品には削除のボタンがない（AC-15、33）。
- [x] **T904** バリアントと在庫：軸のない商品にバリアントがあれば追加の欄がない（AC-24）、在庫の調整の負になるエラーと「その他」のメモのエラー（AC-43、46）。
- [x] **T905** 商品の一覧：絞り込みが URL のクエリになる、在庫数の合計の組み合わせ、集計の取得に失敗しても一覧は出る（AC-48、49）。

## E2E

- [x] **T906** `frontend/e2e` に Playwright のプロジェクトを作る。バックエンド（local profile と compose の PostgreSQL）、管理画面、店舗画面（どちらもビルドしたもの）を起動して動かす。テストのデータは管理 API で作り、品番に実行ごとの印を付けて他のデータと混ざらないようにする。店舗画面の API のキャッシュの秒数を環境変数で変えられるようにし、E2E では短くする（NFR-1 の 60 秒を待たずに、一覧への反映を確かめるため）。
- [ ] **T907** E2E：管理画面で商品を登録し、バリアントを追加し、在庫を調整して公開すると、店舗画面の一覧・検索・詳細に出て、バリアントを選ぶと在庫ありと出る（AC-29、51、58、62〜64）。
- [ ] **T908** E2E：非公開・販売終了にすると、店舗画面の詳細がすぐ「見つかりません」になり、一覧から消える。税区分の違う商品が、税込の価格で並ぶ（AC-30、32、54、65）。
- [ ] **T909** CI に E2E のジョブを追加する（PostgreSQL のサービス、バックエンドの起動、両アプリのビルドと起動、失敗時の Playwright のレポートの保存）。
