# フロントの書き方

管理画面と店舗画面に共通する書き方。アプリごとの構成は [管理画面](../design/apps/admin.md) と [店舗画面](../design/apps/store.md)。

## 規則の一覧

| 節 | 規則 | 確認方法 |
|----|------|----------|
| 1.1 | 画面に依存しない処理は `lib/` の関数、列挙の表示名の置き場所 | レビュー |
| 1.2 | 機能ごとに `features/<機能>/` | 機能の間の import は自動（`scripts/ci/frontend-rules.mjs`）、置き場所はレビュー |
| 2.1 | 生成した型で API を呼ぶ | 自動（型チェック） |
| 2.2 | エラーの文は API の `message` を表示する。エラーのコードは生成した型で比べる | 文はレビュー、コードは自動（型チェック） |
| 2.3 | 入力の制約は契約から書き出した定数 | 自動（`input-constraints.mjs`） |
| 2.4 | API の列挙の値ごとの表示は、全ての値を書く | レビュー（書けば、型チェックが値の漏れを見つける） |
| 3.1 | サーバーアクションは `withActionResult` で包む | 自動（Biome の plugin `no-catch-in-actions`） |
| 3.2 | サーバーアクションの結果は `ActionResult` | レビュー |
| 4 | 整形と lint は Biome | 自動（`pnpm lint`） |
| 5.1 | 共有パッケージに入れるもの・入れないもの | admin と store の同じファイルは自動（`scripts/ci/frontend-rules.mjs`）、共有パッケージに片方だけで使うものがないかはレビュー |
| 6 | 画面の URL は型で確認する | 自動（型チェック）、型の付かない URL はレビュー |
| 7.1 | 表示の文言は文言ファイルに置く | 自動（`hardcoded-text.mjs`、型チェック）、共有の文言に置く基準と読み込み時に引かないことはレビュー |
| 7.2 | 文言キーの形 | レビュー |
| 7.3 | ロケールは 1 か所 | 自動（`scripts/ci/frontend-rules.mjs`） |
| 8.1 | 店舗画面の環境変数は起動時に確認する | 自動（単体テスト） |
| 8.2 | 店舗画面のサーバーログは 1 行 1 件の JSON | 自動（単体テスト）、`console.*` の直書きは自動（Biome の `noConsole`） |
| 9.1 | 依存を追加したら再インストールして確認する | 自動（CI のインストールとライセンス検査） |

確認方法が「レビュー」のものは、各 spec の [レビュー](review.md) で読む。

## 1. 置き場所

### 1.1 画面に依存しない処理は `lib/` の関数

判定、変換、表示の整形、列挙の表示名は `lib/` の関数（React に依存しない）にし、横に単体テストを置く。コンポーネントはその関数を呼ぶだけにする。

- API の列挙の表示名と見た目（Badge の種類など）は、1 つの機能だけで使うなら `features/<機能>/labels.ts`、2 つ以上の機能で使うなら `lib/labels.ts` に置く。
- 2 つの画面で同じ整形は、共有パッケージ（第 5 節）に置く。

理由：規則を描画なしの速いテストで確認し、画面を再作成しても規則が残るようにするため。

### 1.2 機能ごとに `features/<機能>/`

画面とその画面だけで使うコンポーネント・処理は `features/<機能>/`、複数の機能で使うコンポーネントは `components/`、shadcn/ui の生成物は `components/ui/`（手動で修正せず、Biome の対象外）に置く。

理由：機能を追加する・削除するときに触るファイルを 1 か所にまとめるため。

## 2. API

### 2.1 生成した型で呼ぶ

API は `openapi-fetch`（管理画面は `openapi-react-query` の `$api`）で、生成した型を使って呼ぶ。パスや応答の型を手動で書かない。

理由：契約が変わったときに、型チェックで食い違いが分かるようにするため。

### 2.2 エラーの文は API の `message` を表示する

業務と入力のエラーは、API の `message`（項目ごとは `errors`）をそのまま表示する。画面で文を作るのは、通信の失敗など応答がないときだけ。

理由：メッセージの正本をバックエンドの 1 か所にするため。

エラーのコードで処理を分ける所（総額の変更で再表示する、カートへのリンクを添える、更新の競合など）は、契約の全体の列挙（`ErrorCode`）から生成した型の値で比べる（[API の規約](api-conventions.md) 第 5 節）。契約にないコードを書くと、型チェックで失敗する。

### 2.3 入力の制約は契約から書き出した定数

- 入力欄の `maxLength`・`minLength`・`max`・`min` は、`src/api/generated/constraints.ts` の定数で書く（数字を直接書かない）。
- このファイルは `generate:api` が OpenAPI の制約から作る。スキーマの項目は `schemas.<スキーマ>.<項目>`、クエリは `parameters.<操作 ID>.<名前>` で引く。

理由：契約の制約を変えたら、画面の制約も一緒に変わるようにするため。

### 2.4 API の列挙の値ごとの表示は、全ての値を書く

- 列挙の値ごとに文言や見た目を選ぶときは、`Record<列挙, …>`（または `satisfies Record<列挙, …>`）に、全ての値を書く。三項演算子で「それ以外」にまとめない。
- 1 つの値だけを特別に扱う判定（理由が「その他」ならメモを必須にする など）は、比較でよい。

理由：契約に値を追加したときに、表示を決めていない所を型チェックで見つけるため（「それ以外」にまとめると、新しい値が黙って別の表示になる）。

## 3. 店舗画面のサーバーアクション

### 3.1 サーバーアクションは `withActionResult` で包む

サーバーアクション（`src/actions/`）では `catch` を書かず、例外は `withActionResult` で結果にする。`withActionResult` は、最初に `unstable_rethrow(error)` を呼んで Next.js の画面遷移を通す。`redirect` は包みの外で呼ぶ。

理由：Next.js の `redirect`・`notFound` は例外を投げて画面を遷移させるので、捕捉して再スローしないと、ログイン画面への遷移などが通信の失敗として扱われるため。

### 3.2 結果は `ActionResult` で返す

サーバーアクションは失敗を例外にせず、`ActionResult`（`lib/actionResult.ts`）で返す。401 だけはログイン画面へ遷移させる。

理由：操作した場所の近くに結果を表示し、入力した内容を残すため。

## 4. 整形と lint

Biome の設定（`biome.jsonc`）に従う。インデント 2、行の長さ 120、単一引用符、セミコロンは必要な所だけ。Tailwind のクラスの並びも Biome が揃える。

理由：書き方の不統一をツールで防ぎ、レビューで扱わないため。

## 5. 共有パッケージ（`frontend/shared/`）

### 5.1 入れるもの・入れないもの

| 入れる | 入れない |
|--------|----------|
| 2 つの画面で使い、画面のフレームワーク（Vite・Next.js）と API の接続に依存しないもの：カテゴリの木、ログインの戻り先、クラス名の結合、数・日付・金額の整形、同じ表示のコンポーネントとテーマ、共通の文言、2 つの画面の API の生成で使う script（`scripts/`） | API の接続（接続先と認証が違う）、認証、画面の機能、サーバーアクション、片方の画面だけで使うもの |

- 共有のものは、各画面の機能を import しない。
- テーマの CSS は shadcn/ui の生成のまま 1 つにし、片方の画面だけで使う値（サイドバー、グラフ）も含める。テーマは再生成することがあり、分けると、生成のたびに 2 つのファイルを更新する必要があるため。
- shadcn/ui のコンポーネントは各画面の `components/ui/` に追加し、2 つの画面で同じ内容になったら `frontend/shared/src/ui/` に移す。共有コンポーネントは、店舗画面のサーバーコンポーネントからも使えるよう `"use client"` を付けたままにする。
- 共有コンポーネントのクラス名は、各画面の CSS の `@source` で Tailwind に読ませる（`node_modules` の先は自動で読まないため）。

理由：同じ処理とコンポーネントを 1 か所で修正し、片方の画面の都合をもう片方に持ち込まないため。

## 6. 画面の URL

| 画面 | 作り方 |
|------|--------|
| 管理画面 | `src/app/paths.ts` の `paths` の関数で作る（ルーターの定義は同じファイルの `routePatterns`）。URL の文字列を直接書かない |
| 店舗画面 | Next.js の `typedRoutes` で、画面の置き場所と照合する。クエリ付きの URL は機能の `*Query.ts` の関数（戻り値は `Route`）で作る。店舗画面の外の URL（IdP など）だけ `as Route` にし、理由をコメントに書く |

レビューでは、管理画面は `git grep` でパスの文字列の直書きを、店舗画面は `as Route` と、型の付かない `revalidatePath()` と `<form action>` の URL を確認する。

理由：間違った URL を型チェックで見つけるため。

## 7. 表示の文言とロケール

### 7.1 表示の文言は文言ファイルに置く

- 見出し、ボタン、ラベル、知らせ、確認の文、エラーの既定の文、ページの題名、店の名前は、各画面の `messages/ja.json` に置き、コードではキーで引く。
- 共有の文言（`common.*`、`frontend/shared/src/messages/ja.json`）に置くのは、2 つの画面で同じ役割の文言（同じ項目の名前、同じ整形の型）だけ。たまたま同じ文の別の役割の文言（「状態」など）と、片方の画面だけで使う文言は、それぞれの画面に置く。
- 引き方：コンポーネントの中は `useTranslations`（店舗画面の async のサーバーコンポーネントとサーバーアクションは `getTranslations`）、コンポーネントの外の関数は各画面の `src/i18n/translate.ts` の `translate`。
- 文言はモジュールの読み込み時に引いて定数にせず、関数かコンポーネントの中で引く。言語を切り替えたとき、読み込み時に定数にした文が古いまま残るため。
- 数は整形してから渡し（`{amount}` は数を整形しない）、値は名前で差し込む（`{code}を上へ`）。コードで組み立てる表示名（`画像 ${n}` など）も文言にする。
- 例外：テストの中の文字、開発者だけが見るログ、アイコンの代わりの記号、API の応答の文 ※1、言語に依らない入力例（`+10 / -3` など）。地域で形の変わる入力例（電話番号など）も、今は日本だけを扱うので直接書いてよい。地域を追加するときに文言に移す。

※1：検査（`hardcoded-text.mjs`）は、コメント以外の日本語を探す。API に送る値など文言でないものは、理由と一緒に `scripts/ci/hardcoded-text-exclusions.json` に書く。

理由：文言を 1 か所で管理し、2 つ目の言語を追加できるようにするため。

### 7.2 文言キーの形

`<機能>.<画面かコンポーネント>.<項目>`（例：`tax.list.title`）、共通は `common.<項目>`。英小文字で始める `camelCase` を `.` でつなぐ。API の列挙の値やエラーコードの表示名は、値からキーを組み立てるので、最後をその値のまま書く（`labels.publicationStatus.PUBLISHED`）。

理由：キーから表示する所を引けるようにするため。

### 7.3 ロケールは 1 か所

既定のロケール（`ja-JP`）とタイムゾーンは `frontend/shared/src/lib/locale.ts` だけに書き、整形とページの言語（`lang`）はそこから取る。`Intl.*` にロケールを直接書かない。

理由：言語を追加するときに、変える所を 1 か所にするため。

## 8. 店舗画面のサーバーの設定とログ

### 8.1 環境変数は起動時に確認する

本番（`NODE_ENV=production`）で、Cookie の暗号の鍵（`AUTH_SECRET`）、IdP の client ID と secret、IdP と API の場所、店舗画面を公開する URL がなければ、起動（`instrumentation.ts` の `register()`）で足りない名前を並べて失敗させる。ローカル用の既定値は、開発モードとテストでだけ使う ※2。任意の設定（既定値のあるもの）も、同じ所（`src/auth/config.ts` の `readServerConfig()`）で読み、各所で `process.env` を読まない（`NODE_ENV` など、Next.js が決める実行のモードは除く）。管理画面は接続先をビルドの時に埋め込むので、本番ビルドで確認する（管理画面の構成 第 10 節）。

※2：モジュールの読み込み時には確認しない。`next build` も本番モードで動き、CI のビルドには secret がないため。

理由：設定を忘れたまま、公開されている既定値のまま起動しないようにするため。

### 8.2 サーバーログは 1 行 1 件の JSON

- 店舗画面のサーバーログは `src/lib/server/log.ts` で、1 行 1 件の JSON（時刻、レベル、メッセージ、追跡 ID、項目）にする。`console.*` を直接呼ばない。
- レベル：操作は失敗したが続けられるものは `warn`、予期しない失敗は `error`、調べるための記録は `info`。
- バックエンドへの要求に W3C の `traceparent` を付け、同じ追跡 ID をログに出力する。

理由：バックエンドのログと同じ追跡 ID で、1 つの要求を辿れるようにするため。

## 9. 依存

### 9.1 依存を追加したら再インストールして確認する

- 依存を追加・更新したら、ルートで `pnpm install --frozen-lockfile` を再実行する。
- インストール時のスクリプトを持つライブラリ（間接の依存も含む）は、`pnpm-workspace.yaml` の `allowBuilds` に、実行するか（`true`・`false`）と理由を書く。
- ライセンスも確認する（`node scripts/ci/licenses/check-frontend.mjs`）。
- 両方は `scripts/dev/check-frontend.sh` の `install`・`licenses` の手順でも実行できる（既定で実行する）。

理由：`allowBuilds` にないライブラリがあると pnpm はインストールを失敗にするが、手元は依存が入った後なので気づかず、CI で初めて失敗するため。
