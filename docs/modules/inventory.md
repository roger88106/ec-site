# 在庫モジュール

バリアントごとの在庫数と、その調整履歴を管理する。

- レベル：A（並行して調整されても失われないこと。将来の引当・減算の土台）
- 依存：商品カタログモジュール（イベント）
- 関連 spec：001（US-8）、002（引当、注文による増減。BR-11、AC-82〜84、87、101、103、107）
- 用語と識別子：[用語集](../glossary.md)

## 在庫（集約）と在庫調整

- 在庫は、バリアント、商品、在庫数を持つ。
- 在庫調整は、増減量（0 以外）、調整理由、メモを持つ。調整理由が「その他」のときはメモが必須。
- 調整履歴は集約に含めず、追記するだけの記録として別に保存する（増え続けるため）。

## 在庫の調整は「差分の加算」で行う

在庫を読み込んで書き戻す方式（楽観ロック）は使わず、DB 上で「現在の在庫数に増減量を足す。ただし結果が負にならない場合だけ」という 1 回の更新で行う。

```sql
UPDATE inventory.stock_item
   SET quantity = quantity + :delta
 WHERE variant_id = :variantId AND quantity + :delta >= 0
RETURNING quantity;
```

- 楽観ロックだと、+5 と +3 が同時に来ると片方が失敗し、やり直しが必要になる。差分の加算なら DB が順番に処理するので、両方が反映される。将来の引当では、同じ在庫への同時更新がさらに増える。
- 更新されなかった場合は、「負になる」か「在庫がない」のどちらか。どちらかを確認して、エラーを分ける。
  - 増やす調整は、在庫があれば必ず更新される（在庫数は 0 以上）。更新されなかったなら、更新の時点で在庫がなかったので、在庫の有無を確かめずに 404 とする。確かめると、更新の後に作られた在庫（バリアントの登録のイベントで非同期に作られる）が見えて、400 と誤ることがある。
  - 減らす調整だけ、在庫の有無を確かめて、あれば 400、なければ 404 とする。
- 更新後の在庫数を受け取り、同じトランザクションで調整履歴に書く。
- 運営者の調整は、調整履歴に運営者 ID と氏名の写し（token の姓と名）を残す（AC-142。plan 003 第 3.5 節）。表示は写しを使う（運営者の氏名が後で変わっても、記録は変わらない）。注文に由来する調整（減算・戻し）は空。

**「在庫数は負にならない」というルールは、ドメインではなく、この更新の条件と DB の CHECK 制約にある。** ルールを変えるときは、ここを変える。

### 調整の検証と履歴の並び

- 増減量が 0、または理由が「その他」でメモが空のときは、DB に触れる前にドメインで拒否する（400）。メモは 500 文字まで。
- 調整後に負になる調整は 400（AC-43）。在庫がまだないバリアントへの調整は 404。
- 履歴は調整日時の新しい順。同じ日時の調整は、記録した順（連番）の新しい順に並べ、ページをまたいでも順序が変わらないようにする。

## 引当（spec 002）

注文手続きの間、在庫を期限付きで引き当て、ほかの消費者に売れないようにする（BR-11）。

- 引当は、持ち主（注文手続き）、在庫、数量、期限を持つ。持ち主と在庫の組で 1 つ。
- **販売可能数 ＝ 在庫数 − 有効な引当の合計**。期限切れの引当は数えないだけで、消さない（削除は定期ジョブの方式が決まってから）。解放のジョブも Redis も使わずに済み、引当と注文を同じトランザクションで扱える。
- 引当は在庫数を変えない。在庫数を変えるのは、運営者の調整、注文の成立、キャンセルだけ。
- C 側の在庫の有無（店舗向けの API）は、販売可能数が 1 以上かで判定する。

### 操作

いずれも呼び出し元（注文モジュール）のトランザクションに参加する（[plan 002](../specs/002-cart-and-order/plan.md) 第 2 節）。

| 操作 | 内容 |
|------|------|
| 引き当てる | 対象の在庫をバリアント ID の順に行ロックし、ほかの持ち主の有効な引当を除いた販売可能数で判定する。全品目が足りれば、この持ち主の引当を置き換える。足りなければ何も書かず、足りない品目を返す |
| 解く | 持ち主の引当を消す |
| 減算に置き換える | 行ロックのうえ、ほかの持ち主の有効な引当を除いて足りるかを確かめ（期限切れの引き当て直しを兼ねる）、在庫数を減らし、持ち主の引当を消し、理由「注文」と注文番号で調整履歴を書く。1 つでも足りなければ何も変えない |
| 戻す | 在庫数を増やし、理由「注文のキャンセル」と注文番号で調整履歴を書く |

- 運営者の調整は引当を考えない（BR-11）。販売可能数より多く減らすと、引当中の注文が成立しないことがある。
- 理由「注文」「注文のキャンセル」は、運営者の調整では選べない（AC-107。400）。

## 在庫の作成と削除

- バリアントが登録されたら、在庫数 0 の在庫を作る。同じイベントが 2 回届いても、在庫は 1 つだけになるようにする。
- バリアントまたは商品が削除されたら、その在庫と調整履歴を消す。
- イベントはコミット後に非同期で届くため、バリアントの登録直後のごく短い間は在庫がない。
  - C 側：在庫がなければ「在庫なし」として扱う。
  - B 側：その間の在庫調整は「見つからない」になる。

### イベントの処理に失敗したとき（MVP で受け入れるリスク）

MVP では、処理に失敗したイベントを自動では再発行しない（[plan](../specs/001-catalog-and-inventory/plan.md) 第 4 節）。複数インスタンスで再発行が重複しないようにするには分散ロックが必要で、その方式が未定のため（constitution 16）。

- **起きること**：バリアント登録のイベントの処理に失敗すると（DB の一時的な障害など）、そのバリアントの在庫は作られないままになる。C 側では常に「在庫なし」、B 側では在庫の取得・調整が「見つからない」になる。削除のイベントで失敗すると、在庫と調整履歴が残る（実害はない）。
- **気づき方**：未完了のイベントはイベント発行記録に残り、エラーログが出る。B 側で、登録したバリアントの在庫が「見つからない」ままになる。
- **復旧手順**：原因を取り除いたあと、起動時の未完了イベントの再発行を設定で一時的に有効にし、1 インスタンスだけ再起動する。リスナーは冪等なので、再発行で在庫が重複することはない。終わったら設定を戻す。
- **順序の逆転**：削除のイベントが登録のイベントより先に処理されると、削除済みのバリアントの在庫が残る。参照されないので実害はなく、MVP では放置する。

自動の再発行は、constitution 16 の「未完了イベントの自動再発行」で決める。

- バリアントと商品は商品カタログモジュールの ID なので、外部キーは張らない（constitution 6）。
- 商品を持つのは、B 側で商品ごとの在庫数の合計を出すため。
- 調整履歴は、在庫の削除で一緒に消える（`ON DELETE CASCADE`）。バリアント・商品の削除のイベントで在庫を消すため。

- 注文に由来する調整だけが注文 ID と注文番号を持つことは、CHECK 制約でも守る。
