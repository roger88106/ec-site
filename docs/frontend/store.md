# 店舗画面（`frontend/store`）の構成

C 側（消費者）の画面。Next.js（App Router）で、店舗 API（`store.yaml`）をサーバーコンポーネントから呼ぶ。
管理画面（[admin.md](admin.md)）と同じく、置き場所と作り方の決まりを本書にまとめる。新しい画面は、第 8 節の手順どおりに作る。

- 技術の採用：[constitution](../constitution.md) 第 2 節
- 画面の一覧と spec ごとの決定：各 spec の plan（例：[plan 001](../specs/001-catalog-and-inventory/plan.md) 第 3 節）

## 1. 技術

| 用途 | 採用 | 補足 |
|------|------|------|
| フレームワーク | Next.js（App Router） | 画面はサーバーコンポーネントで作り、操作のある部分だけクライアントコンポーネントにする |
| API の型 | openapi-typescript | `store.yaml` から生成する。生成物はコミットしない（constitution 9） |
| API の呼び出し | openapi-fetch | サーバーコンポーネントからだけ呼ぶ。ブラウザから API は呼ばない |
| キャッシュ | Next.js の fetch のキャッシュ | API の結果は最大 60 秒（NFR-1） |
| UI | shadcn/ui、Tailwind CSS、lucide-react | 管理画面と同じ |
| lint・整形 | Biome | 管理画面と同じ設定 |
| テスト | Vitest | 画面に依存しない関数と表示の部品（constitution 12） |

## 2. ディレクトリ

```
frontend/store/src/
├── app/              # ルート（page.tsx、layout.tsx、not-found.tsx）。データの取得と部品の組み立てだけを書く
├── api/
│   ├── generated/    # store.yaml から生成（コミットしない）
│   ├── client.ts     # openapi-fetch のクライアント（サーバー専用）
│   └── types.ts      # 画面から使うスキーマの型の別名
├── components/
│   ├── ui/           # shadcn/ui が生成する部品。手で直さない
│   └── *.tsx         # 機能をまたいで使う部品（価格、ページング、ヘッダーなど）
├── lib/              # 画面に依存しない関数。単体テストを横に置く
└── features/
    └── <機能>/       # catalog（商品とカテゴリ）
        ├── components/   # その機能の中だけで使う部品
        └── *.ts          # その機能の中だけで使う関数・型
```

- ルート（`app/`）は Next.js の決まりで置き場所が決まるので、画面の部品は `features/` に置き、`page.tsx` は薄く保つ。
- 機能どうしは import しない。2 つ以上の機能で使うものは `components/` か `lib/` に置く。
- クライアントコンポーネント（`'use client'`）は、操作のある部品（バリアントの選択、絞り込みの入力など）だけにする。API はそこから呼ばない。

## 3. 画面の URL

| URL | 画面 |
|-----|------|
| `/` | トップ（カテゴリの一覧と新着の商品） |
| `/products` | 商品一覧（クエリ：`categoryId`、`minPrice`、`maxPrice`、`sort`、`page`） |
| `/search` | 検索結果（クエリ：`q`、`page`） |
| `/products/[productId]` | 商品の詳細 |

- URL は商品 ID で作り、品番は使わない（AC-66）。
- 絞り込み・並び順・ページは URL のクエリに持つ。入力の送信は、フォームの GET（URL の書き換え）で行う。
- 表示されない商品・存在しない商品は、どちらも「見つかりません」の画面（404）にする（AC-65）。

## 4. API の呼び出し

- サーバーコンポーネントで `const api = await getApi()` としてから、`api.GET('<パス>', ...)` で呼ぶ。クライアントは `server-only` にし、ブラウザのバンドルに入れない。
- `getApi` は画面をリクエストのたびに作るようにする（ビルドのときに API を呼ばない）。API の結果のキャッシュはこれとは別に効く。
- 接続先は環境変数 `STORE_API_BASE_URL`（既定 `http://localhost:8080/api/store`）。
- 結果のキャッシュは最大 60 秒（NFR-1）。在庫や価格の変更は、1 分以内に表示に反映される。
- 404 は Next.js の `notFound()` にする。それ以外のエラーは、エラーの画面（`error.tsx`）に出す。

## 5. 表示の決まり

| 対象 | 決まり |
|------|--------|
| 価格 | 「1,980 円（税抜 1,800 円）」（BR-4）。C 側の商品は必ず税込価格を持つ |
| 在庫 | 「在庫あり」「在庫なし」だけ。数量は出さない（AC-64）。一覧では在庫のない商品に「在庫なし」を示す（AC-56） |
| 画像 | 画像の機能（US-7）までは、代わりの図を出す |
| バリアントの選択 | 軸ごとに値を並べる。他の軸の選択と組み合わせて、在庫切れ・販売停止のバリアントにしかならない値は、選べない状態（グレー）で出す（AC-62、28） |

## 6. 結果の知らせ方

- C 側の操作は閲覧だけなので、取得の失敗はエラーの画面に出す。入力の誤り（URL のクエリの形が違うなど）は、API のエラーの `message` をその画面に出す。価格帯の下限が上限より大きいときは、API はエラーにせず空の一覧を返す。

## 7. 品質

- CI で、lint（Biome）、型チェック、テスト、ビルドを実行する（constitution 13）。型チェックとビルドは、型の生成の後に行う。
- 単体テストの対象は `lib/` と `features/` の関数（バリアントの選択など）と、価格などの表示の部品。

## 8. 画面を追加する手順

1. 使う API が `store.yaml` にあることを確かめる。なければ、先に plan と `store.yaml` を直す（constitution 15）。
2. `app/` にルートを作り、部品は `features/<機能>/components/` に置く。操作のある部分だけクライアントコンポーネントにする。
3. データはサーバーコンポーネントで取得し、第 4 節に従う。
4. 新しい表示の決まりは `lib/` か `features/` の関数にし、単体テストを書く。
5. lint、型チェック、テスト、ビルドを通し、開発サーバーで表示を確かめる。
