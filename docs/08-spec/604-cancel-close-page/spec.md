# Spec 604：注文の取消で、開いた支払画面を閉じずに支払なしにする不具合を修正する

種類：整理　規模：M　ステータス：確定

## 背景と目的

注文の取消で支払を取り消すとき、未払いの支払は支払なしにするが、決済サービス（Stripe）の支払画面は閉じない。支払画面を閉じる処理があるのは、期限切れのジョブと、支払画面の URL を返す処理（使わない画面を閉じる）だけである。決済サービスの支払画面は、作ってから最大 31 分有効である。消費者が支払画面を開いたまま注文が取り消されると、取り消した注文の代金を払える。

与信の成功の通知が届けば、支払は与信の取消待ちになる（今の規則：支払なしの支払に届いた与信は取り消す）。通知が届かなければ、与信は取り消されない。#549 の pull request #602 の draft を外す前のレビュー（組み込みのコードレビュー）で見つけた。コードを読んでの判断で、実行は未確認である。

ただし、今の注文の規則では起きない。取消が未払いの支払に届く経路がないためである。支払待ちの注文は、運営者のキャンセルも申請もできず、支払の期限切れのキャンセルは、支払が先に支払なしになった後に届く（[注文モジュール](../../03-機能仕様/order.md)の「状態の遷移」、AC-158）。spec の最後のレビューで分かった。利用者は、支払待ちのキャンセルを加えたときの備え（防御のコード）として残すと決めた（2026-11-20）。

期限切れのジョブで同種の問題（#545）があり、#549 で修正した。この spec は、注文の取消の経路で、支払画面を閉じるようにする。今の注文の規則では、消費者・運営者に見える振る舞いは変わらない。変わるのは、取消が未払いの支払に届いたときの 1 点だけである（DN-604-1）。追跡の issue は #604。#544（リリースの前の整理）の段階 3 の線 A（支払と注文）の spec である。

## スコープ

| 含める | 含めない |
|--------|----------|
| 注文の取消で未払いから支払なしにした支払に支払画面があれば、コミットの後に決済サービスで閉じること | 注文のモジュールのコード |
| 閉じる前に支払が済んでいたとき、決済サービスから与信を取得して、与信を取り消すこと | 期限切れのジョブの流れ（#549 で修正した） |
| 決済の機能仕様・設計・用語集の修正 | 支払画面の期限切れの通知の扱い（変えない） |
| | 決済サービスの呼び方（冪等キーの扱いを含む。変えない） |

決定（issue 担当のセッションが利用者に代わって 2026-11-20 に確認した）：

- 規模と種類：整理・規模 M とする。
  - 理由（規模）：DB の構造と API の契約を変えない。変えるのは決済のモジュールだけで、モジュールをまたぐ設計の決定がないため、plan に書くことがない。
  - 理由（整理）：レビューで見つけた不具合の修正で、注文の取消の AC の振る舞い（支払なしにする）は変えないため。前例は spec 549（同じ種類の不具合を、整理の spec の非機能要件の例外として修正した）。
- 決定 1（閉じる仕組み）：
  - 案 A（採用）：支払の集約は、取消で未払いから支払なしにする。支払画面があるときは、決済の中だけで使うイベント「支払画面を閉じる依頼」も登録する。与信の取消の依頼・返金の依頼と同じく、コミットの後にリスナーがイベントを受け取り（トランザクションを持たない）、決済サービスで画面を閉じる。決済サービスが失敗したら例外で終わり、イベントは未完了で残って、再発行で再試行する。
  - 案 B：コミットの後のコールバックで、直接閉じる。決済サービスが失敗したときに再試行がない。
  - 案 C：期限切れのジョブに、支払なしの支払の支払画面も閉じさせる。支払の期限（最大 30 分）まで画面が開いたままになり、ジョブの検索の対象も変わる。
  - 理由（案 A）：今の与信の取消・返金と同じ形で、コミットの後の呼び出しと再試行の仕組みを新しく作らずに済むため。イベントは支払と同じトランザクションで記録されるので、決済サービスが失敗しても、注文のキャンセルをロールバックせずに再試行できるため。
  - 前提：注文の取消は、注文のキャンセルのトランザクションの中から呼ばれ、そのトランザクションに加わる。決済サービスは、トランザクションの外（コミットの後）で呼び出す必要がある。
- 決定 2（閉じる前に支払が済んでいたとき）：
  - 案 A（採用）：決済サービスから与信を取得して、支払に反映する。支払なしの支払に反映した与信は、今の規則で与信の取消待ちになり、与信の取消の依頼が登録されて取り消される。与信を取得できなければ例外で終わり、再発行で再試行する。
  - 案 B：何もせず、与信の成功の通知を待つ。通知が届かないと与信が取り消されない問題が残る。
  - 理由（案 A）：与信の成功の通知が届かないときも、与信を取り消せるため。
- 決定 3（決済サービスを呼ばないとき）：リスナーが受けたとき、支払が支払なし以外の状態である（通知が先に届いて与信の取消待ちになった、など）か、支払画面がなければ、決済サービスを呼ばない。閉じた画面を閉じる操作も成功として扱う（今の決済サービスの port の規則）ので、再発行で同じイベントを複数回受け取っても、結果は変わらない。
- 決定 4（文書）：
  - 決済の機能仕様：注文の取消で支払なしにした支払の、支払画面を閉じる規則と理由を書く。規則は、「与信の取消」の前に節を加えて書く。状態の遷移の後の箇条（イベントを登録する規則）に「支払画面を閉じる依頼」を加える。AC も業務規則の番号（BR）も追加しない。
  - 決済の設計：「注文のキャンセルと、与信の取消・返金」の図と箇条に、支払画面を閉じる流れを加える。
  - 用語集：イベント「支払画面を閉じる依頼」を加える（既存の「与信の取消の依頼」の行と同じ形）。
