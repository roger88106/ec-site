# コメントの書き方

バックエンドとフロントに共通するコメントの書き方。言語は [開発の進め方](workflow.md) 第 3 節。

## 規則の一覧

第 1 節の spec・plan・tasks の番号は、CI の `spec-numbers.mjs` で確認する。第 2 節のうち、本番のコードのクラスとメンバーに Javadoc があることは、Checkstyle（`./gradlew check`）で確認する。第 6.1 節のうち、キーを文字で書いた呼び出しにコメントがあることは、CI の `message-comments.mjs` で確認する。他は、各 spec の [レビュー](review.md) で読む。

| 節 | 規則 |
|----|------|
| 1 | 今のコードが何をし、なぜそうするかを書く。spec の番号と決定の経緯は書かない |
| 2 | Java は、クラスと全てのメンバーに Javadoc |
| 3 | TypeScript は、最上位の関数・コンポーネント・型・定数に TSDoc |
| 4 | 理由が読み取れない処理の前に、1 行で理由 |
| 5 | 複雑な処理の前に、何の結果を得るかを 1 行で |
| 6.1 | 文言をキーにした所に、何が表示されるか |
| 6.2 | 名前と型で分からない型の項目に、論理名と意味 |
| 6.3 | 一目で意図が分からない処理の前に、何のためか |

## 1. 何を書くか

- 今のコードが何をし、なぜそうするか（業務の規則そのもの、根拠の文書の節）を書く。決定の経緯（前の実装との違い、採らなかった案）はコミットメッセージに書く。
- 本番のコード（`src/main`、フロントの `src` のテスト以外）には、spec・plan・tasks の番号（`AC-`・`DC-` など、`plan 001 第 7 節`、タスク番号）を書かず、規則を言葉で書く（`（AC-68）` ではなく「配信する画像は、全て WebP にする」）。spec との対応はテストの名前に書く。
- 根拠は、コードと一緒に修正していく文書の名前と節で書く（`（店舗画面の構成 第 4.2 節）` など）。
- 例外：適用済みのマイグレーションはコメントも変えない（Flyway の checksum が変わるため）。新しいマイグレーションには番号を書かない。

理由：コメントを常に今のコードの説明として正しく保つため。spec の番号は仕様の管理の仕方で変わり、テストの名前と違って照合されないので、気づかれないまま古くなる。

## 2. Java（Javadoc）

- クラスと全てのメンバー（private を含む）に書く。`@DisplayName` を付けたテストのクラスとメソッドには必要ない。
- private のメンバーは、何をするかの 1 文でよい。`@param`・`@return` は書けるなら書く（検査は Javadoc があるかだけを見る）。
- 1 文目に何をするか（何であるか）を書き、補足は 1 文目の後に `<br />` を置いて続ける。
- メソッドには `@param`・`@return`（例外の条件があれば `@throws`）、record は項目を `@param` で書く。

```java
/**
 * 違反した制約の名前を取り出す。<br />
 * jOOQ や Spring の例外に包まれていても、原因をたどって PostgreSQL のエラーを探す。
 *
 * @param ex 例外
 * @return 制約名。制約違反でなければ空
 */
```

理由：使う側が実装を読まずに意味を把握できるようにするため。

## 3. TypeScript（TSDoc）

- モジュールの最上位の関数・コンポーネント・型・定数に `/** */` を書く（型の項目は第 6.2 節）。shadcn/ui の生成物には書かない。
- 関数には `@param`・`@returns` を書き、`@param` の説明の位置を揃える。1 行で書けるものは 1 行にする。

```ts
/** カートを移した結果の知らせ。カートの画面で一度だけ示す */
export type CartMergeNotice = {
  /** 数量を 10 に切り詰めた品目（切り詰めた後の数量） */
  truncated: NoticeItems
}
```

理由：Java と同じ。

## 4. 処理の中のコメント

読んだだけでは理由が分からない処理（例外の扱い、順番に意味があるもの、外部のライブラリやサービスに固有の挙動）の前に、1 行で理由を書く。読めば分かる処理には書かない。

```ts
// redirect は例外で移動を知らせるので、try の外で呼ぶ
redirect(`/checkout/${checkoutId}`)
```

理由：書き換えるときに、意味のある順番や例外の扱いを変えてしまわないため。

## 5. 複雑な処理のコメント

次のどれかに当たる処理の直前に、何の結果を得るか（必要なら理由も）を 1 行で書く。意味が分からない所は推測で書かず、利用者に確認する。

| 当たるもの | 例 |
|------------|----|
| stream の 2 段以上の変換 ※1 | `map` の後に `filter` |
| 集計 | `groupingBy`・`flatMap`・`reduce` |
| 入れ子の繰り返し | — |
| 3 つ以上をつないだ条件 | `a && b && c` |
| 3 つ以上の分岐 | `if`・`else if` の連なり、`switch` |

※1：`toList()` などの終わりの操作は数えない。

```java
// 税率ごとに、税込みの金額を合計する（税は税率ごとに 1 回だけ端数を切り捨てるため）
Map<BigDecimal, Money> totalByRate = lines.stream()
        .collect(groupingBy(Line::taxRate, reducing(Money.ZERO, Line::amount, Money::add)));
```

理由：処理を 1 段ずつ読まなくても何を作っているかが分かり、書き換えるときに結果の意味を変えないようにするため。

## 6. フロントの文言・型・処理のコメント

### 6.1 文言をキーにした所

何が表示されるかを短く書く。文言の全文は転記しない。

| 場所 | 書き方 |
|------|--------|
| JSX の子 | 式の中に `{t('title') /* 税区分 */}` ※2 |
| 属性 | 値の後に `/* 税区分 */` |
| JSX の外の式 | 行の後に `// 税区分` |

※2：要素の後ろに `{/* */}` を置くと、要素の間に空白ができるので使わない。

```tsx
<PageHeader title={t('tax.list.title') /* 税区分 */} />
<Button>{t('common.save') /* 保存 */}</Button>
```

理由：キーだけでは画面に何が表示されるかが分からず、全文を転記すると文言ファイルと食い違っていくため。

### 6.2 型の項目

名前と型で分からない項目に、1 文目に論理名、続けて特別な値の意味・単位・範囲・その値を持つ理由を書く。`id`、`name` など分かるものには書かない。

```ts
type CartLine = {
  /** 数量。1〜10（カートの上限） */
  quantity: number
  /** 税込の単価（円）。表示されない商品なら null */
  unitPrice: number | null
}
```

理由：API の契約や業務の規則を開かずに、値の意味が分かるようにするため。

### 6.3 一目で意図が分からない処理

イベントの処理、コンポーネントの差し替え（`render`・`nativeButton` など）、フレームワークの決まりによる書き方（`unstable_rethrow` など）の前に、何のためかを 1 行で書く。

理由：フレームワークの決まりを知らない人が、意味のある書き方を不要と思って削除しないようにするため。
