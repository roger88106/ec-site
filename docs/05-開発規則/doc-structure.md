# 文書の構成

文書をどこに置き、どう組み立てるかの規則。文書を追加する・内容を追加する・移す・spec を書くときに読む。

## 文書の置き場所

各フォルダーに置くものは、[constitution](../constitution.md)の「文書の地図」にあるフォルダーの `README.md` に一覧がある。文書を追加したら、そのフォルダーの `README.md` の表に行を加える。`docs/` の直下には、constitution とフォルダーだけを置く。文書ごとの書く範囲は、「文書の種類ごとの雛形」にある。次の表は、フォルダーの一覧にない置き場所である。

| 内容 | 置き場所 |
|------|----------|
| 今回の変更（何を・どう・手順） | `docs/08-spec/<番号>-*/` の spec・plan・tasks（1→10 の番号は 0 で埋めない。MVP は archive の下） |
| API の項目 | `api/openapi/` |
| テーブルの定義 | Flyway のマイグレーション（作成するまでは `docs/03-機能仕様/` に草案を置く） |
| 後回しの作業と未決事項 | issue（milestone `1→10`。[起票と記録の操作](issues.md)の「起票」） |
| 規模 M の spec | `docs/08-spec/<番号>-<名前>/spec.md`（[開発の進め方](workflow.md)の「規模」） |
| spec の進み具合 | MVP の spec は README の進捗の表、1→10 の spec は追跡の issue と milestone |
| 決定の経緯 | コミットメッセージ |
| 完了した 1→10 の spec | `docs/08-spec/archive/1to10/`（[起票と記録の操作](issues.md)の「アーカイブの操作」） |

文書には今のルールと設計だけを書く。

## 参照

- 参照の形は `<文書の名前>の「<見出し>」`。Markdown では、文書の名前をリンクにする（`[起票と記録の操作](issues.md)の「起票」`。この文書からの相対パスにする）。`docs/08-spec/` の見出しを指すときは、見出しの番号を除いて書く。末尾に全角の括弧の補足（`（DC-283-20）` など）がある見出しは、補足を省いて書いてよい。文書の名前は、各文書の 1 行目の見出しから、括弧の補足を除いた形。
- コードのコメントなどでは、「の」を挟まずにパスの直後に見出しを書いてもよい（`docs/05-開発規則/issues.md「起票」`）。
- `docs/` の下の文書へのリンクテキストは、見出しの参照の形でなくても、文書の名前にする（`[書き方の規則とレビュー](review.md)`。「レビュー」のように略さない）。理由：略した名前は、文書の名前で検索しても見つからないため。文書の名前の他に許可する形は、次のとおり。
  - ファイル名かパス：文書の地図の表などで使う。見出しの参照の形では使わない。
  - `constitution`：constitution へのリンク。
  - 番号や役割：spec・plan・tasks の文書へのリンク（`MVP-002`、`227`、「レビューの結果」）。
  - `#` の付いたリンク：リンクテキストは見ない。
- 同じ文書に同じ見出しが 2 つ以上あるときは、親の見出しを前に付ける（`「段階 1」の「タスク」`）。
- 同じ文書の中の節は、文書の名前を付けずに `「<見出し>」` と書く。見出しを変えたら、同じ文書の中の参照をレビューで確認する。
- 見出しでない所（表の行や列、用語集の語）を指すときは、この形を使わない。「の」と「」の間に、指すものの種類を書く（`用語集の語「写し」`、`AC 一覧の列「今の内容」`）。パスの後でも同じに書く（`glossary.md の語「写し」`）。
- 規則を参照するときは、constitution の節ではなく、細則の文書を指す（文書の地図を指すのはよい）。
- `第 N 節` と `N 節` の形の参照は書かない（区切りの形を含む判定は `scripts/ci/doc-refs.mjs` の冒頭のコメント）。理由：節の番号は節を加える・移すたびに変わるが、見出しの参照は切れると検査で見つかるため。
- `docs/08-spec/` の外の文書の見出しに、番号（`1.`、`1.2` の形）を付けない。理由：参照は見出しの名前で書くので番号は目印でしかなく、節を加える・移すと親の番号と合わなくなるため。

検査（`doc-refs`）の範囲は、`scripts/ci/doc-refs.mjs` の冒頭のコメントにある。

## spec と plan の書き方

| 対象 | 書き方 |
|------|--------|
| AC・DC | 1 つの AC・DC に条件を 1 つ、1〜2 文で書く。値の一覧と場合分けは、箇条書きか表にする。見た目の細部（px など）は書かない ※1 |
| Given / When / Then | 同時の操作など、手順で示さないと分からない条件だけに使う |
| 括弧 | 1 文に 1 つまで。理由は文の後に `理由：〜ため。` で、長い補足は表の下に `※1：` で書く |
| plan の節 | 決定を表（何を、どこに、確認方法）で先に示し、理由を後に書く。1 つの箇条書きに 1 つの決定 |
| 識別子 | ファイル・クラス・関数の名前は、表の列とコードブロックにだけ書き、本文は役割で書く（[文書の書き方](writing.md)の「論理名と物理名」） |
| 他の文書の内容 | モジュールの設計、API の項目、書き方の規則は転記せず、その文書を指す |

※1：画面の見た目は、後でデザイン案に置き換えるため。

理由：spec と plan は、利用者が承認の前に読み、実装の間にエージェントが何度も読むので、決定と条件を一目で読み取れるようにするため。

### 呼び出し元

- plan で操作やクラスを移す・削除すると決める前に、テスト（`src/test`・`src/integrationTest`・画面のテスト・E2E）を含む全ての呼び出し元を検索し、plan に挙げる。同じ名前のメソッドが複数あるときは、型で区別できる方法（IDE の呼び出しの階層）で調べる。理由：テストだけが使う呼び出しを見落とすと、実装で決定を変更することになるため。

### 形を判定する検査

- 入力の形を判定する script（hook、CI の検査）を作る spec は、許可する形の一覧で判定を書く。理由：禁止する形の一覧に回避の形を 1 つずつ加えても、レビューの指摘が尽きないため。
- その spec は、判定が誤りの防止（誤って書いたものを拒否し、意図して作った回避は対象にしない）か、回避の防止（意図して作った回避も拒否する）かを、DC で先に決める。決めた区分は、レビューで回避の形を重要度「高」にするかの基準になる（skill `review` の prompts.md）。
- 形から推定して判定する検査（`doc-refs`・`ja-text` などの CI の検査と、hook）を作る・拡張する spec は、plan（規模 M は spec）に「検出すべき例」と「検出してはいけない例」の表を置く。レビューでの使い方は[書き方の規則とレビュー](review.md)の「レビューの収束」。例の内容は、着手のときに決める。最初の `[テスト]` の前に、spec の文脈を持たないレビュー役に表を読ませ、例を追加させる。理由：検査を拡張した spec で、新しい漏れや誤りの形が各時点のレビューで重要度「高」で見つかったため（spec 283、284）。

### アーカイブ

- 完了した spec・plan・tasks は、内容と節の番号を変えず、移して切れたリンクも修正しない。理由：アーカイブは当時の記録で、当時の状態は Git の履歴で読めるため。今の設計はモジュールの設計書と `docs/02-設計/` に書く。
- アーカイブは、`docs/08-spec/.ignore` でエージェントの既定の検索（Grep）から外してある。読むときは、アーカイブのパスを指定して検索する。

## 文書の長さの基準

文書はエージェントが読むので、字数がそのまま token の費用になる。

| 項目 | 基準 |
|------|------|
| 大きさの目安 | `AGENTS.md` 8,000 バイト、constitution 10,000 バイト、`docs/05-開発規則/` の 1 つの文書 15,000 バイト（`wc -c` で測る） |
| 冒頭 | 1 行目の見出しから最初の `##` までは、何の文書かと、いつ読むかの 2 文以内。節の一覧を文で列挙しない |
| 表のセル | 1 つのセルは 300 バイトまで |
| 正本 | 1 つの規則の正本は 1 か所。他の文書は見出しの参照で指す |
| 理由 | `理由：〜ため。` の 1 文で書く。手順の 1 項目の短い理由は、括弧の中の句で書いてよい |
| 読める内容 | script・設定・コードから読める内容は書かず、そのファイルを指す |

- 目安を超えたときは、読む場面で分けるか、縮める。分けも縮めもしないときは、理由を[毎回読む文書と固定の文脈の大きさ](../07-記録/context-size.md)に書く。CI の検査は加えない。利用者が定期的にレビューする。
- 人が読む文書は短く保つ。エージェントだけが調べる細目（検査の範囲の説明、経緯、測定の詳細など）は、後で調べる価値があれば `docs/07-記録/` などの別の文書に移し、なければ削る。
- 今の大きさの記録は、[毎回読む文書と固定の文脈の大きさ](../07-記録/context-size.md)にある。

### 文書に内容を追加するときの基準

内容を追加するかは、次の 4 つで決める。

- 消しても読む人が誤らない内容は書かない。
- script が処理できること、script が失敗として示せることは、script を修正し、文書に書かない。
- 手順の 1 項目には、することと条件を書く。理由は、書かないと手順が飛ばされる、または誤って行われるおそれがあるときだけ書く。
- 作業で 1 回起きた問題は、script、エラーの文、文書のどこで防ぐかを先に決める。文書に書くことを前提にしない。

追加すると決めた内容の書き方は、[文書の書き方](writing.md)の「冗長さ」に従う。書き方の規則の文書（`backend-coding.md` など）では、規則と確認方法を[書き方の規則とレビュー](review.md)の「規則の書き方」に従って書く。

例：`docs/06-手順書/setup.md` の、設計書の画像を撮る項目。

- 修正前：設計書の画像（`docs/01-概要/img/`）は `pnpm capture:docs` で撮る。前提は同じ（スロット 0、全てのサーバー、local の seed）。続けて撮るときも DB を再作成する。商品の流れは、同じ品番で再度登録できないため。`pnpm capture:docs` の後に DB を再作成して撮るときは、撮る前に店舗画面のトップと商品一覧を開き、キャッシュを更新する。再作成の前の商品が、キャッシュから画面に表示されることがあるため。
- 修正後：設計書の画像（`docs/01-概要/img/`）は `pnpm capture:docs` で撮る。前提は上の手順 1、2 と同じ。続けて撮るときは DB を再作成し（品番が重複するため）、店舗画面のトップと商品一覧を開いてから撮る（古い商品がキャッシュから表示されるため）。

前提の列挙を手順への参照にし、独立した文だった理由を括弧の中の短い句にした。

## 文書の種類ごとの雛形

| 文書 | 構成 | 書くもの・書かないもの |
|------|------|------------------------|
| `AGENTS.md` | 最初に読むもの・skill・作業の進め方・モデルの区分・Git・環境の 6 つの節（各節の上限は表の下） | エージェントに固有の手順だけ（skill も同じ）。規則は docs/ を指す。全体で 8,000 バイト以下 |
| constitution | 大綱と文書の地図 | 各節は 1 文、要点（3 つまで）、「細則は〜」の案内だけ。表は文書の地図の 1 つだけ |
| 規則の文書 | 冒頭、規則の節、根拠の記録への参照 | 各節の書き方は[書き方の規則とレビュー](review.md)の「規則の書き方」 |
| 用語集 | 用語・識別子・意味の 3 列の表 | 意味は 1〜2 文 |
| 記録 | 冒頭・測り方・結果・判断の 4 つの節 | 測った結果と判断だけ。経緯は書かない |
| README | 概要、起動とテストの案内、進捗の案内 | 文書は constitution へ案内する |
| フォルダーの `README.md` | 文書と内容の表 | 文書の一覧だけ |

`AGENTS.md` の各節の長さの上限の目安は次のとおり。

- 最初に読むもの：6 項目。skill：3 行。環境：4 行。
- 作業の進め方：本書にだけある規則の箇条 10（小節の「完了の基準」「セッションの始めと終わり」を含む）。
- モデルの区分：表 2 つ（モデル、レビューのツール）と注 1 つ。Git：表 1 つと注 2 つ。
