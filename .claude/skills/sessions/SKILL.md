# セッションの運用

issue 担当のセッションと spec 担当のセッションの運用。役割の表は [エージェントの作業フロー](../../../docs/05-開発規則/subagents.md)の「役割と作業の流れ」、作業の形・profile・閾値・使用量を読む頻度は [作業の形と使用量](../../../docs/05-開発規則/resources.md)。ツールの名前は末尾の「ツールの補足」にだけ書く。

## issue 担当のセッション

- 役割：起票と、spec 担当のセッションの起動。資源の配分。危険度が低い変更のマージ。`develop` の CI の見届け。ステップの終わりの集計と振り返り。
- 起動：利用者が開く。1 つだけにする。
- issue の本文とコメントも、skill `docs` の「進め方」のとおり、日本語の要点からサブエージェントに書かせる。数行のコメントは自分で書いてよい。
- 起票とコメントの投稿の前に、本文を校閲役（skill `review` の手順 9。中国語で指示する環境で行う）に読ませる。同時に書いた複数の本文は、1 回にまとめて渡す。
- 待機：待機中は、通知を受けたときに処理を再開する。定期的な問い合わせはしない。

### 他のセッションの成果物に問題があるとき

1. 原因を結論づける前に、成果物を作ったセッションにメッセージで聞く。聞くことは、使った skill、書かせたサブエージェント、モデル、指示。そのセッションがアーカイブ済みなら、その記録を読む。
2. 聞いた結果で原因を分け、修正する場所を決める。

   | 原因 | 修正する場所 |
   |------|--------------|
   | 手順どおりに作ったのに問題があった | skill の中身か校閲役 |
   | 手順を参照しなかった、または従わなかった | 規則を参照する経路 |
   | 規則がない | 規則を加える |

3. 利用者への報告では、確認した事実と推測を分けて書く。

理由：原因を推測で決めると、修正する場所を誤り、同じ問題が再発するため。実際に、作ったセッションに確認せず、今の文書から原因を推測した例がある（issue #299 のコメント）。

### 待機と監視の token を抑える

1. CI を待つときは、バックグラウンドの実行（「ツールの補足」の名前）でまとめて待ち、短い間隔で読み直さない。
2. spec 担当のセッションへの返事は短くし、判断に必要な事実だけを書く。
3. ステップの区切りで文脈を圧縮するか、新しいセッションにする（利用者が行う）。
4. 汎用の区分で動かす（[エージェントの作業フロー](../../../docs/05-開発規則/subagents.md)の「任せる作業とモデル」）。
5. spec 担当のセッションの終わりを待つときは、ターンを使わない待ち方（終わったら知らせる指定）を使い、問い合わせを繰り返さない。

## 資源の配分

- 作業の形、profile、並行の数は、issue 担当のセッションが [作業の形と使用量](../../../docs/05-開発規則/resources.md)の「作業の形と profile の決め方」の表で決める。並行の数の上限は、マシンの環境の文書（`/.local/agent/environment.md`）の値。
- 利用者が特例の配分を指定したときは、[作業の形と使用量](../../../docs/05-開発規則/resources.md)の「作業の形と profile の決め方」に従う。
- 閾値で止めた spec 担当のセッションの再開は、issue 担当のセッションが、使用量が戻った後（戻る時刻の後に使用量を読んで）決め、メッセージで知らせる。単線の兼務のときは、兼ねるセッションが戻る時刻の後に自分で判断する。

## spec 担当のセッションの起動と実装の開始

起動のメッセージに、開始の条件を書く。形：

> 利用者が確認対象を承認し、5 時間の使用量が x% 未満、週が y% 未満なら、問い合わせずに始め、開始を知らせる。

- x と y は、issue 担当のセッションが資源の配分から決める。
- 起動のメッセージに、文書（spec・plan・tasks など）の本文を、skill `docs` の「進め方」のとおり、要点からサブエージェントに書かせる指示も入れる。
- 条件を満たさないとき、または渡されていないときは、spec 担当のセッションは issue 担当のセッションに問い合わせてターンを終える。待つ間は token を使わない。
- 返事がないときは、次に利用者か issue 担当のセッションから指示が来るまで始めない。
- 利用者が確認対象を承認したこと（通常の承認）は、開始の条件の材料である。条件を決めるのは issue 担当のセッション、条件を満たすかを判定して始めるのは spec 担当のセッション。
- 利用者が「今すぐ始めて」などと特例を明示したときは、開始の条件を飛ばし、配分は [作業の形と使用量](../../../docs/05-開発規則/resources.md)の「作業の形と profile の決め方」に従う。
- spec 担当のセッションが直接その特例を受けたときは、issue 担当のセッションに知らせ、返事を待たずに始める。
- 始めたら、[開発の進め方](../../../docs/05-開発規則/workflow.md)の「実装を始める前の照合」に進む。
- spec の最後のレビューの後は、pull request を draft で先に作ってから組み込みのコードレビューを行う。順と理由は [開発の進め方](../../../docs/05-開発規則/workflow.md)の「規模」。spec 担当のセッションは、push を段階の最後に行う（[開発の進め方](../../../docs/05-開発規則/workflow.md)の「push のタイミング」）。

## セッションの間のメッセージ

名前でなく、セッションの識別子で送る。名前は重なったり変わったりして、別のセッションに届くことがある。

## 遠隔操作

利用者が外にいてセッションを操作できないときに、遠隔操作を有効にする。待機中のセッションには、有効にする前に短いメッセージ（「何もせず、待機中と返して終わる」）を送り、次のターンを開始する状態にしてから有効にする。待機中のままでは有効にできない。

## 単線のときの兼務

単線のときは、1 つのセッションが issue 担当と spec 担当を兼ねる。理由：資源の調整がほぼ要らず、2 つのセッションが固定で持つ文脈と通知の token を省けるため。区分は spec 担当の区分（高性能）にする。兼ねるときも、起票と spec の作業の規則は変えない。

兼務のときは問い合わせる先がない。利用者が確認対象を承認したら、自分で使用量を読んで開始の条件を判定し、開始を追跡の issue に書く。

## マージの後

- `develop` の push の CI を、issue 担当のセッションがバックグラウンドの実行（「ツールの補足」の名前）で見届ける。失敗したら、他の pull request のマージを止めてすぐに起票し（[開発の進め方](../../../docs/05-開発規則/workflow.md)の「起票」の急ぐ作業）、直るまで次のマージをしない。
- `.claude/`（skill、サブエージェントの定義、設定）を変えた pull request をマージしたら、issue 担当のセッションが、メインのチェックアウトの `develop` を最新にする。理由：メインの作業ツリーで起動した `claude -p` は、メインの作業ツリーの skill と定義を読み、作業ツリーのものを読まないため。アプリのセッションは、作業ツリーで動くときも、メインの作業ツリーのものを読む（「ツールの補足」の「作業ツリーのセッションが読むもの」の表）。
- 後片付けで自分をアーカイブできないときは、許可した利用者の言葉を添えて、issue 担当のセッションに頼む（[開発の進め方](../../../docs/05-開発規則/workflow.md)の「マージの許可と後片付け」）。

## Dependabot の pull request のマージ

危険度の判定が「低」の pull request を、issue 担当のセッションがまとめてマージするときに使う。判定の読み方は [エージェントの作業フロー](../../../docs/05-開発規則/subagents.md)の「役割と作業の流れ」。

```bash
bash scripts/dev/merge-deps.sh 101 102   # 番号の pull request を順に処理する
```

- script は、最新でなければ更新し、CI が終わるのを待って、マージできる pull request ごとに `gh pr merge <番号> --merge --match-head-commit <SHA>` の 1 行を出力する。衝突、失敗、CI が終わらないときは、理由を出して終了コード 1 で止まる。
- 出力されたコマンドを、エージェントが 1 つずつ実行する。理由：hook は Bash のコマンドの文字列だけを読むので、script の中の `gh pr merge` は判定できないため。
- 1 つ目をマージした後に、2 つ目以降のコマンドが失敗したら（`develop` が進んで最新でなくなるため）、残りの番号で script をやり直す。

## ステップの終わり

詳細は [ステップとフェーズの終わり](rounds.md)。

1. 集計：`node .claude/skills/review/stats.cjs --round <ステップ> --profile <profile> <spec の番号...>`。profile ごとに、その profile で動いた spec だけを渡して実行する。1 つのステップに複数の profile があれば、実行を分ける（profile は spec の起動ごとに決まる。[作業の形と使用量](../../../docs/05-開発規則/resources.md)）。profile の再検討を利用者に提案する。
2. 効果の測定：整理の第 2 フェーズの最初のステップだけ（第 1 フェーズの測定は issue #265 で済んだ）。閾値・並行の上限・spec の最後のレビューの量を、整理の前の基準と同じ script と方法に、`stats.cjs` の集計を加えて測り直す。測る作業は、起票の案で作った issue で行う（[rounds.md](rounds.md)）。
3. 見逃しの一覧を読む：label「見逃し」の issue の本文の「関連」に、エージェントがマージしたと書いたものが 1 件でもあれば、利用者に提案する。提案は、危険度が高い経路の一覧と、危険度が低い変更のマージの条件の再検討である（見逃しの一覧の書き方は [エージェントの作業フロー](../../../docs/05-開発規則/subagents.md)の「モデルや設定を替えるとき」）。
4. 振り返り：skill `agent-retro` で行い、集計して整理の issue の案を利用者に示す。
5. 危険度が低い変更の推奨と起票の案：このステップでマージした危険度が低い変更の pull request から、本文の「推奨の指摘の扱い」と起票の案を集めて利用者に示す。利用者が承認したものだけを起票する。理由：危険度が低い変更は利用者が pull request を確認しないため（2026-10-28 利用者の決定）。

## フェーズの終わり

振り返りと、定期の全体のレビュー（提案だけ。材料と手順は [ステップとフェーズの終わり](rounds.md)）。

## ツールの補足

使うサービスに固有の名前と手順。今のサービスは Claude Code のデスクトップアプリ。サービスを替えるときは、この節だけを修正する。

- セッションへのメッセージ：`mcp__ccd_session_mgmt__send_message`（引数に識別子を渡す。一覧は `list_sessions`）。子のセッションへは `SendMessage` も使える。
- 遠隔操作：`mcp__ccd_session_mgmt__set_remote_control`。待機中のセッションで有効にすると「Remote Control requires an active session」で失敗する。先に短いメッセージを送ってから有効にする（6 つのセッションで成功を確認した、2026-10-27）。
- 親子のセッション：子のセッション（起動された側）のターンが終わると、親のセッション（起動した側）に通知が届く。
- 終わったら知らせる指定：バックグラウンドの実行（`run_in_background`）か、起動したセッションの終了の通知。通知でターンが再開する。
- 見逃しの一覧と CI：`gh issue list --label 見逃し`、`gh run list -b develop -L 1`。
- 使用量：`mcp__ccd_session_mgmt__get_usage`（5 時間と週の使用率、戻る時刻）。
- `claude -p` の起動：`claude -p --model <モデル> --permission-mode default --allowedTools "<許すツール>" "<指示>"`。`--permission-mode bypassPermissions` は auto mode の判定が拒否するので使わない。Write のツールは、`claude -p` を起動したディレクトリの `.claude/` の下（`settings.json`、`agents/`、`skills/`）に書けない（`--allowedTools Write` でも拒否される。2026-10-29）。動作の確認でファイルを置くときは、許可した Bash から script で置く。
- マージの許可の確認の画面：hook（`agent-guard`）が、利用者の許可が必要なマージで Claude Code の確認の画面を表示する（AGENTS.md の Git の表）。遠隔操作（Remote Control）では、確認の画面とアプリの「次の一歩」の表示欄が見えないことがある。許可を求めるときの伝え方は [開発の進め方](../../../docs/05-開発規則/workflow.md)の「マージの許可と後片付け」。

### 作業ツリーのセッションが読むもの

起動の形ごとに、設定・定義・skill を読む場所と、変更が反映される時点。作業ツリーとメインの作業ツリーに、出力が違う一時の設定・定義・skill を置いて実際に実行し、どちらを読んだかを確認した（Claude Code 2.1.309、2026-10-29、[spec 276](../../../docs/08-spec/archive/1to10/276-retro-rules/spec.md)の「作業の記録」）。アプリのセッションは、作業ツリーで動くときも、メインの作業ツリーの、commit していない変更を含む内容を読む。

| 起動の形 | `.claude/settings.json` | `.claude/settings.local.json` | `.claude/agents/` | `.claude/skills/` |
|----------|-------------------------|-------------------------------|-------------------|-------------------|
| アプリの作業ツリーのセッション | メインの作業ツリーのもの | メインの作業ツリーのもの。作業ツリーにあっても読まない。hook の変更は 10 秒ほどで反映される | メインの作業ツリーのもの。作業ツリーに足した定義は読まれない | メインの作業ツリーのもの。作業ツリーに足した skill は読まれない |
| アプリのメインの作業ツリーのセッション | メインの作業ツリーのもの | メインの作業ツリーのもの。hook の変更は 10 秒ほどで反映される | メインの作業ツリーのもの。足した定義は、10 秒後は読まれず、40 秒後には読まれた | メインの作業ツリーのもの。足した skill は 10 秒ほどで読まれる |
| 作業ツリーで起動した `claude -p` | 作業ツリーのもの。hook の変更は、動いているセッションにすぐ反映される | 作業ツリーのもの。メインの作業ツリーのものは、作業ツリーにないときも読まない。変更は、動いているセッションに反映されない | 作業ツリーのもの。起動の後に足した定義は、新しいセッションまで読まれない | 作業ツリーのもの。起動の後に足した skill は、数秒で読まれる（足した直後の最初の呼び出しは失敗しうる） |

メインの作業ツリーで起動した `claude -p` は、メインの作業ツリーの 4 つを読む。アプリのセッションの `settings.json` の hook の変更が反映される時点は、確認していない。手動の作業ツリーで作業するアプリのセッションも確認していないが、読む場所は起動したディレクトリで決まる（上の 3 行）ので、メインの作業ツリーのものを読むと見込む。

Claude Code の公式の文書は、設定のファイル（permissions と hooks）、定義、skill の変更が再起動なしで反映されると書いている（[settings](https://code.claude.com/docs/en/settings)、[sub-agents](https://code.claude.com/docs/en/sub-agents)、[skills](https://code.claude.com/docs/en/skills)。起動の時になかったフォルダーは監視しない）。アプリのセッションの定義・skill・`settings.local.json` の hook の実測は、文書と合う。`claude -p` の実測（`settings.local.json` と定義の変更が反映されない）は、文書と違う。原因は確認していない（1 回の実行が短いことなどの可能性）。

定義・skill・hook を変える spec は、マージの前に、変更を入れた作業ツリーで次を確認する。アプリの作業ツリーのセッションは、作業ツリーの変更を読まないので、確認に使えない。

1. その作業ツリーのディレクトリで `claude -p` を起動する（起動の形は、上の「`claude -p` の起動」）。`claude -p` はメインの作業ツリーの `settings.local.json` を読まないので、`settings.local.json` の hook は、作業ツリーの `.claude/settings.local.json` に置いて確認する。
2. 変更が読まれることを確認する（hook は出力か拒否、定義は Agent のツールが示す名前、skill は Skill のツールが示す名前）。
3. 読まれない起動の形があれば、spec に書き、マージの後の動きを利用者に伝える。
