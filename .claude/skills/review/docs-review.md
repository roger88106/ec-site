# plan・tasks の照合と文書のレビュー

[SKILL.md](SKILL.md) の手順 7 から読む。

## 手順

1. plan と tasks を照合する。plan と tasks を、それぞれ書き終えたときに行う。日本語だけのサブエージェント（汎用）に、下の「指示のひな形（plan・tasks の照合）」で照合させる。結果は、AC・DC、plan の節またはタスク、合否、説明の表で受け取る。抜けと食い違いは、確認の前に修正する。
   完了の条件：全ての AC・DC が表にある。
2. 文書をレビューする。日本語だけのサブエージェント（汎用）に、下の「指示のひな形（文書のレビュー）」で、不自然な言い回しと、差分で増えた行のうち不要な行を候補として挙げさせる。書き方の見本は [エージェントの作業フロー](../../../docs/05-開発規則/subagents.md)と [MVP-018 の plan](../../../docs/08-spec/archive/mvp/018-docs-and-tools/plan.md)。結果は、ファイル・行・今の書き方・修正案・理由の表で受け取り、spec 担当のセッションが採否を判定する。spec・plan・tasks を書き終えたときと、spec の最後に行う。変えた文書のレビューでは、差分をファイルに書き、ひな形に差分のファイルと spec のパスを書く。新しく書いた文書だけのときは、差分を「なし」とする。
   完了の条件：全ての候補の採否が決まっている。
3. 中国語で指示する環境では、校閲役の 2 つの役割に、変えた日本語を順に読ませる。検出役 `ja-proofreader`（[定義](../../agents/ja-proofreader.md)）を先に呼ぶ。次に確認役 `ja-proof-verifier`（[定義](../../agents/ja-proof-verifier.md)）に、検出役の結果の表のファイルと、校閲の対象を渡す。環境は、`git config --local --get ecsite.instructionLanguage` の値が `zh` かで決める（[中国語の混入を調べる](../zh-mixing/SKILL.md)の「環境の印」）。
   - 対象と時点：

     | 対象 | 時点 |
     |------|------|
     | 差分の追加行（文書、コードのコメント、テスト名） | 段階の最後と spec の最後のレビュー、pull request の前のレビュー |
     | 利用者の確認の前の全文 | 規模 M の spec、規模 L の spec・plan・tasks |
     | issue の本文とコメント | 起票と投稿の前（書くセッションの担当によらない） |
     | コミットメッセージ | 段階の最後の push と作業の最後の push の前。push 済みのものと、レビューの指摘を修正した commit のものは渡さない |

     issue の本文とコメントを同時に複数書いたときは、1 回にまとめて渡す。2 回目以降は、前回の校閲の commit からの差分だけを渡す。
   - リポジトリ全体で使う語を変える指摘は、その文書では修正せず、issue #294 に集める。
   - 渡すもの：検出役には、差分（`git diff` の出力、または対象のファイルと行の範囲）と対象のファイル名、結果の書き先だけ。確認役には、検出役の結果の表のファイルと、同じ校閲の対象、結果の書き先。会話の要約と中国語の文は、どちらにも渡さない。指示の文は日本語だけで書く。
   - モデル：呼び出しのときに区分を指定する（検出役は汎用、確認役は高性能）。定義にモデルがなく、指定しないと親のモデルを引き継ぐため。
   - 結果：校閲役が、書き先（[SKILL.md](SKILL.md) の手順 1 の置き場所の下）に表を書く。検出役の表の列はファイル・行・今の書き方・修正案・理由で、確認役はそれに判定と判定の理由の列を加える。
   - spec 担当のセッションが、確認役の判定が「挙げる」の候補だけを読んで採否を決め、結果を利用者に示す。差分の追加行のうち変えていない文の候補は、不採用にしてよい（1 語の修正で行全体が追加行になるため）。
   完了の条件：全ての指摘の採否が決まっている。
4. 校閲役や他のレビューが見つけ、利用者が確認した型を、機械の検査に加える。加えるのは、利用者が型として確認したものだけで、指摘の一件ごとではない。
   - 加える先は原因で決める。日本語の書き方の規則に反する型（使わないと決めた語、文体。由来が中国語でも、誰が書いても避けるべき語）は、層 1 の `scripts/ci/ja-text.json`。層 1 は、CI と commit の前の検査（`scripts/ci/ja-text.mjs`）が全ての環境で行う。中国語の混入（日本語では使わない字、中国語の用語、直訳）は、層 2 の `.claude/skills/zh-mixing/zh-mixing.json`。層 2 は、環境の印がある環境（中国語で指示する環境）だけで動き、CI には入れない（書き方は [中国語の混入を調べる](../zh-mixing/SKILL.md) の「一覧の直し方」）。同じ字・語を両方に置かない。
   - 複合動詞の崩れは、確定した語を `error` に加え、疑いを示す漢語を `style` の `compound` に加える。
   - 層 1 の項目の形は、`error` と `warning` が `{ "word", "use" }`（`error` は許容用語 `allow` も書ける）。部分の一致が誤検出になる語は、`word` の代わりに `pattern`（正規表現の文字列。`u` フラグで使う）で書け、`examples` の `hit`（当たる例）と `miss`（当たらない例）を 1 つ以上ずつ必ず書く（テストが全ての例を確認する）。文体の型は `style` の閾値と、`scripts/ci/ja-text.mjs` の `findStyleWarnings` で扱う。層 2 には warning がなく、見つかれば失敗にする。
   - error と warning の分け方：error にするのは、次のどちらかの型だけである。リポジトリの全体（アーカイブした spec を除く）に当てて誤検出が 0 の型。全ての誤検出を許容用語（層 1 は `allow`、層 2 は `allow` の `{ "word", "file", "reason" }`）で除ける型。
     それ以外は、文脈で正しいかが決まる型なので、層 1 の warning にする。層 2 には warning がないため、それ以外の型は層 2 に加えない。
   - 当てて数える：層 1 は、先に `warning` に加え、`node scripts/ci/ja-text.mjs --warning` で一覧にして誤検出を数える。error にするときは `error` に移し、`node scripts/ci/ja-text.mjs` の失敗が 0 になるまで、見つかった行を修正するか許容用語を追加する。層 2 は、加えてから `node .claude/skills/zh-mixing/zh-mixing.cjs --force tracked` で全体に当てる。環境の印がなくても `--force` で調べられる。
   - 加えたら、それぞれの script のテスト（`node --test scripts/ci/ja-text.test.mjs`、`node --test .claude/skills/zh-mixing/zh-mixing.test.cjs`）と `bash scripts/ci/check-all.sh` が通ることを確認する。
   完了の条件：加えた型ごとに、error か warning かの理由と、全体に当てた誤検出の数が説明できる。

## 指示のひな形（plan・tasks の照合）

手順 1 で使う。日本語だけで書く。tasks の照合では、＜tasks のとき＞の行を加える。

```
あなたは、spec と plan（＜tasks のとき＞と tasks）を照合する担当です。実装の過程は知らされていません。

## 対象
- spec：<パス>
- plan：<パス>
- ＜tasks のとき＞tasks：<パス>

## 観点
spec の各 AC・DC と、plan の決定を 1 件ずつ照合する。
＜tasks のとき＞spec の各 AC・DC・DN と plan の決定が、どのタスクで行われるかを照合する。各段階の完了の条件と各タスクの条件が、spec より厳しくないか・緩くないかを見る。前のタスクが後のタスクで作るものを使っていないかを見る。共有する部品（検査の script の共通の関数、生成するファイル、共通の設定、AC 一覧などの共有の文書）を変えるタスクと、それを使う・前提にするタスクの間に、依存に書いていない順序の制約がないかを見る（特に `[P]` のタスクの間）。
＜tasks のとき＞並行する spec と変えるファイルが重なることと、実装の順序が、plan（規模 M は spec の tasks）に書いてあるかも見る。
spec の「背景と目的」の環境の前提（Claude Code や OS の動き）が、文書の記述によるものか、実際に実行して確認したものかを書き分けているかも見る。

## 結果
<結果の書き先> に、次の表で書く。AC・DC を全て載せる。
| AC・DC | plan の節（＜tasks のとき＞タスク） | 判定（合っている・抜けている・食い違う） | 説明 |

- 判定の根拠は、spec と plan の本文に置き、出典（ファイル:行）を書く。出典のない理由は書かない。
- 他のファイルは変更しない。返すのは件数（合っている、抜けている、食い違う）だけ。
```

## 指示のひな形（文書のレビュー）

手順 2 で使う。日本語だけで書く。

```
あなたは、日本語の技術文書のレビュー担当です。実装の過程は知らされていません。

## 対象
<新しく書いた、または変えた文書のパス>
差分のファイル：<差分を保存したファイルのパス。なければ「なし」>
spec：<対象の spec のパス。なければ「なし」>

## 見本
目指す書き方の見本：<見本のパス>
書き方の規則：docs/05-開発規則/writing.md（表を 1 行ずつ当てはめる）
追加する内容の基準：docs/05-開発規則/doc-structure.md の「文書に内容を追加するときの基準」
`ja-text.mjs --warning` が出力した warning の文：<`node scripts/ci/ja-text.mjs --warning` の出力のうち、対象の文書の行。なければ「なし」>

## 観点
技術文書として不自然な言い回しと、差分で増えた行のうち不要な行を、候補として挙げる。見本の書き方に近づける。次の 5 つを見る。
- 和語の言い換え：技術文書で一般的な語に替える（規則の「用語」の表）。
- 論理、読む人の負担、中身のない言い回し、翻訳調の比喩と擬人化、冗長さ（規則のその他の表）。
- `ja-text.mjs --warning` が出力した warning の文：「の」の連なり、長い文、読点の多い文、否定が続く文、複合動詞の崩れの疑いなど。文脈を読んで、修正すべきものだけを候補にする（「少し修正する」のような正しい日本語は候補にしない）。
- 件数と列挙の照合：本文に書いた件数（「14 語」「次の 3 つ」など）と、列挙した項目の数が合うかを数える。合わないものは候補にする。
- 増えた行：差分で増えた行ごとに、消しても手順や判断が成り立つかを見る。成り立つ行は、削る案を修正案に書く。spec が決めた範囲（行数を含む）と合っているかを照合する。差分が「なし」のときはこの観点を見ない。spec が「なし」のときは範囲を照合しない。

## 守ること
- 意味、番号、節の番号、表の構成を変えない。ただし、増えた行の観点で削る案を挙げるときは除く。
- 識別子、文書の題名、節の名前を変えない。
- プロジェクトの用語集の語を一般の語に替えない。
- 理由には出典（規則または spec のファイル:行）を書く。出典のない理由は書かない。

## 結果
<結果の書き先> に、次の表で書く。
| ファイル | 行 | 今の書き方 | 修正案 | 理由 |

- 対象のファイルは変更しない。返すのは候補の件数だけ。
```
