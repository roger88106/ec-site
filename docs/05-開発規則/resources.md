# 作業の形と使用量

issue 担当のセッションが配分を決めるときと、spec 担当のセッションが使用量を読むときに読む。規則の本文は、使う AI のサービスに依らない言葉で書く。

## 1. 作業の形と profile の決め方

issue 担当のセッションが、セッションの始めと各 spec の起動のときに、プランと使用量を読んで決め、spec 担当のセッションに渡す。spec 担当のセッションが自分で選ぶのではない。

| 条件 | 作業の形 | 実装の並行の数の上限 | profile |
|------|----------|----------------------|---------|
| 最上位を使えないプラン | 単線 | 1 | 標準 |
| 使えるプラン、週の使用量 60% 未満 | 並行 | マシンの上限 | 厚め |
| 同、週 60〜80% | 並行 | マシンの上限から 1 を引いた数。最小は 1 | 標準 |
| 同、週 80% 以上 | 単線 | 1 | 節約 |

- マシンの上限は、マシンごとの環境の文書（`/.local/agent/environment.md`）に書く。書いていないときは、安全側の 1 とする。理由：同時に動かせる実装の数は機械の性能（CPU、メモリ、テストを同時に実行できるか）で決まり、性能が分からないまま 2 以上にすると、テストが失敗するおそれがあるため。
- spec の文書の段階（spec・plan・tasks を書く）のセッションは、並行の数に数えない。理由：文書の作業の使用量は、5 時間の使用量の数 % と小さいため。
- 利用者が特例の profile や配分を指定したときは、利用者の決定が最終である。issue 担当のセッションは、そのための配分（他の spec を区切りで止めるなど）を決めて実行し、利用者に報告する。
- 表の値は、整理の第 1 フェーズの測定（issue #265、2026-10-29）では変えない。理由：新しい規則で全ての段階を通った spec が 2 つ（246、247）だけで、判断する数が足りないため。整理の第 2 フェーズの最初のステップでもう一度測る。

## 2. 止める閾値

- 5 時間の使用量が、並行では 90%、単線では 97% を超えそうなら、spec 担当のセッションは新しいタスクに入らず、commit できる区切りで止まる。issue 担当のセッションに、使用率と戻る時刻を報告する。
- 報告を受けた issue 担当のセッションは、待つか、他の spec を止めるかを決める。
- 週の使用量が 95% を超えたら、全ての spec 担当のセッションを区切りで止める。
- 段階の途中で止めてセッションを替えるときは、利用者に `handoff` の実行を求める。
- 閾値で止めた spec 担当のセッションの再開は、issue 担当のセッションが、使用量が戻った後（戻る時刻の後に使用量を読んで）決め、spec 担当のセッションにメッセージで知らせる。単線の兼務のときは、兼ねるセッションが戻る時刻の後に自分で再開を判断する。
- 値は、整理の第 1 フェーズの測定（issue #265、2026-10-29）では変えない。理由：新しい規則で全ての段階を通った spec が 2 つ（246、247）だけで、判断する数が足りないため。整理の第 2 フェーズの最初のステップでもう一度測る。

## 3. 使用量を読む頻度

読むのにも token を使うので、読みすぎない。読む手段は、マシンの環境の文書にある。

- セッションの始めに 1 回読む。
- 文書の作業（spec・plan・tasks）は、前に読んだ値が 90% 未満なら、区切りごとに読まなくてよい。
- コードの作業は、前に読んだ値が 70% 未満なら、数タスクごとに読めばよい。70% 以上なら、タスクの前に毎回読む。
- 大きいタスク（多くのファイルにまたがる、テストの全体を何度も実行する）の前は、値によらず読む。
- 目安は暫定で、タスクごとの使用率の増え方の記録で再検討する。
