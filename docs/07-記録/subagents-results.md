# エージェントの作業フローの調べた仕組みと実績

[エージェントの作業フロー](../05-開発規則/subagents.md) の根拠を置く。本書の節は、次の内容である。取り入れる仕組みの根拠にした調べた仕組み。サブエージェントに任せた作業の実績（[エージェントの作業フロー](../05-開発規則/subagents.md)の「任せる作業とモデル」の根拠）。運用の規則と並行の判断の理由。取り入れる判断の理由（決定記録に移した）。モデルの区分の出典と軽量の読める量。見逃しの一覧の種類（pull request の前のレビュー役を加える理由）。値を今は変えない理由（作業の形の表、閾値、spec の最後のレビューの量）。校閲の評価の結果（校閲役を 2 つの役割に分けた採点の記録）。仕組みやモデル、範囲を再検討するときに読む。

## 1. 調べた仕組み（2026-10-20 時点）

| 仕組み | バージョン | サブエージェントの使い方 |
|--------|------------|--------------------------|
| cc-sdd | v3 | `kiro-impl` が 1 タスクごとに新しい実装役を立て、TDD（レッド → グリーン）で実装させる。実装役にはタスクの要点だけを渡す。別の独立したレビュー役が、差分、TODO の残り、テストの全体、タスクの境界を確認する。実装役が止まったとき、またはレビューで 2 回差し戻されたときは、調査役が原因と修正方法を返す（最大 2 回）。タスクをまたぐ気づきは tasks の「Implementation Notes」に書き、後のタスクの実装役に渡す。実装は 1 つずつ順に行い、書き手を並行して動かすときは別の作業ツリーを使う。モデルの選び方の記述はない |
| superpowers（subagent-driven-development の skill） | main（2026-10） | 1 タスクごとに新しい実装役を立てる。実装役に渡すのは、タスクの全文、プロジェクトの 1 行の説明、前のタスクで決まったインターフェース、曖昧な点の決定、報告のファイルのパスだけ。計画の全体や会話の履歴は渡さない。実装役は詳しい報告をファイルに書き、状態・commit・テストの 1 行の要約・懸念だけを返す。1 人のレビュー役が、仕様との一致とコードの品質の 2 つの判定を出す。重大な指摘は修正させ、軽い指摘は記録だけにする。修正が 5 回で収まらなければ、制御役（メインのセッション）が裁定する。進み具合は台帳のファイルに書く ※1。実装役を並行して動かさない。モデルは常に明示し、機械的な作業は安価なモデル、複数ファイルの統合は標準、設計と最後のレビューは最も高性能なモデル、レビュー役は中位以上にする |
| Spec Kit | 最新（main） | `/speckit.implement` はサブエージェントを使わない。tasks を段階（Setup、Tests、Core、Integration、Polish）の順に実行し、段階ごとに確認する。`[P]` の付いたタスクは並列で実行できる（同じファイルを触るものは順に）。テストのタスクを実装より先に行う。独立したレビューの段階はない ※2 |
| OpenSpec | 最新（main） | `/opsx:apply` が tasks を順に実行し、`/opsx:verify`（任意）が実装と仕様の一致を確認する。サブエージェント、独立したレビュー、モデルの選び方の記述はない ※2 |

※1：会話の記憶は、文脈の圧縮で失われるため。

※2：フレームワークを導入しない理由。段階ごとの tasks、前提と完了条件、テストのレッド、文書が先、レビュー、AC とテスト名の検査のどれもが、フレームワークにはない。OpenSpec は要件に英語の SHALL・MUST を求め、日本語の文書と合わない。

- 使うツールのサブエージェントは新しい文脈で始まり、親から渡るのは指示の文字列だけ（公式の文書）。必要なファイルのパス、決定、差分は、指示に明示して渡す。

## 2. 実績
[エージェントの作業フロー](../05-開発規則/subagents.md)の「任せる作業とモデル」の、サブエージェントに任せた作業の実績。モデルや範囲を再検討するときに読む。

| 作業 | 条件 | 結果 |
|------|------|------|
| spec 010 の後の全体レビュー | 汎用、読むだけ | 6 つのサブエージェントで、合計約 162 万 token、ツールの呼び出し約 390 回。1 つあたり 6〜11 分 |
| plan 018 の本文 | 汎用、日本語の要点から書く | 約 13.5 万 token、ツール 14 回、約 2 分 |
| tasks 018 の本文 | 汎用、日本語の要点から書く | 約 12 万 token、ツール 12 回、約 1 分 20 秒 |
| 言い回しのレビューの安定度（spec 018 の段階 5） | 3 つの範囲（規範 658 行、手順 376 行、spec 002 の 540 行）を、同じ指示で 汎用 2 回と高性能 1 回、独立に実行 | 3 回とも挙がった候補は 15〜30%、1 回だけの候補は 50〜69%。和語の言い換えなど語の単位の問題は、毎回どのモデルでも確信度「高」で挙がった。高性能は汎用より 1〜4 割多く挙げたが、汎用との重なりの割合は高くなかった。1 回あたり 9〜15 万 token、1.5〜4 分。並行した 7 つの判定のうち 1 つが、同じ名前の一時ファイルの上書きを報告した |

測定に使ったモデルは 2026-10 時点のもの（実際のモデルと区分の対応は [AGENTS.md](../../AGENTS.md)）。

- 1 つのサブエージェントで全体を見るより、範囲を分けたほうが安い。理由：文脈が長いほど 1 回の呼び出しが高くなるため。

## 3. 運用の規則と並行の判断の理由

- spec 181 と 186 を分けたとき、範囲だけで重ならないと判断したが、草案で重なるファイルが 5 つ見つかった（2026-10-24）。これが、並行の可否を関わる全ての spec の変えるファイルの照合で決める理由。
- 語ごとの規則を語ごとに 1 回決めるのは、語の単位の問題が、どの回でも、どのモデルでも同じく挙がるため。
- 文脈で判断する候補を 2 回実行して和集合を取るのは、1 回で挙がるのが 3 回の和集合の 42〜78% で、回ごとに変わるため。
- 並行して動かすサブエージェントの一時ファイルに範囲の名前を付けるのは、同じ作業ツリーのスクラッチパッドを共有し、同じ名前のファイルを上書きするため。

## 6. 見逃しの一覧の種類（2026-10-29）

[エージェントの作業フロー](../05-開発規則/subagents.md)の「役割と作業の流れ」の、pull request の前に高性能のレビュー役を加える規則の理由。対象は、hook・CI の検査の script・認証・支払・権限の経路を変える spec で、レビュー役は文脈を持たない。見逃しの一覧は GitHub の issue の label「見逃し」（[エージェントの作業フロー](../05-開発規則/subagents.md)の「見逃しの一覧」）で、各件が段階のレビューで見つかる種類かを分けた。

| issue | 見逃したもの | 見つかった時点 | 段階のレビューで見つかる種類か |
|-------|--------------|----------------|--------------------------------|
| #256 | ルートの script のグロブが CI（Linux）だけで展開された（spec 192） | pull request の前の高性能のレビュー役 | はい。差分を読めば分かる。CI の失敗でも止まる |
| #257 | 外した export を並行の spec が使っていた（spec 192） | `develop` の取り込みの後の検査 | いいえ。相手の spec は差分にない |
| #258 | mock の 2 回の読み取りの間の競合で null が入る（spec 192） | pull request の前の組み込みのコードレビュー | はい。差分の中のコード |
| #259 | 新しい作業ツリーで API の型が未生成（spec 104） | 段階 4 の手動の起動 | いいえ。実際に実行して分かる環境の問題 |
| #260 | ログインより先に ID の形を確認していた（spec 135 より前） | 後の spec のレビュー | はい。規則（店舗画面の構成の「ログイン画面へ移す」）との照合で分かる |
| #270 | hook が拒否するはずの操作を別の書き方で通した（spec 246） | pull request の後の文脈を持たない高性能のレビュー役（5 回で重要度「高」10 件） | はい。ただし回避の書き方を網羅して探す観点が要り、段階・spec の最後・組み込みのコードレビューでは見つからなかった |
| #238 | `ManagementPortTest` がときどき失敗する（spec 223） | テストの全体の実行 | いいえ。不安定なテストで、レビューの対象でない。本文は見逃しの一覧の形でない |

- 段階のレビューで見つかる種類は 4 件（#256、#258、#260、#270）で、そのうち段階のレビューで見つかったものはない。見つけたのは、後の時点の、観点を絞った別のレビュー役。
- hook・CI の検査の script のように回避の書き方を探す必要があるものには、pull request の前の文脈を持たない高性能のレビュー役を加える（issue #265 の T265-02）。
- spec の最後のレビューの量は、判断する数が足りないので変えない（同 T265-01）。

## 7. 値を今は変えない理由

整理の第 1 フェーズの測定（issue #265、2026-10-29）で、次の 3 つを変えなかった。

- 作業の形の表（[作業の形と使用量](../05-開発規則/resources.md)）
- 閾値（同じ文書）
- spec の最後のレビューの量（[エージェントの作業フロー](../05-開発規則/subagents.md)の「レビューの時点と profile」）

- 理由：新しい規則で全ての段階を通った spec が 2 つ（246、247）だけで、判断する数が足りないため。
- 再検討の時期：整理の第 2 フェーズの最初のステップで、もう一度測る。

## 8. 校閲の評価の結果（2026-11-01）

1 つの校閲役が見つけて判定する形から、検出役と確認役の 2 つの役割に分けた。そのときの、評価の一覧での採点の記録である。手順は[校閲役の評価の一覧](../../.claude/skills/review/evals/ja-proofread.md)の「校閲役を替えるときの手順」にある。

| 日 | 評価の一覧の commit | 設定 | 結果 |
|----|---------------------|------|------|
| 2026-11-01 | 1970c437 | 変える前の校閲役（`ja-proofreader` の変更前の定義、汎用、1 つの校閲役が見つけて判定する） | 見つけた数 24/28、誤検出 0、token 39910、時間 0m50s（2 回の合計） |
| 2026-11-01 | 1970c437 | 検出役（汎用）と確認役（高性能） | 見つけた数 28/28、誤検出 3、token 319046、時間 3m34s（2 回の合計。検出役と確認役の合計）※3 |

※3：2 つの役割の採点は、定義の本文を指示に入れた標準のサブエージェントで行った（アプリのセッションは、メインの作業ツリーの定義を読むため）。標準のサブエージェントは指示の文書を読み込むので、定義（`omitClaudeMd: true`）で動かすときより token が多い。定義で動かしたときの token は未確認で、`develop` に入れた後に測る。

- 変える前の校閲役は、2 回とも `台帳`（M-05）と `段`（M-07）を見逃した。
- 2 つの役割の誤検出は、F-04（進み具合）が 2 回、F-01（日付をまたぐ境界）が 1 回。
- 扱い：採用の基準の「一方が良く、他方が悪い」に当たり、利用者が採用を決めた（2026-11-01）。理由は、見逃しは利用者が読む文書に残るが、誤検出は spec 担当のセッションが採否を決めるときに除外できるため。
- 採点に使わなかった実行：誤検出の例を替える前の評価の一覧（bab4fc43、b017a222）で行った変える前の校閲役の実行は、commit が違うので比べない。
