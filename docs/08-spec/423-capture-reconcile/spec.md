# Spec 423：売上確定の応答が届かなかった支払を、決済サービスと照合する

種類：機能　規模：M　ステータス：確定

## 背景と目的

出荷の登録で決済サービスが売上を確定した後、応答が届かないか、反映の前にインスタンスが止まると、支払は与信済みのまま残る。運営者が出荷の登録もキャンセルもしないと、DB の支払は与信済み、決済サービスの支払は確定済みのまま食い違い、それを見つける処理がない。目的は、売上確定の結果が分からない支払を決済サービスの状態と照合し、DB の支払の状態を決済サービスに合わせること。

追跡の issue は #423。関わる文書は、[決済モジュール](../../03-機能仕様/payment.md)と[決済の設計](../../02-設計/payment.md)。出荷の登録を再実行したとき（確定済みとして反映される）と、キャンセルしたとき（#407 の修正で返金に進む）は、今のコードで扱える。

含めないものの理由は Non-goals に書く。

決定：

1. 規模は M にする（issue 担当のセッションが承認した）。判定の表では DB の構造を変えるので L になるが、plan が必要ないので特例の M にする（[開発の進め方](../../05-開発規則/workflow.md)の「規模」）。理由：決済モジュールの中で閉じ、モジュールをまたぐ決定も API の変更もないため。
2. 照合の対象は、売上確定を求めた時刻の記録で見つける（案 A）。比べた案は次の表。

   | 案 | 内容 | 採る理由・採らない理由 |
   |----|------|------------------------|
   | A（採る） | 売上確定を求める前に時刻を記録し、記録があって与信済みのままの支払だけを照合する | 対象が、結果の分からない支払だけに絞られる。応答が届かない場合と、反映の前にインスタンスが止まった場合の両方を見つけられる |
   | B | 決済サービスの売上確定の通知を受ける | 通知の種類を増やすと、Stripe の通知の登録も変わる。mock は通知を送らないので、ローカルと E2E で確認できない |
   | C | 記録を持たず、与信済みの全ての支払を定期的に照合する | 出荷を待つ全ての注文で、ジョブの回ごとに決済サービスへの問い合わせが増える |

3. 時刻の記録は、決済サービスを呼ぶ前に、別のトランザクションでコミットする。理由：決済サービスでの確定の後にインスタンスが止まっても、記録が残るため。結果を反映したとき（売上確定済み、与信期限切れ）は、状態が与信済みでなくなるので、照合の対象から外れる。接続できないときと予期しないエラーのときは、記録を残す。
4. 照合は、既存の期限切れのジョブの処理に加える。新しいジョブは作らない。順は、期限切れ、与信の取得、照合、長く待つ支払の警告。理由：同じ「決済サービスとの照合」の処理で、ジョブの間隔の設定とロックを増やさないため。
5. 照合の対象は、記録があり、状態が与信済みで、記録から照合を始めるまでの時間（設定。既定は 10 分）が過ぎた支払。理由：売上確定の最中、つまり決済サービスの応答を待つ間の支払を照合しないため。決済サービスの 1 回の呼び出しは、再試行を含めて最大約 75 秒かかる（期限切れのジョブのコメントにある値）。
6. 照合の結果で、次の表のとおり支払を変える。決済サービスの状態は、port の新しい操作（売上確定の状態の取得）で読む。照合では売上確定を求めない。理由：売上確定は出荷の登録でだけ行う。照合で確定すると、出荷しない注文の売上まで確定するため。

   | 決済サービスの状態 | 識別子 | 支払 |
   |--------------------|--------|------|
   | 売上確定済み | `succeeded` | 売上確定済みにし、warn のログに支払 ID を出力する |
   | 与信が切れた | `canceled` | 与信期限切れにする |
   | 売上を確定していない | `requires_capture` | 記録を削除し、与信済みのまま残す。出荷の登録で再実行できる |
   | それ以外 | | 支払を変えず、warn のログに支払 ID を出力する。次のジョブの実行で再試行する |

7. 記録を削除するのは、行ロックの後の記録が、照合で読んだときと同じ時刻のときだけ。理由：照合が決済サービスを読む間に運営者が売上確定を再実行すると、記録が新しい時刻になり、その再実行の結果はまだ分からないため。期限切れの処理も、読んだときの支払画面と行ロックの後の支払画面を比べて、同じように判定する。
8. 照合の失敗の扱いは、与信の取得と同じにする。1 件で例外が起きたときは、warn のログに支払 ID を出力し、次の支払へ進む。接続の失敗が続いたら、その回の照合を打ち切る。1 回の件数の上限も、与信の取得と同じ値にする。
9. 照合で売上確定済みにしても、注文は受付のまま残す。運営者が出荷を登録すると、出荷の登録は決済サービスを呼ばずに成功する。注文をキャンセルすると、返金に進む。どちらも既存の動きである。
10. 照合で売上確定済みにした注文を、管理画面で目立たせる表示は加えない（利用者が承認した）。理由：受付の注文は出荷の対象として一覧に出て、支払の状態の列に売上確定済みと表示され、運営者はそこから出荷を登録するため。与信済みのまま残った受付の注文に出ていた「期限が近い」の表示は、照合で売上確定済みにすると出なくなる。表示の対象が、与信済みと与信期限切れだけのためである。

## User stories

| US | 誰が | 何をできる | なぜ |
|----|------|------------|------|
| US-423-1 | 運営者 | 売上確定の応答が届かなかった支払の状態を、決済サービスと同じ状態で見られる | 消費者に請求済みの注文を、与信済みと誤って扱わないため。例：出荷しないまま放置する、与信の取消を試みる |

## 受け入れ条件

### US-423-1 売上確定の応答が届かなかった支払の照合（B / P1）

- **AC-423-1** 売上確定の応答が届かなかった支払は、照合を始めるまでの時間が過ぎた後、期限切れのジョブで売上確定済みになる。
- **AC-423-2** 売上確定の後、反映の前にインスタンスが止まった支払も、AC-423-1 と同じく売上確定済みになる。
- **AC-423-3** AC-423-1 で売上確定済みにしたときは、その支払 ID を warn のログに出力する。
- **AC-423-4** 照合を始めるまでの時間の前は、その支払を照合しない。
- **AC-423-5** 決済サービスで売上を確定していなかった支払は、与信済みのまま残り、以降のジョブの実行では照合しない。その注文の出荷を登録すると、売上を確定できる。
- **AC-423-6** 決済サービスで与信が切れていた支払は、与信期限切れになる。
- **AC-423-7** 照合が決済サービスを読んでいる間に運営者が売上確定を再実行し、その応答も届かなかった支払は、次のジョブの実行でも照合の対象になる。
- **AC-423-8** 決済サービスから状態を取得できないときは、その支払 ID を warn のログに出力し、支払を変えずに残りの支払を処理する。次のジョブの実行で再試行する。接続の失敗が続いたときの打ち切りは、与信の取得（AC-409-10）と同じ。
- **AC-423-9** AC-423-1 で売上確定済みにした注文は、出荷を登録できる。
- **AC-423-10** AC-423-1 で売上確定済みにした注文をキャンセルすると、総額が返金される。

## 業務ルール

- **BR-423-1** 売上確定の結果が分からない支払だけを、決済サービスと照合する。対象は、売上確定を求めた記録があり、与信済みのままで、照合を始めるまでの時間が過ぎた支払。理由：与信済みの全ての支払を照合すると、出荷を待つ注文の数だけ決済サービスへの問い合わせが増えるため。

## 非機能要件

- **NFR-423-1** API の契約を変えない。
- **NFR-423-2** 管理画面と店舗画面の表示を変えない。支払の状態の表示は、既存の「売上確定済み」「与信期限切れ」を使う。
- **NFR-423-3** 照合は冪等にする。同じ支払を重ねて照合しても、状態は 1 回だけ変わる。
