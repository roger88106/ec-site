# 文書の観点

文書、設計書、skill・agent の定義を書く・変えたときに、結果を返す前の自己確認とレビューの両方で読む。規則の文は、表の「規則の正本」で読む。

| 観点 | 級 | 見る問い | 過去の見落としの例 | 規則の正本 |
|------|------|------|------|------|
| 同じ事実の古い記述 | 重要 | 変えた事実を書いた他の所を、全文検索で全て直したか。設計書の語が、クラスの名前の形と合うか。 | 手順書に古い記述が残った。テストの先頭のコメントが古いままだった。設計書がハンドラーを「リスナー」と書いていた | [文書の構成](../../../../docs/05-開発規則/doc-structure.md)の「参照」 |
| 正本は 1 か所 | 重要 | 同じ規則を複数の文書に書いていないか。正本の一覧を一部だけ写して、抜けを作っていないか。 | 検査の取捨の基準を 3 か所に同じ内容で書いた。テストの観点の一覧を一部だけ写し、いくつかが抜けた | [文書の構成](../../../../docs/05-開発規則/doc-structure.md)の「文書の長さの基準」、[文書の書き方](../../../../docs/05-開発規則/writing.md)の「冗長さ」 |
| 文書の中の食い違いと条件のあいまいさ | 重要 | 同じ箇条や同じ文書の中で、2 つの条件のどちらに従うか決まらない所がないか。規則の範囲が、同じ文書の他の記述と矛盾しないか。 | サブエージェントに index を変えさせない規則が、commit を任せる記述と矛盾した。マージの条件が同じ文書の 2 か所で違った | [文書の書き方](../../../../docs/05-開発規則/writing.md)の「論理」 |
| 例が規則に従うか | 重要 | 文書の例が、同じ文書の規則（同じ差分で加えた規則を含む）に従うか。例が規則の全ての形を示すか。 | 定数の値を書かないと決めた同じ差分で、例の説明に定数の値を書いた。例の Javadoc に `@throws` がなかった | [書き方の規則とレビュー](../../../../docs/05-開発規則/review.md)の「規則の書き方」 |
| 決定との一致 | 重要 | 変えた文書の内容が、利用者の決定と一致するか。決定にない規則を足したり、決定と違う置き場所に書いたりしていないか。 | 確認が必要な項目の後半を、決定を待たずに規則に書いた。振り返りの注意を、決定と違う文書に置いた | [AGENTS.md](../../../../AGENTS.md)の「作業の進め方」 |
| 規則と確認方法 | 重要 | 新しい規則と変えた規則に、確認方法があるか。確認方法が今の規則と script の実際の動きに合うか。 | 規則を変えたのに確認方法の行が古い規則のままだった。文書に「80 字まで」と書いたが、検査は 80 字ちょうどで警告した | [書き方の規則とレビュー](../../../../docs/05-開発規則/review.md)の「規則の書き方」 |
| 指示の実行手順と、skill 間の一致 | 重要 | 指示どおりに実行できるか（コマンド、引数、渡すもの）。同じ手順を、複数の skill で違う形にしていないか。 | 指示の文を検査に通すと書いたが、通し方（引数）がなかった。重い検査の順の決め方が、2 つの skill で違った | skill `writing-for-agents` |
| 理由の書き方 | 次要 | 理由は 1 文で、どの規則の理由か分かる位置にあるか。理由が事実（今の運用）と合うか。 | 理由が 3 文で、本文の箇条の理由を繰り返していた。理由が、毎回再作成する今の運用と合わなかった | [文書の構成](../../../../docs/05-開発規則/doc-structure.md)の「文書の長さの基準」、[書き方の規則とレビュー](../../../../docs/05-開発規則/review.md)の「規則の書き方」 |
| 主語と参照の先 | 次要 | 主語が分かるか。参照した節に、その規則が実際にあるか。 | 「public にしない」の主語がなかった。参照した節に、その規則がなかった | [文書の書き方](../../../../docs/05-開発規則/writing.md)の「読む人の負担」、[文書の構成](../../../../docs/05-開発規則/doc-structure.md)の「参照」 |
| 設計書の型（パッケージの構成） | 次要 | パッケージの構成にクラスの名前や細部を書かず、各行の役割を雛形の長さで書いているか。同じ種類の設計書の習慣に合わせたか。 | パッケージの構成に record などの細部を書いて長くした。1 つの設計書だけ、他の設計書と違う書き方にした | [モジュールの設計の雛形](../../../../docs/02-設計/template.md)の「この雛形の使い方」「パッケージの構成」 |
| 実装の細部とコードの参照 | 次要 | 規則の文書の本文に、実装の細部や、コードが変わると直す必要がある具体的なクラスの参照を書いていないか。 | 共通の規則の文書に、特定の Repository を例に挙げた。多くの所に record などの実装の細部を書いた | [書き方の規則とレビュー](../../../../docs/05-開発規則/review.md)の「規則の書き方」、[文書の書き方](../../../../docs/05-開発規則/writing.md)の「論理名と物理名」 |
| 長さと分け方 | 次要 | 加えた箇条に、複数の条件と理由を詰めていないか。消しても誤らない行がないか。表のセルの字数が基準に収まるか。 | 加えた規則の多くが、1 つの箇条に条件・例外・理由を詰めて長くなった | [文書の構成](../../../../docs/05-開発規則/doc-structure.md)の「文書の長さの基準」「文書に内容を追加するときの基準」、[文書の書き方](../../../../docs/05-開発規則/writing.md)の「読む人の負担」 |
| 日本語の自然さ | 次要 | 語感、列挙のつなぎ方、略語、中国語の直訳調になっていないか。 | 見出しの語感が不自然で、差分の全体に中国語の直訳調があった。「など」の後に列挙を続けた | [文書の書き方](../../../../docs/05-開発規則/writing.md)の「用語の選び方」「言い回しと論理」、skill `zh-mixing` |
| Markdown の表示 | 次要 | 段落・箇条・表・コードブロック・見出しの前後に空行があり、描画で崩れないか。 | 箇条の直後に空行なしで段落を続け、段落が箇条の続きとして描画された | [文書の書き方](../../../../docs/05-開発規則/writing.md)の「表と注」 |

## 重要の行の例

形で示すと分かりやすい行だけ、悪い例と良い例を書く。名前は一般の形。

### 正本は 1 か所

悪い例：正本の一覧を、別の文書に一部だけ写す。
```markdown
観点は、金額、権限、時刻の 3 つ。
```
良い例：正本を指す。
```markdown
観点は、[テストの書き方](test-writing.md)の「テストの観点」。
```

### 規則と確認方法

悪い例：規則を変えても、確認方法が古い。
```markdown
| 表のセルは 60 字まで | 確認方法：自動（80 字） |
```
良い例：確認方法が今の規則と script の動きに合う。
```markdown
| 表のセルは 60 字まで | 確認方法：自動（60 字） |
```
