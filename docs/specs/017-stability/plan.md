## 1. 片付け（US-61、NFR-24）

### 1.1 ジョブの置き場所と設定

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 置き場所 | データを持つモジュールごとに 1 つのジョブを、application 層に置く（支払の期限切れのジョブと同じ形）。イベントの片付けは `config` に置く（イベントの再発行のジョブと同じ所） | ArchUnit（今の層の検査）、レビューで読む |
| 分散ロック | 各ジョブに ShedLock の名前を付ける（AC-287）。名前は `<データ>-cleanup` | 統合テスト（ロックの記録） |
| 設定 | ジョブごとに保存期間と間隔を持つ（AC-285）。間隔の既定は 1 時間 | 単体テスト（既定値） |
| ログ | 削除した件数を info で出力する。0 件なら debug（AC-288） | 単体テスト |

| データ | モジュール | 設定の接頭辞 | 保存期間の既定 | ロックの名前 |
|--------|------------|--------------|----------------|--------------|
| 処理の済んだイベント | `config` | `ecsite.scheduling.event-cleanup` | 7d | `event-cleanup` |
| 引当 | inventory | `ecsite.inventory.cleanup` | 1d | `stock-reservation-cleanup` |
| 注文手続き | order | `ecsite.order.cleanup` | 1d | `checkout-cleanup` |
| カート | cart | `ecsite.cart.cleanup` | 0d | `cart-cleanup` |

```yaml
# 設定の形（例：引当）。環境変数 ECSITE_INVENTORY_CLEANUP_RETENTION などで上書きする
ecsite:
  inventory:
    cleanup:
      interval: 1h
      retention: 1d
```

### 1.2 削除方法

| データ | 削除する条件 | 1 回に削除する件数 | 確認方法 |
|--------|----------|----------------|----------|
| 処理の済んだイベント | 処理を終えた時刻が、今から保存期間より前 ※1 | 上限なし ※2 | 統合テスト |
| 引当 | 期限が、今から保存期間より前 | 1000 件ずつ、残りがなくなるまで繰り返す。1 回ごとに別のトランザクション | 統合テスト |
| 注文手続き | 期限が、今から保存期間より前。注文になったものも削除する（AC-286）※3 | 同上 | 統合テスト |
| カート | 最後の変更から、カートの期限（30 日）と保存期間を加えた時間がたった。品目は外部キーのカスケードで削除される | 同上 | 統合テスト |

- 引当・注文手続き・カートは、1 文の削除で、条件に合う行を件数の上限まで選んで削除する（選ぶのと削除するのを同じ文にし、条件の判定と削除の間に変わった行を削除しない）。
- 期限で探すので、引当の期限、注文手続きの期限、カートの最後の変更の時刻に索引を追加する（モジュールごとのマイグレーション）。

※1：Spring Modulith の「処理の済んだイベントを、処理を終えた時刻で削除する」操作（`CompletedEventPublications#deletePublicationsOlderThan`）を使う。処理を終えた時刻に索引がある。

※2：処理の済んだイベントは、他の操作が読み書きしないので、1 文で削除しても他の操作の行ロックを止めない（NFR-24）。

※3：注文は注文手続き ID を一意に持つ（同じ注文手続きから 2 回注文しない）が、注文手続きを削除しても注文の表示と操作は注文手続きを読まない。期限から 1 日たった注文手続きは、注文を作る操作でも期限切れで拒まれるので、削除して 404 になっても結果は変わらない。

### 1.3 削除した後の操作（AC-289）

| 操作 | 今（期限切れ） | 削除した後 | 確認方法 |
|------|----------------|----------|----------|
| カートを読む・変える・注文手続きを始める | 空のカートとして扱う | 404。店舗画面は、カートが見つからないとき新しいカートを作る（今の振る舞い） | 統合テスト、今の店舗画面の結合テスト |
| 会員のカート（`/me/cart`） | 空のカート | 会員のカートがなければ作る（今の振る舞い） | 統合テスト |
| 注文手続きを読む・注文する | 期限切れのエラー | 404 | 統合テスト |
| 注文を読む・操作する | 変わらない | 変わらない | 統合テスト |

- カートの変更と片付けが同時に起きたときは、カートの保存が 0 行を更新する。その結果（今の版の不一致の扱いで 409 か、404 か）と、予期しないエラー（500）にならないことを、段階 1 のテストで確認する。500 になるなら、止めて報告する。

## 2. 止めたイベント（US-62）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 再発行の条件 | 今の再発行のジョブを、Spring Modulith の再発行の選択肢（`ResubmissionOptions`）で呼び、再発行の回数（イベントの記録の `completion_attempts`）が上限より少ないものだけを再発行する（AC-290）。失敗の種類では分けない ※4 | 統合テスト |
| 上限 | `ecsite.scheduling.event-resubmission.max-attempts`。既定 60（発行の 5 分後から 1 分ごとで、約 1 時間） | 単体テスト（既定値） |
| 止めた印 | 再発行の回数が上限で、最後の再発行が失敗した（状態が `FAILED`、処理を終えていない）イベントの再発行の回数を 1 つ増やし、上限を超えた値にする。この更新で印を付けたイベントだけをログに出力する（1 つのイベントで 1 回だけ）※5 | 統合テスト |
| ログ | error で、イベントの種類、イベント ID、リスナーの ID、再発行の回数を出力する。イベントの中身（`serialized_event`）は出力しない（AC-291） | 単体テスト（ログの項目） |
| メトリクス | 未完了のイベントの件数（`ecsite.events.incomplete`）と、止めたイベントの件数（`ecsite.events.stopped`）を、運用ポートのメトリクスで公開する（AC-292）。再発行のジョブが毎回再集計して値を更新する（メトリクスの収集のたびに DB を読まない） | 統合テスト（メトリクスの値） |
| 片付け | 止めたイベントは処理を終えていないので、処理の済んだイベントの片付けで消えない（AC-293） | 統合テスト |
| 置き場所 | 印を付ける更新と件数の読み取りは、`config` に置く（イベントの記録は `common` スキーマで、モジュールのものでない） | レビューで読む |

※4：失敗の種類（外部サービスの一時的な故障か、データの誤りか）で分ける方法もあるが、Spring Modulith はイベントの記録に例外を残さないので、分けるにはリスナーごとに例外を分類して別に記録する必要がある。今のリスナーは、繰り返しても結果が変わらない失敗（Stripe の「すでに返金済み」など）をすでに正常終了として扱っているので、残る失敗は一時的な故障か、コードの誤りである。コードの誤りを上限まで再発行しても、ログが増えるだけで害はない。

※5：Spring Modulith のイベントの記録のテーブルに、直接書く。新しいテーブルを追加せずに、1 文の更新で「止めたばかりのイベント」だけを取り出せるため（2026-10-20 利用者）。Spring Modulith を上げるときは、再発行の回数と状態の意味が変わっていないかを確認する（イベントの記録のマイグレーションの注記に追加する）。

## 3. 外部サービスのエラー（US-63、BR-39）

### 3.1 分類

| 外部サービス | 外部サービスのエラー（502）にするもの | 入力の誤り（400）にするもの | 予期しないエラー（500）のまま |
|--------------|---------------------------------------|-----------------------------|-------------------------------|
| 決済（Stripe） | 接続できない・時間内に応答がない（`ApiConnectionException`）、Stripe の側の故障（`ApiException`）、回数の制限（`RateLimitException`） | — | 認証・権限・リクエストの誤り（設定かコードの誤り） |
| 画像の変換（imgproxy） | 接続できない・時間内に応答がない、502・503・504（imgproxy の前段のプロキシか、imgproxy が止まっている）※6a | imgproxy が返した 4xx と 500（ファイルを読めない。AC-297）※6a | URL の署名の失敗 |
| ファイル保存（S3） | 接続できない・時間内に応答がない（`SdkClientException`）、5xx の `S3Exception` | — | 5xx でない `S3Exception`（権限・バケットがないなど。404 は今どおり「受付がない」） |

※6a：実装の時に変えた（2026-10-20 利用者）。初めは「4xx は 400、5xx は 502」としたが、imgproxy は壊れたファイルに 500（Internal error）を返すので、壊れたファイルが「しばらくしてからやり直す」になる。imgproxy が応答したら（4xx と 500）ファイルの問題とし、imgproxy に届かない・応答しない（接続、タイムアウト、502・503・504）ときだけ外部サービスのエラーにする。imgproxy の中の故障（受付のバケットを読めないなど）も 500 なので、その時は「ファイルを確認する」のメッセージになるが、許容する（応答はログに残す）。

### 3.2 エラーコード

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 決済 | 今の `PAYMENT_GATEWAY_UNAVAILABLE` を使う。支払画面を作る・閉じる、返金、取消でも、第 3.1 節の分類で投げる（今は売上確定だけ）| 単体テスト（Stripe の実装） |
| 画像 | `IMAGE_SERVICE_UNAVAILABLE`（種類は外部サービスのエラー）を追加する。画像の変換とファイル保存で共に使う ※6 | 単体テスト |
| 投げる所 | infrastructure の実装が分類し、外部サービスのエラーの種類のエラーコードで `SystemException` を投げる。今の共通の例外ハンドラーが 502 にし、warn のログを出力する | 統合テスト |
| 決済の port の契約 | 「売上確定を除き、応答しなければ `SystemException`」の注記を、「接続できなければ外部サービスのエラー」に書き換える。売上確定の結果の `UNREACHABLE` は今のまま | レビューで読む |
| 画像の変換のタイムアウト | 今の「時間内に応答がない → `IMAGE_CONVERSION_FAILED`（400）」を、外部サービスのエラー（502）に変える（AC-296） | 単体テスト |

※6：利用者には、変換と保存のどちらが止まったかは関係がなく、どちらも再試行すればよいため（2026-10-20 利用者：サービスごとにエラーコードを分ける）。

### 3.3 契約と画面

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| OpenAPI | 外部サービスを呼ぶ操作に、502（`BadGateway`）とエラーコードを追加する：店舗の支払画面を開く、管理の画像の登録（AC-300。受付はファイル保存のサービスを呼ばないので書かない）。`store.yaml` に `BadGateway` の応答を追加する | 契約のテスト（今のエラーコードの検査） |
| 契約と実装の食い違い | 店舗の支払画面を開く操作は、`PAYMENT_GATEWAY_UNAVAILABLE` を契約に持つのに、今は投げない。本 spec で投げるようにして合わせる | 統合テスト |
| メッセージ | 外部サービスのエラーのメッセージは「〜に接続できない。しばらくしてからやり直す」の形にし、どのサービスかを示す | 単体テスト（メッセージの検査） |
| 画面 | 店舗画面・管理画面は、今どおりエラーの応答のメッセージを表示する（AC-299）。新しい分岐は作らない | 結合テスト（店舗：支払画面を開く、管理：画像の登録で 502 のメッセージが表示される） |
| API の規約 | 第 3 節の 502 の行を、外部サービスのエラーの定義（第 3.1 節の分類）を指すように修正する。OpenAPI の外のエンドポイント（決済・物流の通知、mock の画面）の表を追加する（AC-300） | レビューで読む |

## 4. タイムアウト（US-64）

| 呼び出し | 決定 | 既定 | 設定 | 確認方法 |
|----------|------|------|------|----------|
| バックエンド → Stripe | Stripe の client に接続と応答のタイムアウトを設定する。今の自動の再試行（2 回）は残す ※7 | 接続 5 秒、応答 20 秒 | `ecsite.payment.stripe.connect-timeout`、`read-timeout` | 単体テスト（設定を client に渡す） |
| バックエンド → S3 | S3 の client に、1 回の試行と呼び出しの全体のタイムアウトを設定する | 試行 10 秒、全体 30 秒 | `ecsite.media.storage.attempt-timeout`、`call-timeout` | 単体テスト、統合テスト（応答しない S3 で 502） |
| バックエンド → imgproxy | 今のタイムアウト（接続 5 秒、応答 30 秒）のまま | — | 今の設定 | 今のテスト |
| 店舗画面 → バックエンド | API の client の fetch に、タイムアウトの `AbortSignal` を付ける | 30 秒 ※8 | `STORE_API_TIMEOUT_SECONDS` | 単体テスト |
| 店舗画面 → IdP（token の更新） | token の更新の fetch に、タイムアウトの `AbortSignal` を付ける | 10 秒 | `AUTH_KEYCLOAK_TIMEOUT_SECONDS` | 単体テスト |
| 店舗画面 → IdP（ログインの Auth.js） | Auth.js の provider の fetch を差し替える仕組み（`customFetch`）で、同じタイムアウトを付ける ※9 | 10 秒 | 同上 | 単体テスト |

- タイムアウトしたら、バックエンドは第 3 節の外部サービスのエラー（502）、店舗画面は今の「接続できない」の扱いにする（AC-303）。
- 店舗画面の設定は、今の任意の設定と同じく 1 か所で読む（[フロントの書き方](../../rules/frontend-coding.md) 第 8.1 節）。

※7：支払画面を開く操作は、利用者のリクエストの中で決済サービスを呼ぶので、Stripe の SDK の既定（応答 80 秒）だと、再試行を含めて数分待たせうる。20 秒は、Stripe の通常の応答（数秒）に十分な余裕を持たせた値。

※8：バックエンドで最も長く待つ呼び出し（支払画面を開く）より短いと、バックエンドが成功しても画面は失敗を表示する。支払画面は開いたものを使い回すので、再試行すれば同じ画面に移れる（[order.md](../../design/modules/order.md) の支払画面）。

※9：Auth.js の `customFetch` が、使う版（next-auth 5 の beta）で provider に適用されることを、段階 5 の最初に確認する。適用されなければ止めて報告する。

## 5. トランザクションの外での外部の呼び出し（US-65、BR-40）

### 5.1 画像の確定

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| メディアの API | 今の「確定」を 3 つに分ける：①用意（受付のファイルを確認し、変換し、配信のバケットに置く。トランザクションの外）、②登録（アセットを記録する。呼んだ側のトランザクションの中）、③破棄（①で置いたファイルを削除する。失敗は warn のログに保存先のキーを出力し、呼び出し元に例外を伝えない） | 単体テスト、統合テスト |
| 商品の画像の追加 | 商品の読み取りと枚数の確認（読み取り専用）→ ①（トランザクションの外）→ 商品への追加と②を 1 つのトランザクションで行う。トランザクションが失敗したら③を呼び、元の失敗を再スローする（AC-304、305） | 統合テスト（商品の版の不一致で、配信のファイルが残らない） |
| 層の置き方 | トランザクションの外の流れを持つ service と、保存の service を分ける（[バックエンドの書き方](../../rules/backend-coding.md) 第 1.1 節の「外部の呼び出しの前の読み取り」と同じ形。支払画面の service と同じ） | ArchUnit、レビューで読む |
| 用意と登録の間の停止 | ①の後、②の前にプロセスが停止すると、配信のファイルが残る。許容する（spec の Non-goals：登録のないファイルを探して削除することはしない） | — |

### 5.2 他のモジュール（AC-306）

| 呼び出し | 今 | 決定 | 確認方法 |
|----------|----|------|----------|
| 支払画面を開く、売上確定、支払の期限切れ | トランザクションの外 | 変えない | 今のテスト |
| 返金・与信の取消（決済のイベントのリスナー） | リスナーのトランザクション（Spring Modulith の既定の `REQUIRES_NEW`）の中で、決済サービスを呼ぶ | リスナーをトランザクションなし（`propagation = NOT_SUPPORTED`）にし、読み取りと更新は、今の参照・更新の service のトランザクションで行う | 統合テスト（今のテストが通る、トランザクションの外で呼ぶ） |
| 出荷のメール（通知のリスナー） | リスナーのトランザクションの中で、送信の記録とメールの送信 | 変えない ※10 | — |
| 配信のファイルを削除する（メディアのリスナー） | リスナーのトランザクションの中で、ファイル保存を呼ぶ（DB は使わない）※11 | リスナーをトランザクションなしにする | 統合テスト（トランザクションの外で呼ぶ） |
| 追跡の開始（配送のリスナー） | リスナーのトランザクションの中で、物流サービスを呼ぶ（DB は使わない。今は mock だけ）※11 | リスナーをトランザクションなしにする | 統合テスト（トランザクションの外で呼ぶ） |

※10：送信の記録（重複を除く挿入）と送信を同じトランザクションにし、送信に失敗したら記録も取り消して、再発行で再送するため。トランザクションの外で送ると、送った後に記録が失敗したとき二重に送る。SMTP には今の上限（10 秒）があり、リスナーは利用者のリクエストと別のスレッドで動くので、DB の接続を持つ時間は限られる。設計書（notification.md）にこの理由を書く。

※11：実装の時に修正した（T017-04-07、2026-10-20 利用者）。Spring Modulith のリスナーは既定で新しいトランザクション（`REQUIRES_NEW`）を始め、DB を使わなくても接続を持つ。初めの plan は、メディアのリスナーをトランザクションなしと誤って書き、配送のリスナーを挙げていなかった。

## 6. 店舗画面のログ（US-66）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| サーバーアクションの失敗 | 例外を結果にする共通の関数で、Next.js の画面の移動・not found を通した後、`log.error` に例外の名前とメッセージを出力してから、今の「接続できない」を返す（AC-307） | 単体テスト |
| 5xx の応答 | API の client（公開用と会員用）の応答の middleware で、5xx なら `log.warn` に状態コード、エラーコード、メソッド、パスを出力する（AC-308）。本文は再度読めるよう複製して読む | 単体テスト |
| 出力しないもの | token、Cookie、リクエストの本文、クエリ（メールアドレスなどを含みうる）。パスは API の定義のパス（`/orders/{orderId}` の形）で出力する（AC-309） | 単体テスト |
| トレース ID | 今のログの関数がリクエストのトレース ID を付ける。変えない | 今のテスト |

## 7. 支払の期限切れのジョブ（US-67）

| 決定 | 内容 | 確認方法 |
|------|------|----------|
| 例外 | 1 件の処理で `RuntimeException` を捕捉し、warn のログに支払 ID を出力して次へ進む（AC-310） | 単体テスト |
| 通知を待つ支払 | 決済サービスで支払済み（画面を閉じられない）と分かった支払に、その時刻（`awaiting_authorization_since`）を記録する。期限切れの支払の検索は、この時刻のあるものを除く（AC-311） | 統合テスト（通知を待つ支払が 100 件を超えても、新しい期限切れの支払を処理する） |
| 与信の通知が届いたとき | 今どおり与信を記録する。待つ時刻は残る（記録として害がない） | 今のテスト |
| 長く待つ支払 | ジョブの最後に、待つ時刻から決めた時間を過ぎ、まだ未払いの支払を数え、1 件以上なら warn のログに件数を出力する（AC-312）。毎回出力する（人が扱うまで知らせ続ける） | 単体テスト |
| 設定 | `ecsite.payment.awaiting-authorization-warning`。既定 1 時間 | 単体テスト（既定値） |
| データ | 支払に待つ時刻の列を追加するマイグレーション。domain の支払に、待つ状態にする操作を追加する（状態は未払いのまま） | 単体テスト（domain） |

## 12. テスト

| 対象 | 単体 | 統合 | E2E |
|------|------|------|-----|
| 片付け（US-61） | 設定の既定値、ログ | データごとに保存期間の前後で消える・残る、注文になった注文手続きを削除しても注文が読める、件数の上限ごとに分けて削除する、ロック（AC-284〜288） | 今の E2E が通る |
| 削除した後の操作（AC-289） | | カート・注文手続きが 404、会員のカートが再作成される、変更と片付けが重なったとき 500 にならない | |
| 止めたイベント（US-62） | ログの項目に中身がない | 上限まで再発行して止まる、止めたときだけログが 1 回、メトリクスの値、片付けで消えない（AC-290〜293） | |
| 外部サービスのエラー（US-63） | Stripe・imgproxy・S3 の分類、メッセージ | 支払画面を開く・画像の登録で 502 と応答の形、画像を読めないとき 400（AC-294〜298） | |
| 画面（AC-299） | | 店舗・管理の結合テストで 502 のメッセージが表示される | |
| タイムアウト（US-64） | 設定が client に渡る、店舗画面の fetch にタイムアウトが付く | 応答しない S3 で 502（AC-301〜303） | |
| トランザクションの外（US-65） | | 画像の変換の間にトランザクションがない、商品の保存が失敗したら配信のファイルが消える、返金・取消のリスナーがトランザクションの外で呼ぶ（AC-304〜306） | 今の画像の E2E が通る |
| 店舗画面のログ（US-66） | サーバーアクションの失敗、5xx の warn、秘密情報を出力しない（AC-307〜309） | | |
