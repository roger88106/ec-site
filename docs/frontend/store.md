# 店舗画面（`frontend/store`）の構成

C 側（消費者）の画面。Next.js（App Router）で、店舗 API（`store.yaml`）をサーバーコンポーネントとサーバーアクションから呼ぶ。
管理画面（[admin.md](admin.md)）と同じく、置き場所と作り方の決まりを本書にまとめる。新しい画面は、第 8 節の手順どおりに作る。

- 技術の採用：[constitution](../constitution.md) 第 2 節
- 画面の一覧と spec ごとの決定：各 spec の plan（例：[plan 001](../specs/001-catalog-and-inventory/plan.md) 第 3 節）

## 1. 技術

| 用途 | 採用 | 補足 |
|------|------|------|
| フレームワーク | Next.js（App Router） | 画面はサーバーコンポーネントで作り、操作のある部分だけクライアントコンポーネントにする |
| API の型 | openapi-typescript | `store.yaml` から生成する。生成物はコミットしない（constitution 9） |
| API の呼び出し | openapi-fetch | 取得はサーバーコンポーネント、変更はサーバーアクションから呼ぶ。ブラウザから API は呼ばない |
| キャッシュ | Next.js の fetch のキャッシュ | API の結果は最大 60 秒（NFR-1）。会員の token を付けて呼ぶ API はキャッシュしない（第 4.3 節） |
| ログイン | Auth.js（`next-auth` v5）の Keycloak の provider | セッションは暗号化した Cookie（JWT 方式）。token はサーバーだけで扱う（第 9 節、plan 003 第 1、4 節） |
| UI | shadcn/ui、Tailwind CSS、lucide-react | 管理画面と同じ |
| lint・整形 | Biome | 管理画面と同じ設定 |
| テスト | Vitest | 画面に依存しない関数と表示の部品（constitution 12） |

## 2. ディレクトリ

```
frontend/store/src/
├── auth/             # ログイン（index：Auth.js の設定とセッション、config：環境変数、refresh：token の更新、logout：IdP のログアウトの URL）。第 9 節
├── instrumentation.ts # 起動のときに、本番で必須の環境変数を確かめる
├── proxy.ts          # 要求ごとにセッションを確かめ、token の期限が近ければ更新して Cookie に書く。いまの画面のパスを知らせる
├── app/              # ルート（page.tsx、layout.tsx、not-found.tsx）。データの取得と部品の組み立てだけを書く
│   ├── api/auth/     # Auth.js の口（IdP からの戻り先など）
│   └── login/        # ログイン・会員登録の画面（IdP）へ移る口（route.ts）
├── actions/          # サーバーアクション（'use server'）。API の変更系を呼ぶ。資源ごとに 1 ファイル（cart、checkout、order、auth）
├── api/
│   ├── generated/    # store.yaml から生成（コミットしない）
│   ├── client.ts     # openapi-fetch のクライアント。公開の口と会員の口（サーバー専用）
│   ├── cartCookie.ts # カート ID の Cookie と、カートを移した結果の知らせの Cookie の読み書き（サーバー専用）
│   ├── cart.ts       # 使うカートを選ぶ（第 4.2 節。サーバー専用）
│   └── types.ts      # 画面から使うスキーマの型の別名
├── components/
│   ├── ui/           # shadcn/ui が生成する部品。手で直さない
│   └── *.tsx         # 機能をまたいで使う部品（価格、ページング、ヘッダーなど）
├── lib/              # 画面に依存しない関数。単体テストを横に置く
└── features/
    └── <機能>/       # catalog（商品とカテゴリ）、cart（カート）、checkout（注文手続き）、order（注文）
        ├── components/   # その機能の中だけで使う部品
        └── *.ts          # その機能の中だけで使う関数・型
```

- ルート（`app/`）は Next.js の決まりで置き場所が決まるので、画面の部品は `features/` に置き、`page.tsx` は薄く保つ。
- 機能どうしは import しない。2 つ以上の機能で使うものは `components/` か `lib/` に置く。
- クライアントコンポーネント（`'use client'`）は、操作のある部品（バリアントの選択、絞り込みの入力、フォームなど）だけにする。API はそこから呼ばず、`actions/` のサーバーアクションを呼ぶ。
- サーバーアクションは複数の機能から呼ぶ（商品の詳細の「カートに入れる」とカートの画面など）ので、`features/` ではなく `actions/` に置く。

## 3. 画面の URL

URL は Next.js の型付きの URL（`typedRoutes`）で、画面の置き場所と照らして確かめる（[フロントの書き方](../style/frontend.md) 第 6 節）。クエリを付ける URL は機能の `*Query.ts` の関数で作る。

| URL | 画面 |
|-----|------|
| `/` | トップ（カテゴリの一覧と新着の商品） |
| `/products` | 商品一覧（クエリ：`categoryId`、`minPrice`、`maxPrice`、`sort`、`page`） |
| `/search` | 検索結果（クエリ：`q`、`page`） |
| `/products/[productId]` | 商品の詳細（カートに入れる） |
| `/cart` | カート。カート ID は Cookie に持つので URL に入れない |
| `/checkout/[checkoutId]` | 注文手続き（内容の確認と、お届け先の入力。メールアドレスは会員のものを示すだけ。AC-127）。注文が成立済みなら注文の画面へ移る。ログインを求める |
| `/orders` | 注文の一覧（新しい順、クエリ：`page`。AC-129）。ログインを求める |
| `/orders/[orderId]` | 注文（注文の直後の表示、後からの照会、キャンセルの申請）。ログインを求め、注文した会員だけが見られる（AC-131） |
| `/login` | 画面ではなく、IdP のログインの画面へ移る口（クエリ：`returnTo` ログインの後に戻る画面、`register` 会員登録の画面にする）。第 9 節 |

- URL は商品 ID で作り、品番は使わない（AC-66）。
- 絞り込み・並び順・ページは URL のクエリに持つ。入力の送信は、フォームの GET（URL の書き換え）で行う。
- 表示されない商品・存在しない商品は、どちらも「見つかりません」の画面（404）にする（AC-65）。商品 ID の形が違う URL も同じにする。注文手続き・注文も、存在しない ID・形の違う ID・他人のものは「見つかりません」にする（AC-126、131）。
  - Next.js 16 では、リクエストのたびに作る画面で 404 にすると、サーバーは状態 404 と枠だけを返し、「見つかりません」の中身はブラウザの JavaScript が出す。

## 4. API の呼び出し

- サーバーコンポーネントで `const api = await getApi()` としてから、`api.GET('<パス>', ...)` で呼ぶ。クライアントは `server-only` にし、ブラウザのバンドルに入れない。
- `getApi` は画面をリクエストのたびに作るようにする（ビルドのときに API を呼ばない）。API の結果のキャッシュはこれとは別に効く。
- 接続先は環境変数 `STORE_API_BASE_URL`（既定 `http://localhost:8080/api/store`。既定は開発のモードとテストだけ。第 9 節）。
- 結果のキャッシュは最大 60 秒（NFR-1）。在庫や価格の変更は、1 分以内に表示に反映される。秒数は環境変数 `STORE_API_REVALIDATE_SECONDS` で変えられる（E2E で短くするため。本番相当の環境では設定しない）。
- ただし、1 件を取る API（商品の詳細）はキャッシュを使わない（`UNCACHED`）。Next.js のキャッシュは、取得し直した応答が 404 だと古い 200 を置き換えないため、キャッシュすると、非公開・販売終了にした商品の詳細がいつまでも表示されてしまう。一覧・検索・カテゴリは常に 200 を返すので、キャッシュしてよい。
- カート・注文手続き・注文の取得もキャッシュを使わない（`UNCACHED`）。数量・引当・状態が操作のたびに変わるため（plan 002 第 6 節）。
- 404 は Next.js の `notFound()` にする。401 はログインの画面へ移す（第 9 節）。それ以外のエラーは、エラーの画面（`error.tsx`）に出す。ただしカートの取得の 404（Cookie のカートがもうない）は、空のカートとして表示する。

### 4.1 サーバーアクション

- 変更（カートに入れる、数量の変更・削除、注文手続きに進む、注文、キャンセルの申請）は、`actions/` のサーバーアクションから API を呼ぶ。API の接続先とクライアントは取得と同じもの（`client.ts`）を使う。
- サーバーアクションは、成功したら表示し直す画面を `revalidatePath` で知らせるか、次の画面へ `redirect` する。失敗は例外にせず、結果（第 6 節の `ActionResult`）として返す。ただし 401 は、ログインの画面へ移す（第 9 節）。
- フォームは `useActionState` で結果を受け取る。送信中はボタンを押せなくする（二重押しの防止。API の側も、注文は同じ注文手続きの再送に作成済みの注文を返す。AC-91）。

### 4.2 カート ID の Cookie

- カート ID は、Cookie `cart_id` に持つ（plan 002 第 3 節）。`HttpOnly`、`SameSite=Lax`、`Path=/`、本番では `Secure`。有効期限は 30 日で、カートを変更するたびに延ばす（カートの有効期限 AC-81 と合わせる）。
- 読み書きは `api/cartCookie.ts` だけで行う。読むのはサーバーコンポーネントとサーバーアクション、書くのはサーバーアクションだけ（Next.js では、サーバーコンポーネントから Cookie を書けない）。
- Cookie がない、または形の違う値なら、カートがないものとする。カートの画面は空のカートを出し、「カートに入れる」のときにカートを作って Cookie に書く（AC-73）。
- カートを変更する API が 404（Cookie のカートがもうない）を返したら、カートを作り直して 1 回だけやり直す。作り直したカートでも 404 なら、エラーにする。
- **使うカートの選び方**（plan 003 第 6 節、AC-120、121、124）：ログインしていなければ Cookie のカート ID を使う。ログインしていれば `GET /me/cart` の ID を使い、Cookie のカート ID は使わない（会員のカートは会員の token を付けて操作する）。選ぶ処理は `api/cart.ts` だけに置き、何を使うかの判定は `lib/` の関数にして単体テストを書く。
- **ログインの直後にカートを移す**（AC-122、123）：IdP から戻ったとき（Auth.js の `signIn` のイベント）に、Cookie にカート ID があれば、そのカートの内容を取ってから `POST /me/cart/merge` を呼び、Cookie のカート ID を消す。移せなかったときも、Cookie は消す（ログインしている間は使わないので、残すと、ログアウトの後に古いカートが見えてしまう。AC-124）。
  - 切り詰めた品目と移せなかった品目があれば、その商品名・バリアント・数量（移す前に取ったカートの内容から引く）を、知らせの Cookie（`cart_merge_notice`、`HttpOnly`、有効期限なし）に書く。カートの画面はそれを読んで知らせ、表示したら消す（一度だけ。サーバーコンポーネントは Cookie を消せないので、知らせの部品から消すためのサーバーアクションを呼ぶ）。Cookie の大きさを抑えるため、知らせる品目はそれぞれ 10 品目までにし、残りは数だけ示す。
- ログアウトでは、Cookie のカート ID も消す（AC-124）。

### 4.3 会員の token を付けて呼ぶ

- 会員の操作（`/me/**`、会員のカート、注文手続き、注文）は、`getMemberApi()` の口から呼ぶ。この口は、セッションの access token を `Authorization` ヘッダーに付け（openapi-fetch の middleware）、キャッシュを使わない（`cache: 'no-store'`）。会員ごとに違う結果を、共有のキャッシュに載せないため（plan 003 第 4 節）。
- 公開の情報（商品・カテゴリ・店舗の情報）は、ログインしていても今までどおり `getApi()` の口から token なしで呼び、キャッシュを使う。
- ログインしていなくても使える操作（Cookie のカートの操作）は、今までどおり `getApi()` の口で呼ぶ。カートの取得には `UNCACHED` を付ける（変更の POST・PUT・DELETE は、もともとキャッシュされない）。

## 5. 表示の決まり

表示の文言は文言のファイルに置き、ロケールは 1 か所から取る（[フロントの書き方](../style/frontend.md) 第 7 節）。文言のキーや型の項目のコメントの書き方は [コメントの書き方](../style/comments.md) 第 6 節。

| 対象 | 決まり |
|------|--------|
| 価格 | 「1,980 円（税抜 1,800 円）」（BR-4）。C 側の商品は必ず税込価格を持つ |
| 在庫 | 「在庫あり」「在庫なし」だけ。数量は出さない（AC-64）。一覧では在庫のない商品に「在庫なし」を示す（AC-56） |
| 画像 | API が返した URL をそのまま使う（縮小・形式の変換は配信の側。plan 001 第 7.4 節）。一覧は代表画像、詳細は大きな画像と小さな画像の並び。バリアントを選ぶと、その画像（指定がなければ代表画像。AC-38）に替える。画像がなければ代わりの図を出す |
| 金額の内訳 | 商品の合計、送料、総額、税率ごとの消費税額（「10% 対象 11,000 円（内消費税 1,000 円）」）の順。カート・注文手続き・注文で同じ部品を使う（BR-7） |
| 購入できない品目 | 「購入できません」と理由（表示されなくなった、販売停止、在庫切れ、在庫が足りない）。数量は出さない（AC-64、80） |
| 注文の状態 | 「受付」「キャンセル申請中」「キャンセル」（BR-9） |
| 日時 | 日本時間で「2026/10/10 14:05」 |
| バリアントの選択 | 軸ごとに値を並べる。他の軸の選択と組み合わせて、在庫切れ・販売停止のバリアントにしかならない値は、選べない状態（グレー）で出す（AC-62、28） |

## 6. 結果の知らせ方

- 取得の失敗はエラーの画面に出す。URL のクエリの入力の誤り（形が違うなど）は、API のエラーの `message` をその画面に出す。価格帯の下限が上限より大きいときは、API はエラーにせず空の一覧を返す。
- 操作（サーバーアクション）の結果は、`ActionResult`（成功、または `message` と入力欄ごとのメッセージ）で返し、操作した部品の近くに出す。
  - 入力の誤り（400）：入力欄に対応するものはその欄の下に、それ以外はフォームの下に、API のエラーの `message` を出す。入力した値は消さない。
    - API の契約の形の検証（OpenAPI の形や長さ）のエラーは、項目ごとのメッセージが検証の部品の既定の文（正規表現など）なので、欄の下には業務の検証エラーと同じ文を出す（`features/checkout/placeOrderErrors.ts`）。
  - 業務のエラー（400 の業務ルール、409）：API のエラーの `message` をフォームの下に出す。次にすべきことが別の画面にあるもの（在庫不足、カートの変更）は、その画面へのリンクを添える。総額が変わった（AC-89）ときは、画面を新しい金額で表示し直す。
  - 通信の失敗（バックエンドが止まっているなど）：「サーバーに接続できませんでした。」と出す。
- 成功の知らせは、次の画面への移動か、表示の変化（カートの数量など）で示す。「カートに入れる」は、成功したらボタンの近くに「カートに入れました」とカートへのリンクを出す。
- キャンセルの申請が却下された注文には、問い合わせ先を示す（AC-96）。問い合わせ先のメールアドレスは、店舗の情報（`GET /shop`）として店舗 API から受け取る（値はバックエンドの設定。plan 002 第 4 節）。店舗画面の環境変数には、接続先・キャッシュの秒数など、画面の処理そのものの設定だけを置く。

## 7. 品質

- CI で、lint（Biome）、型チェック、テスト、ビルドを実行する（constitution 13）。型チェックとビルドは、型の生成の後に行う。
- テストは次のように分ける。管理画面と違い、React Testing Library で部品を描画して操作する結合テストは使わない。画面はサーバーコンポーネントで、操作はサーバーアクション（サーバーで API を呼ぶ）を通るので、ブラウザーの中だけでは振る舞いを再現できないため。代わりに、サーバーの処理を Node の上で直接呼んで確かめる。

| 対象 | テスト | 置き場所 |
|------|--------|----------|
| `lib/`・`features/` の関数（判定、変換、表示の整形、エラーの欄への対応） | Vitest の単体テスト。厳密な TDD（constitution 12.2） | 対象の横（`*.test.ts`） |
| 表示の部品（価格、品目、金額の内訳など。状態を持たないもの） | `react-dom/server` の `renderToStaticMarkup` で HTML にし、出る文字と並びを確かめる | 対象の横（`*.test.tsx`） |
| サーバーの処理（サーバーアクション、`api/cart.ts`、`auth/` のコールバック、`proxy.ts`） | Vitest（Node）で直接呼ぶ。Next.js の口（`next/headers`、`next/navigation`、`next/cache`）と `@/auth` は `src/test/` の置き換えに、バックエンドは MSW（`msw/node`）にする | 対象の横（`*.test.ts`） |
| 画面をつないだ操作の流れ（カートに入れて注文する、エラーの表示、入力が残ること） | E2E（`e2e/`） | `e2e/tests/` |

## 8. 画面を追加する手順

1. 使う API が `store.yaml` にあることを確かめる。なければ、先に plan と `store.yaml` を直す（constitution 15）。
2. `app/` にルートを作り、部品は `features/<機能>/components/` に置く。操作のある部分だけクライアントコンポーネントにする。
3. データはサーバーコンポーネントで取得し、第 4 節に従う。
4. 新しい表示の決まりは `lib/` か `features/` の関数にし、単体テストを書く。
5. lint、型チェック、テスト、ビルドを通し、開発サーバーで表示を確かめる。
6. ログインを求める画面は、第 9 節のとおり、取得の前にログインを確かめる。

## 9. ログイン

plan 003 第 1、4、6 節の決定を、店舗画面でどう作るか。店舗画面のサーバーが IdP とやり取りし（BFF）、token はサーバーだけで扱う。

- **設定**：`auth/` に Auth.js の設定を集め、外からは `@/auth` だけを import する（ライブラリを替えるときの範囲を狭くするため。plan 003 第 4 節）。
  - provider は Keycloak（`ec-store` realm の `ec-store-web`、confidential client）。認可コード + PKCE。
  - 接続先と secret は環境変数：`AUTH_KEYCLOAK_ISSUER`（既定 `http://localhost:8180/realms/ec-store`）、`AUTH_KEYCLOAK_ID`（既定 `ec-store-web`）、`AUTH_KEYCLOAK_SECRET`、`AUTH_SECRET`（Cookie の暗号化の鍵）。既定の値は、ローカルと CI だけで使う値（realm の JSON と同じ。plan 003 第 2.4 節）で、開発のモード（`next dev`）とテストでだけ使う。本番のモード（`next start`）では、この 4 つと `STORE_API_BASE_URL` がなければ、起動のとき（`instrumentation.ts`）に足りない名前を出して失敗する（`src/auth/config.ts`。[フロントの書き方](../style/frontend.md) 第 8.1 節）。E2E は `playwright.config.ts` で値を渡す。
- **セッション**：暗号化した HttpOnly の Cookie（Auth.js の JWT 方式）に、access token、refresh token、ID token、access token の期限、会員の氏名・メールアドレスを持つ。サーバーに状態を持たない（constitution 5-1）。
  - 画面から読める情報（`auth()` の結果。Auth.js の `/api/auth/session` でブラウザーからも読める）には、氏名とメールアドレスだけを入れ、token は入れない。token は `@/auth` の `getAccessToken()` で Cookie から直接読む（サーバー専用）。
  - 氏名は、token の姓（`family_name`）と名（`given_name`）を「姓 名」の順に並べる。
- **token の更新**：access token の期限（5 分。plan 003 第 2.3 節）が 1 分を切っていたら、refresh token で取り直す。
  - `proxy.ts` が要求ごとにセッションを確かめ、取り直した token を Cookie に書く（サーバーコンポーネントは Cookie を書けないため）。
  - ただし、同じ要求の中では画面は古い Cookie を読む。`getAccessToken()` は、読んだ access token の期限が切れていれば（しばらく操作がなかったとき）、自分でも取り直して使う（Cookie には書かない。次の要求で `proxy.ts` が書く）。
  - 取り直せなければ（IdP のログインの状態が切れた。AC-117）、ログインしていないものとして扱う。
- **ログインの状態の取り方**：サーバーコンポーネントとサーバーアクションで `currentMember()`（`@/auth`）を呼ぶ。ログインしていれば氏名とメールアドレス、していなければ `null`。クライアントコンポーネントでは取らない（Auth.js の `SessionProvider` は使わない）。必要なら、サーバーコンポーネントから props で渡す。
- **ログインの画面へ移す**：`/login?returnTo=<戻る画面>` へ移す。ここから IdP のログインの画面へ移り、ログインの後は `returnTo` に戻る（AC-113）。`returnTo` は店舗画面の中のパス（`/` で始まり、`//` と `/\` で始まらない）だけを受け付け、それ以外は `/` にする（外のサイトへ戻さない）。
  - 会員登録は `/login?register=1&returnTo=...`。IdP の会員登録の画面（OIDC の `prompt=create`）へ移る（AC-108）。
  - 画面とサーバーアクションは、`redirectToLogin()` でいまの画面に戻るように移す。いまの画面のパスは、`proxy.ts` が要求のヘッダー（`x-pathname`）に入れて知らせる（サーバーコンポーネントは URL を直接は知らないため）。
- **ログインを求める画面**（注文手続き、注文の一覧、注文）：取得の前に `currentMember()` を確かめ、`null` なら `redirectToLogin()` を呼ぶ。API が 401 を返したとき（token が無効になった）も同じにする。
  - 注文手続きに進む（カートの画面の操作）は、ログインしていなければ、カートに戻るようにログインの画面へ移す（AC-125）。
- **ログアウト**（AC-115）：サーバーアクション（`actions/auth.ts`）で、セッションの Cookie と Cookie のカート ID を消し、IdP のログアウト（RP-Initiated Logout。ID token と、戻り先の店舗のトップを添える）へ移る。IdP のログインの状態も終わるので、パスワードなしではログインし直せない。
- **アカウント**（AC-119）：ヘッダーから IdP のアカウントの画面（`<issuer>/account`）へ移る。氏名を変えたら、次にログインしたときからヘッダーの氏名が変わる（セッションの氏名は、ログインのときの ID token から取る）。
