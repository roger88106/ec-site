# レビューの収束の規則

[SKILL.md](SKILL.md) の手順 1・4〜6 で、2 回目以降のレビュー、まとめ、起票の案を扱うときに読む。

## 規則

| 項目 | 規則 |
|------|------|
| 由来 | レビュー役は各指摘に「由来」を付ける。値は「今回」と「既存」。差分の外の行、または差分の前からある行への指摘は「既存」 |
| 既存の「高」 | その spec が変えるファイルの中なら修正し、外なら起票の案にする |
| 既存の「必須」「推奨」 | 修正しない。GitHub の issue「既存のレビューの指摘の一覧」に、spec の最後に spec ごとに 1 つのコメントで追加する（spec の番号、場所、指摘、重要度）。理由：spec ごとに起票の案にすると案が増える。定期の全体のレビューでまとめて扱えるので、コメントで追加するだけにする。issue は #252 |
| 2 回目以降 | 同じ範囲の 2 回目以降のレビューは、前回のレビューの commit から HEAD までの差分と、前回の指摘の修正だけを対象にする。結果の置き場所に、レビューした commit を記録する（手順 1） |
| 上限 | 同じ対象のレビューと修正の繰り返しは 3 回まで。3 回目で高・必須が残ったら、spec 担当のセッションは修正の前提を 1 文で書いて再検討し、止まって利用者に報告する |
| 同じ種類の指摘 | 修正の前に、対象の全体を検索してまとめて修正する。spec 担当のセッションが修正の指示に検索の式を入れ、実装役は式と件数を報告に書き、spec 担当のセッションが tasks の結果に転記する |
| 同じ判定の別の書き方の指摘 | 同じ判定の別の書き方の指摘が 2 回続いたら、spec 担当のセッションは、修正の前提を変える案を利用者に提示する。変え方は、禁止の一覧から許可の一覧へ替えるか、対象の外（既知の制限）とするか。理由：禁止する形を 1 つずつ加えても、回避の書き方が尽きないため |
| 採らなかった指摘 | 採らなかった指摘と起票の案にした指摘を、各レビューの結果の置き場所（手順 1）の `rejected.md` に書く。同じ spec の後のレビューでは、それまでの `rejected.md` を全てレビュー役に渡す。渡すときは、指示のひな形の根拠の欄「採らなかった指摘の一覧」にパスを書く。レビュー役は、ひな形の「この一覧の指摘は返さない」に従う |
