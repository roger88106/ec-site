# 担当のセッションの起動の指示

issue 担当のセッションが、spec か issue の担当を渡すときに読む。理由：issue 担当のセッションが毎回指示を書くと、パスの誤りや抜けが出たため（振り返りの集計）。

- 宛先は、セッションの識別子にする（[SKILL.md](SKILL.md)の「セッションの間のメッセージ」）。長い指示は、手元のファイルに書いて、そのパスを送ってよい。
- 雛形には、マシン固有のパス、セッションの識別子、`/.local/` の中だけで通じる呼び名（手元のファイルの名前など）を書かない。

雛形（issue ごとに変わる `<...>` だけを埋める）：

```text
1. 役割と確認の宛先：あなたは <spec の番号または issue の番号> の spec 担当のセッション。報告と確認の依頼は、issue 担当のセッション（<識別子>）に送る。
2. 最初に読むもの：作業ツリーの AGENTS.md の「最初に読むもの」、メインの /.local/agent/environment.md（返答の言語。Git に入るものは日本語）、担当の issue（gh issue view <番号> --json title,body,comments）。材料のファイル：<材料>。skill を変えるなら skill writing-for-agents。
3. 作業ツリー：作業ツリーがなければ、メインの作業ツリーで `git worktree add .claude/worktrees/<issue の番号>-<短い名前> -b agent/<issue の番号>-<短い名前> develop` を実行する。作業ツリーで起動されたときは、`git -C <作業ツリー> rev-parse --show-toplevel` で確認する。以後は作業ツリーの絶対パスで作業し、メインの作業ツリーを変えない（cd で移らない）。
4. 確認と開始の条件：<規模の区分と、spec（規模 L は spec・plan・tasks）の確認は、issue 担当のセッションが利用者に代わって行う、と決まっているときだけ書く>。書き終えたら、issue 担当のセッションに確認を求める。本文で決めていない設計の判断は、案と推奨を示して確認を求める。利用者が <確認する対象> を承認し、5 時間の使用量が <x>% 未満、週が <y>% 未満なら、問い合わせずに始め、開始を知らせる。特例：<有無>。レビューの profile：<profile>。
5. 並行の状況：並行している他の担当は次のとおり。両方が変えるファイルは、自分の行だけを変える。相手の範囲を変える必要が出たら、issue 担当のセッションに知らせる。マージの前に develop を取り込んで、衝突を解消する。
   | 担当（issue） | 変えるもの |
   |---------------|------------|
   | <issue> | <変えるもの> |
6. 文書と commit：文書の本文の書き手は、文書の書き方の「本文の書き手」と、skill docs の「進め方」のとおり。校閲は、skill review の docs-review.md の手順 3 の級の表で決めた役が行う。コミットメッセージは、skill local-dev の「最初に読む：検査に拒否されない書き方」のとおり。
7. push と pull request：最初の push は、draft の pull request を作る直前にする（開発の進め方の「push のタイミング」）。pull request の本文は .github/pull_request_template.md に合わせる。ready にしたら、pull request の番号、head の commit、危険度を issue 担当のセッションに知らせ、CI の監視を任せる（マージと後片付けの「ready と CI の順」）。
8. マージ：危険度が高い変更と機能の spec は、利用者が受け入れ、許可を得てから、spec 担当のセッションがマージする。許可は head の commit にだけ有効。転送した許可は auto mode に拒否されることがあるので、拒否されたら回避せず、利用者にこのセッションで直接答えてもらうよう頼み、issue 担当のセッションに知らせる。それ以外は issue 担当のセッションがマージし、spec 担当のセッションはマージしない（マージと後片付けの「マージの許可」）。
9. 後片付け：マージの後は、マージと後片付けの「後片付け」と、振り返り（skill agent-retro）を行い、issue 担当のセッションに知らせる。アーカイブは、利用者の許可を待つ。
10. その他：他のモジュールや規則に関わる判断と、spec・設計の誤りは、その場で issue 担当のセッションに知らせる。<issue ごとの注意>
```

- 4 の x と y と特例は、[SKILL.md](SKILL.md)の「spec 担当のセッションの起動と実装の開始」に従う。
- 予備のセッションの作業ディレクトリは、メインの作業ツリーのままである。
- 新しいセッションを手動の作業ツリーで起動するときは、作業ディレクトリ（`cwd`）を作業ツリーのパスで指定する。理由：アプリの「作業ツリーで起動する」の指定は、手動で作った作業ツリーでは反映されない。この動きを測った記録は[毎回読む文書と固定の文脈の大きさ](../../../docs/07-記録/context-size.md)の「固定の文脈」。
