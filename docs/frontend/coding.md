# フロントの書き方

管理画面と店舗画面に共通する書き方。アプリごとの構成は [管理画面](apps/admin.md) と [店舗画面](apps/store.md)。

## 規則の一覧

| 節 | 規則 | 確かめ方 |
|----|------|----------|
| 1.1 | 画面に依存しない処理は `lib/` の関数 | 人手 |
| 1.2 | 機能ごとに `features/<機能>/` | 人手 |
| 2.1 | 生成した型で API を呼ぶ | 自動（型チェック） |
| 2.2 | エラーの文は API の `message` を出す | 人手 |
| 2.3 | 入力の制約は契約から書き出した定数 | 自動（`input-constraints.mjs`） |
| 3.1 | `catch` では `unstable_rethrow` を先に | 人手 |
| 3.2 | サーバーアクションの結果は `ActionResult` | 人手 |
| 4 | 整形と lint は Biome | 自動（`pnpm lint`） |
| 5.1 | 共有パッケージに入れるもの・入れないもの | 人手（admin と store に同じファイルがないか） |
| 6 | 画面の URL は型で確かめる | 自動（型チェック）、型の付かない URL は人手 |
| 7.1 | 表示の文言は文言ファイルに置く | 自動（`hardcoded-text.mjs`、型チェック） |
| 7.2 | 文言キーの形 | 人手 |
| 7.3 | ロケールは 1 か所 | 人手（`git grep "Intl\."`） |
| 8.1 | 店舗画面の環境変数は起動時に確かめる | 自動（単体テスト） |
| 8.2 | 店舗画面のサーバーログは 1 行 1 件の JSON | 自動（単体テスト）、`console.*` の直書きは人手 |
| 9.1 | 依存を足したら入れ直して確かめる | 自動（CI のインストールとライセンス検査） |

人手のものは、各 spec の [見直し](../process/review.md) で読む。

## 1. 置き場所

### 1.1 画面に依存しない処理は `lib/` の関数

判定、変換、表示の整形、列挙の表示名は `lib/` の関数（React に依存しない）にし、横に単体テストを置く。コンポーネントはその関数を呼ぶだけにする。

理由：規則を描画なしの速いテストで確かめ、画面を作り直しても規則が残るようにするため。

### 1.2 機能ごとに `features/<機能>/`

画面とその画面だけで使うコンポーネント・処理は `features/<機能>/`、複数の機能で使うコンポーネントは `components/`、shadcn/ui の生成物は `components/ui/`（手で直さず、Biome の対象外）に置く。

理由：機能を足す・消すときに触るファイルを 1 か所にまとめるため。

## 2. API

### 2.1 生成した型で呼ぶ

API は `openapi-fetch`（管理画面は `openapi-react-query` の `$api`）で、生成した型を使って呼ぶ。パスや応答の型を手で書かない。

理由：契約が変わったときに、型チェックで食い違いが分かるようにするため。

### 2.2 エラーの文は API の `message` を出す

業務と入力のエラーは、API の `message`（項目ごとは `errors`）をそのまま出す。画面で文を作るのは、通信の失敗など応答がないときだけ。

理由：メッセージの正本をバックエンドの 1 か所にするため。

### 2.3 入力の制約は契約から書き出した定数

- 入力欄の `maxLength`・`minLength`・`max`・`min` は、`src/api/generated/constraints.ts` の定数で書く（数字を直接書かない）。
- このファイルは `generate:api` が OpenAPI の制約から作る。スキーマの項目は `schemas.<スキーマ>.<項目>`、クエリは `parameters.<操作 ID>.<名前>` で引く。

理由：契約の制約を変えたら、画面の制約も一緒に変わるようにするため。

## 3. 店舗画面のサーバーアクション

### 3.1 `catch` では `unstable_rethrow` を先に

サーバーアクションで例外を `catch` するときは、最初に `unstable_rethrow(error)` を呼ぶ。`redirect` は try の外で呼ぶ。

理由：Next.js の `redirect`・`notFound` は例外で移動を知らせるので、飲み込むとログイン画面への移動などが通信の失敗に見えてしまうため。

### 3.2 結果は `ActionResult` で返す

サーバーアクションは失敗を例外にせず、`ActionResult`（`lib/actionResult.ts`）で返す。401 だけはログイン画面へ移す。

理由：操作した場所の近くに結果を出し、入力を消さないため。

## 4. 整形と lint

Biome の設定（`biome.jsonc`）に従う。インデント 2、行の長さ 120、単一引用符、セミコロンは必要な所だけ。Tailwind のクラスの並びも Biome が揃える。

理由：書き方の揺れをツールでなくし、見直しで扱わないため。

## 5. 共有パッケージ（`frontend/shared/`）

### 5.1 入れるもの・入れないもの

| 入れる | 入れない |
|--------|----------|
| 2 つの画面で使い、画面の枠組み（Vite・Next.js）と API の接続に依存しないもの：カテゴリの木、ログインの戻り先、クラス名の結合、数・日付・金額の整形、同じ表示のコンポーネントとテーマ、共通の文言 | API の接続（接続先と認証が違う）、認証、画面の機能、サーバーアクション |

- 共有のものは、各画面の機能を import しない。
- shadcn/ui のコンポーネントは各画面の `components/ui/` に足し、2 つの画面で同じ内容になったら `frontend/shared/src/ui/` に移す。共有コンポーネントは、店舗画面のサーバーコンポーネントからも使えるよう `"use client"` を付けたままにする。
- 共有コンポーネントのクラス名は、各画面の CSS の `@source` で Tailwind に読ませる（`node_modules` の先は自動で読まないため）。

理由：同じ処理とコンポーネントを 1 か所で直し、片方の画面の都合をもう片方に持ち込まないため。

## 6. 画面の URL

| 画面 | 作り方 |
|------|--------|
| 管理画面 | `src/app/paths.ts` の `paths` の関数で作る（ルーターの定義は同じファイルの `routePatterns`）。URL の文字列を直接書かない |
| 店舗画面 | Next.js の `typedRoutes` で、画面の置き場所と照らす。クエリ付きの URL は機能の `*Query.ts` の関数（戻り値は `Route`）で作る。店舗画面の外の URL（IdP など）だけ `as Route` にし、理由をコメントに書く |

見直しでは、管理画面は `git grep` でパスの文字列の直書きを、店舗画面は `as Route` と、型の付かない `revalidatePath()` と `<form action>` の URL を確かめる。

理由：間違った URL を型チェックで見つけるため。

## 7. 表示の文言とロケール

### 7.1 表示の文言は文言ファイルに置く

- 見出し、ボタン、ラベル、知らせ、確認の文、エラーの既定の文、ページの題名は、各画面の `messages/ja.json` に置き、コードではキーで引く。2 つの画面で同じ文言（`common.*`）は `frontend/shared/src/messages/ja.json`。
- 引き方：コンポーネントの中は `useTranslations`（店舗画面の async のサーバーコンポーネントとサーバーアクションは `getTranslations`）、コンポーネントの外の関数は各画面の `src/i18n/translate.ts` の `translate`。
- 数は整形してから渡し（`{amount}` は数を整形しない）、値は名前で差し込む（`{code}を上へ`）。コードで組み立てる表示名（`画像 ${n}` など）も文言にする。
- 例外：テストの中の文字、開発者だけが見るログ、アイコンの代わりの記号、API の応答の文 ※1。

※1：検査（`hardcoded-text.mjs`）は、コメント以外の日本語を探す。API に送る値など文言でないものは、理由と一緒に `scripts/ci/hardcoded-text-exclusions.json` に書く。

理由：文言を 1 か所で管理し、2 つ目の言語を足せるようにするため。

### 7.2 文言キーの形

`<機能>.<画面かコンポーネント>.<項目>`（例：`tax.list.title`）、共通は `common.<項目>`。英小文字で始める `camelCase` を `.` でつなぐ。API の列挙の値やエラーコードの表示名は、値からキーを組み立てるので、最後をその値のまま書く（`labels.publicationStatus.PUBLISHED`）。

理由：キーから表示する所を引けるようにするため。

### 7.3 ロケールは 1 か所

既定のロケール（`ja-JP`）とタイムゾーンは `frontend/shared/src/lib/locale.ts` だけに書き、整形とページの言語（`lang`）はそこから取る。`Intl.*` にロケールを直接書かない。

理由：言語を足すときに、変える所を 1 か所にするため。

## 8. 店舗画面のサーバーの設定とログ

### 8.1 環境変数は起動時に確かめる

本番（`NODE_ENV=production`）で、Cookie の暗号の鍵（`AUTH_SECRET`）、IdP の client の ID と secret、IdP と API の場所がなければ、起動（`instrumentation.ts` の `register()`）で足りない名前を並べて失敗させる。ローカル用の既定値は、開発モードとテストでだけ使う ※2。

※2：モジュールの読み込み時には確かめない。`next build` も本番モードで動き、CI のビルドには secret がないため。

理由：設定を忘れたまま、公開されている既定値で動き出さないようにするため。

### 8.2 サーバーログは 1 行 1 件の JSON

- 店舗画面のサーバーログは `src/lib/server/log.ts` で、1 行 1 件の JSON（時刻、レベル、メッセージ、追跡 ID、項目）にする。`console.*` を直接呼ばない。
- レベル：操作は失敗したが続けられるものは `warn`、予期しない失敗は `error`、調べるための記録は `info`。
- バックエンドへの要求に W3C の `traceparent` を付け、同じ追跡 ID をログに出す。

理由：バックエンドのログと同じ追跡 ID で、1 つの要求を辿れるようにするため。

## 9. 依存

### 9.1 依存を足したら入れ直して確かめる

- 依存を足す・上げたら、ルートで `pnpm install --frozen-lockfile` を流し直す。
- インストール時のスクリプトを持つライブラリ（間接の依存も含む）は、`pnpm-workspace.yaml` の `allowBuilds` に、実行するか（`true`・`false`）と理由を書く。
- ライセンスも確かめる（`node scripts/ci/licenses/check-frontend.mjs`）。
- 両方は `scripts/dev/check-frontend.sh` の `install`・`licenses` の手順でも流せる（既定で流す）。

理由：`allowBuilds` にないライブラリがあると pnpm はインストールを失敗にするが、手元は依存が入った後なので気づかず、CI で初めて失敗するため。
