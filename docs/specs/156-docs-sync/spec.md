# Spec 156：設計の文書と用語集を実装に合わせる（MVP 019 の全体のレビューの指摘）

ステータス：確定

## 1. 背景と目的

MVP 019 の全体のレビュー（2026-10-21）で、設計の文書と用語集が実装と食い違う指摘、文書の間で書き方がそろわない指摘、不要な記述が残った。1→10 で機能を追加する前に、文書を今のコードと規則に合わせる。

追跡の issue は [#156](https://github.com/roger88106/ec-site/issues/156)、扱う issue は [#77](https://github.com/roger88106/ec-site/issues/77)（用語集の mock の説明）と [#91](https://github.com/roger88106/ec-site/issues/91)（文書の推奨の指摘 25 件）、作業ブランチは `156-docs-sync` である。本 spec は整理の spec で、規模は M である（利用者が承認済み）。

#91 の「ほか 20 件」の細目は、MVP 019 のレビューの結果のファイルが残っていない。2026-10-23 に、同じ観点（文書とコード、一貫性、不要なもの）で、今の `develop` の文書（`docs/`、README、AGENTS.md。完了した spec・plan・tasks を除く）を再びレビューした。4 つの範囲を、汎用のサブエージェントで 2 回ずつ実行して和集合を取った。指摘は、spec 担当のセッションがコードと照合した。#91 に名前のある 5 件は、全て今も当てはまる。

並行して、spec 155（バックエンドの構成）が共通コードの設計書とパッケージの構成を、spec 157（管理画面と共有のパッケージ）が管理画面の構成と共有のパッケージを変える。それらの spec が変更する箇所の記述は、本 spec の範囲から除く（第 5 節）。

## 3. 目的と完了条件

### DS-156-1 モジュールの設計書（D / P1）

- **DC-156-1** 商品カタログの設計書のできる操作のフラグの表が、公開・非公開・販売終了のフラグを別々の条件で書く。例：公開できるのは非公開のときだけ。
- **DC-156-2** 商品カタログの設計書が、削除できないときに返す理由を書く。
- **DC-156-3** 注文の設計書のできる操作のフラグの表が、キャンセルの時に在庫に戻すかを確認するフラグの条件を書く。
- **DC-156-4** 決済の設計書の公開の一覧に、支払える注文の ID を得る操作がある。
- **DC-156-5** 地域の設計書の公開の一覧に、都道府県をコードで得る操作がある。
- **DC-156-6** カートの設計書が、カートの API の利用者を注文だけとする。理由：店舗モジュールはカートに依存しないため。
- **DC-156-7** 在庫の設計書が、実在しない集約を書かない。在庫と在庫調整の今の作り（集約のクラスを持たない）に合わせて、節の名前と説明を修正する。
- **DC-156-8** 各モジュールの設計書のデータモデルの節が、そのモジュールのマイグレーションを、全て挙げる（第 6 節の 1）。対象は商品カタログ、在庫、カート、注文、決済、地域。
- **DC-156-9** 決済の設計書が、イベントを全ての箇所で「支払の期限切れ」と呼ぶ。決済サービスの通知の種類の名前とは区別する。
- **DC-156-10** 注文の設計書が「帳票」でなく「レポート」と書く。
- **DC-156-11** カートの設計書の構成が、期限切れのカートの片付けを書く。販売可能数の判定の注は、品目の追加と変更の節に置く。
- **DC-156-12** 今の設計の文書（`modules/`・`apps/`）と、バックエンドのアーキテクチャの本文が、spec・plan の番号と BR の番号を根拠にしない。対象は、メディアとレポートの設計書と、バックエンドのアーキテクチャである。

### DS-156-2 用語集、規則、手順（D / P1）

- **DC-156-13** 用語集の決済サービスと物流サービスが、「テストと既定は mock」と書かない。決済は mock フラグを立てたときだけ mock で、立てなければ Stripe を使う。物流は今の実装が mock だけで、フラグを立てなければ起動に失敗する（#77）。
- **DC-156-14** constitution の CI の要点が、文書だけを変えた push で何を実行するかを、CI の検査の文書と食い違わないように書く。文書だけの push では、CI の検査の script の全てを実行する。
- **DC-156-15** 環境変数の文書に、メディアのストレージの資格情報（アクセスキー ID とシークレット）の環境変数がある。
- **DC-156-16** バックエンドの書き方のメッセージのキーの例が、実在する定数とキーを使う。
- **DC-156-17** バックエンドの書き方の、OpenAPI に書かない例外のエンドポイントに、物流の通知と mock の物流の画面がある。
- **DC-156-18** API の規約の mock の支払画面の説明に、拒否の操作の応答がある。
- **DC-156-19** CI の検査の文書の「CI のジョブ」の列が、ジョブの表にあるジョブの名前だけを使う。
- **DC-156-20** constitution の店舗画面のテストの説明と、フロントのアーキテクチャの店舗画面のコンポーネントのテストの説明が、テストの書き方と店舗画面の構成（ブラウザーの中だけで動くコンポーネントは jsdom で操作する）と食い違わない。
- **DC-156-21** テストの書き方の契約テストの「対象の AC」の表が、全てを挙げるか、例であると示し、AC 一覧と食い違わない。

### DS-156-3 文書の型と書き方（D / P1）

- **DC-156-22** 店舗画面の構成と管理画面の構成の冒頭に、概要の表（依存、関連 spec）がある。skill `docs` の概要の表の記述が、レベルを `modules/` だけに求める（第 6 節の 2）。
- **DC-156-23** コメントの書き方の規則の一覧が、節、規則、確認方法の 3 列である。
- **DC-156-24** 文書の記号と番号の「constitution の記号」の節が、constitution にない記号を案内しない。アーキテクチャのレベルは、定義のあるバックエンドのアーキテクチャを指す。
- **DC-156-25** constitution の各節が、skill `docs` の型（1 文、要点 3 つまで、細則の案内）に合う。対象は、constitution の「プロジェクトの位置づけ」「認証・認可」「CI/CD」の節である。
- **DC-156-26** constitution の文書の地図の `guides/` の説明と、skill `docs` の置き場所の表に、ブランチとリリースがある。
- **DC-156-27** constitution の公開ネットワークへのデプロイの前提の参照が、前提の一覧のある [バックエンドのアーキテクチャ](../../design/backend-architecture.md) 第 7.3 節を指す。
- **DC-156-28** 1 つの文書の中で、注の番号（※）が重複せず、出る順に並ぶ。対象はバックエンドのアーキテクチャ、店舗画面の構成、AGENTS.md である。
- **DC-156-29** モジュールの設計書の節の順（構成、他のモジュールへの公開、データモデル）と、構成の図の並び（`api/`、`event/` の順）が、全ての設計書でそろう。対象は通知、レポート、出荷の設計書である。
- **DC-156-30** 文書の用語が次のとおりにそろう：「ブラウザー」（「ブラウザ」でなく）、「片付け」（「掃除」でなく）、「作業ツリー」（「worktree」でなく）、店舗画面の構成の「ミドルウェア」の前後に空白を入れない。
- **DC-156-31** 参照の書き方がそろう。設計書の関連 spec のリンクは spec のディレクトリを指す。AC 一覧の「変えた spec」のリンクは「元の spec」と同じ形にし、モジュールのリンクの文字は設計書の題と同じにする。開発の進め方、CI の検査、エージェントの作業フローの、他の文書への参照はリンクにする。
- **DC-156-32** 用語集の識別子のない行の書き方が 1 つにそろう。用語集の AGENTS.md への参照はリンクにする。
- **DC-156-33** 用語集が tasks の記号（並行、リスク）を持たず、文書の記号と番号を指す。理由：記号の定義は文書の記号と番号にだけ置き、tasks の 4 つの記号のうち 2 つだけを重複して持っているため。
- **DC-156-34** ロールと権限の対応表の生成元（Keycloak の realm の説明）が「全て」と書き、対応表を再生成している。

### DS-156-4 完了した作業の記録と予定（D / P2）

- **DC-156-35** MVP の完成までの一覧が、削除済みの TODO 一覧へのリンクを持たず、完了した作業の記録（spec の名前の仮の扱い、第 3 節の移したテストの問題、第 4 節の文書の用語）を持たない。spec の一覧の表は、進捗の検査が読むので残す。
- **DC-156-36** モジュールの設計書が、過去の移行の経緯（認証の前の注文の削除、列やコードを追加する前のデータの扱い、画像ファイルの移行）を書かず、今のデータの規則だけを書く。対象は注文、商品カタログ、メディア、レポートの設計書である。
- **DC-156-37** モジュールの設計書が、予定と未決事項（「将来」「1→10 で作る」「MVP の後に再検討する」）を書かない。今はしないことだけを残す。予定と未決事項は issue にあるか、第 8 節の起票の案に入れる。対象は会員、地域、商品カタログ、決済の設計書である。
- **DC-156-38** 規則の文書が、決定を記録した spec の番号を根拠に書かない（テストの書き方の「（spec 012）」）。
- **DC-156-39** constitution と文書の記号と番号が、どの文書も使っていない記号【提案】を案内しない。

- **DN-156-3** 文書の検査（`scripts/ci/check-all.sh`）が通る。

## 6. 決めたこと

2026-10-23 に、利用者が次の 2 つの決定と、第 5 節の採らない推奨の指摘を確認した。Open questions はない。spec 17 の実装が終わった後に、本 spec の前提が変わっていないことを確認して確定にした（利用者の決定、2026-10-23）。

### 1. モジュールの設計書のデータモデルに挙げるマイグレーション（DC-156-8）

今は、テーブルを作るマイグレーションだけを挙げる設計書が多く、後から列や制約を追加したマイグレーション（注文の 4 つ、在庫の 2 つ、カート・商品カタログの 1 つずつ）がない。決済の設計書には 1 つもなく、地域の設計書にはデータモデルの節がない。一方、設計書の本文は、後から追加した制約（税抜価格の上限の CHECK など）を書いている。

- 案 A（採用）：そのモジュールの全てのマイグレーションを挙げる。本文の制約を定義するマイグレーションが分かる。マイグレーションを追加するたびに設計書を修正する必要があり、漏れは後で自動の検査で検出する（第 8 節の起票の案）。
- 案 B：テーブルを作るマイグレーションだけを挙げ、「以後の変更は、同じ接頭辞のマイグレーション」と書く。設計書の修正は少なくて済むが、本文の制約を定義するマイグレーションを特定しにくい。

### 2. 店舗画面と管理画面の構成の概要の表（DC-156-22）

skill `docs` 第 2 節は、`modules/` と `apps/` の冒頭に概要の表（レベル、依存、関連 spec）を置くと決めているが、`apps/` の 2 つにはない。

- 案 A（採用）：概要の表（依存、関連 spec）を置く。レベルはアプリに当てはまらないので、skill `docs` の記述を「`modules/` はレベルも書く」と修正する。関連 spec の行を置くと、関連 spec の検査（`related-specs.mjs`）の対象になり、今後この 2 つの文書を変えた spec の記入漏れを検出できる。今までの spec は、文書の履歴から抽出する。
- 案 B：skill `docs` の記述を `modules/` だけにし、`apps/` には表を置かない。
