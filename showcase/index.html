自社ブランドのための EC サイト

商品を並べて、注文を受けて、
在庫と税金まで正しく回す。

お客様が買い物をする「店舗画面」と、お店の人が商品や注文を扱う「管理画面」の二つで動く、日本向けの通販サイトです。見た目だけの試作ではなく、在庫・消費税・ログイン・権限といった、実際にお店を開くときに困るところから作っています。

店舗画面と管理画面お客様向けとお店向けを別々の画面に分け、それぞれに合った操作にしています。
軽減税率に対応10% と 8% の商品を一緒に買っても、税率ごとの内訳を正しく出します。
売り越しを起こさない最後の 1 個に注文が同時に来ても、在庫がマイナスになりません。

お客様ができること

探す、選ぶ、買う、あとで確かめる

会員登録をしたお客様が、商品を探して注文し、注文の状況を自分で確かめられます。

色やサイズを選んで、カートへ

  • キーワード検索とカテゴリ（衣類 → トップス → T シャツ のような階層）で探せます。
  • 商品ページでは、色やサイズを選ぶとその組み合わせの在庫を示します。
  • 写真は 1 商品に 20 枚まで載せられ、色ごとに見せる写真を決められます。
  • ログインせずにカートに入れた商品も、ログインすると引き継がれます。

注文の明細は、税率ごとに分けて示す

  • 食品（8%）と衣類（10%）を一緒に買っても、税率ごとの対象額と消費税を分けて示します。インボイス（適格請求書）と同じ考え方です。
  • 注文の履歴と状態（受付・キャンセル申請中・キャンセル）を、お客様がいつでも見られます。
  • キャンセルは「申請」として受け、お店が確かめてから取り消します。

お店の人ができること

商品、在庫、税率、注文を一つの管理画面で

専門の知識がなくても、画面の案内に沿って商品を出し、在庫を直し、注文を扱えます。

商品を登録して、公開の日時を予約する

  • 一つの商品に「白の M」「黒の L」のような組み合わせ（バリアント）を持たせ、それぞれに在庫を持てます。
  • 公開の開始と終了の日時を決めておけば、その時間に自動で店に出て、自動で引っ込みます。セールや季節商品に使えます。
  • スマートフォンで撮った写真（HEIC など）もそのまま登録でき、軽い形式に変えて配信します。撮影場所などの情報は自動で消します。
  • 一度店に出した商品は消せず、「販売終了」にします。過去の注文の記録が崩れないためです。

在庫は、増減の理由と操作した人まで残る

  • 入荷・棚卸差異・破損などの理由を付けて在庫を増減します。
  • 注文で減った分も、注文番号付きで履歴に残ります。「なぜ数が合わないのか」を後から追えます。
  • 複数の担当者が同時に在庫を直しても、どちらの操作も失われません。

税率が変わっても、日付を入れておくだけ

  • 「標準 10%」「軽減 8%」のような税区分を商品に割り当てます。
  • 税率には適用の開始と終了の日時を持たせられるので、税制が変わるときや期間限定の減税にも、その日に合わせて自動で切り替わります。

注文を一覧で見て、必要ならキャンセル

  • 注文の明細を品番・税抜単価・税率・税込単価まで表で確かめられます。
  • お客様のキャンセルの申請を受け、在庫を戻して取り消します。
  • 担当者ごとに、できる操作を分けられます。

安心して任せられる理由

お店を開いてから困ることを、先につぶしてある

売り越しと二重の注文を防ぐ

人気商品の最後の 1 個に、同時に何人も注文した場面を自動で再現して確かめています。在庫がマイナスになることはありません。

カード番号を預からない

支払は外部の決済サービスの画面で入力する形にしています。サイト側がカード番号を受け取らないので、漏えいの心配がありません（決済は開発中）。

ログインは専用の仕組みに任せる

パスワードの管理を自前で作らず、実績のある認証の仕組みを使っています。お客様と運営者のアカウントも完全に分けています。

直すたびに、全部を自動で確かめる

変更を入れるたびに、約 1,000 件の自動テストが流れます。新しい機能を足して、前の機能が壊れたまま出ることを防ぎます。

作り方

決めてから作る。確かめてから進む。

一人で開発していますが、チームで本番のサービスを作るときと同じ手順を守っています。作るものを文書で決め、決めたとおりに動くことをテストで証明してから、次に進みます。

166文書で決めた「こう動くべき」という条件。すべてにテストを対応させています
約 1,000自動テストの件数（画面・サーバー・ブラウザでの通し操作）
7仕様書の数。機能を足すたび、また整理するたびに一つ書きます
2画面の数（店舗・管理）。文言は差し替えられるように作り、多言語化に備えています
仕様を書く誰が何をできるか、どうなれば完成かを、条件の一覧として書く。
設計を決める画面とサーバーのやり取りの約束（API）を先に決め、両側がそれに合わせる。
テストを先に書くまだ動かないことをテストで確かめてから、作り始める。
作って、見直すテストが通るように作り、決めた書き方の規則と照らして見直す。
サーバー業務ごとに部品を分け、将来は別々のサービスに切り出せる形にしています。Java 21 / Spring Boot / Spring Modulith / PostgreSQL / jOOQ
店舗画面表示が速く、検索エンジンにも読まれやすい作り。Next.js / TypeScript / Tailwind CSS

運用アクセスが増えたら、同じサーバーを並べて増やせる作りにしています。Docker / S3 互換ストレージ / Prometheus
