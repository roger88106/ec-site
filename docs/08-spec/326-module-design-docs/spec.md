# Spec 326：注文以外のモジュールの設計書を、4 層の形に書き換える

種類：整理　規模：L　ステータス：確定

危険度：高

## 背景と目的

整理の段階の第 2 フェーズの spec 5 である。追跡の issue は #326 で、種類は整理、領域は docs である。規模 L は利用者が承認した（2026-10-29）。消費者・運営者に見える振る舞いと、本番のコードは変えない。

前の spec 4（#321、pull request #322、2026-11-02 マージ）が、設計書の 4 層の雛形を置き、注文だけをその形で書いた。4 層は、① 概要（`docs/01-概要/`）、② 設計（`docs/02-設計/`）、③ 機能仕様（`docs/03-機能仕様/`）、④ 決定記録（`docs/04-決定記録/`）である。注文以外は古い形のまま残した（spec 4 の DN-321-3）。この spec で、注文以外のモジュールの ③ を固定の節に書き換え、② を作り、今有効な業務規則（BR）と受け入れ条件（AC）をアーカイブの外に置く。

方針は、アーカイブを当時の記録として残し、今有効な内容をアーカイブの外に移すことである（整理の段階の棚卸しの「参照の方針」、利用者の決定、2026-10-29）。

作業ブランチは `326-module-design-docs` で、`develop` の 57ef9635（#322 のマージ）から作った。アーカイブ先は `docs/08-spec/archive/1to10/326-module-design-docs/` である。

危険度は高とする。`scripts/ci/`、`docs/05-開発規則/`、`docs/constitution.md` を変え、`scripts/ci/risk.json` の「エージェントの規則と設定」「CI とリリース」の経路に当たるためである。バックエンドのテスト（`ProductionClassesTest`）も変える可能性がある。マージは利用者が許可する。

CI の検査の script を変えるので、pull request の前に、文脈を持たない高性能のレビュー役（`reviewer`）を 1 回加える（[エージェントの作業フロー](../../05-開発規則/subagents.md)の「レビューの時点と profile」。spec 4 と同じ）。認証・支払・権限の経路は変えないので、セキュリティのレビューは行わない。

レビューの profile は「厚め」で、issue 担当のセッションが決めた（週の使用量 12%）。

並行する C3 のセッション（#318、#324）との重なりは、「依存」の表に書く。

## 非機能要件

- **DN-326-1** 消費者・運営者に見える振る舞いを変えない。本番のコードを変えない。例外は、本番のコードのコメントのうち、移した・見出しを変えた設計書を指す参照の修正だけである（spec 4 の DN-321-1 と同じ）。
- **DN-326-2** アーカイブした spec を変えない。
- **DN-326-3** AC と BR の意味を変えない。書き換えで食い違いを見つけたら、その場で直さず起票する（[開発の進め方](../../05-開発規則/workflow.md)の「コードと文書の食い違い」）。
- **DN-326-4** 文書の検査（`doc-refs`、`note-numbers`、`ja-text`）、`scripts/ci/check-all.sh`、`./gradlew check`、CI が通る。
- **DN-326-5** commit の前の hook（`check-all.sh`）の実行時間を、大きく増やさない。理由：commit のたびに実行されるため。
