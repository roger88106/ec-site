共通の決定：

- 本 spec は危険度の高い変更である（DC-245-14）。規則と設定そのものを変えるため、利用者がマージを許可する。
- 実装は実装役に 1 タスクずつ任せる。区分は第 4.1 節の表による。既定は汎用で、`[リスク]` のタスクは高性能とする。
- `[リスク]` のタスクは、危険度の検査の script（CI の必須の検査になる）、CI の job、保護の規則の 3 つである。理由：CI の必須の検査とマージの条件を変えるため。
- 手元の環境（スロット）は使わない。本番のコードを変えないので、バックエンドのテストは実行しない。確認は CI の検査の一括の script と CI と、文書を読むレビューで行う。
- 規則の文書の本文は、日本語の要点から、日本語だけの文脈のサブエージェントに書かせる（[エージェントの作業フロー](../../rules/subagents.md) 第 2 節）。実装役への指示は日本語で書く。
- サービス固有の名前は、AGENTS.md のモデルの区分の表と、ツールの注にだけ書く（DN-245-3）。本 plan では、決定の根拠として名前を書いてよい。
- 1 タスクを 1 commit にする。例外は、`[テスト]` と実装の組で、2 つのタスクを 1 commit にする（[開発の進め方](../../rules/workflow.md) 第 2.1 節）。
- 本 spec の変更は、本 spec のマージの前に、並行する他の spec に適用しない（DN-245-6）。ただし、資源の配分の規則（DC-245-73〜80）は、利用者が決めた運用として既に行っている。

## 3. 続けてマージするときの待ち（DS-245-3：DC-245-33〜36）

| DC | 決定 | 置き場所 | 確認方法 |
|----|------|----------|----------|
| 33 | 保護の規則の「最新の develop を含む」を外す。GitHub Actions の更新を 1 つの group にまとめる。CI の job を経路で省く方法と merge queue は選ばない | GitHub の保護の規則（利用者の許可を得て変える。DN-245-5）、`.github/dependabot.yml`、ブランチとリリースの文書 | 保護の規則の設定を `gh api` で読み、外れたことを確認する。dependabot の検査の script が通る |
| 34・35 | マージの後、issue 担当のセッションが `develop` の push の CI を見届ける。見届けの担当と詳細は skill `sessions`（段階 3）に書き、手順の要点は開発の進め方 第 5.7 節（段階 1）に書く。失敗したら、他の pull request のマージを止め、すぐに起票する（[開発の進め方](../../rules/workflow.md) 第 4.1 節の急ぐ作業）。直るまで次のマージをしない | skill `sessions`、[開発の進め方](../../rules/workflow.md) 第 5.7 節 | 文書を読む |
| 36 | [開発の進め方](../../rules/workflow.md) 第 5.7 節の「マージの許可を求める前に、最新の develop を取り込み、CI が通っていることを確認する」を、「衝突があるとき、または `develop` が同じファイルを変えたときに取り込む」に変える。ブランチとリリースの文書の Dependabot の手順（1 つずつ更新して CI を待つ）を直す | [開発の進め方](../../rules/workflow.md) 第 5.7 節、ブランチとリリースの文書 | 文書を読む |

- 経路で job を省く方法を選ばない理由：必須の検査の job を経路で省くと、必須の検査が実行されず、状態が pending のままになり、マージできなくなる。job の中で条件を分ければ避けられるが、CI の構成を大きく変え、第 3 段の CI の job の分割と重なるため（GitHub の文書、2026-10-28）。
- merge queue を選ばない理由：個人のアカウントの repository で使えるかを、公式の文書で確認できなかった（2026-10-28）。「最新の develop を含む」を外せば待ちの主な原因がなくなるため、確認するための設定の変更をしない。
- 外したときの危険：マージの後に、別の pull request の変更との組み合わせで `develop` の CI が失敗しうる（GitHub の文書の注意）。DC-34・35 の見届けで扱う。

### 4.1 作業の種類の表（DC-37〜41）

[エージェントの作業フロー](../../rules/subagents.md) 第 3 節の表を、次の表に置き換える。モデルの列は区分で書き、実際のモデルと effort の値は AGENTS.md の表で決める。

| 資料を集める（判断しない） | 文書・Web の該当箇所を集めて要約する、事実の確認 | 軽量 | 低 | 固定の分を含めて 1 回の要求が上限（10 万 token）を超えない量。超えるときは範囲を分けるか、汎用にする |
| 機械的な作業 | 一覧の作成、grep の照合、同じ形の置き換え | 軽量 | 中 | 同上 |
| 実装 | タスクの実装 | 汎用 | 中 | 範囲を小さく分ける |
| `[リスク]` の実装 | 金額、セキュリティ、データの移行 | 高性能 | 高 | |

| 原因の調査 | 2 回修正して通らない失敗 | 高性能 | 高 | 調査役が 2 回で特定できないときは最上位（DC-42） |
| spec 担当のセッション | 設計の決定、判定、利用者との相談 | 高性能 | 中 | |
| issue 担当のセッション | 起票、資源の配分、低の変更のマージ、監視 | 汎用 | 中 | 危険度の判定に迷うときは利用者に聞く |

- DC-39：issue 担当のセッションを汎用にする案は、利用者に確認する（第 10 節の確認事項 1）。理由：今は高性能で動かしていて、待機と監視の token の多くがキャッシュ読みのため。汎用は単価が半分である。
- DC-42：最上位の区分の使う場面は、(1) 高性能の調査役が 2 回で原因を特定できないとき、(2) 利用者が指定したとき、の 2 つである。最上位を使えないプラン（2026-10-28 の時点で Pro）では使わず、高性能で代える。使えるプラン（Max）では、最上位の週の使用量が 50% を超えたら使わない。最上位の使用も 5 時間と週の使用量から引かれるので、DC-45 の閾値にも従う。能力・料金・上限は事実の確認の memo にあり、実装のときに AGENTS.md の注に出典を書く。
- DC-43：AGENTS.md の注 ※1 を「固定の分（system prompt とツールの定義など、約 4〜6 万 token）を含めて 10 万 token。実際に読める量は約 4 万 token」に直す。根拠は整理の前の基準の測定である（Haiku の最初の要求が 4.1〜5.7 万 token）。

### 4.2 作業の形と profile の決め方（DC-44〜47）

issue 担当のセッションが、セッションの始めと各 spec の起動のときに、プランと使用量を読んで決める。

| 条件 | 作業の形 | 実装の並行の数の上限 | profile |
|------|----------|----------------------|---------|
| 最上位を使えないプラン（Pro など） | 単線 | 1 | 標準 |
| 使えるプラン（Max など）、週の使用量 60% 未満 | 並行 | マシンの上限 | 厚め |
| 同、週 60〜80% | 並行 | マシンの上限から 1 を引いた数。最小は 1 | 標準 |
| 同、週 80% 以上 | 単線 | 1 | 節約 |

- マシンの上限は、マシンごとの環境の文書に書く。理由：同時に動かせる実装の数は、開発の機械の性能（CPU、メモリ、テストを同時に流せるか）で決まるため（利用者、2026-10-28）。環境の文書に書いていないときは 1 とする。規則には、この値を環境の文書に書くことだけを書き、値は書かない。
- spec の文書の段階（spec・plan・tasks を書く）のセッションは、並行の数に数えない。理由：文書の作業の使用量は、5 時間の使用量の数 % と小さいため。出典はマシンの環境の文書の記録である。
- 止める閾値（DC-45・46）：5 時間の使用量が、並行では 90%、単線では 97% を超えそうなら、spec 担当のセッションは新しいタスクに入らず、commit できる区切りで止まり、issue 担当のセッションに使用率と戻る時刻を報告する。issue 担当のセッションが、待つか、他の spec を止めるかを決める。週の使用量が 95% を超えたら、全ての spec 担当のセッションを区切りで止める。
- 使用量を読む頻度は、今のマシンの環境の文書の目安（セッションの始め、コードの作業は数タスクごと、70% 以上はタスクの前）を規則に移す（DC-47）。移した後、マシンの環境の文書は規則を指す 1 行にする。spec 247 が環境の文書を縮めるので、変える前に issue 担当のセッションに知らせる。
- profile をマシンの環境の文書で選ぶ今の規則（[エージェントの作業フロー](../../rules/subagents.md) 第 4 節）を、上の表で issue 担当が選ぶ形に変える。利用者が特例の profile を指定したときは、それに従う（DC-75）。
- 値（60%、80%、90%、97%、95%）は、本 spec のマージの後の最初の弾の測定（DC-66）で再検討する。

### 4.3 指示の言語（DC-48）

- サブエージェントへの指示とその説明（呼び出しの description を含む）は、日本語だけで書く。中国語の字を含む語を使わない。規則は[エージェントの作業フロー](../../rules/subagents.md) 第 3 節の運用の規則に置く。
- 方法：読むだけのレビュー役の定義（第 5 節）を使うと、プロジェクトの指示の文書と memory が文脈から外れ、それらからの混入もなくなる。memory の索引を日本語で書くことは、spec 249 が扱った。
