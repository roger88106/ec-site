# エージェントの作業フロー

エージェント（Claude Code など）がサブエージェントを使うときの規則。[開発の進め方](workflow.md)と [AGENTS.md](../../AGENTS.md) に従い、ここではサブエージェントへの任せ方だけを書く。

## 1. 調べた仕組み（2026-10-20 時点）

| 仕組み | バージョン | サブエージェントの使い方 |
|--------|------------|--------------------------|
| cc-sdd | v3 | `kiro-impl` が 1 タスクごとに新しい実装役を立て、TDD（レッド → グリーン）で実装させる。実装役にはタスクの要点だけを渡す。別の独立したレビュー役が、差分、TODO の残り、テストの全体、タスクの境界を確認する。実装役が止まったとき、またはレビューで 2 回差し戻されたときは、調査役が原因と修正方法を返す（最大 2 回）。タスクをまたぐ気づきは tasks の「Implementation Notes」に書き、後のタスクの実装役に渡す。実装は 1 つずつ順に行い、書き手を並行して動かすときは別の作業ツリーを使う。モデルの選び方の記述はない |
| superpowers（subagent-driven-development の skill） | main（2026-10） | 1 タスクごとに新しい実装役を立てる。実装役に渡すのは、タスクの全文、プロジェクトの 1 行の説明、前のタスクで決まったインターフェース、曖昧な点の決定、報告のファイルのパスだけ。計画の全体や会話の履歴は渡さない。実装役は詳しい報告をファイルに書き、状態・commit・テストの 1 行の要約・懸念だけを返す。1 人のレビュー役が、仕様との一致とコードの品質の 2 つの判定を出す。重大な指摘は修正させ、軽い指摘は記録だけにする。修正が 5 回で収まらなければ、制御役（メインのセッション）が裁定する。進み具合は台帳のファイルに書く ※1。実装役を並行して動かさない。モデルは常に明示し、機械的な作業は安価なモデル、複数ファイルの統合は標準、設計と最後のレビューは最も高性能なモデル、レビュー役は中位以上にする |
| Spec Kit | 最新（main） | `/speckit.implement` はサブエージェントを使わない。tasks を段階（Setup、Tests、Core、Integration、Polish）の順に実行し、段階ごとに確認する。`[P]` の付いたタスクは並列で実行できる（同じファイルを触るものは順に）。テストのタスクを実装より先に行う。独立したレビューの段階はない |
| OpenSpec | 最新（main） | `/opsx:apply` が tasks を順に実行し、`/opsx:verify`（任意）が実装と仕様の一致を確認する。サブエージェント、独立したレビュー、モデルの選び方の記述はない |

※1：会話の記憶は、文脈の圧縮で失われるため。

- Claude Code のサブエージェントは新しい文脈で始まり、親から渡るのは指示の文字列だけ（公式の文書）。必要なファイルのパス、決定、差分は、指示に明示して渡す。

## 2. 取り入れるもの・取り入れないもの

| 項目 | 判断 | 理由 |
|------|------|------|
| フレームワーク（Spec Kit、OpenSpec、cc-sdd）を導入する | 取り入れない。必要な形だけを借りる（2026-10-16 決定） | 安定の元がどれにも備わっておらず、導入しても同じ仕組みを自前で作ることになるため ※2 |
| 文書（spec・plan・tasks、設計の文書、手順の文書）の本文を、日本語の要点から日本語だけの文脈のサブエージェントに書かせる | 取り入れる。数行の修正はspec 担当のセッションが行い、言い換えの一覧の検査で確認する | 試した 4 回とも言い回しの修正が必要なかったため。spec 担当のセッションの文脈は利用者との会話の言語を含むので、そのまま書くと日本語でない語が混ざる。内容の質は要点の質で決まるので、spec 担当のセッションが内容を確認する |
| 既存の文書の言い回しのレビューに、目指す書き方の見本と、言い回しと論理の規則（skill `docs` の参照）を渡す | 取り入れる。和語の言い換えと、論理・比喩などの 2 つの観点を両方見るように指示する | 見本がないと、プロジェクトの用語を一般の語に替える案が混ざるため。規則がないと擬人化や口頭の語を見落とし、観点を 1 つしか書かないと、もう一方を見落とすため |
| 文書の検査に textlint を使う | 取り入れない | 技術文書のプリセットは和語の言い換えを見つけられず、用語の辞書は言い換えの一覧の検査と重なるため |
| レビューを、実装の過程を見ていないサブエージェントに任せる | 取り入れる | 作業したエージェント自身のレビューは、同じ見落としを繰り返すため。skill `review` で行う。時点は第 4 節 |
| 1 タスクごとにレビュー役を立てる | 取り入れない。`[リスク]` のタスクの後と、段階の最後、spec の最後などの決まった時点にレビューする（第 4 節） | 1 タスクごとに 2〜3 のサブエージェントを立てると、token が数倍になるため。タスクが細かく、`[テスト]` のタスクでレッドを確認しているので、`[リスク]` のタスク以外は段階ごとで足りる |
| 1 タスクごとに新しい実装役を立てる | 取り入れる。spec 担当のセッションはコードを書かず、実装は全て実装役が行う。`[テスト]` と対応する実装は 1 組で、同じ実装役が順に行う。設計の判断が必要なときは、実装役が止まって報告し、spec 担当のセッションが plan から判断する。文書にない設計の判断は、利用者に質問する（[開発の進め方](workflow.md) 第 5.3 節） | 文脈が長くなるほど 1 回の呼び出しが高くなるため。実装を外に出すと、spec 担当のセッションの文脈が膨らまない |
| 実装役に渡すもの | 取り入れる。渡すのは、タスクの全文、関係する plan の節、決まったインターフェース、曖昧な点の決定、報告の書き先。会話の履歴と計画の全体は渡さない | 公式の文書のとおり、渡るのは指示の文字列だけで、余分な文脈は token と誤りを増やすため |
| 結果の受け取り方 | 取り入れる。詳しい報告はファイル（`/.local/` の下）に書かせ、返すのは状態・commit・テストの要約・懸念だけにする | spec 担当のセッションの文脈を小さく保つため |
| 書き手を並行して動かさない | 取り入れる。同じ作業ツリーで、ファイルを書くサブエージェントを同時に動かさない。並行して動かすのは読むだけの作業か、別の作業ツリー | 変更が衝突するため |
| 2 回修正して通らなければ、原因の調査を分ける | 取り入れる。調査は調査役（高性能）が行う | 同じ修正方法を繰り返さないため（cc-sdd の調査役） |
| 気づきを後のタスクに渡す | 取り入れる。tasks のタスクの下に書く（今の書き方のまま） | 既に tasks の補足に書いているため |
| モデルを常に明示する | 取り入れる | 省くと spec 担当のセッションの高いモデルを引き継ぐため |
| 段階ごとの確認、テストを先に | 既にある | 開発の進め方と tasks の形に入っている |

※2：段階ごとの tasks、前提と完了条件、テストのレッド、文書が先、レビュー、AC とテスト名の検査のどれもが、フレームワークにはない。OpenSpec は要件に英語の SHALL・MUST を求め、日本語の文書と合わない。

## 3. 任せる作業とモデル

| 作業 | 例 | モデル | 条件 |
|------|----|--------|------|
| 機械的な作業 | 一覧の作成、grep の結果の照合、同じ形の置き換え | 軽量 | 指示と読む量の合計が 10 万 token を超えない作業に限る ※3 |
| 実装 | タスクの実装（実装役の既定） | 汎用 | 範囲を小さく分ける（1 つのサブエージェントのツールの呼び出しを数十回に収める） |
| `[リスク]` のタスクの実装 | 金額、セキュリティ、データの移行 | 高性能 | |
| 原因の調査 | 2 回修正して通らない失敗の原因 | 高性能（調査役） | |
| 判断が必要な作業 | 規則の当てはめ、一貫性の確認、文書の本文（日本語の要点から書く） | 汎用 | 範囲を小さく分ける |
| レビュー | 第 4 節の時点 | profile で決める（第 4 節の表） | |
| 設計の決定、判定、まとめ、利用者との相談 | | spec 担当のセッション | サブエージェントに任せない |

※3：軽量のモデルは、サービスによって指示の長さで単価が変わることがある。対応表の注を見る（[AGENTS.md](../../AGENTS.md) の「モデルの区分」）。

### 運用の規則

- サブエージェントの文脈は新しい。spec 担当のセッションが規則の要約と対象を指示に書いて渡し、各サブエージェントに原文の全体を読ませない。
- spec 担当のセッションは、サブエージェントの結果を 1 つずつ受けて作業を進めず、全部がそろってからまとめる。理由：結果を受けるたびに、spec 担当のセッションの長い文脈を処理し直すため。
- 語ごとの規則（和語の言い換えなど）は、語ごとに 1 回決め、機械（script）か文脈のサブエージェントで全体に適用する。行ごとのレビューで 1 件ずつ判断しない。理由：語の単位の問題は、どの回でも、どのモデルでも同じく挙がるため（下の実績）。
- 文脈で判断する候補（言い回し、論理）は、同じ範囲を汎用で 2 回実行して和集合を取り、高性能なモデルが採否を判断する。理由：1 回の実行で挙がるのは、3 回の和集合の 42〜78% で、回ごとに大きく変わるため。
- 並行して動かすサブエージェントの一時ファイルには、担当の範囲の名前を付ける（例：`judge-05-01.mjs`）。理由：同じ作業ツリーのスクラッチパッドを共有し、同じ名前のファイルを上書きするため。

### 実績

| 作業 | 条件 | 結果 |
|------|------|------|
| spec 010 の後の全体レビュー | 汎用、読むだけ | 6 つのサブエージェントで、合計約 162 万 token、ツールの呼び出し約 390 回。1 つあたり 6〜11 分 |
| plan 018 の本文 | 汎用、日本語の要点から書く | 約 13.5 万 token、ツール 14 回、約 2 分 |
| tasks 018 の本文 | 汎用、日本語の要点から書く | 約 12 万 token、ツール 12 回、約 1 分 20 秒 |
| 言い回しのレビューの安定度（spec 018 の段階 5） | 3 つの範囲（規範 658 行、手順 376 行、spec 002 の 540 行）を、同じ指示で 汎用 2 回と高性能 1 回、独立に実行 | 3 回とも挙がった候補は 15〜30%、1 回だけの候補は 50〜69%。和語の言い換えなど語の単位の問題は、毎回どのモデルでも確信度「高」で挙がった。高性能は汎用より 1〜4 割多く挙げたが、汎用との重なりの割合は高くなかった。1 回あたり 9〜15 万 token、1.5〜4 分。並行した 7 つの判定のうち 1 つが、同じ名前の一時ファイルの上書きを報告した |

測定は 2026-10 の Claude のモデルで行った（モデルの区分と実際のモデルの対応は [AGENTS.md](../../AGENTS.md)）。

- 1 つのサブエージェントで全体を見るより、範囲を分けたほうが安い。理由：文脈が長いほど 1 回の呼び出しが高くなるため。

## 4. 役割と作業の流れ

### 役割

| 役割 | 数 | 担当 |
|------|----|------|
| issue 担当のセッション | 1 つ | spec 担当のセッションの起動、実装の開始の指示、`release-` のブランチと `hotfix-` のブランチから `main` へのマージ（利用者の許可を得て行う）、`hotfix-` の後の `main` から `develop` への取り込み（利用者の許可を得て行う）、spec 担当のセッションが自分をアーカイブできないときの、そのセッションのアーカイブ（許可した利用者の言葉を添えた依頼を受けて行う） |
| spec 担当のセッション | spec ごと | spec・plan・tasks、サブエージェントへの指示、合格・不合格の判定、作業ブランチから `develop` へのマージ、後片付けの最後の、自分のセッションのアーカイブ（利用者の許可を得て行う） |
| 実装役・レビュー役・調査役のサブエージェント | 必要なとき | 実装役：タスクの実装。レビュー役：レビュー。調査役：失敗の原因の調査 |

- spec 担当のセッションは、コードを書かない。実装は実装役が行う（第 2 節）。
- spec 担当のセッションが書いてよいのは、数行の文書の修正だけである。
- 合格・不合格の判定は、spec 担当のセッションが行う。理由：サブエージェントに渡らなかった情報を持つのは、spec 担当のセッションだけのため。
- 実装役の既定のモデルは汎用、`[リスク]` のタスクは高性能、機械的な作業は軽量。調査役は高性能（第 3 節）。

### セッションの間のやり取り

- issue 担当のセッションが、spec 担当のセッションを起動する。
- issue 担当のセッションが実装の開始を指示するときは、[開発の進め方](workflow.md) 第 5.6 節の実装を始める前の照合を求める。
- セッションのアーカイブ（使うツールの機能で、セッションの一覧から外す）は、利用者の許可を得て、spec 担当のセッションが後片付けの最後に行う。spec 担当のセッションが自分をアーカイブできないときは、issue 担当のセッションが、許可した利用者の言葉を添えた依頼を受けてアーカイブする（[開発の進め方](workflow.md) 第 5.7 節）。
- 2 つのセッションは親子の関係にあり、ターンの終わりに親へ通知される。
- 記録は、追跡の issue のコメントに残す（開始、pull request、完了）。
- skill `handoff` は、spec 担当のセッションを途中で別のセッションに替えるときだけに使う。
- 利用者がチャットで指示すれば、エージェントはセッションを起動できる。

### タスクの実装

- `[P]` のタスクは、作業ツリーを分けた実装役が同時に実装する。`[P]` でないタスクは順に実装する。
- 作業ツリーでバックエンドや画面を動かす実装役は、始めに `node scripts/dev/slot.mjs assign` でスロットを割り当て、作業ツリーを削除する前に `release` する（skill `local-dev`）。
- 書き手を並行して動かすときは、第 2 節の「書き手を並行して動かさない」に従う。

### レビューの時点と profile

レビューの時点は、`[リスク]` のタスクの後、段階の最後、spec の最後、pull request の前、リリースの前である。判定は spec 担当のセッションが行う。

レビューの量は、profile（厚め・標準・節約）で決める。profile は、マシンと利用者ごとの環境の文書（`/.local/agent/environment.md`）で選ぶ。文書の既定は「標準」とする。

| 時点 | 厚め | 標準 | 節約 |
|------|------|------|------|
| `[リスク]` のタスクの後 | 高性能 | 汎用 | 行わない |
| 段階の最後：一般の観点 | 汎用を 2 回（和集合） | 汎用を 1 回 | 汎用を 1 回 |
| 段階の最後：重要な観点（金額、セキュリティ、`[リスク]`、ファイルをまたぐ影響） | 高性能と汎用（和集合） | 高性能を 1 回 | 汎用を 1 回 |
| spec の最後 | 段階の最後と同じ。ファイルをまたぐ影響の観点を必ず含める | 同左 | 同左 |
| pull request の前 | 高性能（spec との一致、完了の定義）と使うツールの組み込みのコードレビュー | 汎用と使うツールの組み込みのコードレビュー | 使うツールの組み込みのコードレビュー |
| リリースの前 | 高性能（マイグレーション、設定、互換性、リリースの説明の案） | 汎用 | 汎用 |

- 重要度は「高」「必須」「推奨」の 3 つ。定義は skill `review` の prompts.md の「重要度」。
- `[リスク]` のタスクの後と、段階の最後のレビューでは、レビュー役は「高」と「必須」だけを返す。
- spec の最後のレビューでは、「推奨」も返す。推奨には、機械の検査に移せるかを付ける。
- レビューごとに token、時間、指摘の数、採用した数を記録し、profile を再検討する材料にする。

### 並行

- 並行の単位は、spec 1 つに、セッション、作業ツリー、ブランチ、pull request を 1 つずつとする。
- 並行してよい条件は、次の 3 つを全て満たすこと。
  - モジュールが違う。
  - 契約や同じテーブルを同時に変えない。
  - 依存がない。
- 並行する spec の依存は、追跡の issue に書く。
- spec を分けるとき・spec を並行してよいと判断するときは、spec の範囲だけで決めず、両方の plan と tasks（規模 M は spec の tasks）の変えるファイルを照合してから決める。理由：spec 181 と 186 の分け方で、範囲だけで重ならないと判断したが、草案で重なりが 5 つ見つかったため（2026-10-24）。
- 照合の前（spec の段階）は、並行の可否を決めず、spec に「並行の可否は plan の段階（規模 M は tasks を書くとき）で決める」と書く。
- 照合の結果（重なるファイルと実装の順序）は、plan（規模 M は spec の tasks）に書く。
- 共有の文書（AC 一覧、用語集）の衝突は、後でマージする pull request が `develop` を取り込んで解消する。
