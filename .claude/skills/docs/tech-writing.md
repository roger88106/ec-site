# 文書の言い回しと論理の規則

文書を書く・レビューするときの、言い回しと論理の規則。出典は k16shikano 氏の `japanese-tech-writing`（SKILL.md、Unlicense、<https://gist.github.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d>）。書籍の原稿向けの規範から、表と短い文が中心のこのリポジトリの文書に当てはまる規則だけを抜き出して書き直した。[SKILL.md](SKILL.md) 第 2 節と食い違うときは、skill `docs` を優先する。

## 1. 論理

| 規則 | 避ける書き方 → 直した書き方 |
|------|------------------------------|
| 確かめていないことを断定しない。確かめてから書くか、未確認と書く | 「この設定が既定値である」（未確認）→ 値を確認して書く。未確認なら「未確認」と書く |
| 「かもしれない」「だろう」を機械的に消さない。残すのは、未確認の可能性、ログからの推定、読む人の疑念。消してよいのは、根拠なく主張を弱めているときと、文書内の根拠で確定しているとき | 「再試行されているかもしれない」（ログから推定）→ 「再試行されている可能性がある」。推定を「再試行されている」に変えない |
| 別のものを「同じ」とまとめない。別々の決定、原因、問題は分けて書く | 相互に依存する 3 つの未決事項を「同じ決定」と書く → 「どれも別の決定で、互いに依存している」 |
| 複数の要因がある事象を、1 つの原因にしない。要因ごとに、どの説明がどれに当たるかを対応づける | 「遅いのは N+1 のため」（インデックスの欠落もある）→ 「N+1 と、インデックスの欠落のため」 |
| 主張は、例が支える範囲に絞る | 「どのモジュールも同じ形」（2 つしか見ていない）→ 「catalog と cart は同じ形」 |
| 因果には、仕組みを 1 文で添える | 「キャッシュを使うと速い」→ 「キャッシュを使うと、同じ問い合わせの DB への往復が減るため速い」 |
| 「必ず」「すべて」「常に」は、条件を付けるか、確かめてから使う。検出・保証・解決を言い切らない | 「テストで必ず検出できる」→ 「テストが対象の経路を通るときに検出できる」 |
| 「A ではない」と書くときは、否定する内容を正確に書き、根拠を 1 文添える。読み違えそうな解釈を先に退ける | 「すべてを任せるわけではない」→ 「設計の決定は任せない。判断の根拠が文書に残らないため」 |
| 「ただし」「とはいえ」を置いたら、その後で論を進める | 例外を書いて終わる → 例外の扱いまで書く |
| 「次節で扱う」「後の spec で行う」と書いた論点は、実際にそこにあることを確かめる。ないなら TODO 一覧に足す | 回収されない先送り → 行き先を指す |
| 同じ概念の分類と定義は、文書全体で揃える | ある節で「利用者が決める」と分けたものを、別の節で「エージェントが決める」と書く |
| 複数の概念を上位の語でまとめるときは、同じものに帰着する理由を、命名の直前に 1 文書く | 突然「境界」と呼ぶ → 「どれも依存の向きを決めるため、境界と呼ぶ」 |
| 確認していない作業を、済んだように書かない | 「全体を検査した」（一部だけ）→ 「catalog だけ検査した」 |
| 理由は、文書やコミットメッセージにあるものだけを書く | 推測の理由を書かない。利用者に聞く（skill `docs` 第 2 節「事実」） |

## 2. 読む人の負担

| 規則 | 避ける書き方 → 直した書き方 |
|------|------------------------------|
| 後で使わない固有名（ファイル名、関数名）を出さない。一般的な言い方で済ませる | 「`FooBar.java` のような仕組み」（以後出ない）→ 「同種の仕組み」 |
| 節の問いや結論に関係しない細部（時刻、ステータスコード、率）を入れない。議論に必要な具体は残す | 例に実行時刻と HTTP の全ヘッダーを書く → 結果と原因だけ書く |
| 新しい概念は、先に種類（部品、手順、制約）を書いてから、性質を書く | 「テストで固定できる `Clock` を注入する」→ 「`Clock` は現在時刻を返す部品。テストで固定するため、注入する」 |
| 節の中心になる語は、使う前に定義するか、定義の節を指す | 第 1 節で「窓口」を使い、定義が第 4 節 → 初出で定義する |
| 指す内容が文脈で決まらない言い回しは、括弧で特定する | 「この方式」→ 「この方式（ポーリング）」 |
| 新しい例を足すときは、前の例との違いと、足す理由を先に書く | 似た例を理由なく並べる → 「前の例は同期、次は非同期」 |
| 表・コード・図は、それぞれ別の説明を担わせる。1 つで確かめた性質を、別の例にそのまま当てはめない | 表に値、コードに手順 |
| 表のセルに、複数の話題を入れない | 理由と例外と手順を詰める → 理由は `※1` に出す |
| 1 文に主張を 1 つにする。短く切る | 「〜であり、〜のため、〜となるが、〜」→ 文を分ける |
| 見出しは、節が答える問いか、扱う対象を指す句にする。手順だけ、または結論を言い切る見出しにしない | 「進め方のまとめ」「重要な点」→ 「サブエージェントへの任せ方」 |

## 3. 用語

| 規則 | 避ける書き方 → 直した書き方 |
|------|------------------------------|
| 定義した語は、言い換えずに使い続ける。曖昧な語に戻さない | 「注文」「オーダー」「購入」を混ぜる → 用語集の「注文」に統一 |
| 分野で慣用されている語を選ぶ。近い意味の漢語を、一般語の感覚で当てない | プッシュ通知の「配送」→ 「配信」 |
| 技術文書で一般的な語を使い、和語で言い換えない（このリポジトリで追加した規則） | 「確かめる」「流す」「照らす」「見直し」「待つ時間の上限」「〜の口」→ 「確認する」「実行する」「照合する」「レビュー」「タイムアウト」「エンドポイント」 |
| 指す対象が決まっているときは、広い語でぼかさず、名前を書く | 「ツールで検査する」→ 「`doc-refs.mjs` で検査する」 |
| 抽象的な名詞でなく、具体的な名詞を使う | 「処理を行う」→ 「在庫を引き当てる」 |
| 1 つの語を 2 つの意味に使わない。術語を、術語でない場面に流用しない | 「層」をパッケージとレイヤーの両方に使う → 一方は「パッケージ」 |
| 言い換えの一覧と、漢字・かなの書き分けは `scripts/ci/doc-terms.json` に従う | 検査が出した語を直す |

## 4. 避ける言い回し

### 4.1 中身のない言い回し

| 規則 | 避ける書き方 → 直した書き方 |
|------|------------------------------|
| 予告と総括を書かない | 「本節では認証を扱う」「ここでは〜を見ていく」「要するに」「〜に他ならない」→ 削って、内容をすぐ書く |
| 「重要なのは〜である」の前置きで主張を予告しない | 「重要なのは、ID を渡すことである」→ 「ID を渡す」 |
| 姿勢だけを宣言する語を使わない | 「正面から扱う」「正面から回収する」→ 「扱う」「ここで回収する」 |
| 中身のない形容と強調を書かない | 「非常に重要な」「不可欠」「核心的」「根本的な」「適切に」→ 何がどうなるかを書く |
| 何をしたかを示さない動詞を書かない | 「掘り下げる」「言語化する」「言及する」「多角的に分析する」→ 実際の作業を書く（「3 つの観点で照合する」） |
| 新しい情報のない接続を書かない | 「〜の観点から」「〜において」、「さらに」「また」「加えて」の連打 → 削る |
| 評価だけの文を書かない | 「これにより、より堅牢になる」→ 防げるものを書く（「二重登録を防ぐ」） |
| 読む人との問答の形にしない。読む人の反応を演じる形も避ける | 「では、どうすればよいか。〜」「〜と感じたかもしれない。そのとおりである」→ 答えだけ書く |
| 「〜という発想である」のような枠取りで、考えを紹介しない | その考えを直接書く |
| 著者の立場の弁明を書かない | 「本書もそれを否定しない」→ 事実だけ書く |
| 飾りの強調（太字、感嘆符）や、危険を煽る列挙を使わない | 「**絶対に**変更しない！」→ 理由を添えて「変更しない（Flyway の checksum が変わるため）」 |

### 4.2 翻訳調の比喩と擬人化

| 規則 | 避ける書き方 → 直した書き方 |
|------|------------------------------|
| 英語の比喩を直訳しない（carry、open、expose、live など） | 「ベクトルが選好を運ぶ」「この問いは開かれている」「責務が露出する」→ 「ベクトルに選好が反映される」「この問いにはまだ答えが出ていない」「責務が公開 API に出ている」 |
| 無生物を主語にして、人の動作をさせない | 「データが語るのは〜」「モデルは文体を知っている」→ 「データから分かるのは〜」「出力には文体の一貫性がある」 |
| 口頭の技術議論の語を書かない | 「テストが効く」「この設計は筋がいい」→ 「テストで回帰を検出できる」「この設計は〜のため有望である」 |
| 判定：字義どおりの動作を想像できる述語は疑う。主体と対象を具体語で言い直せるなら、言い直しを書く | 言い直せない表現は、指す内容が決まっていない。削るか、内容を確定させて書き直す |
| イ形容詞に「です」を付けた文で終えない。文末だけ直さず、前後の流れごと書き直す | 「これは難しいです」→ 「〜のため難しく、〜する」 |

## 5. 冗長さ

| 規則 | 避ける書き方 → 直した書き方 |
|------|------------------------------|
| 同じ主張を言い換えて繰り返さない。加える内容が違う文は、繰り返しではない | 「X は不要。つまり X を置かない」→ 「X は置かない」 |
| 同じ意味を 2 か所に書かない。役割が重なる節は 1 つにまとめる | 重複する節 → 1 か所に書き、他は指す（skill `docs` 第 1 節） |
| 表を示した直後に、同じ内容を文で要約しない | 表の下に「以上のとおり〜」→ 削る |
| 論理の役割が同じ並列の事実は、1 文にまとめる | 「A は X。B も X。C も X。」→ 「A、B、C はどれも X」 |
| 接続や評価のためだけの文を置かない | 「それでは次に見ていく」「それ自体はよい」→ 削る |
| まだ導入していない概念や文書名を、先回りして出さない | 第 2 節で第 5 節の語を使う → 第 5 節で出す |
| 本文内の根拠で確定していることは、弱い述語にせず言い切る | 「〜が有効と考えられる」（確認済み）→ 「〜が必要」 |
| 冗長な語尾を短くする | 「〜することができる」「〜を行う」→ 「〜できる」「〜する」 |
| 字数を減らすために、動機・対象・因果・条件を読む人の推論に任せない | 「X のため Y」の「X のため」を削って意味が通らなくなる → 残す |

## 6. 使わない規則

次の規則は、散文の書籍向けのため、この文書には載せない。

| 種類 | 理由 |
|------|------|
| 段落の構成（1 段落 1 主題、段落の先頭の接続表現、結論を 1 度だけ置く、前方参照の位置） | 表と箇条書きが中心で、長い段落がないため |
| 対比の定義の述部をそろえる、譲歩の書き方、山場の情報を先出ししない | 長い論証の文章の規則で、表では起こらないため |
| 演出の節度（溜め、短い決め台詞の段落、太字の使い方、対句、転回点） | 表と短い文には、演出がもともとないため。飾りの強調だけ 4.1 に載せた |
| 命令調（「〜してはならない」）を避ける | 規則の文書は、規則を命令の形で書くため |
| 例の組み立て（架空の人物を置かない、行為者を主語にする、「あなた」と呼ばない） | 例は、このリポジトリの実際のクラスやコマンドで書くため |
| 人名の原綴り、読者への誠実さ（作為的な例の弁明） | 人名と作為的な例が、このリポジトリの文書にはほとんどないため。確認していないことを書かない規則は 1 に載せた |

## 7. 使い方

| 場面 | すること |
|------|----------|
| 文書を書く | 書き終えたら、1〜5 の表を 1 行ずつ当てはめる |
| サブエージェントに本文を書かせる | 指示に本書を読ませる。要点は日本語だけで渡す |
| 言い回しのレビュー | skill `review` の文書のレビューに、本書を規則として渡す |
| 規則どうしが食い違う | skill `docs` 第 2 節を優先する |
