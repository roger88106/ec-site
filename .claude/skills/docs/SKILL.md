# 文書を書く・修正する

文書の地図は [constitution](../../../docs/constitution.md) 第 3 節。文書は利用者と話して決め、エージェントが書く。

## 1. 置き場所

| 置き場所 | 書くもの |
|----------|----------|
| `docs/constitution.md` | 大綱と文書の地図。各節は 1 文、要点（3 つまで）、「細則は〜」の案内だけ |
| `docs/rules/` | 規範：開発の進め方、記号と番号、レビュー、コメントの書き方、エージェントの作業フロー、バックエンド・フロント・テストの書き方、API の規約 |
| `docs/design/` | 今の設計：全体構成、バックエンド・フロントのアーキテクチャ、`modules/<モジュール>.md`・`apps/<アプリ>.md`、共通コード、ロールと権限、AC 一覧、用語集、ライセンス |
| `docs/guides/` | 手順：開発環境の起動、環境変数、CI の検査、テストの実行方法 |
| `docs/specs/` | spec・plan・tasks（当時の記録）と MVP の完成までの一覧。書き方は [開発の進め方](../../../docs/rules/workflow.md) 第 1.4 節 |
| `docs/todo.md` | TODO 一覧（後回しにする作業と未決事項） |
| `README.md` | 概要、起動とテストへの案内、進捗だけ。文書は constitution へ案内する |
| `AGENTS.md`・skill | エージェントに固有の手順だけ。規則は docs/ を指す |

- `docs/` の直下には constitution、TODO 一覧とフォルダーだけを置く。文書を追加したら constitution の文書の地図にも記載する。
- 同じ意味は 1 か所に書き、ほかは指す。

## 2. 書き方

- **表を先に**：決まり・対応・比べるものは表にする。長い理由と例外は、表の中に `※1`、表の下に `※1：…` と書く。
- **書き方の規則の文書**（`coding.md` など）：冒頭に「規則の一覧」（節、規則、確認方法）、各節は規則と `理由：〜ため。` の 1 行（[書き方の規則とレビュー](../../../docs/rules/review.md) 第 1 節）。
- **今の設計の文書**（`modules/`・`apps/`）：冒頭に概要の表（レベル、依存、関連 spec とそのリンク）。本文には spec・plan・tasks の番号（AC-、BR-、plan の節など）を書かず、規則を言葉で書く。
- **参照**：文書の名前と節で書く（`店舗画面の構成 第 4.5 節`、`バックエンドのアーキテクチャ 第 6.1 節`）。constitution の節の番号ではなく、細則の文書を指す。Markdown ではリンクにする。
- **用語**：複合語とカタカナ語で短く書き、「の」を重ねない（ログイン画面、ライセンス検査、有料版、ツール、ライブラリ）。言い換える語の一覧は `scripts/ci/doc-terms.json`（ng は CI で失敗、caution は文脈で決める）。「他の」「必要」と漢字で書く。日本語だけで書く。
- **技術文書の語**：和語より、技術文書で一般的な語を使う（確認する、レビュー、実行する、追加する、修正する、削除する、照合する、再作成する、必要、手動で、エンドポイント）。「〜し直す」は「再〜」（再試行、再取得、再起動）にする。業務の用語（用語集の「写し」「取消」など）は言い換えない。
- **書面語**：口語的な言い方より、書面語で明確に書く。少し長くなっても、意味がはっきりするほうを選ぶ（「何もせず成功を返す」→「状態を変えずに成功を返す」、「差分で探す」→「差分で特定する」）。かなが長く続いて読みにくいときは、漢字の語を使う（全て、再度）。「こと」「とき」「ため」などの形式名詞は、かなで書く。
- **言い回しと論理**：推測を断定にしない、中身のない言い回しや翻訳調の比喩を書かない、などの規則は [文書の言い回しと論理の規則](tech-writing.md)。書き終えたら、その表を当てはめる。
- **事実**：設定の値、既定値、必須かどうか、クラスの名前は、コードと照合してから書く。理由が文書にもコミットメッセージにもないときは、推測で書かず利用者に聞く。

## 3. 進め方

1. 範囲と形を利用者と決める。大きな整理は、先に計画（置き場所、節の構成、移す先）を示して確認する。
2. 書く。1 つの文書か、まとまりごとに利用者に見せ、指示があるまで commit しない。
   - 新しい文書と、節を追加するような大きな修正：決定・事実・参照を日本語の要点（箇条書きと表）にまとめ、日本語だけの文脈のサブエージェント（Sonnet）に本文を書かせる。指示も日本語だけで書き、要点・対象の spec・本 skill・見本の文書だけを読ませる。メインのセッションは本文の内容を要点と照合する（[エージェントの作業フロー](../../../docs/rules/subagents.md) 第 2 節）。
   - 数行の修正：メインのセッションが修正し、手順 4 の検査で確認する。
   - 既存の文書の言い回しのレビュー：skill `review` の文書のレビューの手順（見本を渡す）で行う。
3. 文書を移した、節の番号や見出しを変えたときは、第 4 節で参照を修正する。
4. 確認する。次が全て通ること：
   - `node scripts/ci/doc-refs.mjs`（Markdown のリンクと、`<文書の名前> 第 N 節` の参照。CI の docs.yml でも実行する）
   - `node scripts/ci/doc-terms.mjs` と `--caution`（使わない語と、文脈で言い換える語。caution で出た語は、言い換えたほうが読みやすければ修正する）
   - コードのコメントを修正したら、フロントは `pnpm lint`、バックエンドは `./gradlew check`
5. commit を分ける：文書のまとまりごとに 1 つ、参照の修正は最後に 1 つ。spec の外の作業はタスク番号を付けない。push は利用者の許可を得てから。

## 4. 参照の修正

| 参照 | 修正方法 |
|------|--------|
| Markdown のリンク | `node .claude/skills/docs/fix-links.cjs 旧パス=新パス ...`（切れたリンクだけを、移した先に修正する） |
| コード・skill・CI・script・文書の本文の中のパス（リンクでないもの） | `node .claude/skills/docs/replace-paths.cjs 旧パス=新パス ...`（適用済みのマイグレーションと seed、テストのデータ、アーカイブを除外する）。その場で置き換えの script を書かない。置き換えた後に `git grep` で旧パスが残らないことを確認する |
| 節の番号（`<文書の名前> 第 N 節`） | 旧番号から新番号への表を作って置き換え、置き換えた行を再確認する。番号が 2 回付け替わらないよう、1 回で置き換える。`doc-refs.mjs` は、ない節を指す参照だけを見つける（番号が残っていて意味の違う節を指すものは見つけない） |
| 見出しの名前（`「他のモジュールへの公開」` など） | 見出しを変えたら、`git grep` で引用を探して修正する |

- 適用済みのマイグレーションと seed の SQL は修正しない（Flyway の checksum が変わり、既存の DB で起動に失敗する）。
- `docs/specs/` の完了した文書は、リンクのパスだけを修正する（開発の進め方 第 1.4 節）。
- コードが多く引用している文書の名前（`管理画面の構成` など）は、見出しを変えずに残す。
