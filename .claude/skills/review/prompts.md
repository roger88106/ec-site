# レビューの観点と指示のひな形

[SKILL.md](SKILL.md) の手順 3 から読む。手順 7・8 のひな形は [docs-review.md](docs-review.md)。

## 観点の一覧

| 観点 | 見ること | 主な根拠 |
|------|----------|----------|
| 規則 | チェックリストの確認方法が「レビュー」の規則に合うか | 書き方の規則の各文書 |
| 一貫性 | 同じことを、モジュール・spec によって違う書き方にしていないか（名前、エラーの扱い、画面の作り、テストの書き方） | 書き方の規則、既存のコード |
| 重複と抽象 | モジュール間の似たコード、共有パッケージに置くべきもの、反対に過ぎた抽象 | バックエンドの書き方の「共通の型」、フロントの書き方の「共有パッケージ」 |
| 境界と依存 | モジュールの `api`・`event` の外に触れていないか、腐敗防止層、循環、共有の中身 | バックエンドのアーキテクチャ、ArchUnit・Modulith |
| 文書とコード | spec・設計の文書・OpenAPI・用語集とコードが一致するか、古い記述とリンク切れ。食い違ったら、コードを正として文書の修正を提案する ※1 | 開発の進め方 |
| テスト | AC に対応するテストの抜け、弱い確認、重複した・壊れやすいテスト | テストの書き方 |
| 安定性と運用 | エラーの扱い、ログ、設定、トランザクションと並行、外部サービスの失敗、セキュリティ、性能 | バックエンドのアーキテクチャ、フロントの書き方 |
| 段階をまたぐ影響 | 段階ごとに通ったものが、段階をまたいで合うか（前の段階で作った script や skill の使われ方、順序、重複） | spec・plan の段階の分け、tasks の各段階の結果 |
| spec との一致 | spec の各 AC・DC・DN と plan の決定が、コードと文書で満たされているか | spec、plan |
| ファイルをまたぐ影響 | 値や制約を変えたとき、同じ値と制約を持つ箇所が全て変わったか（DB の制約、他の AC のテスト、文言） | spec・plan の変更点、変えた値の全文検索 |
| 削った文の行き先 | 削った文ごとに、行き先（移した先、正本）があるか。規則や条件が変わっていないか ※2 | 差分の削除行、※2 の表 |
| 不要なもの | 使われていないコード・依存、TODO・暫定の処理、残った設定 | なし |
| 後の開発への備え | 初めて読む人（エージェント）に分かるか、機能を追加するときの拡張の場所 | なし |

※1：自動の検査がない次の文書は、関わるコードを変えたら必ず照合する。
- モジュールの設計（`docs/02-設計/<モジュール>.md`）の「パッケージの構成」
- 共通コード・ログ・可観測性（`common/`、`config/`、ログと運用の設定）
- API の規約の URL の規則（契約のパス）

※2：「正本にある」として文を削るときは、削った実装役かセッションが次の表を報告に含める。セッションが削るときは、pull request の本文に含める。

| 削った文（ファイル:行） | 正本（ファイル:行） | 正本の文 |
|-------------------------|---------------------|----------|

## 指示のひな形（観点ごと）

レビュー役は前面で呼び、結果の token と時間を受け取る。背景で動いて値が返らなかったときは、記録の表に「—」と書き、表の下に理由を書く。

日本語だけで書く。次の形にする。

```
あなたは、<リポジトリ> のコードと文書のレビュー担当です。実装の過程は知らされていません。

## 対象
<対象のファイルの一覧のパス、差分のファイルのパス、または範囲>

## 観点
<観点の名前と、見ること>

## 根拠
- チェックリスト：<パス>（この観点に関係する部分）
- spec：<パス>、plan：<パス>
- 採らなかった指摘の一覧：<`rejected.md` のパス。なければ省く>
- <観点の主な根拠の文書のパス>

## 結果
<結果の書き先> に、次の表で書く。
| 重要度（高・必須・推奨） | 由来（今回・既存） | 場所（ファイル:行） | 指摘 | 根拠（文書と節、または DC・AC） | 修正案 | 機械の検査に移せるか |

- 重要度の定義と、返す重要度は、[書き方の規則とレビュー](../../../docs/05-開発規則/review.md)の「重要度」のとおり。指示に、この時点で返す重要度（「高」「必須」だけか、「推奨」も含めるか）を書く。
- この一覧の指摘は返さない（採らなかった指摘の一覧）。
- 好みの範囲の指摘は挙げない。根拠を示せない指摘は挙げない。
- 誤りの防止（誤って書いたものを拒否する判定）の spec では、意図して作った回避の形を重要度「高」にしない。回避の防止の spec（DC に書いてある）では、回避の形も返す。
- 根拠と理由には出典（ファイル:行）を書く。出典のない理由は書かない。
- 結果の書き先の外には書かない。返すのは重要度ごとの件数（「高」「必須」「推奨」）だけ。
```
