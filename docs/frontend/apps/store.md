# 店舗画面（`frontend/store`）の構成

C 側（消費者）の画面。Next.js（App Router）で、店舗 API（`store.yaml`）をサーバーコンポーネントとサーバーアクションから呼ぶ（ブラウザから API は呼ばない）。管理画面との違いと共通の決まりは [フロントのアーキテクチャ](../architecture.md)。新しい画面は第 8 節の手順で作る。

## 1. 技術

| 用途 | 採用 | 補足 |
|------|------|------|
| フレームワーク | Next.js（App Router） | 画面はサーバーコンポーネント、操作のある部分だけクライアントコンポーネント |
| API | openapi-fetch | 取得はサーバーコンポーネント、変更はサーバーアクションから呼ぶ |
| キャッシュ | Next.js の fetch のキャッシュ | 最大 60 秒。会員の token を付けて呼ぶ API はキャッシュしない |
| ログイン | Auth.js（`next-auth` v5）の Keycloak の provider | セッションは暗号化した Cookie（JWT 方式）。token はサーバーだけで扱う |
| 文言 | next-intl | サーバーの設定は `src/i18n/request.ts` |
| UI・lint | shadcn/ui、Tailwind CSS、lucide-react、Biome | 管理画面と同じ |
| テスト | Vitest | 関数、表示のコンポーネント、サーバーの処理 |

## 2. ディレクトリ

```
frontend/store/
├── messages/ja.json          # 文言
└── src/
    ├── instrumentation.ts    # 起動時に、本番で必須の環境変数を確かめる
    ├── proxy.ts              # 要求ごとにセッションを確かめ、token を更新して Cookie に書く。今の画面のパスを知らせる
    ├── app/                  # ルート（取得とコンポーネントの組み立てだけ）
    │   ├── api/auth/         # Auth.js の口（IdP からの戻り先など）
    │   └── login/            # ログイン・会員登録（IdP）へ移る口
    ├── actions/              # サーバーアクション。資源ごとに 1 ファイル（cart、checkout、order、auth）と、包みと会員の操作の補助
    ├── auth/                 # ログイン（設定とセッション、環境変数、token の更新、ログアウト）。第 9 節
    ├── api/
    │   ├── generated/        # store.yaml から生成（型と、入力の制約の定数）
    │   ├── client.ts         # クライアント。公開の口と会員の口（サーバー専用）
    │   ├── cartCookie.ts     # カート ID と、カートを移した知らせの Cookie（サーバー専用）
    │   ├── cart.ts           # 使うカートを選ぶ（サーバー専用）
    │   └── types.ts          # 画面から使う型の別名
    ├── components/           # 機能をまたぐコンポーネント（価格、ページング、ヘッダーなど）。ui/ は shadcn/ui
    ├── i18n/                 # next-intl の設定、合わせ方、キーの型、コンポーネントの外で引く translate
    ├── lib/                  # 画面に依存しない関数（単体テストを横に置く）
    │   ├── labels.ts         # 2 つ以上の機能で使う列挙の表示名（1 つの機能だけなら features/<機能>/labels.ts）
    │   ├── searchParams.ts   # URL のクエリの読み取り（配列の最初、ページ番号、型）
    │   ├── format.ts         # 価格をコンポーネントで分けて出す書式（金額・日時などの整形は共有パッケージの lib/format.ts）
    │   └── actionResult.ts   # サーバーアクションの結果の型と、API のエラーからの変換
    ├── test/                 # テストの土台（画面のコードからは import しない）
    └── features/<機能>/      # catalog、cart、checkout、order
        ├── components/       # その機能だけのコンポーネント
        └── *.ts              # その機能だけの関数・型
```

- 画面のコンポーネントは `features/` に置き、`page.tsx` は薄く保つ（`app/` の置き場所は Next.js が決めるため）。
- クライアントコンポーネント（`'use client'`）は、操作のあるコンポーネント（バリアントの選択、絞り込み、フォームなど）だけにし、API ではなくサーバーアクションを呼ぶ。
- サーバーアクションは複数の機能から呼ぶので、`features/` ではなく `actions/` に置く。

## 3. 画面の URL

Next.js の `typedRoutes` で、画面の置き場所と照らす。クエリ付きの URL は機能の `*Query.ts` の関数で作る。

| URL | 画面 | ログイン |
|-----|------|----------|
| `/` | トップ（カテゴリの一覧と新着の商品） | — |
| `/products` | 商品一覧（クエリ：`categoryId`、`minPrice`、`maxPrice`、`sort`、`page`） | — |
| `/search` | 検索結果（クエリ：`q`、`page`） | — |
| `/products/[productId]` | 商品の詳細（カートに入れる） | — |
| `/cart` | カート（カート ID は Cookie に持ち、URL に入れない） | — |
| `/checkout/[checkoutId]` | 注文手続き（確認と、お届け先の入力。メールアドレスは会員のものを示すだけ）。成立済みなら注文へ移る | 必要 |
| `/orders` | 注文一覧（新しい順、クエリ：`page`） | 必要 |
| `/orders/[orderId]` | 注文（照会、支払、キャンセルの申請）。注文した会員だけ。支払の画面から戻る先（クエリ：`payment=returned`） | 必要 |
| `/login` | 画面ではなく、IdP へ移る口（クエリ：`returnTo` 戻る画面、`register` 会員登録） | — |

- URL は商品 ID で作り、品番は使わない。
- 絞り込み・並び順・ページは URL のクエリに持ち、フォームの GET で送る。
- 表示されない・存在しない・ID の形が違う商品、存在しない・他人の注文手続きと注文は、どれも「見つかりません」（404）※1。

※1：Next.js 16 では、要求のたびに作る画面で 404 にすると、サーバーは状態 404 と枠だけを返し、中身はブラウザの JavaScript が出す。

## 4. API の呼び出し

- サーバーコンポーネントで `const api = await getApi()` としてから `api.GET('<パス>', ...)` で呼ぶ。クライアントは `server-only` にし、ブラウザのバンドルに入れない。
- `getApi` は画面を要求のたびに作るようにする（ビルド時に API を呼ばない）。
- 接続先は `STORE_API_BASE_URL`（既定 `http://localhost:8080/api/store`。既定は開発モードとテストだけ）。

### 4.1 キャッシュ

| 取得 | キャッシュ |
|------|------------|
| 一覧・検索・カテゴリ | 最大 60 秒（`STORE_API_REVALIDATE_SECONDS` で変えられる。E2E で短くするため） |
| 商品の詳細 | 使わない（`UNCACHED`）※2 |
| カート・注文手続き・注文 | 使わない（操作のたびに変わるため） |
| 会員の token を付ける API | 使わない（`cache: 'no-store'`。会員ごとの結果を共有のキャッシュに載せないため） |

※2：Next.js のキャッシュは、取り直した応答が 404 だと古い 200 を置き換えないので、非公開にした商品がいつまでも表示されてしまうため。

### 4.2 エラー

| 応答 | 扱い |
|------|------|
| 404 | `notFound()`。ただしカートの 404（Cookie のカートがもうない）は空のカートとして表示する |
| 401 | ログイン画面へ移す（第 9 節） |
| それ以外 | エラーの画面（`error.tsx`） |

- 待つ時間の上限：店舗 API の口（公開の口と会員の口）は、要求の middleware で上限の signal を付ける（`STORE_API_TIMEOUT_SECONDS`、既定 30 秒）。上限を過ぎた要求は例外で失敗し、サーバーアクションでは接続できないときと同じ結果になる。既定は、バックエンドで最も長く待つ操作（支払画面を開く）より長くする（短いと、バックエンドが成功しても画面は失敗を出す）。
- 5xx のログ：店舗 API が 5xx を返したら、応答の middleware で warn のログに状態コード、エラーコード、メソッド、API の定義のパス（`/orders/{orderId}` の形）を出す。token、Cookie、要求の本文、クエリ（メールアドレスなどを含みうる）は出さない。エラーコードは、呼んだ側が本文を読めるよう、応答を複製して読む。

### 4.3 サーバーアクション

- 変更（カートに入れる、数量の変更・削除、注文手続きに進む、注文、支払う、キャンセルの申請）は、`actions/` のサーバーアクションから呼ぶ。
- 成功したら、表示し直す画面を `revalidatePath` で知らせるか、次の画面へ `redirect` する。失敗は例外にせず `ActionResult` で返す（401 はログイン画面へ移す）。
- 会員の API の 401 と成功の後の移動は、`actions/memberAction.ts` の補助で書く。
  - `redirectIfUnauthenticated(response, returnTo?)`：応答が 401 ならログイン画面へ移す。戻り先を渡さなければ、いまの画面に戻る。
  - `redirectOnSuccess(work)`：`withActionResult` で包み、処理が返した移動先へ移る。失敗の結果はそのまま返す（`redirect` を包みの外で呼ぶ形を 1 か所にする）。
- `withActionResult` が例外を結果にするときは、画面の移動・not found を通した後、error のログに例外の名前とメッセージを出す（要求の本文や token は出さない）。
- フォームは `useActionState` で結果を受け、送信中はボタンを押せなくする（二重送信の防止。API も、同じ注文手続きの再送には作成済みの注文を返す）。

### 4.4 カート ID の Cookie

- カート ID は Cookie `cart_id`（`HttpOnly`、`SameSite=Lax`、`Path=/`、本番は `Secure`）。有効期限 30 日で、変更のたびに延ばす。
- 読み書きは `api/cartCookie.ts` だけ。読むのはサーバーコンポーネントとサーバーアクション、書くのはサーバーアクションだけ（サーバーコンポーネントは Cookie を書けないため）。
- Cookie がない・形が違うなら、カートがないものとする。「カートに入れる」のときにカートを作って Cookie に書く。
- 変更の API が 404（カートがもうない）なら、カートを作り直して 1 回だけやり直す。

### 4.5 使うカートの選び方

| 状態 | 使うカート |
|------|------------|
| ログインしていない | Cookie のカート ID |
| ログインしている | `GET /me/cart` の ID（Cookie のカート ID は使わない） |

選ぶ処理は `api/cart.ts` だけに置き、判定は `lib/` の関数にして単体テストを書く。

- **ログインの直後にカートを移す**：IdP から戻ったとき（Auth.js の `signIn` のイベント）に、Cookie にカート ID があれば、その内容を取ってから `POST /me/cart/merge` を呼び、Cookie のカート ID を消す（移せなくても消す ※3）。
- 切り詰めた品目と移せなかった品目があれば、商品名・バリアント・数量を知らせの Cookie（`cart_merge_notice`）に書く。カートの画面が一度だけ知らせ、表示したら消す（知らせのコンポーネントから、消すためのサーバーアクションを呼ぶ）。Cookie の大きさを抑えるため、品目はそれぞれ 10 まで、残りは数だけ。
- ログアウトでは Cookie のカート ID も消す。

※3：ログインしている間は使わないので、残すとログアウトの後に古いカートが見えてしまうため。

### 4.6 会員の token を付けて呼ぶ

| 呼ぶもの | 口 |
|----------|----|
| 会員の操作（`/me/**`、会員のカート、注文手続き、注文） | `getMemberApi()`。セッションの access token を `Authorization` に付け、キャッシュしない |
| 公開の情報（商品・カテゴリ・店舗の情報） | `getApi()`。ログインしていても token なしで、キャッシュを使う |
| ログインしていなくても使える操作（Cookie のカート） | `getApi()`。カートの取得は `UNCACHED` |

### 4.7 支払の画面への移動と戻り

| 場面 | 動き |
|------|------|
| 注文の成立 | 支払の画面の URL を API で求め、決済サービスの画面（外部の URL）へ `redirect` する。得られなければ注文の画面へ移る |
| 注文の画面の「支払う」 | 同じ API で URL を求めて移る。支払えなければ（支払済み、期限の後）メッセージを示す |
| 支払の画面から戻る | 戻る先はバックエンドの設定（`ECSITE_PAYMENT_RETURN_URL`）で、注文の画面に `payment=returned` を付ける。まだ支払待ちなら「確認中」と示す ※2 |

※2：与信の結果は、決済サービスからバックエンドへの通知だけで届くので、戻った時点ではまだ届いていないことがある。画面は決済サービスに問い合わせない。

### 4.8 お届け先の都道府県と市区町村

都道府県と市区町村は、地域のマスターデータ（店舗 API の `region` の操作）から選ぶ。画面に都道府県の表を持たない。

| 場面 | 動き |
|------|------|
| 欄の並び | 郵便番号、都道府県（選ぶ）、市区町村（選ぶ）、市区町村より下の住所 |
| 都道府県の一覧 | 注文手続きのページを作るときに `getApi()` で取る（公開の情報なのでキャッシュを使う） |
| 市区町村の一覧 | 都道府県を選んだときに、サーバーアクション（`actions/region.ts`）で取る。選び直すと、市区町村の選択を外す |
| 郵便番号で補う | 郵便番号がハイフンを除いて 7 桁になったら、サーバーアクションで引く。補い方は下の表 |
| 補った後 | どの欄も変えられる。補った値を消費者が直しても、もう一度は補わない（郵便番号を変えたときだけ引き直す） |

| 郵便番号を引いた結果 | 補うもの |
|----------------------|----------|
| 1 件 | 都道府県と市区町村を選ぶ。住所の欄が空なら、町域を入れる（町域が空なら入れない） |
| 複数で、都道府県と市区町村がすべて同じ | 都道府県と市区町村を選ぶ。町域は入れない（どれか分からないため） |
| 複数で、都道府県か市区町村が違う | 何も補わない（1 つの郵便番号が 2 つの市区町村にまたがるとき。誤りを補わないよう、消費者に選ばせる） |
| ない、通信の失敗 | 何も補わず、メッセージも出さない（消費者は一覧から選べる） |

- 一覧を引くサーバーアクションは、変更でなく読むだけなので `ActionResult` を返さず、失敗は空（市区町村の一覧は `null`）で返す。
- 補い方は `features/checkout/` の関数にし、単体テストを書く。古い応答（引いている間に都道府県や郵便番号を変えた）は捨てる。

## 5. 表示の決まり

| 対象 | 決まり |
|------|--------|
| 価格 | C 側の商品は必ず税込価格を持つ |
| 在庫 | 「在庫あり」「在庫なし」だけ（数量は出さない）。一覧では在庫のない商品に「在庫なし」 |
| 画像 | API の URL をそのまま使う（縮小・変換は配信の側）。一覧は代表画像、詳細は大きな画像と小さな画像の並び。バリアントを選ぶとその画像（なければ代表画像）に替える。画像がなければ代わりの図 |
| 金額の内訳 | 商品の合計、送料、総額、税率ごとの消費税額（「10% 対象 11,000 円（内消費税 1,000 円）」）。カート・注文手続き・注文で同じコンポーネントを使う |
| 購入できない品目 | 「購入できません」と理由（表示されなくなった、販売停止、在庫切れ、在庫が足りない） |
| 注文の状態 | 「支払待ち」「受付」「キャンセル申請中」「キャンセル」。出荷済みの注文は、注文の状態の代わりに配送状態（「出荷済み」「配送中」「配達完了」「返送」）を出し、注文詳細に配送業者と送り状番号を添える。申請のフォームは `actions.requestCancellation` で出す |
| 日時 | 「2026/10/10 14:05」 |
| バリアントの選択 | 軸ごとに値を並べ、在庫切れ・販売停止のバリアントにしかならない値はグレーで選べなくする |

## 6. 結果の知らせ方

- 取得の失敗はエラーの画面に出す。クエリの誤り（形が違うなど）は API の `message` をその画面に出す（価格帯の下限が上限より大きいときは、API は空の一覧を返す）。
- 成功は、次の画面への移動か表示の変化で示す。「カートに入れる」は、ボタンの近くに「カートに入れました」とカートへのリンクを出す。

| 操作の失敗 | 出し方 |
|------------|--------|
| 入力の誤り（400） | 入力欄に対応するものはその欄の下、それ以外はフォームの下に `message`。入力は消さない ※4 |
| 業務のエラー（400、409） | フォームの下に `message`。次にすべきことが別の画面にあるもの（在庫不足、カートの変更）はそこへのリンクを添える。総額が変わったら新しい金額で表示し直す |
| 通信の失敗 | 「サーバーに接続できませんでした。」 |

※4：欄の下には、API の応答の項目ごとの文（`errors[].message`）をそのまま出し、画面で文を作らない（`features/checkout/placeOrderErrors.ts`）。契約の形の検証で見つかった誤りも、API が業務の検証エラーと同じ文を返す（[バックエンドの書き方](../../backend/coding.md) 第 3.3 節）。

キャンセルの申請が却下された注文には、問い合わせ先（`GET /shop` の店舗の情報。値はバックエンドの設定）を示す。店舗画面の環境変数には、画面の処理の設定（接続先、キャッシュの秒数など）だけを置く。

## 7. テスト

| 対象 | テスト | 置き場所 |
|------|--------|----------|
| `lib/`・`features/` の関数（判定、変換、整形、エラーの欄への対応） | Vitest の単体テスト | 対象の横（`*.test.ts`） |
| 表示のコンポーネント（状態を持たないもの。client の部品の初めの表示を含む） | `renderToStaticMarkup` で HTML にし、文字と並びを確かめる（`src/test/render.tsx` の `renderMarkup`） | 対象の横（`*.test.tsx`） |
| client の部品の、ブラウザーの中だけで終わる操作（サーバーアクションを呼ばないもの） | ファイルの先頭で jsdom を選び（`// @vitest-environment jsdom`）、Testing Library で操作する（`src/test/render.tsx` の `renderInBrowser`）。サーバーアクションを呼ぶ操作は、サーバーアクションのテストと E2E で確かめる。例外：読むだけのサーバーアクション（お届け先の市区町村の一覧、郵便番号で引く。第 4.8 節）は、`vi.mock` で結果を差し替えて、フォームの操作を確かめる ※7 | 対象の横（`*.test.tsx`） |
| サーバーの処理（サーバーアクション、`api/cart.ts`、`auth/` のコールバック、`proxy.ts`） | Node で直接呼ぶ。Next.js の口（`next/headers` など）と `@/auth` は `src/test/` で置き換え、バックエンドは MSW（`msw/node`） | 対象の横（`*.test.ts`） |
| 画面をつないだ流れ | E2E | `e2e/tests/` |

※7：補い方の組み合わせ（1 件、複数、ない、通信の失敗、住所の欄の入力の有無）が多く、E2E では確かめきれないため。読むだけなので、差し替えても送る内容を見落とさない。サーバーアクションそのものは、サーバーの処理のテストで確かめる。

## 8. 画面を追加する手順

1. 使う API が `store.yaml` にあるかを確かめる。なければ、先に plan と `store.yaml` を直す。
2. `app/` にルートを作り、コンポーネントは `features/<機能>/components/` に置く。操作のある部分だけクライアントコンポーネントにする。
3. データはサーバーコンポーネントで取得する（第 4 節）。ログインを求める画面は、取得の前にログインを確かめる（第 9 節）。
4. 新しい表示の決まりは `lib/` か `features/` の関数にし、単体テストを書く。
5. lint、型チェック、テスト、ビルドを通し、開発サーバーで表示を確かめる。

## 9. ログイン

店舗画面のサーバーが IdP とやり取りし（BFF）、token はサーバーだけで扱う。

| 項目 | 決まり |
|------|--------|
| 設定 | `auth/` に Auth.js の設定を集め、外からは `@/auth` だけを import する（ライブラリを替えるときの範囲を狭くするため）。provider は Keycloak（`ec-store` realm の `ec-store-web`、confidential client）、認可コード + PKCE |
| 環境変数 | `AUTH_KEYCLOAK_ISSUER`（既定 `http://localhost:8180/realms/ec-store`）、`AUTH_KEYCLOAK_ID`（既定 `ec-store-web`）、`AUTH_KEYCLOAK_SECRET`、`AUTH_SECRET`（Cookie の暗号化の鍵）、`AUTH_URL`（店舗画面を公開する URL。既定 `http://localhost:3000`）※5 |
| 戻り先 | ログイン（IdP からの戻り先）とログアウト（IdP のログアウトの後の戻り先）の URL は `AUTH_URL` から作り、リクエストヘッダーのホストとプロトコル（`host`、`x-forwarded-*`）を使わない（ヘッダーは偽れるため）※6 |
| セッション | 暗号化した HttpOnly の Cookie に、access・refresh・ID token、期限、氏名・メールアドレスを持つ（サーバーに状態を持たない） |
| 画面から読める情報 | `auth()` の結果（ブラウザからも読める）には氏名とメールアドレスだけ。token は `getAccessToken()` で Cookie から直接読む（サーバー専用） |
| 氏名 | token の姓（`family_name`）と名（`given_name`）を「姓 名」で並べる |
| ログインの状態 | サーバー側で `currentMember()`（ログインしていれば氏名とメールアドレス、していなければ `null`）。クライアントコンポーネントでは取らず、要れば props で渡す |
| アカウント | ヘッダーから IdP のアカウント画面（`<issuer>/account`）へ移る。変えた氏名は次のログインから反映する |

※5：既定値はローカルと CI だけで使う値（realm の JSON と同じ）で、開発モードとテストでだけ使う。本番モードでは、この 5 つと `STORE_API_BASE_URL` がなければ起動時に失敗する（`src/auth/config.ts`）。E2E は `playwright.config.ts` で渡す。

※6：Auth.js は `AUTH_URL` があれば、リクエストの URL をそれに置き換える。`trustHost` は指定しない。ログインの戻り先のテストは、このファイルだけ本物の Auth.js を使う（`auth/loginRedirect.test.ts`）。

### 9.1 token の更新

access token の期限（5 分）が 1 分を切っていたら、refresh token で取り直す。

- `proxy.ts` が要求ごとにセッションを確かめ、取り直した token を Cookie に書く（サーバーコンポーネントは Cookie を書けないため）。
- 同じ要求の中では画面は古い Cookie を読むので、`getAccessToken()` は期限切れなら自分でも取り直して使う（Cookie には次の要求で `proxy.ts` が書く）。
- 取り直せなければ（IdP のログインが切れた）、ログインしていないものとして扱う。
- IdP に届かない・上限（`AUTH_KEYCLOAK_TIMEOUT_SECONDS`、既定 10 秒）を過ぎたときは、ログインの状態を残す（期限が切れていれば、API が 401 を返してログイン画面へ移る）。
- ログインの IdP への呼び出し（discovery、token の交換、userinfo）にも、Auth.js の provider の fetch を差し替える仕組み（`customFetch`）で同じ上限を付ける。

### 9.2 ログイン画面へ移す

- `/login?returnTo=<戻る画面>` から IdP へ移り、ログイン後は `returnTo` に戻る。`returnTo` は画面の中のパス（`/` で始まり、`//` と `/\` で始まらない）だけを受け付け、それ以外は `/`。
- 会員登録は `/login?register=1&returnTo=...`（OIDC の `prompt=create`）。
- 画面とサーバーアクションは `redirectToLogin()` で今の画面に戻るように移す。今のパスは `proxy.ts` が要求のヘッダー（`x-pathname`）で知らせる（サーバーコンポーネントは URL を直接知らないため）。
- ログインを求める画面（注文手続き、注文一覧、注文）は、取得の前に `currentMember()` を確かめ、`null` なら `redirectToLogin()`。API が 401 を返したときも同じ。注文手続きに進む操作も、ログインしていなければカートに戻るようにログイン画面へ移す。

### 9.3 ログアウト

サーバーアクション（`actions/auth.ts`）で、セッションの Cookie と Cookie のカート ID を消し、IdP のログアウト（RP-Initiated Logout。ID token と店舗のトップを添える）へ移る。IdP のログインも終わるので、パスワードなしではログインし直せない。
