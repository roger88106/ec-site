# Spec 430：店舗画面のログインの手続きが失敗したときに、1 回だけ自動で再試行する

種類：機能　規模：M　ステータス：確定

## 背景と目的

会員登録の後、確認メールのリンクを開く前に、同じブラウザーで店舗からログインを試すと、パスワードはまだないので失敗する。

その後、確認メールのリンクでパスワードを設定する。店舗画面に戻ると、英語の「Server error / There is a problem with the server configuration.」の画面になる。この画面は Keycloak のものではなく、店舗画面がログインに使うライブラリ（Auth.js）の既定のエラーの画面である。

原因は次のとおり。

1. Auth.js は、ログイン手続きの PKCE の値を 1 つの Cookie に保存する。
2. 会員登録（1 回目のログインの手続き）の後に、同じブラウザーでログインを試す（2 回目）と、Cookie が 2 回目の値に上書きされる。
3. パスワードを設定すると、IdP は 1 回目の手続きに認可コードを返す。
4. 店舗画面がそのコードを token に交換するとき、PKCE の照合に失敗する（IdP の応答は `invalid_grant`）。

会員登録に限らず、同じブラウザーの 2 つのタブでログインを始め、先に始めた方を終えたときも同じ失敗になる。このとき IdP の側では、パスワードの設定とログインは済んでいる。もう一度ログインの手続きを始めれば、パスワードを入れずにログインできる。

追跡の issue は #430。調査の結果は[issue のコメント](https://github.com/roger88106/ec-site/issues/430#issuecomment-6970693242)にある。利用者の決定（2026-11-18、issue 担当のセッション経由）は、IdP から戻ったときの失敗で、店舗画面がログインの手続きを 1 回だけ自動で再試行すること。再試行した後は、店舗のトップに戻る（ログインを始めた画面には戻らない）。

### 確認した範囲と限界

| 確認した内容 | 方法と出典 |
|--------------|------------|
| 同じブラウザーでログインを試した後にパスワードを設定すると、Auth.js の既定のエラーの画面になる | E2E の AC-111 のテストを同じブラウザーで試す形に変えて実行した（issue #430 のコメント） |
| そのとき、店舗画面のログに CallbackRouteError が出る。IdP は `invalid_grant`（PKCE verification failed）を返す | 同じ E2E の実行の、店舗画面のログ（issue #430 のコメント） |
| IdP のログインが済んだ後に、もう一度ログインの手続きを始めると、パスワードを入れずにログインできる | 同じ E2E の環境で確認した（issue #430 のコメント） |
| IdP から戻ったときの失敗（token の交換、state・PKCE の照合）は、Auth.js が `pages.error` へ `error=Configuration` を付けてリダイレクトする | `node_modules` の `@auth/core/index.js:130-140`（next-auth 5.0.0-beta.32） |
| `pages.error` がなければ、Auth.js は既定の画面を表示する | `@auth/core/index.js:98-106` |
| IdP がエラーを返したとき（`error=access_denied` など）は、Auth.js はエラーの画面ではなく、ログインの画面の設定（`pages.signIn`）へリダイレクトする | `@auth/core/lib/actions/callback/oauth/callback.js:95-103`、`@auth/core/errors.js`（OAuthCallbackError の kind は signIn） |
| 店舗画面の Auth.js の設定に、エラーの画面の設定はない | `frontend/store/src/auth/index.ts:46-93` |
| `/login` はクエリ `returnTo`、`register` を受けて IdP へリダイレクトする | `frontend/store/src/app/login/route.ts` |

2 回目も失敗する場合（IdP の障害など）は、ブラウザーで確認していない。

## スコープ

| 含める | 含めない |
|--------|----------|
| IdP から戻ったときの失敗で、ログインの手続きを 1 回だけ自動で再試行する | IdP がエラーを返したとき（Auth.js のログインの画面への移動）の扱い |
| 再試行しても失敗したときの、ログインできなかったことを示す画面 | Auth.js の Cookie の使い方（PKCE を 1 つの Cookie に保存すること）の変更 |
| E2E の AC-111 のテストを、同じブラウザーでログインを試す形に変える | 再試行した後に、ログインを始めた画面へ戻すこと |
| AC 一覧、会員登録とログインの流れ、店舗画面の構成の更新 | |

決定で使う論理名と識別子は次のとおり。

| 論理名 | 識別子 |
|--------|--------|
| Auth.js のエラーの画面の設定 | `pages.error` |
| エラーのエンドポイント | `/login/error`（`frontend/store/src/app/login/error/route.ts`） |
| ログインできなかったことを示す画面 | `/login/failed` |
| ログインの操作 | `/login` |
| 再試行のフラグ | Cookie（名前は実装のタスクで決める） |

決定：

1. 規模は M にする。理由：AC を変える・追加するが、API の契約と DB の構造を変えず、店舗画面だけを変えるため。
2. Auth.js のエラーの画面の設定に、店舗画面のエラーのエンドポイントを指定する。エラーのエンドポイントは画面でなく、リダイレクトだけをする。
3. エラーのエンドポイントは、次のとおりリダイレクトする。

   | 条件 | 動き |
   |------|------|
   | クエリの `error` が `Configuration`（IdP から戻ったときの失敗など、サーバーの側の失敗）で、再試行のフラグがない | フラグを設定して、`/login?retry=1` へリダイレクトする（戻る画面は店舗のトップ） |
   | それ以外（フラグがある、`error` が別の値） | フラグを削除して、ログインできなかったことを示す画面へリダイレクトする |

   理由：Auth.js は、IdP から戻ったときの失敗も、設定の誤りも、同じ `Configuration` で知らせ、区別できないため。1 回に限るのは、設定の誤りや IdP の障害で、店舗と IdP の間のリダイレクトが繰り返されないようにするため。
4. 再試行のフラグは、期限の短い Cookie（10 分）に保存する。HttpOnly、SameSite=Lax、本番では Secure。名前には、Auth.js の Cookie と同じ接頭辞（環境変数 `STORE_COOKIE_PREFIX` で設定する）を付ける。ログインできたときも削除する。理由：フラグは IdP への往復を越えて残る必要があり、クエリは IdP を通ると失われるため。期限は、再試行で IdP がログイン画面を表示したときに、入力を終えるまで残る長さにするため。
5. `/login` は、`retry=1` のときに再試行のフラグがなければ、IdP へリダイレクトせず、ログインできなかったことを示す画面へリダイレクトする。理由：Cookie を受け付けないブラウザーではフラグが残らず、再試行が繰り返されるため。Cookie が届くことを、IdP へリダイレクトする前に確認する。
6. ログインできなかったことを示す画面は、見出し、時間をおいてもう一度ログインする案内、ログインの操作へのリンク、トップへのリンクを表示する。ログインを求めない。見た目は、今のエラーの画面（`app/error.tsx`）に合わせる。文言は実装のタスクで決める。
7. 再試行した後は、店舗のトップに戻る。理由：ログインを始めた画面（戻る画面）は、Auth.js が Cookie に保存し、2 回目のログインの手続きで上書きされているため（利用者の決定）。
8. [店舗画面の構成](../../02-設計/apps/store.md)の「画面の URL」の表と「ログイン画面へ移す」の節、[会員登録とログインの流れ](../../01-概要/member.md)の「業務の流れ」の箇条を、この spec の動きに合わせて書き換える。

## 受け入れ条件

### US-430-1 同じブラウザーで 2 つのログインの手続きを始めてもログインできる（C / P1）

- **AC-430-1** IdP から戻ったときにログインの手続きが失敗したら、店舗画面はログインの手続きを 1 回だけ自動で再試行する。IdP のログインが済んでいれば、パスワードを入れずにログインした状態で店舗のトップに戻る。
- **AC-430-2** 再試行しても失敗したときは、ログインできなかったことを示す画面を表示し、それ以上再試行しない。画面から、もう一度ログインする操作と、トップへの移動ができる。
- **AC-430-3** Cookie を受け付けないブラウザーでは、再試行せずに、ログインできなかったことを示す画面を表示する。

### AC-112 の変更

AC-112 に、今の文の後に次の文を加える。変えた spec に 430 を加える。[AC 一覧](../../03-機能仕様/acceptance-criteria.md)の AC-112 の行の更新は、tasks で行う。

## 非機能要件

- **NFR-430-1** API の契約とバックエンドを変えない。
- **NFR-430-2** エラーのエンドポイントと `/login` のリダイレクトの先は、店舗画面の中の決まったパス（`/login`、`/login/failed`）だけにし、クエリから戻る画面を受け取らない。理由：外部のサイトへのリダイレクトに使われないようにするため。
- **NFR-430-3** 再試行のフラグの Cookie には、フラグの有無だけを保存し、token や会員の情報を入れない。

## Non-goals

| 項目 | 理由 |
|------|------|
| IdP がエラーを返したとき（Auth.js のログインの画面への移動）の扱い | 原因と画面が別で、この不具合の範囲外のため。必要なら別の issue にする |
| Auth.js の Cookie の使い方の変更（PKCE を手続きごとに保存する） | ライブラリの内部の動きで、店舗画面の設定では変えられないため |

| 2 回目も失敗する場合の E2E のテスト | E2E の環境で、再試行だけを失敗させる手段がないため。単体テストで確認する |
