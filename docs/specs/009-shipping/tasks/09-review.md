## 結果

### 修正したこと

| 段階・タスク | 内容 |
|--------------|------|
| T9901 | 送り状番号に数字が 1 つもない入力（「---」）がリクエストの検証を通り、売上を確定した後に出荷の作成で失敗していた。OpenAPI の形で数字を 1 つ以上求める |
| T9901 | 与信期限切れの注文をキャンセルしても、与信期限が近い印と絞り込みに出続けていた。「受付」の注文に限る（AC-186） |
| T9901 | 返金を追加した後の古いコメント、未使用のコード（出荷の一覧、ログ、古いキャンセルのオーバーロード）、import の順 |
| T9901 | `order.application` が 13 ファイルで目安を超えていたので、注文手続き・支払・出荷のパッケージに分けた（バックエンドの書き方 第 1.4 節） |
| T9902 | 与信期限の印の文言キーを、機能・コンポーネント・項目の形にした |
| T9903 | 用語集（注文の出荷済み、支払の 4 つの状態）、店舗画面の構成（出荷後の状態の出し分け）、通知の設計書（SMTP の待ち時間の上限）。機能紹介のページに出荷と配送状況を追加した |
| 段階 5 の確認 | SMTP サーバーが応答しないとメールのリスナーが止まったままになるので、タイムアウトを追加した（T9406〜T9408） |
| 段階 10 | 支払のない local の seed の注文は、出荷を登録すると 404 になっていた。seed の注文に状態に合う支払を追加した。再作成した DB で seed が制約に反していたのも修正した（[段階 10](10-seed.md)） |

### 修正せずに残したこと

| 項目 | 理由 |
|------|------|
| 支払の集約の与信期限判定（`Payment.isAuthorizationExpiring` など）は、照会側と別に実装している | 照会は集約を読まずに一覧の行から判定する。規則を表すクラス・型（`AuthorizationTerm`、`PaymentStatus`）は 1 か所なので、規則は重複しない |
| `MockCarrier` のオーバーロードの並び、`ShippingProperties.Carrier` と `shipping.domain.Carrier` の同じ名前、`SmtpMailer` の設定の有効化の場所、通知のエンドポイントの例外による分岐 | 読みやすさの好みで、規則に書いたものではない。修正すると mock と通知のエンドポイントの差分が広がるため |
| ローカルの E2E の画像のテスト | ローカルで SeaweedFS の 8333 が Windows の予約範囲に入っていた（利用者が WinNAT を再起動して解消）。CI では通る |

### 完了の確認

段階 9 の完了条件を満たした。`./gradlew check`、管理画面・店舗画面のテスト、E2E が手元と CI で通る（CI の E2E は T9804）。
