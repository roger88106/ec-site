# レビューの観点と指示のひな形

[SKILL.md](SKILL.md) の手順 3 で観点を選び、手順 4・7・8 でサブエージェントに渡す指示を書くときに読む。

## 観点の一覧

| 観点 | 見ること | 主な根拠 |
|------|----------|----------|
| 規則 | チェックリストの確認方法が「レビュー」の規則に合うか | 書き方の規則の各文書 |
| 一貫性 | 同じことを、モジュール・spec によって違う書き方にしていないか（名前、エラーの扱い、画面の作り、テストの書き方） | 書き方の規則、既存のコード |
| 重複と抽象 | モジュール間の似たコード、共有パッケージに置くべきもの、反対に過ぎた抽象 | バックエンドの書き方 第 1.5 節、フロントの書き方 第 5 節 |
| 境界と依存 | モジュールの `api`・`event` の外に触れていないか、腐敗防止層、循環、共有の中身 | バックエンドのアーキテクチャ、ArchUnit・Modulith |
| 文書とコード | spec・設計の文書・OpenAPI・用語集とコードが一致するか、古い記述とリンク切れ。食い違ったら、コードを正として文書の修正を提案する ※1 | 開発の進め方 |
| テスト | AC に対応するテストの抜け、弱い確認、重複した・壊れやすいテスト | テストの書き方 |
| 安定性と運用 | エラーの扱い、ログ、設定、トランザクションと並行、外部サービスの失敗、セキュリティ、性能 | バックエンドのアーキテクチャ、フロントの書き方 |
| 不要なもの | 使われていないコード・依存、TODO・暫定の処理、残った設定 | なし |
| 後の開発への備え | 初めて読む人（エージェント）に分かるか、機能を追加するときの拡張の場所 | なし |

※1：自動の検査がない次の文書は、関わるコードを変えたら必ず照合する：モジュールの設計書の「構成」（パッケージ）、共通コード・ログ・可観測性（`common/`、`config/`、ログと運用の設定）、API の規約の URL の規則（契約のパス）。

## 指示のひな形（観点ごと）

日本語だけで書く。次の形にする。

```
あなたは、<リポジトリ> のコードと文書のレビュー担当です。実装の過程は知らされていません。

## 対象
<対象のファイルの一覧のパス、または範囲>

## 観点
<観点の名前と、見ること>

## 根拠
- チェックリスト：<パス>（この観点に関係する部分）
- spec：<パス>、plan：<パス>
- <観点の主な根拠の文書のパス>

## 結果
<結果の書き先> に、次の表で書く。
| 重要度（必須・推奨） | 場所（ファイル:行） | 指摘 | 根拠（文書と節、または DC・AC） | 修正案 | 機械の検査に移せるか |

- 必須：規則・spec に反する、不具合になる、セキュリティ・データ・金額に関わる。
- 推奨：読みやすさ、一貫性、将来の保守。
- 好みの範囲の指摘は挙げない。根拠を示せない指摘は挙げない。
- 根拠と理由には出典（ファイル:行）を書く。出典のない理由は書かない。
- 他のファイルは変更しない。返すのは件数（必須、推奨）だけ。
```

## 指示のひな形（plan・tasks の照合）

手順 7 で使う。日本語だけで書く。tasks の照合では、＜tasks のとき＞の行を加える。

```
あなたは、spec と plan（＜tasks のとき＞と tasks）を照合する担当です。実装の過程は知らされていません。

## 対象
- spec：<パス>
- plan：<パス>
- ＜tasks のとき＞tasks：<パス>

## 観点
spec の各 AC・DC と、plan の決定を 1 件ずつ照合する。
＜tasks のとき＞spec の各 AC・DC・DN と plan の決定が、どのタスクで行われるかを照合する。各段階の完了の条件と各タスクの条件が、spec より厳しくないか・緩くないかを見る。前のタスクが後のタスクで作るものを使っていないかを見る。

## 結果
<結果の書き先> に、次の表で書く。AC・DC を全て載せる。
| AC・DC | plan の節（＜tasks のとき＞タスク） | 判定（合っている・抜けている・食い違う） | 説明 |

- 判定の根拠は、spec と plan の本文に置き、出典（ファイル:行）を書く。出典のない理由は書かない。
- 他のファイルは変更しない。返すのは件数（合っている、抜けている、食い違う）だけ。
```

## 指示のひな形（文書のレビュー）

手順 8 で使う。日本語だけで書く。

```
あなたは、日本語の技術文書のレビュー担当です。実装の過程は知らされていません。

## 対象
<新しく書いた、または変えた文書のパス>

## 見本
目指す書き方の見本：<見本のパス>
言い回しと論理の規則：.claude/skills/docs/tech-writing.md（1〜5 の表を当てはめる）

## 観点
技術文書として不自然な言い回しを、候補として挙げる。見本の書き方に近づける。次の 2 つを両方見る。
- 和語の言い換え：技術文書で一般的な語に替える（規則の「用語」の表）。
- 論理、読む人の負担、中身のない言い回し、翻訳調の比喩と擬人化、冗長さ（規則のその他の表）。

## 守ること
- 意味、番号、節の番号、表の構成を変えない。
- 識別子、文書の題名、節の名前を変えない。
- プロジェクトの用語集の語を一般の語に替えない。
- 理由には出典（規則のファイル:行）を書く。出典のない理由は書かない。

## 結果
<結果の書き先> に、次の表で書く。
| ファイル | 行 | 今の書き方 | 修正案 | 理由 |

- 対象のファイルは変更しない。返すのは候補の件数だけ。
```
