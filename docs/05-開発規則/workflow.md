# 開発の進め方

[constitution](../constitution.md)の「開発の進め方」の細則で、毎回読む。場面ごとの規則は[起票と記録の操作](issues.md)と[マージと後片付け](merging.md)にある。

## 1. 仕様駆動開発（SDD）

### 1.1 流れ

規模 L の流れを示す。規模 S・M の文書は「規模」にある。全ての変更は issue から始まる（[起票と記録の操作](issues.md)の「起票」）。

| 段階 | 文書 | 書くこと |
|------|------|----------|
| spec | `spec.md` | 何を、なぜ作るかと、受け入れ条件（整理の spec は完了の条件）。実装（クラス名、カラム、フレームワーク）は書かない |
| plan | `plan.md` | 今回の変更について、モジュールをまたぐ決定、API と AC の対応、テストの割り当て、実装の順序。あわせて OpenAPI を書き、モジュールの業務規則・状態・データモデルが変わるなら `docs/03-機能仕様/`、境界・処理の流れ・パッケージの構成が変わるなら `docs/02-設計/` を更新する |
| tasks | `tasks/` | plan を検証可能な小さなタスクに分け、対応する AC を記す。段階ごとに 1 ファイル |
| 実装 | コード | tasks に沿って、TDD（「テスト駆動開発」）で進める |

### 1.2 spec の種類と書くこと

| 種類 | 書くこと | 番号 |
|------|----------|------|
| 機能 | 背景と目的・スコープ・User stories・受け入れ条件・業務ルール・非機能要件・依存・Non-goals・Open questions | US・AC・BR・NFR |
| 整理 | 背景と目的・スコープ・目的と完了条件・変える範囲・非機能要件・依存・Non-goals・Open questions | DS・DC・DN |

節の名前と順、冒頭の種類・規模・ステータスの行は、[spec の雛形と見本](../08-spec/templates/README.md)の雛形のとおりにする。`scripts/ci/spec-structure.mjs` が確認する。

- 機能の spec は、単独で検証できる機能の縦切り（バーティカルスライス）1 つ。
- 整理の spec は、消費者・運営者に見える振る舞いを変えない。変える必要が出たら、機能の spec にする。
- Open questions を空にし、利用者が spec を確定してから plan に進む。
- DC の確認方法（CI、テスト、検査の script、レビューで読む）は、plan で決める。規模 M は、タスクの確認方法に書く。
- 設計への影響が大きい spec は、ステータスの下に「危険度：高」の行を書く（[マージと後片付け](merging.md)の「マージの許可と後片付け」）。

### 1.3 spec と plan の書き方

AC・DC・plan の節・識別子と、plan と tasks を書くときの注意は、[文書の構成](doc-structure.md)の「spec と plan の書き方」。参照の書き方は、[文書の構成](doc-structure.md)の「参照」。本文の書き手は、[文書の書き方](writing.md)の「本文の書き手」のとおり。

### 1.4 コードと文書の食い違い

- 現在の振る舞いは、コードを唯一の正とする。文書は、その振る舞いと設計の理由を説明する。
- 文書とコードの食い違いに気づいたら、誤っている方で扱いを分ける。コードが正しく文書が古いときは、文書を修正する。コードが spec の意図と異なるとき（不具合）は、その場ではコードも文書も変えない。自分の spec の範囲の不具合は、tasks に追加してテストから修正する。spec の範囲の外の不具合は、issue に起票する（[起票と記録の操作](issues.md)の「起票」）。
- 完了した spec の AC を変える振る舞いの変更（上限の値を変える、など）は、新しい機能の spec で行い、AC 一覧の行で示す。整理の spec で行うのは、レビューで見つけた不具合の修正（その spec の非機能要件で例外にしたもの）だけ。
- 値（上限、件数、期限など）を変えるときは、AC の番号によらず、古い値をテスト（バックエンド、画面、E2E）と文言の全体で検索する。境界の値（上限と上限 ＋ 1）は、別の AC のテストにもある。
- AC 一覧の操作（AC の転記、BR の記載）は、[起票と記録の操作](issues.md)の「AC 一覧の操作」。

理由：文書を正とすると、コードと異なる文書に従って作業し、誤りが広がるため。

## 2. テスト駆動開発（TDD）

### 2.1 循環

1. **レッド**：失敗するテストを書き、失敗することを確認する。
2. **グリーン**：テストが通る最小の実装を書く。
3. **リファクタリング**：テストが通ったまま、コードの構造を改善する。次の振る舞いのレッドに進む。

振る舞いを変えないリファクタリングの前には、今の振る舞いを固定するテストを追加してよい。このテストは最初から通るので、一時的にコードか期待値を変えて、失敗しうることを確認する。

CI の検査の script（`scripts/ci/`）のテストは、commit の前の hook が実行するので、レッドのままでは commit できない。`[テスト]` のタスクは手元でレッドを確認するところまでとし、続く実装のタスクと同じ commit に入れる（「1 つの commit に 1 つのタスク」の規則の例外）。commit の本文に、レッドを確認したことを書く。

### 2.2 対象ごとの進め方

| 対象 | 進め方 |
|------|--------|
| domain | 厳密な TDD |
| AC 単位の振る舞い | 実装前に受け入れテストを書き、レッドから始める |
| infrastructure、Controller の配線 | 実装後に書いてよい |
| フロントの関数（判定、変換、表示の整形） | 厳密な TDD |
| フロントの主な操作の流れ（保存、エラーの表示、確認など） | 結合テストを書く。実装の前でも後でもよい |
| フロントの見た目 | 求めない（目視で確認する） |
| E2E | 実装の後に書く（`[E2E]` のタスク）。レッドは求めない |

※ E2E は、画面・API・バックエンドがそろってはじめて動き、先に書くと失敗の理由を絞れない。振る舞いのレッドは、単体・結合・統合のテストで確認する。

## 3. 規模と push

起票は[起票と記録の操作](issues.md)の「起票」、アーカイブの置き場所と手順は[起票と記録の操作](issues.md)の「アーカイブの操作」、試作は[起票と記録の操作](issues.md)の「構成が決まっていないときの試作」にある。

### 3.1 規模

規模（S・M・L）はエージェントが提案し、利用者が承認する。文書は次のとおり。

| 規模 | 文書 |
|------|------|
| S | issue だけ。issue の本文を spec とする |
| M | `spec.md` の 1 つのファイル。目的、完了の条件か AC、tasks の節 |
| L | spec・plan・tasks |

判定の基準は次のとおり。

| 条件 | 規模 |
|------|------|
| API の契約かデータベースの構造を変える、または 2 つ以上のモジュールにまたがる | L |
| AC を追加する・変える | M 以上 |
| 振る舞いを変えず、範囲が小さい | S |

- 規模 M の spec.md は、`docs/08-spec/<番号>-<名前>/` に置く。理由：検査の script が spec.md を読むため。

### 3.2 push のタイミング

作業ブランチの push は、段階の最後（段階のない規模 S・M では、作業の最後）に行う。段階の途中は commit だけにする。理由：push のたびに CI が全て実行されるが、段階の途中の CI の結果は使わないため。

段階の途中で push してよいのは、次のときだけ。

| とき | 例 |
|------|----|
| CI でしか確認できないことを確認する | Linux での E2E、CodeQL、GitHub での Markdown の表示 |
| 量の大きいタスクの途中で、バックアップを残す | 複数の commit にわたるタスクの区切り |
| セッションの交代や引き継ぎの前 | skill `handoff` で引き継ぎの文書を作るとき |

## 4. 利用者の確認と中断

### 4.1 利用者が確認する対象

| 規模 | 利用者が確認する対象 |
|------|----------------------|
| L | spec、plan と tasks を一緒に、pull request |
| M | 1 つのファイルの spec、pull request |
| S | 規模の区分、pull request |

pull request の確認は、利用者の許可が必要なマージだけ（[マージと後片付け](merging.md)の「マージの許可と後片付け」）。

規模 M の spec と、規模 L の spec・plan・tasks は、文書のレビュー（skill `review` の手順 8）と校閲役（同 手順 9。対象と時点は [docs-review.md](../../.claude/skills/review/docs-review.md)の手順 3）を通してから、利用者の確認に出す。理由：造語や不自然な言い回しを、利用者が見つける前に修正するため。

### 4.2 待たないこと

段階とタスクの間で、利用者の確認を待たない。

### 4.3 中断して質問する条件

次のときだけ、作業を中断して利用者に質問する。

- spec・plan の誤り
- 「実装を始める前の照合」で、設計が変わる差
- 文書にない設計の判断
- 重要度「高」（定義は[書き方の規則とレビュー](review.md)の「重要度」）の指摘のうち、修正が機能の追加に相当するもの
- 最上位（使えなければ高性能）でも原因を特定できない失敗
- 同じ対象のレビューと修正の繰り返しが上限に達したとき（[書き方の規則とレビュー](review.md)の「レビューの収束」）

使用量の閾値に達したときは、区切りで止まって報告する（[作業の形と使用量](resources.md)の「止める閾値」）。

### 4.4 まとめて質問する

確認事項は、plan と tasks の確認でまとめて質問する。

### 4.5 実装を始める前の照合

spec 担当のセッションは、照合の前に、開始の条件（起動のメッセージに書かれる）を確認する。満たさないときは、issue 担当のセッションに問い合わせてターンを終える。兼務のときは skill `sessions` に従う。

満たしたら、最初のタスクの前に、作業ブランチに最新の `develop` を取り込み（merge で行う。理由：push 済みの履歴を守るため）、次を照合する。理由：承認の後に `develop` が進み、plan の前提が成り立たなくなることがあるため。

- plan（規模 M は spec）の前提が、最新の `develop` で成り立つか
- 変える範囲（ファイルとモジュール）が、最新の `develop` と合うか
- 依存する spec と部品の状態
- tasks が、承認の後に変わった規則（本書など）に合うか
- 並行する spec の変えるファイル（plan と tasks。規模 M は spec の tasks）との重なりが、spec の確定の後に増えていないか。増えていれば、実装の順序を再検討する

差があれば、plan（規模 M は spec）と tasks を直す（文書が先）。

- 設計が変わるときは、plan と tasks の確認（規模 M は spec の確認）で利用者に再度確認する。設計が変わらない直し（パスの修正、依存する spec の完了の反映、タスクの順序の変更）は、確認を待たない（「待たないこと」）。
- 承認の直後に実装を始めるときも行う。`develop` が進んでいなければ「差なし」。
- 結果（差の有無と直したもの）は、実装の開始のコメントとして追跡の issue に書く。

## 5. 完了の定義

### 5.1 `develop` に入れる条件

次の 3 つを満たしたものだけを `develop` に入れる。

- CI が通る。
- 作業ブランチで手動の確認を終えた。
- 文書を更新した。

### 5.2 公開を遅らせたい機能

公開を遅らせたい機能は、設定のフラグで無効にする。
