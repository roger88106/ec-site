共通の決定：

- 危険度は高。レビューの profile は標準で、重要な観点のレビューは高性能で行う。
- 確認の考え方（誤操作の防止であること、注文の時点の判定が最終の判定であること）は、[注文の設計](../../02-設計/order.md)の「注文手続きと注文の成立」に書く。支払わない注文を増やす不正への対策は、#411 の上限である。
- 各節は、「利用者に確認すること」の推奨した案 A で書く。
- #409（pull request #428）と重なるのは、機能仕様の注文の文書である。テストの `OrderPaymentApiTest` と `ShipmentApiTest` も重なる可能性がある。モジュールの主な変更は別なので、並行してよく、マージの順序は決めない。後にマージする側が、先の変更を取り込んで競合を解消する。
- #408 と #410 との重なりは、実装を始める前の照合で確認する。#411 は、この spec のマージの後に始める。
- 用語集だけは、検査が識別子の実在を確認するので、T406-01-06 で更新する。

## 確認の受け渡し（US-406-1、US-406-2：AC-406-1、7、9〜12）

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 開始の要求の任意の本文で、確認した注文の ID の一覧 `acknowledgedOrderIds` を受ける | `api/openapi/store.yaml` の `startCheckout` | `CheckoutApiTest` |
| その時点の支払待ちの ID の集合が、受けた一覧に全て含まれるかを判定する。含まれなければ 409 で、注文手続きを作らない | `CheckoutService` | `CheckoutApiTest` |
| 確認の結果として、その時点の支払待ちの ID の集合を注文手続きに保存する。本文がないときは空の集合 | `ordering.checkout` の列 `acknowledged_order_ids`、`Checkout` | `CheckoutApiTest`、`Checkout` の単体テスト |
| 注文の時点は、画面の値を受けない。その時点の支払待ちの ID の集合が、保存した集合に全て含まれなければ 409 | `OrderPlacementService` | `PlaceOrderApiTest` |

確認していない注文手続きは空の集合を持つので、確認なしの注文（AC-406-11）と、確認の後に増えた場合（AC-406-12）は、1 つの判定で扱える。古い一覧を送っても、その時点の支払待ちを含まなければ 409 になる。

## API の形（US-406-1、US-406-2：AC-406-1、4、11）

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 確認が必要なときの応答は、エラーコード `PENDING_ORDER_CONFIRMATION_REQUIRED`（409）。開始と注文の両方の `x-error-codes` に加える | `store.yaml`、`OrderErrorCode` | 統合テスト、エラーコードの単体テスト |
| 確認の画面の材料は `GET /me/orders/pending`（`listMemberPendingOrders`）。`items` は既存の `Order` の配列で、注文日時の新しい順 | `store.yaml`、`StoreOrderController`、`OrderQueryService` | `MemberOrderApiTest` |

既存の注文の型は、明細、総額、支払の期限、支払できるかを示すフラグ（`actions.pay`）を持つ。画面が判定を持たずに済むため、この型を使う。ページ単位にしない。理由：件数は少なく、#411 で上限が決まるため。

## DB の変更（US-406-2：AC-406-18）

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 判定は既存の注文の列（会員、状態）で行う。注文の列を追加しない。既存の索引（会員と注文日時）を使う | `OrderRepository`、`JooqOrderRepository` | 統合テスト |
| 注文手続きに、確認した注文の ID の一覧を JSON で追加する。必須で既定は空の配列 | Flyway のマイグレーション | 統合テスト |
| 会員ごとの行ロックの表を追加する（「同時の注文の防ぎ方」） | Flyway のマイグレーション | 統合テスト |

- 既存の注文のデータは変えない。適用の時点の支払待ちも判定の対象になり（AC-406-18）、支払待ちが複数あっても失敗しない（NFR-406-2）。
- 適用の時点で進行中の注文手続きは空の集合になり、注文の時点で確認に案内される。
- 一覧を JSON にする理由：注文の明細の軸の値と同じく、変わらない一覧であるため（[注文モジュール](../../03-機能仕様/order.md)の「データモデル」）。

## 同時の注文の防ぎ方（US-406-2：AC-406-14）

複数の支払待ちを認めるので、部分一意索引では防げない。理由：確認した 2 件目も支払待ちであり、一意にできないため。防ぎ方は、[注文の設計](../../02-設計/order.md)の「同時の注文」に書く。

| 何を | どこに | 確認方法 |
|------|--------|----------|
| 注文のトランザクションの最初に、会員ごとの行を挿入または更新して行ロックを取り、コミットまで保持する | 新しい表 `ordering.member_order_lock`（主キーは `member_id`）、`MemberOrderLockRepository` | `PlaceOrderConcurrencyTest` |
| 同じトランザクションで、ロックの後に支払待ちの ID を読む。READ COMMITTED なので、待った後の読み取りに先の注文が見える | `OrderPlacementService` | `PlaceOrderConcurrencyTest` |

ロックの順序と、開始でロックを取らない理由は、同じ「同時の注文」に書く。行は増え続けず、片付けは要らない。

## 判定の順序と上限との関係（US-406-1、US-406-2：AC-406-2、3、11、12、15、17）

判定の順序は、注文の時点が[注文の設計](../../02-設計/order.md)の「注文手続きと注文の成立」、開始の時点が[注文モジュール](../../03-機能仕様/order.md)の「注文手続き」にある。確認は、注文の時点を `PlaceOrderApiTest`、開始の時点を `CheckoutApiTest` で行う。

- 判定を `PendingOrderGuard`（`application/checkout/`）に集める。
- #411 の上限の判定は、注文の時点で会員の行ロックの中で、支払待ちの ID の集合の件数を見て行える。

## 店舗画面（US-406-1、US-406-2：AC-406-4〜8、13）

| 何を | どこに | 確認方法 |

| 確認の画面。支払待ちの注文がなければカートへ移る。「支払へ進む」は `actions.pay` が真の注文にだけ表示する ※1 | `frontend/store/src/app/checkout/pending-orders/page.tsx`、`features/checkout/components/PendingOrdersConfirmation.tsx` | 画面のテスト |

## 利用者に確認すること

| # | 確認 | 案 | 推奨と理由 |
|---|------|----|------------|
| 1 | 確認の結果を、どこで持つか | 案 A：確認の結果をサーバーが注文手続きに持つ。案 B：確認の結果を別の表で持ち、確認の ID を発行する。案 C：署名した確認の token を画面に渡す | 案 A。古い一覧を送っても 409 になる。案 B は表と片付けが増え、注文手続きと同じ寿命のものを別に管理する。案 C は改ざんを検出できるが、鍵の管理が増え、水平スケールの構成で鍵を共有する必要があり、案 A より利点がない |
| 2 | API の形 | 案 A：409 のエラーコードと、一覧の取得を分ける。案 B：409 の Problem に注文の一覧を載せる。案 C：開始の 200 の応答を、注文手続きと確認の要求のユニオン型にする | 案 A。Problem の形を変えない。案 B は共通の例外ハンドラーに項目の追加が必要で、API の規約の「エラーの本文」を変える。案 C は生成する型の扱いが複雑になり、注文の時点の拒否と形が揃わない |
| 3 | DB の変更 | 案 A：注文の列を追加せず、注文手続きに確認した ID の一覧だけを追加する。案 B：issue の案（注文にカートの ID を追加する） | 案 A。判定は既存の注文の列で足りるため。案 B は、複数の支払待ちを認める判定に使えない |
| 4 | 同時の注文の防ぎ方 | 案 A：専用の表の行ロック。案 B：PostgreSQL のアドバイザリロック（会員の ID のハッシュ）。案 C：その会員の注文手続きの行を全てロックする | 案 A。リポジトリの既存の排他（行ロック）と同じ方法で、スキーマから読み取れる。案 B は表が要らないが、リポジトリで初めての方法で、スキーマから読み取れない。ハッシュの衝突は無関係の会員を待たせる。案 C は表が要らないが、片付けのジョブの削除と順序が逆になるとデッドロックしうるうえ、正しさの説明が複雑である |
