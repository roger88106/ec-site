# Spec 502：画面に出るメッセージの文の書き方をそろえる

種類：整理　規模：M　ステータス：草案

## 背景と目的

#497 で `messages.properties` を整えたとき、画面に表示されるメッセージの文の書き方がモジュールの間で違うと分かった。文を変えると画面の表示が変わり、文を照合する統合テストもあるので、#497 では変えなかった（issue #502 の本文）。

- 例 1：「メールアドレスの形が正しくありません」（`ecsite.order.invalid_email`）と「メールアドレスの形式が正しくありません」（`ecsite.validation.email`）。
- 例 2：入力の誤りを伝える文の文末が、order は「〜で入力してください」、ほかは「〜にしてください」。

文の書き方の規則は、まだどの文書にもない。[バックエンドの書き方](../../05-開発規則/backend-coding.md)の「エラーは `XxxErrorCode` と `BusinessException`」と「入力の検証のメッセージ」は、キーと差し込みの規則だけである。

この spec は整理だが、メッセージの文だけは画面の表示が変わる。特例にするかは、Open questions の 1 で確認する。

追跡の issue は #502。全体の issue #544 の「進める順」では、段階 3 の C（共通と契約。#550 → #517 → #502 → #556 → #477 → #501）にある。

## スコープ

| 含める | 含めない |
|--------|----------|
| `messages.properties` の、画面に表示される文の修正 | 店舗画面・管理画面の文言ファイル（`frontend/*/messages/ja.json`） |
| 文を照合するテスト（バックエンドの単体・統合、E2E、画面テストの API 応答のモック）の修正 | メールの件名と本文（`ecsite.notification.*`）、配送業者の名前 |
| 規則の文書（[バックエンドの書き方](../../05-開発規則/backend-coding.md)）への追加 | コード・コメント・テスト名の中の社内の語（「C 側」「形」など） |

決定：

- 規則は[バックエンドの書き方](../../05-開発規則/backend-coding.md)に、新しい節「メッセージの文の書き方」として、「入力の検証のメッセージ」の後に置く。理由：メッセージのキーと差し込みの規則が同じ文書にあり、文を書く人が同じ所で読めるため。
- 規則の案は、利用者の確認待ちである（画面の文言は利用者が決める）。
  - 規則 1：条件を示して修正を求める文は、「<項目>は<条件>にしてください。」で終える。「〜で入力してください」「〜で指定してください」は使わない。理由：同じ種類の誤りを同じ形で伝えるため。今の文の多くがこの形である（入力の検証の文を除いて 21 件。「〜で入力してください」は 5 件、「〜で指定してください」は 1 件）。
  - 規則 2：値がないことを伝える文は、「<項目>を入力してください。」で終える。選ぶ項目は「選んでください」、件数や対象を指定させる項目は「指定してください」。今の文は全てこの形なので、変える文はない。
  - 規則 3：「<条件>にしてください」で示す上限は、文字数・件数・個数は「以内」、数の値は「以下」で書く（小数の桁は「小数第 n 位まで」）。上限を述べる文（「〜までです」「〜まで登録できます」）は「まで」で書く。
  - 規則 4：同じことを指す語をそろえる。「形」でなく「形式」を使う。理由：入力の検証の文（`ecsite.validation.*`）とメディアの文が「形式」を使っているため。内容や状態の確認を求める文は「確認してください」「確認して」を使う。理由：今の文の 4 件が使っている語（「変える文」の 7〜10）は、文書で使わない語の一覧（`scripts/ci/ja/ja-text.json`）で「確認する」に言い換える語であるため。
  - 規則 5：社内の呼び名（「C 側」など）は使わず、画面の語（「店舗」）で書く。理由：運営者の画面と消費者の画面に表示されるため。管理画面の文言ファイルも「店舗に表示されたことがある」と書いている。
  - 規則 6：漢字とかなの書き分けは、[文書の書き方](../../05-開発規則/writing.md)の「用語の選び方」（「すべて」→「全て」）に従う。
- 規則の確認方法は、Open questions の 3 で決める（推奨：自動）。

- 2 と 4 に「1 文字以上」を加えるのは、空のときもこのエラーになるため（氏名と住所は、空か上限を超えると同じエラー）。商品名などの文と同じ形にした。
- 6 に「1 文字以上」を加えないのは、空のときは別のエラー（「キャンセルの理由を入力してください。」）になるため。
- `{…}` は差し込む値の名前で、変えない。
- メールの本文（`ecsite.notification.shipment.body`）にも「確かめ」があるが、スコープの外なので変えない。
- 「前」の列は文書で使わない語を含むので、`scripts/ci/ja/ja-text.json` の許可の一覧（`permit`）にこの節を加える。

## 非機能要件

- **DN-502-1** エラーコード、メッセージのキー、差し込む値の名前、HTTP の状態、AC を変えない。変わるのは、「変える文」の表の文だけ。
- **DN-502-2** 店舗画面・管理画面の文言ファイルを変えない。
- **DN-502-3** 並行する #569・#549 が `messages.properties` に加えた行と変えた行には、手を入れない。この spec の行だけを変える。

## Non-goals

| 項目 | 理由 |
|------|------|
| 店舗向けの文と、店舗画面の文言ファイルの敬語の統一 ※1 | 店舗画面の文言の方針として決めることで、店舗画面の文言ファイルも変えるため。Open questions の 2 で確認する |
| 範囲の書き方（「1〜{max} 文字」と「1 文字以上 {max} 文字以内」）の統一 | Open questions の 4 で確認する |
| コード・コメント・テスト名の中の社内の語（「C 側」「形」） | 画面に表示されないため |

※1：対象は、文の「お選びいただけません」「お問い合わせください」「お待ちください」と、文言ファイルの「お支払い待ちのご注文」など。

## Open questions

1. 整理の spec で、メッセージの文（画面の表示）を変えてよいか。整理の spec は振る舞いを変えない規則（[開発の進め方](../../05-開発規則/workflow.md)の「spec の種類と書くこと」）と食い違う。
   - 案 A（推奨）：この spec だけの特例にする。AC を変えず、変わるのは文だけで、利用者が「変える文」の表で確認するため。
   - 案 B：機能の spec にする。機能の spec には User stories と AC を書くが、この変更には書く振る舞いがない。
2. 店舗向けの文の敬語をこの spec で扱うか。推奨：扱わない（Non-goals のとおり）。
3. 規則の確認方法。
   - 案 A（推奨）：自動。メッセージのテストに、DC-502-3 の使わない言い回しが文にないことの確認を加える。今のテストは、文に 2 以上の数字がないことを確認している（[バックエンドの書き方](../../05-開発規則/backend-coding.md)の「エラーは `XxxErrorCode` と `BusinessException`」の確認方法）。
   - 案 B：レビューだけ。
4. 範囲の書き方をそろえるか。推奨：そろえない。今は、品番・数量・桁は「1〜{max}」、名称の文字数は「1 文字以上 {max} 文字以内」で、どちらも読み違えにくい。品番の文に「1 文字以上 {max} 文字以内」を使うと、もともと長い文がさらに長くなる。
5. 規則の案（決定の規則 1〜6）と、「変える文」の表の 14 件の文を、この形で確定してよいか（画面の文言は利用者が決める）。
