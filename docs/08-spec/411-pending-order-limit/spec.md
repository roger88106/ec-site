# Spec 411：会員ごとの支払待ちの注文に上限を設ける

種類：機能　規模：L　ステータス：草案

## 背景と目的

確認済みのメールアドレスを持つ会員は、支払わずに在庫を確保し続けられる。注文が成立すると在庫が減り、支払は期限（既定 30 分）まで必要ない。支払待ちの注文は運営者もキャンセルできない（AC-158）。このため、注文を繰り返すと、商品を売り切れのまま保てる。issue #411 で、バックエンドの統合テストで確認した。店舗画面は操作していない。

この spec の目的は、1 人の会員が支払わずに確保できる在庫を限ることである。会員ごとの支払待ちの注文の数に上限を設け、上限に達した会員の新しい注文を拒否する。拒否された会員は、店舗画面で支払待ちの注文へ案内される。

追跡の issue は #411。関わる文書は、[注文モジュール](../../03-機能仕様/order.md)の「支払待ちの注文の確認」、[注文の設計](../../02-設計/order.md)の「同時の注文」、[バックエンドのアーキテクチャ](../../02-設計/backend-architecture.md)の「公開ネットワークへのデプロイの前提」。

利用者は 2026-11-06 に、次を決めた。

- 上限は 3 件とする。実績に基づかない暫定の値である。
- 上限に達したときはエラーを返し、店舗画面で支払待ちの注文へ案内する。
- 複数のアカウントによる回避は、この spec で扱わない。アプリの外に置く入口のレート制限で扱う。

## スコープ

| 含める | 含めない |
|--------|----------|
| 注文の時点の上限の判定と拒否 | 複数のアカウントによる回避の防止 |
| 注文手続きの開始時の上限の判定と拒否 | 入口のレート制限の実装 |
| 同時に注文した場合に上限を超えないこと | 支払待ちの注文のキャンセル |
| 店舗画面での拒否の表示と、支払待ちの注文への案内 | 上限の値を運営者が画面で変えること |
| 公開ネットワークへのデプロイの前提への追記 | |
| 機能仕様と設計の文書の更新 | |

## User stories

| US | 誰が | 何をできる | なぜ |
|----|------|------------|------|
| US-411-1 | 運営者 | 1 人の会員が支払わずに確保できる在庫を、支払待ちの注文の上限までに限る | 他の消費者が買えない状態を、1 人の会員が作り続けられないようにするため |
| US-411-2 | 消費者 | 上限に達して注文できないとき、その理由と、支払待ちの注文を支払う道を知る | 注文できない理由が分からないまま、注文を何度も試さないため |

## 受け入れ条件

### US-411-1 支払待ちの注文の上限（B / P1）

- **AC-411-1** 会員の支払待ちの注文が上限の件数（3 件）に達しているとき、注文を拒否する。注文を作らず、在庫を減らさない。
- **AC-411-2** 会員の支払待ちの注文が上限より少なければ、従来どおり注文できる。上限 − 1 件のときに注文すると成立し、支払待ちが上限の件数になる。
- **AC-411-3** 会員の支払待ちの注文が上限の件数に達しているとき、確認した注文を送って注文手続きを開始するときも、拒否する。注文手続きを作らず、在庫の引当を変えない。前の注文手続きの引当も解かない。
- **AC-411-4** 上限の判定は、支払待ちの注文の確認の判定（AC-406-1、AC-406-11）の後に行う。確認していない支払待ちの注文があるときは、上限に達していても、確認を求める応答を返す。
- **AC-411-5** 同じ会員の注文手続きから同時に注文しても、支払待ちの注文が上限の件数を超えない。
  - Given：支払待ちの注文が上限 − 1 件で、それらを全て確認した注文手続きが 2 つある。
  - When：同時に注文する。
  - Then：一方だけ成立し、在庫が 1 件分だけ減り、他方は拒否される。
- **AC-411-6** 支払待ちの注文が、期限切れのキャンセルか、与信の成功による受付で上限より少なくなったら、再び注文手続きを開始して注文できる。
- **AC-411-7** 同じ注文手続きの再送は、上限に達していても、従来どおり作成済みの注文を返す（AC-91 を変えない）。
- **AC-411-8** 変更を適用した時点で、既に上限以上の支払待ちの注文を持つ会員も、判定の対象にする。既存の注文は変えない。

### US-411-2 上限に達したときの店舗画面（C / P1）

- **AC-411-9** 店舗画面は、注文手続きの開始が上限で拒否されたら、支払待ちの注文の確認の画面に、上限に達したため新しく注文できないことと、支払うか期限切れを待つよう促す文を表示する。
- **AC-411-10** 店舗画面は、注文が上限で拒否されたら、支払待ちの注文の確認の画面へ遷移し、AC-411-9 と同じ文を表示する。入力したお届け先は保存しない。
- **AC-411-11** AC-411-9、AC-411-10 の確認の画面でも、支払の期限の前の注文には「支払へ進む」を表示する（AC-406-5、AC-406-6 を変えない）。

## 業務ルール

- **BR-411-1** 上限の件数は、会員ごとの支払待ちの注文の数で数える。支払の期限を過ぎていても、期限切れのキャンセルが済むまでは数える。理由：キャンセルまで在庫は戻らないため（BR-406-1 と同じ）。
- **BR-411-2** 上限の判定は、注文の時点の判定を正とする。開始の時点の判定は、お届け先を入力してから拒否されることを減らすためのものである。理由：開始の後に、別の注文手続きから注文が成立しうるため。

## 非機能要件

- **NFR-411-1** 上限の判定はサーバーで行い、画面の判定に頼らない。同時の注文の判定は DB で保証し、JVM 内のロックを使わない（constitution の「水平スケール」）。
- **NFR-411-2** 上限の件数は、設定で変えられる。既定は 3 件である。理由：暫定の値で、実績を見て変えるため。

## Non-goals

| 項目 | 理由 |
|------|------|
| 複数のアカウントによる回避の防止 | 利用者の決定（2026-11-06）。アプリの外に置く入口のレート制限で扱う |
| 入口のレート制限の実装 | デプロイ先が決まっていないため。デプロイの前提に挙げる |
| 支払待ちの注文のキャンセル | AC-158 を変えない（spec 406 と同じ） |
| 上限の値を運営者が画面で変えること | 暫定の値で、変える頻度が低いため。設定で変える |
| 確認の画面で、上限に達しているときに「新しく注文する」を隠すこと | 画面が上限の値を持つことになるため。押したときの拒否の文で案内する |
