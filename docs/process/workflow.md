# 開発の進め方

[constitution](../constitution.md) 第 4、13 節の細則。仕様駆動開発（SDD）で何を作るかを先に決め、テスト駆動開発（TDD）で作る。
番号と記号の意味は [文書の記号と番号](notation.md)、エージェントの作業の手順は [AGENTS.md](../../AGENTS.md) にある。

## 1. 仕様駆動開発（SDD）

### 1.1 流れ

| 段階 | 文書 | 書くこと |
|------|------|----------|
| spec | `spec.md` | 何を、なぜ作るかと、受け入れ条件（整理の spec は完了の条件）。実装（クラス名、カラム、フレームワーク）は書かない |
| plan | `plan.md` | 今回の変更について、モジュールをまたぐ決定、API と AC の対応、テストの割り当て、実装の順序。あわせて OpenAPI を書き、モジュールの設計が変わるなら `docs/backend/modules/` を更新する |
| tasks | `tasks/` | plan を検証可能な小さなタスクに分け、対応する AC を記す。段階ごとに 1 ファイル |
| 実装 | コード | tasks に沿って、TDD（第 2 節）で進める |

### 1.2 spec の種類と書くこと

| 種類 | 書くこと | 番号 |
|------|----------|------|
| 機能 | 背景と目的、User stories、受け入れ条件、業務ルール、非機能要件、Non-goals、Open questions | US・AC・BR・NFR |
| 整理 | 背景と目的、目的、完了の条件、非機能要件、Non-goals、Open questions | DS・DC・DN |

- 機能の spec は、単独で検証できる機能の縦切り 1 つ。
- 整理の spec は、消費者・運営者に見える振る舞いを変えない。変える必要が出たら、機能の spec にする。
- Open questions が空になるまで plan に進まない。
- DC の確かめ方（CI、テスト、検査の script、見直しで読む）は plan で決める。

### 1.3 文書の置き場所

| 内容 | 置き場所 |
|------|----------|
| 今回の変更（何を・どう・手順） | `docs/specs/NNN-*/` の spec・plan・tasks |
| モジュールの今の設計<br/>（集約、不変条件、公開する api・event、設計の理由） | `docs/backend/modules/<module>.md` |
| フロントのアプリの今の構成 | `docs/frontend/` |
| API の項目 | `api/openapi/` |
| テーブルの定義 | Flyway のマイグレーション（できるまでは `docs/backend/modules/` に草案） |
| 用語と識別子の対応 | `docs/reference/glossary.md` |
| コードの書き方 | `docs/backend/coding.md`、`docs/frontend/coding.md`、`docs/testing/writing.md`、`docs/process/comments.md` |
| 起動・テストの手順 | `docs/dev/` |
| spec の進み具合 | README の進捗の表 |
| 決定の経緯 | コミットメッセージ |

文書には今のルールと設計だけを書く。

### 1.4 spec と plan の書き方

| 対象 | 書き方 |
|------|--------|
| AC・DC | 1 つに 1 つの条件を、1〜2 文で書く。値の一覧と場合分けは、箇条書きか表にする |
| Given / When / Then | 同時の操作など、手順で示さないと分からない条件だけに使う |
| 括弧 | 1 文に 1 つまで。理由は文の後に `理由：〜ため。` で、長い補足は表の下に `※1：` で書く |
| plan の節 | 決定を表（何を、どこに、確かめ方）で先に示し、理由を後に書く。1 つの箇条書きに 1 つの決定 |
| 識別子 | ファイル・クラス・関数の名前は、表の列とコードブロックにだけ書き、本文は役割で書く（第 3.2 節） |
| 他の文書の内容 | モジュールの設計、API の項目、書き方の規則は写さず、その文書を指す |
| 参照 | 文書の名前と節で書く（`店舗画面の構成 第 4.5 節`）。constitution の節の番号は使わない |

- 完了した spec・plan・tasks は当時の記録として、内容と節の番号を変えない。直すのは、文書を移して切れたリンクのパスだけ。
- 今の設計は、モジュールの設計書と `docs/frontend/` に書くので、古い spec を今の形に書き直す必要はない。

理由：spec と plan は、利用者が承認の前に読み、実装の間にエージェントが何度も読むので、決定と条件を一目で拾えるようにするため。

## 2. テスト駆動開発（TDD）

### 2.1 循環

1. **レッド**：失敗するテストを書き、失敗することを確かめる。
2. **グリーン**：テストが通る最小の実装を書く。
3. **リファクタリング**：テストが通ったまま整える。次の振る舞いのレッドに進む。

振る舞いを変えないリファクタリングの前には、今の振る舞いを固定するテストを足してよい。このテストは最初から通るので、一時的にコードか期待値を変えて、失敗しうることを確かめる。

### 2.2 対象ごとの進め方

| 対象 | 進め方 |
|------|--------|
| domain | 厳密な TDD |
| AC 単位の振る舞い | 実装前に受け入れテストを書き、レッドから始める |
| infrastructure、Controller の配線 | 実装後に書いてよい |
| フロントの関数（判定、変換、表示の整形） | 厳密な TDD |
| フロントの主な操作の流れ（保存、エラーの表示、確認など） | 結合テストを書く。実装の前でも後でもよい |
| フロントの見た目 | 求めない（手で確かめる） |

## 3. 文書の書き方

### 3.1 言語

- Git に入るものはすべて日本語で書く：ドキュメント、コメント、Javadoc、テスト名、テストデータ、seed、コミットメッセージ、エラーメッセージ。
- 識別子（クラス名、変数名、API のパス、テーブル名・カラム名）は英語。
- 例外：外部から取り込んだ skill（`.claude/skills/`）は、原文の言語のまま置いてよい。出典の更新を取り込みやすくし、許諾の条件（原文と出典の表示）を守るため。その代わり、`SKILL.md` の frontmatter の直後に、何をする skill か・いつ使うかの日本語の説明をコメント（`<!-- -->`）で書く。このリポジトリ向けの追記と、自分で作る skill は日本語で書く。

### 3.2 論理名と物理名

- spec・plan・モジュール設計書の本文は、業務の用語（論理名）で書く。
- 識別子（物理名）を書くのは、[用語集](../reference/glossary.md)、表の識別子の列、コードブロックだけにする。
- 新しい用語や識別子を作ったら、用語集に追加する。
- 実装の細部（SQL の句、アノテーション名など）は本文に書かず、意図だけを書く。
