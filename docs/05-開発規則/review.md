# 書き方の規則とレビュー

書き方の規則（[バックエンドの書き方](backend-coding.md)、[フロントの書き方](frontend-coding.md)、[テストの書き方](test-writing.md)、[バックエンドのテストの書き方](test-writing-backend.md)、[フロントのテストの書き方](test-writing-frontend.md)、[コメントの書き方](comments.md)）を書くときの形と、段階の最後のレビューでの使い方。

## 1. 規則の書き方

- 各節の規則と理由の後に、確認方法を `確認方法：` で始まる行に書く。1 つの節に確認方法の違う規則が複数あるときは、`確認方法：` だけの行の後に、規則ごとの箇条（`- <規則の短い名前>：<確認方法>`）を置く。規則の一覧の表は置かない。理由：同じ規則を表と本文の 2 か所に書くと、片方だけを修正して食い違うため。確認方法が「レビュー」の規則を集めたチェックリストは、skill `review` の script が作る。
- 確認方法は、自動（ArchUnit・Modulith のテスト、Biome、テスト、CI の script）かレビュー（段階の最後のレビューで読む）。自動のものは、使うツールやテストの名前を書く。
- 規則の節は、規則（何をどう書くか）と、1 行の理由（なぜか）を書く。細かな例外は ※ で、規則の後（表があれば表の下）に書く。
- constitution は原則を、各文書は具体的な書き方を書く。constitution の文を転記しない。
- 新しい習慣が決まったら、その spec の plan か tasks で各文書に追加する。

## 2. レビュー

各段階の最後のレビューで、変えたコードを、各文書の確認方法が「レビュー」の規則と照合する。レビューの段階の tasks は、本書を参照に挙げる。レビューは、実装の過程を見ていないサブエージェントが skill `review` の手順で行う。

1. 変えたファイルを、spec の最初の commit の 1 つ前（`<base>`）からの差分で特定する ※1。
2. 各文書の確認方法が「レビュー」の規則と照合しながら読み、合わない所を修正する。修正しないものは、理由をレビューの報告に書く。
3. 規則にない習慣に気づいたら、規則に追加するかを利用者に確認する。自動で確認できるようになった規則は、確認方法を「自動」に修正する。
4. 文書・コメント・コミットメッセージが、日本語として自然に書けていることも確認する。

※1：`git diff -M -l0 --name-status <base> HEAD | grep -v '^R100'`。`-l0` がないと、移動が多いときに移動の検出が打ち切られ、追加と削除として表示される。`R100`（中身の変わらない移動）は読まなくてよい。

## 3. 重要度

指摘の重要度は、次の 3 つ。他の文書は、この定義を指す。重要度を指すときは「重要度『高』の指摘」、危険度を指すときは「危険度が高い」のように書き、単独の「高」「低」は使わない。

| 重要度 | 内容 | 返す時点 |
|--------|------|----------|
| 高 | セキュリティ、データの破損、金額の誤りなど、誤った結果を生むもの | 全ての時点 |
| 必須 | 規則・spec・plan との食い違い | 全ての時点 |
| 推奨 | それ以外の改善（読みやすさ、一貫性、将来の保守） | spec の最後のレビューだけ。機械の検査に移せるかを付ける |

`[リスク]` のタスクの後と、段階の最後のレビューでは、レビュー役は重要度「高」と「必須」の指摘だけを返す。

## 4. レビューの収束

- **由来**：レビュー役は各指摘に「由来」を付ける。値は「今回」と「既存」。差分の外の行、または差分の前からある行への指摘は「既存」
- **既存の重要度「高」**：その spec が変えるファイルの中なら修正し、外なら起票の案にする
- **既存の重要度「必須」「推奨」**：修正しない。GitHub の issue「既存のレビューの指摘の一覧」に、spec の最後に spec ごとに 1 つのコメントで追加する（spec の番号、場所、指摘、重要度）。理由：spec ごとに起票の案にすると案が増える。定期の全体のレビューでまとめて扱えるので、コメントで追加するだけにする。issue は #252
- **2 回目以降**：同じ範囲の 2 回目以降のレビューは、前回のレビューの commit から HEAD までの差分と、前回の指摘の修正だけを対象にする。結果の置き場所に、レビューした commit を記録する（skill `review` の手順 1）
- **上限**：同じ対象のレビューと修正の繰り返しは 3 回まで。3 回目で重要度「高」「必須」の指摘が残ったら、修正の前提を 1 文で書いて再検討し、止まって利用者に報告する
- **同じ種類の指摘**：修正の前に、対象の全体を検索してまとめて修正する。spec 担当のセッションが修正の指示に検索の式を入れ、実装役は式と件数を報告に書き、spec 担当のセッションが tasks の結果に転記する
- **同じ判定の別の書き方の指摘**：同じ判定の別の書き方の指摘が 2 回続いたら、spec 担当のセッションは、修正の前提を変える案を利用者に提示する。変え方は、禁止の一覧から許可の一覧へ替えるか、対象の外（既知の制限）とするか。理由：禁止する形を 1 つずつ加えても、回避の書き方が尽きないため
- **採らなかった指摘**：採らなかった指摘と起票の案にした指摘を、各レビューの結果の置き場所（skill `review` の手順 1）の `rejected.md` に書く。同じ spec の後のレビューでは、それまでの `rejected.md` を全てレビュー役に渡す。渡すときは、skill `review` の prompts.md の「指示のひな形（観点ごと）」の根拠の欄「採らなかった指摘の一覧」にパスを書く。レビュー役は、同じひな形の「この一覧の指摘は返さない」に従う
