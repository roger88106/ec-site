# Spec 157：管理画面と共有のパッケージの部品とテストの書き方を整える

ステータス：草案

## 1. 背景と目的

spec 134 で管理画面と共有のパッケージを整えた後に、共有の部品の使い方の案内、管理画面のテストと型の書き方、数の整形の重複が残った。あわせて、フロントのテストのコードを、[テストの書き方](../../rules/test-writing.md)と[フロントの書き方](../../rules/frontend-coding.md)にそろえる。

| 項目 | 値 |
|------|----|
| 追跡の issue | [#157](https://github.com/roger88106/ec-site/issues/157) |
| 作業ブランチ | `157-frontend-tidy` |

扱う issue は次のとおり。

| issue | 扱う部分 |
|-------|----------|
| #149 | 共有の部品の一覧と使い方を、画面を作るときの skill に書く部分。共有の部品を使わずに書いた箇所を script で検出する部分は #158 が扱う |
| #150 | 全体（管理画面のテストと型の書き方、管理画面の構成の用語） |
| #151 | 全体（数の整形） |
| #16 | フロント（管理画面、店舗画面、共有のパッケージ）のテストのコード。バックエンドの部分は後の spec が扱う |

#16 は範囲が広いので、spec を書く前に、フロントのテストのファイル（管理画面 42、店舗画面 56、共有のパッケージ 7）を 2 つの書き方の規則と照合した。レビューは 2026-10-23 に、範囲ごとに汎用のモデルで 2 回行い、両方の指摘を合わせた。指摘は高 0、必須 12、推奨 約 30 件（重複を除く）で、spec 134 の起票の案（#150）の指摘も全て残っていた。目的と完了の条件は、この結果から決めた。

本 spec は整理の spec である（[文書の記号と番号](../../rules/notation.md)）。

## 2. 用語

| 用語 | 意味 |
|------|------|
| 共有の部品 | 共有のパッケージにある、2 つの画面で使うコンポーネントと関数（金額の内訳、リンクの見た目のボタン、注文の表示名、「すべて」を先頭に付けた選択肢、整形 など） |
| テストの補助 | 複数のテストで使う、データの作成、API の差し替え、操作、確認の関数。各画面のテストの補助の置き場所に置く |
| 既定の数の整形 | 既定のロケールで、3 桁ごとに区切る数の整形。金額の整形の数の部分も同じ |
| 型を回避する変換 | 値の型を検査させずに、別の型として扱わせる書き方。例：`as never`、`as unknown as` |

用語集に追加する語は、plan で決める。

## 4. 目的と完了条件

### DS-157-1 共有の部品の案内（D / P1）

対象の skill は `new-screen` である。

- **DC-157-1** skill に、共有の部品の一覧（置き場所、役割、使う場面）がある。一覧は、共有のパッケージのコンポーネントと関数の全てを含む。
- **DC-157-2** skill に、画面に同じ表示や処理を書く前に、共有の部品を探して使う手順がある。

### DS-157-2 数の整形（D / P1）

- **DC-157-3** 既定の数の整形を作る箇所は、共有のパッケージの 1 か所だけである。
- **DC-157-4** 管理画面の数の整形、共有のパッケージの金額の整形、店舗画面の税込・税抜の金額の表示は、DC-157-3 の整形を使う。
- **DC-157-5** 既定と違う書式の数の整形（符号付き、率、短縮）は、使う画面に残す。理由：片方の画面だけで使うため（[フロントの書き方](../../rules/frontend-coding.md) 第 5.1 節）。Open questions 2 で確定する。

### DS-157-3 管理画面の型と構成（D / P1）

- **DC-157-6** 自分の権限の一覧を読む処理の戻り値は、状態（取得中・失敗・取得済み）ごとの型である。各状態の型は、その状態に関係する値だけを持つ。例：失敗の中身と再試行は、失敗の型だけが持つ。
- **DC-157-7** レポートの条件の項目（粒度、送料を除く、商品の指定）の props の型は、1 か所に定義する。レポートの共通の画面と条件のフォームは、その型を使う。
- **DC-157-8** 商品の項目のフォームに渡す制約の組は、操作の契約のスキーマ（登録の要求、更新の要求）から、同じ関数で作る。制約は今と同じく、操作ごとのスキーマから取得する（spec 134 の DC-134-22）。
- **DC-157-9** [管理画面の構成](../../design/apps/admin.md)の「middleware」（3 か所）を「ミドルウェア」にし、店舗画面の構成の用語とそろえる。

### DS-157-4 探し方と API の差し替え（D / P1）

- **DC-157-10** 結合テストは、コンポーネントの内部の属性、CSS のクラス、内部の要素を使って要素を探さない（[テストの書き方](../../rules/test-writing.md) 第 4.1 節）。
- **DC-157-11** DC-157-10 で探す名前がない要素には、画面に支援技術向けの名前を追加する。
- **DC-157-12** 結合テストは、DOM の位置（隣の要素、親の要素、HTML の要素の種類）と、並びのインデックスを使って要素を探さない。
- **DC-157-13** 詳細の項目の値と一覧の行は、テストの補助を使って、項目名と行の名前で探す。
- **DC-157-14** HTML に描画して確認する店舗画面と共有のパッケージのテストは、Tailwind のクラスの文字列、見た目のための要素、属性の並びに依存せずに確認する。見た目は目視で確認する（[テストの書き方](../../rules/test-writing.md) 第 1 節）。例：取り消し線、代わりの図。
- **DC-157-15** API の差し替えは、型を回避する変換を使わず、OpenAPI の型に合ったハンドラーで応答を返す（[テストの書き方](../../rules/test-writing.md) 第 4.2 節）。
- **DC-157-16** 契約にない応答だけは、型付きのハンドラーの外で作り、理由をコメントに書く。例：通信の失敗。
- **DC-157-17** DC-157-15 でテストが使うステータスコードが契約にないときは、バックエンドの振る舞いを確認し、契約の不足なら契約の文書を先に修正する。不足かどうかと修正の方法は plan で決める。
- **DC-157-18** API の差し替えの外でも、テストの値の型を、型を回避する変換で一致させない。型に合う値を作るテストの補助を使う。

### DS-157-5 テストの名前と確認（D / P1）

- **DC-157-19** テストの名前とまとまり（describe）の名前は、関数名をそのまま書かず、振る舞いを「〜すると〜になる」の形で書く。出典は[テストの書き方](../../rules/test-writing.md) 第 2.2 節。
- **DC-157-20** 複数の AC の番号は、読点で区切る形で書く。例：`AC-8、9、10`。
- **DC-157-21** AC の番号は、まとまりの名前だけでなく、AC を確認するテストの名前の先頭に書く（[テストの書き方](../../rules/test-writing.md) 第 2.1 節）。
- **DC-157-22** テストの名前に書いたこと（AC の番号を含む）は、全てテストの中で確認する。確認しないことは名前から外す。
- **DC-157-23** 例外の確認は、例外の種類か内容を確認する。
- **DC-157-24** 存在することだけを確認するテストは、値や状態の確認に置き換える。例：見つからなければ失敗する探し方の結果を、さらに真であると確認する書き方。
- **DC-157-25** 「起きないこと」を確認するテストは、処理の結果が画面に反映されるまで待ってから確認する（[テストの書き方](../../rules/test-writing.md) 第 5 節）。
- **DC-157-26** テストは、対象の実装と同じディレクトリの、その実装のテストのファイルに書く。
- **DC-157-27** 同じ振る舞いを確認するテストは、1 か所にまとめる。
- **DC-157-28** 本 spec の決定で追加した書き方の規則は、[テストの書き方](../../rules/test-writing.md)に書いてある。例：テストの関数の選び方、テストの補助の置き場所。Open questions 3 で確定する。

### DS-157-6 テストの補助とテストデータ（D / P2）

- **DC-157-29** 管理画面のレポートの 3 つの CSV のテストは、ダウンロード（URL の作成とリンクのクリック）を 1 つのテストの補助で差し替える。
- **DC-157-30** DC-157-29 の差し替えは、テストの後に元に戻す。
- **DC-157-31** 同じテストデータを、複数のテストのファイルで定義しない。テストの補助にある値は、その値を使う。
- **DC-157-32** 同じ API の差し替えを、複数のテストのファイルで定義しない。
- **DC-157-33** 店舗画面の標準エラー出力のログは、1 つのテストの補助で確認する。
- **DC-157-34** 全てのテストの後に行うクリーンアップを、各ファイルで繰り返さない。

DC-157-31、32 の主な対象は次のとおり。

| 種類 | 例 |
|------|----|
| テストデータ | 税区分、注文、お届け先、バリアント、本番の環境変数の一式、カートの ID |
| API の差し替え | 通信の失敗、409 の応答、在庫数の取得 |

## 5. 非機能要件

- **DN-157-1** 運営者・消費者に見える振る舞いを変えない。DC-157-11 で画面に追加する支援技術向けの名前は、見える文言を変えない。
- **DN-157-2** API の契約とデータベースの構造を変えない。DC-157-17 で修正するのは、今のバックエンドの振る舞いに合わせる契約の文書の記述だけである。
- **DN-157-3** AC を追加・変更しない。AC の番号をテストの名前に移したときは、AC 一覧のテストの列を再生成する。
- **DN-157-4** テストを修正するときに、確認を弱めない。修正したテストは、一時的に実装か期待値を変更して、失敗しうることを確認する（[開発の進め方](../../rules/workflow.md) 第 2.1 節）。
- **DN-157-5** shadcn/ui の生成物は修正しない（[管理画面の構成](../../design/apps/admin.md) 第 2 節）。
- **DN-157-6** CI の検査の script は変えない。script による検査に移せる指摘は、#158 に伝える。
- **DN-157-7** 並行の spec（#155、#156、#158）と同じファイルを変更する箇所は、plan に挙げ、その spec に知らせる。

## 6. Non-goals

| 項目 | 扱う場所 |
|------|----------|
| 共有の部品を使わずに書いた箇所と、テストの書き方の違反（型を回避する変換、内部の属性、AC の番号の区切り など）を script で検出すること | #158 |
| バックエンドのテストのコードを書き方の規則にそろえること | #16（バックエンドのテストの補強の spec） |
| E2E のテストのコード（Open questions 4） | #16 に残す |
| 新しい機能、画面の見た目の変更 | 新しい機能の issue で扱う |

## 7. Open questions

1. **#16 の推奨の指摘の範囲**：レビューの推奨の指摘を、どこまで本 spec に含めるか。
   - 案 A（推奨）：第 4 節の DC の全て。ただし、次の 2 つは本 spec から外し、#16 に残す。
     - 店舗画面の HTML に描画するテストを、全て DOM に読み込んで役割と名前で探す形に書き換えること。約 20 ファイルある。本 spec では、DC-157-14 の、見た目に依存する確認を修正する箇所だけを扱う。
     - 店舗画面の 2 つのフォームのテストが React の関数を差し替えている箇所を、結果を props で受けるコンポーネントに分けること。理由：画面のコンポーネントの構成を変えるため。
   - 案 B：必須の指摘と、#150 が挙げた箇所（DC-157-6〜8、10、14、29、30）だけにし、残りの推奨は #16 に残す。
   - 案 C：推奨の指摘を全て含める。
2. **数の整形の範囲**（DC-157-3〜5）：#151 の完了の目安は「`Intl.NumberFormat` を作る所が共有のパッケージの 1 か所だけ」である。今は既定の書式が 3 か所あり、ほかに管理画面だけで使う書式（符号付き、率、短縮）が 3 か所ある。
   - 案 A（推奨）：既定の書式の 3 か所だけを共有の 1 か所にし、管理画面だけの書式は管理画面に残す。[フロントの書き方](../../rules/frontend-coding.md) 第 5.1 節の、片方の画面だけで使うものを共有に入れない規則に合う。
   - 案 B：全ての書式を共有のパッケージに移す。
3. **テストの関数の選び方**（DC-157-28）：テストの関数に `test` と `it` が混ざっている。`test` を使うファイルは約 80、`it` を使うファイルは約 25 で、管理画面の画面のテストは `it` を使う。
   - 案 A（推奨）：`test` にそろえ、テストの書き方に書く。`test` のファイルが多いので、変更するファイルが少ない。
   - 案 B：`it` にそろえる。
   - 案 C：そろえない（規則を書かない）。
4. **E2E**：#16 の「テストのコード」に E2E を含めるか。今回のレビューは E2E を対象にしていない。
   - 案 A（推奨）：本 spec では扱わず、#16 に残す。
   - 案 B：本 spec に含める。spec を確定する前に、E2E のレビューを行う。
