# Spec 572：出荷のイベントからメールアドレスを外し、通知は注文の API で宛先を読む

種類：整理　規模：M　ステータス：確定

## 背景と目的

公開のイベントには個人情報を載せず、受ける側が必要なら公開の API で読む。この方針は #558 で決め（2026-11-18）、規則は[バックエンドのアーキテクチャ](../../02-設計/backend-architecture.md)の「モジュラーモノリス」にある。理由：イベントの記録は、処理を終えた後も保存期間（既定 7 日）の間 DB に残るため。

今、個人情報を載せている公開のイベントは、注文の出荷（メールアドレス）だけである。この spec で、出荷のイベントからメールアドレスを外し、通知が注文の API で宛先を読むようにする。消費者・運営者に見える振る舞い（出荷通知メールの宛先と内容）は変えない。追跡の issue は #572（全体の issue #544 の sub-issue。段階 2 の「#558 の決定から作った issue」）。

規模は、判定の表では 2 つ以上のモジュール（注文、通知）にまたがるので L になる。ただし、API の契約（OpenAPI）・DB の構造・AC を変えず、決定が少ないので、特例で M とする（issue 担当のセッションが、利用者の委任で承認する）。#569 と同じ扱い。

## スコープ

| 含める | 含めない |
|--------|----------|
| 注文の出荷のイベントから、メールアドレスを外すこと（注文 ID・注文番号・配送業者・送り状番号は残す） | 出荷と状態の変化の 2 つのイベントを注文が発行すること（今のまま） |
| 注文の公開の API に、注文のメールアドレスを返す操作を加えること | 通知から出荷モジュールの API への依存（配送業者の表示名。今のまま） |
| 通知モジュールが、注文の API を腐敗防止層を通して呼び、宛先を読むこと | 保存期間の値（既定 7 日）の変更 |
| 設計書・機能仕様・用語集・Javadoc の説明の修正 | 送ったメールの記録（通知モジュールのテーブル）に宛先を残すこと（今のまま） |
| | 変更の前に記録された、メールアドレスを含む未完了のイベントとの互換性 |

決定：

- 注文の API に、注文 ID で注文のメールアドレスを返すメソッド `OrderApi.findEmail(UUID orderId)` を加える。戻り値は `Optional<String>`（注文がなければ空）。理由：返す個人情報をメールアドレスだけにするため。
- 注文の参照の型（`OrderSnapshot`）には加えない。理由：注文の参照の型はレポートが使い、個人情報を返さない規則が注文の設計書の「他のモジュールへの公開」にあるため。
- メソッドの名前は、提供する側の用語で、呼ぶ側の名前を入れない（[バックエンドの書き方](../../05-開発規則/backend-coding.md)の「名前の形」、#569 の決定）。
- 通知モジュールに、注文の腐敗防止層を作る。port は `OrderDirectory`（`notification/application/port/`）、実装は `OrderApiDirectory`（`notification/infrastructure/directory/`、public にしない）。通知モジュールの許可する依存に `order::api` を加える。
- 通知は、出荷通知メールを送る前に、腐敗防止層で宛先を読む。注文が見つからないときは例外を投げ、イベントを未完了のまま残す（送ったメールの記録も残さない）。理由：出荷のイベントは出荷の登録で発行するので、注文がないのは不整合で、メールを送らずに完了にすると気づけないため。
- 宛先を読む時点は、送ったメールの記録の前にする。理由：記録に宛先を書くため。
- 保存期間の既定（7 日）は変えない。バックエンドのアーキテクチャの「片付け」の保存期間の理由から、括弧書き「イベントの記録には購入者のメールアドレスが入る」を削除する。理由は Non-goals に書く。
- イベントの配送業者の列挙（`OrderShipped.Carrier`）と、出荷の腐敗防止層は変えない。
- テストは次のとおり。
  - 注文の API の統合テスト（`OrderApiTest`）に、注文のメールアドレスを返すことと、注文がなければ空を返すことを加える。
  - 通知の腐敗防止層の実装の単体テストを加える。
  - 通知の統合テスト（`ShipmentMailTest`、`SmtpTimeoutTest`）は、注文を作らずにイベントを発行している。注文の腐敗防止層をテスト用に置き換え、イベントの注文 ID に対応する宛先を返す。テスト用の宛先は、イベントのメールアドレスに頼らずに、テストが持つ値にする。期待値（宛先、件名、本文、通数）は変えない。
  - 通知の統合テスト（`ShipmentMailTest`）に、注文が見つからないとき、メールを送らず、イベントが未完了のまま残ることを加える。
  - 出荷通知メールのサービスの単体テスト（`ShipmentMailCommandServiceTest`）は、腐敗防止層から宛先を受ける形にする。注文が見つからないときに、記録も送信もしないことを加える。
  - 本物の注文の出荷からメールが会員のメールアドレスに届くことは、今の E2E（`e2e/tests/shipping.spec.ts`）が確認している。変えない。
  - イベントを作るテスト（`OrderShipmentTest`、`ShipmentApiTest`、`OrderStatusChangedEventTest` など）は、メールアドレスの引数を外す。イベントのメールアドレスを確認する部分（`OrderShipmentTest` の検証、`ShipmentMailTest` の処理の待ちの条件）は、削除するか、注文 ID などの残る項目で書き換える。他の期待値は変えない。
- 修正する文書は次のとおり。
  - `docs/02-設計/backend-architecture.md`：「片付け」の保存期間の理由の括弧書き。
  - `docs/03-機能仕様/order.md`：「出荷の登録」の、イベント「注文の出荷」に載せる値からメールアドレスを外す。
  - `docs/03-機能仕様/notification.md`：宛先は注文の API で読み、他の値はイベントに載っている、と修正する。
  - `docs/02-設計/notification.md`：「境界」の「注文の API は呼ばない」を、注文の API の「注文のメールアドレス」の操作を腐敗防止層を通して使う、に修正する。「出荷通知メールの送信」の図に、宛先を読む呼び出しを加える。
  - `docs/02-設計/order.md`：「他のモジュールへの公開」の表に API「注文のメールアドレス」（利用者は通知）を加え、その節の説明を修正する。「注文の参照」の「メールアドレスは返さない」は残す。
  - Javadoc：`OrderShipped`、通知モジュールの `package-info.java`、`ShipmentMailCommandService`。

## 目的と完了条件

### DS-572-1 公開のイベントに個人情報がない（D / P1）

- **DC-572-1** 注文の出荷のイベントに、メールアドレスがない。注文 ID・注文番号・配送業者・送り状番号は残っている。
- **DC-572-2** 公開のイベント（全モジュールの `event/`）に、メールアドレス・氏名・住所・電話番号の項目がない。

### DS-572-2 通知が注文の API で宛先を読む（D / P1）

- **DC-572-3** 通知は、注文の API の注文のメールアドレスを返す操作を、腐敗防止層を通して呼び、その値を宛先にする。
- **DC-572-4** 注文が見つからないとき、通知はメールを送らず、送ったメールの記録も残さず、イベントは未完了のまま残る。
- **DC-572-5** 注文の公開の API の型は、注文の参照の型に個人情報を加えていない。

### DS-572-3 振る舞いと文書が保たれる（D / P1）

- **DC-572-6** 出荷通知メールの宛先・件名・本文・通数の期待値を変えずに、既存のテスト（AC-183〜185）と E2E が通る。
- **DC-572-7** 設計書・機能仕様・用語集・Javadoc が、変更後の設計（イベントに宛先がなく、通知が注文の API で宛先を読む）を説明している（決定の「修正する文書」）。
- **DC-572-8** `./gradlew check` と統合テストと、文書の検査（`doc-refs.mjs`、`note-numbers.mjs`、`ja-text.mjs`）が通る。

## 変える範囲

パスは、`backend/ecsite/src/main/java/com/ecsite/module/` からの相対パス。ただし、テストと文書の行は、リポジトリのルートからのパス。

| まとまり | ファイル |
|----------|----------|
| イベント | `order/event/OrderShipped.java`、`order/domain/order/Order.java` |
| 公開の API | `order/api/OrderApi.java` |
| 通知 | `notification/package-info.java`、`notification/application/`（`ShipmentMailCommandService`、`port/OrderDirectory`）、`notification/infrastructure/directory/OrderApiDirectory` |
| テスト | `backend/ecsite/src/{test,integrationTest}/java/com/ecsite/module/{order,notification}/` の関係するテスト |
| 文書 | `docs/02-設計/{backend-architecture,notification,order}.md`、`docs/03-機能仕様/{order,notification,glossary}.md` |

## 非機能要件

- **DN-572-1** 消費者・運営者に見える振る舞い（出荷通知メールの宛先・件名・本文、1 通だけ送ること、送信の失敗と再試行）を変えない。
- **DN-572-2** API の契約（OpenAPI）と DB の構造を変えない。
- **DN-572-3** 既存のテストの期待値を変えない。変えるのは、イベントの引数、イベントのメールアドレスを確認する部分（決定の「テスト」）、テストの準備（宛先を返す腐敗防止層）だけ。
- **DN-572-4** 出荷のイベントを受けるハンドラーのスレッドプール（外部サービス用）と、トランザクションの扱い（コミットの後に新しいトランザクションで受ける）を変えない。

## Non-goals

| 項目 | 理由 |
|------|------|
| 保存期間の値の変更 | 整理の spec で値を変えないため。保存期間の規則（BR-38）は、他のデータ（引当、注文手続き、カート）にも当てはまるため ※1 |
| 変更の前に記録された、メールアドレスを含む未完了のイベントとの互換性 | デプロイ先がなく（constitution の「CI/CD」）、記録が残るのは手元の DB だけで、DB は再作成できるため |
| 送ったメールの記録に宛先を残すことの変更 | 記録は通知モジュールのテーブルで、公開のイベントではないため |

※1：保存期間の値と対象のデータは、バックエンドのアーキテクチャの「片付け」の表にある。
| 出荷のイベントと状態の変化のイベントを 1 つにすること | issue で今のまま残すと決めているため |
| 通知から出荷の API への依存の変更 | issue で今のまま残すと決めているため |
