# Spec 249：中国語の混入と不自然な日本語の検査をまとめ、コメントと文体に広げる

ステータス：確定

## 1. 背景と目的

整理の段階（milestone「整理の段階」）の第 1 段として、日本語の文の検査を再構成する。今は、中国語の混入の検査と文書の用語の検査が別々の場所にある。文書の用語の検査（`doc-terms`）は、コードのコメントとコミットメッセージを調べない。文体の読みにくさ（「の」の連なり、長い文）は、規則があっても守られていない。

追跡の issue は [#249](https://github.com/roger88106/ec-site/issues/249) である。扱う issue は次の 2 つである。

- [#234](https://github.com/roger88106/ec-site/issues/234)：コードのコメントの用語と、改善のまとまりを数える中国語の書き方
- [#100](https://github.com/roger88106/ec-site/issues/100)：1 文の長さと読点の数

関連する issue は [#187](https://github.com/roger88106/ec-site/issues/187)（バージョンの意味の語。クローズ済み）である。

作業ブランチは `249-ja-check` である。本 spec は整理の spec で、規模は M である。規模は issue 担当のセッションが見込み、2026-10-28 に利用者が第 1 段の spec の分け方とともに承認した。AC、API、データベースは変えない。

第 1 段は 6 つの spec（#245〜#250）が並行する。マージは、利用者が全ての pull request を確認してから行う。本 spec の検査は、第 4 段（全ての内容の日本語の走査）のツールになる。以下、「第 1 段」「第 4 段」は整理の段階の区分を指し、「段階 1」「段階 2」は本 spec の tasks の区分を指す。

候補の一覧（R- の番号）は、issue 担当のセッションの作業用の記録（Git に入らない）である。本 spec に必要な内容は、本 spec に書いた。

### 2 つの層に分ける

検査を、原因で 2 つの層に分ける（利用者との検討、2026-10-28）。

| 層 | 内容 | 原因 | 置き場所 |
|----|------|------|----------|
| 層 1：日本語の書き方の規則 | 用語の統一、コメントとテスト名への適用、文体の warning | 書き手の言語によらない。今の日本語の文書にも「の」の連なりと長い文がある（第 1 節の文体の測定） | リポジトリの検査。CI と commit の前に実行する |
| 層 2：中国語の混入 | 中国語の字・用語、中国語の語感（直訳） | 利用者が中国語で指示し、日本語で書かせるため | リポジトリの skill に置き、中国語で指示する環境だけで有効にする。CI には入れない |

- 層 2 を CI に入れない理由：中国語の混入は、利用者が中国語で指示する作業の形から生じる。日本語で指示する環境では起きないので、全ての環境の標準の流れに入れる必要はない。
- 層 2 をリポジトリの skill に置く理由：script とテストを Git で管理でき、別の環境で中国語で指示するときにも使える。

### 中国語の混入は、書く時点では防ぎきれない

日本語だけで書かせたつもりのサブエージェントでも、中国語の語が混ざった（利用者、2026-10-28）。混入の元は次のとおりである。

- 会話：主のセッションは中国語の会話から日本語の要点を作るので、訳す時点で混ざる。
- 文書・コメント・コード：既に混ざった文を、エージェントが写して広げる。
- サブエージェントの文脈：2026-10-28 に、サブエージェントの文脈に何が入るかを調べた（次の表と ※1）。

| 文脈に入るもの | 普通のサブエージェント | `omitClaudeMd` を付けたサブエージェント |
|----------------|------------------------|------------------------------------------|
| 親のセッションの会話 | 入らない | 入らない |
| AGENTS.md | 入る | 入らない |
| 利用者の全体の指示（`~/.claude/rules/`） | 入る | 入らない |
| memory の索引（MEMORY.md） | 入る | 入らない |
| skill の一覧 | 入る | 入らない |
| git status、作業ディレクトリ、利用者のメールアドレス | 入る | 入る |

※1：`omitClaudeMd` は、サブエージェントの定義（`.claude/agents/`）の設定である。表は、`claude -p` の `--agents` で 2 つのサブエージェントを定義し、それぞれに文脈を報告させた結果である。

- 調べた時点で、memory の索引の 1 行が中国語だった。そのため、日本語だけで書かせたつもりのサブエージェントの文脈にも、中国語があった。spec 担当のセッションが memory を日本語に書き換え、「memory は日本語で書く」の memory を加えた（2026-10-28）。
- memory を直しても、主のセッションが中国語の会話から訳すことと、既に混ざった文を写すことは残る。そのため、書く時点の混入は防ぎきれないと考える。memory を直した後の混入の数は測っていない。
- 本 spec は、混入した後に、記録される前に安く見つけることを目指す。見つける時点は 3 つである（第 3 節の DS-249-5、6）。

| 時点 | 方法 | 見つけるもの |
|------|------|--------------|
| 書いた直後 | Claude Code の hook（ファイルの書き込みの後）が、中国語の字・用語を調べ、エージェントに返す | 字と用語 |
| commit の前 | git の hook が、追加行とコミットメッセージを調べる | 字と用語（書いた直後の検査を通らなかった書き込みを含む） |
| レビュー | 中国語を含む文脈を持たないサブエージェントが、差分の日本語を読む | 語感、直訳。機械の一致では見つからないもの |

### 「要求」

HTTP の request の意味の「要求」は「リクエスト」にそろえる候補である（R-001）。「要求」は、アーカイブの外の 124 ファイル（コードを含む）にある。HTTP の request の意味でない「要求する」も含み、それは残す。出現の数は測っていない。

### 外部の AI のレビューの指摘

2026-10-27 に、利用者が別の AI に第 6 弾の spec を読ませた（R-067）。warning やレビューの観点の候補として挙がった型を次に示す。具体例は修正済みのものが多いので、型として扱う。

- 「の」の連なり（1 文に 4〜6 個）。外部の AI の指摘で最も多かった。名詞を「の」でつなぎ続けて述語を落とす文も、同じ原因とみられる。
- 否定が続く文（「〜なく〜ない」）。
- 複合動詞の崩れ。「〜し直す」の「直す」だけを「修正する」に替えた形で、一括の置換の跡と推定される。本 spec の草案を書くときにも、置換の script で同じ崩れが起きた。
- 文脈で正誤が変わる語。例：バージョンの意味の語は中国語の書き方だが、エディションの意味の複合語（有料版）は日本語である。

崩れと確定する複合動詞の語（DC-249-3）は、「〜し直す」の動詞の連用形に「修正」が続く次の 15 語とする（T249-01-01、2026-10-28）。どの語も、アーカイブを含むリポジトリの全体とコミットメッセージに 0 件で、正しい日本語の一部にならない。

- 「修正」の前の語：書き、作り、置き、読み、やり、考え、組み、問い、洗い、貼り、撮り、練り、言い、数え、測り（それぞれの後に「修正」が続く形。語そのものを書くと error になるので、前の語を挙げる）

「し修正」（「やり直す」以外の「し直す」の崩れ）は、「少し修正」「もし修正」と形が同じなので、error にしない。DC-249-36 の warning で示す。

## 3. 目的と完了条件

完了条件は、第 6 節で選んだ案で書いた。

### DS-249-1 文書の用語の検査を、日本語の文の検査に広げる（D / P1）

- **DC-249-1** リポジトリに、日本語の文を調べる 1 つの検査がある。一覧の各項目は、error（失敗にする）か warning（失敗にしない）のどちらかである。
- **DC-249-2** 改善のまとまりを数える中国語の字が、error の項目にある。批判・批評などの日本語の語は、許す語に書く。
- **DC-249-3** 崩れと確定している複合動詞の形（第 1 節の「複合動詞の崩れ」のうち、実際に見つかった語）が、error の項目にある。崩れかどうかが文脈で決まる形は、DC-249-36 の warning にする。
- **DC-249-4** 誤検出の除外は、項目ごとの許す語と理由で書く。
- **DC-249-5** 層 1 の一覧と層 2 の一覧に、同じ字・語がない。中国語に由来する語のうち、層 1 に置くもの（DC-249-2 と決めたこと 8）は、層 1 の一覧だけにある。

### DS-249-2 検査の対象をコードのコメントとテスト名に広げる（D / P1）

- **DC-249-6** 検査が、次のソースのコメントを調べる。
  - Java（Javadoc を含む）と Gradle の設定（.kts）
  - TypeScript（.ts、.tsx）と JavaScript の script（.mjs、.cjs）
  - シェルの script（.sh）
- **DC-249-7** 検査が、テスト名を調べる。テスト名は、Java の `@DisplayName` の文字列と、フロントの `describe`・`it`・`test` の名前の文字列である。
- **DC-249-8** アーカイブの外のコメントとテスト名に、error の語がない。

### DS-249-3 文体の型を warning として示す（D / P1）

- **DC-249-9** 1 区間の「の」の数が閾値以上の文を、warning として示す。区間の定義は第 1 節の文体の測定と同じである。
- **DC-249-10** 字数が閾値以上の文を、warning として示す。
- **DC-249-11** 読点の数が閾値以上の文を、warning として示す。
- **DC-249-12** 否定が続く文（「〜なく〜ない」の形）を、warning として示す。
- **DC-249-13** warning だけのとき、検査は成功する。
- **DC-249-14** DC-249-9〜11 の閾値が、本 spec に数値で書いてある。
- **DC-249-36** 助詞を挟まずに、かなの直後に「修正」「確認」などの漢語が続く形を、複合動詞の崩れの疑いとして warning で示す。理由：「少し修正する」のような正しい日本語と、形では区別できないため。

### DS-249-4 層 1 の検査を commit の前に実行し、warning をエージェントが読む手順を作る（D / P1）

- **DC-249-15** commit の前の hook が、ステージした追加行を層 1 の検査で調べ、error があれば commit を失敗にする。
- **DC-249-16** commit の hook が、コミットメッセージを層 1 の検査で調べ、error があれば commit を失敗にする。
- **DC-249-17** commit の前の hook が、ステージした追加行の warning を表示する。warning だけなら commit は成功する。

## 6. 決めたこと

### 方向

2026-10-28 に、利用者と次を決めた。

- 検査を 2 つの層に分ける（第 1 節）。中国語の混入は、リポジトリの skill に置き、中国語で指示する環境だけで有効にする。CI には入れない。
- 書く時点の混入は防ぎきれないので、書いた直後、commit の前、レビューの 3 つの時点で見つける（第 1 節）。
- レビューは、`omitClaudeMd` を付けたサブエージェントに任せる。
- memory を日本語で書く。memory への書き込みも、書いた直後の検査の対象にする。

### 選んだ案

2026-10-28 に、利用者が次の 7 つとも案 A（推奨）を確認した。Open questions はない。検査の置き場所は上の方向で決めたので、番号を 2 から振る。

同じ日に、複合動詞の崩れの扱いと、error と warning の分け方も決めた（DC-249-3、36〜38）。崩れと確定している形だけを error にし、文脈で決まる形は warning にして、エージェントが読んで決める。

#### 決めたこと 3：文体の warning をどう作るか（#100）

影響する DC・DN：DC-249-9〜12、14、DN-249-5。

| 案 | 内容 |
|----|------|
| 案 A（推奨） | 自作する。数え方は第 1 節の測定と同じにし、否定が続く文は形の一致で見つける。依存のパッケージを加えない |
| 案 B | textlint と日本語の技術文書の規則集（preset-ja-technical-writing）を入れる。形態素解析で、助詞の重複や二重否定も見る。規則ごとに error・warning を選べる |

- 案 A の理由 1：対象にコードのコメントとコミットメッセージを含む。textlint は Markdown とテキストのファイルを読むツールなので、コメントを取り出して渡す処理が必要になる。コメントを取り出す処理は `scripts/ci/lib/` にすでにある。
- 案 A の理由 2：「の」の連なり、字数、読点は、数えるだけで見つけられる。否定が続く文は、形の一致で見つける。
- 案 A の理由 3：案 B は依存を加えるので、ライセンスの検査と Dependabot の対象が増える。形態素解析の辞書の分、インストールの時間と容量も増える。
- 案 A の注意：整理の段階の目的の 1 つは、外部のライブラリで済む所を自作しないことである。案 A は、コメントとコミットメッセージを読む必要から、この目的の例外とする。
- 案 B の理由：形態素解析で語を区切るので、正規表現より誤検出が少ないと見込まれる（測っていない）。整理の段階の目的に合う。
- 閾値は次の表のとおり決めた（T249-01-06、2026-10-28）。案のとおりである。warning は失敗にしないので、示す文が多くても commit は止まらない。
- 数は `node scripts/ci/ja-text.mjs --stats` で測った。対象は、アーカイブの外の文書（第 1 節の測定の対象に `.github/` と本 spec を加えたもの）と、コードのコメントとテスト名（`ja-text` の対象。語を挙げるテストを除く）である。コメントとテスト名は、複数行のコメントを行ごとに文とみなすため、文書より文の数が多い。
- 決めた閾値は `scripts/ci/ja-text.json` の `style` に書いた。

| 測るもの | 決めた閾値 | 文書で示す文 | コメントとテスト名で示す文 |
|----------|------------|--------------|----------------------------|
| 1 区間の「の」 | 4 以上（3 以上は 567・1,291、5 以上は 18・38、6 以上は 3・4） | 89 | 217 |
| 1 文の字数 | 100 以上（80 以上は 208・328、120 以上は 21・22） | 73 | 96 |
| 1 文の読点 | 5 以上（4 以上は 284・157、6 以上は 79・27） | 160 | 66 |

- 閾値を案から変えなかった理由：読点の 5 以上が文書で最も多い（160 文）が、4 以上は 284 文で、6 以上は 79 文に減る。5 は文書の約 2%で、1 回のレビューで読める数であり、「の」と字数の数（89・73）に近い。
- 閾値の対象の文のほかに、次の数も測った（文書・コメントとテスト名）。「〜なく〜ない」は 12・42、複合動詞の崩れの疑い（「修正」「確認」が続く形）は 12・5、「要求」を書いた行は 55・219 である。
- warning の一覧を出力するコマンド：`node scripts/ci/ja-text.mjs --warning`（リポジトリのルートで。終了コードは 0）。既定の実行（`node scripts/ci/ja-text.mjs`）は、warning の件数を「警告：」の行で示す。

#### 決めたこと 4：warning をエージェントにどう読ませるか

## 7. tasks

### 並行の判断

[エージェントの作業フロー](../../rules/subagents.md) 第 4 節の並行の規則を、本 spec に当てはめる。

- 本 spec の中：`[P]` のタスクはない。段階 1 のタスクは、層 1 の検査の script と一覧を変えるか、前のタスクが変えた script と一覧を使うため、番号の順に実装する。段階 2 のタスクは層 2 で、層 1 のファイルを変えないが、層 1 の後に順に実装する（作業ツリーを分ける手間のほうが大きいため）。
