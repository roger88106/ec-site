# Spec 018：文書とツールの整理

ステータス：確定

## 1. 背景と目的

spec 011〜017 で、ツール、テストの安全網、書き方の統一、セキュリティ、マスターデータ、安定性の整理を終えた。MVP の完成（spec 019）の前に、**文書とツールを 1→10 の開発に耐える形に整え、受け入れ確認に使うレビュー skill を作る**。

- 後回しにした作業（1→10、将来の spec、条件付きのもの）が、各 spec の Non-goals、レビュー結果、ローカルのメモに散らばっている。spec をアーカイブすると、探すたびに全ての spec を読むことになる。
- 全体構成図、レベル A のモジュールの構成、共通設定・ログ・可観測性の設計、ロールと権限の対応表、API の URL 規則がない。用語集と設計書には、古い記述と漏れがある。
- 文書の多く（完了した spec を含む）が、技術文書として不自然な言い回し（「確かめる」「待つ時間の上限」「〜の口」など）で書かれている。エージェントはこの書き方を読み、同じ書き方で出力する。
- `docs/specs/` が文書の 7 割を占め、規範・現在の設計・開発記録が同じ階層に並ぶ。現在有効な AC を知るには、全ての spec を読む必要がある。
- これまでのレビューは、作業したエージェント自身が spec の最後に差分を読んで行ってきた。「人手」の規則の多くは機械で検査でき、独立したレビューの仕組みもない。
- 振り返り（spec 015〜017）で挙げた改善と、spec 013・015 のレビューで残した項目が、まだ対応されていない。
- 依存ライブラリの既知の脆弱性と、リポジトリへの秘密情報の混入を検出する仕組みがない。

**コードを唯一の正とする**。文書とコードが食い違う場合は、コードに合わせて文書を修正する。コードが誤っている場合は、不具合として扱う。

本 spec は**整理の spec**（[文書の記号と番号](../../process/notation.md)）であり、消費者・運営者に見える振る舞いを変えない。DS・DC・DN の番号は、spec 017 からの連番とする。

## 2. 用語

| 用語 | 意味 |
|------|------|
| TODO 一覧 | MVP の後に行う作業と未決事項を 1 か所にまとめた文書。アーカイブしない |
| アーカイブ | 完了した spec・plan・tasks を開発記録の置き場所に移し、以後は参照専用とすること |
| AC 一覧 | 全ての AC について、現在の状態（有効、変更、廃止）、現在の内容の所在、テストの所在をまとめた一覧 |
| 文書レビュー | 日本語だけで書いた指示と文脈を渡したサブエージェントが、文書の言い回しをレビューすること |
| 日本語だけの文脈 | サブエージェントに渡す指示・参照する文書・会話の履歴が、全て日本語であること |

用語集への追加は plan で行う。

## 4. 目的と完了条件

### DS-46 後回しにした作業と未決事項が、アーカイブしない 1 つの一覧にある（D / P1）

- **DC-163** アーカイブの対象外に、TODO 一覧が 1 つある。spec 001〜017 の Non-goals とレビュー結果、MVP の完成までの一覧 第 3 節、ローカルのメモ、外部レビューの意見から、後回しにした項目を洗い出して載せる。
- **DC-164** 一覧の各項目に、テーマ、対応時期（1→10、条件付き など）、出典（spec と節、または決定日）がある。
- **DC-165** 「行わない」と決めた項目は、TODO 一覧ではなく、現在の設計の文書に理由とともに書く。設計の文書にない「行わない」の決定は、spec から移す。
- **DC-166** TODO の追加・完了のときにこの一覧を更新することが、AGENTS.md にある。spec の Non-goals に「1→10」と書く項目も、一覧に載せる。

### DS-47 「人手」の規則と、文書とコードの一致を、機械で検査する範囲を広げる（D / P1）

- **DC-167** バックエンドの書き方・フロントの書き方・テストの書き方の「人手」の規則のうち、機械で検査できるものを、ArchUnit か CI の検査 script で検査し、規則の一覧の確認方法を「自動」に変える。少なくとも次を含む。
  - 現在時刻を `Clock` から取得する、テストで Lombok を使わない、インスタンスを作らないクラスを `final` にする、列挙型の変換に `name()` を渡さない、本番コードのコメントに spec の番号を書かない
  - フロントの層・パッケージ間の import の方向（Biome の import 制限など）
- **DC-168** README の進捗、tasks のチェックボックス、MVP の完成までの一覧の状態が食い違う場合、CI の検査が失敗する。
- **DC-169** 設計の文書を変更した commit の spec が、その文書の概要表の「関連 spec」にない場合、CI の検査が検出する。既存の漏れは本 spec で修正する。
- **DC-170** 環境変数の文書の既定値と、コードの設定クラスの既定値が食い違う場合、CI の検査が失敗する。
- **DC-171** 単体テスト・統合テスト・テスト用共通コードの間に、完全修飾名が同じクラスがある場合、`check` が失敗する。
- **DC-172** 必須の設定がない状態で本番の jar を起動すると失敗し、エラーメッセージに設定名が出ることを、`check` で検査する。AC-245 を除外の一覧から外す。
- **DC-173** E2E の実行中に画面のビルドを始めると、ローカルの検査 script が理由を示して停止する。
- **DC-174** 用語集の識別子の列にある名前が、コードかデータベースに存在することを、CI の検査が確認する。
- **DC-175** 次の手順が文書にある。
  - ビルドスクリプトを変更したら、先にビルドの設定だけを評価する。
  - 長い検査（全体の検査、E2E、CI の完了待ち）は、最初からバックグラウンドで実行する（目安の時間を付ける）。
  - 移動・削除を含む plan を書く前に、テストを含む全ての呼び出し元を検索する。
  - Gradle のプロジェクトの場所。

### DS-48 過去の spec で残した項目に対応する（D / P1）

- **DC-176** モジュール構成の ArchUnit のレベル A の一覧に payment がある。金額型の ArchUnit が、表示用の型（`application/model/view/`）も検査する（spec 013 のレビューで残した項目）。
- **DC-177** 物流の mock のうち、テストだけで使う操作（不正な署名・日時の通知を作る）を本番コードに残すか移すかを決め、決定どおりにする（spec 015 のレビューで残した項目）。

### DS-49 依存ライブラリの脆弱性と秘密情報の混入を、GitHub の機能で検出する（D / P1）

- **DC-178** 依存ライブラリの既知の脆弱性の通知（Dependabot alerts）が有効である。
- **DC-179** 秘密情報の検出（secret scanning）と、秘密情報を含む push の拒否（push protection）が有効である。
- **DC-180** コードの静的セキュリティ解析（CodeQL）が Java と TypeScript を対象に動く。CI の時間には含めない。初回の結果の確認は spec 019 の DC-219 で行う。理由：既定の設定は `main` だけを見るが、`main` にはまだコードがないため（Dependabot alerts も同じ）。
- **DC-181** 有効にした機能と、結果の見方・対応手順が、開発者向けの文書にある。

### DS-50 現在の設計の文書に、全体像と不足していた設計がある（D / P1）

- **DC-182** システムの全体構成図がある。モジュールとその依存・イベントの図はコードから生成し、外部システム（IdP、決済、物流、メール、画像）とモジュールの役割の図は手動で書く。
- **DC-183** 手書きの図のモジュール一覧と依存が、コード（Spring Modulith の検出結果）と食い違う場合、CI の検査が失敗する。
- **DC-184** レベル A のモジュールの設計書に「構成」の節がある。
- **DC-185** 共通コード（`common/`、`config/`）、ログ、可観測性の設計の文書がある。
- **DC-186** ロールと権限の対応表（どのロールが、どの API・画面の操作を実行できるか）がある。対応表は契約と設定から生成するか、テストでコードと照合する。
- **DC-187** API の規約に URL の規則がある：`/api` の接頭辞、2 番目のセグメントの意味（契約の範囲であり、モジュールではない）、契約外の URL（通知、mock、運用）、リソース名、ネストの深さ、操作を表す URL、OpenAPI の `servers.url` と `paths` の関係。
- **DC-188** 公開ネットワークへのデプロイの前提の一覧（バックエンドのアーキテクチャ 第 7.3 節）に、spec の Non-goals にだけある前提を追加する（注文 URL の総当たり対策、通知のエンドポイント、匿名カートの作成回数、アップロード受付の保存期間、メトリクスのアラート、第三者ライセンスの告知と SBOM）。
- **DC-189** 用語集に漏れがなく（notification、`RefundRequested` など）、同じものを指す用語が統一されている。
- **DC-190** 文書に古い記述とリンク切れがない。spec 010 の後の全体レビュー（DOC-02〜17）の各項目を、現在の状態と照合して修正する。

### DS-51 全ての文書が、技術文書として自然な日本語で書かれている（D / P1）

- **DC-191** 対象は、`docs/` の全て（完了した spec・plan・tasks を含む）、README、AGENTS.md、自作の skill とする。
- **DC-192** エージェントが文書を実際に読み、技術文書として不自然な言い回しを候補として挙げる（場所、現在の書き方、修正案）。利用者が 1 件ずつ判断し、承認したものだけを修正する。tasks には修正の記録（ファイル、修正内容）だけを書く。
- **DC-193** 修正するのは言い回しだけとし、意味、番号、節の番号と構成、表の構成は変えない。完了した spec・plan・tasks の修正は、本 spec だけの特例とする（開発の進め方 第 1.4 節）。
- **DC-194** 文書の書き方の規則（skill `docs` 第 2 節）と言い換えの一覧（`doc-terms.json`）に、本 spec で決めた書き方と言い換えを追加する。MVP の完成までの一覧 第 4 節の 3 つ（〜の口、支払画面、client ID）を含む。
- **DC-195** 言い換えの一覧に追加した語は、コードのコメントと Javadoc でも修正する。

### DS-52 文書が規範・現在の設計・開発記録に分かれ、現在有効な AC が 1 つの一覧で分かる（D / P1）

- **DC-196** `docs/` が、規範（constitution、開発の進め方、書き方の規則）、現在の設計（アーキテクチャ、モジュール、画面の構成、API、用語集）、開発記録（spec・plan・tasks）に分かれている。spec のアーカイブの置き場所を決める（移動は spec 019 の最後に行う）。
- **DC-197** AC 一覧がある。全ての AC について、状態（有効、変更、廃止）、変更した spec、現在の内容の所在、テストの所在がある。
- **DC-198** AC とテストの対応の検査が AC 一覧を読み、有効な AC にテストがない場合と、廃止した AC をテストが参照している場合に失敗する。
- **DC-199** コードを唯一の正とすること、文書とコードが食い違う場合の扱い、AC の追加・変更を AC 一覧に反映する手順が、開発の進め方にある。

### DS-53 エージェントの作業フローを再検討し、レビュー skill がある（D / P1）

- **DC-200** 他の SDD の仕組み（cc-sdd、Spec Kit、OpenSpec など。調査時点の最新版）のサブエージェントの使い方を調査し、取り入れるもの・取り入れないものと理由を文書にする。
- **DC-201** サブエージェントに任せる作業と、使うモデルの選び方が文書にある。リスクの高い作業には高性能なモデルを使う。
- **DC-202** レビュー skill がある。実装の過程を見ていないサブエージェントが、差分（または対象範囲）、spec、規則だけを読み、指摘を「必須」と「推奨」に分け、根拠の規則の番号を示す。
- **DC-203** レビュー skill は、書き方の規則の一覧から「人手」の行を自動で抽出してチェックリストにする。plan の完成時に、spec の AC・DC と plan の決定を 1 件ずつ照合する手順を持つ。
- **DC-204** レビュー結果に、各指摘を機械の検査に移したか（移さない場合は理由）を記録する欄がある。
- **DC-205** 文書の言い回しを安定させる手順がある。日本語だけの文脈のサブエージェントに、文書の作成とレビューのどちら（または両方）を任せるかを、試した結果で決める。レビューは、spec・plan・tasks を書き終えたとき（利用者に見せる前）と、spec の最後のレビュー（実装中に変更した設計の文書が対象）で行い、指摘は修正案付きで利用者に示す。
- **DC-206** token の削減を目的に、MCP サーバー（IntelliJ、LSP によるコード参照、ライブラリの最新ドキュメントなど）を試し、導入するかを決める。導入するものは、設定手順が Git にある。開発者の環境に依存するもの（有料の機能を含む IDE など）は任意とし、なくても作業できる。
- **DC-207** AGENTS.md の skill の表が、現在の skill と一致している。

## 5. 業務ルール

なし（本 spec は業務の規則を変えない）。

## 6. 非機能要件

- **DN-21** API の応答、画面、データベースの構造とデータを変えない。
- **DN-22** 文書の言い回しの修正（DS-51）と移動（DS-52）では、意味、番号、節の番号を変えない。移動で生じたリンク切れは、同じ commit で修正する。
- **DN-23** CI 全体が 10 分以内に終わる状態を保つ（spec 011 の DC-85）。CodeQL は別に実行し、この時間に含めない。
- **DN-24** 新しく追加する文書は、それを検査する自動の検査か、レビュー skill のチェックリストの項目と組にする。理由：検査のない文書は、コードと乖離していくため。
